# 新功能接入规范

`rule-services-own-content` 重构（2026-08-31 并入 main）之后，「CMD handler → 业务服务 →
规则服务 → 纯规则」成为强制分层。本文回答一个操作问题：**我要加一个新功能，代码往哪写、
按什么顺序写、在哪接线。**

- 分层的**推导过程**见 [`领域结构重构设计.md`](领域结构重构设计.md)。
- 分层的**权威记载与约束**在仓库根的 `AGENTS.md`（接口后缀分类法、切片边界规则、
  handler 业务语义规则）。本文不重复它们，只在会撞墙的地方指过去。
- 本文是操作清单，不是设计文档。

---

## 一、先定落点：三个问题定一层

写第一行代码之前，把功能拆成几块，每块问一遍：

| 这块代码要做的事 | 落点 | 后缀 |
|---|---|---|
| 读 PVF 档案 / 读游戏规则配置 / 持有表达归档语义的常量 | **规则服务** | `*RuleService` / `*Policy` |
| 读或写世界状态（角色、背包、房间、在线、任务） | **业务服务** | `*DomainService` |
| 既不读内容也不碰状态，输入直接决定输出 | **纯规则** | `*Rules`（静态类） |
| 把连接身份翻成命令、把命令结果翻成帧 | **handler** | `*Handler` |

**这四个不是四选一，是自上而下的一条链。** 一个像样的功能四层都要写一点：

```text
CMD handler          解出身份 → SendAsync → 发帧
  → 业务服务         读写世界状态，编排用例
    → 规则服务       内容 + 传入的 facts + 显式种子 → 值/决定，无状态
      → 纯规则       静态类，纯函数，不碰 I/O
```

### 两条自检，命中即为放错

1. **handler 里注入了 `I*RuleService`** —— 除端点解析 `IChannelEntryPolicy` 外，一律错。
   规则答案要经拥有该用例的业务服务取。
2. **业务服务里注入了 `I*DefinitionSource` / `I*ContentSource` / `I*Catalog`** —— 一律错。
   内容源只被规则服务注入。

重构前第二种形状全仓有 42 处（内容源注入点落在规则服务之外），第一种有 4 处
（Protocol 层越级直调规则服务）。**现在两者都是 0**，`IChannelEntryPolicy` 那 3 处除外。
新代码把它加回来，评审会拦。

两条都可以直接 grep 复核：

```bash
# 应当只剩 3 处 IChannelEntryPolicy
grep -rn "I[A-Za-z]*RuleService\|IChannelEntryPolicy" Server/src/Dfo.Server.Protocol --include=*.cs
# 命中的文件应当个个是 *RuleService.cs
grep -rln "I[A-Za-z]*\(DefinitionSource\|ContentSource\|Catalog\|PoolSource\|TableSource\) " \
  Server/src/Dfo.Server.Application Server/src/Dfo.Server.Protocol --include=*.cs
```

第二条有**唯一一个看起来不像的命中**：`Application/Characters/PlayingCharacter.cs`。
它里面是 `ItemUseJudgementService`，一个与邻居共用文件的规则服务。
不是漏网的，是它该搬个家而一直没搬。

### 反方向的一半

规则服务**不许自己查世界状态**（`领域结构重构设计.md` §6）：不得注入任何
`*Repository` / `*Registry` / `*Directory` / `*Store` / `*DomainService`。它要什么事实，
调用方喂给它。一旦它自己去查，它就成了世界的第二个所有者。

两半合起来才是一条线——上面不许绕过它去够内容，它自己不许往上摸世界。

## 二、固定动作清单

**自下而上写。** 下层先定形，上层才不返工。

### 0. 协议取证先行（新协议才需要）

按 `protocol/README.md` 的模板在
`protocol/<endpoint>/<direction>/<type>-<name>/README.md` 建记录，登记
`protocol/catalog.md`。**布局确认后才可具名字段**，推断要标明是推断。

### 1. 内容源（档案里有本仓还没读过的东西时才需要）

| | |
|---|---|
| 契约 | `Dfo.Server.Abstractions/Content/*.cs` —— 接口 + 它产出的 record |
| 实现 | `Dfo.Server.Infrastructure/Content/Pvf*.cs` |
| 接线 | `InfrastructureModule`：`services.TryAddSingleton<I…Source, Pvf…Source>();` |

档案读法要在 XML doc remarks 里写明出处，**不凭记忆**。读不出来的字段记为未查明，
不要填一个看起来合理的数——`DropRateContent.cs` 里 `RarityLadder` 那段注释是范本：
上游把基数写死成一百万，而档案说是 1000003，于是史诗和远古永远摇不到，
**而且看起来完全正常**。

### 2. 纯规则（静态类）

`Dfo.Server.Application/<领域>/*Rules.cs`，静态类，纯函数，不碰 I/O。
**只由规则服务调用**——它是规则服务的下一层，不是它的替代。

配置值作为**参数**传进来，不要在里面默认一个。参考
`ExperienceBonusRules` 接 `ExperienceEntitlementPolicy` 的形状。

### 3. 规则服务

| | |
|---|---|
| 契约 | `Dfo.Server.Abstractions/<领域>/I*RuleService.cs` |
| 实现 | `Dfo.Server.Application/<领域>/*RuleService.cs`，`internal sealed`，主构造器 DI |
| 接线 | `ApplicationModule`：`services.TryAddSingleton<I…RuleService, …RuleService>();` |

只吃三样：内容源、游戏规则配置、别的规则服务。样板是
`EntryPlacementRuleService(ITownDefinitionSource, ChannelEntryOptions)`——
同时吃 PVF 与配置的最小形状。

**只吃它真正需要的源。** 见第六节第 1 条。

### 4. 业务服务

| | |
|---|---|
| 契约 | `Dfo.Server.Abstractions/<领域>/I*DomainService.cs` |
| 实现 | `Dfo.Server.Application/<领域>/*DomainService.cs` |
| 接线 | `ApplicationModule` |

它是唯一同时看得见世界状态和规则答案的地方。它向规则服务提问时，
**facts 由它准备并传入**。

### 5. 切片

`Dfo.Server.Protocol/<Endpoint>/<Protocol>/` 一个目录，最多六类制品
（`AGENTS.md` 「切片边界规则」有表）：消息 record → payload codec → 入站解包器 →
出站编码器 → 消息 handler → 命令与命令 handler。

**切片内不跨协议引用。** 要共用就上提到 endpoint 层
（`Game/GameProtocol.cs`、`Game/GameDropIdentity.cs`、`Channel/ChannelProtocol.cs`）
或领域服务。

目录名不得与任何被引用类型同名（C# 名称查找里外层命名空间优先，同名会得到 CS0118）。

### 6. 接线：三个 Module，各管各的

| 你新建了什么 | 注册在哪 |
|---|---|
| 内容源 | `InfrastructureModule` |
| 规则服务、业务服务 | `ApplicationModule` |
| 解包器 / 编码器 / 命令 / 消息 handler | `ProtocolModule`（**新协议唯一要改的接线点**） |

`ProtocolModule` 里一个协议对应四类注册行：

```csharp
// 入站解包器：线级键 + 声明它能产出哪些目录成员
services.AddGameCmdMessageDecoder<GetItemDecoder>(
    GameProtocol.GetItemType, ClientMessageType.GameGetItem);
// 消息 handler：目录成员
services.RegisterMessageHandler<GetItemHandler>(ClientMessageType.GameGetItem);
// 命令：ExecutionKind（+ 可选的 onlineUser / account AccessMode，默认 Unscoped）
services.AddCommandHandler<
    PickUpGroundDropCommand, GroundPickupResult, PickUpGroundDropCommandHandler>(
    CommandExecutionKind.Transactional);
// 出站编码器：消息 CLR 类型 + 允许端点
services.AddGameCmdMessageEncoder<GetItemResponse, GetItemResponseEncoder>();
services.AddGameNotiMessageEncoder<GroundPickupNotification, GroundPickupEncoder>();
```

`Dfo.Server.Data/Networking/NetworkMessages.cs` 只加 `ClientMessageType` /
`ServerMessageType` 的**目录成员**，消息 record 不放这里。目录可以先于接线存在。

### 7. 测试三件套

codec 向量 → handler/命令单测 → `Networking.Tests` 线级集成测试。
读档案的用例用 `SkippableFact` 挂 `ContentArchive.Available`。

## 三、走一遍：翻牌子

拿实际的下一个功能当例子。取证在
`.rks-agent/tasks/finishing-and-leaving-a-run/card-reward-evidence.md` 与
`drop-rules-evidence.md`。

### 先说这两份取证已经过时的地方

它们写于 2026-08-29，列了三块「本仓没有、要新建的」。重构与掉落任务之后：

| 取证当时说 | 现在 |
|---|---|
| 「装备掉落池索引……**这是最大的一块**」 | **已有**。`IDropItemPoolSource` / `PvfDropItemPoolSource` 按 `(品级, 稀有度)` 分桶、按 creation rate 加权，装备与堆叠物两侧都在 |
| 「角色金币**既没有落库路径，也没有告诉客户端金币变了的帧**」 | **两半都有了。** 落库路径是 `character_stats.carried_gold`，经 `ICharacter.AddGoldAsync` / `TrySpendGoldAsync` 这个唯一入口进出，携带上限在那里生效；变更通知有两种语言——GET_ITEM 的金币形态带**增量**（客户端累加），NOTI 0x000E 的主背包槽 0 带**总额**（客户端赋值）；翻牌只发后者，地面拾取两者都发，让玩家既看到「捡到多少」又把总额钉死。实机核销：翻牌与拾取当场即变，重登后仍是那个数。见下方「这张表自己踩过的坑」 |
| 「可复现的随机源」 | **已有**。`DropRandom.SeedFor(局seed, 房间, 格子, actor)` |

#### 这张表自己踩过的坑

上面「角色金币」那一行，在 2026-09-02 之前写的是「**已有**。`IAccountMoneyService.AddAsync` +
`GroundGoldPickupNotification`」。**那是错的，而且是后续一连串问题的源头。**

这个游戏有**两笔互不相同的钱**：

- **随身金币**——玩家背包上显示的那个数字。角色级，每个角色各自一份。客户端表示是主背包容器
  （listType=0）的**虚拟槽位 0**，itemId 恒为 0。
- **账号金库金币**——账号级，一个账号下所有角色共用，只有打开账号金库才看得到。客户端表示是
  账号金库容器（listType=12）帧头里、selection key 与 item count 之间的 i32。

客户端有 `DEPOSIT_MONEY` / `WITHDRAW_MONEY` 一对协议专门在两者之间搬钱——**存在搬运协议本身
就证明它们是两笔账**。

当时被认作「角色金币已有」的那个服务，写的是**金库**那一笔。于是翻牌收益、地面捡钱都进了金库，
付费翻牌也从金库扣；而玩家背包上那个数字从来没有人写过，每次登录读出来都是 0。**钱没有丢，
它在金库里躺着，玩家看不到也花不到。**直到玩家在实机上发现金币重登归零才暴露。

那个变更通知帧（`GroundGoldPickupNotification`）本身一直是对的——它确实作用于随身金币，客户端收到后
会把数字加上去。**正因为如此，当时捡钱当场看起来完全正常。**服务端把这笔钱记进了金库，客户端把它加在
随身金币上，两边各自成立，只有下一次登录会揭穿。这是那次事故最难看见的一环。

随身金币已于其后实现，这一栏因此改成了「两半都有了」。**但上面这段留着**：它记的不是缺什么，
而是一种失败的形状——两边各自成立、只有时间差会揭穿。下一次遇到「当场正常、重登不对」，先看这里。

教训不在于「查得不够仔细」——查的时候确实找到了一个真实存在、真的在往客户端发金币的字段。
教训在于：**当一个字段的名字与它的所指不一致时，取证会取到一个看起来完全成立的假结论。**
那个服务的注释当时就声称自己是「客户端显示的钱包」并引了客户端取值器为证；那条引用确有出处，
但描述的是参照服务端修理回包里的金币，那笔钱读的是角色主背包槽 0，与金库无关。

所以这张表往后填「已有」时，判据不是「找到了一个能用的东西」，而是**「玩家能观察到的那个结果
是否真的成立」**。角色金币的判据是：打一把、赚钱、退出、重新登录，那个数字还在。

**翻牌子最大的一块障碍已经不在了。** 更进一步，`DropRateTables.ClearReward` 常量已经声明——
重构时刻意留的钩子。**但它钩住的不是「换一张表」。**

该常量的 XML doc（`Server/src/Dfo.Server.Abstractions/Content/DropRateContent.cs`）
在 2026-09-02 随翻牌落地被改写过一次。改写前说的是「同样的段落，只有 `[drop prob]` 形状不同」，
**「同样的段落」不成立**；现在说的是：

> 不是同一套段落：它的 16 个段标签里，7 个是同族共有的，另外 9 个别的文件一个都没声明。
> 共有的那 7 个里还有一个它写法不同——`[drop prob]` 是「一率一具名 profile」而不是
> 「一带五率」——所以翻牌由 `IClearRewardRateSource` 读，
> 而不是把这个路径交给 `IDropRateTableSource`。

（上面是中译；原文是英文 XML doc。段数与两组段名由
`PvfClearRewardRateSourceTests.Seven_of_this_files_sixteen_sections_are_shared_and_nine_are_declared_nowhere_else`
逐段列名钉住。）

### 逐层要写什么

**内容源** ——
`IClearRewardRateSource`（读 `etc/itemdropinfo_clearreward.etc` 的 profile 形状
`[drop prob]`、`[drop item type prob]`、`[reward item rate per map max count]`）。
**最后这一段不是探索度加成**：它按「这个迷宫一共有几间房」取值，与玩家走了几间无关，
而本服务器根本不记录探索度。它是「房间数 → 基础值」的一张表，A21 只声明 1–5 房五行。
**这张表的 16 个段全部由 `IClearRewardRateSource` 自己读**，包括看起来与怪物表共有的那 7 个
（稀有度阶梯、`[item drop ref table]`、难度/组队加成都在其内）。
**段名共有不等于可以把这个文件交给 `PvfDropRateTableSource`**——交了会抛
（`The_sibling_reader_refuses_this_file_over_a_section_it_read_correctly`）。
**`[item drop ref table]` 尤其借不得**：借怪物表的行会在 **80–89 级多开一个品级、且不报任何错**，
而那正是 A21 的毕业段（`The_grade_bands_share_the_monster_tables_below_column_and_differ_above_at_80_to_89`）。
可以复用的是**抽取**那一层，不是读取这一层——见下面的「纯规则」。
副本自己的 `[result card]` 覆盖声明（1047 个 `.dgn` 里只有 4 个有）**不是翻牌的按副本覆盖，
本服务器不实现它**：那是大会（tournament）玩法的数据。四元组第一位那个 key 档案没说是什么，
**参照服务端**把它填成大会已完成轮数（0..4，优胜另取 5）；总之不是通关评级——
本仓的通关评级是 `RankSystemInfo.etc` 的八档，数目都对不上。大会翻牌走另一对协议
`0x01CA`/`0x01CB`；且那四个副本（120/121/122/4119）一个都没有 `[map specification]`，
正常进本路径根本到不了（`DungeonResultCardDeclarationTests` 钉住这一条）。
真正落在 `IDungeonDefinitionSource` 那一侧的是 `[gold card use]`：五个副本声明 `0`，
读作「这个副本不提供付费牌」（`DungeonDefinition.OffersPaidCard`）。

**纯规则** —— 抽取那一步（掷率 → 掷稀有度 → 品级带 → 桶内加权抽一件）
`DropRules` 已经有了。翻牌只是喂另一张表，能复用就复用；
真正新的只有**几率合成**这一段（`ClearRewardRules.ChanceOf`：房间数基础值 + 难度加成 +
骰子×组队增益，与 `[drop prob]` 所选 profile 的阈值比大小）。
**全局表不按通关评级分概率**——`[drop prob]` 的六个 profile 是按**场合**命名的
（default / event / event2 / pcroom 三个），不是按评级；本服务器只取 `default`，
且启用条件未查明（这六个名字在整份档案里只出现这一处，无从横向对照）。
合成方式、组队乘在骰子上、`[drop prob]` 读作阈值、房间数超表取最大一行、整数比较——
这五条档案一条都没声明，全是本服务器自定，逐条具名写在 `ClearRewardRules` 上。

**规则服务** —— `IClearRewardRuleService`：吃 `IClearRewardRateSource` +
`IDropItemPoolSource` + `IDungeonDefinitionSource` + `ClearRewardRateOptions`，接收 facts
`ClearRewardOccasion(牌型、角色等级、副本基准等级、难度、迷宫房间数、队伍人数)` 与**显式种子**，
产出四个牌位各自的内容。无状态。
**里面没有副本 id，没有评级，也没有探索度**；多出来的是**副本基准等级**（`[basis level]`），
品级带与付费价都按它取而不按角色等级——否则 85 级角色刷 1 级门槛的副本会拿到 85 级装备
并被按 85 级收费。角色等级仍然传，但只用来在 `[drop prob]` 那个 profile 的等级段里取阈值那一档。

**业务服务** —— 牌面内容**在结算时定死并留在服务端**，点击只是揭示与发货。
所以要有一个持有「本局四个牌位翻没翻、里面是什么」的业务服务
（`DungeonRunState` 的邻居），它在 `SET_PLAY_RESULT` 时向规则服务要一次内容并记住，
点击时按位置去重、标记已翻、把内容交出去。

**为什么不能点击时现算**：重连或重放会给出不同的东西。

**切片** —— `Protocol/Game/CardReward/`，三个请求：

| 交换 | 请求 | 应答 |
|---|---|---|
| 卷轴 | `CMD 0x0045`（0B） | `CMD 0x0045 [01]` **加** `CMD 0x0046` 版式（17B） |
| 版式 | `CMD 0x0046`（0B） | 同上那 17B |
| 翻牌 | `CMD 0x0047 [cardType, cardIndex]` | `CMD 0x0047`（33B） |
| 发货 | — | `NOTI 0x000E` 背包变化 |

33B 应答是 8 条记录 × 4 字节起，每条 `a(u8) b(u8) c(u8)` + `c` 个 `(u32 id, u32 count)` 对。
`b` 是**牌位序号**（读法来自寻址结构与 `> 7` 上界，未实测），
`c = 0` 就是这一位不显示内容。上游只给牌位 0 填东西，**那是它的简化不是协议的限制**——
客户端按槽统一读，四张全填是它本来就支持的。

发货用 `GameExplicitMessageDelivery` 把 `0x0047` 应答与 `NOTI 0x000E` 一次发出，
顺序照 `GetItemHandler` 的先例：先应答后通知。

**接线** —— `NetworkMessages.cs` 加**两个**目录成员（`GameCardSelectRightState`、`GameSelectCard`，
两个枚举各加这两个，共四行），`ProtocolModule` 加四类注册行。
命令要触达持久写（东西进背包、金币进账），**必须 `Transactional`**。

### 已定的设计决定

**先只出装备**（2026-08-31，用户决定）。客户端对种类无约束（`setSlot` 全程不问这是装备
还是堆叠物），三样都收得下，但档案与体感都指向装备：副本 144 的
`[drop item type prob] 0 9500 0 500` 是装备 95% / 时装 5%，**没有材料那一支**；

## 四、会挡住你的硬约束

**编译期**

- 项目引用图强制分层。`Application` **永远不能引用 `Protocol`**。任何要同时看到
  「某个具体消息」和「某个领域服务」的代码，只能落在 `Protocol` 里。
- `Persistence` 与 `Infrastructure` 互不引用。
- `TreatWarningsAsErrors`。

**启动期**

- 消息注册表检查**闭合性**：任何已注册解包器声明能产出的消息类型，必须有已注册的
  handler，否则启动即抛。命令注册表**没有**这个检查——未知命令要到 dispatch 时才报错。
- `PersistenceModule` 与 `InfrastructureModule` 必须同时注册，二者并列不可选。

**评审期**

- 规则服务不许持有任何 repository / registry / directory / store / 领域服务。
- **命令处理器禁止嵌套 dispatch**。协议 handler 可以按顺序发多条命令；
  `ICommandHandler` 内部不得再经 `ICommandBus` 派发。要共用就抽成应用服务。
- handler 里只允许四类动作（`AGENTS.md`「handler 业务语义规则」）。

**事务**

- **凡能触达持久写的命令一律 `Transactional`**——只有它会让 `UnitOfWorkBehavior` 开边界，
  没有边界，写会各自落定且无人能收回。
- 一次事务只收**一个** `CommitCanFail` 参与者，第二个在 `Enlist` 时抛。
- SQLite 侧 identity 是连接字符串，**一个数据库一个参与者**——物品、人物、任务是同一个
  参与者的三个面。

## 六、重构里踩过、值得避开的坑

1. **给已有规则服务加一个内容源，会让下游 DI 图变宽。**
   往一个规则服务里塞进第二个源，9 个手搭 DI 图的测试当场红——它们没有理由知道
   这个服务突然还要另一个源。**新规则服务只吃它真正需要的源**；
   要往已有的加，先 grep 谁在手搭它。

2. **不要为了「唯一所有者」硬合并。**
   `EquipmentKind = 1` 现在有三个规则服务各持一份。试过合并：创建角色会因此要求注册
   `IItemPlacementDefinitionSource`，18 个测试红。**同一个归档事实有多个合理归属时，
   耦合的代价可能大于重复的代价**，重复各自写明理由即可。

3. **搬常量要连注释一起搬。** 这个仓库因为「常量搬家时默认值悄悄改变」吃过两次亏
   （经验通告的两个槽、频道比率的来源），**两次都是「看起来完全正常」**。

4. **actor type 的怪物/友军边界现在有三种读法**，`actor type 4` 三处不一致：
   `MonsterExperienceRules.IsMonster` 用 `<= MonsterRank.Boss`（4 不是怪，不给经验）、
   `DungeonRunState.LastHostileActorType = 3`（4 是友军，不挡清房）、
   `DungeonRoomRuleService.FirstAiCharacterActorType = 5`（4 是怪，按怪编号）。
   这是**既有行为**，改它就是改行为。碰到 actor type 先查清你要哪一种。

5. **`using` 顺序**：`System.*` 在前，本仓**不做**字母序。工具批量整理会制造无谓 diff。

6. **业务服务活在 Protocol 里，编译器不会拦。**
   `QuestOfferRefresher` 曾是 `Protocol/Game/Quests/` 下的 `public sealed class`，
   持有一个规则服务和一个领域服务，被五个 handler 注入——它是个跑错了程序集的业务服务，
   而**没有任何一条规则会捕捉到它**，因为它不是 handler。
   新建类型时先问一句：它读写世界状态吗？读的话它就是业务服务，得在 `Application`。
