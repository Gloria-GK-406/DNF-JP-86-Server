# `.vmp1` 个案（三）：装扮栏 `0xC0000005` —— listType 分派、容器选择表与 AV 落点

日期：2026-09-07。转储：`DNFClient-A21-protocol/dumps/dnf-dump-20260906-224825-165-31384/DNF-memory-rva.bin`
（固定基址 `0x00400000`）。承接 [`vmp1-8.md`](vmp1-8.md)、[`vmp1-9.md`](vmp1-9.md)。

新证据（另一 agent 提供）把问题**一分为二**，本篇只处理第二个：

| 场景 | 崩溃码 | 性质 | 归属 |
| --- | --- | --- | --- |
| 主背包 + 42 字节追加块 | `0xC0000409` | `/GS` 栈溢出 | `vmp1-9.md` 的 `rec+0x2F` `rep movsd`（已用 H1 验证）|
| **装扮栏非空（任意内容/容量）** | `0xC0000005` | **访问违例** | **本篇**|

装扮栏帧字节已确认干净（`param=483, count=1, rec` 全字段正常，`rec+0x1A`=0、`rec+0x2F`=0），
所以 AV **与数据无关**、与 `rep movsd` 无关。是 `0x0117C670`（`NOTI_ITEM_LIST`, type 0x0D）里
**另一条代码路径本身**的问题。

---

## 一、纠正方向：被当指针解引用的不是"记录字段"，是**容器**（已核实）

`0x0117C670` 的循环体（`0x0117CC22..0x0117D649`）对**所有 listType 共用**，逐条记录做：

```
edx = (i16) rec+0x00                         ; SlotIndex           0117D35B movsx edx,word[ebp-0x17c]
edi = container                              ; = [ebp-0x184]       0117D362 mov edi,[ebp-0x184]
esi = findItemBySlot(edi, SlotIndex)         ; 0117D369 call 0x16EE6C0   ← 【第一处 deref 容器】
if (esi != 0)  更新既有物品（虚调 [esi]+0x5c / [esi]+0x40）
else {                                       ; 0117D3A5
    item = createItem(...字段...)            ; 0117D462 call 0x1A85220（ItemFactory::createItem）
    setItemAt(edi, SlotIndex, item, 1, 0)    ; 0117D489 call 0x16F2FB0   ← 【第二处 deref 容器】
}
```

`0x16EE6C0`（findItemBySlot）与 `0x16F2FB0`（setItemAt）**入口第一件事就是取容器的内部集合
`[container+0x44]`**，再按低半字节做变体分派：

```
016EE6C7  lea ecx, [esi + 0x44]     ; findItemBySlot: 集合 = *(this+0x44)
016EE6CA  mov edx, ecx / and edx,0xF / cmp 0xC / jmp [edx*4 + 表]
016F2FB7  lea ecx, [ebx + 0x44]     ; setItemAt: 同一个集合
```

> **结论（已核实结构 + 推断因果）**：记录里没有任何字段被当指针解引用；被解引用的是
> **`container` 与 `container+0x44` 的物品集合**。`count=0` 时循环体一次都不进 → 不碰
> `container+0x44` → 不崩；`count>0` 时第一条记录立刻在 `0x0117D362 → 0x16EE6C0` 取
> `[container+0x44]`。**这解释了"空不崩、非空必崩、与内容/容量无关"的全部现象。**

## 二、listType 如何选容器（已核实：`0x1648AC0` 全表）

`0x0117C670` 的 listType = **NOTI 体首字节** `[ebp-0x17d]`（`0117C6C2` 读入 1 字节）。
容器由 `0x1648AC0(listType)` 选出并写入 `[ebp-0x184]`（`0117C93E..0117C94B`）。该函数是一张
**listType → 全局容器指针**的表：

| listType | 容器来源 | 语义（推断） |
| --- | --- | --- |
| `0`, `0x1D` | `*[0x3A5C9BC]`（默认，`0x1648B8B`）| 主背包 |
| **`1`** | **`*[0x3A5C9D0]`** | **装扮栏 / avatar（本案）** |
| `2` | `*[0x3A5C9C0]` | |
| `0xC` | `*[0x3A5C9C4]` | |
| `4` | `0x1705330(*[0x3A5C9E8],0)` | （经函数取，非裸全局）|
| `7` | `*[0x3A5C9D4]` | |
| `0xB` | `*[0x3A5C9CC]` / `0x26`→`*[0x3A5C9D8]` / `0x1C`→`*[0x3A5C9E0]` / `0x20`→`*[0x3A5C9DC]` | |
| `0x12..0x16` | `0x1648B82` 分支 | |

listType `1` 之外，还有 `0x27/0x28/0x29` 三个**特殊支路**（`0117C95A/0117CA06/0117CAB2`），
它们不走 `0x1648AC0`，而是 `getMyCharacter`(`0x19E3290`) → `0x19DAC30` → `0x551640` →
`0x1833E70/0x1833EA0/0x1833DE0` 取角色身上的容器（穿戴/avatar 装备）。**这三条支路每一步都有
`je 0x117D695` 空指针兜底**，因此空指针不会崩——和 listType 1 一样，崩只可能发生在**容器非空、
但其 `+0x44` 集合无效**时。

> 请另一 agent 用干净帧确认 listType 字节（NOTI 0x0D 体首字节）：
> - 若 = `1` → 容器 = `*[0x3A5C9D0]`，AV 在 `0x0117D362 → 0x16EE6C0` 取 `[*[0x3A5C9D0]+0x44]`；
> - 若 ∈ `{0x27,0x28,0x29}` → 装扮是"角色穿戴"路径，容器来自 `getMyCharacter` 链，AV 同样在
>   循环内 `0x16EE6C0`/`0x16F2FB0` 取 `[容器+0x44]`。

## 三、为什么"从没兜过底"（已核实控制流）

- listType `1` 的**预循环**分支 `0x0117C86A`（`cmp [ebp-0x17d],1; jne` 不成立时执行）与
  listType `0` 的分支 `0x0117C74D` 各建了一个 `new(0x98)` 的临时对象、用不同的 setup 调用
  （type0 用 `0x15BA9B0`，type1 用 `0x15B9300`）后**当场释放**——它们是作用域内的
  日志/通知对象，**都不初始化容器的 `+0x44` 集合**。容器的 `+0x44` 初始化发生在别处
  （库存对象创建时）。
- 主背包（type 0）容器 `*[0x3A5C9BC]` 客户端全程在用，`+0x44` 一定就绪；**装扮栏容器
  `*[0x3A5C9D0]` 在参照会话里始终收到空帧（count=0），这条"非空装填"路径从未执行**，
  所以它的 `+0x44` 是否就绪从未被任何实机字节验证过。这正是另一 agent 的判断，本篇把它
  精确到了 `container+0x44` 这个成员与 `0x16EE6C0`/`0x16F2FB0` 两个 deref 点。

> 静态取不到根因的最后一跳：`*[0x3A5C9D0]` 及 `[*[0x3A5C9D0]+0x44]` 是**运行期**状态，
> 本转储里这些全局为 0（库存尚未装填）。到底是 `*[0x3A5C9D0]` 本身为野指针、还是它非空但
> `+0x44` 集合未建，只能在 AV 现场读这两个值定夺——见下。

## 四、给另一 agent 的精确断点（绕开 WOW64 SEH 干扰）

你三次抓转储都被 attach 干扰 SEH、`c0000005` 被转成二次 `c00001a5`、EIP 落进 wow64.dll。
下面的断点在**AV 发生之前**触发，直接读出被解引用的容器与地址，不依赖抓到二次异常现场：

1. **`0x0117D362`**（`mov edi,[ebp-0x184]`）——命中时读 `edi`(=容器) 与 `edx`(=SlotIndex)。
   - `edi==0`？理论上前面 `0117CBAA` 已兜底，不该到这；若真为 0，是兜底被绕过。
   - `edi!=0`：读 `dword[edi+0x44]`（集合指针/内联头）。若它是野值/不可读地址，就是根因。
2. **`0x16EE6C0`** 入口（`ecx`=容器）——`dd ecx+0x44 L4`；再看 `0x16EE6CA` 之后按
   `(ecx+0x44)&0xF` 跳的分支目标是否落进有效 case。
3. 若第 1 步 `edi` 就是野值 → 回到容器来源：断 `0x0117C94B`（`mov [ebp-0x184],eax`，
   `eax=0x1648AC0(listType)` 的返回）或直接 `dd 0x3A5C9D0 L1`，确认 `*[0x3A5C9D0]` 是不是
   一个未完成构造的对象（读它的 vtbl `dword[*[0x3A5C9D0]]` 是否在 `.rdata` 合法区间）。

这三点任取其一即可把"野指针 vs +0x44 未建"二选一定死。修法随之而定：
- 若 `*[0x3A5C9D0]` 为空/野 → 客户端在收此 NOTI 前未创建装扮栏库存：服务器侧**不要对装扮栏
  发送非空 ITEM_LIST(type=1)**，或客户端补一个 `if(!container) return;`（其实 `0117CBAA` 已有，
  说明问题在"非空但未初始化"，更可能是下一条）。
- 若 `*[0x3A5C9D0]` 非空但 `+0x44` 未建 → 客户端装扮栏库存对象漏了集合初始化：这是**客户端
  bug**，服务器侧只能规避（避免走 type=1 装填路径，改用角色穿戴路径或延迟到库存就绪后再发）。

## 五、与主背包线的关系（收口建议）

两件事可并行：

1. **主背包线（`vmp1-9.md`）已可收口**：H1 证实定长 101 不崩，珠宝正确位置是 `rec+0x1A` 内嵌
   子数组而非尾部 42 字节追加。服务器侧"去掉 42 字节追加块 + 按 `vmp1-9` 表把珠宝走 `rec+0x1A`"
   可以正经做成 SDD 任务——**赞成**，它与装扮栏 AV 是两个独立根因、两套改动。
2. **装扮栏线**在断点定死"野指针 vs +0x44 未建"之前，先**不要**在服务器侧动 type=1 装填路径；
   等现场结论再决定是规避（服务器）还是补初始化（客户端）。
