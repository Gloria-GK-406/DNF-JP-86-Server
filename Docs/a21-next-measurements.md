### 0.3 `.text` 里有 2.25 MB 根本不是任何 TU 的代码——`.text$x`

```
_x8.py:  EH thunk 22,892 个，连续分布 02CAA5C1..02EE8E3B，段内 >4KB 的空洞只有 5 个
         => .text$x 带 = 0x02CAA000..0x02EE9000，2.25 MB，占 .text 的 5.1%
         全部 22,892 个 thunk 都 jmp 到同一个目标 0x02C6249C（__CxxFrameHandler）

这是 MSVC 把 `__ehhandler$` thunk 放进 `.text$x` COMDAT 组、链接器统一排在 `.text` 尾部的结果。

`.text` 的真实预算（`_x8.py`）：

| 区间 | 范围 | 大小 | functions.csv 行数 |
| --- | --- | ---: | ---: |
| 游戏代码 | `0x00401000`–`0x02C00000` | 40.00 MB | 65,562 |
| CRT / 加载器 | `0x02C00000`–`0x02CAA000` | 0.66 MB | 1,495 |
| **`.text$x` EH thunk** | `0x02CAA000`–`0x02EE9000` | **2.25 MB** | **17** |
| 未枚举尾部 | `0x02EE9000`–`0x03029000` | 1.25 MB | **0** |

## P0 — 用 C++ EH 前导重建函数入口清单（最高优先级，纯脚本）

**要测什么：** `.text` 里真正的函数入口。

**新增的 oracle（本次发现，上一轮判死过）：**
x86 MSVC 的 C++ EH 在函数前导里长这样：

```
55 8B EC              push ebp ; mov ebp,esp
...
68 <thunk>            push  offset __ehhandler$...      <- thunk 落在 .text$x
64 A1 00 00 00 00     mov   eax, fs:[0]
```
thunk 体尾部是 `B8 <FuncInfo> E9 <__CxxFrameHandler>`，FuncInfo 带 magic `0x1993052x`。

```
_x1.py / _x4.py / _x5.py:
  .code 里对齐的 0x1993052x magic                     23,229（结构自洽的 22,880 个，
                                                       全在 0x03768E2C..0x03959F64）
  'push <thunk> ; mov eax,fs:[0]' 现场                37,536   其中游戏区(<0x02C00000) 35,500
  thunk 100% 能在 0x60 字节内解析到 FuncInfo          37,536 / 37,536
  回退 16 字节找到 55 8B EC 的                        37,510 (99.93%)
  ——恢复出的入口                                     37,510
      已经是 functions.csv 条目的                     25,747 (68.6%)
      functions.csv 里没有的新入口                    11,763
      前一字节是 0xCC 的                              35,353 (94.2%)
      新入口里前一字节是 0xCC 的                      11,066 (94.1%)
```

**为什么这条比之前所有 oracle 都好：** 它不依赖调用边。`E8` 目标法看不见只从注册表间接调用的函数，
vtable 法只覆盖虚函数，而 EH 前导覆盖**任何用了 try/析构的函数**，并且自带 99.93% 的
`55 8B EC` 自校验和 94% 的 `int3` 对齐佐证。68.6% 与现有清单一致，说明它不是在乱认。

**它同时量化了 blob 损伤：**
```
_x5.py:  functions.csv 里含 >=2 个恢复入口的行        4,272
         单行里最多塞了多少个真入口                    1,650   (0x02DF3903)
         次坏的几行  0x02C05678:113  0x02C28E5C:87  0x027E50C0:63  0x00EDD440:57
```

**并且它证明 ground truth 本身是错位的：**
```
_x5.py:  759 个 __FILE__ 锚点里，所在 functions.csv 行含 >1 个真入口的：130 (17.1%)
```
proto-5 抓到过 1 例（`0x0110C2C0` 被误标 `CMD_Etc.cpp`）。**实际是 130 例。**
换句话说 17% 的"确定档"锚点标的是 blob，不是那个真正 push 了 `__FILE__` 的函数。

**命令：**
```
cd SCRATCH && set PYTHONIOENCODING=utf-8
python _x5.py                # 产出 _x5_eh_entries.txt（37,510 个入口，已落盘）
python _x9.py                # 与注册表 oracle 求并集
```
**已跑出的并集：**
```
functions.csv                67,074
EH 前导入口                  37,510   新增 11,763
注册表/工厂 handler（12 张表合并） 1,394   新增 1,389（其中 1,236 个 int3+prologue 双确认）
并集                         79,780   比 functions.csv 多 19%
新增的 12,706 个里 int3+55 8B EC 双确认：11,883 (93.5%)
```

**验收判据（先写死）：** 重建后的清单必须满足
(a) 37,510 个 EH 入口全在里面；
(b) 1,394 个注册 handler 里 int3+prologue 双确认的 1,236 个全在里面；
(c) `.text$x` 带 `0x02CAA000`–`0x02EE9000` **整段标为 non-TU**，不参与任何源文件归属；
(d) 没有任何条目内部还含 ≥2 个 EH 入口。
现状分别是 25,747/37,510、5/1,394、未标、4,272 条违规。

**还要补的：** 用 capstone 从每个入口线性走到终结，重算真实 `span_bytes`，重建 `callgraph.csv`
（现在的边是 blob→blob）。FuncInfo 的 unwind map 给了 **120,526 个 `.text` 内部地址**
（`_x2.py`；其中只有 1 个是 functions.csv 条目），那些是析构 funclet，**不是入口，但能给函数体定上界**——
一个 funclet 属于哪个函数是确定的，可以直接用来切开被合并的 blob。

## P3 — 字面量池坐标（保留，但把它的实际能力说准）

上一版把这条排 P1 并写"一条 99.2% 精度的规则，直接把覆盖率翻倍"。我复核了：**坐标是真的，
精度被高估了，召回被高估得更多。**

**坐标本身成立（复现）：**
```
_x6.py:  code_va 与 __FILE__ 字面量 VA 的相邻逆序：1 / 753 = 0.13%
```
MSVC 每个 .obj 的字符串常量按链接顺序连续排布，和代码块顺序一致。这条是硬的。

**但 99.2% 是自证的。** `_nm_dual.py` 的自测把函数**自己的 `__FILE__` 字面量**留在输入里，
而那个字面量就是地标本身——命中自己的区间是构造上必然的。留一法：

```
_x7.py:
  A 原样（保留自己的 __FILE__ 字面量）   correct=514 wrong=4  undecided=241  精度 99.2%
  B 留一法（去掉自己的 __FILE__ 字面量） correct=513 wrong=15 undecided=231  精度 97.2%
```
**规则活下来了，97.2%，但要写 97.2 不是 99.2。**

**真正的问题是召回，而它是结构性的：**
```
_x7.py:  规则对 8,798 个带字面量的函数弃权 1,958 个（22%）
         能判的 6,840 / 67,074 = 10.2%   <- 这就是天花板
  字符串池化把一个函数的字面量摊开：
         >=3 条字面量的函数，字面量 VA 跨度 p50=1,192  p75=967,016  p90=4,075,964 字节
         而地标区间中位数只有 4,256 字节
```
四分之一的函数其字面量横跨约 1000 个地标区间——精度是靠"跨区间就弃权"换来的。
另外这条规则**只能吐出 345 个有地标的文件名之一**，对没有 `__FILE__` 的 TU 无能为力
（`_x7.py` C 组：抽掉某文件的地标后，该文件的函数 609 个全判错——这是构造上必然，
不是反驳，但它精确说明了边界在哪）。

**结论：保留为交叉验证与补洞手段，不要当主干。** 且必须在 P0 之后重跑：现在 `literals.csv`
的 `func_va` 是 blob 级的，8,798 这个分母会显著变大。

```
cd SCRATCH && python _nm_order.py && python _nm_dual.py && python _x7.py
```

## P4 — vtable 聚类（不需要类名）

```
（上一轮 _nm_yield3.py，本次未重跑）
  vtable 槽位指向 .text 的目标  14,184
  被恰好一张 vtable 引用的      12,796 (90.2%)
```
一个类的虚函数几乎总在同一个 .cpp 里，所以每张 vtable 就是一个 TU 内部的成员簇，哪怕它没名字。

`rtti-vtables.csv` 里还有一样上一轮没用的东西：**基类链**（`TD#540e|TD#02|TD#03|…`）。
5,407 行里 5,013 行类名是 `TD#xxxx` 占位符，但**占位符照样是同一性标记**——
共享同一个基类 TD 的一组派生类通常落在相邻目录/文件里。这是没花过的一层。

```
cd SCRATCH && python _nm_yield3.py

## 明确不要重复上一轮的哪些做法

1. **不要再按地址等分切区，也不要按任何固定大小切区。** 这是 49/55 被推翻的直接原因。
   正确的切分单位是 TU；在 P0 交付前，连"函数"这个单位都还不成立。

2. **不要在 `functions.csv` 上做任何统计推断。** 它是 `.text` 的一个分区（0/67,073 例外），
   `span_bytes`/`in_degree`/`parser_calls` 全是 blob 级的。单行最多吞了 1,650 个真入口。

3. **不要再用"最近的前一个锚点"填充归属。** 那把覆盖率从 ~10% 虚报到 97.6%，
   也是"55% 已归属"这个数字最可能的来源——该数字我和上一版都复现不出来。

4. **不要用 PE 数据目录去判断"有没有异常表"。** 这是上一轮唯一一条**方法错误导致漏掉大鱼**的判死：
   目录确实是空的，但 x86 MSVC 的 C++ EH 数据从来不在那里。代价是 22,880 个 FuncInfo、
   37,510 个函数入口被晾了一轮。同类教训：**否定一个来源之前，先确认自己测的是那个来源的实际表示形式。**

5. **不要把自测当验证。** `_nm_dual.py` 的 99.2% 是把答案留在输入里测出来的；留一法是 97.2%，

6. **不要为了覆盖率派 agent。** 上一轮 6,250,368 subagent tokens / 2,223 次工具调用 / 2 小时，

   **agent 只该花在"两个候选切点都说得通、要人来判"的地方**，而那种情况在 P0 交付前根本还没出现。

7. **不要再假设高频前缀有区分力。** `DNFClient\RDAR`（479/479 条路径）、`.xui` 的 `UI/`（91%）
   都是无差别前缀。用任何前缀前先算基准率——`.xui` 第二段（冲突率 1%）才是能用的那一层。

8. **不要再对 `.vmp1` 派定向问题。** 上一轮 8 个全失败；vmp1-0/1/6/7 已定死：VMProtect 系、

   （加 `fs:` 建模 34.9%）。**这是能力边界，不是没努力。**

9. **保留"返回前先写盘"。** 上一轮 13 个 agent 的返回值被 API 吃掉、靠文件救回，成本几乎为零。
