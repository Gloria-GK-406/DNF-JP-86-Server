# 领域结构重构设计

**这份文档记录的是重构意图，不是已验证的结论。** 结构主张来自 2026-08-17 的设计讨论，
其中有出处的部分标了出处，没有出处的部分标成待决。后续按本文档动手，动完之后按第 14 节的
标准判断这个结构是不是真的更好；判断不通过就停，代价被限定在一个切片里。

## 1. 为什么改：现有痛点及其出处

不是审美问题，四条都有具体出处。

| 痛点 | 出处 |
|---|---|
| **身份类型把三件事焊在一起** | `SelectedSessionIdentity` 是六元组：`AccountId` + `CharacterId` + `NetworkConnectionId` + `ConnectionGeneration` + `WireUserId` + `ListenerPort`。每个服务收这一整包，没有服务能只用"角色"表达，永远拖着连接 |
| **陈旧性检查遍地** | `SelectCharacterHandler` 里 `EnsureCurrent` 调用 12 次，每个 await 之后一次 |
| **锁的粒度表达不了队伍** | `SelectedSessionTransitionGate : UserExecutionGate<AccountId>`，键在账号。而副本入场的真正单位是队伍，跨账号 |
| **一个类扛三个接口**（已于 2026-08-18 解决） | 当时是 `UserService : IAccountService, IOnlineUserService, IActiveCharacterService`，内含一把锁与三个字典 |

反面也要记下：它能跑，619 个测试兜着，2026-08-17 一天里五次修复都是从它里面穿过去的，
**没有一次是被它挡住**。所以本文档不主张大爆炸式重写，见第 14 节。

## 2. 核心分界：规则服务 vs 领域聚合

现在被统称为"领域服务"的东西其实是两类，其中一类根本不是领域服务。

| | 规则服务 | 领域聚合 |
|---|---|---|
| 输入 | 内容（PVF）+ facts + **显式种子** | 命令 |
| 输出 | 值 / 给客户端的指导指令 | 状态变更 |
| 有身份、生命周期吗 | **没有** | 有 |
| 记录什么 | 什么规则、怎么算 | 游戏世界当前是什么、正在怎么变 |
| 例子 | 如何创建地下城、能否领取任务、能否进入地下城 | 角色、队伍、地下城实例 |

**规则服务在这条线上面，聚合在下面。这条线就是"游戏外"与"游戏内"的分界。**
唯一的接触点是：**规则的产出成为聚合状态**——迷宫布局与种子由规则算出，写进地下城实例。

这一点不能划错成"创建地下城是外部行为、所以无状态"。它只对了一半：客户端要知道布局，
**服务端也必须记住**，因为客户端之后会拿这个布局上报事件（"我在某房间打死了 boss"）。

## 3. 拆分判据

拆多少个服务不是问题，判据只有一条：

> **这块状态参不参与别的聚合的不变量？参与 → 放在那个聚合里面；不参与 → 自己一个服务。**

按它检验：

| 状态 | 参与谁的不变量 | 判定 |
|---|---|---|
| 属性、技能 | 角色自身 | 角色聚合内 |
| **已装备的那一套** | **角色的派生属性** | **角色聚合内，不拆** |
| 背包（未装备物品） | 不影响派生值 | 独立服务 |
| 快捷栏、技能快捷键 | 不影响任何派生值，已是独立帧、独立表 | 独立服务 |
| 邮箱 | 独立 | 独立服务 |
| 仓库 | 独立 | 独立服务，**键在账号不在角色** |
| 角色口袋 | 未确认是角色级还是账号级 | **待决**，见第 15 节 |

两条有出处的约束：

- **装备不能拆出去**：属性帧同一帧里同时携带已装备物品与属性，两份必须一致——
  见 `DungeonSelectionSlice.cs` 里那句注释「the stat frame carries the equipped items
  alongside the stats and the two copies have to agree」。装备一旦是独立聚合，
  "角色属性"就跨两个聚合，而不一致会直接以帧的形式发出去。
- **仓库键在账号**：现有代码已经是 `AccountCargoEntryState(accountId, …)`。
  按角色凭证取会把它建错。

## 4. 聚合与服务清单

```text
规则服务（无状态，不查世界）
  地下城布局规则      内容 + 种子 → 迷宫选择、出生点、boss 点
  角色创建规则        职业表 → 初始属性（已实现：PvfCharacterStatDefinitionSource）
  任务领取规则        facts → 能不能领
  入场资格规则        facts → 能不能进
──────────────────────────────────────────────────────
在线表              账号 → (角色, session)，一账号一角色
角色聚合            属性 + 技能 + 已装备的一套 + 任务进度，带版本
队伍聚合            成员、入图能力、租约
地下城实例          布局（规则产出）+ 房间进度
独立服务            背包 / 快捷栏 / 邮箱 / 仓库(账号键)
──────────────────────────────────────────────────────
投影器              聚合状态 + 阶段 → 帧集合
```

## 5. 在线表与账号边界

**角色持有 session，不是 session 持有角色。** 在线表记录当前在线的全部角色及其 session；
session 记在这里只为一件事：**顶掉同账号已开的那个**。

规则：**一个账号在本服务里只能有一个登录的角色。**

这套结构已经在代码里了，只是埋在 `UserService` 的私有字段里、和 online-user 混在一处：

```csharp
Dictionary<AccountId, ActiveCharacterRegistration> activeByAccount;
record ActiveCharacterRegistration(OnlineUserId, SelectedSessionIdentity? Session, ActiveCharacterState Character);
```

所以本节是**给已有结构正名**，不是新增不变量。

顶号那一步同样已实现，而且比"断开旧 session"更细，重构时要吸收而不是重新推导：
`RegisterReplacing` 返回被顶掉的 session；同账号旧 session 用 `includeOwner: true` 清理、
被顶掉的用 `false`；同区域其他玩家收 `TownDeparture`；连接**在迁移完成后才关**；
先清旧的再发布新的，否则目录里会同时存在两个。

**账号是边界概念**——外部不可信的名字在那里换成内部身份，过了边界只谈角色。
（现状：登录 `m_id` 未经任何认证，`ON CONFLICT(m_id) DO NOTHING` 之后并不比对第二个串。
认证若要做，只该落在这一个边界点上。）

## 6. 规则服务的约束：接收 facts，不查状态

**规则不许自己查世界状态，只能被喂。** 否则它成为世界的第二个所有者，
本次重构要拆掉的耦合会从这里长回来。

判据的必要性来自这三条不是同一种东西：

| 规则 | 需要世界状态吗 |
|---|---|
| 如何创建地下城 | 不需要（内容 + 种子），纯函数 |
| 能否领取任务 | 需要角色状态 |
| 能否进入地下城 | 需要角色 + 队伍 + 任务 + 内容 |

后两条必须把状态当**参数**接收，由聚合或用例负责收集。两边都有先例：
我们的 `EquipmentEligibilityCharacterFacts`；上游的
`EvaluateDungeonAdmission(dungeonId, activeQuestIds, clearedQuestIds)`。

**显式种子**是同一条约束的延伸：随机不能来自环境里的 `Random`，否则规则既不可测、
也没法把同一份布局重放出来。上游的 `run.Seed` 是随运行存在、并且要发给客户端的。

## 7. 寿命规则：本作没有重连

游戏行为（2026-08-17 由项目所有者确认）：

- 在图中掉线 → 下次登录在城里 + **虚弱状态**，不存在重连
- 建了队掉线 → 上线是无队状态，队伍已消失

由此：

| 对象 | 寿命 |
|---|---|
| 地下城实例 | 没有关联的人 → 销毁；通关/退出 → 销毁。**不需要宽限期** |
| 队伍 | 全员退队/离线 → 自动销毁 |
| 队伍与实例的关系 | 队伍**可以**拥有实例（不需要按 id 弱引用） |

### 现有的重连机制是死件，应删（已于 2026-08-18 删除）

`IDungeonRejoinRegistry` / `DungeonAttachment` / `ResolveRejoin` / `DungeonRejoinStateMessage`
/ `PlanSelectedCharacterRejoinCommand` 是从上游转录来的，**从未被填过也从未被发过**：

- 没有任何地方调用 `Attach`（只有 `ReleaseAttachmentExact`），所以
  `rejoin.Find(characterId)` 恒为 null，`ResolveRejoin` 只可能返回 `NoOffer`——
  底下 `IdentityMismatch` / `NotDetached` / `PartyUnavailable` / `Expired` / `Available`
  整棵决策树不可达
- 那一帧压在 `SendsFramesAfterTheCompletionMarker` 之下，生产用 `ReferenceSequence`（false）

留着它，新写的运行聚合会面对一个"看起来支持重连"的现有接口，而它什么都不支持。

## 8. 掉线 = 按失败结算

掉线不是"保住那一局等人回来"，是**把那一局按失败结算**，并且这个后果要持久化。

虚弱有已知的协议表达（2026-08-17 定出）：`0x0002` subtype 1 偏移 95 的当前血量百分比
+ `0x01E8 CHARACTER_ADD_BUFF` + `0x01E9` + `0x0088 CHANGE_HP`。

落点也是现成的：会话清理时已经在写位置（`PersistPositionAsync`），虚弱只是同一次写入里
多两个值。

因此运行聚合需要一个显式的**「放弃」迁移**（带持久化后果），而不是"清理时把对象删掉"。

## 9. 持久化：聚合不自己落库

**反对"角色实体内部决定如何持久化"**，理由是事务而不是风格。

现状：没有跨仓储的事务接缝。每个仓储方法自己开 `SqliteConnection`、自己开事务
（12 处 `BeginTransactionAsync`，各自独立）。所以"一个仓储方法 = 一个事务"，
多行不变量只有写在同一个方法里才成立。

这个代价已经付过一次：建角色只写了 `characters` 一行，而入场 profile 查询对
`character_subtype0_fields`、`character_subtype1_fields`、`character_init_flags`
做 INNER JOIN —— **建出来的角色进不去游戏**，修法是把四行写进同一个事务。

若实体自己持久化，同一个用例里对同一个角色的两处改动就没法原子。

**保留写法，搬走决定权**：

```text
角色.领取任务(任务)     → 在内存里改聚合并记下变更
仓储/工作单元.提交(角色) → 一个事务里写完所有受影响的行
```

调用点读起来仍是 `角色.领取任务(任务)`，而持久化留在能跨行、能持事务的那一层。

## 10. 并发：一次守卫提交，不是每个 await 一次

读出**带版本**的聚合 → 改 → **带版本校验提交**。

这样做的理由不是风格，是让并发机制统一：它和队伍租约、运行的 generation 守卫是同一个机制，
否则会有三套不同写法。

**队伍租约**是那把缺失的锁：队伍服务发租约（`AcquireAsync` 返回 lease 已是本库词汇），
等于把队伍粒度的锁变成领域概念（"持有队伍来决定入图"）而不是基础设施细节。

入图是聚合上的原子迁移：

```text
Idle → Entering → InDungeon → Settling → Idle
```

`Entering` 期间拒绝队员移动、队伍变更、队员入图请求。"所有队员在同一区域"在**迁移内部**
校验，检查-使用竞态因此消失。

### 为什么上游需要那么多检查点，而我们不需要照抄

上游的跨账号冲突有明确成因：**它把入图能力给了每个队员**——入场 handler 里除了
fan-out 那一处 `IsLeader`，没有任何地方拒绝非队长。队员自己发 `0x0010` 会给自己开一局，
队长 fan-out 又会给同一个队员开一局，两个写者。`IsRunSlotUnchanged(bs, …) → continue`
就是在处理这个竞态。

而上游**没有覆盖 handler 的锁**（只有 `Interlocked`/`Volatile` 的计数器和只圈住槽位交换
那一瞬的 `SyncRoot`），所以那些检查点就是它的并发机制本身，位置是"每个对外可见的效果之前
一次"。

**入图能力只给队长，冲突的成因就没了**，剩下的（队员掉线、队员移动、队伍变更）全都变成
同一个聚合的改写，一把队伍粒度的锁就能序列化。

## 11. 出帧：投影器，而不是"改了就发"

目标是"不用自己发回包"，但**不能用变更追踪实现**。四条反证：

| 事实 | 为什么"改了就发"表达不了 |
|---|---|
| `0x007C` 是闸点，之后多发**必崩**、少发无害 | 该发什么取决于**阶段**，不取决于哪个字段变了 |
| 换区要 `0x0017` **然后** `0x0018` | 协议级配对，不是"位置变了" |
| `0x000F` 要重发一遍 `0x0002`，属性一个字节没变 | 变更追踪会把它省掉，而省掉的后果是空血 |
| 持久化的 town/area/pos 不告诉客户端 | 有些改动就是不该发 |

正确形状：

```text
用例 → 产出状态（不发帧）→ 投影器（阶段作为显式入参）→ 帧集合 → 发送
```

这样"不用手搓回包"达到了，而帧的顺序与集合住在投影器里、按阶段索引。

已有一处先例：`SelectedCharacterStateMessageFactory` 收 `SelectCharacterResult`、
产出 58 帧的既定顺序。问题是它只有这一处——`EnterSelectDungeonHandler` 的五条、
`SetUserAreaHandler` 的两条都是 handler 里手搓的。重构目标是让投影器成为常态。

## 13. 单人 = 一人队

聚合永远存在，成员数为 1 是常态而不是特例。

单人队与"单人未建队"的差别是**协议差异**（能否在队伍列表里被看到），
不是执行差异——所以"是否发布到队伍列表"是聚合上的一个标志，而不是两种代码路径。

这条让"不推迟所有权建模"变得便宜：教程那一刀走的就是真正的聚合，
不是一个日后会被重写的特例。

## 14. 可否证的验证标准

不靠审美判断这个结构是否更好，靠一刀的结果：

> 副本入场按新形状写完后，如果它**不需要 per-await 的陈旧性检查**，并且在后续加入组队时
> 也没有长出来，形状即算验证通过，往后按第 12 节增量吸收。
> 如果它照样长出自己的一套检查点，说明形状没买到东西——**停**，代价只是这一刀。

## 16. 修订记录

**2026-08-17 初稿。** 结构主张由项目所有者提出，本文档记录并补充出处。

过程中作废的两处判断，记下来以免重走：

1. **我曾主张"实例必须活得比最后一个参与者久、队伍不能拥有实例、需要宽限期"**，
   依据是代码里的重连机制（`DungeonAttachment` 的 `IdleExpiresAt`/`HardExpiresAt`）。
   **作废**——本作没有重连，那套机制是从未被填过的转录死件。
   *教训*：从代码里的机制反推游戏行为不可靠；机制可能是抄来的空转件。
2. **我曾把上游的并发检查归因为"防挤号"。** 作废——真正的成因是它把入图能力给了每个队员，
   导致跨账号双写者。
   *教训*：解释一段防御性代码之前，先找出它防的那个写者是谁。
