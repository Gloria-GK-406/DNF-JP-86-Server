# 跨模块修正点：双 dump 差分测定

更新时间：2026-08-21（第二轮：加入模块表后修订）

## 结论摘要

`runnable-rebuild-phase3.md` 记录的「保护器把大量 DLL 绝对地址内联写进客户端代码/数据，
近 900 处，级联长尾」这一判断**不成立**。用两份不同启动时刻采集的 dump 做差分测定，
整个跨模块引用面是 **469 个站点**，其中 **357 个已被现有枚举表覆盖**，
真正未覆盖的只有 **112 个**。

关键性质：**37.5 MB 的 `.text` 里一个站点都没有。原始客户端代码完全干净。**
全部站点集中在壳自己的节和 IAT 区域。

## 方法

两份 dump 取自不同启动，KnownDLL 基址不同：

| 模块 | dump A (08-14) | dump B (08-19) | delta |
| --- | --- | --- | ---: |
| kernel32 | `0x75EE0000` | `0x75680000` | `+0x860000` |
| ws2_32 | `0x77960000` | `0x764D0000` | `+0x1490000` |
| user32 | `0x75C50000` | `0x75940000` | `+0x310000` |
| msvcp60 | `0x607A0000` | `0x607A0000` | 0（已 rebase 钉死） |
| msvcr71 | `0x7C340000` | `0x7C340000` | 0（固定基址） |

判定规则：某个 DWORD 在两份 dump 之间的差值**恰好等于某模块的基址差**，
则它是指向该模块的真指针；数值相同的则是常量。随机数据几乎不可能同时满足
「两份之间有差异」且「差值是页对齐的模块基址差」。

这解决了纯静态符号化不可靠的问题（USENIX Sec 2023 *Reassembly is Hard*）：
事后静态盲扫在本镜像上产生 3,076,132 条候选，几乎全是把代码字节误读成指针；
差分把它降到 469 条。

   排除 `.j`-` 尤其重要：那 24 MB 高熵数据是静态盲扫误报的主要来源。
3. 新增工作量是 **112 条**，其中 103 条是本次新发现。

## 已知局限

- 差分只能看见**在这两份 dump 之间移动过**的模块。msvcp60 / msvcr71 基址相同，

- `.,_W` 那 100 个站点的模块归属，离线投票不可靠（单点站点缺乏投票支持，
  自动归属会把 winmm 误判成 kernelbase）。需要在采集时读取活进程的模块列表。
- 若有站点指向模块内的**非导出地址**，修正记录只能是 `模块+偏移`，
  该 DLL 被 Windows Update 更新后会失效。需在模块归属确定后统计比例。

# 第三轮：修正表接入、实测，以及真正的阻断点

更新时间：2026-08-21

## 方法修正

第二轮用 **dump B 的数值**配 **dump C 的模块表**做归属。这对 kernel32/user32 这类
KnownDLL 成立（同一次启动内基址稳定），但对 d3d9 这类按进程 bottom-up 随机化的模块不成立
——B 和 C 是不同进程，d3d9 基址不同，于是这类站点全部归属失败被当噪声丢弃。

正确做法：**从 PE 导入 thunk 反推每份 dump 自己的模块基址**。原始导入表 40 个描述项、
46 个 thunk，每个 DLL 恰好一个具名函数，因此 `基址 = 槽值 − 该导出的 RVA`。三份 dump
各自解出 26 个模块基址，其中 21 个在 A/B 之间移动过（d3d9：A `0x6A0A0000`、
B `0x07360000`、C `0x07260000`）。

判据同步改为「**同一模块的同一偏移**」：`vA − baseA[m] == vB − baseB[m]`，而不是
「差值等于某个页对齐 delta」。

## 修正后的结果

| 差分对 | 移动的模块 | 差异区段 | 指针站点 | 具名导出 |
| --- | ---: | ---: | ---: | ---: |
| A ↔ B | 21 | 752 | 370 | 370 / 370 |
| B ↔ C | 2 | 22 | 2 | 2 / 2 |

并集 370 个站点。扣除已有机制覆盖的（6 段 loader 声明导入 + 入口桩的 9 个孤立槽）
再加上第二轮新增的 14 条，**剩余未处理 = 0**。

值得注意：**整个镜像里指向 d3d9 的普通指针只有一处**，就是 `.lA0` 里的 PE 导入 thunk，
loader 会正确解析它（实测崩溃瞬间该槽为正确值 `0x072316B0`）。

## 已接入重建器的改动

`ClientHack/tools/rebuild_runnable_pe.py`：

- `ORPHAN_SLOTS` 从 9 条扩到 24 条（新增 14 条，另把原先特判的 msvcp60 数据指针改为按名解析）。
- 入口桩加空值保护：模块或导出解析失败时**保留槽内原值**，不写 NULL。
- 节属性自动补 `IMAGE_SCN_MEM_WRITE`：凡是含修正槽的节都授予写权限。

最后一条是路上踩到的真实缺陷：`.,_W` 原属性是 `RXC`（只读），桩往里写当场 fault，
第一版构建连 startup gate 都没到。原有 9 个槽都落在可写节里，所以这个缺陷此前从未暴露。

顺带纠正 handoff §8.2：它称 `0x04712340` 那个 msvcp60 槽「标准命名导入不能可靠恢复」。
实际可以，它是具名数据导出
`?_C@?1??_Nullstr@?$basic_string@GU?$char_traits@G@std@@V?$allocator@G@2@@std@@CAPBGXZ@4GB`。

## 真正的阻断点：Themida Advanced API-Wrapping

主 fault 首次被完整定位（此前 `0006_B1StartupGuard` 只能断言「存在一个 PRIMARY fault」）：

```
EIP 0x072E16B1   ( = dump 时 d3d9 基址 0x07260000 + Direct3DCreate9 的 0x816B0 + 1 )
[esp] = 0x021321CD
```

调用链：

```
0x021321C0  push 0x20                  ; D3D_SDK_VERSION
0x021321C8  call 0x025035D0            ; ← 客户端以为这是 Direct3DCreate9 的 thunk
0x021321CD  mov  [0x31FB468], eax      ; 存 IDirect3D9*

0x025035D0  call 0x04ECBCF8            ; ← 不是 jmp [IAT]，而是跳进 .mackt 的壳包装桩
```

也就是说：**客户端的导入调用并不经过 PE IAT，而是经过壳的 API 包装桩**，由包装桩
在运行期重建 API 地址。dump 冻结的是包装桩的数据，于是重放时它复现出采集时刻的地址。

这解释了两件此前矛盾的事实：

1. PE IAT 槽在崩溃瞬间是**正确**的，却仍然崩在陈旧地址上——因为调用根本不读那个槽。
2. 陈旧地址 `0x072E16B0` 在整个镜像里**一次都不出现**——包装桩里的地址是编码存放的。

编码存放同时意味着**差分判据看不见它**：`vA − baseA == vB − baseB` 对编码值不成立，
所以这类站点全部落进 A↔B 的 382 个「未解释区段」里。

## 结论与下一步

普通跨模块指针这条线已经**做完并收敛**（370 个站点、零遗留）。剩下的是性质不同的问题：
壳的 API 包装。修正表无法修复它，因为要修的不是一个指针，而是一段会自行重建地址的代码。

标准解法是 **包装桩 → 真实 IAT 的重写**（Unlicense 对 Themida 做的就是这件事）：

1. 枚举 `.text` / `.code` 里所有 `call <落在 .mackt / .,_W 的地址>` 站点；
2. 确定每个包装桩对应哪个 `模块!导出`（在 packed 客户端里 hook 包装桩、记录其最终跳转目标）；
3. 在重建的 PE 里为这些 API 建立真实 IAT，并把 `call rel32` 重定向到我们自己的
   `jmp dword ptr [槽]` 小 thunk——`call rel32` 长度不变，可原地重定向，无需改指令长度。

第 2 步需要运行 packed 客户端采集，不需要服务端。

# 第四轮：跨模块重定位表 —— B1 起来了

更新时间：2026-08-22

## 关键认识：壳存的是 `api + K`

第三轮判定「Themida API 包装桩的地址是编码存放、差分看不见」。**这个判断只对了一半。**

包装桩存的是 `api_address + K`（每站点一个常量 K），K 在调用时被减掉。加常量对减法透明，
所以两份 dump 之间该值**仍然精确地移动一个模块基址差**。之前看不见它，是因为我在判据里
多加了一条「值必须落在该模块的地址区间内」——变换过的值当然不落在里面，于是被全部否掉。

去掉那条多余约束，只保留「**差值等于某个模块的基址差**」，站点立刻全部现形。

**推论：K 永远不需要解出来。**`新值 = 存值 + (当前基址 − dump 时基址)` 对普通指针
（K=0）和变换指针（K≠0）同时成立。这不是一张导入表，是一张**重定位表**。

## 测定

用四份 dump 的三组差分，每组都用各自 dump 的模块表：

| 差分对 | 移动的模块 | 差异区段 | 重定位站点 | 歧义 |
| --- | ---: | ---: | ---: | ---: |
| A ↔ B（不同启动，KnownDLL 移动） | 21 | 752 | 725 | 0 |
| B ↔ C | 2 | 22 | 6 | 0 |
| C ↔ D（editbin 重定 7 个 app-local） | 7 | 196 | 179 | 0 |

并集 **904 个站点**：370 个普通指针，534 个变换指针。扣除 loader 声明导入与入口桩已处理的，
**431 条进入重定位表**（`.,_W` 419、`.mackt` 11、`.tls` 1），零重叠。

## 接入

`ClientHack/tools/crossmodule-relocs.csv`（431 行）+ `rebuild_runnable_pe.py`：

- `load_reloc_table()` / `load_module_bases()`：站点表来自工具目录，dump 时基址来自
  **同一份采集**的 `DNF-modules.csv`。
- `_emit_crossmodule_relocs()`：按模块分组发射 `LoadLibraryA → eax−dump_base → 逐站点
  加 delta`。模块加载失败则跳过该组全部站点（保留 dump 值，不会更糟）。
- 含站点的节自动补 `IMAGE_SCN_MEM_WRITE`。

约 6 KB 桩代码，在跳 OEP 之前执行。

# 更正：真实重启验收失败（2026-08-22）

上文两处「尚未验证：真实重启后的表现（本轮以 editbin 重定基与原版 ASLR DLL 作等价
验证）」现已验证——**结论是失败的**。等价验证不等价。

## 事实

机器于 2026-08-22 10:30 重启。用上一 boot（08-19）dump 构建的 B1 EXE：

| 条件 | 结果 |
| --- | ---: |
| 关闭 PageGuardTrace，重启后直接运行 | `0xC0000005` 2 / 2（12s、15s） |

`0006_B1StartupGuard` 记录的首次异常有极整齐的特征：

```
at 0x06961A28  ->  target 0x06D61A28     差 0x400000
at 0x74120E70  ->  target 0x74520E70     差 0x400000
```

两条都是「访问地址 = 出错指令地址 + 0x400000」，即某个指针被多加了一个 `0x400000`。

## 为什么之前的三重验证漏掉了它

比较两份 dump 的模块基址表：

```
重启前后：64 个模块中 61 个移动
delta 直方图：0x4D0000 x2、0xFDCD0000 x2、0xFDB10000 x2、0x3A0000 x2、
              0xFD7E0000 x2、0x2F0000 x2 …
```

**一次重启会移动几乎所有模块**，而此前的三项验证都在同一次启动内完成：

* 「钉死基址」「editbin 重定到 `0x64xxxxxx`」只移动了 7 个 app-local DLL；
* 「原版 ASLR DLL」只覆盖到**每进程随机化**的那几个（d3d9、ddraw），
  KnownDLL（kernel32 / user32 / gdi32 / ntdll）的基址**每次启动才变一次，同一 boot
  内根本不动**。

而重定位表 431 条里 user32 占 92、kernel32 占 90，正是同 boot 内测不到的那部分。
换言之：**当时验证的样本，系统性地排除了唯一会暴露该缺陷的模块类别。**

## 推定根因（未定案）

模块归属错误。差分测量按「delta 等于某模块基址差」给站点归属，而 delta 直方图显示
**多个模块共享同一个 delta**，归属本身就有歧义。同 boot 内多数模块 delta 为 0，
歧义更严重。重启后各模块 delta 互不相同，错误归属立即致命。

尚未定案：未逐条复核 431 个站点的归属。

## 现状

* `重建debug-exe.bat` **没有退休，仍然必需**——上文「原理上已不再需要」的判断是错的。
  该脚本自身的抬头注释一直是对的。
* 重建耗时约 15 秒，已顺带加上 `--drop-sections 13`，产物仍为 82.8 MB slim 版。
* `prepare_b1_runtime.ps1` 的 DLL 钉基址是否也需要恢复：未测（本轮重建后未钉基址即
  通过冒烟与 90 秒长跑）。

## 教训

「等价验证」必须证明它覆盖了目标变量的**全部取值类别**。这里的类别是「模块基址何时
改变」：每进程随机 / 每启动随机 / 固定。只测了第一类，却对第三类下了结论。

# 修复：重定位表的真实缺陷与跨启动验收（2026-08-22）

上一节把重启崩溃归因为「模块归属错误」。**归因错了。** 用跨重启的 dump 对逐条核对，
旧表 431 条里 **430 条归属正确**，真实缺陷是另外两个。

## 缺陷一：漏站点（53 条）

旧表用**同一次启动内**的两份 dump 建成。同 boot 内只有每进程随机化的 DLL（d3d9、
ddraw）会动，KnownDLL 的基址要重启才变——所以差分对 kernel32 / user32 / ntdll 这类
模块**天然测不到**任何站点。

改用跨重启的一对（`20260821-231752` × `20260822-105044`，61/64 个模块移动）重扫，
共 849 个站点，旧表是其**严格子集**，漏了 53 条：kernel32 8、combase 5、user32 3 等。
同 boot 内这些陈旧值恰好是对的，所以从未失败过。

## 缺陷二：一条归属错误

```
0x04D03639 [11:.,_W]  标为 shell32.dll，实测 delta 属于 wkscli.dll
```

## 两个方法学修正

**扫描必须按字节粒度。** 多数包装站点是嵌在指令里的立即数，不是 4 字节对齐的。按对齐
扫会漏掉大部分，并且把其余的读错最多 3 个字节——第一次核对旧表时正是这个 bug 让我得
出「50 % 的行从未变化」的假结论：观察到的 delta `0x0D000000` 其实是模块 delta
`0x020D0000` 左移 8 位。

**排除必须按地址，不能按节。** 中途有一版按「排除 `01:.code`」来剔除客户端 IAT，产出
628 条表，结果仍然崩。原因是**重复施加**：

* 客户端那 406 个 IAT 槽**并不都在 `.code`**——其中 141 个在 `.tls`。它们在 B1 模式下
  被声明为真实 PE 导入，由加载器填入当前地址；
* 24 个 `ORPHAN_SLOTS` 由入口 stub 自己用 LoadLibraryA/GetProcAddress 解析，且**在**
  重定位代码**之前**执行。

任一类被写进重定位表，stub 就会在已经正确的值上再加一次基址差。当时
`kernel32.dll!TlsGetValue/TlsSetValue/TlsFree`（RVA `0x04AEE124`）就是这样被加了两次，
第一次经它调用即跳进未映射内存。

规则应为：**任何已被别的写入者拥有的站点都必须排除**——排除 341 个客户端 IAT 槽与 24
个孤儿槽后，表为 **484 条**。

（旧的 431 条表本身没有这个重叠，重复施加是我在中途引入的。）

## 顺带更正一个误读

`0006_B1StartupGuard` 的 first-chance 记录里，`at` 与 `target` 恒差 `0x400000`，我当作
「指针被多加了一个基址」的证据。**那是日志格式的假象**：插件用 `at >= dnf_base` 判断
是否在镜像内，而几乎任何地址都满足，于是连 DLL 地址也被减了一次 `0x400000` 当作 RVA
输出。`at + 0x400000 == target` 说明两者是同一地址，即**执行型故障**。

## 验收

离线模拟（把旧 dump 套上表、与新 dump 逐字节比对）后，残差只剩加载器/stub 自己拥有的
站点与 21 个非模块指针。实机：

| 场景 | 结果 |
| --- | ---: |
| 用**重启前**的 dump 构建、在**当前 boot** 运行（修复前 3/3 崩） | **ALIVE 3 / 3** |
| 用当前 boot 的 dump 构建 | ALIVE 2 / 2 |

**启动器的新鲜度检查暂不移除。** 上一次正是在这里，用「等价验证」下了「已不再需要」的
结论而翻车。这次的证据更直接（真正的跨启动构建），但仍应由**下一次真实重启**来收尾。

# 第二次修正：同 boot 配对能拆开跨 boot 拆不开的组

## 上一版留下的问题被真实重启证实了

上文那 484 条表里有 116 条标着 `same-delta`：两个模块在建表用的那对 dump 里恰好移动了
相同的距离，无法区分，于是按字母序取了第一个。当时把它记为「潜在风险」。

2026-08-22 22:44 的重启把它变成了事实。用**重启前**构建的 exe 在新 boot 启动，
`0xC0000005`。离线比对（把旧 dump 套上表、与新 boot 的 dump 逐字节比）给出确切数字：

| 分类 | 数量 | 说明 |
| --- | ---: | --- |
| 加载器/stub 自己拥有的站点 | 365 | 342 个客户端 IAT + 23 个孤儿槽，**本就该由它们写** |
| 非模块指针 | 17 | 真的在变的数据，任何表都修不了 |
| **误归属** | **9** | 标成 `ntdll.dll`，实际需要 `version.dll` 的差值 |

除这 9 条外没有一条「无法解释」，说明表的**覆盖**是完整的，坏的只有**归属**。

## 解法：两种配对的切分方式是互补的

跨 boot 的配对里，一批模块会被焊在一起同进同退；而**同一 boot 内**：

* 每个 KnownDLL（ntdll/kernel32/user32/gdi32）保持基址不变 → 差值恒为 0；
* app-local 的 DLL 每次**启动**重新随机化 → 各自移动不同的距离。

于是跨 boot 拆不开的组，同 boot 往往一拆到底。S4A21 上实测：

```
跨 boot 组：d3dx9_43 | dbghelp | fmodex | msacm32 | msvcp60 | msvcr100 | tbbmalloc
同 boot 内：七个各自移动了 -1179648 / +2359296 / -786432 / +786432 / +1638400 /
            -131072 / +851968  —— 完全分开
```

`build_crossmodule_relocs.py --refine OLD NEW` 就是这件事：候选集在**每一对**里都要
能解释观测到的变化，取交集。S4A21 的歧义因此从 **115 → 17**，剩下的三组全是同 boot
不动的 KnownDLL，只能等下一次重启。

反过来，S4A12 的 app-local DLL 是**每 boot** 随机化而非每启动（它们被
`prepare_b1_runtime.ps1` 重定过基），同 boot 配对里一个都不动，所以这招在 A12 上
refine 出 0 条。这也解释了为什么 A12 只要「每次重启后重建」就一直没出事：
exe 与 dump 同 boot 时所有差值都是 0，归属错了也不体现。

## 验收（这次没有靠运气）

先说一次**失败的验收**，因为它比结论更值得记：我用未 refine 的表建了个 exe 想当反例，
结果它**照样跑起来了**。原因不是表没问题，而是 A21 的 DLL 布局在少数几种排列间跳，
那次启动恰好抽到了和 build dump 相同的排列，所有差值都是 0。**一次「跑通了」不能证明
表是对的**，正如一次「崩了」不能证明表是错的。

改成离线判决就没有这个问题——固定用 build dump，去比对一份布局确实不同的 dump：

| 表 | 误归属 | 说明 |
| --- | ---: | --- |
| refined（已入库） | **0** | 残差只剩 22 处真在变的数据 |
| 未 refine | **84** | 49 msvcp60 + 32 fmodex + 2 tbbmalloc + 1 dbghelp，全被标成 d3dx9_43 |

这 84 条不是「以后可能出问题」，而是**每次启动抽到不同排列就会炸**。

## 现在的规矩

* 建表必须用**跨重启**的一对，再用**同 boot** 的一对 `--refine`；
* 表里仍标着 `same-delta:` 的行是已知未决，不要当成已解决；
* 判断一张表对不对，用离线残差比对，**不要用「启动成功」**。

## 后续：符号求值能定差分定不了的行（2026-08-23）

上面「同 delta 歧义要等下一次重启的 dump 对」这条**不再是唯一出路**。

`ClientHack/tools/resolve_wrappers.py` 从另一端解这个问题：`.text` 调用的每个

就直接证明了它读的那一行属于哪个模块。
