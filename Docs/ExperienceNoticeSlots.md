# 经验通告 `NOTI 0x0025` 的加成槽位语义

客户端在一次击杀后弹出的那条「获得 N(基础:… + …)点经验值」，是由帧里十四个 `u32` 加成槽拼出来
的。本页记录**每个槽客户端自己怎么叫、它参不参与基础值的计算**，以及由此得出的建模约束。

不下实现结论。`ExperienceBonusKind` 的成员按本页第四节的结论定，代码里逐个引用本页。

测量日期 2026-08-28。客户端 = `DNFClient-A21-protocol`（重建的 b1 debug exe，本次开机构建）。
服务端 = 本工作树，`Experience:LabelProbe=true`。

---

## 一、为什么必须实测，不能抄上游

上游 `ExpNotificationBuilder.Build` 给每个槽都起了名字。**其中至少两个是错的**，而且错得看不
出来——名字只影响人怎么理解，不影响字节，所以照抄不会有任何报错。

| 偏移 | 上游叫法 | 客户端画出来的 |
|---|---|---|
| `+0x2F` | elite monster kill | **Buff奖励** |
| `+0x4B` | channel bonus | **赛丽亚的欢迎** |

`+0x4B` 是先发现的：我们按上游的说法把频道加成写进这个槽，实机弹出来却是「赛丽亚的欢迎:3」。
一处标签被证伪之后，其余十三处就都失去了证据地位——它们和这一处出自同一份表、同一种来源。

于是名字改为向客户端要。

## 二、怎么问的

服务端开一个测量开关（`Experience:LabelProbe`），让一次击杀往**每个槽填一个互不相同的值**，
客户端弹出来的那条就会把每一行连名带值列出，值即槽号。一次击杀拿全部。

两轮，同一个开关，换了填充值：

* **第一轮**填 `1..14`。拿到十条槽位的客户端叫法。
* **第二轮**填 `2, 4, 8 … 16384`（2 的幂，**bit0 空着**）。基础值的亏空于是是一个位掩码，
  哪一位置 1 就是哪个槽被减，唯一确定，不用再从和数反推。

第二轮只抬高帧里**报告**的总数，库里一分不动：下一只怪发回真实总数，客户端自己纠回来。测量不
污染测试角色。

第二轮读到的是**第二只**怪的那条：探针每帧抬高同一个常数，增量于是回到真实的 75，基础值把减法
集合直接暴露出来。

## 三、两轮的原始读数

第一轮（填 `1..14`）：

```
获得105(基础:35+网吧奖励:7+队伍奖励:1+疲劳值Buff:2+赛丽亚的祝福奖励:3+成长之契约奖励:4
+疲劳值燃烧奖励:6+Buff奖励:8+极速成长Buff奖励:11+赛丽亚的欢迎:13+公会奖励:14)点经验值。
```

第二轮（填 2 的幂）：

```
获得75(基础:-27283+网吧奖励:128+队伍奖励:2+疲劳值Buff:4+赛丽亚的祝福奖励:8+成长之契约奖励:16
+疲劳值燃烧奖励:64+Buff奖励:256+极速成长Buff奖励:2048+赛丽亚的欢迎:8192+公会奖励:16384)点经验
```

由第二轮解掩码：

```
Σ(被减) = 75 − (−27283) = 27358
27358  = 16384 + 8192 + 2048 + 512 + 128 + 64 + 16 + 8 + 4 + 2
```

十个被减项，与反汇编里数出的十次减法个数一致。

**回代第一轮做交叉验证**：按同一个减法集合，第一轮应有 `Σ(被减) = 1+2+3+4+6+7+9+11+13+14 = 70`，
基础值 `105 − 70 = 35`——与截图分毫不差。两轮不同填充值互相印证，集合是定的。

## 四、结论：十四个槽的实测语义

「画」= 客户端在通告里为它单列一行；「减」= 客户端算基础值时从增量里扣掉它。

| 偏移 | 客户端叫法 | 画 | 减 | 可用 |
|---|---|---|---|---|
| `+0x05` | 队伍奖励 | ✓ | ✓ | **可用** |
| `+0x15` | 疲劳值Buff | ✓ | ✓ | **可用** |
| `+0x1A` | 赛丽亚的祝福奖励 | ✓ | ✓ | **可用** |
| `+0x1E` | 成长之契约奖励 | ✓ | ✓ | **可用** |
| `+0x22` | —— | ✗ | ✗ | 惰性 |
| `+0x26` | 疲劳值燃烧奖励 | ✓ | ✓ | **可用** |
| `+0x2A` | 网吧奖励 | ✓ | ✓ | **可用** |
| `+0x2F` | Buff奖励 | ✓ | ✗ | **不可用**（见下） |
| `+0x33` | —— | ✗ | ✓ | **不可用**（见下） |
| `+0x37` | —— | ✗ | ✗ | 惰性 |
| `+0x43` | 极速成长Buff奖励 | ✓ | ✓ | **可用** |
| `+0x47` | —— | ✗ | ✗ | 惰性 |
| `+0x4B` | 赛丽亚的欢迎 | ✓ | ✓ | **可用** |
| `+0x4F` | 公会奖励 | ✓ | ✓ | **可用** |

### 两个不一致的槽

**`+0x2F`「Buff奖励」画而不减。** 往它写 N，玩家看到多一行「Buff奖励:N」，同时基础值**不会**
相应减少——这一份被算了两次，明细的和会比宣布的总数多出 N。

**`+0x33` 减而不画。** 往它写 N，基础值凭空少 N，而没有任何一行解释这 N 去哪了。

两者都不是我们的 bug，是客户端这条通告自身的不对称。**它们不可用**：任何一个被写入，玩家看到
的明细就不再自洽，而这条通告的全部价值就在于自洽。

### 惰性的三个

`+0x22`、`+0x37`、`+0x47` 既不画也不减。上游把 `+0x37` 叫 growth capsule，它有自己的 UI，不进
这条通告，说得通；另两个仍然不知道是什么。往它们写值对这条通告没有任何可观察影响——这也意味着
**无法用这条通告去探它们的语义**，要另找入口。

## 五、被否掉的一个假设

第一轮读数里，画出来的十行加基础值是 104，而宣布的是 105，差 1。当时推断是客户端把**荣誉等级**
（`+0x3B`，值为 1）也从增量里减掉了，属于客户端的一个 bug。

**第二轮否掉了它。** 掩码 27358 是偶数，bit0（预留给"十四个槽以外的来源"）没有置位，荣誉等级
没有参与。那 1 点的真实来源是 `+0x33` 被减（第一轮值 9）而 `+0x2F` 被画不被减（值 8），`9−8=1`。

留在这里是因为这个假设当时看起来严丝合缝：它由一次实验的**一个**数字反推而来，而那个数字有不
止一种解释。第二轮之所以换成 2 的幂，正是为了让读数从"一个和"变成"一个掩码"，把反推变成读取。

## 六、对建模的约束

1. `ExperienceBonusKind` 只开**九个**成员，即上表标「可用」的九个偏移，每个带客户端叫法和本页
   的出处；`+0x2F`、`+0x33` 明确记为不可用并写明原因，免得后人看到"上游给它起了名字"就填进去。
2. 付了却没有槽可申报的加成，走 `Unlisted`：客户端会把它算进基础值。总数仍然正确，明细把它归给
   了这次击杀本身。这是有意的取舍——**宁可少一行，不可写进一个会让明细算不平的槽**。
3. 通关结算那一半用的是同一条通告，因此同一张表同样适用，不必重测。

## 七、结算帧 `NOTI 0x0023` 的槽位还没测

同一招还没在结算帧上用过。`CLEAR_DUNGEON_REWARD` 的基础块里，四个头部字段之后跟着**二十三个
固定槽**，客户端会把其中一部分画在结算屏上。这些槽的语义我们一个都没实测。

上游旧版把频道奖励写在第 24 个槽（下标 23），但那份帧的固定槽数与我们已经逐偏移核对过的这份
**不一致**；上游当前版本干脆连频道奖励一起删了，`BuildClearDungeonReward` 的参数表里已经没有它。
两边都不构成证据。

因此 2026-08-29 的结算实现**只付它报得出来的两项**——通关基数与评分奖励，写在帧的前八字节。
结算侧的频道奖励与账号权益加成没有付，理由是付了就报不出来，结算屏的合计会短一截，而那种不一致
只有玩家自己做加法才看得出来。

**下次怎么测**：往二十三个固定槽各填一个互不相同的值（2 的幂最省事，理由见第二节：亏空变成位掩码，
唯一确定），跑一次通关，结算屏会把它认得的那几个连名带值列出来。和第二节测经验通告十四个槽是
同一招，成本是一次通关。

另外，帧头四个字段的**位置**是结构性的（前十六字节），**含义**（通关基数、评分奖励、组队分解、
装扮奖励）取的是上游命名，同样没有实测。通关基数远大于评分奖励，所以第一张实机结算屏截图就能
看出前两个有没有被写反。
