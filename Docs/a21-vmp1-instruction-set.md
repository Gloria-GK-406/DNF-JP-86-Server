# `.vmp1` 虚拟机指令集（2026-08-31 还原）

前置：`Docs/a21-vmp1-virtualization.md`（VM 结构）、
`Docs/a21-vmp1-handler-enumeration.md`（枚举方法与三次静态失败）。
产物：`ClientHack/tools/vmp1-opcodes-a21.csv`。

## 一句话

276 个 handler（覆盖真实执行的 90%）逐个还原语义，得到 **19 种虚拟操作**。
证据 **276/276 零拒收**。这是去虚拟化流水线的指令表。

## 指令集（对抗复核后）

```

VM_POP_REG          35     10,385    31.9%   pop 到 [CTX + idx*4]
VM_PUSH_REG         40      7,222    22.1%   push [CTX + idx*4]
VM_PUSH_IMM         60      5,247    16.1%   push 内联立即数（加密，见下）
VM_PUSH_VSP         20      2,015     6.2%   push VM 栈指针

VM_SHR / VM_STORE / VM_ADD_VSP / VM_SHL / VM_MEMCPY / VM_REP_MOVSB   合计 2.7%
```

**16 种操作、276 个变体。** 前三种（寄存器搬运与立即数）占 **70%** 的派发。

## 三个对去虚拟化有决定性影响的发现

### 1. `VM_NOR` 是 VMProtect 的招牌

27 个变体、6% 的派发全部是 NOR。VMProtect 用 NOR 实现**全部**布尔逻辑，
因为 NOR 函数完备（可表达任意布尔函数），这样指令集里就不必出现
AND/OR/NOT/XOR。判定协议只在名称列表里顺带提过一次 NOR，
**是 agent 从字节里独立认出来的**，属于正确性的强佐证。

推论：去虚拟化时不能指望看到 `and`/`or`/`xor` 操作码——
它们全部以 NOR 组合的形式出现，提升器必须做代数归约才能还原可读表达式。

### 2. 立即数是 **VIP 密钥化加密**的，不能直接从字节码读

多个批次独立报告同一条解密链：

```
种子 = VIP - [CTX+4]
然后 rol 7 / dec / not / ror 1 / xor 0x31DB5127 / ror 7 / not
```

链是双射的，所以可逆；但种子含**运行期 VIP**，意味着
**同一个常量在不同位置的字节码里编码不同**。

推论：静态去虚拟化必须逐站点重放这条解密链，
直接读操作数会得到错误的常量。这是最容易出错也最容易被忽略的一点。
另有 1 字节变体用 `xor 0xA4 / ror 4 / dec / ror 4 / not`，
零扩展后以 `66 50`（`push ax`）压半个 slot。

### 3. 算术 handler **不压 EFLAGS**

`VM_ADD`、`VM_NOR` 的所有变体都不在结果之后压入标志位 dword——
H-05、H-07、H-08 三个批次独立报告。这**与 VMProtect 的通常约定相反**。

推论：提升器不能假设 ALU 之后栈上多一个标志位 slot，否则栈深度全盘错位。
`VM_JCC` 的标志来源另有出处（`VM_POP_DISCARD` 有 15 个变体、1,174 次派发，
一个候选解释是它丢弃的正是标志位 dword——已进对抗复核清单）。

## 方法

- **单元集合是跑出来的**：`0160_VmEntryTrace` 活体捕获 1,028 个真实 VM 密钥
  → 961 个 VM 函数 → `walk_vmp1.py` 走行 → 977 个 handler，取覆盖 90% 的 276 个。
  静态枚举三次失败（见枚举文档），这一步是整个工作的前提。
- **证据确定性**：`symeval` 折叠混淆（跟穿 `call`-当-`jmp` 蹦床），
  每条指令带逐字节原样 hex，agent 引证据靠复制。**276/276 零拒收。**
- **校准两轮**：第一轮 top-10 三轮一致但只覆盖 2 种操作；
  第二轮按引用数分层抽样（522→21），**9/10 三轮一致**，
  已知答案 `0x05275444` → `VM_POP_REG` 三轮命中（agent 被禁止查仓库）。
  唯一分歧是命名粒度（`VM_PUSH_IMM` vs `VM_PUSH_IMM16`），已写入判定协议修正。
- **规模**：28 个 agent 跑全量，high 250 / medium 26 / low 0，零死批次。

## 对抗复核结果（74 个高风险行）

**71 维持、3 推翻**，三个推翻全部是栈指针族的同义词归并：
`VM_PUSH_SP` → `VM_PUSH_VSP`、`VM_ADD_SP` → `VM_ADD_VSP`。
指令数因此从 19 收敛到 **16**——原来的 19 里有 3 个是同一操作的不同拼法。

复核确认的关键点：

- **「算术不压 EFLAGS」经攻击后成立。** 复核直接指出 `9c`（pushfd）
  只是被当作 `sub esp,4` 用来预留槽位，其标志位 dword 随即被
  `89 04 24` 覆盖——不是发布标志位。这条现在是硬结论。
- **`rol eax,2` 与 `shl eax,2` 等价成立。** 索引被 `and eax,0xff` 掩过，
  最大 0xFF，两者对 ≤0x3FFFFFFF 的值同义。之前担心的 64 槽上限问题不存在。
- **`VM_ADD_VSP` 与 `VM_PUSH_VSP` 是真的两个操作**，不是同义词：
  前者 `03 e0`（esp += 符号扩展的 imm16），后者 `8b d4` + `89 14 24`
  （把入口 esp 快照写进新分配的槽）。
- **一处栈效果被纠正**：`0x05771F9F` 用 `66 50`（`push ax`）压入，
  **esp 只减 2 字节而非一个 dword**。普查记的 `+1` 是符号执行把字压当成
  dword 压的产物。半 slot 的存在意味着提升器不能假设栈永远按 dword 对齐。
- 4 个 `VM_POP_DISCARD` 从 high 降为 medium：被弹出的 dword 在 handler
  退出时仍活在 ecx 里，"死值"这一点单个 handler 证不了，需要跨 handler 约定。

最终置信度：**high 247 / medium 29 / low 0**，其中 74 个经对抗复核
（`vmp1-opcodes-a21.csv` 的 `verified` 列标注）。

## 七、翻译实验：提升器原型（2026-08-31）

`ClientHack/tools/lift_vmp1.py`。输入是走行结果 + 指令表 + dump，
输出是折叠回表达式的伪代码。**目的不是产出可用产物，是检验指令表对不对。**

### 7.1 四条独立佐证说明判读基本正确

**① 寄存器保存顺序自动对上。** 每个 VM 函数的开头 8 个 `VM_POP_REG` 折叠成：

```
r33 = in_edi     r13 = in_ebp    r32 = in_EFLAGS   r42 = in_esi
r30 = in_eax     r51 = in_ebx    r25 = in_edx      r62 = in_ecx
```

正是既有分析测得的入口保存顺序，**提升器并不知道这个顺序**——它只是按
`VM_POP_REG` 的语义从栈上取值，顺序是自己浮现的。

**② 出现了编译代码该有的栈帧算术。**

```
r33 = (r13 + 0xFFFFFFE4)     ; ebp - 0x1C，局部变量
[…] = (r13 + 0xFFFFFFFC)     ; ebp - 4，/GS 安全 cookie 槽
```

**③ 立即数解密链 60/60 全部还原**，解出的值全是合理的小常量与真地址：
`VSP + 0x8` / `+0x10` / `+0xC`（栈槽偏移）、移位计数 `0x6`、
以及落在 `.text` / `.vmp1` 内的地址。

32 位变体在 `eax` 上跑 `rol 7 / dec / not / ror 1 / xor K / ror 7 / not`；
1 字节变体在 **`al` 上跑 8 位运算**（`ror al,4` 是字节旋转）再
`xor ah,ah / push ax` 压半字——两种宽度都必须从各自 trace 里读出来，
假设成 32 位会解出垃圾。

**④ NOR 归约还原出布尔算子。** `~(~a | b)` → `a & ~b`：

```
r10 = ([VSP] & [(VSP + 0x8)] | [VSP])
r32 = (r25 & ~r10)
```

VMProtect 用 NOR 编码全部布尔逻辑，不做归约就只能看到一串 NOR。

### 7.2 还缺什么（诚实清单）

- **`VSP` 只是个符号，没被当作值跟踪**，所以本该是具体栈槽的地方显示成 `[VSP]`。
  这是目前最大的短板，函数中段因此不可读。
- **`VM_UNKNOWN`**：走行踩到普查范围外的低频 handler（276 之外那 701 个）。
- **`<underflow>`**：栈建模漂移，是 VSP 问题的下游。
- **控制流未重建**：`VM_JMP` 的目标没有解析成基本块。
- 括号优先级只是拼接，不是真表达式树。

### 7.3 结论

**指令表基本正确。** 四条佐证都不是提升器被"喂"进去的——保存顺序、栈帧偏移、
立即数落在有效地址、NOR 归约成合理算子，全是从字节里自己浮现的。

距离可用的去虚拟化产物还差三步：VSP 值跟踪、补齐尾部 701 个 handler、
控制流重建。**都是工程，不是研究。**
