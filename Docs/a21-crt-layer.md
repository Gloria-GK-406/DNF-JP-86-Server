# 变形 CRT 层：规模与可分离性（2026-08-31 实测）

前置：`Docs/clean-exe-section-removal.md`（运行期/构建期变换的二分）、
`Docs/a21-ei4-bytecode.md`（`.eI4` 是 CRT 解释器的字节码池）。

## 一句话

变形 CRT 占 `.-wI` 的 **445 页 / 1.78 MB**，与 API 包装器用的 233 页 / 0.93 MB
**零重叠**。字节层面两者交织、静态可达性分不开；**页粒度上完全分离**。
这是替换 CRT 之前需要的规模数。

## 一、它在哪

A21 的变形 CRT **不在独立段里**，就在 `.-wI`——与 1,654 个 API 包装器同段、交织存放：

```
CRT 续点      0x05D06329   在命名包装器入口 0x05D05DBB 之后 1,390 字节
.eI4 读点     0x05C33BB0   在命名包装器入口 0x05C3386D 之后   835 字节
```

（`clean-exe-section-removal.md` 里的 `.,_W` 是 A12 段名，A21 布局不同。）

**推论：不能靠丢地址区间去掉 CRT。**

## 二、静态可达性分不开（第三次同类失败）

从 1,654 个包装器入口与 CRT 续点分别做递归下降（两边都跟条件跳转、
`call` 同时当跳转处理，因为变形层大量使用 `call X` + 被调用方 `lea esp,[esp+4]`）：

```
包装器下降  818,472 条指令  覆盖 .-wI 的 25.5%
CRT 下降    793,091 条指令（单种子！）覆盖 23.9%

归属：包装器独有 1.6%   CRT 独有 0.0%   两者都到 23.9%   都不到 74.5%
```

**「CRT 独有 = 0」**：单个 CRT 种子走到的地方包装器全能走到。原因是两条下降
都灌进了同一个**共享蹦床池**（既有文档记过「11 个高引用共享件全是体内共享块」），
进池之后就到处都是。

这与 `.vmp1` 的三次静态失败同因：**对变形代码做静态过度近似，
量到的是变形器的输出分布，不是程序结构。**

## 三、活体测量分开了：按页，按调用栈

`0001_PageGuardTrace`，`Sections=11`（`.-wI`）、`ArmDelayMs=0`（init 期布防），
一局跑到登录界面：

```
布防 959 页，首触 679 页（71%）
第一条记录就是 0x05D06329（CRT 续点本身），access=8（执行），
栈上是 kernel32 地址——入口桩跳进来的那一刻
678/679 的首触 EIP 落在 .-wI 内部：变形代码在自己走
```

用**调用栈里有没有游戏代码帧**做时序切分：

```
                        页数    体积    首触序号
CRT 期（栈上无游戏帧）   445   1,780 KB   0 .. 444
包装器期（游戏代码调入） 233     932 KB   445 .. 677
重叠                       0
从未触碰                 281   1,124 KB
```

**零重叠是关键结果**：页粒度可以做到字节粒度做不到的分离。

## 四、对替换 CRT 的含义

- **规模已知**：要替换掉的是约 1.78 MB 变形代码 + `.eI4` 的 1.05 MB 字节码池。
- **可定位**：CRT 期页集合已经能测出来，替换后这些页应当全部变成死区。
- **验收判据现成**：替换后重跑同样的页布防测量，CRT 期首触应当归零；
  包装器期的 233 页应当不受影响。**这是一个可证伪的验收条件**，
  比"客户端还能启动"强得多。

## 五、这次测量的边界

- **一局、只到登录界面。** CRT 启动只跑一次，所以 CRT 期的 445 页应当接近完整；
  但包装器期的 233 页是下限——完整会话会触到更多包装器页。
- **「栈上无游戏代码帧」是启发式**，用的是 4 层栈样本，可能漏掉更深的帧。
- 页粒度零重叠不等于字节粒度零重叠：同一页内仍可能既有 CRT 也有包装器字节，
  只是这局里没有哪一页被两边都首触。丢页之前需要按字节复核。

## 六、复现

```ini
[PageGuardTrace]
Enabled=1
Sections=11      ; .-wI
ArmDelayMs=0     ; init 期布防，抓得到 CRT 启动
```

需 B1 exe（`CLIENTHACK_B1_MODE=1`）。日志 `clienthack-pageguard.log`，
每条首触带 `addr` / `eip` / `access` / `tid` / 4 层 `stack`。
`0001_PageGuardTrace` 与客户端无关，但 CMake 只输出到非 A21 stage，
需手工复制到 `DNFClient-A21-debug\plugins\`。

## 七、反转：A21 的程序 C 运行时**没有被变形**

第三节按页把 `.-wI` 分成"CRT 期 445 页 / 包装器期 233 页"，但那个"CRT 期"的命名
是错的。给整个 `.text`（11,304 页）布防后，真相很清楚。

### 7.1 首触归属

一局跑到登录界面，`.text` 页首触 3,769 次，**按触碰者所在段**统计：

```
   .text     3,761  (99.8%)
   .vmp1         7  ( 0.2%)
   .-wI          1  ( 0.0%)   ← 而且是一次读，不是执行
```

**`.-wI` 那层几乎不进入 `.text`。** 它不是穿插在客户端初始化里的东西。

（方法注记：`0001_PageGuardTrace` 排在 `0010_DisableGameGuard` 之前布防时，
后者的 `patch_apply` 会因 `memory.Protect & PAGE_GUARD` 直接失败、宿主 fatal。
把 DLL 改名为 `0090_PageGuardTrace.dll` 让它最后加载即可。）

### 7.2 程序的 CRT 在 `.text`，且是明文

第一次首触 `seq=0` 的 EIP 是 `0x02C865DE`——即 port-status 记录的
cookie RVA `0x028865DE` + 基址。反汇编：

```
0x02C865DE  8b ff              mov edi, edi          ; 热补丁序言
0x02C865E0  55 8b ec           push ebp / mov ebp,esp
0x02C865E6  a1 e0 ce 99 03     mov eax, [0x0399CEE0] ; __security_cookie
0x02C865F5  bf 4e e6 40 bb     mov edi, 0xBB40E64E   ; MSVC DEFAULT_SECURITY_COOKIE
0x02C865FF  3b c7 / 74 0d      cmp eax,edi / je      ; 是默认值就重新生成
0x02C86607  f7 d0              not eax
0x02C86609  a3 e4 ce 99 03     mov [0x0399CEE4], eax ; __security_cookie_complement
0x02C86615  ff 15 5c 93 02 03  call [0x0302935C]     ; GetSystemTimeAsFileTime
```

**教科书式的未变形 MSVC CRT。** 它位于 `a21-next-measurements.md` 标定的
CRT/加载器带 `0x02C00000`–`0x02CAA000`（0.66 MB、1,495 个函数），
该带内**已知游戏源文件函数为 0 个**，最近的已知函数在 652 KB 之外——
与"这是库代码、无源文件映射"一致。

### 7.3 结论：这一项被错误归类了

`clean-exe-section-removal.md` 的天花板表里「CRT 变异（`.,_W`）——构建期变换，
必须重新合成」是 **A12 的观察**。A21 的对应层不是程序的 C 运行时：

- **程序的 CRT 在 `.text`，明文，不需要重新合成。**
- `.-wI` 里的是**壳自己的启动/支撑层 + API 包装器**。包装器已有拆除方案
  （`Docs/wrapper-rewrite-trampoline-plan.md`，1,158 个入口）；
  壳的启动层在 B1 重建里**本来就跑不到**——入口是我们自己的 `.chstub` 桩，
  AEP 路径按构造不可达。
- 第三节那 445 页"CRT 期"页，实际是**启动期被执行到的 `.-wI` 代码**
  （壳的支撑层 + 启动期用到的 API 包装器体），不是程序的 C 运行时。

**天花板表里的两项构建期变换，A21 实际只剩一项：`.vmp1` 虚拟化。**

### 7.4 边界

- 首触只能看见**首次**进入。若 `.-wI` 在某 `.text` 页已被 `.text` 自己碰过之后
  再调进去，本测量看不到。所以"接口很窄"是对**初始化期**成立，不是对全运行期。
- API 包装器的方向是 `.text` → `.-wI` → DLL，不是 `.-wI` → `.text`，
  所以它们不出现在这个统计里，与结论不冲突。
- `.eI4` 解释器在启动期仍有一次执行（1/268 页），它做什么仍未知。
  但它不调用 `.text`，所以不参与客户端初始化。
