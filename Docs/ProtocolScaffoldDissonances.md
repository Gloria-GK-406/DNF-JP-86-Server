# 协议脚手架建设中浮现的失谐

2026-08-16 建设 [Game 协议全量索引](../protocol/game/index.md) 时，把客户端静态提取的 body
布局与上游服务端（`D:\project\86JP`）的解析/构造代码逐条对位，发现下列不一致。

**这里只记录，不修改。** 每一条都需要一份实机样本才能判定哪一侧是对的，而样本要等游戏走到
那个状态。过早"弥合"只会把一个猜测固化成两处代码。凡受影响的字段，协议文档里已按
`留空 = unknown` 处理，不会把任一侧当作事实。

## 一、重复组的位置模型两侧不一致（影响面最大）

客户端提取按指令地址还原字段序，重复组落在循环所在处；上游多数 builder 却把可变项**插在
计数字节之后、固定尾部之前**。两种模型在 `n = 0` 时一致，`n > 0` 时其后所有偏移都会漂移。

| 协议 | 客户端提取 | 上游 |
|---|---|---|
| `NOTI 0x0002` USERINFO | 组宽 15B/条 | `WriteAppearanceEntry` 23B/条（多 `i32 ExpansionLen + 4B`） |
| `NOTI 0x0025` EXP | 组排在固定段之后 | 可变项插在 offset 50 的计数之后 |
| `NOTI 0x0023` | 一个 u8 在 offset 126 | `DungeonNotificationBuilder` 是连续两字节 117/118 |
| `NOTI 0x00D1` | `2 + 9n` | `BuildReward` 是 `3 + 8n + 3` |

**影响**：重复组之后的顶层偏移在文档里带 `*` 标记，表示**名义值**——累加时按重复次数
`n = 0` 排布，真实位置 = 名义值 + Σ(组宽 × 实际重复次数)。这类偏移**仍然接受字段含义**：
位置不确定不代表字段身份不确定，上游代码往往能确证"这个字段是什么"，只是"它在第几字节"
要等计数确定。落在名义偏移上的含义，其证据列会注明「位置为名义值」。

早先本节曾写"这类偏移一律显示为 `?` 且不接受字段含义"。那描述的是一个更早的版本；
按 `?` 处理会连带丢掉上游已经证实的字段身份，因此改为名义值 + 显式标注。要取真实偏移，
仍然必须有样本。

## 二、提取器选中的构包点归属另一个 opcode

`CMD 0x031C` 的最优构包点是 `8 + n×7` 形态，而其分发目标
`Handle_EQUIPMENT_EMBLEM_ATTACH`（`InventoryHandler.Equipment.cs:432`）解析的是 `7 + n×7`、
无前缀字节。与 `8 + n×7` 逐字节吻合的上游代码是 `TryParseEmblemAttachBodyAt(body, 1, …)`，
它挂在 `CMD 0x00C9` AVATAR_EMBLEM_ATTACH 上。

同类：`CMD 0x00A0` 名为 `USE_BOOSTER_ITEM`，实际分派到 `Handle_OPEN_SELECTABLE_PACKAGE`；
`CMD 0x0218` 名为 booster，实际走 `TrySaveCrystalContractSelection`；
`CMD 0x03EA` 名为 `BIND_PLUS`，实际是 `Handle_COMPOUND_AVATAR_SET`。

**结论**：**枚举名给"叫什么"，分发表给"做什么"，两者可以不一致。** 实现前必须跟进分发目标，
不能按名字推语义。

## 三、上游存在零调用点的 builder，且它才与客户端吻合

`NOTI 0x0184`：在跑的发送点用 `TournamentPacketBuilder.BuildTournamentMapInfo`，产出 13 字节、
无重复组；而客户端提取的 `27 + n×18` 与 `Network/Builders/Party/DungeonRoomP2pBuilder.cs`
逐字段完全吻合——那个 builder 在整个上游树里**零调用点**。两者在前 11 字节上互相冲突
（offset 2 一个是 `seed`、一个是 `partyId`）。

**推测（未证实）**：上游改过该 type 的用途，旧 builder 留在树里没删。客户端仍按旧格式解析。

## 四、上游 `NotiPacketType` 与本客户端的对应存在个例偏差

`NOTI 0x0247`：上游枚举里 `0x0247 = MODULE_REQUEST`、`RAID_DO_BEHAVIOR = 0x0296`，但
`RaidHandler.cs:167` 把 raid behavior 转发到 `0x0296`，而**客户端接收表里根本没有
NOTI `0x0296`**。

**边界**：CMD 族的名称已由 16 条已双向验证协议交叉核对、零错位；NOTI 族的锚点较少
（`0x0289`/`0x00AD`/`0x01C7`/`0x0187`/`0x01BA`/`0x0002` 均吻合）。上述个例不足以推翻枚举，
但**NOTI 名称的置信度应低于 CMD**，遇到行为对不上时先怀疑名称。

## 五、上游要求的 body 长度与客户端构包长度冲突

| 协议 | 客户端 | 上游 |
|---|---|---|
| `CMD 0x0128` | 20B，含条件分支 | `SecretShopBuyRequest.cs:19` 要求恰好 8B，否则整条拒绝 |
| `CMD 0x0257` | 闭合 11B，无字符串字段 | `CreateExpertJobStoreRequest` 要求 `15 + nameLen` |
| `CMD 0x02CA` | 1B | `InventoryHandler.Move.cs:220` 要求 ≥ 3B |
| `NOTI 0x0016` | 9B（offset 7 为 u16） | `BuildUserPosition` 写 8B（末位 u8） |
| `NOTI 0x0104` | 6B | 血之祭坛路径只发 1 个零字节 |
| `NOTI 0x02AA` | 259B | `BuildRejoinableDungeon` 只写 4B |

`0x0257` 这一条直接导致了提取器的一处修正：`walk_builder` 原先静默跳过未识别的直接调用，
写 dstring 的辅助函数会被整段漏掉却仍报告"布局已闭合"。现已改为跟进调用，跟不动的显式降级
为「布局部分可得 / 构包路径上有跟不下去的调用」。

## 六、上游对相当一部分 CMD 根本不解析 body

`0x0003 EXIT`、`0x0007`、`0x0009`、`0x0025`、`0x0028`、`0x000F`、`0x0060`、`0x0131`、
`0x0198`、`0x007B`、`0x013C`、`0x0270`、`0x026B`、`0x02A8`、`0x0312`、`0x035D` 等，
handler 要么只把 body 打进日志，要么完全不引用它。

**这对服务端实现是好消息**：这些 type 只需接收并回帧（若客户端注册了响应 handler），
不必理解 body。但**不能反推"客户端也没发内容"**——客户端构包点确实写了字段。

## 七、`NOTI 0x0002` 子类型 `0x02` 在本仓有两个编码器

角色列表界面走 `Dfo.Server.Protocol/Game/AccountRoster/AccountCharacterRosterPayloadCodec`，
入场序列走 `Game/StateSynchronization/SupplementalSynchronizationCodec.EncodeRoster`。
两者产出的是**同一条线级事实**——同一个 type、同一个子类型、同样的头部与条目形状——
却各写一份，包括各自的 `WriteRosterTail`。

已经因此付出过一次代价：A21 把条目尾部从 32 字节改为 36 字节时，两处都要改，
少改一处就会在两个角色的账号上丢掉第二个角色，而单角色账号看不出来。

两者的输入也不同：界面那条拿 `CharacterSummary`（本次为它补上了外观条目），
入场那条拿 `CharacterRosterMemberState`（外观来自逐角色载入的完整入场状态）。
后者顺带把等级之后那十字节建模为两个进度值加一个保留字段，而界面那条按实测字节写
`0x0B 0x01` 加两个零——**同一段字节，两种读法并存**，这一条本身也需要一个样本来收口。

**这里还有一个今天就存在的不一致**：已知良好会话在入场序列里重发的那一帧，与角色列表界面
那一帧**逐字节相同**（含等级之后的 `0B 01`）。而本仓入场路径现在写的是两个进度值，
除非某角色的首个进度值恰为 267，否则它发出的字节与该会话不同。角色列表那条已经对齐，
入场那条**尚未**——它属于入场序列成果的范围，在那之前这条差异是已知的。

> **2026-08-25 已收口。** 入场那条改为写与界面那条相同的两个实测字面量加八个零，
> 两处共用 `AccountCharacterRosterPayloadCodec.FirstByteAfterLevel/SecondByteAfterLevel`。
> **两种读法的分歧没有解决**，只是不再表现为两条不同的线级字节；仍需一个进度值不同的角色
> 样本来判定它到底是「两个字面量」还是「一个值为 267 的 `u32`」。
> 「两个编码器」这条不谐本身仍在。

**2026-09-08 更正：上面「两者的输入也不同」那一段现在还差了更要紧的一层——
两者的外观来自两个互相不同步的真源。**
界面那条的 `CharacterSummary.Appearances` 已改成从角色**当前穿戴**现算
（`CharacterRosterService.ListByAccountWithAppearanceAsync` 读账号下全部穿戴，交给
`Application/Characters/DrawnAppearance.cs`，与世界内 NOTI `0x0002` 子类型 0 同一处规则）。
同名的 `ListByAccountAsync` **不**现算，它是刻意保下来的廉价 listing，供不画外观的调用方用。
走界面那条编码器的有两个发送方：客户端请求 `0x0208`，以及建角色成功之后推的那条刷新，
两者拿的都是现算过的那份。
入场那条的 `CharacterRosterMemberState.Appearances` 仍解 `characters.appearance_blob`
（`CharacterEntryStateTables` 读列，`SelectCharacterPreparationService.BuildRosterEntryAsync`
解码），而那个列只在角色创建时写一次，`Server/src` 下零条 UPDATE（本仓代码读出）。
**所以一个玩家换了装之后，选人界面画新的，入场那一批里的角色列表帧画创建时那一份。**
两者的槽位判据也因此不同：现算那条是 `0..12` ＋ `23`（沿用世界内那一帧的），
创建时写 blob 那条是 `<= 13`。

这是刻意留下的边界：入场那一帧在字节锚 `SelectCharacterAcceptedTranscriptTests` 之内。
收口的做法是让入场那条也问同一处规则，那会移动锚里的字节，是一件独立的事。

## 十一、升级之后少发的两帧 → 只剩一帧（2026-08-27 补上其中一帧）

**2026-08-26。** `CMD 0x01E4 TUTORIAL_LEVEL_UP` 上游回四帧：`NOTI 0x0025 EXP`、
`NOTI 0x0015 ACCEPTABLE_QUEST_LIST`(25B)、`NOTI 0x0002 USERINFO`(579B)、`CMD 0x01E4 [01]`。
当时**本仓只发第一和第四**。

**2026-08-27：`NOTI 0x0015` 已补。** 原先说「两帧都是整份重投影、没有局部更新路径」——对
`0x0002` 成立，对 `0x0015` 不成立：可接任务表是一条纯规则的输出，重新调一次
`IWorldContentEntryRuleService.LoadAsync` 就够，会话现在也留着算它的入参
（`GameWorldEntryState.Subject`）。等级本来就是这条规则的入参之一，而且**这一帧的首字节就是
角色等级**，不发的话客户端连等级都是旧的。

同一次确认了两件客户端侧的事实，都来自反汇编普查而非猜测：
- `0x0015` 的注册路径是 `batch:batch`——启动时批量注册，不是运行时转发器（那 571 个才随上下文
  来去）。所以**任何时候都能推，副本里也行**；参照 08-23 那次正是在教学副本里推的。
- 全档案没有「刷新可接任务表」的 C2S 帧。这张表只能服务端主动推，客户端要不来。

**仍缺 `NOTI 0x0002 USERINFO`**（角色面板重投影）。那条确实要整份重投影，留着。

## 十三、背包内拖动一件装备时回报的数量

**2026-08-26。** `ContainerSlotItem.Count` 取的是 `Core.Value`，而装备的 `Value` 装的是**实例值**
而不是件数（角色创建时那三件就是这样写的，上游 `ResolveDropValue` 也按这个分叉）。于是在背包内
把一件装备从一格拖到另一格，`MOVE_ITEMSPACE` 回包的"移动数量"会是那个实例值 —— 一个八九位数。

穿脱路径不受影响：那两个方向明写一件。**没有实机样本**：客户端在背包内拖装备的那一帧还没抓到过，
所以不知道它对这个字段做什么。改它要动堆叠算术共用的那个属性，判据是一次背包内拖装备的抓包。

## 十六、`CMD 0x001F ACCEPT_QUEST` 是真缺口,不是有意不回

**2026-08-26。** 参照收到它并**回了** 8 字节 `01 F8 03 01 00 00 00 00`;本仓没回。

没有实现的原因是**任务表只有读路径没有写路径**(`character_active_quests`、
`character_invisible_flags` 的接口只有 `ReadAsync`)。回一个成功而没有任何东西记住这次接受,等于
宣称一件没发生的事。要收口先得有任务接受的落库,这是任务系统而不是协议管道。

那次实机里它没被应答并没有挡住任何事。

> **2026-08-27 已收口。** 领取已实现并与参照逐字节相同;三张任务表现在都有写路径,经
> `IQuestStore` 与人物、物品同一个事务参与者落定。剩下的差异是受理判据而不是管道,
> 见[第二十二条](#二十二领取任务比上游宽松两条判据评估不了)。

## 十七、进入副本没有任何准入规则

**2026-08-26。** 拒绝帧的形状齐了(同 type 的 3 字节 `00 | 错误码 | 上下文`,八个码抄自上游
`DungeonAdmissionRejectBuilder`),**判定没有**:等级、疲劳、入场道具、每日次数一条都不查。

其中等级门是最接近能做的一条:档案有 `[minimum required level]`。没有做,是因为上游的判定是

客户端本地按等级与任务过滤过列表,所以这些拒绝在原版客户端上都不可构造 —— 这也是它们排在后面的
原因。判据是先有世界地图/剧情副本的判定。

## 十九、选图打开时不发账号成长进度

**2026-08-26。** 上游 `ENTER_SELECT_DUNGEON` 在五帧之后还调
`GrowthCapsuleSync.SendExpProgressAsync`,那会发一帧 `NOTI 0x0025 EXP`(账号成长进度与荣誉)。
本仓不发 —— 账号那一层的成长胶囊数据没有建模,发一帧编出来的数字比不发更糟。

没有证据表明它与选图列表为空有关(那一帧是经验,不是列表)。判据是一次能看出账号成长条差别的实机。

## 二十、客户端普查没有 `CMD 0x0084` 的构包点

**2026-08-26。** 客户端明明发了三次 `CMD 0x0084 BACK_2_VILLAGE`,而 `protocol-identity.tsv` 里
**C2S 一行都没有**,只有 `S2C NOTI 0x0084 END_ASSAULT`。

与 `SET_UDP_IP_PORT` 同一类:构包点在静态扫不到的混淆区。这不是矛盾,是普查盲点的又一次直接确认。
静态索引仍不能凭空生成这条身份，但真实 A21 帧足以建立手写例外。现已补入
[0x0084 协议页](../protocol/game/client-to-server/0x0084.md)，并由服务端资料同步检查持续对账；
原始观察仍见 [a21-dungeon-admission-20260826](../protocol/patterns/data/traces/a21-dungeon-admission-20260826.md)。

## 二十一、解码器抛异常就拆连接，哪怕那一帧根本没人回

`Server/src/Dfo.Server.Networking/Runtime/NetworkPlugins.cs` 的 `Decode` 捕获解码异常、记日志、
**然后 `throw;`**，连接随之断开。理由写在那段注释里：读不懂的帧不是能继续会话的帧。

**但帧本身已经被读懂了。** 分帧是信封层做的——能走到 `Decode`，说明长度、类型、校验都已成立，
`Decode` 里抛出的一定是**体内布局**与我们的模型不符，而不是流失步。这两件事的严重程度不一样：

- **信封层失败**：流已经错位，后面每一帧都会跟着错，必须断。
- **体内布局不符**：流是好的，错的是我们这一个类型的模型。断连接等于把"某个类型读错"升级成
  "整局玩崩"。

2026-08-27 实机就是后者：`CMD 0x00C2 CLIENT_SPEC_PROFILE` 是一帧**上游都不回**的遥测上报，
本仓因为包头少算一字节把它抛掉，玩家在城里退出游戏时卡死。2026-08-25 的 `CHANGE_TUTORIAL_FLAG`
是同一形状。两次都不是"读不懂就没法继续"，两次都断了。

**没有在本次任务里改**：这是全局收包策略，牵一发动全身，且"继续跑"也确实会让读错的类型更晚被
发现。可选项大致三种——

1. 维持现状：任何解码异常都断。
2. 分级：只有信封/分帧失败断连接；体内布局异常记 Error 后丢弃该帧继续。
3. 折中：按类型分级，**没有回包的纯上报类型**（本仓的 `IUnansweredReport` 那一族）异常时丢弃，
   其余照断。

倾向是 3——它精确对上了两次事故的形状，又不会让一个需要回答的请求被静默吞掉。

> **2026-08-27 已决定：暂时维持 1（任何解码异常都断），等协议覆盖度上来再按重要程度分级。**
> 理由是覆盖度：现在还有大批类型没有解码器，此时降敏等于给自己留一批"读错了也照跑"的静默
> 漏读，而这类漏读正是要靠断连接才会被立刻发现的。分级本身没有被否掉，只是判据不足——
> 等大部分协议落地之后再做，那时"哪些类型没有回包"才是一份完整的名单而不是一个片段。
>
> 这条决定现在有线级对照（2026-08-27 打在跑着的服务端上）：捕获的那帧 362 字节被接受、
> **0 帧回应**、随后 `CMD 0x04DD` 仍被答——连接存活；把它截成 A12 的 361 字节，**连接当场中止**。
> 探针是一次性工具没有入库，复现步骤与观察记在
> `protocol/patterns/data/traces/a21-exit-and-return-20260827.md` 五之二。

## 二十二、领取任务比上游宽松：两条判据评估不了

**2026-08-27。** `CMD 0x001F ACCEPT_QUEST` 已实现，但上游的六条受理检查本仓只做到四条。
评估不了的两条是：

- **已通关且不可重复**（上游拒绝码 `18`）
- **前置任务未满足**（上游拒绝码 `21`）

两条都需要同一份状态：**这个角色通关过哪些任务**。承载是有的——`character_invisible_flags`
就是那张表，入场投影一直把其中非零的行读成已通关任务，任务日志现在也能写它。
缺的是内容：**还没有任何东西能完成一个任务**，所以每个角色的已通关集合恒为空，
按空集判定等于把两条检查写成恒真。

于是本仓会**接受**上游会拒绝的请求。真实客户端只提供自己那份状态允许的任务，其余在发送前
自行拦下，所以从实机基本够不到；构造帧够得到。

**不在本次收口**，因为收口的前提是任务完成落地，而那是另一段协议。等 `FINISH_QUEST` 那条
做完，已通关集合才第一次非空，这两条检查也才有判据。届时回来划掉本条。

顺带一条命名：`0x001F` 在两个族里是两个协议——CMD 是领取任务，NOTI 是副本通关公告开关。
本仓给了两个常量（`AcceptQuestType` 与 `EnableClearDungeonNotificationType`），值相同、名不同。

## 二十三、可接任务表里有已经受理的任务：本仓有意与参照不同

**2026-08-27。** 唯一一条**主动偏离参照字节**的条目，单独记在这里。

参照的 `NOTI 0x0015 ACCEPTABLE_QUEST_LIST` 由等级、职业、成长、已通关任务与宠物条件算出，
它的构造器 `QuestListBodyBuilder.BuildBody(level, job, growType, clearedFlags, allowedCreatureKinds)`
**没有「当前持有」这个入参**——所以它列出角色正拿着的任务不是疏漏，是构造上做不到。

实机后果是可见的：主线任务由客户端自动弹窗，弹窗依据就是这张表。玩家接下任务后服务端
受理并回这张表，表里那个任务还在，客户端于是**再弹一次**，玩家再接一次，第二次被拒
（`00 12`）。参照抓包 `packet_log.upstream-finishquest-20260827.txt` 里同一段被点了四次、
只受理一次——**参照服务端在真客户端上复现同样的行为**。

**本仓的读法：可接与已接是两个状态，表里去掉正持有的。** 落在两处：

- `WorldContentSubject` 增加 `CarriedQuestIds`，入场算表时就排除；
- 受理与交任务之后，从会话缓存的那份里去掉该任务并写回会话（`QuestOffers.Without`）。

**为什么敢偏离。** `ServerS4A21` 不是官方服务端，它是另一份对同一个客户端的重写实现——**只有
参考价值，不是权威**。权威是客户端自己：反汇编出来的构包点与 handler，以及实机表现。一份能让
真客户端把主线弹窗连弹两次的实现，说明错的是它。判据也在客户端手里：弹窗不再弹第二次，就说明
它认这个读法；仍然弹，就退回参照的发法并把这一条改写成"客户端要求如此"。

**第一版是减法，那是错的。** 只把受理/通关的任务从缓存那份里删掉，能解决弹窗重复，却做不了另一半：
通关可以满足**别的任务的前置**，那个任务必须**出现**，而只会缩短的表永远不会有它。档案里就是现成的
案例——任务 1776 声明 `[pre required quest] 101`，交掉 101 正是它该出现的时刻。2026-08-27 实机撞上：
玩家交完青之守护者塔娜，没有新主线、也进不了副本，只能退出游戏重进。

现在是**重算**：`GameWorldEntryState` 额外保存算表用的 `WorldContentSubject`，受理和交任务之后用
当前的等级、已通关、正持有重新调一次 `IWorldContentEntryRuleService.LoadAsync`。两个方向都对了。
