# Themida API 包装层还原：用 x86 语义求值，不是规则匹配

更新时间：2026-08-23

## 结论摘要

S4A21 的 `.text` 通过 `.-wI` 段的一层「包装器」调用所有 Win32 API。这层包装是
Themida 生成的变形代码，每个调用点一个专属副本，从不复用，静态看不出调的是谁。

**现在能看出来了。1654 个包装器已命名到具体 API**（338 个不同 API），
方法是把包装器当程序**执行**，而不是识别它的生成规则。

| 调用方 | 已命名包装器 |
| --- | ---: |
| `.text`（游戏主体） | 749 |
| `.tls`（伪装段，实为游戏 C++ 代码） | 673 |
| `.vmp1` | 215 |
| `.mackt` / `.#|U` | 17 |

配套的 `crossmodule-relocs-a21.csv` 是用双 dump 差分独立测出来的，两种方法在
**351 个重合行上零矛盾**；更进一步，差分法定不了的 9 行现在有了见证人，**纠正 8 行**，
`.-wI` 那侧的「同 delta 歧义需要再来一次重启」因此不再是阻塞项。

| 产出 | 位置 |
| --- | --- |
| x86 部分求值器 | `ClientHack/tools/symeval.py` |
| 包装器解析器 | `ClientHack/tools/resolve_wrappers.py` |
| 结果表 | `ClientHack/tools/wrapper-apis-a21.csv` |

## 为什么之前六次都失败：锚点选错了

包装器把 API 地址以 `api + K` 的形式存在镜像里，K 每个站点不同。此前六次尝试全部
**从数据出发**，试图恢复 K：

| 尝试 | 结果 |
| --- | --- |
| 同模块共享一个 K | 95 个站点 95 个不同 K |
| K = f(站点地址) | 0/452 |
| 共享解码 helper | 188 个站点 186 个不同 helper |
| K 是 64K 对齐 | 6/452（噪声水平） |
| 镜像里存着 K 表 | 分布跟着数据量走，不跟着表走 |
| 对数据后面的代码符号求值 | 0/188 |

失败的共同原因在最后一次测量里暴露：**全镜像逐字节只有 21 处引用指向那 455 个数据站点，
而随机期望约 3 处**。没有任何东西存着指向它们的指针，读它的代码是用算术把地址算出来的。
从数据出发根本没有线头可拉。

正确的锚点在另一头：**`.text` 直接 `call` 进 `.-wI`，这些目标在构造上必然是真入口**，
因为是编译器生成的游戏代码在调它们。从入口正向求值，K 根本不需要被恢复。

## 方法：这不是反混淆器

`symeval.py` 对 Themida 一无所知。它实现的是 x86 指令语义，一条一条实现，混淆是**副产品**地坍塌掉的。

这个区别有可检验的后果：猜生成规则的话，待办列表无界且由对方控制；补指令语义的话，
待办列表被 x86 指令集**封闭**了，Themida 发明不出新指令。

实际起作用的是三种机制，只有第二种沾「等价」：

- **具体求值**——生成器把常量烤进了代码，所以大部分垃圾只是一道很长的算术题。
  例：`mov ecx,0x260072a6` / `not ecx` / `neg ecx` / `dec ecx` / `add ebp,ecx`，
  求值器没有「not+neg+dec 是恒等」这条规则，它就是在算。
- **表达式化简**——对合相消、`(x op k1) op k2 → x op (k1 op k2)`。这是代数，
  在 Themida 出生前就成立。
- **死代码**——不存在「消除」这一步。写了没人读的寄存器天然不出现在最终表达式里。
  「混淆指令」在这里的定义就是「答案不依赖的部分」。

求值器看不穿的只有两样：真正依赖运行期状态而 dump 里没有的东西；以及**虚拟化**——
忠实求值一台 VM 解释器，得到的是解释器，不是它解释的那个函数。`.vmp1` 的 2508 个入口
是另一个问题，同一把锤子，那不是钉子。

## 求值器的五个窟窿

每次「卡住」最后都是模型的缺陷，不是壳的新花样。每补一个都是**通用**的涨，横跨所有模块：

| 修复 | 命名数 |
| --- | ---: |
| 换锚点（从 `.text` 的调用目标出发） | 97 |
| 私有栈不该被野指针存储污染 | 105 |
| **条件跳转要判定，不能一律当空操作** | **228** |
| 补 `bt/bts/btr/btc`、`adc/sbb`、`rcl/rcr`、`cmovcc`、`xadd`、`sar`、`lahf/sahf`、`rep movsb` | 237 |
| **内存模型改成字节粒度** | **475** |
| **`ret` / `ret imm` 要调整 esp** | **644** |
| 喂入真实返回地址 | 695 |
| 用字节扫描补全调用点 | **749** |

（以上是 `.text` 一侧的口径；把普查扩大到其他段后总计 1654。）

三个最大的收益都不玄：

- **不透明谓词是可判定的。** 它对混淆器有价值的前提就是生成时可判定，所以输入是具体值。
  补上 CF/ZF/SF/OF/PF 的具体求值，一次多认出 123 个。
- **x86 的内存本来就是按字节寻址的。** 模型只认 4 字节，于是
  `mov word ptr [esp+0xc],0x1fd5` 会把整个槽抹掉。壳大量使用混宽度栈写，八成正是冲这个来的。
- **`ret` 要弹栈。** 单跳链看不出来（返回值就是答案），多跳链每跳偏 4+imm 字节。
  中位跳数是 1，所以它藏了很久。

另外两条是正确性而非产量：未建模指令必须把标志位置为**未知**（否则后面的 `jcc` 会用一个
从不存在的值判定）；行走必须有**可执行段围栏**（本镜像里段名是伪装，`.code`/`.data`/`.rdata`/
`.eI4`/`."2A` 都不可执行，走进去会把数据解码成指令并给出一个纯由噪声构成的自信答案）。

## 校验：为什么这些名字可信

**结构校验（每次）**：算出的目标必须落在「dump 里真正占据那段地址的那个模块」的
**真实导出地址**上。导出表只有几千个地址散在 4GB 空间里，单次误中概率约 1e-6。

**跨 dump 校验（决定性）**：三份模块布局不同的 dump（user32 基址 `77A10000` vs `753A0000`），
逐个包装器解析，**644 个全部命名且 API 名 100% 一致**。这不是「落在某个导出上」，
而是「在不同地址布局下落在**同一个函数**上」。

**跨方法校验**：与差分法测出的重定位表在 351 个重合行上**零矛盾**，
且没有任何一行被 1654 个包装器中的任意两个指向不同模块。

尚未做的：拿运行中的客户端独立验证。上述全部是离线证据。

## 包装器普查：谁在调这一层

对每个可执行段做字节扫描，找出所有 `call rel32` 落进 `.-wI` 的调用点：

| 源段 | 候选调用点 | 已命名 | 与 `.text` 共享入口 |
| --- | ---: | ---: | ---: |
| `.text` | 1174 | 749 | — |
| `.tls` | 716 | 673 | **0** |
| `.vmp1` | 390 | 215 | **0** |
| `.mackt` | 147 | 16 | **0** |
| `.#|U` | 104 | 1 | **0** |
| `.bss` | 3 | 0 | **0** |

（候选数含字节扫描误报，光靠计数无法与「确实难解的包装器」区分。）

两个结论：

**`.tls` 是游戏代码，不是壳。** 它 2.37MB、可执行、名字是伪装。673 个已命名包装器里
**596 个调 `msvcp60.dll`**——`std::string` / `std::vector` 那套。Themida 把客户端一大块
C++ 代码搬进了这个段。全局按模块看，`msvcp60` 以 678 次高居第一。

**各段的包装器集合几乎完全不相交。** 六个源段两两之间只有 `.mackt ∩ .tls = 3` 一处重叠，
其余全是 0。每个包装器入口基本只属于一个调用方，这直接消掉了下面改造方案的风险 1。

## `.-wI` 段内部：99.5% 一次性，外加十来个共享件

对全部可执行段做完整线性扫描（capstone，带重启循环），统计落进 `.-wI` 的直接转移目标：

```
.-wI 内部   22301 call   26592 jmp      ← 段内自己跳自己
.text         713 call       7 jmp
.tls          668 call      17 jmp
.vmp1         267 call      33 jmp
.mackt        134 call     244 jmp
.#|U           45 call      42 jmp
.bss            1 call

被指向的不同 .-wI 地址：51031
```

**内外两层是干净分开的**（改造方案的风险 4，已排除）：

| | 数量 |
| --- | ---: |
| 只被段内进入 | 48849 |
| 只被段外进入 | 2152 |
| 内外都进入 | **16** |
| 其中是已命名包装器的 | **0** |

**引用次数分布极度倾斜**：

```
refs = 1      50791   (99.5%)
refs = 2..9     187
refs = 10..99    42
refs >= 100      11
```

变形织体几乎完全是一次性的——每条链专属，从不复用。例外只有那 11 个高引用地址，
形状高度一致，都是栈帧准备后转走：

```
05D1C88E  (389 refs)   dec esp ; lea ebp,[esp+0x100] ; jmp ...
05AA628D  (272 refs)   lea eax,[esp+0x60] ; jmp ...
05AA7FB2  (272 refs)   lea ecx,[esp+0x60] ; jmp ...
```

它们是生成器唯一复用的构件，主要由 `.mackt:jmp` 和 `.-wI:jmp` 到达。

## 结构发现

**1:1 专属。** 713 个（capstone 扫描口径）入口的入度**全是 1**——每个调用点一个专属包装。
这和「452 个 K 全都不同」是同一件事的两面。

**每个包装器恰好读一个重定位行。** 642/644 精确成立。240 个不同的行被 749 个包装器消费，
平均 3.1 个包装器共用一行——**站点存共享的 `api + K_site`，每个包装器再套自己那层变换**。

**四种调用约定**（下表为 `.text` 一侧口径）。用带标记的栈实测「API 在入口看到什么」，对照正常 `call` 应为
`esp+0, [esp..] = R a1 a2 a3`：

| 组 | 数量 | API 看到 | 含义 |
| --- | ---: | --- | --- |
| B | 287 | `esp+0`, `R+1 a1 a2 a3` | 返回地址 +1 |
| A | 305 | `esp+4`, `R a2 a3 a4` | 吞掉调用方压的第一个 dword |
| C | 68 | `esp+4`, `a1 a2 a3 a4` | 返回地址被换成 a1 |
| D | 61 | `esp+8`, `a2 a3 a4 a5` | 吞两个，a2 当返回地址 |

B 组的 `.text` 调用点长这样：

```
00466C91  e8 a3 36 54 05    call 0x59aa339
00466C96  c3                ret            <- 返回地址正指着这个字节
00466C97                    lea ecx,[ebp-0x1c]   <- 真正的续行点
```

那个 `C3` 是给静态反汇编看的**诱饵**：顺着走会认为函数到此结束。包装器把返回地址 +1
交给 API，于是 API 返回时跳过它。

## 后续改造方案

目标是让 `.text` 直接走标准导入表，`.-wI` 那层不再被需要。**方案是改包装器入口，不改 `.text`。**

不改 `.text` 的三个理由，都是测出来的：

1. **尺寸对不上。** 调用点是 5 字节 `E8 rel32`，`call dword ptr [IAT]` 是 6 字节。
   只有 B 组因为后面那个诱饵 `C3` 才刚好凑够。
2. **四种约定改法不同**，A 组还要连带删掉 `call` 前那条 `push`，其编码有 1/2/5 字节三种。
3. **还有没解出来的**，动了 `.text` 会变成混合状态。

```
新增 .chiat 段：每个不同的 (module, function) 一个 IAT 槽 + import descriptor
                → Windows 加载器按名字自己绑定，不需要任何运行期代码

每个包装器入口原地改写（本体 25~130 条指令，空间绰绰有余）：
  B 组   add dword ptr [esp], 1 ; jmp dword ptr [IAT_slot]
  A 组   把返回地址上移一格吃掉那个 push ; jmp dword ptr [IAT_slot]
  C 组   add esp, 4 ; jmp dword ptr [IAT_slot]
  D 组   add esp, 8 ; jmp dword ptr [IAT_slot]
  未解出 不动，继续走原包装器
```

收益：`.text` 一个字节不改；IDA 会把两条指令的 thunk 识别成 `jmp ds:PtInRect` 并把名字
传播回所有调用点；重定位表 532 行里 **351 行**（已被见证的全部）变成死行。

**风险清单**：

1. ~~这些入口是否只被一个调用方进入。~~ **基本排除**：各段包装器集合两两之间
   只有 `.mackt ∩ .tls = 3` 一处重叠，其余为 0。那 3 个改造时单列。
2. 壳的运行期是否校验包装器本体。`.-wI` 运行时读 `.eI4`（1.05MB，熵 7.96，磁盘上 raw size 0），
   若那是完整性校验，改了会被发现。**只能实测。**
3. 约定是符号执行**单条路径**测出来的。三份 dump 一致是证据，不等于路径无关。
4. ~~某个外部入口同时是 `.-wI` 内部跳转的落点。~~ **已排除**：内外都进入的地址只有
   16 个，其中已命名包装器 **0** 个（见上）。

风险 2 最适合先用插件试：ClientHack 已有 `patch_apply`，在运行期打桩跑一个副本，
出问题删插件即可，不必碰那个 94MB 的 exe。

## 未决

- 532 行重定位里还有 **181 行**没有见证人：`.-wI` 104、`."2A` 47、`.code` 18、
  `.tls` 10、`.mackt` 2。其中 `."2A` 那 47 行是 K=0 的明文指针，
  `name_api_sites.py` 已能直接命名，不需要见证人。
- 17 行 `same-delta` 歧义已解 9 行；另有 20 行 `range-tiebreak` 仍未被见证。
- 那 11 个高引用共享件（`refs>=100`）没有单独分析过；它们不是包装器入口，
  但改造后若原包装器本体不再执行，需确认没有别的东西依赖经它们的路径。
- 剩余未命名的包装器：多数卡在一次无法折叠的内存读，少数碰到 `int3`/`int`。
- `.vmp1` 的 2508 个虚拟化入口未处理。上游的做法是照干净参考实现**重写**
  （`CThread::Create`、`ISocket::Write`），不是还原。
