# `.vmp1` handler 枚举：普查开工前的 Phase 0，以及它推翻的三件事

日期：2026-08-31。前置：`Docs/a21-vmp1-virtualization.md`、`Docs/a21-vmp1/vmp1-7.md`。

为 handler 语义普查做确定性解码包时，Phase 0 推翻了三个前提。**普查未开工**——
枚举问题必须先解决，否则会普查一个错的集合。

## 一、规模先更正

`.vmp1` 完整虚拟化的目标是 **1,472 个**（1,673 个 call 目标里不可读的那部分），
不是「2,508 个入口」——后者复现不出来，真实计数是 call 1,673 / jmp-only 2,867 /
并集 4,268 / 过滤后 3,557。

## 二、`symeval` 可以直接提取 handler 语义（好消息）

`symeval.run(img, va, follow=True, xok=...)` 在 `0x05275444` 上**逐字节复现**了
`vmp1-7.md` 手工解出的 17 条指令 trace，自动跟穿两次 `call`-当-`jmp` 蹦床
（被调用方 `lea esp,[esp+4]` 丢掉返回地址），停在间接派发跳转上。

**所以 handler 语义提取不需要 Unicorn**，`symeval` 够用。这一条成立。

## 三、推翻：偏置不止一个，「158 个 handler」是单偏置扫描的产物

`vmp1-7.md` 的注释写了「per-handler bias, NOT 0x4CC42998」——**这句话是字面意思**。
每个派发点带自己的加性偏置。用单一偏置扫描字节码，只能找到**经由该偏置可达**的 handler。

对偏置做闭包迭代（追踪 → 收割派发表达式里的加性常量 → 用集中度筛出真偏置 →
扫描 → 再追踪），第 4 轮收敛：

```
0x31D7789A  k=167   hits=187,375        0x32843B90  k=293   hits=44,720
0x5B7DF9F4  k=158   hits=166,253  ←文档  0x4B4826E0  k=358   hits=41,718
0x5BAD2460  k=141   hits=136,695        0x28563364  k=381   hits=34,771
0x28971298  k=181   hits=79,963
```

**至少 7 个派发偏置**，候选地址并集 1,199 个。文档记的 158 是 `0x5B7DF9F4` 的 top-k。

## 四、推翻：静态 dword 扫描不足以枚举 handler

对 1,199 个候选逐个符号追踪：

```
停在派发上 (jmp/ret)   407
预算耗尽               342
ret 但目标不带已知偏置  288
间接 call              112
解码出 int / iretd / int3   50   ← 明显是把数据当代码
```

**只有 34% 停在派发上**，且这 407 个归一化后有 **380 种不同形态**（克隆因子中位数 1）。
既不像「~158 个语义 handler 的克隆集」，也不像干净的 handler 集。

根因是命中率：单偏置命中 2.03%，8,175,613 个 dword 位置里 166,253 个「落回 `.vmp1`」，
绝大多数是巧合。**集中度是信号，尾部是噪声**，而多偏置取并集把噪声成倍放大。

## 五、正确的枚举路线：从真 VM 入口走字节码

`vmp1-7.md` 的结果是 **Unicorn 仿真 282 个真 VM 入口**得到的——那才是对的方法：
只会走到真 handler，按执行顺序，且操作数宽度由实际步进给出。

**但那套仿真工具不在仓库里**（`ClientHack/tools/` 没有），本机也没装 Unicorn。
文档留下的是结论，不是可复现的工具。

不过重建它不需要 Unicorn，`symeval` + 已知的密钥调度就够：

1. 找 `push imm32; call vm_entry` 桩（文档记 282 个）；
2. `VIP = rol(key,9) + 0xBD81ACE6 + delta`（已算术验证：235/258 落在 `.vmp1` 内）；
3. `handler = [VIP] + 0x4CC42998`；
4. `symeval` 追踪该 handler → 得到它的 VIP 步进与**它自己的**派发偏置；
5. `VIP += 步进`，`next = [VIP] + 该 handler 的偏置`；回到 3。

走完即得该 VM 函数的真实 handler 序列。对 282 个入口做一遍，并集就是 handler 集。

## 六、结论

**闸门不是 handler 语义，是 handler 枚举。** 语义提取已经验证可行（`symeval`），
但在枚举解决之前，任何普查都会普查一个不可信的集合。

下一步是重建 VM 字节码走行器（第五节五步法）。它同时产出：
真 handler 集、每个 handler 的操作数宽度、以及 282 个 VM 函数的字节码序列
——后者正是去虚拟化的输入。

## 七、静态枚举三次失败，根因是同一个

尝试按第五节的五步法建走行器，卡在第 1 步——**找不到真 VM 入口**：

- 53 份 vm_entry 克隆能可靠定位（用不含自重定位常量的 29 字节不变段匹配，
  数量与文档「41~53 份」吻合）；
- 对克隆的直接 `E8`/`E9` 引用有 **14,760 处**；
- 但按「`push imm32` + 寄存器保存串 + `jmp`」回溯，只匹配到 **15 个**候选，
  其中只有 **1 个**密钥能算出落在 `.vmp1` 内的 VIP。

原因看原始字节即知——进 vm_entry 的路径本身是变异过的，连续多个 `jmp` 串联：

```
68 09 d1 23 9f   51 52 53 50 56   e9 c7 8f 5e 04 ...   <再一个 jmp>
push key         push 寄存器串      jmp                    jmp vm_entry
```

**静态方法在 `.vmp1` 上已经失败三次**：偏置扫描（34% 命中率）、形态聚类
（1,199 → 1,107 种形态，不是克隆）、入口提取（15/14760）。根因同一个：
`.vmp1` 及其周边控制流被 Themida 的变异层覆盖，静态模式匹配测的是变异器的输出分布，
不是程序结构。这与 `a21-vmp1-virtualization.md` 里那条方法学修正是同一件事的另一面。

## 八、正确路线：活体捕获 VM 入口

文档的结果来自 Unicorn 仿真「282 个真 VM 入口」——那些入口本身多半也是**跑出来的**。

现在有当时没有的条件：**包装器改写工作中已建成并验证的活体插桩设施**
（`0150_WrapperPilot` 的一次性 `0xCC` 陷阱 + VEH + 还原继续，四局会话零故障）。
把同一手法用在 VM 上：

1. 在 53 份 vm_entry 克隆各下一个一次性陷阱；
2. 命中时从栈上读密钥（文档已测：保存顺序不变，密钥在 `[esp+0x20]`）、
   记录调用方返回地址，还原字节并继续；
3. 一局游戏即得**真实 VM 入口清单 + 真实密钥**；
4. 有了真密钥，第五节的五步走行器就能纯静态跑完剩下的部分
   （VIP 由密钥算出、handler 由 `symeval` 追踪、偏置从派发表达式取）。

陷阱是一次性的、命中即还原，对会话无影响——与见证模式完全同构。

## 九、活体捕获成功，走行器跑通（2026-08-31，已完成）

### 9.1 捕获

新插件 `0160_VmEntryTrace`（`plugins/0160_vm_entry_trace/`，零警告编译）：
在 53 份 vm_entry 克隆的字节 0 各下一个 `0xCC`，命中时从 `[esp+0x20]` 读密钥
（调用方已压入密钥 + 8 个保存的 dword，保存顺序不变），然后**模拟被覆盖的
`call $+5`**（压 `clone+5`、`EIP = clone+5`）而不是还原字节——
**陷阱因此在命中后仍然挂着**，每次 VM 调用都被观测，而不是只抓第一次。
攒够 `MaxKeys` 个不同密钥后自动全部拆除，会话恢复满速。

一局完整会话（登录→副本→退出）结果：

```
armed 53/53 vm_entry clones (0 byte mismatches)
distinct VM keys captured: 1,028
key schedule: 961/1,028 (93.5%) 的 VIP 落在 .vmp1 内
distinct first handlers: 33          ← 文档静态推算为 32，独立复现
entry clones actually used: 34 / 53
```

对比静态提取（15 个候选、1 个有效），活体捕获**登录前就拿到 170 个、98% 有效**。

### 9.2 走行器

`ClientHack/tools/walk_vmp1.py`。关键点是**派发偏置取自 handler 自己的 trace**
而不是全局常量——这正是扫描法失效的原因：

```
VIP  = rol(key,9) + 0xBD81ACE6
h    = [VIP] + 0x4CC42998 ; esi = VIP + 4        ← vm_entry 自己的偏置
loop:  symeval 追踪 h → 操作数宽度 与 h 自己的派发偏置 b
       next = [esi] + b ; esi += 4 + 操作数宽度
```

全量 961 个 VM 函数：**960 个走到干净终止**（「handler 不派发（ret）」＝ VM 退出
handler），1 个下一 handler 不可执行。

```
派发步总数     36,215        步数 min/中位/max = 12 / 28 / 218
不同 handler   977，分布极不均匀：
   41 个覆盖 50%   161 个覆盖 80%   276 个覆盖 90%
   核心 84 个（≥100 次引用）占每个函数步数的中位数 82%
   长尾 184 个只出现 1 次、395 个出现 2-9 次（大概率是每实例变异的克隆）
操作数宽度     +5 ×19,576   +4 ×11,116   +8 ×4,172   +6 ×391
```

最后一行独立复现了 `vmp1-7.md` 的实测 VIP 步长分布（+5 ×1889 / +4 ×549 / +8 ×324），
比例一致。
