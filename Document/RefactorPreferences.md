# 重构判断与设计考量

调整结构前结合 [Architecture.md](Architecture.md) 判断。以下是项目设计偏好的归纳，
用于判断当前改动；具体需求与用户决定优先，不能据此自行扩大任务范围。

## 何时重新划分职责

| 信号 | 需要检查的问题 |
|---|---|
| 同一事实有第二份快照、平行集合或同步副本 | 能否从唯一 owner 查询，消除同步义务？ |
| 同一判定存在多种算法或多处口径 | 是否属于一个领域服务或规则服务？ |
| 一个关系重复声明、只靠名单维护 | 能否用类型、编译期、注册检查和拒绝反例守护？ |
| 每新增协议都要改同一个业务文件 | 是否缺少协议切片或注册边界？ |
| 名称、DTO 或接口形状误导调用方 | 是否应按领域概念命名和分层？ |
| 领域为扇出通知去查连接或组协议字段 | 是否应交给通知／协议边界？操作主体自己的会话例外见事件指南。 |
| 用延迟解析、可空依赖或同步补丁绕结构问题 | 是否应拆清职责、消除依赖环或副本？ |
| 新功能需要建立在不合适的状态模型上 | 是否应先修正模型，再添加功能？ |
| 内容、客户端或协议证据变化 | 现有假设是否仍成立，失配能否被检查发现？ |

## 实施原则

- 按概念和不变量划分领域，不按协议段或数据库表机械拆分。
  合表要同时满足同一键、同一生命周期、同一写入用例；不能只因字段相近合并。
- 让错误编译不过、启动失败或由真实行为测试暴露，减少只能靠人记住的约束。
- 先明确当前真源、证据与待定项，再修改结构。结构搬迁与行为变更分别说明和验证。
- 声称行为不变时，使用可观察且能失败的依据，如字节基线、表征测试、反例或真实工作单元结果。
- 在已批准范围内完整迁移调用方并删除失效路径；确需兼容时说明仍存在的消费方和边界。
- 服务端与客户端各自的判断权由协议证据决定，不替客户端猜测或主动推进未获证实的流程。
- 修正错误结论时更新当前正文；保留影响正确判断的证据和陷阱，不保留演化流水账。
- 范围外问题交由用户决定，不借重构顺手扩展；既有参考单体仅用于行为对照。

## 验证的两个盲点

反向检查既要看拒绝点，也要看谁能制造违规状态；仅覆盖一个写入者不等于覆盖了约束。
规则检查应扫描真实生产类型，并有反例证明违规形状会被拒绝；一张允许名单不能自行证明架构正确。
