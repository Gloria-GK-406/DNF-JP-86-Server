# 装扮栏条目的形状（实机判定，2026-09-07）

## 结论

**装扮栏（`listType = 1`）的每条条目是「101 字节记录 + 一段 u32 长度前缀的数据」，
而不是主背包那样的定长 101。** 服务器此前只发 101 字节，客户端读完记录后继续读 4 字节
当长度，那 4 字节落在接收缓冲的填充区，于是拿到 `0x30303030`，随即以这个长度做 memcpy
把栈打穿。

**这条已由实机判定，不是推断**：把 A12 时代那 42 字节长度前缀块**只对装扮栏**补回去之后，
客户端正常进入游戏，装扮栏里能看到时装，服务器零异常。

## 判定它的那次实验（隔离矩阵里唯一缺过的一格）

| 主背包 | 装扮栏 | 42 字节块 | 结果 |
|---|---|---|---|
| 有时装 | 空 | 按物品种类追加（A12 原样） | 崩 `0xC0000409`（栈溢出） |
| 有时装 | 空 | 不追加 | **不崩** |
| 无时装 | 有时装 | 不追加 | 崩 `0xC0000005`（野长度） |
| 无时装 | 有时装 | **只对装扮栏追加** | **不崩** ← 本次 |

**A12 那个块一直是对的，错的是它的条件**：原实现按「物品是不是时装（`ItemKind == 8`）」
判断，于是主背包里的时装也带上了尾块，打乱了 `listType 0` 的定长 101 跨步——那是主背包
`STATUS_STACK_BUFFER_OVERRUN` 的成因。**正确条件是按容器，不是按物品种类。**

## 转储里的逐字节证据

客户端工作缓冲（`dnf-gs-avatarbag.dmp`）：

```
0b351022  01            listType = 1
0b351023  e3 01         listParam16 = 483   ← 见下方说明，这不是游戏的值
0b351025  01 00         count = 1
0b351027  ……            101 字节记录起点
0b35108C  ← 记录末尾（0b351027 + 0x65），也正是 '0' 填充的起点
0b351090  ← 全局包读游标 [0x03BAAE38] 停在这里 = 记录末尾 + 4
```

`'0'` 填充的起点与记录末尾**是同一个字节**，游标恰好再多 4 —— 即客户端在记录之后
**又从流里读了一个 u32**，读到 `0x30303030`（ASCII `"0000"`）。

> **上面那个 `listParam16 = 483` 不是任何权威来源的值**，是本仓调试期手工写进
> `character_container_state` 的一个凑数（按 `7×7×10−7` 猜的）。它对本节要证的事
> （游标越过包体、把填充当长度）没有影响，但**不得被当成实测到的容量**。
> 上游对装扮栏发 **0**，`ItemSlotBoundService.GetAvatarOpenRange` 收下该参数直接丢掉、
> 恒返回 `0..209`。逐容器的正确含义见
> `protocol/game/server-to-client/NOTI-0x000D.md` 的补记。
>
> 另注：本节这份转储的装扮栏 `count = 1`（一件普通堆叠物），与后来做扩容对照那两次
> （各 11 件时装）**不是同一次会话**。

## 相关的原生代码（非虚拟化部分，`u` 直接可读）

```
read_bytes(dst, len) @ 0x027C5380
  027c5383  mov eax,[ebp+8]      ; dst
  027c5387  mov esi,[ebp+0Ch]    ; len ← 调用方传入
  027c538b  mov edi,[03BAAE38]   ; src = 全局包读游标
  027c5394  call 02c61c00        ; memcpy(dst, src, len)   ← 崩在这里面
  027c5399  add edi,esi          ; 游标 += len
  027c539c  mov [03BAAE38],edi

F @ 0x01637740   （崩溃链上 0x0117D028 调它）
  01637743  mov eax,[ebp+10h]    ; 第三参 = 容器选择子
  01637749  cmp eax,1            ; == 1 → 装扮栏
  0163774e  mov eax,[ebp+8]
  01637752  call 0274fbe0        ; ← 只传缓冲；长度在它内部算
  0163775f  cmp eax,3            ; 另一条支路
```

`0x0274FBE0` 是 VMProtect 虚拟化的（`jmp 0572B79D` + `push 0E2A3F942h` + VM 分发器），
**但不需要反它**：上面的字节流已经把它的行为说清楚了——它从流里读一个 u32 长度，
再 `read_bytes` 那么多字节。

## 与静态分析结论的分歧，及其判定

另一个 agent 的静态分析结论是「装扮栏库存**无可发形状**，经 `0x000D` 或 `0x000E` 发都必崩」，
依据是容器全局 `*[0x3A5C9D0]` 只由选择子 = 1 取到，而 1 正是 `F` 的致命 `kind`，同一字节绑死。

推理本身成立，但结论被实机推翻。差别在于：**进了 `0x0274FBE0` 不等于必崩**——
崩的前提是它读到的长度是垃圾。发对了长度前缀，这条路就是通的。

它另有两处值得记的：
- `[ebp-0x17d]` 确是真字段（`0x0117C6C2` 用 `read_byte` 从 NOTI 体读入的容器选择子）。
  本仓此前有一处观测说它「不是 listType，只是 `0x16A8` 的高字节」——**那句说过头了**，
  当时只有「值为 0」这一个观测，与两种读法都相容。已更正。
- 目标缓冲是 `[ebp-0x58]`，到 /GS cookie 72 字节、到返回地址 92 字节。
  它据此推「即便长度正确、拷 101 字节也已越界」——该推论假设被拷进去的是那条 101 字节记录；
  实机结果表明这条路拷进去的是长度前缀数据（30 字节 + 4 字节），在 72 字节之内。
