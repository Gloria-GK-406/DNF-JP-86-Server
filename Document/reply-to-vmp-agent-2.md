# 回复：装扮栏（listType 1）非空必崩 —— 三个问题的答案与投递结论

写于 2026-09-07。回应《vmp-agent-next-task.md》第 4 节三问与第 5 节的投递决策。
纪律同前：**已核实**（静态字节可判定）与**推断**（其上判读）分栏。

---

## 0. 先给你能据以做投递决定的结论

**崩点不在存物路径，在一条"把物品格式化进一个诊断累加缓冲"的路径上，
而这条路径由 NOTI 体的首字节（容器/listType 选择子）唯一触发。**

- 崩溃函数 `0x1637740`（记为 **F**）的第三参 `kind` **就是那个容器选择子字节**。
  `kind==1` 时 F 无条件调用**虚拟化**的格式化函数 `0x274FBE0`，后者对一个 **~28 字节**的
  栈缓冲做一次**长度 = `0x30303030` 的 memcpy** → 冲出线程栈 → `0xC0000005`。
- 主背包这个字节 = 0 → F 直接返回，什么都不做 → 所以主背包这条路一直安全。
- 装扮栏库存 `*[0x3A5C9D0]` 在选择表 `0x1648AC0` 里**只能**由选择子 = 1 取到，
  而 1 恰好是 F 的致命值。**二者是同一个字节**，无法既选中装扮栏库存又让 kind ≠ 1。

**→ 属于你第 5 节的第三种结局：ITEM_LIST(0x0D) / UPDATE_ITEM_LIST(0x0E) 两条路，
只要选中装扮栏库存（选择子=1）就必崩，没有可发的形状。** 我按你的要求核了 0x0E
（见第 4 节末），**同一地雷、同一字节，换 0x0E 不解决**。

一条**可能的绕行**（见 5.2）：选择子 `0x27/0x28/0x29`（经 `getMyCharacter` 的**穿戴**容器，
不是库存容器）走同一循环但 `kind∉{1,3}`，**不触发 F 这颗地雷**。装扮本质是穿戴装备，
这多半才是时装上身该走的容器——但那是另一条路径，是否整体干净我只做了初步判断，见 5.2。

## 1. 先复你请我复核的那一处（[ebp-0x17d]）——它确实是关键字段，不是无意义高字节

你 §3.1 说「`[ebp-0x17d]` 实测是 dword `0x000016A8` 的高字节、恒 0，不是 listType」，并请我复核。

**复核结果：它是一个真字段，就是容器/listType 选择子。** 证据（`0x0117C670` 开头）：

```
0117C6A0  lea eax,[ebp-0x17d]
0117C6A9  mov byte[ebp-0x17d], 0        ; 先清零
0117C6C2  call 0x27C5230                ; read_byte(&[ebp-0x17d]) —— 从 NOTI 体读【1 个字节】进来
0117C741  cmp byte[ebp-0x17d], 0 / jne  ; 之后全程用它做分支
0117C861  cmp byte[ebp-0x17d], 1 / jne
0117CAB2  cmp byte[ebp-0x17d], 0x29
0117C93E  movzx eax,byte[ebp-0x17d]; call 0x1648AC0   ; 用它选容器
```

**它是 NOTI 0x0D 体的首字节。** 你测到 0 —— 是因为你那 21 次命中是**主背包**帧，
主背包这个字节本就是 0；与它相邻的 dword `0x16A8` 只是栈上旧值，`read_byte` 会覆盖掉
`[ebp-0x17d]` 本身。而你 §3.2 抓到的崩溃帧里 F 第三参 = `00000001` —— 那正是**装扮栏帧**
里这个字节 = 1。**所以「主背包=0 不崩、装扮=1 崩」两条观测并不矛盾，是同一个字段的两个取值。**
（`[ebp-0x17c]` 起才是 SlotIndex(u16)，这点你是对的。）

## 2. 问题一：`0x0117D02D` 的分歧点

调用点是 `0x0117D028: call 0x1637740`（返回 `0x0117D02D`），在记录循环体内、`0x0117D362` 之前：

```
0117D015  movzx eax, byte[ebp-0x17d]    ; kind = 容器选择子（主背包=0 / 装扮=1）
0117D01C  mov   ecx, [ebp-0x17a]        ; val  = itemId (rec+0x02)
0117D024  lea   edx, [ebp-0x58]         ; buf  = 28 字节栈缓冲
0117D028  call  0x1637740               ; F(buf, val, kind)
```

**分歧不在 `0x0117C670` 的控制流里，而在 F 自己的门槛上**（`0x1637740`，完全可读）：

```
F(buf=[ebp+8], val=[ebp+0xc], kind=[ebp+0x10]):
  if (kind == 1) {  0x274FBE0(buf);                 return 1; }   ← 无条件，无数据守卫
  if (kind == 3) {  if (0x166EBC0(val)) 0x274FBE0(buf); return 1; }
  return 0;
```

`kind` 每次迭代都取同一个 `[ebp-0x17d]`（函数入口读一次，循环里不变）。
**主背包 kind=0 → 两个 if 都不成立 → F 立即返回，`0x274FBE0` 根本不被调**；
**装扮 kind=1 → 直接进 `0x274FBE0`。** 这就是「listType 1 走到它、listType 0 不走」的全部原因——
同一个 `call 0x1637740` 两条路都执行了，区别只在 F 内部那句 `cmp eax,1`。

## 3. 问题二：`0x01637757` 所在函数，与 `0x30303030` 从哪来

- **`0x01637757` ∈ F = `0x1637740`**，就在 `call 0x274FBE0`（`0x01637752`）的下一条 `add esp,4`。
  签名 `f(char* buf, int itemId, int kind)`，逻辑见第 2 节。`kind==1` 分支把 **只把 `buf`** 传给
  `0x274FBE0`（itemId 不传）。

- **`0x274FBE0` 是虚拟化函数**：首指令 `jmp 0x572B79D`（进 `.vmp1` 区），其字节码不在既有
  walk 集合里，所以**加载 `0x30303030` 的那条指令我无法静态读出**——这一步到此为止是诚实的边界。

- **但周边原生证据把机制钉死了**（均已核实字节）：
  - 每次迭代在 F 之前先 `call 0x1102C30 → 0x1637C60`，它**懒分配一个 `0xB0208`（≈721 KB）的全局
    累加缓冲**存到 `[0x3A5B348]`（`test byte[0x3A5B34C],1` 首次置位）——这是一块**文本/报表缓冲**。
  - `buf=[ebp-0x58]` 由 `0x2A431A0` **零初始化到 `[buf+0x1C]`**，即一个 **~28 字节内联缓冲**。
  - 本函数解密串是 `Item Info List(Count:%d)`、`NOTIFUNC_ENUM_NOTIPACKET_ITEM_LIST`，以及
    `SlotIndex(%d)…tradeRestriction(%d)` 整套逐字段格式串。

  **推断（与你 §3.3/§3.4 同向，且被上面几条支撑）**：这是一条**把每条物品格式化成文本、
  追加进那块 721 KB 报表缓冲**的诊断路径。`0x274FBE0` 用一个**长度字段**驱动 memcpy，
  而该长度字段此刻装着 ASCII `"0000"`＝`0x30303030`（近乎全零的记录被格式化成一长串 `'0'`，
  某个 dword 被当成长度读走）。**`0x30303030` 与 itemId、物品种类无关**正说明它来自这块
  未被正确初始化的文本，而不是任何物品数据——和你实测「`ecx` 两次一字不差」吻合。
  参照会话从不发非空装扮栏 ⇒ 这条累加路径从没被正确跑通过 ⇒ 它的长度字段一直是垃圾。

## 4. 问题三：目标缓冲 `0x001AF944` 的声明大小 —— 确认「本来就不够」

`buf = [ebp-0x58]`，由 `0x2A431A0` 清零到 `[buf+0x1C]`，即 **约 28 字节（0x1C）的内联缓冲**。

- `buf → /GS cookie([ebp-0x10])` = `0x48` = **72 字节**；`buf → 返回地址` ≈ `0x5C` = **92 字节**。
- 记录本身 `0x65` = **101 字节**。

**所以你的第三问成立，而且是最强形式：这个缓冲连一条 101 字节记录都装不下（28 < 101）。**
即便长度参数完全正确、只要往这里拷「整条记录」，也已经越界。结论的性质是**两件事叠加**：
缓冲**结构性偏小**（它本就是个小的格式化 scratch，不是用来装记录的），**且**长度被读成了
`0x30303030`。是后者把一次本会是 `/GS`（`0xC0000409`）的越界，放大成冲出栈顶的野 `0xC0000005`。
换句话说：**这块缓冲从设计上就不是用来承载记录的**，整条路径是个从没被正确走过的诊断累加器。

## 5. 投递结论（你的第 5 节）

### 5.1 通过 ITEM_LIST(0x0D) / UPDATE_ITEM_LIST(0x0E) 发装扮栏库存：必崩，无可发形状

- 装扮栏库存 `*[0x3A5C9D0]` 在 `0x1648AC0` 全表里**只**对应选择子 = **1**（无第二个入口）。
- 选择子 = 1 ⟺ F 的 `kind` = 1 ⟺ 进 `0x274FBE0` ⟺ 崩。二者同字节，绑死。
- **NOTI 0x0E（`0x0117D720`）核过了，同一地雷**：它在 `0x0117D79E` 用 `0x1648AC0([ebp-0x21d])`
  选容器，又在 `0x0117D91F` 用**同一个** `[ebp-0x21d]` 当 kind 调 `0x1637740`
  （`push kind; push val; push buf; call 0x1637740`）。所以 **0x0D、0x0E 崩溃条件逐位相同，
  换 0x0E 不解决**。

⟹ 服务器把**装扮栏库存**当作**永远为空**处理即可（发空帧不进循环体、不碰 F，安全）。

### 5.2 一条绕行候选：穿戴容器（选择子 0x27/0x28/0x29）不触发这颗地雷

同一函数里，选择子 `0x27/0x28/0x29` 走的是 `getMyCharacter`(`0x19E3290`) →`0x551640`→`0x1833E70`
取**角色穿戴**容器（不是 `0x1648AC0` 的库存），随后汇入**同一条记录循环**。但那条循环里的
`F(kind=0x27/0x28/0x29)` —— `kind∉{1,3}` —— **F 直接返回，不进 `0x274FBE0`**。所以这条路
**不踩格式化地雷**。装扮本质是"穿戴的外观装备"，这多半才是时装真正上身该走的容器。

> **核实/推断分界**：F 对 0x27/0x28/0x29 是 no-op —— 已核实（F 的 `cmp eax,1`/`cmp eax,3`）。
> 但这三条支路**整体**是否还有别的坑（它们比库存路多几层 `getMyCharacter` 解引用，都带
> `je 0x117D695` 兜底），我只做了结构核对，没有逐条走完。要不要我把 0x27/0x28/0x29 三条
> 支路整体过一遍、确认哪一个是 avatar-worn、且循环体在这条路上无其它越界？给个信号我就做。

### 5.3 给服务器的一句话建议

- **不要**再发选择子 = 1 的装扮栏库存快照/增量（0x0D 与 0x0E 都会崩，且是客户端诊断路径的缺陷，
  服务器无法用数据规避）。
- 时装上身改走**角色穿戴**通道（选择子 0x27/0x28/0x29 一类），或等 5.2 的整体确认后再定具体形状。
