卡恩礼盒开盒协议与抽象业务流程

适用对象
========

卡恩的命运回响礼盒：10007368
普通幸运魔锤：10007367

本文只说明协议解析、PVF规则查询、数据库结算以及客户端界面更新流程，
不涉及服务端具体类、方法和代码组织。


一、客户端发起开盒请求
======================

批量开启使用：

    方向：Client -> Server
    帧族：CMD 0x01
    Type：0x0450
    用途：批量开启魔盒

请求Body固定为15字节：

    u8   客户端列表类型
    i16  箱子所在槽位
    i32  客户端所见箱子ID
    i16  材料所在槽位，-1表示未指定
    i32  客户端所见材料ID
    u16  本次开启数量

卡恩礼盒的真实请求样例：

    00 4200 48B39800 7A00 47B39800 3C00

解析结果：

    列表类型       = 0
    箱子槽位       = 66
    箱子ID         = 10007368
    魔锤槽位       = 122
    魔锤ID         = 10007367
    开启数量       = 60

单个开启还可使用CMD 0x00D0。它的Body只有列表类型、箱子槽位和材料槽位，
开启数量固定为1，实际物品ID由服务端从当前角色背包读取。


二、抽象业务流程
================

1. 解析请求

   服务端确认协议类型、Body长度、槽位格式、物品ID和开启数量是否合法。
   格式错误直接返回失败，不进入物品结算。

2. 确认当前角色和背包状态

   服务端确认当前连接已经选择角色，并从该角色的服务端背包读取箱子槽位。
   客户端提交的箱子ID只是校验值，不能替代服务端背包中的真实数据。

3. 查询PVF开盒规则

   服务端使用背包中真实的箱子ID查询PVF，取得：

   - 该物品是否属于可开启魔盒；
   - 每次开启需要消耗多少个箱子；
   - 是否需要钥匙或其他材料；
   - 每次要抽取哪些奖励池；
   - 奖励物品ID、数量和权重；
   - 是否存在期限、装扮属性、宠物或其他特殊奖励规则。

4. 校验请求与PVF是否一致

   服务端将客户端提交的箱子槽位、箱子ID、材料槽位、材料ID和开启数量，
   与当前背包和PVF要求进行比对。

   如果箱子不存在、数量不足、魔锤不匹配、材料不足、物品已过期，
   或请求试图绕过PVF材料要求，则整次开启失败。

5. 根据PVF计算奖励

   服务端按照PVF定义独立计算每次开启的奖励。
   客户端不能指定奖励物品或奖励数量。

   批量开启时，服务端重复执行指定次数的奖励计算，最后汇总同类奖励，
   同时保留开盒结果窗口需要的奖励展示信息。

6. 预先规划完整结算

   在修改数据库之前，服务端先确认：

   - 要扣除的箱子和材料仍然存在；
   - 所有奖励都是服务端支持创建的物品；
   - 奖励没有失效或过期；
   - 可以合并到哪些已有堆叠；
   - 需要占用哪些新槽位；
   - 背包、装扮栏或宠物栏是否有足够空间。

   只要任意奖励无法完整发放，整个请求都失败，不扣箱子和材料。

7. 在一个事务中持久化

   服务端把以下变化作为一个整体写入数据库：

   - 扣除箱子；
   - 扣除魔锤或其他材料；
   - 增加全部奖励物品；
   - 写入新物品实例及其期限、属性等信息；
   - 如果该箱子使用幸运值，同时更新账户幸运值；
   - 如果包含期限权益或宠物，同时更新对应持久化记录。

   事务全部成功后才视为开盒成功；任何一步失败都整体回滚。

8. 数据库提交后通知客户端

   成功结算后的发送顺序为：

   第一帧：S -> C CMD 0x0450

       这是批量魔盒的成功应答，也是驱动客户端原生开盒结果窗口的协议。
       回包中包含成功标志、开启数量、箱子槽位、材料槽位、奖励条目，
       以及普通奖励列表和幸运奖励列表。

       客户端据此关闭或刷新开盒操作窗口，并在原生结果窗口中显示
       本次获得的物品和数量。

   后续帧：S -> C NOTI 0x000E UPDATE_ITEM_LIST

       该通知携带变更后槽位的绝对状态，用于刷新客户端背包UI。
       奖励进入或合并到的槽位会发送最新物品和数量；
       箱子或材料被用完的槽位会发送空槽状态；
       尚有剩余数量的槽位会发送扣除后的绝对数量。

   如果奖励包含期限权益、宠物等非普通背包内容，再追加相应的专项通知。

   必须先发送CMD 0x0450，再发送NOTI 0x000E。
   原因是客户端处理魔盒成功应答时会先在本地扣除箱子和材料，
   随后的绝对背包状态用于把客户端UI校正为服务端数据库中的最终结果。

9. 失败处理

   失败时仍使用S -> C CMD 0x0450返回：

       00 7E  背包空间不足
       00 16  材料不足
       00 02  其他拒绝

   失败回包不包含奖励列表，不发送背包更新通知，数据库也不产生物品变化。


三、卡恩礼盒60连开示例
======================

1. 客户端发送CMD 0x0450：

       箱子槽位66，物品10007368，数量60
       魔锤槽位122，物品10007367

2. 服务端读取PVF后得到：

       每开启1次消耗：
           卡恩的命运回响礼盒10007368 x1
           普通幸运魔锤10007367 x1

       每开启1次获得：
           瞬间移动药剂2600014 x2
           赛丽亚魔盒2682272 x1

3. 服务端计算60次结果：

       消耗：
           10007368 x60
           10007367 x60

       获得：
           2600014 x120
           2682272 x60

4. 服务端先把扣除和奖励作为一个事务持久化到数据库。

5. 数据库提交成功后，服务端发送：

       CMD 0x0450
           让客户端确认开盒成功，并在原生开盒结果窗口中显示：
           瞬间移动药剂 x120
           赛丽亚魔盒 x60

       NOTI 0x000E UPDATE_ITEM_LIST
           把奖励所在槽位、箱子槽位和魔锤槽位的最终绝对状态发给客户端，
           让背包UI与服务端数据库保持一致。


四、流程摘要
============

客户端发送CMD 0x0450
    -> 服务端解析箱子槽位、材料槽位和开启数量
    -> 从服务端背包确认真实物品
    -> 查询PVF取得材料要求和奖励规则
    -> 校验材料、数量、期限和背包空间
    -> 服务端计算奖励
    -> 在一个事务中扣除箱子/材料并写入奖励
    -> 数据库提交成功
    -> 返回CMD 0x0450显示原生开盒结果窗口
    -> 发送NOTI 0x000E刷新背包槽位和数量


证据状态
========

卡恩礼盒的客户端CMD 0x0450请求和15字节Body来自真实抓包。
服务端PVF解析、事务结算和回包编码已有自动化验证。
成功回包在真客户端上的最终窗口表现仍需实机成功开启验证。
