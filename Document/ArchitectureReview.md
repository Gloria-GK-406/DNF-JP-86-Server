# 架构漂移审核规范

用于 PR 的架构验收。目标是判断新增或修改的实现是否沿着现有架构扩展，
以及暴露的问题应由实现归位解决，还是需要人工重新决定架构。

## 审核范围

只评估职责、依赖、状态所有权、能力复用及架构例外。功能是否正常、玩法是否符合预期、
客户端表现和实机验收由各自流程负责，本审核不重复执行，也不以它们作为通过依据。
测试与运行记录可以帮助理解调用边界或状态归属；测试通过不能证明实现符合架构，
缺少功能复测也不能单独成为本审核的阻断项。

审核基准是 [架构与分层](Architecture.md) 及变更涉及的专项约束。
[重构判断](RefactorPreferences.md) 用于识别结构信号，不要求每个 PR 都做架构重构。
以 PR 相对目标分支的实际增量为对象，结合目标分支已有能力和周边实现判断。
现有代码中的偏离不是新增偏离的许可；本 PR 修改文档或放宽判据也不自动证明新结构合理。

## 先判断实现能否由现有架构承接

先用简短描述说明本功能引入了哪些职责、读取或修改哪些事实，再沿实际调用和依赖关系核对：

| 检查方向 | 需要回答的问题 |
|---|---|
| 职责归属 | 每段逻辑应由哪个层、哪个领域 owner 承担？实际是否在那里？协议、用例编排、业务、规则、内容、存储、投递是否各司其职？ |
| 状态所有权 | 是否通过既有 owner 读写事实？是否新增平行状态、镜像、缓存或同步义务，形成第二个真源？ |
| 能力复用 | 同类能力是否已经存在？是否调用既有领域能力、机制或扩展点，还是另写一套同义判定、流程或基础设施？ |
| 边界与依赖 | 依赖方向、事务归属、执行器、请求权限、精确会话和事件／投递边界是否符合对应专项约束？ |
| 扩展方式 | 新代码是否是既有职责内的自然扩展，还是需要绕过边界、增加例外或把特殊业务塞进通用机制？ |

位置正确指实际职责和依赖正确，不是目录、类名或接口后缀看起来正确。
把规则复制到一个新 `DomainService`，或在正确目录里通过转发门面绕边界，仍可能是错位或重复造轮子。
已有能力缺一个方法不等于架构无法承接；应先判断能否在原 owner 内自然补齐能力。
不同业务仅有代码形状相似，也不等于必须共用抽象；复用依据是相同责任、语义和不变量。

## 再区分实现问题与架构限制

发现偏离后，先给出它在现有架构下的正确归属或复用路径，再判断该路径是否实际可行。

- **实现错位或未复用：** 现有 owner、机制或允许的扩展方式能承接，但实现放错层、绕过接口、
  重复保存事实或另建同义能力。应归位或复用，不能用“改起来麻烦”“这样更快”解释为架构限制。
- **架构限制：** 职责已放在合理 owner，使用现有扩展方式仍无法表达该需求，
  必须引入架构尚未覆盖的关系或能力。需指出具体缺口，以及按现有边界实现为什么行不通。
- **证据不足：** 尚未查清已有能力、实际调用路径或例外边界。继续补查；仍无法确认时标明待判定，
  不直接宣布通过，也不凭猜测宣布架构有缺陷。

一项功能可以同时包含这两类问题，应分别判定。发现真实架构缺口，不会免除其中可以归位的实现错位。
“没有现成 API”或作者声称“只能这样写”都不是架构限制的充分证据。

## 判断架构限制的影响强度

对无法被现有架构承接的部分，检查同类责任的周边实现、共享 owner、调用方和相似用例。
按事实与行为搜索，不能只搜索当前新增的类名，也不能只看 diff。

| 维度 | 较弱信号 | 较强信号 |
|---|---|---|
| 例外分布 | 只有一个独立用例，相关范围未发现同类妥协 | 多个独立用例重复绕同一边界，或本次继续复制既有妥协 |
| 结构范围 | 局部且封闭，职责和依赖仍清楚 | 形成较大子结构，穿透多个层或迫使共享机制理解专项业务 |
| 扩散影响 | 不要求其他正常路径跟随特判 | 相邻调用方被迫增加分支、复制状态、同步逻辑或新增依赖 |
| 调整性质 | 例外可在所属 owner 内局部隔离，不牵动其他职责 | 需重新划分所有权、依赖方向、生命周期或核心机制才能消除冲突 |

“范围小”按受影响的责任和依赖判断，不按代码行数、文件数或类数判断。
一个方法也可能改变全局所有权；多个文件也可能只是同一职责的正常协议切片。
“单一个例”指独立业务原因，不是只看到一个入口；多个入口调用同一实现不能机械计成多个例外。
说明实际检查了哪些相似路径及其结果，不能把“没找过”写成“没有其他例子”。

只有在职责位置正确、例外范围小且封闭、同类扫描支持其孤立性、没有明显向共享边界扩散时，
才适用小范围单例的通过条件。审核须明确指出它偏离了哪一条现行约束，以及为什么仍可作为单例接受，
不能通过改写术语或隐藏依赖把例外描述成完全符合架构。
如果周边已有多处同类妥协，即使每处都很小，也不能继续按“单一个例”放行；
应判断能否用既有能力统一解决，还是已形成需要调整架构的系统性信号。

## 裁定

| 情况 | 结论 | 审核应说明 |
|---|---|---|
| 现有架构能够承接，但逻辑放置错位、绕过应有边界，或存在应复用而另造的同义能力 | **不通过：实现归位** | 违规位置、应属 owner／可复用能力及归位方向；即使功能正常、规模很小也不能通过 |
| 职责位置正确，现有架构完整承接，复用与扩展方式合理 | **通过** | 关键职责和已有能力的对应关系 |
| 职责位置正确，确有小范围、封闭且孤立的架构例外，满足上述条件 | **通过：附例外说明** | 无法承接的部分、为何属于架构限制、同类检查范围、为何影响可控 |
| 无法承接的部分形成明显较大结构，且与现有架构有根本冲突，局部归位无法解决 | **不通过：人工接手** | 冲突的责任或不变量、受影响范围及需要人工决定的架构问题 |
| 多处同类妥协，既有能力无法统一承接；或关键证据不足，无法确认以上任何通过条件 | **待人工判定，不视为通过** | 已确认事实、缺口、重复模式和待决定事项；不把未知说成已证实的大规模冲突 |

整个 PR 只有在所有相关部分均满足通过条件时才能通过；一个阻断项不能被其他部分符合架构抵消。
小范围例外应在本次审核中显式说明，不因本次通过就成为其他功能可以照抄的通用许可。
审核结论仅针对架构，不代替功能验收、CI 或合并授权。

## 审核输出

先给结论，再给足以复核的依据。通过时同样需要简短明确的结论，不能把没有评论当作通过。

1. **结论：** 使用上表中的结论，说明是否需要实现归位或人工接手。
2. **架构对应：** 简述本次功能的职责分布、复用的能力及自然扩展的位置；无需逐文件复述 diff。
3. **问题或例外：** 给出代码位置、适用约束、实际依赖／调用／状态关系，区分实现错位与架构限制。
4. **周边证据：** 对例外列出检查过的相似用例，说明是孤立、重复还是证据不足，以及影响如何扩散。
5. **处理方向：** 错位指向正确 owner 或既有能力；架构冲突说明需人工决定的边界，不自动展开全仓重构。

不要输出一般功能缺陷清单、重复实机验收步骤或风格偏好。架构发现不需要先证明功能已坏，
但必须给出具体结构事实与适用约束，不能只用“耦合高”“不够优雅”“以后可能扩展”作为阻断理由。
已有偏离仅作为判断本次增量的周边证据；不把与本次变更无关的旧问题逐项列作本 PR 缺陷。
如审核工具另要求优先级，按真实影响填写；本规范的通过条件与优先级标签分别表达，不能靠夸大级别制造阻断。
