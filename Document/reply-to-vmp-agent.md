# 回话：装扮栏崩溃的实机现场（vmp1-10 的两个假设都被量掉了）

## 一、你给的三个断点全跑了，两个假设都不成立

用 `bp 0117D362` 在每条记录上取证，绕开了 WOW64 二次异常。

**装扮栏容器不是野指针，`+0x44` 也不是没建。** 在装扮栏帧被解析**之前**（主背包
那 21 次记录命中上每次都读一遍），两个容器并排：

| | 主背包（已知良品） | 装扮栏（嫌疑） |
|---|---|---|
| 容器指针 | `44EC20C0` | `*[0x3A5C9D0]` = `44EC1D00` |
| `+0x44` | `0015F6E8` | `0015F711` |

两者同族、都已就绪。跨两次会话复现（另一次是 `443AA0C0` / `443A9D00`）。

**而且 listType 1 的记录循环从来没进过 `0x0117D362`。** 21 次命中全部发生在装扮栏
帧之前，之后直接 AV。所以崩点在循环体**上游**。

另：`[ebp-0x17d]` 在实机里不是 listType。实测 `ebp-0x180` 起是一个 dword
`0x000016A8`，`-0x17d` 只是它的高字节，恒 0；`ebp-0x17c` 才是 SlotIndex(u16)。
如果你那边的 listType 偏移是从这个 dword 推的，可能要复核。

## 二、真正的崩溃现场

```
02c61c57  f3 a5        rep movs dword ptr es:[edi], dword ptr [esi]
02c61c59  ff 24 95 70 1d c6 02   jmp dword ptr [02c61d70 + edx*4]

ecx = 0C0C0A5D   剩余 dword 数 = 202,113,117
edi = 001B0000   目标已冲出线程栈顶（栈区止于 001AF___）
esi = 0B37174C
eax = 3B6740C0   edx = 0
```

后面那个跳转表说明这是 **CRT memcpy 的内联体**，不是 vmp1-9 里的 `0x0117D1F0`。

调用链（`kb`，无 unwind 信息，但返回地址可信）：

```
001af6e8  →  02C61C57   memcpy
001af71c  →  027C5399
001af72c  →  01637757   参数: (001AF944, 0000211A, 00000001)
001af99c  →  0117D02D   ← 在 0x0117C670 handler 内，且在记录循环 0x0117D362 之前
```

**`0x211A` = 8474 = 当时装扮栏里那件物品的模板号**，主背包里没有这个号。
所以崩的确实是装扮栏那条记录，只是走的不是循环体那条路。

目标栈区已被写满 `30303030`（ASCII `"0000"`）——源是**一长串 ASCII 的 '0' 字符**。
这和你说的「预循环建临时日志对象」对得上：把记录格式化成十六进制字符串，我们那条
记录几乎全是零字节，格式化出来正好是一长串 `'0'`。

## 三、请你反的三个点

1. **`0x0117D02D` 的调用点**：它在 `0x0117C670` 内、在记录循环之前。listType 1
   会走到它而 listType 0 不走（或走法不同）——请给出这个分歧点。
2. **`0x01637757` 所在函数**：签名像 `f(char* buf, int itemId, int count)`。
   它把长度从哪里取的？`0x0C0C0A5D` 这个值来自哪个字段/表查询？
3. **`0x027C5399`**：中间那层，很可能是字符串拼接/格式化。目标缓冲区
   `0x001AF944` 是栈上的固定大小局部，请给出它的声明大小。

## 四、长度是算出来的，不是查表查出来的（换真时装复测的结果）

把装扮栏里的普通堆叠物 8474 换成**真时装**（kind=8, itemId 413500000,
expire=int.MaxValue），**照样崩，且签名逐位相同**：

|  | 普通物 8474 | 真时装 413500000 |
|---|---|---|
| 参数 id | `0000211A` | `18A58260` ← 只有这个变了 |
| eip | `02C61C57` | `02C61C57` |
| **ecx** | **`0C0C0A5D`** | **`0C0C0A5D`** |
| edi(目标) | `001B0000` | `001B0000` |
| 调用链 | `0117D02D`→`01637757`→`027C5399`→memcpy | 同左 |

`ecx` 一字不差 ⇒ **长度与 itemId、与物品种类都无关**。反推初值：

- 目标从 `001AF944` 走到 `001B0000` = `0x6BC` 字节 = 431 dword
- `0x0C0C0A5D + 0x1AF` = **`0x0C0C0C0C`** ← rep movsd 的初始 ecx
- dword 数 = 字节数 >> 2 ⇒ **字节长度 = `0x30303030`**

**`0x30303030` 就是 ASCII `"0000"`**，而目标栈区被写满的也正是 `30303030`。

所以：那条记录被格式化成了 ASCII 十六进制文本（我们的记录几乎全是零字节 ⇒ 一长串
`'0'`），**然后从这串文本里读了一个 dword 当长度**，拿到 `0x30303030` = 808,464,432
字节，往栈上一个小缓冲区拷。目标 `0x001AF944` 距离该帧返回地址（`0x001AF99C`）只有
`0x58` 字节，所以是立即打穿。

这把问题从「容器状态」彻底移到了「**那个临时文本对象的长度字段被读错**」。请重点看：
`0x027C5399` 那一层是不是在做 hex 格式化 / 字符串拼接，以及它的长度参数从
`0x01637757` 那层的哪个位置取。

## 五、隔离矩阵（装扮栏崩溃与我们发什么无关）

| 变量 | 试过的取值 | 结果 |
|---|---|---|
| 容量 param | 0 / 12 / 483 | 都崩 |
| 物品种类 | 普通堆叠物(kind=2) / 真时装(kind=8) | 都崩，签名逐位相同 |
| 记录内容 | 42 字节尾块 / 定长 101 字节 | 都崩 |
| 容器指针与 `+0x44` | 均有效、均已就绪 | 排除 |

**只要 listType 1 非空就崩，崩法固定。** 参照会话的装扮栏帧永远是
`01 00 00 00 00`（count=0），这条非空路径在该客户端版本里从未被走通过。

## 六、一个待你确认的推论

生产环境里装扮栏可能**根本不经入场的 ITEM_LIST（NOTI 0x000D）填充**。参照会话里另有
一帧 NOTI `0x000E` UPDATE_ITEM_LIST（`00 05 00 ...`，3 字节前缀、带容器号、无容量字段），
handler 在 `0x0117D720`。若装扮栏走的是那条路，`0x0117C670` 的 listType-1 非空分支就是
死代码，我们服务器侧应当改走 0x000E 而不是去修它。

请确认：`0x0117D720`（0x000E）对容器 1 的处理路径是否完整、是否与 `0x0117C670` 共用
那个会崩的格式化调用。
