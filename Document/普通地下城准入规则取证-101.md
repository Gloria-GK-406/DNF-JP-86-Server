## 当前代码可确认的缺口

### 用户确认的普通地下城疲劳规则

来源：2026-09-20 用户依据长期游戏经验明确确认，并要求作为实现基准，不再验证规则本身。此为用户确认的业务规则，不冒充权威服务器抓包结论；没有可用的权威服务器，不安排重复刷图来证明规则。

- 进入新的、尚未清理的房间消耗 1 点疲劳；初次进入地下城的首房也按此规则处理，不另加一次独立入场扣费。重访房间不重复扣除，清怪本身不是扣点时机。
- 扣点下限为 0，即 `remaining = max(0, remaining - 1)`。
- 已进入的地下城中，疲劳降至 0 仍可继续换房并完成整张地图，不因疲劳耗尽中断当前 Run。
- 剩余疲劳为 0 时，不允许再次进入普通地下城。这个准入检查与当前 Run 内换房分开处理。
- 特殊地下城可以有独立规则；已发现的 PVF 疲劳声明用于识别例外，不将其推广为普通规则。
- 燃烧疲劳活动/选项启用时，疲劳消耗倍率为 2，普通房间对应消耗 2 点，仍遵循疲劳不低于 0、当前 Run 可继续的规则；每只怪物的经验同时翻倍。此规则同样由用户确认，不要求重复验证规则本身，不扩展到任务奖励或通关结算经验。

燃烧疲劳的业务规则与协议证据分开：已发现 NOTI `0x01EB USER_FATIGUE_ACCELERATION_STATE` 作为状态同步线索，但开关入口、请求布局、活动资格与生效时点仍待核对；不能仅凭消息名称声称已实现。剩余疲劳不足完整倍率、当前 Run 内已为 0 时的经验倍率，以及其他经验加成如何叠加，用户尚未具体定义，实施对应边界前再收敛，不擅自补规则。

用户后续确认当前界面没有燃烧按钮，并明确要求暂时只记录、后续再处理。因此燃烧激活方式、开关协议及边界调查延期，不作为本轮测试或 #101 收口阻塞项。

剩余人工验证顺序：先由助手准备限定测试会话的难度权限投影夹具，验证同图难度选项及选图请求差分（T04/T03）；随后准备非零/零疲劳投影，验证疲劳显示与新入场请求/拒绝表现（T06）。夹具准备并验证前，不要求用户继续刷图或尝试尚未设置的条件。此处验证客户端协议表现；真实扣点、持久化及零值服务端准入实现仍交给 #6/#103。

实现责任：由服务端根据已接受的入场/换房行为和房间状态判定、记账并发送疲劳投影，不依赖客户端另发“减少疲劳”命令。用户关于客户端可能没有该 CMD 的表述仍是协议假设；无需证明此类 CMD 绝不存在，才能实施上述业务规则。

后续 #6/#103 只验收实现是否符合这套规则：首次有效进入扣一次、重访或请求重试不重复扣、1→0 后当前 Run 可继续、0 时新入场被拒绝、持久化与客户端显示一致。T06 的零值样本只用于验证投影/提示路径，不再用于裁定“0 是否应拒绝新入场”；T09 已有换房基线，无需继续让用户刷图取证扣点政策。恢复、重置及特殊副本例外另行定义。

### T01 漂流洞穴空列表的原因

证据级别：过滤谓词为 `High / PvfStatic + ClientStatic + Read-only RPM`；完成整条蜘蛛任务链前后的普通/冒险选项差分已有用户界面验证，具体哪个任务子集控制模式切换尚未逐项验证。

真实 `driftcave.wdm` 已在客户端完整加载全部 10 项（[实时区域表](outputs/issue-101/live/t01-loaded-wdm.json)）。150、151、152、153、155 的区域条件为 `-1`，直接通过区域条件门；它们随后在普通列表构建 `RVA 0x0231D490` 中被任务关联谓词 `RVA 0x00A62D90` 排除。该谓词遍历地下城定义 `+0x168` 的任务列表：满足类型条件的已接任务、或类型 0 的已完成任务命中时放行；均未命中且存在类型 0 任务时拒绝。当前普通模式的后续分支将拒绝项直接跳过，不构造选图记录。

## 静态调查结果

PVF 清单与脚本见 [outputs/issue-101/pvf/summary.md](outputs/issue-101/pvf/summary.md)。输入 SHA-256 为 `19F5FA85FF73CCE94E299E0902269DE2F0164934128F15B8A7B99249C881BE1A`，扫描 `dungeon/dungeon.lst` 全部 1047 行，全部找到档案文件。

- `[minimum required level]` 在 1042 个文件中声明；`[no fatigue]` 在 506 个文件中声明。
- 另有 `[enter without fatigue]`（163 个文件）和 `[use fatigue only start dungeon]`（52 个文件）。三者不能仅凭英文名互相替代，当前读取器只处理 `[no fatigue]`。
- 有可投影 Maze 的文件为 346 个。“可投影”指当前服务端支持的结构，不代表剩下的文件没有地图。
- 地图 144 炽晶森林最低等级为 1，普通 Maze 为 m0，另有四个任务 Maze；地图 145 冰晶森林最低等级为 5，同样混合普通与任务 Maze。以它们作为普通基准与等级边界候选，UI 可达性仍需验证。
- 免疲劳教程 10000/10004 不能假设能从普通选图 UI 进入；非教程免疲劳候选 100/5006 还带活动/许可及材料条件，因此不扩展为普通玩法验收。

A21 转储 SHA-256 `6BD2746DA3858E6F29B3E2D386AF4938056269BAD6C9FFF9455E133E7D953507` 中，`0x00D45ED4` 调用 ReadU32、`0x00D45EDF` 调用 ReadU8；`0x0232DF52` 调用 WriteU32、`0x0232DF5F` 调用 WriteU8。完整来源见[客户端静态证据](outputs/issue-101/client/static-evidence.md)。

协议记录已同步：[普通选图](../protocol/game/client-to-server/0x0010.md)、[权限列表](../protocol/game/server-to-client/NOTI-0x0005.md)、[疲劳更新](../protocol/game/server-to-client/NOTI-0x0024.md)。NOTI `0x0024` 静态闭合为5×u16；前三项与选角初始化同槽，后两项语义未知。实机确认150/state1出现普通、冒险，冒险入场请求offset4=1，初始化(187,188,0)显示剩余1，初始化(188,188,0)后仍发送0010并入场。本通知0024的增量UI效果尚未实测，不能把初始化样本算作本通知验证。

拒绝码已确认客户端静态消费：`0x16` 按成员槽位显示疲劳不足，`0xAD` 按成员槽位及客户端附加状态选择权限不足/次数已满。`0x01` 在本 handler 中未命中提示分支，不能直接作为已确认的等级不足提示码。具体指令与资源绑定留在协议页，服务端的等级不足如何映射仍是未决输入。

## 实机执行方式

由助手准备场景和抓包，用户逐步操作。每次只给一个测试步骤；用户报告完成后，助手先归档证据、核对状态，再给下一步。没有采集就不把用户的操作计为协议验收。

每个样本绑定客户端/PVF 哈希、运行服务基准、测试条件、时间范围、原始实帧摘要、用户观察、预期及实际结果。结果分开记录：客户端本地阻止、服务器拒绝、成功进入。客户端没发包时，先确认采集器健康，不能仅以日志没有记录推断本地阻止。

### 采集前置

1. 核对服务进程、实际监听、数据库和客户端目标地址。配置文件与正在运行的设置可能不同。
2. 使用针对本任务的透明中转；A21 历史记录表明 `0100_NetworkHook` 与 `0050_A21RuntimeFix` 冲突，不通过重新启用旧插件解决抓包。
3. [capture_admission.py](outputs/issue-101/capture_admission.py) 仅监听显式指定的本机端口，转发原字节，仅落盘准入相关白名单，不记录登录、聊天或角色完整资料。对成功选角响应仅提取 body `[11:17]` 的三项疲劳初值，不保存其他正文。它不会自动修改任何端口配置。真实使用前须安排前端/后端端口，完成连通性和目标帧检查。
4. 每个测试用单独文件，归档原件哈希及中转控制台。JSONL 出现 `capture_status=incomplete` 或控制台出现 `CAPTURE_INCOMPLETE` 时，不作“未发包”的否定判断；中途停止的会话也不能作为完整观察窗口。
5. 需要改变疲劳或权限投影的测试，使用已检查的独立会话夹具；不为取证顺手实现 #6/#102。角色资料变更仅限用户另行授权的蜘蛛链，保留备份。夹具已停止，10010/10011均恢复透明中转；服务端继续运行，蜘蛛链完成记录按用户要求保留。
