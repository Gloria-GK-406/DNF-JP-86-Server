## 1. 你的探测有一处实质遗漏，说它是因为它指向方法而不是这一次

你的表里这一行标了 **✓**：

> `EmblemSocketCount u8` | `rec+0x2F` | 附加选项数（**致命计数**） | ✓

然后结论是「**唯一问题**就是那 42 字节尾部追加」。

**偏移对，值不对。** 服务器往 `rec+0x2F` 写的是 `core.EmblemSocketCount`，
它直接来自 `item_core[45]`——一个 `byte`，取值 0..255，**存储侧没有任何约束**
（建表语句对 `item_core` 只有 `CHECK (length = 82)`）。而「致命计数」这四个字是你自己写的：
按你 `vmp1-9.md` 第五节，这个字节在客户端驱动一条**无上界的 `rep movsd`**，
两个处理器都只用 `jle` 挡 `<= 0`，`1..127` 都能打崩。

也就是说：**服务器此前一直带着一个能打崩任意客户端的向量，而这一格被标成了正确。**

遗漏的性质不是粗心，是**只核了偏移没核取值范围**——「客户端从哪里读」问完了，
没有回头问「那么服务器往那里写什么、写得进多大的值」。这一类问题在协议工作里反复出现，
值得记一条口径：

> **凡是被判定为「计数」「长度」「索引」的字段，除了核偏移，必须核两件事：
> 上游能写进多大的值，以及下游能吃下多大的值。两者不重合就是缺陷，
> 与「今天的数据碰巧没触发」无关。**

顺带说明这条为什么很难靠判据发现：改动前**没有任何既有用例走到这条路径**。
实测过——把夹紧移除，入场序列字节锚 62 帧一帧不差、全量只红新加的判据。
所以「全量判据全绿」对这条路径什么都证明不了。

（已在 `f5c00fb8` 里夹到 **2**——即编码器在 `rec+0x30` 之后实际写出的选项 dword 条数

### 3.2 崩溃现场（拦第一现场 `c0000005` 取得，不是二次异常）

```
02c61c57  f3 a5                    rep movs dword ptr es:[edi], dword ptr [esi]
02c61c59  ff 24 95 70 1d c6 02     jmp dword ptr [02c61d70 + edx*4]

ecx = 0C0C0A5D    剩余 dword 数 = 202,113,117
edi = 001B0000    目标已冲出线程栈顶（栈区止于 001AF___）
esi = 0B36174C    eax = 3B6640C0    edx = 0
```

调用链（`kb`，无 unwind 信息，但返回地址可信）：

```
001af6e8  →  02C61C57   memcpy 内联体
001af71c  →  01637757
001af72c  →  0117D02D   ← 在 0x0117C670 内，且在记录循环 0x0117D362 之前
001af99c  →  （已被 30303030 冲毁）
```

`001af72c` 那帧收到的参数是 `(001AF944, <itemId>, 00000001)`。
**`<itemId>` 随装扮栏里放什么而变**——普通堆叠物时是 `0000211A`(8474)，
换成真时装后是 `18A58260`(413500000)——**其余寄存器与调用链逐位不变**。

### 3.3 长度是算出来的，不是查表查出来的

- 目标从 `001AF944` 走到 `001B0000` = `0x6BC` 字节 = **431 dword**
- 出错时 `ecx = 0x0C0C0A5D`，加回已拷的 431（`0x1AF`）→ **初始 `ecx = 0x0C0C0C0C`**
- `rep movsd` 的 dword 数 = 字节数 `>> 2` ⇒ **字节长度 = `0x30303030`**

**`0x30303030` 就是 ASCII 的 `"0000"`**，而目标栈区被写满的也正是 `30303030`。
`ecx` 在两次实验里一字不差，说明**长度与 itemId、与物品种类都无关**。

### 3.4 一处交叉印证：崩点在你自己标定的那个函数里

你 `vmp1-9.md` 的附录把 `read_bytes(buf, 0x65)` 的实现定在 **`0x27C5380`**，并列出 9 个调用站点。
崩溃栈里的 `027C5399` **就在这个函数内部**。

也就是说：**它该拷 `0x65`（101），实际拷了 `0x30303030`。**
结合 3.3 的 ASCII `'0'` 与「预循环建临时日志对象」那条线索，最像的解释是：
某处把记录格式化成十六进制文本（我们的记录几乎全是零字节 ⇒ 一长串 `'0'`），
**然后从这串文本里读了一个 dword 当长度**。

## 5. 什么样的答案才算够用

服务器侧只需要能据此做一个**投递决定**，不需要客户端补丁。三种结论都算够：

- **这条路是死代码**（参照会话装扮栏永远收空帧，非空分支从没跑通过）
  → 服务器改走别的路，例如 NOTI `0x000E` UPDATE_ITEM_LIST（handler `0x0117D720`，
  3 字节前缀、带容器号、无容量字段）。**请顺便确认 `0x0117D720` 对容器 1 的路径是否完整、
  是否与那个会崩的格式化调用共用。**
- **有可发的形状**（例如某个字段必须非零、或某个前缀必须先发）→ 给出那个形状。
- **无论怎么发都会崩** → 那就明说，服务器把装扮栏当作永远为空来处理，
  时装另找路径上身。
