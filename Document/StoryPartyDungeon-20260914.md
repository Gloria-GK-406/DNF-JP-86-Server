# 剧情地下城固定队伍首发入场

状态：服务端实现与自动化验证完成，等待 A21 双客户端实机确认。本文中的队员首发投递顺序仍是实现假设，不能标记为 `ClientVerified`。

## 实现边界

- 仅剧情地下城的 `Directed` 入场意图启用队伍编排；普通地下城 `Interactive` 仍按当前角色单人选择，不会因持有剧情任务而改路由。
- 队长发起时读取并冻结 `PartySnapshot`。任一成员的账号、角色、WireUserId、选中角色会话或运行投影不可附着时，整队拒绝，不创建半局。
- 副本领域态只保存 RunId、账号、角色、槽位和队长标记。连接 generation 单独冻结在 Protocol 层投递注册表中，发送前重新核对，replacement connection 不继承旧局通知。
- 布局、房间版本、死亡怪物、地面掉落和拾取声明为共享事实；经验、自己的任务 Trigger、结算、奖励卡和离场状态按参与者独立处理。
- 首版队长负责换图；任一成员可以报告死亡或拾取。同一 actor、同一地面编号在共享局内只接受一次。
- 剧情布局和 Boss 完成资格取冻结队长的任务状态。没有相同任务的队员可以随队进入和结算，但任务推进仍查询该队员自己的活动任务。
- 不实现 `ENTRY_INTO_PARTY` / `ENTRY_INTO_PARTY_FINISH`、中途加入、副本内重连、入场后队伍变更同步或服务重启恢复。

## 双客户端实机流程

1. 两个角色进入同一频道、同一城镇区域，组成两人队伍；A 为队长并持有当前已验证的主线任务，B 不要求持有相同任务。
2. 可先由 B 尝试发起剧情地下城，预期被拒绝且两端仍在城镇；随后由 A 正常发起。
3. 预期两端一起进入同一布局和同一起始房间。服务器 `Select dungeon` 日志应显示同一 RunId 且 `party=2`。
4. 由 A 清怪并换图，观察 B 是否同步切换；B 不应能够单独把共享局推进到别的房间。
5. 任选一端完成击杀，观察两端怪物消失、掉落一致且各自经验变化；B 没有匹配任务时不应获得 A 的任务进度。
6. 一端拾取地面物品，预期另一端同步看到地面物品消失；另一端再次拾取不能重复获得物品。
7. 击杀 Boss 后，两端都应出现清关/结算。两端分别结算和翻牌；先让一端回城，另一端仍应能完成并回城。
8. 另做两个短回归：单人剧情地下城一局、持有同一主线任务时显式进入普通地下城一局。

实机若出现卡图或只有一端进入，优先保留两端 `clienthack-frame-capture.log` 和服务端从 `Select dungeon` 到离场的日志；不要把未确认的投递顺序写成协议事实。

## 首次实机问题与修复

首次两人进入地下城选择区时，客户端提示与队友连接失败。服务端已成功建队并收到两端 UDP 端点报告；本机 UDP 监听和防火墙放行也正常。问题位于 `0x000B` 端点投影：客户端报告的是已失效的虚拟网卡地址，服务端此前将其直接广播给队友。

修复参考上游 `E:\Project\86JP` 提交 `e95cb259` 的 direct path：以已认证 Game TCP 连接的 remote IPv4 作为双方可见地址，只保留客户端报告的动态 UDP 端口，并将直连语义固定为 `NatType=0`、`MTU=1500`。转换只发生在 Protocol 边界，PartyService 继续保存传输无关的端点镜像。上游 UDP relay 明确标注待真机验证且默认关闭，本次不移植。

修复后完整 Debug 回归为 3247 Passed、0 Failed、2 NotExecuted，独立复审批准。仍需重新执行上面的双客户端流程，确认客户端接受同机 `127.0.0.1 + 不同 UDP 端口` 的端点组合。
