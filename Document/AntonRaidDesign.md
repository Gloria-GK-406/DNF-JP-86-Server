# 安图恩团本领域设计草案

2026-11-19。本文记录 JP86 安图恩攻坚实例、小队容器租借及其与现有组队、副本的边界。范围是 A21 安图恩攻坚团本。下面的接口与规则是设计意图，协议时序与客户端行为以实机证据为准。

## 三层成员关系

| 层 | 所有者 | 生命周期 |
| --- | --- | --- |
| 团员 | 攻坚实例 | 入团到退团或团解散 |
| 小队成员 | 借出的小队容器，由攻坚实例编排 | 团长编入到移出、本人掉线或团收尾 |
| 出战成员 | `DungeonRun` | 一次进图 |

`REJOIN_RAID` 重入的是团员身份，不是队伍。现有副本只存内存、不支持重连：角色在副本中掉线会回到城镇（[副本查询契约](../Server/src/Dfo.Server.Abstractions/World/IDungeonRunDomainService.cs#L462)）。团本保持这一点：掉线照常让角色离开小队与本局，团员身份留在攻坚实例。重入后放回原小队、其他小队还是未编队区，由攻坚实例决定。

## 攻坚实例

- **实例注册表**由攻坚领域服务内部持有，创建、查找和移除攻坚实例，维护团号、团员归属和频道目录，不对外暴露。每次建团有独立实例身份。定时命令、入场回执和归还操作都能据此核对是否仍属于原实例。
- **安图恩攻坚领域服务**（`IAntonRaidDomainService`）是攻坚对外唯一的领域服务，推进一支团从招募、编队、准备、两阶段攻坚、结算到解散的生命流程。团长、团员、攻坚编成、阶段、地图开闭、跨地图机制、截止时间、出战与阶段奖励资格都由该实例裁决。定时源按 [现有局内截止时间机制](DungeonRunKinds.md#一局之内的到点推进) 提交命令，实例维护截止时间并核对阶段和代次。
- **普通地下城运行服务** 管理每支出战小队所在的 `DungeonRun` 及其房间、战斗和单局参与。一次团本可以并行有多支小队出战，每支小队一局。攻坚实例根据经核对的进图、通关、退出等结果更新全团进度。库存、邮件和任务仍通过现有领域提交门票、奖励与任务进度。

## 小队容器与租借

### 容器与普通组队规则分层

现有 `PartyService` 的私有队伍实例同时承担容器与普通组队规则（[队伍实例](../Server/src/Dfo.Server.Application/Parties/PartyService.cs#L576)）。拆为两层：

- **小队容器**只守机械不变量：至多四个槽位、本队内成员不重复、至多一名队长且队长须在本队。允许空队、允许无队长。保留 `PartyKey` 与版本号，客户端 `PartyId` 按 `PartyKey` 与队长版本分配（[队伍号登记](../Server/src/Dfo.Server.Protocol/Game/Party/PartyClientProjectionService.cs#L24)）。
- **普通组队规则**留在 `PartyService`：建队必有队长、队长离队由槽位最前者接任、最后一人离队即注销队伍（[离队](../Server/src/Dfo.Server.Application/Parties/PartyService.cs#L439)）。

创建攻坚实例时，由 `PartyService` 借出五个空容器，每个容器持有独立且稳定的 `PartyKey`，向该实例授予独占租借。五个编组位置始终存在。空队保留 key，不占用副本。团员也可以留在未编队区。清空当前成员与归还容器是两个独立动作。

| 职责 | 所有者 |
| --- | --- |
| 借出空容器、分配 `PartyKey`、维护角色归属索引、拦截普通入口、校验归还并注销 | `PartyService` |
| 决定成员放在哪支小队、委任与撤换小队队长、确定可调队的阶段、决定何时归还 | 持有租借的安图恩实例 |
| 槽位、本队成员唯一、队长归属等机械不变量 | 小队容器 |
| A21 队伍号、名单和清理通知 | 协议投影层 |

### 共享归属索引

`PartyService` 不管理借出容器的成员与队长，但必须感知它们。借出容器中的成员要登记在同一份角色归属索引里：

- `KeyOf` 对已编入小队的团员返回该容器的 `PartyKey`。副本运行、队伍聊天、击杀奖励、副本广播都按 key 读名单，因此可以直接复用普通下图逻辑。
- `FindByKey` 能查到借出容器，名单与队长来自容器本身。
- 一个角色同一时刻只在一个队伍或容器里，跨队唯一由索引保证。

容器的写操作经 `PartyService` 交给攻坚实例的租借句柄执行。攻坚实例决定放谁、换谁当队长；句柄只机械地更新容器、索引和版本号，不做规则判断。攻坚实例不能绕过句柄直接改容器，否则索引会成为第二份名单。一次改编涉及的多个容器与索引在同一个执行器作业里完成；玩法写入本就由唯一执行器串行，不另加锁（[单一执行器](GameplayExecution.md#单一执行器与生产者)）。

开团冻结名单、单次出战名单和阶段奖励资格可以由攻坚实例各自保存，因为它们记录的是不同时间点的业务事实。

### 普通入口遇到借出容器

团员在开团准备期和攻坚中会走普通组队协议：参照服务端在 `PREPARE_START_RAID` 后由客户端按团编组自建小队，攻坚中也放行团员之间的组队操作（`UpstreamStatic`，见 [上游招募调研](tasks/anton-raid/research/01-upstream-recruitment.md#26-普通组队动作反向改写团编组state-2-或-5)）。因此按发起者与目标分流：

- 组队类协议命令先识别涉及的角色是否为团员。是团员就交给攻坚实例裁决，由它经租借句柄写容器；不是团员才交给 `PartyService`。各状态下的处理见 [服务设计](tasks/anton-raid/design.md#43-团员发出的普通组队请求)。
- `PartyService` 自身拒绝任何直接作用于借出容器或其成员的普通操作，返回专门的失败原因，作为分流遗漏时的兜底。
- 周围队伍查询（`Query`）过滤借出容器，团本小队不出现在城镇的公开队伍列表里（[目录查询](../Server/src/Dfo.Server.Application/Parties/PartyService.cs#L38)）。
- 会话清理里的 `CleanupCharacter` 不处理借出容器的成员。攻坚实例在会话清理流程中登记自己的一步，放在现在组队清理的位置（[会话清理](../Server/src/Dfo.Server.Application/Sessions/SelectCharacterLifecycleServices.cs#L178)）。这一步要先把角色移出容器，再结束本局，因为副本离场要求成员先离队（[副本离场](../Server/src/Dfo.Server.Application/World/DungeonRunStore.Departure.cs#L72)）。

## 未编队团员与虚拟队

已编入小队的团员拿到借出容器的 key，不受虚拟队影响。未编队区的团员不在任何容器里，`PartyService` 把他们视为单人虚拟队：

- **普通组队**：未编队团员可能互相邀请、被外人邀请或申请加入普通队。`PartyService` 只感知借出的容器，不感知团员名单。「团员不能自组普通队」是攻坚实例的规则，由上一节的分流交给攻坚实例裁决，做法与 [`PartyRunAdmission`](../Server/src/Dfo.Server.Protocol/Game/Party/PartyProtocolCommands.cs#L305) 一样放在协议命令里。
- **单人下图**：未编队团员若能走到普通选图入口，会以虚拟队开一局。团本城镇内的入场是否放行由攻坚实例判定。
- **入团前已在普通队**：入团时攻坚实例先让角色走普通离队流程退出原队，再登记为团员。退队失败则入团失败。

## 团长改编与出战

攻坚实例提供按目标编成调整小队的操作。团长可以分配、移动或交换成员，委任或撤换小队队长，也可以把团员撤回未编队区。先检查团长权限、实例和阶段、成员归属、容量、槽位和队长归属，再经租借句柄一次应用变更。例如两支满队互换成员，按交换完成后的名单校验容量，两边一起生效。调整失败时保持原编成。

容器允许无队长，但副本入场与运行要求恰有一名队长（[副本队长](../Server/src/Dfo.Server.Application/World/DungeonRunStore.Model.cs#L99)），队伍快照与名单编码也按唯一队长取值（[快照队长](../Server/src/Dfo.Server.Data/Parties/PartyModels.cs#L180)）。攻坚实例守住一条不变量：**正在选图或出战的小队只要非空，就恰有一名队长**。入场前校验；出战中队长掉线或离开时，攻坚实例先委任继任者再移出该角色，或者结束这支小队的本局。城镇投影、公开列表等读取路径因借出容器被过滤，不会读到无队长的容器。

`DungeonRun` 按 `PartyKey` 读取当前小队成员与队长，并用实际进图名单限制本局参与者。改编必须与选图、入场和离场协调。首版拟允许团长调整待命小队，涉及正在选图或出战的小队时拒绝整次调整。这是暂定规则，最终允许调整的时机、需要的客户端确认和通知顺序以 A21 实机为准。

## 收尾与归还

1. 攻坚实例进入收尾，停止新编队和新入场，使过期的阶段、计时和编队操作失效。
2. 结束相关选图和地下城运行，按结束原因完成结算，释放参与者占用。留存清理客户端队伍显示所需的原队伍标识及收件人。
3. 经租借句柄从五个容器清退所有成员，并清理团员归属。容器清空期间仍保有原 `PartyKey`。
4. 攻坚实例凭本实例的租借凭据归还五个空容器。`PartyService` 只校验凭据与容器为空，随后注销容器及其索引。「各局已结束」由攻坚实例的收尾顺序保证，`PartyService` 不依赖副本。重复归还得到安全结果，过期请求无法注销其他实例的容器。`PartyKey` 按单调序号生成、不复用，残留的旧 key 查询只会得到空结果。攻坚实例收尾完成后从实例注册表移除。

单个团员离队只释放其小队成员关系与本局参与。整团归还发生在攻坚实例完成收尾时，覆盖最终阶段结算完成、总攻坚超时和提前解散等路径。

## 依据与待确认项

- **JP86 当前实现。** `PartyService` 的队伍实例必须有队长，最后一名成员离队时注销队伍，掉线清理直接走离队逻辑。`DungeonRunStore` 以 `PartyKey` 绑定一局，成员取自 `FindByKey`，已有按 `RunId` 结束整局并释放占用的入口。协议层以投影服务包住 `IPartyService`，按 `PartyKey` 与队长版本分配客户端队伍号。租借设计需要拆出容器、扩展归属索引、租借句柄、普通入口拦截、目录过滤与会话清理中的攻坚步骤。[组队服务](../Server/src/Dfo.Server.Application/Parties/PartyService.cs#L393) · [副本成员](../Server/src/Dfo.Server.Application/World/DungeonRunStore.Model.cs#L77) · [整局离场](../Server/src/Dfo.Server.Application/World/DungeonRunStore.Departure.cs#L32) · [会话清理](../Server/src/Dfo.Server.Application/Sessions/SelectCharacterLifecycleServices.cs#L175)
- **ServerS4A21 参照实现 `1870c85`。** 招募时 `Network/Handlers/RaidHandler.cs` 的 `HandleRaidManagerWork` 更新攻坚编组。攻坚中和阶段间歇，`Network/Handlers/PartyHandler.cs` 的 `ReassignLiveRaidPartyAsync` 联动实际小队，并检查受影响成员的选图及出战状态。上游用于对照行为与协议，小队容器租借是 JP86 的设计。
- **A21 待实机确认。**
  - 借出小队在客户端怎样显示：走普通队伍名单与端点通知（`0x0009`、`0x000B`），还是只靠团本专用协议。普通下图依赖队伍端点做 P2P，很可能仍需普通队伍通知；这决定改编后的通知复用组队通知计划还是由攻坚实例自行投影。
  - 招募时拖动成员是否立即形成实际小队，开团准备是否依赖组队应答，阶段间歇、退队和重入攻坚队时怎样恢复编组，结束时小队与团显示的清理顺序。
  - 团长委任小队队长是否有独立客户端动作。
  - 团本城镇内普通选图入口是否可达。
