城镇人物同步与赛丽亚旅馆私有空间协议流程

适用范围
========

本文说明城镇中玩家角色的创建、区域名册、移动、换区和离开协议，
以及如何让每个玩家进入同一个赛丽亚旅馆区域编号时，仍然处于各自独立的私人空间。

重点是协议和区域模型，不展开服务端具体类、方法或代码组织。


一、核心结论
============

城镇人物同步不是“广播一条人物出现协议”，而是一个完整的可见性生命周期：

    建立远端人物对象
        -> 下发人物可见性
        -> 下发人物所在区域和坐标
        -> 下发当前区域权威名册
        -> 持续同步移动
        -> 换区时重建新旧区域的可见性
        -> 真正退出时销毁人物对象

赛丽亚旅馆也不应通过给每个玩家伪造不同的城镇ID或区域ID实现。
正确思路是：PVF中的区域编号保持不变，但区域模型决定它是共享空间还是每角色私有空间。


二、城镇人物同步涉及的主要协议
================================

1. S -> C NOTI 0x0002 USERINFO，subtype 0

   用途：在客户端创建或补齐一个远端角色的公开人物对象。

   主要包含：

   - 网络角色ID；
   - 角色身份和名称；
   - 职业、等级等公开状态；
   - 装备与外观；
   - 宠物等公开展示信息。

   只发送位置或区域名册，不足以让客户端创建一个从未见过的远端角色。
   因此，远端角色第一次进入接收者视野时，必须先发送本协议。

2. S -> C NOTI 0x0165 CHARAC_INVISIBLE_FALGS

   用途：同步该角色的可见性状态位。

   Body核心内容：

       u16 角色网络ID
       u8  可见性状态位

   它决定客户端是否以及如何绘制已经建立的人物对象。

3. S -> C NOTI 0x0017 USER_AREA

   用途：告诉客户端某个角色当前位于哪个城镇区域和哪个坐标。

   Body为10字节：

       u16 角色网络ID
       u8  城镇ID
       u8  区域ID
       i16 X坐标
       i16 Y坐标
       u8  朝向
       u8  区域状态

   它负责“这个人物位于哪里”，但不负责创建人物对象，也不代表完整区域成员关系。

4. S -> C NOTI 0x0018 AREA_USERS

   用途：发送一个城镇区域的完整权威名册。

   Body结构：

       u8  城镇ID
       u8  区域ID
       u16 名册人数

       对每名角色重复：
           u16 角色网络ID
           i16 X坐标
           i16 Y坐标
           u8  朝向
           u8  区域状态

   该协议不是只有多人时才发送。
   单人区域仍然发送count=1并包含本人，否则客户端可能无法完成换区状态切换。

   多人时，每个接收者收到的名册都应把自己放在第一条，后面再列同区域其他角色。

5. C -> S CMD 0x0023 SET_USER_POSITION

   用途：客户端上报角色在当前区域内的移动位置。

   A21已知Body为7字节：

       i16 X坐标
       i16 Y坐标
       u8  朝向
       u16 移动状态尾部

6. S -> C NOTI 0x0016 USER_POSITION

   用途：确认并广播角色在当前区域内的位置变化。

   A21已知Body为9字节：

       u16 角色网络ID
       i16 X坐标
       i16 Y坐标
       u8  朝向
       u16 移动状态尾部

   服务端向上报者回送一份，同时向当前可见范围内的其他玩家广播。

7. C -> S CMD 0x0024 SET_USER_AREA

   用途：客户端走到区域边界后，请求进入另一个城镇区域。

   当前协议中可确认的主要字段：

       u8  目标城镇ID
       u8  目标区域ID
       i16 目标X坐标
       i16 目标Y坐标
       u8  朝向
       其余为区域切换上下文字段

   成功路径不是简单回一条同类型CMD，而是通过NOTI 0x0017和NOTI 0x0018完成换区。

8. S -> C NOTI 0x0006 USER_LEAVE

   用途：销毁客户端持有的该角色对象。

   Body核心内容：

       u16 离开的角色网络ID

   它只适合角色真正退出当前世界，例如正常退出、返回选角、会话替换或断线清理。
   普通城镇换区不应使用它，否则可能连带销毁客户端上的队员和P2P状态。


三、进入城镇区域时的人物同步流程
================================

1. 服务端得到当前角色的城镇、区域、坐标、朝向和公开外观。

2. 服务端从区域模型读取该角色对当前接收者是否可见，以及当前区域的权威成员集合。

3. 对于接收者此前没有建立过的每个远端角色，依次发送：

       NOTI 0x0002 subtype 0
           创建远端角色的公开人物对象

       NOTI 0x0165
           设置远端角色的可见性状态

       NOTI 0x0017
           把远端角色放入正确的城镇、区域和坐标

4. 所有需要建立的远端角色都准备好以后，发送：

       NOTI 0x0018 AREA_USERS

   该帧给出接收者当前应看到的完整区域名册，并把接收者本人放在第一条。

5. 对区域内原有玩家执行对称流程：

   - 给原有玩家发送新进入者的0x0002、0x0165和0x0017；
   - 再向每个原有玩家发送以其本人开头的0x0018完整名册。

因此，同区人物出现的最小协议顺序是：

    0x0002 subtype 0
        -> 0x0165
        -> 0x0017
        -> 0x0018

其中0x0002创建人物，0x0017放置人物，0x0018确认区域成员关系。


四、区域内移动同步流程
======================

1. 客户端发送CMD 0x0023，上报位置、朝向和移动状态。

2. 服务端确认该角色仍属于当前会话和当前区域。

3. 服务端更新区域模型中的最新位置。

4. 服务端向上报者返回NOTI 0x0016，确认服务器采用的位置。

5. 如果当前区域是共享区域，则向该区域其他可见玩家广播同一条NOTI 0x0016。

6. 如果当前区域是私人赛丽亚旅馆，则接收者集合只有本人，不向其他会话广播。

移动协议只更新已经存在的人物对象；如果接收端还没有该人物对象，必须先完成上一节的
0x0002、0x0165、0x0017、0x0018人物建立流程。


五、城镇换区同步流程
====================

1. 客户端发送CMD 0x0024，声明目标城镇、区域和落点。

2. 服务端查询PVF，确认：

   - 目标城镇和区域确实存在；
   - 当前频道允许进入该城镇；
   - 目标区域属于共享区域还是私人区域；
   - 目标位置和区域上下文可以接受。

3. 服务端把角色从旧区域成员集合迁移到新区域成员集合。

4. 向迁移者发送：

       NOTI 0x0017
           确认新的城镇、区域和落点

       对新区域中尚未建立的其他角色发送：
           NOTI 0x0002 subtype 0
           NOTI 0x0165
           NOTI 0x0017

       NOTI 0x0018
           发送迁移者在新区域看到的完整权威名册

5. 向新区域原有玩家发送：

       新迁入角色的0x0002、0x0165、0x0017
       以及各自个性化的0x0018完整名册

6. 向旧区域剩余玩家发送：

       NOTI 0x0018

   这份旧区域权威名册不再包含迁移者，客户端据此移除旧区域中的人物投影。

7. 普通换区不发送NOTI 0x0006。

换区的本质不是“销毁角色再创建角色”，而是同一个在线角色从一个区域投影转移到另一个区域投影。


六、赛丽亚旅馆成为私人空间的机制
==================================

PVF城镇定义会给区域标注用途：

    [gate]
        角色进入城镇时的赛丽亚到达房间

    [normal]
        普通共享城镇区域

    [dungeon gate]
        通往地下城的共享区域

当前A21内容和实机结果表明：

    [gate]          = 每角色私有的赛丽亚旅馆空间
    [normal]        = 同频道、同城镇、同区域玩家共享
    [dungeon gate]  = 同频道、同城镇、同区域玩家共享

关键点是：两个玩家可以拥有完全相同的townId和areaId，但仍然不属于同一个可见空间。

建议把区域的有效可见空间建模为：

    共享区域：
        channelId + townId + areaId

    私人赛丽亚区域：
        channelId + townId + areaId + ownerCharacterId

也可以不直接暴露这个组合键，而使用等价的可见性规则：

    如果区域类型是[gate]：
        一个玩家只能看见自己

    如果区域类型是[normal]或[dungeon gate]：
        玩家可以看见同频道、同城镇、同区域的全部共享成员

私人赛丽亚旅馆中的协议表现为：

1. 每个玩家仍收到自己的NOTI 0x0017。

2. 每个玩家仍收到NOTI 0x0018，但名册是：

       count = 1
       唯一成员 = 自己

3. 不向另一个私人旅馆玩家发送对方的：

       NOTI 0x0002 subtype 0
       NOTI 0x0165
       NOTI 0x0017
       NOTI 0x0016
       NOTI 0x0018成员信息

4. 两个玩家即使townId和areaId完全相同，也不会互相出现、互相收到移动或区域成员变化。

5. 当玩家从[gate]走入[normal]时，才加入共享区域名册，并触发远端人物建立与完整名册同步。

6. 当玩家从[normal]返回[gate]时：

   - 共享区域剩余玩家收到不含该玩家的0x0018；
   - 返回者收到只包含自己的0x0018；
   - 不需要为私人房间制造新的城镇ID或区域ID。


七、重点建议：对区域进行响应式建模
====================================

不要让登录、选角、移动、换区、地下城返回、断线和会话替换各自决定要向谁发送哪些协议。
这种“每个业务点手工推送”的方式会快速产生大量独立通知点位，并容易出现：

    - 新增一种进入路径却忘记发送0x0002；
    - 换区只更新新区域，没有清理旧区域名册；
    - 私人赛丽亚房间把移动错误广播给同编号的其他玩家；
    - 断线与普通换区都使用0x0006，误删队伍或P2P状态；
    - 不同入口产生不同协议顺序；
    - 延迟事件把旧区域状态重新覆盖到客户端。

更合适的模型是维护一个权威区域状态：

    AreaState
        区域标识：channelId、townId、areaId
        区域类型：private-per-character或shared
        私人空间拥有者：仅私人区域需要
        当前成员集合
        每个成员的公开人物快照
        每个成员的坐标、朝向和区域状态
        当前区域版本号

所有业务入口只更新事实：

    角色进入区域
    角色移动
    角色换区
    角色退出世界
    角色公开外观或可见性变化

区域模型随后为每个受影响的接收者计算：

    DesiredView(viewer)
        = viewer在当前区域按可见性规则应该看到的角色集合

再把DesiredView与该接收者上一次已投影视图进行差分：

    新增角色
        -> 0x0002 subtype 0
        -> 0x0165
        -> 0x0017

    区域成员集合变化
        -> 0x0018完整权威名册

    已存在角色移动
        -> 0x0016

    角色普通跨区而不再可见
        -> 旧区域0x0018中删除

    角色真正退出世界
        -> 0x0006

这样，协议发送点集中在“区域状态投影器”，业务流程只负责改变区域事实。

响应式区域模型的主要收益：

1. 减少推送通知的独立点位。

   登录、选角、换区、地下城返回和重连都复用同一个进入区域投影流程。

2. 私有空间与共享空间使用同一套协议。

   差别只在DesiredView的过滤规则，不需要维护两套人物同步实现。

3. 协议顺序稳定。

   远端人物始终先0x0002，再0x0165、0x0017，最后0x0018。

4. 旧区域清理自然发生。

   成员集合变化后重新计算旧区域权威名册，不需要每个换区入口单独记得清理谁。

5. 更容易处理延迟和会话替换。

   每次投影使用最新区域版本和当前会话身份；旧事件只能触发重算最新状态，不能恢复旧名册。

6. 更容易测试。

   可以直接给定区域前后状态，断言应产生哪些0x0002、0x0165、0x0017、0x0018、0x0016或0x0006，
   不必分别为每个业务入口重新验证整套协议逻辑。


八、两个玩家的赛丽亚旅馆示例
================================

初始状态：

    玩家A：频道1，城镇1，区域0，[gate]
    玩家B：频道1，城镇1，区域0，[gate]

虽然两人的channelId、townId和areaId都相同，但有效空间分别为：

    A的私人空间：1 / 1 / 0 / A
    B的私人空间：1 / 1 / 0 / B

服务端分别发送：

    给A：0x0018，count=1，成员只有A
    给B：0x0018，count=1，成员只有B

A和B之间不发送远端人物建立或移动协议，因此双方互不可见。

当A进入区域1的[normal]区域：

    A进入共享空间1 / 1 / 1
    A收到自己的0x0017和count=1的0x0018
    B仍在自己的私人空间，不会看见A

当B随后也进入区域1：

    给A发送B的0x0002、0x0165、0x0017，再发送包含A和B的0x0018
    给B发送A的0x0002、0x0165、0x0017，再发送包含B和A的0x0018

此时双方才在共享城镇区域互相出现，之后的0x0023移动通过0x0016互相广播。


九、流程摘要
============

选角或返回城镇
    -> 从PVF确定区域类型和落点
    -> 更新权威区域成员状态
    -> 根据接收者计算可见角色集合
    -> 发送远端角色0x0002 subtype 0
    -> 发送0x0165可见性
    -> 发送0x0017区域和位置
    -> 发送0x0018完整区域名册

区域内移动
    -> 客户端CMD 0x0023
    -> 更新区域模型中的位置
    -> 本人和可见同区玩家收到NOTI 0x0016

城镇换区
    -> 客户端CMD 0x0024
    -> 查询PVF并确定private或shared
    -> 更新新旧区域成员状态
    -> 旧区域发送不含迁移者的0x0018
    -> 新区域执行人物建立和0x0018完整名册流程

赛丽亚私人旅馆
    -> PVF [gate]
    -> 每角色独立可见空间
    -> 0x0018恒只包含自己
    -> 不向其他同编号旅馆玩家广播人物和移动协议

真正退出世界
    -> 从权威区域状态移除角色
    -> 向仍能看到该角色的客户端发送NOTI 0x0006


证据状态
========

A21双客户端已经实机确认：两个角色在PVF [gate]赛丽亚到达房间中互不可见，
进入同一[normal]共享区域后能够互相出现。

0x0002 subtype 0、0x0165、0x0017、0x0018的人物建立顺序与共享区域同屏已经通过当前客户端消费验证。
0x0023到0x0016的移动链路已有协议证据和自动化覆盖；双客户端连续移动显示仍应继续实机复验。

普通换区通过旧区域0x0018权威名册移除迁移者的修正已有自动化覆盖，
修正后的双客户端旧区域移除行为仍应继续实机复验。
