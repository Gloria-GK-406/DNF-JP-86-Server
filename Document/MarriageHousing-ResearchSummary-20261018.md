现阶段不能把 S4A21 的固定家具回放改成当前玩家数据后直接视为实现完成。至少要补齐房间归属和隔离、装饰库存与摆放、扣费原子性、双端刷新、断线恢复。

上表的 14B 是本次客户端构包中识别出的不透明序列化前缀，不直接认定为 Networking 的外层帧头。当前协议 decoder 接口可能收到包含该前缀的块，实现时必须保持同一长度口径。

## 2. 实现前首先需要处理的三个问题

### 心意点的所有权

当前 `MarriageRelation.LovePoints` 存在关系行；心意券使用成功后更新关系点数，再向双方发送通知。这是当前实现事实，不是已经确定的 A21 原服规则。

2014 年署名“DNF 官网”的[历史国服介绍转载](https://dnf.17173.com/content/2014-02-25/20140225140628839_8.shtml)将心意点描述为角色各自持有、婚房由夫妻共用。它只能提供版本差异线索，不能替代 A21 字节证据。客户端 `03D3` 按角色 ID 更新本机点数视图，同样不足以单独证明服务端应存个人点数还是共享点数。

**实现决定待收敛：**与 Claude 对照调查后，先确定个人钱包或共享钱包，再确定购买家具、升级戒指由谁付款。不能一边沿用共享点数，一边按个人钱包设计消费和通知。

### 消费与旧数据兼容

`IMarriageRelationDomainStore` 当前只提供正向 `AddLovePointsAsync`。`MarriageRelationMigration` 每次启动把关系点数提升至已完成婚礼旧列的较大值，代码注释明确以“点数只增不减”为前提。

婚房消费会改变这个前提。如果只减关系行、没有处理旧列与启动对账，重启可能恢复已经消费的点数。引入消费前必须先选定新的真源与迁移策略；仅修改余额字段不够。

**建议：**扣点、金币、券或材料消耗，以及家具/升级结果写入同一命令事务；余额带条件检查；消费后的数据不能任意交给不理解新状态的旧二进制继续运行。兼容双写或结束旧版本兼容，需要在实现方案中明确决定。

### 保管箱与房间的共享范围

历史说明中的保管箱保存婚房装饰，不等于夫妻可以存入任意背包道具的普通共享仓库。当前库存的角色/账号所有权模型也不自动表达婚姻关系所有权。

单次双账号命令锁与“从打开 UI 到关闭 UI 期间只有一方编辑”的约束不同。后者还需要会话归属、失效释放和断线处理。只在打开命令执行时加锁，命令返回后另一方仍可能同时编辑。

房间进入还需要检查当前有效关系及实例隔离。不能因为所有婚房都使用同一 town/area，就让不同夫妻共用同一在场广播范围。

当前 `TownAreaKey` 只有 `(ChannelId,TownId,AreaId)`。`SharesTownPresence=true` 共享同键可见成员，设为 `false` 则只能看见自己，也不能表达“仅配偶之间互相可见”。教堂通过为婚礼分配不同的 area `12..62` 隔离，并没有现成的同 area 私人实例键。因此只能复用教堂的准入/分配/清理思路，不能声称现有教堂 room key 已经解决婚房隔离。具体新增隔离键还是采用客户端可支持的映射，需要在入口方案中决定并验证。

## 3. 建议按玩家闭环推进

以下是调查后的推进建议，不是已批准的实现规格。

这些阶段按玩家验收目标划分；入口可能已经依赖 `03D8` 或相邻消息的必要只读子集，不能把协议强行切成完全独立的阶段。树与戒指两支的先后可按协议闭合情况调整。

| 顺序 | 玩家可观察结果 | 必要保护与证据 |
|---|---|---|
| 1. 进入与恢复 | 已婚双方从原生入口进入同一婚房，离开后能回来，重登保留房间状态 | 入口/回程、关系归属、夫妻之间的房间隔离、非空快照格式 |
| 2. 家具闭环 | 购买进入装饰保管箱，摆放/移动/收回/删除，另一方正确刷新，重登保持 | 钱包归属与原子扣费、编辑会话、容量/摆放规则、失败与重复请求 |
| 3. 属性与戒指 | 婚房属性随有效摆放改变，合法升级戒指后双方状态和属性恢复正确 | 属性计算来源、等级/券/费用校验、双端刷新、不能重复叠加 |
| 4. 树的循环 | 种植、浇水、跨时间成长、收获或移除，断线与重启后可继续 | PVF 时间/次数规则、持久时间戳、奖励一次性结算、双方并发操作 |

家具、戒指、树仍可在同一婚姻系统中作为内部组件组织。独立的关系账本继续提供身份与阶段真源；新组件不应为了查询配偶再依赖完整婚姻门面。

建议保留依赖方向：`协议用例 → 婚姻编排 → 内部婚房/家具/树组件 → 自身存储与规则`，关系事实由账本取得后传给内部组件。库存、任务和通用效果路径需要婚姻身份时，仅依赖关系只读接口，避免形成新的 DI 回环。

## 4. 对照 Claude 报告时需要统一的事项

| 事项 | 为什么必须统一 |
|---|---|
| 心意点归个人还是关系 | 决定钱包键、扣费方、通知接收者和旧数据迁移 |
| 婚戒等级归属及双方同步 | 不能把一对婚戒误建成两件独立普通装备 |
| 装饰保管箱的物品范围、初始/扩展容量 | 避免把家具玩法扩大为任意物品共享仓库 |
| 已购买价值、已摆放价值与婚房属性的关系 | 避免用累计消费值代替实际生效的装饰值 |
| 房间隔离与跨频道进入 | 单纯 town/area 坐标不能表达每对夫妻的私人房间 |
| 编辑权在关闭、断线和重启时如何释放 | 防止永久占用或双人同时编辑 |
| 树成长时间、浇水限制、收获奖励时点 | 时间显示、扣物品和奖励必须依赖同一份状态 |
| 客户端构包总长度与业务尾段 | 旧静态页有长度口径混用，不能直接拿拷贝长度解释业务字段 |

若双方报告对同一字段有不同解释，应先对照固定工件与指令，再安排最小的双端取证；不采用按猜测补零或放宽校验的方式消除差异。
