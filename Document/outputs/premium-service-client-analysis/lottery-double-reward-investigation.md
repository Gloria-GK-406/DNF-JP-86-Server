## 0. 一句话结论

**核心假设成立（一处修正、一处补强）**：双倍不需要在 ACK 里编码两份奖励——ACK 仍是一份 62B
（62B 布局与字节序完全不变），**把 count 字段写成 2 即是 ×2 显示（客户端没有任何自动乘 2 逻辑，
显示数量=ACK count 原样）**；ACK 本身会在本地把第一件实例插入奖励槽（0x1A85220 创建+0x16F2FB0
按槽插入——这是已验收普通流程的同一条链），**第二件装备只由其后的绝对库存投影投递到另一槽**；
slot1 used 客户端不自行计数，**必须在开罐事务后重发 CMD 0x036F 全量快照**（现有
`receipt.ChangedPremiums → GameInstanceDelivery.Premium` 管道已具备）。服务端拒绝额度耗尽的
mode=1 时用 **reason=0x73**（客户端已证弹 70727「已达到今日使用上限。」+ 窗口 0x209）。

## 3. 核心假设裁决

| 假设分句 | 裁决 | 直接依据 |
|---|---|---|
| "ACK 正常展示抽中的一种产物" | **成立（补强）** | ACK 单奖励槽、单物品属性组；且 ACK **本地插入该实例**（0x0113FBD7→0x0113FBF0）——与已验收普通流程同链 |
| "客户端根据双倍标志显示 ×2" | **不成立（修正）** | 全镜像 [mgr+0x15] 读者仅 2 处（构包 0x024F3D9A、ACK 尾调度跳过 0x011404E9），无任何显示路径读取；handler 内无 ×2/shl/自加模式。**显示数量=ACK count 字段原样** → 服务端写 2 才显示 ×2 |
| "服务端通过现有物品列表更新投递两个独立装备槽位" | **成立** | ACK 只插一件于奖励槽；第二件无本地载体，只能由绝对投影投递（投影绝对覆盖后两槽定真） |
| "再通过 036F 同步 slot1 used" | **成立且必要** | handler 无计数写入；若不重发，按钮资格门一直用陈旧 used（可继续放行 mode=1） |
| （隐含）无需双倍专用结果窗口/第二槽位/附加数组/另一 NOTI | **成立（未发现）** | handler 成功路径无第二槽位消费、无额外通知构包；失败路径错误表亦单奖励语义 |

**两个不可堆叠装备的表示**：ACK=（第一件槽位, itemId, count=2, 第一件属性）+ 投影第二槽第二件。
"随机属性是否完全相同"：A21 客户端对第二件**没有任何属性期望**（它只从投影拿）——静态不能证明
"应当相同"；上游 `AggregateRewardEntries(selectedRewards, 2)` 是同一抽取结果数量×2（即上游两件
属性相同）。**建议跟随上游：同一抽取结果的两份 grant（同 id 同属性源），分占两槽**；这不是客户端
约束，是服务端选择。

失败帧 = `u8 result=0 + u8 reason`（result 字节由分发层消费）。reason→表现：

|---|---|---|---|
| 0x11 / 0x0E / 0x04 / 0x13 | 765/766/767/768 | 0x209 | 文案未解码 |

| 0x16 | 2058 | 0x209 | |
| 0xE1 | 70147 | 0x209 | |
| **0x73** | **70727「已达到今日使用上限。」** | 0x209 | **slot1 额度耗尽应答（已证分支）**；与自动修理 0x73 同码同文案 |
| 其他（含 0，现状） | 无（静默） | — | 窗口仍被关闭 |

## 5. 次数、上限与连续开罐（Q4 汇总）

- **读取**：used=[mgr+0x2A]（快照块 slot1）、limit=[mgr+0x62]（PVF 8）；按钮门=0x143FB30(1) 三态（0=未订阅、2=用尽、3=可用——buff-slot3 轮已证该函数内部，无 now() 比较，**过期不过滤**）。
- **请求前检查**：双倍按钮查（不足→70727 不置位）；**复选框路径与构包点都不查**——客户端可能发出"未订阅/已耗尽"的 mode=1（复选框置位后过期/耗尽），服务端必须权威拒绝（0x73）。
- **成功 ACK 本地加次**：否。**必须重发 036F**（现有 OpeningCompleted→ChangedPremiums 管道）。
- **快照重发副作用**：无（036F handler 不触碰开罐/标志）。
- **剩 1 次点全部开启**：连开由 slot7 驱动；双倍标志不清 → 每罐 mode=1；第 8 次成功后服务端 used=8；第 9 次 mode=1 → 服务端 0x73 → 客户端 70727+关窗+停链（**停止，不降级普通**）。静态推导，待实机。
- **时序窗口**：同连接 FIFO，原生结果→投影→036F 的现状顺序与客户端消费序一致（ACK 先插、投影覆盖）；036F 在动画期间到达无副作用。**唯一需避免**：把 036F 放在 62B 原生结果**之前**（未证客户端接受逆序，不采用）。
- **上游 DailyLimit=8**：本轮有 A21 PVF 直接支持（`lottery_onemore 364 8`），不再是纯上游值。

## 7. 最小服务端实现建议（不实施）

**保持不变**：4B 请求解码（mode∈{0,1}+槽位）；62B 成功布局与全部字段序；失败帧形状；
"原生结果在前→绝对投影→清源槽→金币"顺序；单事务+重复 seq 拒绝；PVF 权重抽取（#121）。

**必须改变**：
1. `LotteryOpeningDomainService`：移除 `mode != 0` 一刀切拒绝；mode=1 走双倍分支：
   a. 资格：slot1 订阅 end>now（**服务端做过期过滤**——客户端不过滤）且 used<8；
   b. 同事务：`selector.Roll` 抽一次 → 两份 grant（同 itemId；装备属性按同一抽取结果，各占一槽，
      目标空间 CarriedEquipment×2，与现有单件校验同型）→ 扣罐/金币 →
      `lottery_double_reward_used` 计数 +1（现有周期用量服务，CAS）；
   c. 背包装不下两件：整单拒绝（不消耗、不扣次）。
2. ACK：仍 `Rewards.Single()` 语义——**rewardSlot=第一件槽、itemId、count 写 2、属性=第一件**；
   其余 54 字节与现状逐字节相同。投影投递两槽。
3. 失败应答：额度耗尽/未订阅/过期 → reason **0x73**（70727 已证）；其余维持现状 reason 0。
4. 036F：经 `receipt.ChangedPremiums` 在 OpeningCompleted 聚合内自动重发（核对双倍扣次会产出
   ChangedPremiums——当前只给虚弱/修理/金卡写过，需把 slot1 计数纳入同一回执路径）。
5. 堆叠奖励（未来）：双倍=同槽 count×2，ACK count=两件合计。
