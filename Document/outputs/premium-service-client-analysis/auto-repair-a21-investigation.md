## 0. 一句话结论

**自动修理是客户端驱动的：客户端在"快照到达（mode==3）/ 换房间（MOVE_MAP ACK）/ 移动物品
（MoveItemSpace ACK）/ 本地耐久应用"等时机扫描穿戴装备列表（Equipment 索引 0..31）与快捷栏
（Main 索引 3..8），发现"当前耐久=0 且上限>0"的装备且 slot6 可用时，自动发送 CMD 0x0017 的
**7 字节**全身修理请求（`00 FF FF FF FF 01 00`，auto=1），由服务端完成实际修理与计次并回 ACK；
客户端收到 ACK 后把扫描范围内（含少量排除位差异，见 §6）的装备本地置满耐久并显示
"当前快捷栏里和穿戴中的装备已全部修理。"（70984）。一次触发=一个通配符请求；"每请求消耗一次额度"
是有客户端触发结构支撑的**业务规则建议**，计数本身无客户端证据（§7-A）。**

当前服务端 decoder 只收 8 字节、handler 拒绝 auto≠0，该 7B 请求会被直接丢弃——按 §7 接入。

## 1. CMD 0x0017 全部构包变体与字段宽度（v2 逐字节复核，ClientStatic）

构包 API（定宽依据：0x274D2F2 计数器 +1 / 0x274D322 计数器 +2，写入字节数即计数增量）：
`0x274CA50`=取全局 writer；`0x274D1E0(cmd,flag)`=BeginCommand；
**`0x274D2E0(v)`=写 1 字节；`0x274D310(v)`=写 2 字节（小端 u16）**；
`0x274CED0(buf,len)`=写字节串；`0x274E6D0`=发送。

真实构包点共 3 处（按 cmd 参数过滤 4424 个 writer 调用；`0x00A4EA2D` 为伪引用——那是
BeginCmd 0x48，`push 0x17` 是音效参数）。**各变体逐字节布局**：

### 1.1 自动修理（构包 0x0143FC6F–0x0143FCBD，发送前置见 §2.1）——总长 7 字节

| 偏移 | 宽度 | 序列化调用 | 传入值 | wire 字节 | 语义 | 证据等级 |
|---:|---|---|---|---|---|---|
| 0 | 1 | 0x274D2E0 | 0 | `00` | invenType=Main | 宽度 ClientStatic；语义=参照服命名 |
| 1..2 | 2 | 0x274D310 | 0xFFFF | `FF FF` | slot=-1（全身） | 同上 |
| 3..4 | 2 | 0x274D310 | 0xFFFF | `FF FF` | 材料槽=-1（无） | 同上（参照服未读该字段） |
| 5..6 | 2 | 0x274D310 | 1 | `01 00` | **auto=1 + pad=0**（见下） | 宽度 ClientStatic；auto/pad 拆分=参照服读法 |

**示例（按字节排列）：`00 FF FF FF FF 01 00`**

**auto 字段宽度裁决**：客户端把偏移 5..6 作为一次 2 字节写（u16 值 1 → `01 00` 小端）。
不存在"两个独立 u8 先后写出"的指令形态，也**不应**把这两字节理解成单一 u16 语义字段：
参照服按 `body[5]==1`（auto）+ `body[6]`（pad）两个字节消费，与客户端
"合并写 u16、值恒 ≤1（高字节恒 0）"的序列化完全兼容。表述为：**wire 上 2 字节，
低字节 auto、高字节 pad（恒 0）**。

### 1.2 NPC 全部（构包 0x023EC80B–0x023EC877，修理窗 UI，ebx==0 分支）——总长 8 字节

| 偏移 | 宽度 | 序列化调用 | 传入值 | wire 字节 | 语义 |
|---:|---|---|---|---|---|
| 0 | 1 | 0x274D2E0 | ebx=0 | `00` | invenType=Main |
| 1..2 | 2 | 0x274D310 | 0xFFFF | `FF FF` | slot=-1（全部） |
| 3..4 | 2 | 0x274D310 | u16 [0x3992CAC] | 视值 | NPC/上下文（Hypothesis：==−1 时无对应处理，本变体直接取 u16） |
| 5..6 | 2 | 0x274D310 | ebx=0 | `00 00` | auto=0 + pad=0 |
| 7 | 1 | 0x274D2E0 | flag | `00`/`01` | 参照服命名 quick（[ebp+0x14]≠0→1） |

**示例（NPC 全部、无 NPC 上下文）：`00 FF FF 00 00 00 00 01`**（flag 位视 UI 状态）。
v1 曾把本变体记为 9B——**算术错误，实为 8B**（§9 撤回 #1）。

### 1.3 NPC 单件（构包 0x023EC893–0x023EC957）——总长 8 字节

| 偏移 | 宽度 | 序列化调用 | 传入值 | wire 字节 | 语义 |
|---:|---|---|---|---|---|
| 0 | 1 | 0x274D2E0 | edi | `00` 或 `03` | invenType：背包路径=0；**槽位回退命中穿戴位后=3**（0x023EC8EF `mov edi,3`） |
| 1..2 | 2 | 0x274D310 | esi | 槽位索引 | 背包路径=0x16EF980 查到的 Main 索引；回退路径=vt[0xA58] 命中的 Equipment 索引 |
| 3..4 | 2 | 0x274D310 | [0x3992CAC]==−1 ? 0xFFFF : u16 值 | 视值 | NPC/上下文 |
| 5..6 | 2 | 0x274D310 | 0 | `00 00` | auto=0 + pad=0 |
| 7 | 1 | 0x274D2E0 | flag | `00`/`01` | quick |

回退逻辑（0x023EC8CE）：背包查不到时用 `[0x3B3DFB8].vt[0xA58](i)` 在 i=0..0x1F 内按
物品指针找位，命中→以 invenType=3 重发；仍无→字符串 1106 + 窗口 0x209 中止。

### 1.4 字段语义证据分级小结

- **已证（ClientStatic）**：三变体的总长、每字段宽度与写入顺序、slot 与 invenType 的
  "FFFF=通配 / 0/3=Main/Equipment"取值（由 NPC 单件回退路径的 invenType=3 重发直接证明
  两坐标系一致性）。
- **参照服命名（ReferenceServer）**：invenType/slot/material/auto/pad/quick 的**名字**与
  `body[5]==1` 的 auto 判定、"slot==-1 → 遍历 Equipment 11..22 与 Main 3..8"的全身语义。
- **Hypothesis**：[0x3992CAC]（NPC 上下文）与偏移 7（quick）的具体含义（NPC 路径细节，
  与自动修理无裁决关系）。
- **无实帧**：三种形状均未取得成对帧（§8 实测）。

### 1.5 decoder 最小兼容方案（建议，不实施）

```
长度==8：现状解码保持不变（invenType / i16 slot / i16 material / auto / reserved / quick）。
长度==7：仅当逐字节等于 00 FF FF FF FF 01 00 时接受，
         解码为 { invenType=0, slot=null(全身), material=-1, auto=1, quick=0 }；
         其余任何 7B 组合仍按非法长度拒绝。
其他长度：拒绝（不放宽）。
```

依据：7B 形状的全部已观测构包点只有一个（0x0143FC6F），其字段值是常量；
严格匹配可避免把截断/伪造的 8B 变体误读。该方案保留手动请求全部现有行为。

## 2. 触发链：谁在什么时候发（ClientStatic）

### 2.1 发送函数与六道前置门（0x0143FC10，esi=mgr=[0x3A42CCC]=0x3A42CD0）

```text
[mgr+0x53]!=0        ← 即 slot6 end u32（块偏移 6+6*9=60 → mgr+0x17+60=mgr+0x53）：已订阅
[mgr+4]==0           ← 无在途请求（重复触发抑制，见 §4）
0x119B940([0x3A5C9B0])→0x119B4E0(obj)!=0   ← 当前地图/世界对象存在
0x19FC7E0(obj)=[obj+0xCC]!=0               ← 地图属性（可修理区域，Hypothesis）
0x164B880()==0        ← 非"商店/交易 UI 打开"状态（==1 则放弃）
0x143FB30(mgr,6)==3   ← slot6 可用（end≠0 且 limit>used；上限字节=mgr+0x69，有符号读）
→ 构包发送（§1.1）→ [mgr+3]=1（字节旗标），[mgr+4]=1（dword，在途）
```

### 2.2 破损扫描器（0x0143FF70）——触发的主力路径（v2 修正容器命名）

```text
要求 [0x3B3DFB8]（角色）非空；两轮扫描：
LOOP1：ebx=0..0x1F（32 位）  item = 角色对象.vt[0xA58](ebx)
       ← 穿戴装备列表（wire Equipment=3 的索引系；§5 映射表）
       无显式排除索引/类型门，仅靠属性条件过滤（见下）
LOOP2：ebx=3..8（6 格）      item = 0x1833E70(角色,ebx)→0x16EE6C0(子对象,ebx)
       ← 0x1833E70 返回 [角色+0x5C18] 子对象（忽略入参，ebx 留栈被 0x16EE6C0 消费）；
         0x16EE6C0 读 [对象+0x44] 带标签列表元素 —— Main（背包/快捷栏）列表索引 3..8
         = 快捷栏 6 格（与服务端映射规则 Main 3..8→QuickSlot 完全一致）
每件（LOOP2 先过 vt[0x2C](2) 物品类检查）：
  cur = item.vt[0x150]()（当前耐久，带标签值+0x28）
  max = item.vt[0x144]()（耐久上限，带标签值+0xC）
  若 cur < max 且 cur == 0   ← "耐久已归零且该件有耐久系统"
  → call 0x0143FC10（发送自动修理），扫描结束
```

扫描器的调用者（触发时机）：

| 调用点 | 所在 handler | 前置 |
|---|---|---|
| 0x0110E142 | **CMD 036F（契约快照）ACK handler** | `0x143F880(mgr,6)`（end≠0）且 **mode==3**（0x163E1E0；语义未定名，按商品文案推测=非城镇游戏区，Hypothesis） |
| 0x01173D03 | **CMD 0x2D = MOVE_MAP（换房间/入图）ACK handler** | `0x143F880(mgr,6)`（end≠0）；无 mode 检查 |
| 0x0144062A | 事件门 0x01440610（`(1,8)` 且 [mgr+0x53]≠0） | 契约事件分发入口（Hypothesis） |

### 2.3 其他直接触发点（不经扫描器）

| 触发点 | 条件 | 说明 |
|---|---|---|
| 0x0113D075 | **CMD 0x13 = MoveItemSpace（移动物品/换装）ACK handler** 内，读物品带标签属性==0 | 注册 0x01144C21（push 0;push 0x113C620;push 0x13） |
| 0x022F429E | UI 簇大函数（0x022F3E00 起，带标签属性比较 ×3 组 + 音效 0x1648A20）后 `[ebp-0x1C14]==0` | 疑似本地耐久应用路径，Hypothesis |
| 0x01440610（事件门） | `(arg1==1 && arg2==8)` | 调用者 0x01644A4C 区域按 (type,slot) 分发契约事件 |

**无定时扫描**（未发现 timer 驱动的扫描/发送）。

### 2.4 耐久数据流（谁改耐久）

服务端已有链（ServerCode）：客户端 C2S **0x0030** DecreaseDurability（u8 slotIndex）→
EquipmentDurabilityDomainService → NOTI 回 `01|slot`（不含新耐久值）。耐久数值由客户端演算、
服务端确认记账；归零后由上述触发链发 0x17 自动修理。客户端本地耐久写入走 `item.vt[0x164](value, flag)`。

## 3. ACK（CMD 0x0017 响应，客户端 handler 0x01122C40）成功/失败全表（ClientStatic）

成功（[ebp+0xC]≠0；body 10B = `01 | u32 | u8 | u16 | u16`）：

```text
u32 → [0x3A5C9BC]mgr.vt[0x40](v,1)        ← 修理后金币（免费=不变；"金币余额"语义=参照服命名，
                                            写入 setter 与 CMD 0009 成功路径同型）
u8  = invenType 回显：0(Main)→0x16EE6C0 按容器索引查件；3(Equipment)→vt[0xA58] 按穿戴索引查件
u16 = slot 回显：0xFFFF=全身 → 双轮清扫（范围与差异见 §6）：
      读各自 item.vt[0x144]（上限）→ item.vt[0x164](上限, flag) 置满
      （不做"当前是否损坏"过滤——本地把范围内物品全部置满）
u16 = 传入 vt[0x164] 的 flag（服务端按 0 写；客户端把 (本字段==0) 作布尔用）
尾部：[mgr+4]==1 → 置 2 → call 0x01440C90（条件 slot6 end≠0 且 [mgr+4]==2）：
      特效 + 系统消息 70984「当前快捷栏里和穿戴中的装备已全部修理。」→ [mgr+4]=0
```

失败（错误码 [ebp+0x10]，线性比较链 0x011231FB 起；**已证实分支**）：

| 错误码 | 表现 | 证据 |
|---|---|---|
| 0x0A | 系统消息 751「修理费不足」 | ClientStatic |
| 0x11 / 0x13 | 静默 | ClientStatic |
| 0x15 / 0x16 | 46379「缺少相应物品」/ 46380「指定物品不存在」 | ClientStatic |
| 0x7E | 70069 疲劳公告（窗口 0xFB+聊天） | ClientStatic |
| 0xD2 | 70147+窗口 0x29E（安全模式） | ClientStatic |
| 0x69 | 70379 格式化（登录时间限制） | ClientStatic |
| **0x73** | **70727「已达到今日使用上限。」+ 窗口 0x209** | ClientStatic |
| 其他（含 4） | 公共尾 0x26181C0 默认=静默返回 0 | ClientStatic（虚弱报告已全量走读公共尾） |

尾部：`[mgr+4]==1 → [mgr+4]=0`。**ACK 不更新 slot6 used**（无本地乐观计数；依赖服务端 036F 快照）。

## 4. 状态机与重复触发（ClientStatic）

```text
[mgr+4]（dword）：0 空闲 → 发送=1 → ACK 成功=2（钩子后回 0）/ ACK 失败=0
[mgr+3]（字节）：发送=1；三个 handler 在"slot6 end≠0 且可用(==3)"时清 0
    （0x0114CF7B / 0x01163920 / 0x0119380A —— v1 所称三个"slot6 导航点"实为旗标清理器）
```

**客户端已证行为**：在途标志保证客户端同一时刻只挂一个请求；ACK 成功后本地置满使重扫不再命中。
**客户端不保证**：请求不丢失、不重复、不被伪造（网络层/注入面不在客户端状态机覆盖内）。
**风险点**：服务端持续拒绝时（[mgr+4] 归 0 且耐久仍 0），下一次触发事件会重发——
客户端以事件为重试节奏，服务端拒绝必须幂等无副作用（§7-A/B）。

## 5. 客户端索引 ↔ 服务端槽位映射表（v2 新增，本轮核心交付）

**坐标系统一依据（ClientStatic+ServerCode）**：NPC 单件回退路径用 vt[0xA58] 找到穿戴位后
**以 invenType=3 + 该索引**重发（0x023EC8EF）；ACK 的 invenType==3 分支也用 vt[0xA58](slot)
查件——即 **vt[0xA58] 的索引就是 wire InventoryContainerType.Equipment 的索引**。
服务端 `InventorySlotMappingRuleService`（ServerCode，权威）给出 wire→business 的全部区间。

| 客户端访问 | 索引范围（本轮走读） | wire 坐标 | 服务端 BusinessSlot（映射规则） | 自动修理是否覆盖 | 证据等级 |
|---|---|---|---|---|---|
| `角色.vt[0xA58](i)` | **扫描 LOOP1：0..0x1F 全部**；ACK 置满 LOOP1：0..0x1F **排除 {13,19,20,21,22,23}**，另跳过类型 0x1E | Equipment(3) 索引 i | i∈0..10→WornAvatar；**11..23→WornEquipment**；24→WornCreature；25..27→WornCreatureEquipment；29→WornEquipmentExtension | 扫描：是（含时装/宠物位，靠属性条件自然过滤）；ACK 置满：排除 6 索引+类型门 | 索引系 ClientStatic；区间切分 ServerCode |
| `0x16EE6C0(mgr+0x44 列表, i)` | **扫描 LOOP2：固定 3..8**；ACK 置满 LOOP2：3..count（count=0x16EE780() 读 +0x44 列表计数，**语义未定**） | Main(0) 索引 i | **3..8→QuickSlot(0..5)**；9..64→CarriedEquipment | 扫描：仅快捷栏 6 格；ACK：到 count（若 count=全 Main 长度则**含背包装备**，未定） | ClientStatic + ServerCode |
| `0x16EF980(mgr, itemPtr)` | 遍历 [mgr+0x58..0x5C) 指针数组 | Main(0) 任意索引 | 任意 Main 槽 | 仅 NPC 单件手动修理用；自动修理不经过 | ClientStatic |
| `0x16EE780(mgr)` | — | — | — | ACK LOOP2 上限来源 | ClientStatic（值语义缺口） |

**特别说明（按问题逐条）**：

- **扫描触发范围 ≠ ACK 置满范围（不完全相同，ClientStatic）**：
  ① 扫描 LOOP1 无排除索引/类型门，ACK LOOP1 排除 {13,19,20,21,21?→准确集 {13,19,20,21,22,23}}
  与类型 0x1E——若被排除位上存在归零装备：扫描会触发请求，但 ACK 后客户端**不置满该位显示**；
  ② 扫描 LOOP2 固定 3..8，ACK LOOP2 到 count——置满侧可能更宽（见缺口 G2）。
- **首饰/辅助装备/魔法石**：均落在本服 WornEquipment（wire 11..23）内。客户端 ACK 排除的
  6 个索引（13,19..23）**恰好也在 11..23 内**——这些位具体是什么件**静态无法定名**（缺口 G1）。
  若它们是"无耐久穿戴位"则行为等价；若是有耐久位则存在"修了不显示"的脱节风险（§7-C）。
- **快捷栏中的装备**：包含（LOOP2=Main 3..8=快捷栏 6 格，与服务端 QuickSlot 一一对应）。
  **背包普通装备**（Main 9..64 / CarriedEquipment）：扫描两侧均不覆盖——**自动修理不含背包装备**，
  与商品文案"快捷栏里或穿戴中"一致（ClientStatic+ServerCode）。
- **无耐久/显式排除槽**：排除索引 {13,19..23}（件名未定，G1）；类型 0x1E（ACK LOOP1）；
  vt[0x2C](2) 类检查（LOOP2）；LOOP1 中时装位 0..10、宠物装备 25..27、扩展位 29 **未被排除**，
  依赖物品自身无耐久属性自然跳过（时装在 DNF 无耐久为常识级假设，Hypothesis）。
- **服务端 RepairAllSlots（QuickSlot 0..5 + WornEquipment 0..11）与客户端范围的差异清单**：
  1. 快捷栏：**一致**（wire 3..8）。
  2. WornEquipment：服务端覆盖 wire 11..22（business 0..11，出向 12 格；入向映射却接受 11..23
     ——服务端自身 13 格/12 格的小不对称，ServerCode 事实）；客户端扫描 11..23 全部、ACK 置满
     11..18 + 24..31（减排除）。差异集中在：**排除 6 索引的定名（G1）与宠物/扩展位（见 3）**。
  3. 宠物装备（wire 25..27）/扩展（29）：客户端 LOOP1 扫描范围内；服务端全身列表**不含**。
     若那些位可持有带耐久物品：客户端会触发请求、服务端全身修理不修它们 → ACK 后客户端置满
     显示与服务端状态脱节 → 下次扫描可能再触发（静态推导的循环风险，需 G3 实测裁决）。

**映射缺口（不强行命名，给差分实测）**：
- **G1**：Equipment 排除索引 {13,19,20,21,22,23} 的件名。实测：穿戴窗口逐件记录 wire 索引
  （服务端 MoveItemSpace/穿戴投影日志已有索引），对照排除集。
- **G2**：0x16EE780() 计数语义（快捷栏子列表长度 vs 全 Main 长度）。实测：背包放一件**低耐久**
  （未归零）装备，触发一次自动修理，观察 ACK 后该背包件是否被显示置满。
- **G3**：宠物装备/扩展位是否存在带耐久物品并参与扫描。实测：给宠物穿装备磨耐久（若可行）。

## 7. 服务端接入建议（Q5，v2 修订，不实施）

**裁决：方案 A**（耐久扣减只做状态记账；客户端自动 CMD 0x17 进业务）。
**表述修正（v2）**：现有证据已完整证明"客户端检测→请求→ACK 应用→提示"链，因此当前实现
应采用该链，并避免另加一套服务端主动触发造成双执行。**不**断言"服务端主动修理绝对不可能"
——未证伪，只是没有已证载体，不在本轮展开。

1. **decoder**：按 §1.5 严格接受 7B 常量形状；8B 现状保留。
2. **handler**：7B/auto=1 走自动分支；9B→8B 的 NPC 手动路径现状不动（v1 的"9B"为笔误）。
3. **领域层（自动分支事务内，顺序即一致性边界）**：
   a. 校验订阅（PremiumServiceType.AutoRepair=586 IsActive）与每日额度（剩量>0）；
   b. **读取真实装备状态**：仅在存在"耐久<上限且耐久==0（或按业务口径：耐久<上限）"的
      覆盖槽位时才执行修理与计次；**装备已全部完好（无操作请求）不得扣额度**——
      这是对抗重复/延迟/伪造请求的服务端权威校验（客户端在途标志不覆盖这些面）；
   c. 对覆盖槽位（建议=快捷栏 6 + WornEquipment 全部；是否加宠物/扩展位等 G3 裁决后定）
      执行 0 金币置满；
   d. 计次（完整时间戳持久化、06:00 重置模型）与耐久写入同事务。
4. **响应序列（候选，标静态依据与实测边界）**："事务提交 → 修理 ACK（`01|金币不变|00|FF FF|00 00`）
   → 036F 快照（slot6 used+1）"。顺序分析（v2，替代 v1"无顺序依赖"的绝对表述）：
   - **ACK→快照**：ACK 先置满本地 → 快照到达触发扫描（mode==3 时）不再命中 → 无重发；
     在途标志亦为 0。安全。
   - **快照→ACK**：快照先到（used+1）→ 扫描仍见 0 耐久 → 发送函数被 [mgr+4]==1 在途门挡住
     → 不重发；随后 ACK 置满。安全。
   - 两种顺序静态均不产生重发/遗漏；**遗漏更新风险**只在"只发 ACK 不发快照"时出现
     （客户端 used 陈旧 → 本地资格门放行多余请求 → 服务端权威拒绝兜底）。
   - 实测边界：以上基于 [mgr+4] 生命周期与扫描条件的指令走读，未经实帧验证两序并发的真实到达形态。
   - **无操作请求的响应方式（待决定）**：装备已全部完好时，回成功空 ACK（幂等、避免客户端
     重试节奏下反复弹错）或回错误码——业务规则，本轮不裁。回错误会触发客户端消息（如 0x73 弹窗），
     回成功则静默。
5. **失败路径**：**额度不足 → 0x73**（客户端弹 70727，语义正确，ClientStatic）。
   **未订阅/资格缺失**：已证分支中**没有**"未开通订阅"的专用提示——0x0A 是"修理费不足"、
   0x11/0x13 静默、0x15/0x16 是物品族错误，均不宜借用。建议用静默类（0x11 或默认分支），
   不为弹窗效果借用错误语义（正常客户端在未订阅时本地门已拦截，此路径只兜异常态）。
   错误响应必须幂等无副作用（客户端按事件重试，§4）。
6. **耐久 NOTI/队友同步**：无需额外帧——ACK 自身驱动客户端置满；客户端 handler 无广播路径。
   保持 EquipmentDurabilityChanged 仅投递本人（ServerCode 现状）。
7. **双修/双计次防护**：不采用方案 B（不在耐久扣减处顺带修理）；自动分支以 §7-3b 的
   真实状态校验防重复计次。
