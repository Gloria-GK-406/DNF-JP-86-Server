## 1. 结论先行

1. **[ClientStatic / Confirmed] `0x03F0/0x03F1/0x03F7` 的现有机器文档把 A21 14 字节客户端帧头算进了 body。**三个构包器传给最终发送器的总长度分别为 21、22、23；业务字段从帧内 offset 14 才开始，因此真实 body 长度分别是 **7、8、9 字节**。一期 decoder 若按 21/22/23 字节读 body，会拒绝真实客户端请求。
2. **[ClientStatic / Confirmed] 求婚/响应链的骨架已足以写保守 codec。**`03F0` body 为 `u32 id + u8 action + u8 + u8`；`03F1` 为 `u32 id + u8 action + u8 + u8 + u8 outcome`；`03F7` 为 `u32 + u32 + u8`。其中 ID、action/outcome 的结构由多个独立构包点一致确认；各数字的完整业务名称仍需实帧差分。
3. **[ClientStatic / Confirmed] 客户端有原生 UI 控制器路径会调用这些构包器。**`03F0` 有三类构包路径，`03F1` 有 UI dispatcher，`03F7` 至少有五处直接调用，其中一处位于大型 native/script/menu dispatch。静态证据不能证明这些路径在当前 PVF/town graph 中可达，也不能证明 NPC、任务、角色右键菜单或物品中的哪一个是唯一入口。
4. **[ClientStatic / Confirmed] 接收侧固定消费形状已经进一步闭合。**CMD `03F0` 成功/错误回包读 11 字节，CMD `03F1` 读 12 字节，CMD `03F7` 读一个 `u32`；NOTI `03CD/03CE/03D0/03D4/03D7` 分别一次读取 11/12/15/79/68 字节。
5. **[ClientStatic / Confirmed] A21 `NOTI 03D8` 不是旧彩票 204 字节结构。**客户端先读 `u32 count`，循环读 `count × 6` 字节，再读 13 字节尾部；消费形状为 `17 + 6n`。重复项能进一步确认成 `u16 slot + u32 value/itemId` 的形状，尾部是 `u32 + u32 + u32 + i8`。
6. **[WireCaptured / Confirmed] 既有 A21 入场样本的 `03D8` 是 204 个零。**这只证明 `count=0` 的空态兼容：handler 消费前 17 字节，帧层容忍其余 187 个零。它不验证旧彩票非空形状。
7. **[CurrentImplementation / Confirmed] 当前非空彩票 encoder 会被 A21 误读。**它在 offset 0 写 `2`，A21 会把它解释为两个 6 字节婚房条目，随后从错误位置读 13 字节尾部。婚姻一期应将 `03D8` 限定为“空婚房兼容体”，并从 A21 `03D8` 发送路径移除非空彩票语义。
8. **[Proposal / High] 第一个可运行闭环应是双客户端求婚与响应，再做仪式和重登。**单客户端可以验证长度、ACK 和空态重登不崩；接受/拒绝、双方同步、在线身份和持久关系必须用两个客户端。来宾/邀请和非空婚房可后置。

## 3. 先纠正 C2S 长度：21/22/23 是总帧，不是 body

A21 客户端到服务端的 Game header 已由实帧确认是 14 字节。三个婚姻构包器都呈现同一形状：

1. `MakeHeader(type)`；
2. 在本地总帧缓冲区的 `+14` 起写业务字段；
3. 把 21/22/23 作为总帧长度送入最终写出链。

因此长度算术是：

```text
03F0: 21 - 14 = 7 byte body
03F1: 22 - 14 = 8 byte body
03F7: 23 - 14 = 9 byte body
```

例如 `03F0` action 1 路径在 RVA `0088ADC4..0088ADCD` 写本地 `[ebp-0x1A..-0x14]`，而总帧起点是 `[ebp-0x28]`，两者相差 `0x0E`。`03F1` 和 `03F7` 的字段布局同样从各自总帧缓冲区 `+14` 开始。

这说明 `protocol/game/client-to-server/0x03F0.md`、`0x03F1.md`、`0x03F7.md` 当前记录的 21/22/23 应解释为构包总长，不能直接生成服务端 body decoder。正式回写机器提取器前，应先给 A21 出站提取增加“减 14 字节 header”的规则和回归样本。

## 4. C2S 请求结构

### 4.1 CMD `0x03F0` `WEDDING_REQUEST`

三个独立构包器分别位于：

| 路径 | 函数 RVA / VA | 明确 action | 直接调用点 |
|---|---|---:|---|
| A | `0088AA80` / `00C8AA80` | `1` | `0088B069` / `00C8B069` |
| B | `0088AF10` / `00C8AF10` | `5, 6, 7` | `0088B413`、`0088B433`，另有同函数 tail-jump |
| C | `0088ECF0` / `00C8ECF0` | `2` | `0088EF65` / `00C8EF65` |

**[ClientStatic / Confirmed] body 长度 7：**

| Body offset | Size | 类型 | 静态结论 |
|---:|---:|---|---|
| 0 | 4 | `u32 LE` | 路径 A/C 由目标对象函数 `RVA 008BCEC0 / VA 00CBCEC0` 返回的 `u16` 零扩展；路径 B 在 action 7 时同样取目标，action 5/6 时为 0。`High` 候选为目标角色 ID |
| 4 | 1 | `u8` | action，已见 `1,2,5,6,7` |
| 5 | 1 | `u8` | 路径 A/B 为 0；路径 C 来自一个 UI getter，业务语义 Unknown |
| 6 | 1 | `u8` | 路径 A/B 为 0；路径 C 来自另一个 UI getter，业务语义 Unknown |

路径 A 的发送前置门包括：双方对象存在、两个值分别与 30 比较、关系管理器状态、双方某一属性不相等，以及目标位于当前对象集合。这里可以写成“本地资格/可交互门”；不能仅凭调用地址把属性命名为性别、等级或组队。结合 PVF 最低等级规则，`>=30` 是等级门的高可信候选，但仍需运行时对象字段或错误提示验证。

路径 B 由同一 UI controller 的 `this+0x1A4 = 0/1/2` 分支选择 action 5/6/7。路径 C 要求两个 UI 选择值均不大于 2，并检查费用/状态/目标同场一类条件。它们证明原生窗口中有多阶段操作，不证明具体按钮文本。

### 4.2 CMD `0x03F1` `WEDDING_RESPONSE`

**[ClientStatic / Confirmed] body 长度 8：**

| Body offset | Size | 类型 | 静态结论 |
|---:|---:|---|---|
| 0 | 4 | `u32 LE` | 三个小构包器从 `this+0x1A8` 取值；UI dispatcher 路径写 0。High 候选为参与者/目标 ID，零值可能表示上下文已持有身份 |
| 4 | 1 | `u8` | action，仅见 `1,2,7` |
| 5 | 1 | `u8` | 当前所有已见构包点均为 0 |
| 6 | 1 | `u8` | 当前所有已见构包点均为 0 |
| 7 | 1 | `u8` | outcome/flag，已见 `0,1,2` |

三个小构包器：

| RVA / VA | action | outcome |
|---|---:|---:|
| `00889D90` / `00C89D90` | 1 | 0 |
| `00889DF0` / `00C89DF0` | 2 | 0 |
| `00889E50` / `00C89E50` | 7 | 0 |

UI dispatcher `RVA 0088A200 / VA 00C8A200` 生成六种组合：`{1,1}`、`{2,1}`、`{7,1}`、`{1,2}`、`{2,2}`、`{7,2}`。数字集合是 Confirmed；`1=接受、2=拒绝` 或相反仍是 Unknown。第一轮双客户端差分必须各做一次两个按钮，不能从 UI 分支顺序猜名称。

### 4.3 CMD `0x03F7` `WEDDING_ENTER_CEREMONY`

构包器：RVA `008955D0` / VA `00C955D0`。

**[ClientStatic / Confirmed] body 长度 9：**

| Body offset | Size | 类型 | 静态结论 |
|---:|---:|---|---|
| 0 | 4 | `u32 LE` | value/id，语义 Unknown |
| 4 | 4 | `u32 LE` | value/mode，语义 Unknown |
| 8 | 1 | `u8` | flag；构包器内明确有 0/1 两条路径 |

直接调用至少五处。`RVA 0089703C` 与 `00897FFB` 前均要求本地角色对象存在、某状态函数返回 2、另一个值位于 12..62；后者还比对一个 ID。`RVA 00F92C98` 传 `(1,0,0)`；`RVA 021AB5DD` 位于大型 native/script/menu dispatch，先检查 manager 后传 `(0,0,0)`。这证明进入仪式并非只有一个静态调用点；它不能证明玩家当前能通过哪个入口触发。

## 5. 服务端回包与双方通知

### 5.1 CMD ACK

| Identity | handler RVA / VA | 固定消费 | 字段结构 |
|---|---|---:|---|
| CMD `03F0` | `00894CD0` / `00C94CD0` | 11B | `i32 status, u32 id, i8 action, u8 opaque9, u8 opaque10` |
| CMD `03F1` | `00891FD0` / `00C91FD0` | 12B | `i32 status, u32 id, i8 action, u8 opaque9, u8 opaque10, i8 outcome` |
| CMD `03F7` | `008924B0` / `00C924B0` | 4B | `i32 status` |

`03F0` 在 `status == 0` 时按 action 1..7 进入不同 UI 分支；非零状态进入错误提示映射。`03F1` 在 `status == 0` 时继续按 action/outcome 驱动 manager/UI；`03F7` 的零状态触发窗口关闭/转换，负值 `-10..-6` 一带可见错误映射。第一阶段成功 ACK 应严格发上述长度，错误码先只实现已理解的最小集合，未知错误不要伪装成功。

### 5.2 NOTI `03CD` 与 `03CE`

| Identity | handler RVA / VA | 固定消费 | 字段结构 |
|---|---|---:|---|
| NOTI `03CD` `WEDDING_REQUEST` | `00891140` / `00C91140` | 11B | `u32 status, u32 actor/id, i8 action, i8 value, u8 opaque` |
| NOTI `03CE` `WEDDING_RESPONSE` | `00891960` / `00C91960` | 12B | `u32 status, u32 actor/id, i8 action, u8 opaque9, u8 opaque10, i8 outcome` |

`03CD` 仅在 status 0 时进入请求 UI；action 2 时额外使用 offset 9。`03CE` 仅在 status 0 时走 action 1/2/7 与 outcome 0/1/2 分支。两者与 C2S/CMD 的尾字段形状一致，支持“请求者 ACK + 对方 NOTI”的状态机推断，但正常实帧仍缺失。

## 6. 婚礼、关系与重登投影

### 6.1 NOTI `03D0` `WEDDING_INFO`

handler RVA `008959B0` / VA `00C959B0` 一次读取 15 字节，并按以下边界重组：

```text
u32 @0
i8  @4
i8  @5
u32 @6
u32 @10
i8  @14
```

offset 4 等于 3 时会关闭一个特定 UI；全部字段随后传给 couple manager `RVA 00895290 / VA 00C95290`。消息名来自 A21 上游表，具体字段含义尚无实帧。它是“已婚关系/婚礼状态重登投影”的首要候选，但不能把参考常量直接命名成双方角色 ID 或时间戳。

### 6.2 NOTI `03D4` `WEDDING_CEREMONY`

handler RVA `00895B10` / VA `00C95B10` 一次读取 79 字节。能直接确认：

- offset 0、4、8、12 是四个 `u32`；
- offset 16 是一个字节；
- offset 17 开始有 30 字节区域；
- offset 47 开始有 32 字节区域；
- 两个后部区域均进入字符串转换/展示链；
- offset 0 会与本地角色 ID 比较，offset 8 会与当前时间相关值比较，之后驱动婚礼 UI/town 逻辑。

这足以保留字段边界和设计定向探针，不足以命名 79 字节全部字段。服务端一期不应凭字符串长度猜新郎/新娘顺序或时间单位。

### 6.3 NOTI `03D7` `WEDDING_CEREMONY_BEGIN`

handler RVA `00897B00` / VA `00C97B00` 一次读取 68 字节：

```text
u32 @0
u32 @4
bytes[30] @8
bytes[30] @38
```

两个 30 字节区域均转成字符串，全部字段交给 ceremony manager `RVA 00897770 / VA 00C97770`。这是目前最清晰的仪式开始通知结构；两个 `u32` 和两个人名顺序仍需真实双方抓包确认。

### 6.4 ReferenceOnly 重登顺序

`ServerS4A21` `WeddingReplayBodyBuilders.cs` 的选角/刷新顺序是：

```text
NOTI 03D0 WEDDING_INFO
CMD  03F3 WEDDING_CHARAC
NOTI 03D8 COUPLE_ROOM
```

其 `03D0` 是固定 15 字节，`03F3` 是 31 个零，`03D8` 是 113 字节。它没有读取角色关系或数据库状态，因此只能作为 **ReferenceOnly 回放次序和形状提示**。一期应通过真实已婚/未婚双客户端重登确定哪些帧必需，再建立按关系生成的投影。

## 7. `03D8` 冲突：为何空态能进城、非空彩票会错位

### 7.1 A21 parser

handler RVA `008820F0` / VA `00C820F0`：

```text
u32 count
repeat count times:
    6 bytes
13-byte tail
```

重复项交给 RVA `00881510` / VA `00C81510`。该 helper 对第二个参数取低 16 位作为 slot，另一个 `u32` 参与查找和应用，因此当前最窄、可实现的结构是：

```text
u16 slot
u32 value_or_item_id
```

13 字节尾部被拆成 `u32 @0, u32 @4, u32 @8, i8 @12`，写入 couple-room manager 的 `+D8/+DC/+E0/+E4`。这些字段的业务名称仍 Unknown。

所以 parser 消费长度为：

```text
4 + count * 6 + 13 = 17 + 6n
```

`ServerS4A21` 的 113 字节常量恰满足 `n=16`：`17 + 16×6 = 113`，这是对结构的独立一致性佐证，但其中值仍属 ReferenceOnly。

### 7.2 204 个零的真实含义

既有 A21 入场抓包两处均出现 `03D8` 204 个零。parser 会读到 `count=0`，再消费 13 字节零尾部，总共只读前 17 字节；其余 187 字节是被当前帧分发层容忍的尾随零。

因此可得：

- **[WireCaptured / Confirmed]** 204 零是已观察的 A21 入场体；
- **[ClientStatic / Confirmed]** 它在 `COUPLE_ROOM` parser 中表示空条目和零尾部；
- **[Unknown]** A21 是否要求 204 的固定总长，还是只需 17 字节；静态 parser 本身只消费 17；
- **不能推出**旧彩票非空数据与婚房共用语义。

### 7.3 CurrentImplementation 风险与处置

当前 `LotteryProgressStateMessage` 固定占用 NOTI `03D8`。`EncodeLotteryProgress` 在无记录时返回 204 零，因此偶然匹配空婚房兼容体；有记录时写：

```text
i32 2 @0
i32 -1 @4
i32 -1 @8
8 × 24-byte lottery records @12
```

A21 parser 会把 `2` 当 count，吞掉两条 6 字节“家具”，随后从 offset 16 读 13 字节尾部。彩票记录与婚房边界完全不同；非空时必然语义错位。

一期建议：

1. 将当前消息重命名/拆成明确的 `CoupleRoomEmptyCompatibilityMessage`；
2. body 保持既有 WireCaptured 的 204 零，直到 17 字节短体通过真实客户端；
3. A21 发送路径不再接受 `AccountProgression.LotteryProgress`；
4. 若旧彩票进度仍要保留，先保留数据库，不在 `03D8` 投影；不得无证据迁移到另一个 opcode；
5. 非空婚房另建 `count + entries + tail` encoder，并等正常实帧后启用。

## 8. 原生入口的证据边界

静态调用图确认的是“代码存在并被 UI/controller/native dispatch 引用”，不是“当前角色在当前内容图里一定能点到”。

已确认：

- `03F0` A/B/C 都有原生 controller 直接调用者；
- 调用前检查多个 widget active/state；
- `03F7` 同时有 controller 和大型 native/script/menu dispatch 调用；
- 客户端内存在婚姻请求、响应、仪式和关系 manager。

仍未知：

- 入口是否从角色右键菜单、NPC 对话、Wedding quest、道具、专用窗口或多者共同到达；
- 当前服务端 town graph 是否把所需 NPC/地图接通；
- 未婚/已婚状态如何决定菜单显隐；
- 哪个 action 对应求婚、取消、接受、拒绝、选择婚礼档位或其他阶段。

因此第一轮实机不要先假定“NPC 不可达就没有入口”。应并行检查角色交互菜单/已有 Wedding UI；若原生 UI 没有可达入口，再恢复 NPC/任务链。PVF/NPC/quest 的内容可达性应由 [PVF 专项产物](../pvf/) 独立回答，不能从这份客户端静态报告外推。

## 9. 一期最小状态机与消息编排建议

下面是用于落地和验证的 **Proposal**，不是已抓到的日服完整时序：

```text
发起方 C2S CMD03F0 (7B)
  -> 发起方 S2C CMD03F0 ACK (11B)
  -> 对方   S2C NOTI03CD (11B)

对方 C2S CMD03F1 (8B, outcome=1/2)
  -> 对方   S2C CMD03F1 ACK (12B)
  -> 发起方 S2C NOTI03CE (12B)
  -> 双方关系进入 AcceptedAwaitingCeremony 或回到终态

任一方 C2S CMD03F7 (9B)
  -> 请求方 S2C CMD03F7 ACK (4B)
  -> 双方   S2C NOTI03D4 / NOTI03D7（具体顺序待抓）
  -> 完成时持久化 Completed

重登/回城
  -> 按持久关系发 NOTI03D0
  -> 是否还需 CMD03F3 由实机决定
  -> 发 204-zero 03D8 空婚房兼容体
```

服务端领域状态至少应区分 `Pending`、`AcceptedAwaitingCeremony`、`Completed` 与拒绝/取消/过期终态。协议 action 数值先作为未经命名的枚举保存；只有在双客户端差分后再绑定产品名。成功 ACK、对方通知和 durable commit 的先后必须保证失败时不会让一方 UI 显示成功、数据库却未完成。

## 10. 可运行验证顺序

### 阶段 A：离线 codec 与单客户端安全探针

1. 修正 C2S body 长度为 7/8/9，保留未知尾字节；为 11/12/4 字节 ACK 做严格长度测试。
2. 将 A21 `03D8` 非空彩票发送面切断；选角只发 204 零兼容体。
3. 单客户端分别测试未婚态登录、选角、回城和重登，确认 `03D0` 缺省策略与 `03D8` 空态不崩、不弹错误窗口。
4. 对非法长度、未知 action、过期 connection generation 和非零 status 做服务器日志验证；不能把“连接仍在”称为功能通过。

### 阶段 B：双客户端求婚/拒绝/接受

前置：两个独立账号/角色，处于同一频道和可见场景，双方均开启 frame capture。

1. 从真实 UI 触发一次 `03F0`，记录请求方 C2S、ACK、对方 `03CD`；核对 7/11/11 字节和 ID/action。
2. 第一次选择响应按钮 A，记录 `03F1/03CE` 的 outcome；第二次重新发起后选择按钮 B。以 UI 可见结果给 `1/2` 命名，不按按钮顺序猜。
3. 接受后验证双方实时 UI、角色名/图标/关系窗口；拒绝后验证无持久关系残留。
4. 在 pending、accepted 两个阶段分别让一方断线重登，验证过期会话不收通知、重登状态一致。

### 阶段 C：仪式

1. 双客户端触发真实 `03F7`，记录 9 字节三字段；先确认 flag 两路径由什么 UI 动作触发。
2. 捕获 `03D4` 与 `03D7`，对调双方角色后复测，以确定两个 ID、两个 30 字节名字区的顺序。
3. 验证仪式场景/窗口、双方完成状态、扣费/奖励和断线恢复。
4. 来宾、邀请函和第三客户端观察可在核心双人闭环后补，不阻塞一期。

### 阶段 D：关系重登投影

至少覆盖：

- 一方在线、一方离线；
- 双方同时重登；
- 切换同账号其他角色；
- 婚礼后回城再进城；
- 服务端重启后重登。

每次记录 `03D0`、可选 `03F3`、`03D8` 的实际顺序和字节，并让用户确认配偶名、图标、关系窗口等可见结果。只有此阶段通过，才能把关系恢复标为 ClientVerified。

## 11. 尚未闭合的问题

1. `03F0` action 1/2/5/6/7 的官方业务名称。
2. `03F1` outcome 1/2 中哪个是接受、哪个是拒绝；outcome 0 的场景。
3. `03F7` 两个 `u32` 和 flag 的语义。
4. `03D0` 六个字段的关系/阶段含义。
5. `03D4` 79 字节完整字段表与 `03D4/03D7` 顺序。
6. `03D8` 13 字节尾和非空条目业务语义；17 字节短空态是否被真实 A21 接受。
7. NPC/任务/角色菜单/道具的实际入口及当前内容图可达性。
8. `CMD03F3 WEDDING_CHARAC` 是否是日服 A21 已婚重登必需消息。

这些 Unknown 不妨碍先实现保守 codec、双账号 pending 关系和 204-zero 空态隔离；它们会限制对婚礼 UI、完整重登和婚房的完成声明。
