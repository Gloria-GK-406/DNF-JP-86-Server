## 1. 先给结论

1. **构包形状与 03F0 相同。** 每个带正文的请求都是 `MakeHeader(type)` → `WriteBytes(&raw, N)` → `Finalize`。**正文就是 N 字节**，业务字段从正文 +14 开始，前 14 字节为 raw 结构内的不透明区（栈上未初始化，服务端不得校验其内容）。不能再减 14。机器区记录的 15/28/24/20/20/19/22/34 字节就是正确的正文长度。`0x0402/0x0403/0x0404/0x0405/0x0406` 的正文是 0 字节，为 Confirmed。机器区把 0403 标成“否证、不能断言为空”，现在已经推翻。
2. **NOTI 03D8 的 13 字节尾部就是爱情树快照**，读法与 NOTI `0x03DC COUPLE_TREE` 完全相同，二者写入同一组 manager 字段（Confirmed）。尾部含义：`u32 树种类(0=无树)`、`u32 枯萎时刻(UTC Unix 秒)`、`u32 成长值`、`i8 未知`（High）。
3. **03D8 的 6 字节条目是 `u16 家具槽位 + u32 家具物品 ID`。** 写进 slot→itemId 的有序 map。**协议不带坐标**：摆放位置由“槽位 → 婚房布局固定点”加上物品自身的矩形决定（High）。
4. **情侣仓库（“物品保管箱”）有 40 格**，是全局物品管理器 `[0x03A5C9DC]` 上的一个容器，窗口 id 为 0x1BD，物品容器类型为 0x1F（High）。`03D9` 是全量快照，`03DB/03DA` 是增量，都用 11 字节记录 `u8 kind + u32 itemId + u16 slot + u32 value`：kind=1 表示仓库格（value 是数量，0 清空），其他 kind 表示婚房家具（value 0 撤下、1 摆放）。
5. **`0x03FE` 只覆盖三种移动：仓库内拖动/交换、仓库→房间摆放、房间→仓库回收。** 个人背包与情侣仓库之间的存取**不走 0x03FD..0x0406 中的任何专用协议**，静态上只能追到通用物品代码，并且可达 `CMD 0x0013 MOVE_ITEMSPACE`（Hypothesis，必须抓包）。
6. **爱情树完全由服务端驱动。** 客户端只拿服务端给的枯萎时刻与本地秒时钟 `0124F710` 比较，得出“已枯萎”标志。成长阶段、浇水冷却、收获资格都由服务端推送的数值和错误码决定。种植、浇水、收获、清理分别是 NPC 菜单 1021..1025 和确认框（Confirmed）。
7. **进入婚房没有专用 C2S。** 客户端只用 `town==101(0x65)` 判断“当前在婚房”：在婚房时才生成或刷新家具与树对象。“移动到伴侣身边”（`03FB/03FC`）在任一方处于 town 101 时直接被客户端拒绝，提示 dstr `0x11D0C`（Confirmed）。进入路径、是否需要配偶在线、能否访问他人婚房，静态上都无法回答（Unknown）。
8. **仓库是夫妻互斥的。** `CMD 03FD/03FE` 的错误码 -4/-20 会弹出 dstr `0x11C5E`“您的爱人正在使用物品保管箱”（Confirmed）。
9. **成长胶囊三条请求都是空正文**，状态挂在 manager `[0x039ADF6C]` 的 `+0x110` 能量值、`+0x114` 待领取（对方送来）数、`+0x118` 我方持有数上（High）。

## 3. 婚房与家具

### 3.1 状态容器

婚房 manager 指针为 `[0x039ADF58]`（VA `0x039ADF58`），字段如下：

- `+0x14`：`std::map<u16 slot, u32 itemId>`（`00881140` erase、`0261D200` insert），是家具快照；
- `+0x10`/`+0x28`：在 town 101 中实际生成的家具对象及其列表（`0087F6A0` 按槽位 `010449E0()` 找对象并移除，`008802B0` 生成）；
- `+0x58`：爱情树对象，也就是 `000422C0` getter 的返回值；
- `+0x55`：经 NPC 菜单打开仓库时置 1，回包成功后连同婚房装饰店一起打开；
- `+0xD8..+0xE4`：树快照缓存。

### 3.2 槽位与坐标（问题 1）

- **[Confirmed]** 条目宽 6B，`u16` 槽位与 `u32` 值的读法见 `008820F0` + `00881510`。值进入 `+0x14` map，并在 town 101 时作为物品 ID 生成家具对象（`008802B0(itemId, slot)`）。
- **[High]** 值就是**家具物品 ID**。`00881DF0` 对 map 中每个值调用 `CreateItem(id)`（`01685220`），再从物品数据 +0x1BC 列表里累加数值。ReferenceOnly 的 113B 常量中，16 个值都落在 `10002692..10002802` 区间，与物品 ID 相符。
- **[High]** **坐标不在协议里。** 点击命中函数 `0087FC90(x,y)` 对每个已摆放槽位调用 `0273D000(slot)`，从婚房布局对象（mgr+4）取得该槽的固定点，再加上物品数据中的 16B 矩形做命中测试。`0087E5E0`/`00880E20` 在构包前都用 `0273CF60(itemId)` 校验物品是否属于可摆放装饰。因此槽位是预定义摆放点的编号，与地图或 PVF 的布局数据对应（布局表来源需 PVF 子代理确认）。
- **[High]** `00881DF0` 的累加结果写入本角色对象 +0x388，`03DD` 也为他人角色写同一字段。结合 dstr `0x11CDB`“已使用的心意点(婚房布置)”、`0x11C7B`“当前装饰婚房的物品总数 %d个”和 `0x11C7C`“超过 3/7/12/20 个时追加奖励特效”，它是“婚房装饰值/已用心意点”一类汇总。是数量还是心意点，要看物品 +0x1BC 列表（Hypothesis）。
- 相关提示：`0x11C5F` 该婚房装饰无法摆放在此处；`0x11C60` 此处已存在装饰物；`0x11C6B` 壁纸和地板一旦设置不能回收；`0x11C6C` 窗帘与窗户类只能择一；`0x11C6D` 收回的装饰移至物品保管箱。由此可知服务端必须做的校验有：槽位与物品类别是否匹配、槽位是否占用、壁纸和地板不可回收。

### 3.3 `0x03FE` 的三种用法（问题 2）

raw 结构 28B，业务区 14B = 2 × 7B 记录 `(u8 kind, u16 slot, u32 itemId)`。注意它与 NOTI 11B 记录的字段顺序不同。

| 构包函数 | 触发 | 记录A | 记录B | 前置 |
|---|---|---|---|---|
| `0087C490`（仓库窗口虚表 `02DA4B54`，拖放） | 在保管箱内把格子拖到另一格（拖拽源类型 0x13） | `{1, 源格, 源物品ID}` | `{1, 目标格 this+0x1DC, 目标格现有物品ID或0}` | 目标格≠源格 |
| `0087E5E0(itemId, roomSlot)`（来自 `010454D0`） | 收回房间里的装饰 | `{0, roomSlot, itemId}` | `{1, 同ID堆叠格或第一个空格, itemId}` | 无空格 → `0x54BF` 仓库空间不足 |
| `00880E20(itemId, roomSlot)`（来自 `010446A0`、`01045220`） | 把保管箱里的装饰摆到房间槽 | `{1, 物品所在仓库格, itemId}` | `{0, roomSlot, itemId}` | 客户端检测到占用冲突 → `0x11C5E` |

kind 1 表示情侣仓库格，kind 0 表示婚房槽，与 NOTI 中的 kind 一致。三处构包前都调用 `012F4F40(4)` 锁定容器 4，CMD 03FE 回包时 `012FB9D0(4)` 解锁。服务端应在回包后用 NOTI `03DA`（op=0，A 为源、B 为目标）或 `03DB` 下发结果。

### 3.4 情侣仓库：打开、删除、互斥

- **打开/关闭（03FD）。** NPC 菜单 1020（`021AB26C` → 构包器 B）是主入口。冷却检查不通过时提示 `0x11C8F`“开启物品保管箱和婚房装饰店需要 3 秒缓冲”。关闭窗口时（`0087BF60` → 构包器 A(0)）发送 flag=1。
- **[Confirmed]** 回包 status -4 提示“您的爱人正在使用物品保管箱”。可见原服的情侣仓库同一时刻只允许一方打开。服务端应在 open 时加锁，在 close 或掉线时解锁。
- **[High]** 删除（03FF）走通用的“丢弃物品数量”确认框 `01FEA380`。物品所在容器类型为 0x1F 时取窗口 0x1BD，并调用 `0087BFC0(slot, count)`；物品 ID 取自物品数据 +0x18。客户端不读 CMD 03FF 回包，结果应由 NOTI 03DB（kind=1,value=剩余数）告知。
- **[Hypothesis]** **个人背包与情侣仓库之间的存取**：保管箱格子点击 `0087C310` 走到通用物品函数 `01304E40`，进而可达 `012FA5F0`，后者以 `CMD 0x0013 MOVE_ITEMSPACE`（或 0x19C/0x19D）构包（见 `reach-housing.txt`）。没有任何 03FD..0406 构包器处理这种方向。NOTI 03DA 的 op=1/2 只更新一个仓库格，最贴合“放入/取出”的结果通知，但这是推断。

## 4. 爱情树（问题 3）

### 4.1 快照字段（03D8 尾部 / 03DC）

`01049C90(kind, witherAt, growth, x)`：

| offset | 类型 | 去向 | 结论 |
|---:|---|---|---|
| 0 | `u32` | 树对象 +0xA4；0 → `01047C20` 清树并关闭窗口 0x2A4..0x2A7；≠0 → `01048FF0(kind)` 生成树外观，`01048E50` 查种类表 | **树种类 ID**，0=无树（High） |
| 4 | `u32` | +0x64（加密存放）；`+0x5C = (witherAt <= now)`，now 取自秒时钟 `0124F710`（已有婚礼文档确认其为 Unix 秒） | **枯萎/到期时刻**，UTC Unix 秒（High）。菜单在 +0x5C 为真时提示 `0x11D15` 已枯萎；`01047E30` 用它算“剩余天数”`0x11C9E` |
| 8 | `u32` | +0x24（加密存放）；与种类表的 `+0x54`（存于 +0x20）比较 | **当前成长值**（`0x11C9D`）。≥ 阈值才可收割；否则提示 `0x11CCB` 成长值不足（High） |
| 12 | `i8` | +0x2C | Unknown（种类表加载时也写 +0x2C=0）；候选为今日浇水次数或浇水标志 |

ReferenceOnly 的 113B 常量尾部是 `kind=3, witherAt=1761947886(2025-10-31 21:58:06 UTC), growth=30, x=1`，与上述解释自洽，但只是回放值。

### 4.2 客户端状态机（树对象 +0x94；`01048A40` 每帧推进）

```text
0 空闲 ──NPC菜单──> 弹窗/选择 ──确认──> 1 (种植准备) ──角色空闲──> 2 ──发 0400──> 0
                                         浇水：立即发 0401，状态=4（等回包）──成功──> 5 ──动画完──> 0
                                         收割：6 ──动画完──> 7 ──发 0402──> 0
                                         清理：确认框 kind7 ──> 立即发 0403
CMD 0400/0401/0402/0403 非零 status：状态强制归 0 并提示错误
```

- NPC 菜单 dispatch `021AB244`（menu id 0x3ED 起）中，**1021..1025** 都进入树对象 `01047F90(menuId)`（`npc-menu-dispatch.txt`）：
  - 1021 种植：没有树时打开窗口 0xC 选种子，已有树时提示 `0x11C91`；
  - 1022 浇水：已枯萎时提示 `0x11D15`；成长值已满时弹确认框 kind 4；否则打开窗口 0x2A5“选择洒水壶”（`0x11C9B`/`0x11C9C`）；
  - 1023 收割：成长值不足时提示 `0x11CCB`，否则弹确认框 kind 5；
  - 1024 清理：确认框 kind 7（`0x11CC9`/`0x11CC7`）；
  - 1025 信息：窗口 0x2A7（成长值、剩余天数）；
  - 没有树时，各项提示 `0x11CCA`。
- 确认框 OK 处理 `01093C50`：kind 0 → 种植准备 `01049A80(+0x200,+0x208,+0x210)`；kind 1/2 → 浇水 `01093860` → `01049E40(+0x200,+0x208)`；kind 5 → 收割准备 `01049F30`；kind 7 → `01047AA0`（0403）。
- 种植的两个字段来自选种窗口 `010972A0`。它校验选中物品是合法种子（`0087F870`），并核对物品 ID 与槽位≥0，然后存入树对象 +0x74（发送时为 u16）和 +0x7C（u32）。宽度确定；“槽位 + 物品 ID”是 High。
- **谁能操作。** 客户端没有区分夫妻双方的门；任何能触发 NPC 菜单的一方都会发请求。错误串 `0x11C95`“没有搜索到伴侣信息”、`0x11C97`/`0x11CCC`“您或伴侣没有完成结婚任务”说明资格检查在服务端。是否双方都能浇水或收割，由服务端决定（Unknown，建议两端都允许并由服务端去重）。
- **时间。** 客户端只用本地秒时钟与服务端给的 witherAt 比较，用来显示枯萎状态和剩余天数。成长值、每日浇水次数（`0x11C92`/`0x11C93`）和收获资格全部由服务端维护。需要推送新状态时，服务端应发 NOTI 03DC（收获后另发 03DE 奖励列表）。
- 收获奖励：`03DE` 中的 `(itemId,count)` 只用于展示，物品实际入包要另走通用物品同步。`0x11CF4`“婚房装饰奖励”、`0x11CF5`“丰收的音乐盒 : 剩余%d分钟”提示另有 buff 类奖励（Unknown 协议）。

## 5. 成长胶囊

- 胶囊 manager 指针为 `[0x039ADF6C]`：`+0x110` 能量值（03DF/03E0/CMD0404 成功写入）、`+0x114` 对方送来待领取数（03DF、CMD0406）、`+0x118` 我方持有数（03DF、CMD0404/0405）、`+0x108` 传送道具 ID（03FC 用）、`+0x5C` 本人角色 id（03DD 比较用）。
- UI 为窗口 0x1C3（CMD 0404/0405 回包会先通过 dynamic_cast 取得该窗口并解锁按钮 `008780A0`/`008780B0`）。make/give 是窗口里的两个按钮（`[esi+0x274]`、`[esi+0x27C]`），必须在城镇内（`0123E1E0()==1`，否则提示 `0xB587`）。take 是确认框回调（`.rdata 02DA66F4`，arg==0 即 OK）。
- NPC 菜单 1026（`021AB5FF`）在已婚时以配偶身份值打开窗口 0x1C6，大概率是胶囊/礼物 NPC 窗口（Hypothesis）。相关串：`0x11D00` 收到另一半送来的礼物(%d个)、`0x11D01/0x11D05` 暂无礼物、`0x11D02` 能量不足、`0x11D03` 超出携带上限、`0x11D29` 请到婚房内相关 NPC 处查看。

## 6. 进入婚房与访问权（需求中的专项问题）

- **[Confirmed]** 客户端用当前 town/area 对象 `0069AEE0()` → `02019650()` 是否等于 0x65 来判断“当前在婚房”。全镜像共 11 处这样的判定（`town101-xrefs.txt`），全部位于婚房 manager、树、家具点击与 03FB 回包中，**没有一处位于构包函数里**。
- **[Confirmed]** 03FB/03FC“移动到伴侣身边”在伴侣位于 town 101、自己位于 town 101 或伴侣位于 town 0x11 时，由客户端拒绝（`0x11D0C`）。所以它不是进入婚房的方式。
- **[High]** 03D8/03D9/03DB 都是对**当前角色**的快照或增量，客户端不携带“房主”或“访问哪个房间”的字段。婚房内容完全取决于服务端推送哪对夫妻的数据。字符串 `0x11C7F`“只有已婚的角色才能拥有婚房”。
- **[Unknown]** 进入婚房的具体请求（PVF 地图门、NPC 传送，还是通用 town/area 移动 `0x0024 SET_USER_AREA`/`0x002D MOVE_MAP`）、是否需要配偶在线、能否访问他人婚房：静态客户端证据都无法回答，需要 PVF 地图门数据与实机抓包。
- 建议的本服策略（Proposal）：只允许已婚角色进入自己夫妻共享的婚房实例；配偶不在线也能进入；暂不开放访客。

## 9. 建议的实机取证（需要一对已婚测试角色，双端开 FrameCapture）

1. **仓库开关与互斥。** A 在婚房 NPC 选“物品保管箱”（菜单 1020），抓 `C2S 03FD`(flag 0) 与 `CMD 03FD`。B 同时打开，确认 -4 互斥提示；A 关窗，抓 flag 1。
2. **背包 → 仓库 → 背包。** A 把一件可交易物从个人背包拖进保管箱、再拖回，抓全部 C2S（确认是不是 0x0013 以及 space id）和 S2C（`03DA` op 值、背包同步 NOTI）。
3. **仓库内交换。** 在保管箱里拖动两格，抓 `03FE`（A/B kind=1）与 `03DA` op=0。
4. **摆放与回收家具。** 从保管箱把壁纸、家具摆到房间槽，再收回非壁纸家具，抓 `03FE` 与 `03DA/03DB`。用两个不同槽位比对 slot 编号，并记录屏幕位置。
5. **树全流程。** 种植（菜单 1021）→ 浇水（1022，选洒水壶）→ 观察次日或成长值变化 → 收割（1023）→ 清理（1024）。每步抓 C2S 0400..0403、CMD 回包、NOTI 03DC/03DE。B 端同时观察是否收到 03DC。
6. **胶囊。** 打开胶囊窗口，依次 make/give，B 端 take；抓 0404..0406 与 03DF/03E0。
7. **进入婚房。** 从入口进入 town 101，抓进入前后全部 C2S（确认使用哪条移动协议），以及服务端进入时下发的 03D8/03D9/03DC 顺序。再让配偶离线后单人进入一次，对比结果。
