# A21 邮箱发送、打开与收件人查询的线协议边界

2026-09-24，实施前只读取证。证据等级沿用 [客户端报告](../mail-system-investigation/86-client.md)：本文的 A21 反汇编结论是 **ClientStatic**，没有 A21 邮箱实帧或 `ClientVerified` 结论。未运行客户端、部署补丁、attach 或操作数据库。

## 可直接实现的响应读取合同

下表均为 Game `CMD` 同 type 的服务端响应。`result` 是客户端响应分派入口传入的首个状态字节；成功分支条件为非零。多字节整数按客户端读写原语的顺序解释为小端。`+` 后的字段从该状态字节之后开始。

| Type | A21 客户端消费的成功载荷 | 失败载荷 | 静态证据与边界 |
| --- | --- | --- | --- |
| `0x0060` 打开 | `u8 result!=0 + i16 value`；该 `i16` 交 `0x01A52190`，业务名未由客户端闭合 | `u8 result=0 + u8 error` | handler `0x0111B390..0x0111B3C6`；失败 UI `0x01A51FF0` 仅对错误 `22` 打开资源 `0x810` 分支。旧服把成功值命名 `notLoadedCount`，仅是旧服语义。 |
| `0x005E` 玩家发信、`0x013B` 多附件发信 | `u8 result!=0`；共用入口不再读取字段，转 `0x01A52BA0` | `u8 result=0 + u8 error`，交 `0x01A52C60` | 共用响应入口 `0x0111F950..0x0111F96D`，见 [handler 切片](../mail-system-investigation/mail-handler-slices.txt)。只能确认客户端此入口不消费更多成功字段，不能断言服务端绝不附加字段。 |
| `0x0144` 收件人查询 | `u8 result!=0 + u32 nameByteLength + byte[nameByteLength] nameBytes + u8 f0 + u16 levelLike + u8 f1 + u8 f2 + u8 f3 + u8 f4`，即成功状态后 **`11 + nameByteLength` 字节** | `u8 result=0 + u8 error` | handler `0x0111B250..0x0111B339`：`0x0274FCB0 → 0x0274FC10` 先读 `u32` 长度与名字字节，再转宽字符写入本地 20 码元缓冲；后续读取顺序如左。`levelLike/f1..f4` 传 `0x01A3F460`，其中 `f1` 用作职业图标查询，末位 `f4==1` 影响 UI 分支；其余业务名待样本与 UI 核对。 |

`0x0144` 的 `0x14` 是**本地接收缓冲的上限**，不是线上的 40 字节：`0x0274FC10` 明确先调 `0x027C5310` 读 `u32` 字节长度，再在 `0 < length < 20` 时调 `0x027C5380` 读这些字节；`0x027BAE40` 才用 `MultiByteToWideChar` 转换，`0x0072E7D0` 最后拷贝最多 20 个宽字符到 UI 缓冲。长度 `>=20` 会进入回退支路，不能安全作为正常成功回包。上表 `f0` 在线上名字后、`u16` 前；旧服的成功回包 `u8 + i32 byteLength + UTF-8 name + u16 + 3*u8`（`E:\Project\86JP\Server\DfoServer\Network\Handlers\MailboxHandler.cs:783-798`）虽有相同的长度前缀，但少了 `f0` 和末尾一字节，且编码仍未获 A21 实帧确认；其 `GetResponseNameBytes` 最多可给 20 字节（`:1590-1598`），恰好达到 A21 读取器的回退条件。实施时不能直接沿用旧服回包。

## `0x0144` 请求：已闭合编码

A21 构包入口 `0x01A3D9B4..0x01A3D9E3`（对应旧机器区 RVA `0x0163D9B4`）把 type `0x0144` 写入 CMD 帧，从 UI 控件虚函数 `+0xDC` 取得宽字符名字，再调用 `0x0274D4A0` 写字符串并发送。因此当前可实现的请求 body 为：

```text
u32 byteLength (little-endian)
byte[byteLength] receiverNameBytes
```

`0x0274D4A0` 先调用 `0x027BADD0` 将宽字符转为多字节，再由 `0x0274D410` 写 4 字节长度与不带终止符的字节序列。转换调用是 Windows `WideCharToMultiByte`，代码页来自可变槽 `VA 0x03B89610`。该槽在取证快照中为 `0`（若此刻调用即 `CP_ACP`），运行时可以再设置为别的值；因此 **0144 的实际名字编码尚不能从快照判定**。其他协议已验收的 UTF-8 名字也不能替代本调用点的运行时证据。ASCII 名字在多种代码页中相同，校验至少需要一个非 ASCII 角色名样本。此构包链没有额外请求字段；具体名字长度限制及非法字符处理仍应由实帧和 UI 验证。

旧协议目录 [0x0144](../../../protocol/game/client-to-server/0x0144.md) 的 `UTF-8` 字段释义来自上游 handler，而非 A21 客户端。`E:\Project\86JP\Server\DfoServer\Network\Handlers\MailboxHandler.cs:1391-1401` 也按 UTF-8 解码，是旧服行为；新实现应按本版构包器和运行环境代码页处理，不能把旧注释提升为 `ClientStatic`。

## 尚不能实现为 A21 确认布局的请求

| Type | 当前已证 | 旧服候选（**LegacyOnly**） | 缺口 |
| --- | --- | --- | --- |
| `0x0060` | 客户端注册响应 handler；成功响应读一个 `i16`。普通代码区未找到请求构包点。 | `HandleOpenMailbox` 忽略 request body（旧服 `MailboxHandler.cs:113-126`）；70 样本 `Dispatcher_MailBox_Open` 同样仅提供打开/加载行为线索。 | **请求是否空 body 未证**。不能据旧服忽略 body 或成功回包含计数倒推请求空。 |
| `0x005E` | 发送响应入口与错误反馈；请求构包点未在普通 `.text` 找到。 | 旧服 `TryParseSendMailboxRequest`：`dstr receiverName, i32 gold, u8 itemType, u16 slot, i32 itemId, i32 count, [dstr text], [tail]`（`:1403-1480`）。 | 收件人编码、正文编码、金币/费用、附件及尾字段的 A21 字节边界全部未证。尤其旧服 `TryReadDstr` 固定用 UTF-8，不能据此推断 A21。 |
| `0x013B` | 与 `0x005E` 共用响应入口；请求构包点未在普通 `.text` 找到。 | 旧服候选在名字/金币后有 `u16 attachmentCount`，第 1 项无类型字节、后续项有 `u8 itemType`，每项再有 `u16 slot+i32 itemId+i32 count`，其后可读 `dstr text/tail`（`:1403-1480`）。 | 多附件计数、分项布局和发送触发条件全待 A21 帧；不能仅凭旧服解析器实现 decoder。 |

`0x005E/0x0060/0x013B` 的旧 [协议目录](../../../protocol/game/index.md)也明确标为结构未知。70 ELF 的 `0x61/0x63` 出站常量及 `Dispatcher_MailBox_Send::read` 是另一版本的服务端行为，只提供发送/打开流程参照；不能推成 A21 请求格式。参见 [70 报告](../mail-system-investigation/70-server.md)。

本轮又沿邮箱 UI 的回调注册 `0x01A44BEB/0x01A44BFD` 到 `0x01A3DA10/0x01A3DAF0` 定向复查，并在相邻 `0x01A3D000..0x01A53000` 查找对已知 CMD 初始化原语 `0x0274D1E0` 的直接调用；能定位 `0x0144` 查询及其他非发送操作，未定位 `0x005E/0x013B/0x0060` 构包。该负证据仅限已查普通代码链，不覆盖保护区，也不能代替实帧。

## A21 错误码消费证据

- `0x0144` 失败交 `0x01A3F5B0`：代码 `2→资源 0x15B8`、`7→0x817`、`21→0x15B6`；其他值走资源号 `0`。这证明**客户端分支**，并不证明旧服注释中的“重试/自己/不存在”等业务定义。
- `0x0060` 失败交 `0x01A51FF0`：只有 `22→资源 0x810` 的显式 UI 分支；其他失败仍会清打开状态，但静态未见专属提示。
- `0x005E/0x013B` 失败先调用通用错误处理 `0x026181C0`；若未处理，`0x01A52C60..0x01A52DF5` 的专属跳表按 `u8` 错误码选资源。明确映射为 `3/19/24→0x80B`、`7→0x817`、`8→0xC170`、`10→0x80C`、`14→0x814`、`17→0x80D`、`22→0x55B5`、`23→0x80E`、`70→0x992`、`77→0x129B`、`90→0x1918`、`114→0x89B3`、`159→0x119`、`206→0x112D0`、`214→0xA4F8`、`217→0xACD6`、`219→0xADD4`、`227→0x111F8`、`235→0xADC0`；其余值在此专属跳表直接返回。映射由该 dump 的 `0x01A52E58` 索引表和 `0x01A52E08` 目标表复核。资源号的日文内容及触发条件未在本报告校准，不能把旧服 `ToClientErrorCode` 的业务枚举当作 A21 已证语义。

## 最小实帧采样与落地判据

已检查 A21 debug 目录及仓库内现有 `*.jsonl`/capture 文件名与 opcode；没有找到 `0x005E/0x0060/0x013B/0x0144` 的 A21 邮箱请求/响应成对实帧。现有机器区的 `0x0144` 文义由上游服务端导入，旧 A12 `0x0061` 空箱帧也不可替代本版样本。为关闭实现门槛，需在后续获准的实机采样中保留 **原始 C→S 与 S→C 完整帧、时间点、客户端 SHA-256、UI 操作、成功/失败画面**，按以下最小矩阵取样：

1. 打开邮箱一次，记录 `0x0060` 请求 body 是否为空及 `i16` 回包与未加载数量的关系；再取一种可复现失败，核对错误码。
2. `0x0144` 查 ASCII 名和含日文/中文等非 ASCII 名各一次，分别取存在、自己、不存在角色的响应。逐字节验证请求与响应代码页、名字的长度前缀及 `f0..f4` 与 UI 显示；成功名字的编码字节长应小于 20。勿用只有 ASCII 的样本宣告 UTF-8。
3. `0x005E` 至少取**纯文字无附件、带金币、单物品**三种发送 C→S 帧，并取各自 ACK；用仅改一个输入的差分样本标出金额、物品槽、ID、数量、文本长度与编码。发送有资产影响，采样需由运行环境负责人安排。
4. `0x013B` 取两个不同附件项的发送帧及 ACK，和 `0x005E` 单项帧对照计数与每项类型前缀；取一个失败码与对应 UI 文案，校准错误码业务含义。

在以上样本之前，可先实现响应骨架、0144 请求 decoder 和严格的长度边界检查；**玩家发信与打开请求的 decoder 不能宣称 A21 协议闭合**。开发时可用旧服布局作受控候选，但不得将其写入 `protocol/` 的 `ClientStatic` 字段表或以仅能解析旧服自造包为验收。
