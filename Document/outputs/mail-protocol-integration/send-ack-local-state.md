# A21 发信成功回调与资产投影顺序

2026-09-25。静态证据来自 `DNFClient-A21-debug/dumps/dnf-dump-20260922-194214-883-23144/DNF-memory-rva.bin`，以 VA 减 `0x400000` 读取文件偏移；用 `Document/outputs/mail-system-investigation/disasm_mail.py` 只读复核。置信度：调用链与指令为 **ClientStatic**，余额偏差为一次**实机观察**，邮资计算方式仍是 Hypothesis。

## 实机触发

角色 000 发送含 100 金币的 mail17，数据库余额由 208984 变为 208884；客户端最终显示 208679，低于数据库权威值 205。该样本证明当前发送事务扣 100 后，客户端显示又发生额外变化；仅凭一次差额不能确定 205 是固定邮资、等级公式、其他本地预估或同时发生的另一变化。无金币纯正文的本地扣费仍未采样。

## 同版客户端指令链

- `0x0111F950..0x0111F96D` 是 `005E/013B` 共用响应入口。成功标志非零时 `0x0111F959..5A` 跳转 `0x01A52BA0`；失败时读取错误码转 `0x01A52C60`。
- 成功函数 `0x01A52BA0` 先于 `0x01A52BCE` 调 `0x02305520`，随后在 `0x01A52BDD..EF` 取本地发送对象并调用 `0x01A44B60`；再处理提示窗口和资源 `0x80F/0x209`。ACK 成功并非纯提示。
- `0x01A44B60` 从对象 `+0x358` 取内部状态，跳入 `0x01A42FE0`。后者在 `[esi+0x14] > 0` 时从 `+0x18` 的每项记录循环，依次调用 `0x016F4F40`、`0x016F34D0`、`0x01648AC0`，条件成立再调 `0x016F3360`，然后将数组及计数清零；这说明成功 ACK 后会逐项改变本地发送选择/相关 UI 状态。对象的准确业务类型与是否直接修改真实背包槽位，不能仅由本切片断言。
- 即使 `[esi+0x14] <= 0`（无选择项），也跳至 `0x01A4302D`，继续刷新 UI 并调用 `0x01A406E0`。故无附件不代表成功回调无本地副作用；但此处没有证明无金币纯文扣多少金币。

## 服务端含义

现有发送完成通知先送背包/材料/金币绝对值再送 ACK，ACK 回调可在其后改写本地显示，和上述实机差异一致。修复应对发送成功采用 `ACK → 全部权威资产投影`；领取沿用既有顺序。发信不附金币时，资产变化集合没有 Gold 值，但 ACK 仍执行同一成功路径，因此每次成功发信都需在事务内读取最终携带金币，并在 ACK 后以绝对值通知。失败仅发错误 ACK，不做成功资产投影。

验证至少覆盖 `005E/013B × 附金币 0/非零` 的通知顺序与最终绝对金币；实机需再测一封有金币和一封无金币纯文，并分别记录 ACK 前后 UI、数据库、同版完整帧。确认前不把 205 写成服务端邮资，也不把这一机制标为 `ClientVerified`。

## 复测读数口径补充

修复后Luna在尚未发新邮件时看到写信页208784，而数据库仍208884。写信页可能呈现预计剩余（扣默认邮资），不能等同背包携带总金币。因此最初205差额包含何种预览扣费仍未定案；复测必须读取关闭写信页后的背包金币。ACK后全量权威投影作为防客户端局部估算覆盖的策略保留，其实机效果以背包读数为准。
