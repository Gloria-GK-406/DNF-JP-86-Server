# A21 邮箱接收线静态核对（实施边界）

2026-09-24。结论等级为 **ClientStatic**，不是 `ClientVerified`。只读核对 A21 dump `AAAE24216E0E260AFA528445775E767D104F658FD68FDAD21EC7BB601B9C8A3D`、本工作树编码器和 `E:\Project\86JP` 旧服；没有启动或 attach 游戏、没有改客户端或数据库。地址均为 VA，减 `0x400000` 得 RVA。旧服仅用于对照，不能证明 A21 客户端实际效果。

## 直接供实施使用的结论

| 帧 | 可确定布局 / 客户端消费 | 实施含义 |
|---|---|---|
| S→C `NOTI 0x0061` | `u8 summaryCount, u8 resetMode, summaryCount × 可变长摘要, u16 groupValue, u16 detailCount, detailCount × 可变长正文记录`。`resetMode=0` 清两份本地集合；`groupValue` 传给本地集合方法，语义不能仅凭读取证明。 | 空形状恰好 6 字节；现有 A12 的 6 字节读取跟踪不能当作 A21 实帧。两组都必须按条件字段和长度字段写，不可用固定行宽。 |
| 第一组摘要 | 每条开头顺序是 `u32 claimSlotId, u32 senderLikeId, string(max 0x1e), u32 value, u32 itemTemplateId, u8 flag, u32 instanceValue, u16 durability, u8 attr, u32 enchantCardId, u8 enchantUpgradeCount, u8 amplifyType, u16 amplifyValue`；后续含物品类型条件 `u32`、`u32 expireTime`、带计数的徽章/随机选项、若干尾字段与两段无条件长度块 `u32(4)+4B` 与 `u32(8)+8B`，再接 `u8`，末尾再读 `u32 remainingLike, u32 messageId, u8 terminal`。此表按读取顺序概括，**不保证中间每个字段已闭合业务名**。 | 第一 `u32` 是逐附件槽领取键，末尾 `u32` 是聚合邮件对象键。相同 `messageId` 的多条摘要并到同一对象，但各槽保留各自 `claimSlotId`。正文 ID 不能代替领取键。 |
| 第二组正文 | 每条读 `u32 messageId, u32 senderLikeId, string(max 0x1e), string(max 0x200), u32 timeLike, u16 category, u8 terminal`，`category` 仅 `1/2/3` 进入当前已追到的对象路径。第二组自身没有附件对象读取。 | 第一 `u32` 与摘要末尾 `messageId` 是同一邮件对象键。`0x01199613` 的末字节无条件读取，编码器已补零。当前编码器把标题与正文拼成一段显示字符串属于服务端投影选择；客户端只证明该位置读取一段字符串，未证明其中的换行和标题语义。 |
| C→S / S→C `CMD 0x005F` | 请求 `u32 claimSlotId`。成功 ACK `u8 success=1 + u32 claimSlotId`；失败 ACK `u8 success=0 + u8 error`。 | ACK 的 `u32` 必须回显被领槽位 ID；客户端遍历附件 ID 数组逐项查找，之后更新该槽 UI。一次请求对应一槽，不能以邮件 ID 作为 ACK 键。 |
| C→S / S→C `CMD 0x0086` | 请求 `u32 messageId + u16 action`；成功 ACK `u8 1 + u32 messageId + u16 action`；失败 `u8 0 + u8 error`。 | `0` 的本地投影会移除邮件，`2` 更新对象状态，`3` 先关闭当前邮件窗口，再以 `messageId` 进入另一集合处理。`3=保存` 仅旧服命名支持；A21 静态只能确认调用链，作为当前实施范围外动作安全拒绝是合理的。 |

摘要 ID 链的直接证据：`0x01198F7B` 读取本条第一个 `u32` 至局部 `-0x578`，`0x0119951D` 读取尾部 `u32` 至 `-0x570`，`0x0119952B` 无条件再读 `u8`；`0x01199540..6C` 传二者给 `0x01A4AC70`。该函数以尾部值 `+0x2C` 查已有邮件对象（`0x01A4ACC5..D3`），命中时把首值 `+0x0C` 传给对象更新方法 `0x01A49060`（`0x01A4ACF0..FE`）。新对象构造 `0x01A48FB0 → 0x01A489A0` 将尾部值存对象 `+0x14`（`0x01A489F1..0x01A48A0A`；零时可能回退首值），首值进入 `+0x6C..+0x70` 的附件 ID 数组（`0x01A48C70..89`）；getter `0x01A47330` 和 `0x01A47530` 分别读取这些位置。第二组在 `0x011995C3` 读首 `u32` 到 `-0x570`，`0x011996A9..AC` 仍把它作为聚合键传给同一构造路径。上述地址对应既有切片 `mail-parser-object.txt`、`mail-parser-tail.txt` 和本轮 `disasm_mail.py` 静态复核。

## 对当前编码器的核对与必须修正

`Server/src/Dfo.Server.Protocol/Game/StateSynchronization/StateSynchronizationPayloadCodec.Entry.cs:626-769` 的外层两组形状、随机选项块、尾字段和可选时装双长度块，和 A21 消费顺序及旧服 `MailboxHandler.cs:956-1134` 仅部分一致。A21 `0x011991CC`、`0x011991E6` 在物品判断前无条件读取两段长度块，`0x011991FA` 再读 `u8`；当前 writer 原先对所有摘要漏写这些块，已按静态读取顺序补 `4+4B零、8+8B零、u8零`，连同末尾 `u8零` 合计增加 22 字节；字段语义待实帧确认。集成测试又发现首字段的 `uint/int` 条件表达式被提升成 `long`，曾写出 8 字节；现已统一按 `uint` 固定 4 字节，协议消费测试覆盖了该边界。旧服时装 socket 长度写 30；当前共用 A21 外观常量写 18，且接着仍写 `u32(4)+两 u16`。先前据此判断没有漏长度块是错误的；时装专有块不能替代前述无条件块。因块自带长度，不能仅凭旧服改回 30；实帧/读跟踪仍需校准具体内容。现有编码器的徽章数组只从 core 中取最多两个、随机选项按非零 `Type` 压缩，也是投影选择，不能由旧服同形证明任意物品的客户端效果。

**必须保持两种 ID 独立。** 当前 `WriteMailboxSummary` 对物品与金币使用独立的 `0x40000000 + attachmentId`，纯正文才用 `messageId`；尾字段写 `messageId` 并补 A21 终止 `u8`。其中高位标记是本服内部的领取键编码，不是客户端强制的常量；金币独立槽必须保留自己的稳定、可回显 `claimSlotId`，并让成功 `0x005F` ACK 返回这个确切值。不能把金币槽和第一物品槽共用一个领取键，也不能只用 `messageId` 推断要领取的附件。旧服的 `seedOnly` 尾 ID 零值是兼容技巧；当前实现将纯正文首尾均写邮件 ID。协议测试已模拟两条纯正文逐字段消费到帧末，但仍不是 A21 实机验证。

摘要的普通邮件、金币、纯正文读取顺序已闭合；时装、宠物等物品分支**尚未达到可称完整布局的证据强度**。A21 handler 在 `0x01199031` 按 PVF 类型分支，并通过 `0x0154D560`、`0x01A85220` 等对象构造消费物品数据；这些调用内部及可变数组尚未逐项验证全部类型。现有 writer 对时装/宠物仍只是未校准候选，需至少用同版非空 `0x0061` 解密帧及读取 trace 校准一个金币槽、一个普通物品、多附件和时装。不能把 `protocol/game/server-to-client/NOTI-0x0061.md` 旧机器区名义偏移当作真实偏移；它来自不同 SHA 的静态下界，A12 空帧实测也不能替代 A21。

## `0x005F` 错误消费

`0x0111B340..82` 成功时读一个 `u32` 并传 `0x01A4E860`；后者 `0x01A4E985..994` 在对象的 `+0x6C` ID 数组查找该值。失败时只取 `u8` 传 `0x01A4ECF0`。对该函数的跳转表作只读静态复核，得到下列**已识别分支**，资源号是 UI 资源索引，中文文案未核：

| 错误码 | A21 消费分支 | 旧服对照语义（非 A21 证明） |
|---:|---|---|
| `4` | 特殊背包/物品检查；可走资源 `0x809` 或格式资源 `0xA45D`，并非单一固定文案 | 无空间或单物品携带上限 |
| `10` | 资源 `0x80A` | 金币携带上限 |
| `19` | 资源 `0x1D60` | 交易受限 |
| `21` | 资源 `0x808` | 邮件不存在 |
| `60` | 资源 `0x54E` | 个人商店开启 |
| `219` | 资源 `0x8D24` | 交易中 |

其余码进入通用分支，不能默认为上述任一具体错误。跳转表在 `0x01A4ED65..7D`，目标 `0x01A4ED84/0x01A4EE6C/75/7E/87/90`；旧服映射见 `E:\Project\86JP\Server\DfoServer\Network\Handlers\MailboxHandler.cs:672-777`。分支资源号来自客户端静态，业务名仅上游对照。

## `0x0086` 动作 3 的边界

发送点 `0x01A4FFA5..DA` 先设 `esi=3`，检查当前对象两项状态后以对象 getter `0x01A47330` 的 ID 调用构包器 `0x01A4E800`。成功 ACK 处理 `0x0111B3D0..400` 把 `u32+u16` 交 `0x01A4F490`；`action=3` 路 `0x01A4F49D..AE` 先调用 `0x01A4F090` 关闭窗口，再以 ID 调用 `0x01A4AF90` 处理另一集合。旧服 `HandleChangeLetterStatMailbox` 将 3 实现为 SaveMail，但客户端这些静态指令不能单独证明“保存”的持久化语义或目标箱。当前阶段可拒绝该动作并返回明确失败码；如果将来实施，必须让服务端状态变化、`0x0061` 后续投影与 ACK 的三值一致。

## 最小后续证据

1. 同版 A21 解密帧和客户端读取 trace：空箱、纯正文、金币、普通物品、多附件、时装各一例；逐分支核对摘要可变数组、时装长度、末尾 `remainingLike/messageId` 及两个组的共同键。
2. 对 `0x005F` 做请求与响应成对实帧，验证成功 ACK 回显的实际领取键，以及金币和多附件是否逐槽发送。
3. 若启用 `0x0086 action=3`，对 UI 文案及执行后集合/刷新取证；当前静态只支持安全拒绝或将其作为待实现。
