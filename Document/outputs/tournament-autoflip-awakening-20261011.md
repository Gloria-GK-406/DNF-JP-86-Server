# 黄龙自动翻牌与觉醒材料任务修复

2026-10-11，基线 `ec4432b2`，工作分支 `task/despair-tower`。
用户授权两处修复一起部署；本次为原功能的 Direct 修复，不另建任务契约。

## 原因与变更

- ClientStatic：A21 单人奖励 state6 为 1500ms，只有该状态调用的 `15557D0` 才会扫描 owner 并启动翻牌控件。`01CB ACK` 处理 `1555D70` 写 owner，本身不初始化可见翻牌。原服务端 3 秒补选已经错过显示初始化。
- CurrentImplementation：单人大会规则把补选窗口改为 1 秒；后台每 50ms 检查。已手选的行不覆盖，仍由同一事务命令发奖，每行幂等。增加自动补选行及超期延迟日志。不新增协议、不修改客户端；目前大会仅支持单人，未来多人必须另定时限。约 500ms 余量不构成高延迟网络下的时序保证。
- PVF + 只读数据库：1123 为 character=2/account=4，已接 quest=974“觉醒－剑圣（1/4）”，要求 `3034×1000、3035×1000、3155×100、3150×100`。共享材料实际存放于账号 `item_slots/list_type=240`，不能拿 `accounts` 的历史 cube 列当实时数量。本次读取时共享白晶块 10014、红晶块 10242，背包另两种各 100，已满足条件。
- 材料变化同步及提交前有效进度漏读共享材料；接取不发物品时不补算持有量。现在接取、持有变化、提交前复核均纳入共享材料。原先认为登录补检的虚拟资源支持已经覆盖共享材料，实机反馈证明这个判断不完整：角色与账号虚拟资源是两份独立投影，登录补检只读取了前者。后续纠正见下节。
- 普通 seeking 的奖励计划还遗漏了材料消费。现在纳入消费计划，用既有容器消费 effect 扣除共享／背包材料，支持金币要求，在同一事务记录完成和奖励；预演的共享材料也叠加消费／奖励后的值，以便更新其他已接任务。ACK 不携带消费列表，后续 `000E` 绝对值更新负责同步，包括耗尽清槽。
- 接取与修正同一事务会使暂存的新任务变成带 SQL UPDATE 前提的写入，导致并发错误。任务暂存覆盖现在保留首次 SQL 期望值，新接任务保持 INSERT 语义，已有任务继续保留原始并发保护。
