**Hypothesis** = 命名或业务映射推测。另按"构包指令 / 调用发送函数 / 真实网络帧 / 实机效果"四层区分。

## 一句话结论

CMD 0x0029 成功 ACK 触发的 category=2/msgId=0x001E 是 **UDP/P2P 消息 `USE_COIN`**（名池锚定），
body 5 字节 = `u16 付款人(本地) actorId + u16 复活目标 actorId + u8 分支布尔`。
**接收端把末字节读入后从未使用**——消息文案只取决于两个 actorId 是否相等与一个模式开关；
发送端两个分支的本地结算路径不同（队列/消息处理），但接收端的复活不依赖这条 P2P：
**改状态的唯一途径是 NOTI 0x0020（state=1 满恢复 / state=2 约三分之一恢复）**，
P2P USE_COIN 只是队友端的展示层通知（系统消息 + 付款人实体上的一个表现调用），
且 0x1E 不在服务器中继表内、走直连 peer 投递——单人无队友时它无处可去，复活照常由 NOTI 完成。

## 1. 基础设施与全局身份（修正一处易混点）

- 出站 writer 单例 `[0x03A5C9B0]`（`malloc(0x20A604)`→ctor `0x022E8760`，创建点 `0x01667529`），
  vtable `0x035B9264`：`+0x08 beginPacket(u16 msgId, u8 category)`（7 字节序言：category、msgId、
  4 字节校验和槽）、`+0x20 writeU8`、`+0x24 writeU16`（lab unit-020；本轮复核）。
- **`0x0119B4E0/0x0119B2E0` 是"对压栈对象做 vt[0x8C] 虚分发"的 helper**（读 `[ebp+8]`，
  `0x0119B4F0`），不是 UI 查询——ACK 两分支里的 `push [0x3A5C9B0]; call 0x119B940; call 0x119B4E0`
  实际是 **writer 单例的 `vt[0x8C]()`**（`0x022E55A0`：`mov eax,[ecx+0x20A024]`，返回 writer 的
  成员指针），结果交 `0x19904F0`（成员映射查询）。同理 `push [0x3A5C9B0]; …; call 0x119B2E0`
  = 同一成员的 `vt[0x8C]`。初稿把这类链当 UI/场景事件是错的（revive-timeout 已更正，本轮坐实）。
- 传输全局 `[0x03B55D60]` 与 `[0x3A5C9B0]` 指向**同一个 writer/module 单例**（ctor 内
  `0x022E57B0` 懒登记，调用点 `0x022E890B`）。
- 入站 reader 即同一 module：分发函数 `0x022EA7B0` 是其 **vt+0x04** 槽（无 E8 直调者，虚调用）。
  reader 读宽：**`vt+0x54 = readU16`、`vt+0x50 = readU8`**（用 SET_MOVE_INFO 0x04 的已知
  u8 计数 + u16 坐标布局在 `0x022EBDA9–0x022EBDEC` 交叉验证，Confirmed）。

## 2. 接收注册与完整调用链

P2P/UDP 体系与 Game CMD/NOTI 两张注册表**完全独立**（不同连接、不同帧格式、不同注册机制）：

```text
UDP 收包
→ CNRDUdpModule::分发 0x022EA7B0（vt+0x04）
    序言校验：0x274C9C0(载荷, len) vs 头[3..6]（发送端在 0x022E8AA8 写入同一校验和，Confirmed）
    cell X/Y 过滤（不同格消息丢弃，既有 UDP 字典结论）
    → 主跳转表 0x22FB8E0（0x9A 槽）按 msgId 分发
        槽 0x1E → 0x022F42A8 = USE_COIN 接收 handler（本报告主角）
```

**msgId 0x1E 的名字**：解密字面量名池 0x035B7000–0x035B8CAC 按地址降序 = msgId 升序，
池序 0x1E = `USE_COIN`（字面量 @`0x035B8814`）；锚点复核：池序 0x45 = `BOOSTER_APPENDAGE_STATE`
与既有锚定一致（Confirmed）。**不要与 Game NOTI/CMD 的同编号 0x001E 混淆**——那是另一张表。

`USE_COIN` 发送点全像扫描（既有三跳状态机法）：ACK 短分支 `0x01106352`、长分支 `0x0110660E`
两处 `push 0x1e; push… beginPacket`；未发现第三发送点（覆盖范围：.text 直接构包模式）。

## 3. 5 字节 body 字段表（发送端写 / 接收端读对齐）

| off | size | 发送端来源（Confirmed 指令） | 接收端用途（Confirmed 指令） |
|---:|---|---|---|
| 0 | u16 | **本地（付款人）actorId**：串表 `0x3B3E190` 查询（短 `0x01106356–0x011063D8`、长 `0x0110641A–0x0110668C`），`writeU16`（`0x011063E3`/`0x01106697`） | `readU16`→`0x019E2EF0` 找**付款人**角色 `ebx`（`0x022F42B6–0x022F42F4`） |
| 2 | u16 | **ACK 里的 targetActorId**（`[ebp-8]`，`0x011063F1`/`0x011066A5`） | `readU16`→`0x019E2EF0` 找**复活目标**角色 `edi`（`0x022F42C6–0x022F4307`） |
| 4 | u8 | **分支布尔**：flag==1 写 1（`0x01106402–07`），其他值写 0（`0x011066AE–BB`）——布尔化，非原样转发 | `readU8`→`[ebp-0x1B89]`（`0x022F42D6–0x022F42EB`），**此后整个 handler 无任何引用（读而不用）** |

两角色任一找不到 → 直接跳 `0x022FB866`（分发公共尾，丢弃）。

## 4. 接收 handler 全行为（0x022F42A8–0x022F446F，Confirmed）

1. 见上：解析 + 双角色解析，失败丢弃；
2. **付款人实体动作**：`0x1985F30(ebx)`（=角色 `+0x474` 场景实体，`0x01985F30` 两指令 getter）
   非空 → 实体 `vt[0xBB4](1)`（`0x022F431C–0x022F433A`）。槽语义未命名——付款人实体上的
   表现层调用（候选：币使用效果/资源刷新；Hypothesis）；
3. `0x164B880()` 为真 → 丢弃（该门同样出现在死亡 UI 状态设置的语音选择里，判定为观战/回放类门；
   Hypothesis）；
4. **消息文案选择**（`0x022F4367–0x022F4444`）：
   - `ebx==edi`（付款人==目标，自救）：`0x1102DC0()`（=writer 成员→`0x171C570`→查模式位
     `[obj+0x44C]`）为真 → 消息 `0x95F3(付款人名)`，否则 `0x1F8(付款人名)`；
   - `ebx!=edi`（救他人）：同开关为真 → `0x95F4(目标名, 付款人名)`，否则 `0x1F9(目标名, 付款人名)`；
   - `0x28C14C0` 取串，`0x442570` 拷入 0x100 缓冲；
5. 显示：`ecx=[0x3A5C9B8]; 0x0A9AF50(0xFF9BC8E6, 0x1D, 文案, 0,0,0,0)` → `0x1A60620`
   （`0x022F4447–0x022F446A`，系统消息 idiom，与死亡全灭分支同款）；
6. 结束。

**末字节 0/1 的行为差异：接收端为零**（Confirmed，handler 内字节无第二处引用）。
它只影响发送端走哪个分支（§5）。文案变体由"自救/救他人 + 模式位"决定——因此
**flag 不能命名为"自救/救队友"**：自救还是救他人由两个 actorId 是否相等表达，flag 表达的是
付款人本地结算的两种形态。

## 5. 发送端（付款人）两分支的本地差异（0x011062E0，Confirmed）

入口：result==0 → 直接结束（`0x011062E6`）；读 `u16 targetId`（`[ebp-8]`）+ `u8 flag`（`[ebp+0xF]`）；
`flag==1 → 0x0110631C`，否则 → `0x01106419`。

| | 短分支 flag==1 | 长分支 flag!=1 |
|---|---|---|
| 复活币待办队列 `[0x3A5C9BC]` | `0x016F3360` **无条件弹出一个元素** | **三分支条件弹**：`0x164B880()` 真→弹；writer 成员→`0x19FC7E0`→`0x1729F00` 通过→弹；死亡 UI `0x0138A190(0)>=0`→弹；**否则 `0x016F34D0` 重新入队**（带 +0x44 记账） |
| 消息 | 无 | targetId≠myId → `0x0E75B80`（`[0x3A5C9EC]` 窗口）消息 0x11/0x198C；队列非空时再弹消息 9（`0x011064A5–0x011064FA`） |
| 死亡 UI | 不碰 | 尾部 `0x0138AD10`（死亡 UI 类方法）+ `0x0162C410()` |
| writer 成员查询 | `vt[0x8C]`→`0x19904F0` | 同左（尾部再来一次） |
| P2P USE_COIN | 发（末字节 1） | 发（末字节 0） |

队列辅助命名（Confirmed 指令）：`0x016F3360`=弹尾元素；`0x016F34D0(a,b)`=弹尾+记账；
`0x016F17D0`=按 key `0x98D341` 查待办（-1 无）；`0x016ED5C0`=取向量第二元素（count≤1 抛）。
`[0x3A5C9BC]` 即"复活币待办队列"管理器。

## 6. 投递范围（0x022E56F0 → vt[0x44] = 0x022E89D0，Confirmed/High）

`0x022E56F0(0,0)` → `module->vt[0x44](0, -1, 0, 3)`（-1 = 全部目标）：

1. `0x2768ED0(msgId)` 查**服务器中继位图表**（msgId 5..0x29 的 37 项 bitmap，索引表
   `0x2768F00`、跳转 `0x2768EF8`）：命中者经 `[0x3B7F09C]→0x1A182F0→vt[0x20]`（flag 7）走
   服务器连接转发。**`0x1E` 的表项 = 0：不在中继表，不经服务器**（Confirmed）。
2. 直连路径：载荷先过 `0x022D2C60`（xor+ror 流混淆，密钥 `0x022D2DD0`，原地变换）；
   然后 peer 管理器（`0x0289E620` → `0x4DAEC30`）槽循环：槽==-1 且非广播模式 → 跳过；
   `0x022E7080(module, idx)`（取 `[module+0x20A078+idx*4]`）非零 → 跳过；否则
   `0x0289EF30(管理器, 头, 长, idx)` 逐 peer 发送（`0x022E8D5A–0x022E8D93`）。
3. **本机回环：未找到**——入站分发 `0x022EA7B0` 无 E8 直调者，按 vt[4] 间接调用模式扫描
   两个全局的 12 字节窗口亦零命中；peer 槽集合是否含本机未验证。**边界如实记录**，
   用实测区分（见 §10 E4b）。
4. **单人（无 peer）**：循环无可发对象，该 P2P 消息无处投递——**复活不受影响**：
   付款人本地结算在 ACK handler 完成，目标状态由 NOTI 0020 完成（§7）。
   "broadcast"注释不作依据，本节全部指令断链。

## 7. ACK / NOTI 0020 / P2P 三者职责（核心问题四）

### 谁改谁的死亡状态

- **NOTI 0x0020（state=1/2）是唯一的状态变更者**（Confirmed）：handler `0x0114F420` 复活分支
  `0x0114F862+`：角色 `vt[0x5C8](1,0,1)`、`vt[0xB18](1)`（复活特有虚调用，语义未命名）；
  **HP/MP 恢复**：`vt[0x3DC]`（取满值）→`vt[0x3D4]`（写入）、`vt[0x3E4](1)`→`vt[0x6D8]`——
  **state==1 原值写入（满恢复）**（`0x0114F958–0x0114F99D`）；
  **state==2 两处各除以 3**（`0x0114F906–0x0114F950`：64 位除法 helper `0x2C63C80(…,3,…)`
  与 `0x55555556` 魔数除 3）→ **约三分之一恢复**。死亡标志清零在公共尾
  `0x011500D0–0x011500E8`（`vt[0xB10]`，state==0 写 1/否则写 0，死亡复活共用）。
  之后进入与死亡同款的下游（0x011500A0+）：存活者>0 → 倒计时 UI 收起为状态 0/1
  （复活者的倒计时由此消失，与前两轮结论衔接）。
  state=1/2 的业务名：参照服 USE_COIN 成功写 **0x01**（DungeonCombatHandler.cs:906-913）；
  state=2 的触发场景未知（推测为非满额复活形态，Hypothesis）。
- **CMD 0x0029 ACK（回付款人）**：不改任何死亡/HP 状态。做付款人的请求结算（§5）并触发 P2P。
- **P2P USE_COIN**：不含任何状态写（§4）——纯展示层。

### P2P 是必需步骤吗

**不是**（Confirmed，静态）：复活所需的一切（标志、HP/MP、表现）都在 NOTI 0020 的 handler 里；
P2P 接收端只有消息与一个实体表现调用。单人模式下它甚至无处投递。

### 重复执行与顺序

- 队列弹出只发生在 ACK handler；NOTI 0020 不碰队列 → **无双弹风险**（Confirmed）。
- 付款人本地消息（长分支）与队友收到的 P2P 消息在不同客户端，天然不重复；唯一潜在重复是
  "本机也收到自己的 P2P"（§6.3 未证实，实测点）。
- 顺序：参照服 **NOTI 0020 先、ACK 后**（DungeonCombatHandler.cs:906–920）。静态上 ACK 长分支的
  三分支队列门（`0x1729F00` 复活队列等）在死亡状态已清/未清时可能走出不同路径，
  **建议保持 NOTI→ACK**（High；顺序敏感性未实测）。

### ACK 的接收方

**只回付款人（发出 0x0029 的会话）**（Confirmed 机制层：CMD 响应只投递到请求连接；
参照服同样只 `session.SendPacketAsync`）。目标与队友收到的都是 NOTI 0x0020 广播。
实机已见两连接都收到 0020 类广播（死亡场景）；复活场景的广播送达待 E1 顺带确认。

| 端 | 收到 | 动作（Confirmed 除注明） |
|---|---|---|
| 付款人 | CMD 0x0029 ACK | 按 flag 走短/长结算（§5）；构发 P2P USE_COIN(localId, targetId, flag') |
| 付款人（同时） | NOTI 0020 (target, 1/2) | 若自救：目标=自己 → 本地复活（标志清零、HP/MP、特效、倒计时收起） |
| 复活目标（≠付款人时） | NOTI 0020 (target, 1/2) | 本地复活同上 |
| 其他队友 | NOTI 0020 | 远端角色复活表现 |
| 其他队友 | P2P USE_COIN | 系统消息（自救/救他人文案）+ 付款人实体 `vt[0xBB4](1)` |
| 服务器 | —— | 0x1E 不经服务器（中继表无此项） |
| 单人（无队友） | 无 P2P 接收者 | 复活完全由 NOTI 0020 完成 |

## 9. 候选服务端响应顺序（普通副本；实施参考）

自救（付款人==目标）与救队友（付款人≠目标）**同一套顺序**，仅 targetId 不同：

1. 服务端校验/扣币（领域侧，不在本报告范围）；
2. **S2C NOTI 0x0020** 广播给副本内全体：`u16 targetActorId + u8 state + u8 0`，
   state=**0x01**（满恢复；与参照服一致、与客户端 state1 分支对齐）；
3. **S2C CMD 0x0029 ACK → 仅付款人**：`01 + u16 targetActorId + u8 flag`（**4 字节**）。

已可确定的字段：NOTI 的 actorId/state/尾 0；ACK 的 result/targetId 与总长 4 字节
（客户端 `0x011062F0–0x0110630A` 连续读 u16+u8，Confirmed）。
**仍需实测确定**：
- **flag 的正确业务值**：0/1 都被接受且只改付款人本地结算路径（==1 简单/无条件弹队列，
  !=1 完整/条件弹+消息）。无实帧。若参照服 ACK（3 字节、无 flag，DungeonCombatHandler.cs:915–920）
  在 A21 客户端上运行，读越界 1 字节后 flag 大概率≠1 → 走长分支——该已知冲突的实际表现待实测，
  不能把参照服的"省略 flag"当作 A21 的正确默认；
- NOTI/ACK 顺序敏感性（建议 NOTI 先，见 §7）；
- state=2 的适用场景（若只做复活币，可先不实现）。

## 11. 边界与未闭合项

- `vt[0xBB4]`（付款人实体）、`vt[0x5C8]/vt[0xB18]`（复活核心）三个槽的**语义未命名**
  （结构定位 Confirmed，业务名 Hypothesis）；命名它们需要 actor 类的更多横向对照，本轮不做。
