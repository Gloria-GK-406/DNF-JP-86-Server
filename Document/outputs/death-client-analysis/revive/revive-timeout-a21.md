## `0x0029` 发送门与响应影响

界面入口 `02301EE0` 先检查全局状态和 `[this+0x9258]` 许可位，再按场景选择路径。地下城路径在 `02301FF8–2026` 从 UI 对象虚表 `+0x4C` 取得目标，调用 `016F62D0`；其他路径在 `0230202C–204B` 调用 `00A9C270`，以及在 `02302075–2083` 调用 `016FF630`。当前只定位到界面回调入口，尚未定位物理按键或按钮资源 ID，不能据此指定某个按键。

地下城直接发送函数 `016F62D0` 在 `016F62D6–635B` 顺序检查：游戏/地下城上下文存在；`[this+0x6C, +0x70]` 所表示的容器元素数 `<4`；`01705320` 返回假；`016EF580(target)` 非负；`[this+0x7C]==0`；以及 `01A551B0`、`024E9430` 两道情境门。任一不满足就返回，不构包。通过后 `016F635D–637D` 写 `u16 target` 并发送；`016F6382–639A` 随即触发本地动作。`00A9C270` 与 `016FF630` 是另两条满足各自场景门后写同一 `u16 target` 的路径。UI 状态机 `023D7BB0` 的状态 0 也在 `023D7C28–7C48` 写 `0x0029`，状态 1 写 `0x002A`。

因此“死亡后没有观察到 `0x0029` 请求”首先是客户端发送门没有全部通过的现象，不能由成功 ACK 缺少字段直接解释；ACK 错误是发出请求后的另一项兼容性问题。仅凭一次无请求日志无法判定究竟是哪一道门挡住了它。

参照服 `ServerS4A21/Server/DfoServer/Network/Handlers/Dungeon/DungeonCombatHandler.cs` 的成功 ACK 在 `915–920` 行只写 `u8 result=1 + u16 targetId`。在 A21 客户端通用 `result` 前缀之后，它还要再读一个 `u8 flag`，所以该 ACK 相对客户端静态解析少 1 字节。参照服失败 ACK 在 `879–885` 行写 `u8 result=0 + u16 targetId`，但通用失败前缀读取的第一个尾字节是错误码；不能把这两个字节当作客户端认可的 `targetId`。这两点是静态布局冲突，实际响应效果仍需真实帧验证。

### `flag=0/1` 的可观察差异与最短后续取证

静态代码足以区分两种路径，尚不足以给它们命名。以 `targetId=1` 示意，成功响应 body `01 01 00 01` 选择短路径，`01 01 00 00` 选择长路径：前一个字节为通用成功结果，随后为小端 `u16 targetId`，最后为 `flag`。两条路径均触发场景事件 `(0x1E,2)`，但短路径给同一 UI 虚接口的值为 `1`（`01106402–6407`），长路径给 `0`（`011066B4–66BB`）。长路径还会比较目标与本地 actorId（`0110649C–64BD`），并执行 `0138AD10` 等额外角色/UI检查；短路径不做这些检查。故不能据 `flag` 推断目标是否本人，亦不能在缺少实帧时任选 `0` 或 `1` 作为“正确默认”。

后续最短实测只需一份**自然发生的**成功复活会话：保留客户端发出的 `CMD 0x0029`、服务端同 type 响应的完整 body、对应 `NOTI 0x0020`、响应前后的 UI/角色状态。首要测量是成功响应第 4 个 body 字节的真实值；若不同场景（本人/队友、普通地下城/领地）出现两种值，再各保留一份以命名其模式。这个采样发生在服务端行为具备前置条件且用户允许实机验证之后；当前没有采样，也没有向游戏发送构造响应。

## 倒计时与 `0x00E4` 的边界

死亡 UI 的倒计时另有本地路径：`0138A36C–A371` 从 UI 计时器取已经过毫秒数，以常量 `9999` 相减后换算成秒并绘制 `coin_countdown.img`；`0138AE10` 设置 UI 状态时重置计时器（由并行的死亡 UI 分析确认）。`0x00E4` 的实际动作是删除 HUD 状态图标 `0x60`。配对添加点 `01A858E9–85902` 给这个图标 20 分钟的剩余/总时长；这与死亡 UI 的 10 秒倒计时在数据结构和调用链上不同。它既不启动死亡倒计时，也不提供倒计时秒数；本次服务端未发 `0x00E4` 不能解释死亡倒计时不出现。

本地倒计时到期时，另一路仅在 `[死亡UI+0x54]!=0` 才发送 CMD `0x002A`，而状态设置路径会清零此位。`0x00E4` 的图标删除器不会置位；这条超时发送门仍待单独证实。

## 给服务端方案的直接约束

1. 保留 `0x0029` 请求 `u16 targetActorId` 的已证实布局；响应成功需要区分通用结果前缀与额外的 `u16 targetId + u8 flag`。在确定 `flag` 值前，不能选一个未经观测的默认模式代替协议事实。
2. `0x00E4` 是移除 HUD 状态图标 `0x60`；不应把它用于启动死亡 UI 倒计时，也不应凭 `0x60` 定义“服务端传 96 秒”。
3. 不应让 `0x007B` 承担 A21 客户端死亡回城的协议含义；它的可见发送路径是六项角色统计。


## 2026-09-21 复核修正：共同尾部实际是 P2P 构包

此前把 `[03A5C9B0]` 的虚接口调用描述为 UI/场景事件不准确。lab `Docs/a21-units/unit-020.md` §2.1 与 `unit-004.md` 的构造和虚表证据将此单例识别为出站 packet writer，vtable `035B9264`：+08=022E4BA0 beginPacket，+20=022E5310 writeU8，+24=022E5330 writeU16。后两者本轮直接反汇编确认写入 cursor 并推进 1/2 字节。

0029 成功 handler 的两个分支都构建 category=2、msgId=001E 的包，依次写入本地 actorId、应答 targetId、分支字节，再调用 022E56F0(0,0) 发出。flag==1 写最后字节 1，其他值写 0（布尔化而非无条件复制）。因此此前所谓“UI 接口参数 0/1”实际是对等网络载荷字段；它可能影响队友端的复活效果，需要继续追踪接收方。尚未确认这个字段的最终业务名称或合法默认值，不据此直接实现扣币。原报告中相关 UI/场景事件表述均由此节更正。
