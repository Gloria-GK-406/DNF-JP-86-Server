# T01 普通地下城列表过滤：A21 客户端闭合证据

日期：2026-09-20。范围限于 A21 静态指令与主线程归档的只读运行时读取；没有启动或操作客户端，没有修改游戏、数据库、生产代码或共享协议文档。

## 结论

T01 中漂流洞穴 150、151、152、153、155 没有进入客户端普通选图记录，直接原因是 **A21 客户端按地下城定义中的 quest list 同时查询“当前任务”和“已完成任务”投影；该角色两处都没有这些地下城关联的主线任务**。这不是 WDM 加载失败、等级不足、空 `NOTI 0x0005` 或 `NOTI 0x001B` 前十字节选错 region/mode。

客户端在本次运行中已经正确加载 `driftcave.wdm` 的十个 12 字节条目。当前任务容器只有 2489；已完成任务树只有 101、1016、1776..1782。地下城 150/151/152/153/155 的定义均列出对应漂流洞穴主线任务，且这些任务都不在上述两个投影中，因此过滤函数返回 false，调用者立即跳到下一条 WDM 记录，不创建该地下城的 UI 记录。8007 的 quest list 只有 `-1`，同一函数返回 true，所以它能通过该门。

154 还在 WDM 条目层带任务 1895，走另一道前置判断；本页不把 154 强行归入与其余五图完全相同的分支。运行结果仍表明 154 没有进入普通候选。

## 普通 WDM 构建链

真实 WDM 资源管理器是绝对 VA `0x03A5C934`，运行时 type 为 13，缓存中包含 16 个 `.wdm`。`driftcave.wdm` raw 为 `0x4045D600`。绝对 VA `0x03A5C96C` 的 type 为 40，只有 `advancealtar.stm`；它对应特殊祭坛列表路径，不能作为普通 WDM 证据。

普通选图链为：

```text
RVA 0x02338990  当前选图入口
  当前分支把 world-map key 23 传给 VMP 0x053558DF
RVA 0x02339D06  读取 select+0x44C（本次为 23）
RVA 0x02339D15  [VA 0x03A5C934]->lookup(23, 1)
RVA 0x02339D21  call 0x0231D490(select, driftcave.wdm raw)
RVA 0x0231D594  从 raw+0x68 取得迭代器
                 实际 begin=raw+0x6C, end=raw+0x70, stride=12
```

只读运行时读取到十项：

```text
(150,-1,0) (151,-1,0) (152,-1,0) (153,-1,0) (154,1895,0)
(155,-1,0) (239,1925,1) (239,1927,1) (8007,-1,0) (2011,13505,0)
```

因此普通地下城原始条目没有在加载阶段丢失。

## WDM 条目门

`RVA 0x0231D64B..0x0231D659` 把当前 12 字节 WDM 条目交给 `RVA 0x00A64AC0`；false 才跳过。

`0x00A64AC0` 的直接指令说明第二字段 `-1` 是无 WDM 任务门：

```asm
00A64ACA  mov  ecx,[edi+4]
00A64ACD  cmp  ecx,-1
00A64AD0  je   00A64AE9
...
00A64AE9  pop  edi
00A64AEA  mov  al,1
00A64AEE  ret  4
```

所以 150/151/152/153/155/8007 都通过这一层；154 的第二字段为 1895，单独处理。

## 地下城 quest-list 门

`RVA 0x0231D735..0x0231D748` 对每个 dungeonId 调 `RVA 0x00A62D90`。本次 `select+0x3EC=0`，且 `RVA 0x023BB70` 返回 false，所以调用点的 `BL` 保持 1。若 `0x00A62D90` 返回 false：

```asm
0231D735  mov  ecx,[03A5C9EC]
0231D73B  push edi                 ; dungeonId
0231D73C  call 00A62D90
0231D741  test al,al
0231D743  jne  0231D74E
0231D745  cmp  bl,1
0231D748  je   0231D9BE            ; 跳过本图
...
0231D9CF  mov  esi,[ebp+8]
0231D9D4  jmp  0231D5A0            ; 下一条 WDM 记录
```

`0x00A62D90` 遍历 dungeon definition `+0x168` 容器；实际 begin/end 在 `+0x16C/+0x170`，元素为 `i32 questId`。其三段控制流为：

1. 对每个非 `-1` 的任务，读取 quest raw。若 `raw+0x9C==0` 或 `raw+0xC4!=0`，再由 `0x00A505A0` 查询 `[manager+8, manager+0xC)` 的 12 字节记录。命中即返回 true。运行时该容器只有 quest 2489。
2. 若第一段未命中，再对 `raw+0x9C==0` 的任务查 `manager+0xB0` 树；搜索结果不等于 end 时在 `0x00A62F6A` 返回 true。运行时该树的 9 个 key 为 101、1016、1776..1782，与 DB 及 `NOTI 0x0164` clear bitmap 一致。
3. 若两段均未命中，第三遍把“存在任一 `raw+0x9C==0` 的有效任务”记为 `BL=1`；函数末尾 `test bl; sete al`。所以有常规主线任务但既不在当前任务容器也不在已完成树时返回 false；列表只有 `-1` 时返回 true。

T01 的具体差分：

| Dungeon | definition `+0x168` 的关键任务 | T01 结果 |
| ---: | --- | --- |
| 150 | 1856、1857、1859、1863、1864；另有 circle 14930..14934 | 当前/已完成均不命中；常规任务 `raw+0x9C=0`，返回 false |
| 151 | 1866、1867、1869、1871、1872 | 同上 |
| 152 | 1875、1877、1878、1881、1882 | 同上 |
| 153 | 1885、1887、1889、1890、1891、1892 | 同上 |
| 155 | 2100、2107、2113、2115、2116 | 同上 |
| 8007 | 仅 `-1` | 无有效任务令 `BL` 置 1，返回 true |

circle 任务 14930..14962 的 `raw+0x9C=15`、`raw+0xC4=0`，不会替代上述常规主线任务的命中要求。154 的 definition quest list 也存在，但其 WDM 条目本身先带 1895，故不把它的完整拒绝路径与其余五图合并。

## 对 #101 的含义

当前角色 85 级，但当前任务只有 2489（安徒恩线），已完成任务只有 101、1016、1776..1782。客户端因此把漂流洞穴主线地下城从普通选图构建中剔除。要让 150 等出现，服务端必须向客户端投影与该地下城 quest list 匹配的当前或已完成任务状态；具体应激活哪条任务仍应按 PVF 前置链和服务端领域规则决定，不能从客户端提示反推原版服务端应自动补哪一条。

这也解释了为什么“等级 85”不足以保证列表出现。空 `NOTI 0x0005` 仍只影响逐地下城 clearState/难度上界，不是这道可见性门。`NOTI 0x001B` 的 37 字节正文也没有提供这里所需的任务 ID。

运行时还观察到 8007 通过任务门，但用户界面视觉上为空。当前证据只证明 8007 进入后续候选处理；它为何不形成可见普通按钮属于另一条展示规则，不影响 150..155 被任务门剔除的根因。

## 最小验证

在隔离测试角色上保持等级、位置、WDM、`NOTI 0x0005` 和 `NOTI 0x001B` 不变，只让客户端的当前任务容器或已完成任务树命中 150 的关联主线之一，再重开选图。预期 `0x00A62D90(150)` 改为 true，调用者不再走 `0x0231D748 -> 0x0231D9BE`。验证应使用服务端正常任务投影，不直接改客户端内存。
