## 已闭合的协议关系

| 场景 | 客户端静态证据 | 结论与边界 |
|---|---|---|
| 列表/正文 `NOTI 0x0061` | handler VA `0x01198E70`：先在 `0x01198F3C/4A` 读两个 `u8`，第一字节控制第一类邮件循环，第二字节为 0 时清两份本地集合；第一循环在 `0x01198F74..0x01199577`。随后 `0x01199584/A7` 读两个 `u16`，第二个控制另一类循环至 `0x011996BD`。 | **同帧包含两类记录，且有条件字段/字符串/附件解包；不是一张固定宽度表。** 第一类中有物品、状态与条件读取；第二类有 ID、两段字符串和 `1/2/3` 分类。尚不能逐字段给稳定业务名、总长或完整正文偏移。 |
| 邮件 ID 与附件 ID | 对象 getter `0x01A47330` 取 `+0x14` 的 `u32` 邮件 ID；附件 getter `0x01A47530` 从同一对象 `+0x6C..+0x70` 的 `u32` 数组按 index 取值。 | 客户端**分开维护两种 ID**。不能把附件领取 ID 当邮件 ID。数组元素如何从 `0x0061` 具体字段填充仍需实帧/读跟踪。 |
| 附件领取 `CMD 0x005F` | UI `0x01A4F7F0..0x01A4F85D` 遍历附件索引，调用 `0x01A47530` 取数组元素，传 `0x01A4E6E0..0x01A4E703`。响应 `0x0111B340` 成功路读 `u32`，交 `0x01A4E860`；后者在 `0x01A4E985..0x01A4E994` 用该值与同一附件 ID 数组逐项比较。 | 请求 body 为**一个 `u32` 附件领取 ID**；成功 ACK 的 `u32` 也作为附件 ID **查找键**被客户端消费。一次构包对应数组一项；静态不能推定它自动领取整封邮件。尚无实帧证明服务端实际回显何值。失败路读 `u8` 错误码。 |
| 阅读/状态 `CMD 0x0086` | `0x01A4E800..0x01A4E841` 写 `u32` 邮件 ID + `u16` action。`0x01A4D18B` 发 action `2`；`0x01A4ECBC` 与 `0x01A4F8AF` 发 `0`；`0x01A4FFDA` 发 `3`。响应 `0x0111B3D0` 成功路读 `u32+u16`，交 `0x01A4F490` 按三值更新本地对象/集合。 | `0/2/3` **均经本版客户端校准**，非沿用上游注释。`0` 的成功投影移除邮件，`2` 更新对象状态，`3` 有另一关闭/集合处理分支。中文动作名中“删除/已读/保存”仍需 UI 文案或实机对齐。失败路读 `u8` 错误码。 |
| 邮件移除 `NOTI 0x0062` | `0x01189C60` 先读 `u32` 数量，再逐个读 `u32` ID，调用第一邮件集合的 `0x01A4A910`；其 `0x01A4A922 → 0x01A4A6D0` 遍历集合，以对象 getter `0x01A47330`（对象 `+0x14`）比较 ID。 | 一帧可按计数移除多个**邮件对象键**，键与 `0x0086` 使用的对象 ID 是同一路径，**不是 `0x005F` 的附件 ID 数组元素**。70 在线过期的同 opcode 通知可能携邮包 ID；两版此处是否语义不同需真实 86 帧对照，不能按 opcode 强行合并。 |
| 新邮件提示 `NOTI 0x0063` | `0x01189CC0` 读 `u16`；值 `>0` 时走 `0x01398140` 窗口/提示链，之后传 `0x01A4A680` 更新状态。 | 正数触发提示 UI；上线、在线分别何时发送是服务端/运行时问题，本 handler 无法证明。 |
| 打开 `CMD 0x0060` | 响应 `0x0111B390`：成功路读 `u16` 并调用 `0x01A52190`，失败路读 `u8` 错误码并调用 `0x01A51FF0`。 | 请求构包点与 body 未在普通 `.text` 找到，位于当前静态缺口。不能据响应推断请求字段。 |
| 玩家发信 `CMD 0x005E/0x013B` | 共用响应入口 `0x0111F950`：成功 `0x01A52BA0`，失败读 `u8` 错误码交 `0x01A52C60`。 | 能确认成功/错误反馈分叉；请求体主题、正文、收件人、附件与费用均未闭合。 |
| 收件人查询 `CMD 0x0144` | 旧定位 RVA `0x0163D9C1` 有构包点线索；响应 VA `0x0111B250` 按返回值分支到 UI。 | 查询/校验是发送前独立交互；字符串编码及全部响应字段仍待校准，不采用上游 UTF-8 注释作客户端事实。 |
| 期限显示/可领性 | 对象 `0x01A472F0..0x01A4732D` 在期限非零时，用当前时间与对象基准差换算，再同期限字段比较；领取 UI `0x01A4F7F0..0x01A4F85D` 有有效性判断。`0x0061` 在 `0x01199200..0x01199246` 处理特殊时长值。 | 客户端确实消费时间状态并影响显示/操作。单位、时区、服务器过期清理/退回政策未由静态证实。 |

`0x0061` 的静态外层轮廓是 `u8 countA, u8 resetMode, repeat countA {复杂记录}, u16 groupValue, u16 countB, repeat countB {另一类复杂记录}`。`countA/countB/resetMode/groupValue` 是本文结构名，不是业务字段名。两循环皆零时按代码会读 6 字节，**不等同于本版已有 6 字节实帧**。第一循环有 `0x1E` 上限字符串读取及条件分支；第二循环的 `0x011995D4/E0` 分别读 `0x1E/0x200` 上限字符串，`0x0119963D..0x01199677` 对第二类记录的一个值按 `1/2/3` 分流。这个值的业务含义未确认，也不能和 `0x0086` 的 action 混同。因此旧机器区名义偏移不能直接作 A21 附件编码表。

## 实施前仍需的最小证据

1. **完整 `0x0061` 附件编码**：空箱、纯正文、金币、单物品、多附件各取一份本版解密帧与客户端读取 trace，校准两类记录、附件 ID 数组和正文/期限字段。当前只闭合外层分组与部分分支。
2. **`0x0060` 打开与 `0x005E/0x013B` 发信请求**：普通代码区构包器缺失，需同版真实 C→S 帧及 UI 操作时间点；保护区推测不能替代字段表。
3. **错误与通知细节**：`0x005F/0x0086/0x0060/0x005E/0x013B/0x0144` 的错误码→UI 文案、背包满/金币上限反馈、上线/在线 `0x0063` 顺序要实测。
4. **过期规则**：客户端倒计时/有效性分支不能决定服务端过期删除、退回或持久化政策，待设计与实机验证。

本轮不改 `protocol/` 机器区，也不将任何结论升级为 `ClientVerified`。
