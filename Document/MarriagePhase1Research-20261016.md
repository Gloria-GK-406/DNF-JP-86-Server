# 婚姻与情侣系统：一期信息探查报告

日期：2026-10-16。范围：资料、客户端静态协议、参考实现与当前服务端接缝调查；本轮不实施或部署功能。

## 结论

**可以进入一期预设计，但不能把现有固定回放接上就称为婚姻实现。** 当前 PVF 同时具备婚前任务、婚礼规则、礼包、戒指与婚房资源；服务端还没有真实关系、求婚流程或婚礼结算。A21 有相应收发代码，但原生入口、完整交互时序和若干字段语义仍需双端实机取证。

本轮需要更正三项旧认识：

1. **结婚任务 `20737/20738` 存在。** 正确索引是 `n_quest/quest.lst`。问题在专用入口、双人进度和资格校验，不在资源缺失。
2. **NOTI `0x03D8` 在 A21 按婚房结构读取。** 历史上的 204 个零只兼容了空态；不能证明同长度的非空旧彩票数据也是合法 A21 消息。
3. **婚姻 C2S 的 `21/22/23` 是含 14 字节帧头的总长。** 求婚、答复、进入仪式实际正文分别为 `7/8/9` 字节；旧机器记录把帧头计入正文，不能直接用来写 decoder。

建议一期围绕“合法取得资格 → 求婚与答复 → 婚礼完成 → 双方持久配偶关系 → 重登恢复”验收。婚房家具、共享仓库、树、胶囊、完整离婚与戒指升级可分后续阶段；一期需要哪些最低戒指/婚房摘要，按原生 UI 的必要读值决定。

## 3. 当前任务接缝的两个实质缺口

**[CurrentImplementation / Confirmed]** Wedding grade 有意被普通可接任务列表排除。另一方面，通用 `0x001F` 接任务的完整路径 `AcceptQuestHandler → AcceptQuestCommandHandler → QuestLog.AcceptAsync` 没有统一检查等级、职业和前置；Wedding 走普通接取分支。

因此手工对 `20737/20738` 发请求能够绕过其内容资格。原生婚姻 UI 是否这样发请求尚未确认。这是服务端受理校验缺口，不能靠客户端不显示任务来防止。

**[CurrentImplementation / Confirmed]** `20737` 的 subtype `22` 不符合当前 `DungeonClearRequirement` 的 subtype `6` 投影规则；三参数也不足 trigger 打包所用的四字段 stride，初始值会退回默认 `1`。现有通用任务能力不能直接完成“二人五次普通图”的婚前闭环。

**[Proposal]** 一期需要婚姻资格服务和搭档绑定的试炼进度，并让合法入口与通用接取入口采用一致的门控。不能预先标记任务完成来代替实现。

## 4. 协议发现与 `0x03D8` 冲突

### 婚姻收发结构

**[ClientStatic / Confirmed]** 三个构包器都从总帧 offset 14 开始写业务字段：

| C2S | 总帧 / 正文长度 | 正文结构 | 对应 CMD 回包固定消费 |
|---|---|---|---:|
| `0x03F0` 求婚相关请求 | 21 / 7 字节 | `u32 id + u8 action + 2B opaque` | 11 字节 |
| `0x03F1` 答复相关请求 | 22 / 8 字节 | `u32 id + u8 action + 2B opaque + u8 outcome` | 12 字节 |
| `0x03F7` 进入仪式 | 23 / 9 字节 | `u32 + u32 + u8` | 4 字节 |

此处 ID 的业务身份是高可信候选；部分路径把对象返回的 `u16` 零扩展为 `u32`，不能未经验证当成数据库 CharacterId。action 已见 `1/2/5/6/7`，outcome 已见 `0/1/2`；接受与拒绝的数值映射仍未知。没有 14 字节名字区，14 字节属于帧头。当前服务端 `GameClientFrameRequestInfo.HeaderLength` 也为 14。

NOTI `0x03CD/03CE/03D0/03D4/03D7` 分别固定消费 `11/12/15/79/68` 字节。精确 offset、分支、RVA 和剩余未知以 [A21 专项报告](outputs/marriage-research-20261016/a21/a21.md) 为准。

固定长度和 action 分支不足以证明完整求婚、拒绝、接受、仪式开始/完成时序。后续必须捕获双端正常操作，确认错误码和 UI 状态解除行为。

### 婚房消息的具体风险

**[ClientStatic / Confirmed]** NOTI `0x03D8` 的 A21 handler 消费：

```text
u32 count
count × (u16 + u32)
13-byte tail
总读取长度 = 17 + 6 × count
```

尾部按三个 `u32` 和一个单字节读取；其业务含义尚未全部闭合。上游 113 字节婚房常量恰好符合 `count=16` 的长度。

**[CurrentImplementation / Confirmed]** 当前仓仍把该 opcode 实现为 204 字节旧彩票进度，选角时从账号进度构造。空体全零等价于 `count=0`：客户端读 17 字节并容忍剩余 187 字节，因此历史空态能够工作。非空旧彩票体首值 `2` 则会被当成两个婚房条目，后续字段错位。

当前生产构造点在选角/重登；普通开罐流程使用 CMD `0x001B`、库存同步及 premium `0x036F`，没有在开罐后构造此 NOTI。**本轮没有查询在线数据库确认是否存在非空旧彩票进度，也没有实机复现它的界面后果。** 此处结论是已定位的协议语义冲突和受影响路径。

**[Proposal / High]** 婚姻实施前应把 A21 `0x03D8` 的所有权交给婚房投影，保留既有空态兼容验收，停止发送非空旧彩票形状。不得猜一个新 opcode 把旧彩票代码搬过去。

## 5. 参考实现能提供什么

**[UpstreamReference / Confirmed]** 本次所列 S4A21 checkout 的婚姻内容是常量回放：15 字节 `WEDDING_INFO`、31 个零的 `WEDDING_CHARAC`、113 字节 `COUPLE_ROOM`，不读取角色关系。它还在部分库存/进出图刷新中重放这些常量。扫描范围内未找到求婚、婚礼结算、配偶持久化或恢复流程。

旧单体在本地所列 checkout 中也未定位到真实婚姻业务，仅有 opcode 和商品相关命中；未刷新其远端源码。

**[70Reference / High]** 对指定 70 二进制的 119,333 个函数符号条目与可打印 ASCII 做限定英文词表扫描，没有婚姻相关命中。没有做匿名函数控制流恢复、非 ASCII 或其他地区版本调查，所以只能说本次没有找到可用实现，不能断言 70 完全不存在婚姻。

## 6. 服务端可复用与必须新增的部分

| 可复用能力 | 用法或边界 |
|---|---|
| `IMultiAccountCommand` 与排序账号锁 | 双方变更沿现有 account ID 升序锁定，无需另造锁 |
| 现有 SQLite 命令事务 | 关系、费用、奖励幂等记录在同一事务落地 |
| exact selected session / generation | 拒绝旧连接和角色切换后的过期操作 |
| durable domain event | 提交后通知与可恢复投影 |
| 物品交付、库存 seeking、邮件 | 奖励和婚前材料复用；婚姻来源唯一键需要新增 |

**需要额外处理的共享路径：** `EffectOperationContext.Record` 约束 effect owner 必须与当前请求捕获的主收件人具有相同 session、account 和 character。双账号锁不自动解除这个约束。双人扣费与奖励不能简单给双方各建一个 effect context；应明确结算所有者、原子资产变化、双方提交后投影及主请求重放的边界，再验证专门编排。

**[Proposal]** 新增持久关系聚合、参与者唯一约束、求婚/答复/婚礼状态机、奖励账本、协议适配和重登摘要。领域接口进入 Abstractions，SQLite 实现进入 Persistence，PVF 内容源进入 Infrastructure，协议适配进入 Protocol；Application 不引用 Infrastructure/Persistence。

候选状态为 `Pending → AcceptedAwaitingCeremony → Completed`，另有拒绝、取消、过期终态。只有 `Completed` 对下游暴露为配偶。具体试炼在求婚前后哪个阶段绑定，需按原生 UI 取证决定，不能把候选状态机当官方流程。

关系应有角色参与者唯一约束、版本条件更新和操作幂等键。事务失败不得留下单边配偶、单边扣费或只给一方奖励；重复请求不得重复结算。

## 7. 建议一期实施顺序与验收

这是待审预设计输入，不是本轮实现结果。

1. **补原生入口证据。** 追踪求婚 UI 的进入方式，采集双方请求/通知、接受与拒绝、任务接取、仪式选择和重登。同步校准 `0x03D8` 空态投影。
2. **完成资格与婚前试炼。** 最低等级、已有关系、专用任务受理和搭档绑定；五次普通图进度及心意娃娃 seeking；拒绝通过通用任务 ID 绕过。
3. **实现真实关系与交互。** 求婚、答复、取消/过期、双方会话校验、持久化恢复；双方在线和每角色仅一个 pending 可作为一期保守策略，须在设计中明确为本服选择。
4. **接婚礼结算。** 根据协议落实档次、费用、票据与奖励，原子提交；教堂/仪式完成必须有可见、可重试的实际流程。
5. **提供配偶只读查询。** 爱之摩伽陀按双方角色 ID 和同一 Completed 关系校验夫妻资格，另行执行副本自己的等级、门票和队伍条件。

最低验收矩阵：

| 场景 | 应验证的结果 |
|---|---|
| 正常双端求婚、拒绝、接受、婚礼 | 两边 UI 可完成，错误/拒绝也能解除等待 |
| 等级不足、已婚、错误对象、绕过任务 ID | 服务端明确拒绝，不只依赖 UI 隐藏 |
| 二人普通图试炼 | 五次累计正确；换搭档、非普通图、非二人队不得误计 |
| 重复答复、重复完成、双方同时操作 | 关系唯一，不重复扣费或发奖 |
| 结算任一步失败、资产不足 | 双方关系和资产原子回滚 |
| 掉线、切角色、重登、重启服务 | 状态可恢复，旧会话不能完成新结算 |
| 选角/回城/开罐回归 | 不误发非空旧彩票婚房包，库存和普通开罐维持正确 |
