## 已闭合的状态与饱食规则

| 状态 | 含义 | 证据 |
|---|---|---|
| 1 | 穿戴且战斗；按秒耗饱食 | `CCreature::Equip` `0x08337330-0x0833735f` 依据 `CUser::is_fighting` 设 1；`CStomach::GetStomachValue` `0x08336d43-0x08336d95` |
| 2 | 卸下；在线按秒恢复饱食 | `CCreature::Reset` `0x083370d7`、`Dismantle` `0x08337382-0x083373a2`、`LoadCreatureItem` `0x08338708-0x0833871d` |
| 3 | 穿戴且非战斗；在线按秒恢复饱食 | `Equip` `0x08337361-0x08337376`；`TurnStomach(false)` `0x0833c2e0-0x0833c313` |

`CCreatureMgr::Equip/Dismantle` `0x083392f6-0x083393a1` 维护当前宠物指针；`EquipCreatureItem` `0x083393a2-0x083393fa` 先卸旧宠、再穿新宠；`SwapCreature` `0x08339574-0x083395ca` 只有角色装备槽 `0x16` 与其它位置交换时才走这条路径。`CParty::dungeon_start` `0x085a1f0b` 调 `TurnStomach(true)`；`CUser::set_state` `0x0867edf2-0x0867ee1a` 根据 `is_fighting` 调 `TurnStomach`。此处是状态触发，不需每秒把数据库写一遍。

`CStomach` 初始锚点是当前秒，值为 100（`0x08336cd8-0x08336cf7`）。`GetStomachValue` `0x08336cfc-0x08336ded` 先判断是否有饱食机制：`CCreature+0x4c != 1` 直接返回 100；否则取 `now-anchor`，状态 1 作 `value = max(0, value - elapsedSeconds/60)`，状态 2/3 作 `value = min(100, value + elapsedSeconds/360)`，随后把锚点设为 `now`。常量由 `.rodata` `0x08c2f450=100.0f`、`0x08c2f454=-60.0f`、`0x08c2f458=360.0f` 及 x87 除法 `0x08336d64-0x08336da8` 共同证明；这是浮点累计，向客户端/持久层输出时截断为整数（`CCreature::GetStomach` `0x0833851a-0x08338530`、`SaveCreatureItem` `0x08338822-0x0833883e`）。`CStomach::IncrementValue` `0x08336e66-0x08336ead` 只做加值及 100 上限；`CCreature::UseFeed` `0x083373d4-0x08337493` 对有饱食机制宠物加 `30.0f`，若死亡先广播复活，再发送饱食状态。

`CCreature::SetState` `0x08337163-0x08337324` 先结算旧状态再切新状态。进入状态 1，若有饱食机制，按 `trunc(remainingStomach*60)` 注册 `TimerQueue::InsertTimer` 消息 `0x5c`（`0x083371b0-0x08337224`；常量 `0x08c2f460=60.0` double）。`TimerCreature::dispatch_sig` `0x08635e96-0x08635f4e` 验证在线 user、unique id 与角色号后调用 `CCreatureMgr::CheckDiedCreature`；后者到 `CCreature::IsDieCreature` 按当前时间结算饱食，归零时 `Die` 广播。未见周期性一秒 tick。进入状态 3，若旧状态不同且有饱食机制、当前胃值已空，`SetState` `0x0833723d-0x083372e5` 广播复活，把胃值设为 **1.0f**，发状态通知；这是入城状态切换的保底复活，并非自动消耗饲料。

**离线边界**：`SaveCreatureItem` `0x0833881d-0x0833883e` 结算并把整数饱食写入详情 `+0x18`；`LoadCreatureItem` `0x08338619-0x08338632` 恢复该整数，然后 `CStomach::Resume` `0x08338703` 把锚点重设为当前秒，再 `SetState(2)`。所以 70 服不会把离线时长补计为恢复或消耗。细节记录只有整数，浮点余数跨登录丢失。`CStomach::IsSaveStomach` `0x08336dee-0x08336e46` 在状态 1 值为 0、状态 2/3 值为 100 时认为无需再保存。

**自动饲料与装备消耗率边界**：全 `.text` 直接调用检索见 `xrefs-stomach.asm.txt`。`GetStomachValue` 只有状态变更、普通经验、死亡检查、状态读取与保存调用，参数无装备消耗率。`CCreatureMgr::UseFeed` 的直接调用点仅 `CCreatureMgr::UseItem` `0x0833a5d3`，根据 `Inven_Item` 的 item ID `0x18` 分流。因此此 ELF **未证实服务端自动用饲料**；若自动喂食存在，可能是客户端驱动，需 JP86 实帧/静态客户端另证。也不能把装备经验百分比当作饱食消耗率。

## 经验与等级

`CUser::FatigueUp(int)` `0x08655c67-0x08655d94` 将入参 0 改为 1，再**覆盖写** `CUser+0x8e08c`。全 `.text` 对该偏移的读写见 `exp-accumulator-xrefs.asm.txt`：唯一写者就是 `FatigueUp`，所以这不是累计角色经验或累计击杀经验。直接调用点见 `fatigue-xrefs.asm.txt`：普通地下城 `CParty::dungeon_start` `0x085a1b53/0x085a1b9b`（赛事图采用脚本疲劳值，其余传 0→1）、换图 `CParty::changePartyMemberInfo` `0x085a8e07`、特殊图 `CBattle_Field::kill_monster` `0x0830c08e`。后两处需带控制流条件理解，不能把每次换图或每次击杀当成无条件给经验。

`CParty::prepare_dungeon_clear` `0x085aa3f6-0x085aa54d` 在 **grid clear**、有效玩家、`+0x8e08c > 0` 且当前穿戴宠物非成长型时，取该疲劳值调用 `CCreatureMgr::GainExp`，随后清零。紧接着 `0x085aa59d-0x085aa5c8` 才判断最终地下城通关，所以该经验触发是**每次符合条件的清房**，不限最终通关。`WarRoom::HandleMonsterKill` `0x086be717-0x086be7d4` 在 grid clear 处也有同形调用。普通地下城应以最近一次 `FatigueUp` 的值为宠物经验基础；不应把角色累计疲劳或怪物经验拿来替代。

`CCreatureMgr::GainExp` `0x08339b06-0x08339b6c` 仅转给当前穿戴宠物；`CCreature::GainExp` `0x083378fc-0x083379be` 要求脚本存在、未达多选进化等级或脚本最高等级，然后根据脚本是否成长宠物选择两条路径。普通宠物 `GainExpCreature` `0x08337bbc-0x08337d51` 要求饱食整数大于 0，才 `CalculateExp`。`CalculateExp` `0x083377b6-0x083378a9` 对宠物装备槽 `0x17/0x18/0x19` 各取 `CArtifact::GetExperienceAmount`，后者从装备 PVF `CEquipItem::get_experience_amount` 读取 float（`0x08336fc8-0x08337010`），并受装备最低宠物等级限制（`GetAddExp` `0x08337724-0x083377b4`）。计算式为 `granted = fatigueBase + trunc(fatigueBase * (slot23Pct + slot24Pct + slot25Pct) / 100)`；累加 `CCreature+0x30` 经验，调用 `CDataManager::get_creature_exp_level(totalExp)` 求等级，再按宠物脚本 `maxLevel` 封顶，并通知经验/等级。成长宠物是另一套基于指定物品和成长次数的逻辑（`0x083379c0-0x08337bbb`），不能沿用此式。

`CDataManager::get_creature_level_exp` `0x0836053c-0x08360560` 从 `CreatureScript::ExpTable_` 读取阈值（level 2 对应 index 0），`get_creature_exp_level` `0x08360562-0x083605a6` 顺序比较阈值；表位于运行时 BSS `0x094fefa0`，不是这份 ELF 内的静态数表。`GetExpLevel` `0x083374d2-0x0833756c` 对普通宠物使用这个表并受脚本最高等级约束。加载链：`CDataManager::init` 调 `initCreatureScript`，传入 `Creature/`、`Creature.lst`、`ExpTable.tbl`；`initCreatureScript` `0x08a35d37-0x08a35e07` 打开 RDAR `Creature/ExpTable.tbl`，循环 `ScanInt` **99 次**写入 BSS `0x094fefa0`。这证明数据来自脚本表，但这份 ELF 没有该表的实际 99 个值。

**当前 A21 静态档案（ClientStatic，非 70 表）**：`E:\Project\DNF\DNFClient-A21-debug\Script.pvf` 中路径是 `creature/ExpTable.tbl`，实读 55 个递增整数，首三个 `2,5,9`，末值 `5579`；`creature/creature.lst` 将 creature ID 映射到 `.cre`，各定义 `[max level]` 分别给上限（例如 Faras=50、Bobo=20）。证据为 `pvf-list-sample.txt`、`pvf-creature-sample.txt`，并由真实档案自动化测试读取。当前实现按表加定义上限计算，**不硬编码 max50，也不把 A21 表伪称为 70 数值**。

宠物装备 PVF 的 `[creature experience amount rate]` 是三槽经验百分比，不是胃消耗率；`[creature minimum level]` 限制该加成何时有效。A21 `equipment/equipment.lst` 下 850 条 `creature/` 装备中，有 3 条声明该加成：`63500`、`64000`、`64500`，各为 `10%`；`63500` 的最低宠物等级为 `10`。扫描与原始 token 可由同目录 `pvf-inspect --scan-creatures` 复现。

## 孵化、改名与进化（已确认框架）

孵化请求 `Dispatcher_HatchCreature::read/process` `0x081cd3ae-0x081cd561` 读取 `itemSpace:u8`、`slot:i16`，通过库存物品 `add_info` 找到宠物对象，再转 `CCreatureMgr::Hatch`。后者 `0x08339fa0-0x0833a10f` 要求登记物是蛋（type 0），经 `CEgg::Hatch` `0x0833912a-0x08339195` 读取蛋装备 `get_hatch_item_id`（A21 `[output index]`）求目标 item ID。`CCreatureItem::Set` `0x0833ef20-0x0833ef97` 只复制旧蛋 item ID/type/UID/槽号与基础标志；新 `CCreature` 的 `Reset` `0x083370b0-0x08337158` 初始 level1、exp0、名字零，再由 `Hatch` 设置新 item ID 与饱食 **100**。`0x0833a203-0x0833a3fa` 从 map 注销旧蛋并登记新宠，替换背包格物品 ID，发 DB 孵化消息、响应与物品列表。目标装备的有效期按其 PVF `getUsablePeriod/getExpirationDate` 重算（`0x0833a135-0x0833a1fe`），无期限时为零。失败码与超时物品分支见 `manager.asm.txt` 对应地址；这不是另建一个独立于物品的宠物 UID。

改名 `CCreatureMgr::RenameCreature` `0x08339b6e-0x08339db9` 要求有已穿戴宠物，调用 `CInventory::use_item` 消耗改名道具后写宠物名（`CCreature::RenameCreature` `0x083373aa-0x083373d3` 固定 12 字节字段），广播名字通知并向 DB 发 `RenameCreatureItem`，再发命令响应。

普通自动进化：`CCreature::GainExpCreature` `0x08337cf7-0x08337d32` 升级后调用 `IsAbleEvolute`；后者 `0x083380fc-0x083381e9` 要求脚本 `[evolution level]` 非零且当前等级达到门槛；若有 `[evolution quest]`，只发送任务信息并返回 false，故任务型不能仅凭等级自动变化。`CCreature::Evolute` `0x083381ea-0x08338317` 取脚本 `[evolution creature id]`，解析目标脚本的 item ID，对**同一个宠物对象** `SetItemId`，原 UID/经验/等级/饱食/名字不因这个动作重置；然后修改穿戴槽物品模板，发 DB/通知。A21 Faras `.cre` 是 `evolution level=20`、目标 creature2，当前 63000 `.equ` `[output index]=63001`，目标 63001 `.equ` 对应 creature2；当前实现只在该输出目标与 `.cre` 目标交叉校验一致时自动进化。多选 `SelectEvolute`、物品与事件进化有独立入口与门槛，不能与普通自动进化混用。

70 进化通知 `CPacketRespondent::MakeNotipacketEvoluteCreature` `0x08340842-0x083408b4`：`put_header(0,0x6a)` 后，`put_byte(targetCreatureId)`，再 `put_short(CUser::get_unique_id())`。`Evolute` `0x083383e2-0x083383ef` 把目标脚本 creature ID 原样传入；故 70 的首字段为 **u8 新 creature ID**、第二字段为 **u16 用户 unique ID**，不是装备 item ID。此处只证明 70，A21 客户端若读两字节首字段则属于版本差异，不能混作同一线格式。反汇编见 `evolve-notify.asm.txt`。

## 实施顺序与未决

1. 在宠物详情上建立状态、整数持久饱食与在线时间锚点；穿戴/卸下、入图/出图和登录恢复共用一个 `SetState`。死亡 timer 可用同一角色调度器在预估归零时触发，回调必须再按时间重算并校验角色会话身份。
2. 让疲劳结算与通关触发普通宠物经验；配置化阈值表和脚本最高等级，装备三槽百分比与等级门槛；成长宠物独立建模。经验与背包详情保存处于同一事务。
3. 接入蛋到宠物的物品状态变更、改名道具消费、进化变形，再补技能冷却/解锁的脚本规则与消息。

未决：`FatigueUp` 在换图与特殊图击杀处的完整条件、70 RDAR 的实际经验表数值；多选、任务、物品与事件进化的完整动作与 A21 请求；宠物技能脚本字段/触发；JP86 客户端对自动喂食、状态通知的真实需求。这些保持 `70Reference`、`ClientStatic` 或 `Unknown`，不得提升为 `ClientVerified`。

## 当前规则模块的接线契约

`Server/src/Dfo.Server.Abstractions/Creatures/ICreatureRuleSource.cs` 中 `GetAsync(itemTemplateId, ct)` 返回装备模板对应的 `CreatureRule`：`CreatureId` 是 `.cre` ID，`MaxLevel` 是 `[max level]`，`ExperienceThresholds` 是整张 `creature/ExpTable.tbl`，`HungerEnabled` 来自 70 已证 `IsItemGrowCreature` 判定需要的 `.cre` 字段；路径缺失时为 null（未知）。A21 `.cre` 有 29 条含选择成长字段，例如 creature 122 / 装备 63158 的 `[selective grow creature]`、`[using exp item]=1`、A/B 成长物品索引使 `HungerEnabled=false`。普通 Faras 63000 为 true。`Evolutions` 复用现有 `ICreatureDefinitionSource` 投影，蛋 `IsEgg` 由装备 `[sub type]=1`、`HatchOutputTemplateId` 由 `[output index]` 得出（A21 egg 63022→63023）。

`GetArtifactExperienceAsync(itemTemplateId, ct)` 给出装备 `[creature minimum level]` 和 `[creature experience amount rate]`。调用方按当前三个已穿戴神器槽和宠物等级筛选后，将有效百分比传入 `CreatureRules.CalculateExperienceGain(fatigueCost, percents)`。纯算法 `CreatureRules.AdvanceStomach(current, elapsed, combat, hungerEnabled)`、`Feed(current,30)`、`GainExperience(rule,currentExp,gain)` 不承担状态切换、离线补时、道具消费、事务与网络通知。成长型宠物的物品经验另走一套规则，不能调用普通经验公式。

`ICreatureTransformationDomainService` 只提供事务内 `HatchAsync(session, eggSlot, ct)` 与 `EvolveAsync(session, ct)`。前者仅修改已验证的背包蛋，同 UID 输出、100 饱食与初始经验；后者仅对当前穿戴、单目标、无任务、等级达到且装备输出与目标 `.cre` 一致的普通自动进化。方法失败返回 null 且不写物品；外层用例负责请求解析、响应/投影与提交事务。此有限实现有意不宣称覆盖 70 的多选、任务、物品和事件进化。
