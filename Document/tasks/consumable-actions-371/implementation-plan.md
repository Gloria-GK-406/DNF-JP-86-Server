# #371 实现方案

本方案以[调查](investigation.md)、[79行矩阵](action-matrix.md)和[证据快照](evidence/README.md)为输入。它是建议的实施方案，尚未修改玩法代码或获得实机通过结论。基线、范围与统计口径见[入口](README.md)。

## 1. 预期结果与范围

用户右键使用范围内物品后，应按真实A21路径获得正确的界面或效果。服务端负责的效果与资产变更原子提交，客户端得到可理解的反馈。纯打开界面的动作不扣物品。真正执行消费时扣使用物品1个，额外费用由该操作自己的规则提供。`[need material]` 属于商店定价。失败或取消不产生消费及效果。

每个action type最终必须有明确结论：支持并通过实机验收，或有充分A21不支持证据并明确拒绝。对于尚缺玩法/协议证据的条目，保持“未完成”，不能通过改成拒绝就算修复。

本轮不把#372/#373/#374的全部内容并入。共享领域修正可以复用，但在矩阵里保留归属和交叉回归；发现路径属于专用CMD时先修正归属，避免做两套实现。

## 2. P0：先完成路径与语义取证

### 2.1 取证产物

为每个矩阵身份A001～A079建立一条记录，至少包含：

`action type → 物品ID/模板路径/参数族 → 客户端使用分支 → 最终CMD/长度/参数 → 成功/失败读取 → 业务效果及消费时点 → 来源/置信度`。

动作映射表写入`protocol/game/client-to-server/0x0204.md`人工区；如果最终走其他协议，则更新该协议页并从0204页/矩阵引用。每个编号、布局与置信度对应到可复核证据，不把本任务的候选表直接升级为Confirmed。

### 2.2 静态与运行期工作顺序

1. 使用ClientStore当前登记的b1，核对本次镜像SHA和ImageBase，所有地址区分VA/RVA。从物品实例`+0x528`的来源反追定义字段/解析函数，识别完整字符串或token到枚举的转换，而非只收集散落的整数比较。
2. 检查0204已列出的17个构包点：归并真正相同的请求形状，区分通用确认、目标装备/宠物、活动目标和客户端本地UI。输入宽度按指令/实帧定，不套用第三方或70的结构。
3. 为有目标的道具确认“打开选择框”和“点击确定”分别发什么；记录取消、空目标、错误目标时是否发包。确认槽位是wire容器还是业务容器，不能把快捷栏或宠物槽偏移当数据库槽号。
4. 若字符串转换链进入静态盲区，使用独立trace/debug客户端，在PVF读取/动作字段赋值处做运行期跟踪。调试插件先在ClientHack构建并登记debug组件，再由ClientStore生成客户端；不手改现有客户端dll/exe。
5. 对每种动作先点至少一个真实代表物品，再按不同参数、目标容器、材料/奖励语义补代表。每次操作关联客户端send/recv、服务端收发日志、原始body、调用栈、UI截图与可见效果；原始日志归档进ClientEvidence，协议页引用归档身份。
6. 没有0204请求时继续检查是否本地UI、其他CMD、受等级/地点/活动限制或缺确认步骤。不能把“未发包”直接记作“不支持”。

### 2.3 先补可观测性

在0204解码/CMD具名拒绝点记录：请求相关ID、连接/精确会话代数、角色/账号、seq/入站序号、完整长度、槽/容器、权威物品ID（有则记录）、请求动作、已知语义、目标参数和拒绝原因。包不合法或无会话时物品ID明确为未知，不伪造0号物品。

槽位解析只通过既有领域入口，并在实际写入事务中重新核验；不能为了日志另开数据库、绕过请求权限或在薄handler加入业务。对不同动作按已证失败分支返回；客户端提示码需静态读取/实测闭合，不能将所有错误替换为猜测码。通用文字提示只在现有已证通知路径适用时使用，不能用提示掩盖错误ACK或卡住的选择框。

**P0放行条件：** 一个动作的请求/目标/回复形状、PVF参数解释、材料/奖励、失败/取消消费时点已足以定义可验证预期，才进入该动作实现。全表仍可含Unknown，但Unknown不进入生效分支，不算完成。

## 3. P1：协议入口与领域接线

### 3.1 职责设计

| 层/owner | 负责 | 约束 |
|---|---|---|
| Protocol 0204切片 | 精确decode、A21动作号到语义操作的有限映射、参数范围、ACK/提示编码、CMD流程与出站顺序 | 不读取PVF或直接查行表；不把业务规则塞在decoder/handler |
| 既有领域owner | 读取权威源/目标、校验语义、准备效果、提交状态、返回具名结果 | 按任务/宠物/塔/装备/余额等真实责任复用；不认识协议字节或socket |
| 规则服务 | 物品可用性、PVF动作兼容、参数、目标类型、保留字段、奖励与限制 | 只依赖规则输入和内容源；不复制另一owner的相同算法 |
| Infrastructure内容源 | 读取类型化动作定义与相关表、标记不支持的形状 | 不把所有action都做成不校验的int数组供CMD直接解释 |
| Persistence | 新owner确需的新事实、CAS、迁移 | 不新增平行余额、第二份塔进度或客户端镜像真源 |
| 通知投影/发件箱 | 提交后的权威库存、对应领域状态、外观及必要旁观者消息 | 不在写事务中发包，不由领域查询他人连接 |

现有`QuestClearCoupon`实际上承载多类0204动作，命名具有误导性。可在本切片增量推广为`UseStackableAction`，保留线上opcode和既有行为；是否同步重命名CLR/目录成员以最小必要改动为准，不重写网络层。

路由使用已证动作号和具体请求变体，领域层再次核实当前槽位PVF声明，防止伪造动作、换槽或错目标。取消以“只认几个物品ID”的能力判定后，也不能接受任意同标签但参数不可读的模板。对于客户端明确查固定ID的既有入口，保留其兼容能力并让新增动作入口复用领域效果。

各族由所属领域的具名用例承接；不为79行各建一套机制，也不创建一个持有所有玩法、内容源和存储的万能动作服务。单一0204CMD只组织已实现的有限业务分支，handler保持一次typed dispatch。不能用service locator、可空依赖、执行器内再派发CMD或跨切片调用旧handler拼装实现。

### 3.2 事务、资产与重放

1. 在当前CMD中取得原精确会话与显式effect request；每个动作声明真实角色/账号和目标保护参与者。
2. 在`ICommandWorkUnits.WriteResultAsync`主结算内重新读取源/目标、持有量、期限、锁、等级、地点和当前玩法事实；规则产出完整计划后才写。
3. 消耗物品、额外材料、状态变化、必要奖品/计数以及可靠领域事实同一事务。目标失效、材料不足、上限或任何写入失败使整笔回滚；随机结果只为这一次结算生成并以已提交事实恢复，不能重放时重抽。
4. 库存通过现有物品/效果能力变更；宠物/装备尽量保留UID，由规则决定可保留字段。既有内存参与者跟随事务提交/回滚，不另作影子快照靠事后同步。
5. 成功提交后登记经取证确认的ACK、绝对库存/清槽及领域投影。每个动作的顺序需由实际读取路径/样本支撑，不能从任务券顺序推定全部动作相同。
6. 更新重放足迹与最小投影需求：除库存外，按实际效果包括任务、宠物、外观、账号余额、次数或场景位置。重复帧不得再扣券、重复发奖、重复推进层数或重复传送。
7. 网络断开或投影失败不倒推为数据库回滚；按既有交付/关闭机制收尾，重登从事实恢复。事务结果不确定按既有隔离策略处理，不直接重试再消费。

## 4. P2：先交付已有领域可承接的动作

本节对应矩阵B1，8种、79个模板。以下顺序用于减少依赖，不代表业务优先级或无需取证。

1. **幸运星与光环栏。** 两条最直接的复用路径：账号幸运星余额、光环栏开关已有事实与操作。0204与原002C/0357共用判定、上限和扣量；补齐相应动作的失败界面/重复点击收尾。
2. **有限任务券扩展。** `[any quest clear]`与剩余`[quest clear]`分族设计选择规则。读取指定任务集合、职业、等级和奖励，复用原子清理和任务投影。保留10006007已有用户确认的无奖主线策略，类型以对应券的证据为准。
3. **修理类。** 核实是真正修理还是打开修理UI，再复用耐久owner与修理规划。全部已满耐久、不适用装备、锁/到期、金币或额外材料的拒绝/消费口径先确定。
4. **异界追加次数。** 在异界owner中增加明确的额外次数事实和当日读数；现有入场扣次/界面必须消费同一事实。不能给通用quota读接口加任意setter绕过owner。
5. **随机疲劳药。** 证明int data的权重语法后复用疲劳和道具使用限制。疲劳低于106的条件、恢复上限、随机抽取与消耗一瓶秘药统一事务。第三方硬编码概率不能代替PVF。

每项完成后独立自动验证与实机验证，可形成小批交付；#371的总体状态仍按79行矩阵保持未完成项。

## 5. P3：领域扩展

本节对应B2，23种、359个模板；具体逐项效果与取证门槛见矩阵，不将整组一刀切实现。

- **觉醒/成就券：** 区分任务完成标记、职业成长、技能授予、称号簿和奖励；接回原owner，不能只清flag。单任务经验券先解决R类的最终选择协议再归入任务实现。
- **宠物：** 经验和既有进化复用实例能力；任意模板转换与随机变化扩展宠物实例规则，明确名字/等级/经验/技能/饱食/期限/UID保留矩阵。跨界石先核专用CMD，不能绕账号容器约束。
- **绝望之塔：** 给真实owner增加券操作，区分入场许可、直达和速通结算。不能伪造怪物死亡/RunId调用真实副本结算，或只改HighestClearedFloor而遗漏奖励与次数。
- **装备期限/转换：** 期限、模板变化、当前强化/锻造/附魔/词条/封装/徽章/锁字段分别定保留规则；复用统一永久/到期表达，不以某个未来日期冒充永久。异界气息清除先验证原专用路径，不重复建规则。
- **技能冷却/场景对象：** 先证明客户端与服务端分别拥有的状态；若效果由客户端算，明确服务端校验与消费的责任，实测真正冷却或对象效果，不能只看道具消失。
- **故事簿/伴侣传送/装扮转换/符咒：** 依原任务、婚姻、城镇放置、物品身份owner扩展。涉及其他玩家可见状态时走既有人群投影；跨区域、婚房或副本目标先校验准入。

## 6. P4：玩法基础与不明路径

B3有39种、322个模板；R有9种、59个模板。保持全量范围的前提下，不能承诺这些仅补一个动作分支即可实现。

- **B3先补真实玩法。** 账号级地下城额度、自动扫荡、攻坚、奖励资格、公会系统、各独立活动等，应先有事实owner、实际消费方、持久化/生命周期和投影，然后接道具入口。以计数或成功ACK代替玩法不满足验收。
- **R逐项作路径裁定。** 跨界、净化等若已证走专用CMD，则明确移交#372/#373或本仓既有切片；指南UI按只读方式验收；占位任务/转换类先恢复规则。保留issue追踪和原范围，不能悄悄删除。
- **不支持结论要求证据。** 明确识别该A21构建的解析/使用/界面路径缺失或固定拒绝，排除脚本限制、活动未启用、资源缺失和取证盲区，记录能复核的地址/样本/资源身份。必要时取得独立客户端路径证据；“没有抓到包”不够。
- **临时行为。** 未放行分支明确拒绝、不消费，且客户端有提示或正常结束界面；仍标记未完成，不作为最终不支持结果。

要优先完成B1/B2可以作为阶段性范围，但剩余矩阵必须继续开放。若要从原issue排除旧活动或本地UI，应由用户明确批准范围调整，并同步issue验收；本方案没有代替用户作此裁剪。

## 7. 数据兼容与回退

- B1优先复用现有事实；不为完成任务而预先增表。B2/B3确需新字段/表时，先确定唯一owner及读取/消费方，再按[迁移规范](../../DatabaseSchemaMigration.md)同改schema版本、DbMigrate和迁移验证。游戏发布版本号保持不动。
- 账号级额度不能通过虚构角色ID或在角色次数中复制记录实现；缺少账号owner时作为真实结构依赖处理。
- 在隔离的当前结构副本中验证旧数据保留、迁移幂等、服务重启与新建库形状一致，再准备当前主干库实机测试。
- 使用当前主干库前核实进程、启动参数与配置覆盖；保存一致备份与原服务恢复材料。两个Host不能同时写同一个库。
- 仅代码回退不等于数据回退；已发生迁移/消费时，恢复需结合停服、对应程序及一致备份，另行协调。不能把整个玩家库回滚当作单个道具测试的常规清理。

## 8. 实施完成门槛

每批必须同时满足：对应矩阵行取证足够、领域实现及有风险的回归检查通过、协议页与catalog同步、测试服务准备可核验、用户按[实机计划](acceptance-plan.md)反馈通过。CI或合成请求通过不能替代实机。

功能PR在用户通过后创建；之后执行仓库当前Codex架构审核与CI闭环。本轮仅形成方案，没有创建PR或推送。整体#371只能在79行全部形成可接受结果后关闭，或者先由用户明确批准调整范围。
