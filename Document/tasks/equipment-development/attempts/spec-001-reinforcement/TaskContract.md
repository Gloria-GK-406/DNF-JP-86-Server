# TaskContract：装备普通强化

## Context

### Source Request

根任务授权在 `task/solo-play-roadmap` 分支分别完成强化、附魔、魔法封印、异次元属性和锻造。每个内聚功能按 70 服务端、上游、A21 客户端探查，设计方案，实现的顺序推进；本子项承担普通强化。

### Current Situation

已接受基线 `a790a243` 的装备实例保存强化等级，修理费用计算会读取该等级；普通强化的服务端规则、消息切片、材料与失败结算尚未实现。A21 `CMD 0x0050` 的静态请求记录提供字段下界，上游有独立强化实现，70 端有 `Dispatcher_UpgradeItem`，实际 PVF 含强化配置；这些来源需核对，不能直接互相替代。

## Goal

实现装备普通强化的可操作闭环，使目标装备、金币、材料和保护道具在成功或失败后产生一致、可持久化、可向客户端展示的结果，并交付集中实机验收步骤。

## Scope

### In

- 调查 70 端的普通强化入口与规则，上游实现，A21 客户端请求/响应/通知及 PVF 强化表，记录差异和不确定性。
- 形成普通强化的规则、状态、事务与投递方案，并实现客户端可触发的普通强化及相关保护/失败分支。
- 验证目标与材料准入、费用、概率或确定性分支、失败降级/破坏/保护、重复请求与持久化失败，以及重登后的装备状态。
- 提供普通强化的 Human Test List，等待用户随后集中实机验收。

### Out

- 异次元增幅、净化与属性扭转的业务规则；它们由根任务 SC-4 负责。
- `UPGRADE_ITEM_SEPARATE` 锻造业务；它由根任务 SC-5 负责。
- 尚未得到真实客户端观察的 `ClientVerified` 宣称，以及推送、合并或发布。

## Constraints

- 遵守根 TaskContract 的装备身份、资产原子结算和证据边界。
- 即使 A21 `0x0050` 可承载多种强化方式，本子项不得把未实现的增幅或锻造当作普通强化成功处理。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 普通强化请求的合法目标、材料、金币和保护道具被按 A21/PVF 可支持的规则判断；不合法请求不变更资产。 | 70/上游/A21/PVF 对照和方案；拒绝路径自动验证。 |
| SC-2 | 成功、普通失败、降级或破坏及保护生效等适用分支，均正确结算装备和消耗，并将结果投影给客户端；重登状态一致。 | 实现差异、结果和资产守恒测试、协议编码测试、持久化重载测试。 |
| SC-3 | 用户可按固定样本和步骤集中验收普通强化，未实测点被清楚标注。 | Markdown Human Test List、自动验证摘要和证据等级说明。 |

| Capability | Evidence | Authorized scope |
|---|---|---|

## Assumptions

- 当前子项先实现普通强化。A21 `0x0050` 若复用增幅模式，仅为解包时正确分流或拒绝，不提前实现 SC-4。
- 用户的客户端实机验收在本次自动验证之后进行；本子项交付可执行的验收包，不把未执行的实机测试算作通过。
