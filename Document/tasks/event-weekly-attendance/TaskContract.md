# TaskContract：活动管理与累计周签到首个闭环

## Context

### Source Request

用户提出：活动服务从注册的活动实例获取信息，通过类似 `GetEventInfoList` 的能力投影到 `EVENT_INFO`；同一活动实现对象承载统一管理接口与具体玩法接口，活动服务负责列出、启动、关闭。先用一个活动完成注册、显示、操作，再扩展其他实例。

用户接受累计周签到（A21 活动 ID 2208）作为首例，并授权：「可以，写一个任务契约实施吧」。

### Current Situation

基线 `af0715492d9b9850756afdd908f8a93614795ea6`，代码工作区为 `DNF-JP-86-Server/.worktrees/warehouse-storage`，分支 `task/warehouse-storage`。本服入场只发送空 `EVENT_INFO`；上游具有周签到及其日历、进度、领奖协议。A21 静态读取已证明丰富活动信息与内置窗口映射；70 的活动包结构不同，不能直接移植。

## Goal

实现可扩展的活动管理领域能力，以累计周签到完成活动注册、客户端信息投影、进度累计、操作领奖、启停管理和持久化的首个开发闭环；交付可供真实客户端验收的实现，不以自动测试冒充客户端验收。

## Scope

### In

- 一个活动管理领域服务和统一的活动管理接口；从已注册实例获取日历信息。
- 累计周签到活动同一实现对象提供管理与玩法两个领域接口。
- 客户端日历、周签到窗口所需状态、签到请求响应和奖励投递。
- 推荐地下城有效完成与周签到进度接线。
- Web GM 活动列表、配置及启动/关闭操作，遵循现有统一通知、权限和审计模式。
- 配置、启停、期次、玩家进度和领取状态重启保存；重复操作不重复发奖。
- 必要的协议/领域/持久化/HTTP/前端验证、简明使用说明及真实客户端验收清单。

### Out

- 其他活动实例、通用脚本/插件执行平台、任意新客户端窗口或资源。
- 改写客户端或 PVF 来降低签到条件；模拟完成副本或篡改真实玩家进度。
- 远端发布、PR、合并及清理现有分支/工作区；自动替用户执行游戏验收。

## Constraints

- 用户指定的双接口必须共享同一活动实现和生命周期状态；不能另建与玩法脱节的日历配置真相源。
- 领域服务返回领域信息，由协议层映射 `EVENT_INFO`；保持现有项目分层。
- 活动展示与玩法授权共用生效状态、有效期和参与资格；后台列表能够查看未启动或已结束活动。
- 活动类型和期次区分，启停同一期次不重置领奖状态，新的期次不误用旧进度。
- 结算重试和重复签到不能重复计数或发奖；领奖状态和奖励投递具有失败一致性。
- 保留当前客户端/PVF 活动语义，不将上游或 70 资料直接提升为 A21 实机证据。
- 研究与实现按用户授权使用 GPT-6.1 Sol 子代理；共享工作区生产写入串行，浏览器验证使用本机 Chrome。

| SC-1 | 注册的周签到实例同时提供管理与玩法接口；管理列表和日历来源一致 | DI 同实例及列表/生效过滤自动验证 |
| SC-2 | A21 入场获得活动详情和周签到状态，签到请求具有正确响应与刷新 | 客户端静态布局、编码/请求与隔离协议验证；实机验收项独立列出 |
| SC-3 | 有效推荐副本完成推进当周进度，达标可签到并获当周奖励；不达标/关闭/过期拒绝 | 真实结算接线与领域回归，包含边界和重复结算 |
| SC-4 | 奖励、进度及领取状态一致并跨重启保存；启停不刷新领取资格 | SQLite 重启、重复/并发请求和失败回滚验证 |
| SC-5 | Web 可列出、配置、启动/关闭首例活动，错误统一通知且权限审计沿用现有约束 | HTTP/前端验证及 Chrome 页面检查 |
| SC-6 | 交付结果可复核，既有日历空基线被真实投影替换且相关功能不回归 | 适当回归和构建；实现说明与人工测试清单标明未验项目 |
