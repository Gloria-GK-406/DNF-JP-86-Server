## 各类根因与修复方案

### 1. 宠物消耗品被当成宠物本体（386）

- **现象**：例如 2016问鼎天下礼包的奖励"宠物换名卡"（ID 25），共 5 个消耗品，被 374 个礼包引用。
- **根因**：`PvfCeraShopDefinitionSource.cs:352` 只要类型名是 `[creature]` 就判为宠物本体，不区分装备和消耗品，随后要求 `[creature species]`，找不到就判为不支持。物品放置规则（`PvfEntryLifecycleContentSource.ResolveStackableItemKind`）则把消耗品的 `[creature]` 判为宠物消耗品栏（ItemKind 7）。同一物品，两处判断不一致。
- **参照**：70 把消耗品类型 9 `[creature]` 和 10 `[feed]` 走宠物消耗品路径（Confirmed，`_processCreature`）；只有装备的 `[equipment type] [creature]` 才是宠物。C# 两套参照相同。
- **方案**：`[creature]` 只有在装备上才判为宠物，消耗品走普通可堆叠物。同时让奖励分类以放置规则为唯一依据，不再由商城物品源另判一遍（见"架构"一节）。商城卖这几样东西时也会受影响，和 #327 是同一处缺陷。

### 2. 物品文件里字段重复就判为坏数据（132）

- **现象**：
  - 110 个礼包：奖励物品里写了两次 `[attach type]`，例如先写 `[trade]` 再写 `[account]`。商城物品源因此记 `MalformedItem`。
  - 22 个礼包：奖励物品里 `[equipment type]`、`[stack limit]`、`[usable period]` 写了两次，物品元数据读取器（`PvfEntryLifecycleContentSource.TryRead`、`PvfItemLifetimeReader`）直接抛异常。称号类装备是因为条件块（`[if]`/`[then]`）里也有同名字段，没有限定在顶层读取。
- **参照**：
  - 客户端：`[package data]` 后出现的会清掉前面的（Confirmed），说明客户端的做法是覆盖。单值字段是否都是后者生效还没有逐项核对（High）。
  - 70：发放链从不读 `[attach type]`，只有 `[sealing]` 会影响生成的物品（Confirmed）。
- **方案**：
  - 只在顶层读这些字段，条件块内的同名字段不算。
  - 顶层确实重复时按客户端规则"后者生效"。落地前先在客户端 `ImportStackableScript`（`02999F40`）和装备导入里核对 `[attach type]`、`[stack limit]`、`[usable period]` 三个处理器是覆盖还是追加。
  - `[attach type]` 只影响封装和交易属性，不再作为能否发放的条件。

### 3. 随机时装池的两个扩展字段未实现（126）

- **现象**：`[booster info]` 下 `[avatar]`/`[special avatar]` 每行是 5 个数：物品、权重、数量、扩展1、扩展2。扩展字段不为 0 一律拒绝。阐释者礼盒（10007317）、闪烁之光礼盒（10007318）就是这类。
- **根因**：之前修逐暗者礼盒（10007316）时，只按物品 ID 写死放行，并把 `(3,0)` 解释为"不可交易"。
- **参照**：
  - 70：扩展1 是该时装自身 `[avatar type select]` 表的**行下标**，决定期限和徽章孔布局；越界（-1 截成 255 也算）就用时装自己的 `[usable period]`。扩展2 是**时装属性下标**。两者都和交易限制无关（Confirmed，`getAvatarPeriod` `0x08151120`、`getAvatarSocket` `0x08150f36`）。PVF 里写的 7/15/30 大多因为越界，回落到同样天数的 `[usable period]`。
  - A21 客户端：扩展1 存为 u16，在自选窗口里同样当 `[avatar type select]` 行下标用（High）；扩展2 存为 u8，和请求里的属性字节同宽（Hypothesis）。
  - C# 两套参照：丢弃这两个字段。
- **方案**：
  - 按 70 语义实现：期限和孔位取 `[avatar type select]` 第 ext1 行，越界回落到 `[usable period]`；属性取 ext2，并校验它在该时装的属性表内。
  - `[avatar type select]` 已有读取方（`PvfItemSocketDefinitionSource`），复用它。A21 的行宽和 70 不同（逐暗者武器是 7 个数一行），按现有读取方的行定义取。
  - 删除 10007316 的硬编码。是否保留"不可交易"见待裁定 1。

### 4. 奖励是服务类道具（148）

- **现象**：例如金库升级工具（50/58/68/110）、角色栏扩展券（2660239）、技能类型扩展券（821）、物品栏扩展券（2660296/2660297）、拍卖行优惠券（137）、恶魔契约分项（2681929–2681934、2682205/2682206）、名称装饰卡等，共 22 个物品。商城物品源把它们标为 `Service`，开礼包一律拒绝。
- **参照**：
  - 70：发放前先查 premium 表和一张硬编码特殊物品表（`IsSpecialItem`），命中就直接生效（扩仓库、扩背包、角色栏、技能栏、premium、点券礼券），不进背包；没命中就当普通物品发（Confirmed）。
  - 作为奖励出现的 `[cera package]`/`[cera booster]` 会被递归展开（Confirmed）。
  - C# 两套参照的做法相同：在 premium 表或恶魔契约里的才算服务，其余都当物品放进背包。
- **方案**：
  - 建一个商城与开礼包共用的"特殊奖励解析"：premium 物品延长契约（已有），扩容类调 `IInventoryLevelDomainService`，角色栏、技能栏走 #327 待做的增值服务发放。没有即时效果的就当普通物品发。
  - 对照表以本仓商城现有的服务道具名单为准，70 的物品 ID 不能直接搬用。
  - `[cera booster]` 用固定 (id, 数量) 对写服务的写法（例如恶魔契约 30 天礼包 10007846）一并纳入。
  - 和 #327 商城"增值服务发放未实现"是同一块工作，应一起做。

### 5. `[charactor]` 按职业分池（111）

- **写法**：`[charactor]` 段内写 `[swordman] A B N` 后跟若干 (物品, 权重, 数量)，每个职业一段。
- **参照**：
  - A21 客户端：职业名表共 14 项（0–13，查不到为 14）。开启请求不带职业，客户端没有本地筛选（Confirmed / Hypothesis）。
  - 70：没有这个标签。
  - C# 两套参照：按角色职业取对应那段；职业对不上就拒绝且不消耗。上游把 A 当抽取次数，按样本应是 N（有 N=2 的样本，例如 `[at swordman] 1 99 2 …`）。A、B 推测为等级下限和上限（Hypothesis）。
- **方案**：
  - 服务端按角色的职业（含转职前的基础职业）选中那一段，按权重放回抽 N 次。没有对应职业就拒绝，不消耗礼包。
  - 职业名映射复用本仓已有的职业表，不另起一份。
  - A、B 先只校验格式，是否作为等级限制见待裁定 4。

### 6. 按类别选择（447）

- **写法**：
  - `[booster category num] n a b`：n 是类别层数（最多 2），a 是第一层个数，b 是每个第一层下的第二层个数。
  - `[booster select category] c1 c2`：标出这个块的坐标。
  - `[booster selection num]`：大于 0 时恰好选 N 个；等于 0 时玩家只选类别，**整个类别全部发放**。
  - `[booster category autoget from job]` 等：只在 b=0 且 selection num=0 时生效，客户端按职业或持有物品自动定 c1，c2 为 0。
  - 例如 2019绯樱之舞套装礼盒：`2 11 4` 表示 11 个职业 × 4 种配色，选一格得到整套 8 件。
- **参照**：
  - A21 客户端（Confirmed）：0x00A0 选择形态里的 context1、context2 就是 c1、c2，取自两个下拉框；selection num=0 时客户端按 PVF 声明顺序发出该类别全部物品 ID。
  - 70（Confirmed）：服务端只在客户端指定的类别里匹配，最多读 20 个 ID。
  - 第三方参照：也改成了按类别取奖励行。
- **方案**：
  - 自选礼包的定义改成"类别坐标 → 条目列表"，不再把所有块的物品平铺成一个列表。
  - 开启时用请求里的 (c1,c2) 定位类别：
    - selection num>0：校验选中 ID 都属于该类别、互不重复、个数等于 N。
    - selection num=0：校验 ID 集合等于该类别的全部条目。
  - 按类别定位后，"跨类别重复 ID"（103 个）自然消失，不再拒绝。同一类别内的重复 ID 协议表达不了，单独记诊断。
  - 当前 selection num>0 的已支持礼包也要改成按类别校验，否则客户端可以选别的类别的物品。
  - autoget 类别：服务端用同样的规则复核客户端发来的 c1。
  - `[booster category name]` 只是 UI 文案，忽略。

### 7. 自选块里的物品类别与修饰标签（约 400）

- **参照（A21 客户端，Confirmed，`refs/a21-client.md`）**：
  - 自选块内只认 7 个修饰标签：`[booster equipment upgrade]`、`[booster equipment separate]`、`[booster equipment grade]`、`[default select]`、`[recommend]`、`[random probability]`、`[force insert avatar option]`。
  - 其余带数字的标签都是物品类别，`[stackable]`、`[cera]` 是合法类别，条目为 (id, 数量)。
  - 修饰值从出现处生效到块结束，只作用于写在它后面的条目。upgrade、separate、grade 只对 equipment 类别生效。
  - `[action usable place]`、`[booster category num]` 是**顶层**标签，本仓误当成块内内容。
- **方案**：

| 标签 | 处理 | 依据 |
|---|---|---|
| `[stackable]`、`[cera]` 等其他类别 | 按 (id, 数量) 读成条目，和 etc 同样发放 | 客户端 Confirmed，70 Confirmed |
| `[default select]`、`[recommend]` | 只是界面标记，服务端不发不校验；**不能**当奖励读（上游这么做会把数量覆盖成 1） | 客户端 Confirmed，70 Confirmed |
| `[booster equipment upgrade] n` | 之后的装备以强化 +n 生成 | 70 `SetUpgrade` Confirmed；第三方参照同 |
| `upgrade 255` + `[random probability] (等级 权重)…` | 每件装备各自按权重抽强化等级 | 第三方参照代码；客户端要求 255 才合法（Confirmed），pair 语义 Hypothesis |
| `[booster equipment separate]`、`[booster equipment grade]` | 生成装备时写入对应实例字段 | A21 新增，70 没有；语义按标签名推测（High），写进哪个实例字段需要再查客户端 |
| `[force insert avatar option]` | 先记诊断拒绝，待查 | 客户端只追到存入条目 |
| `[action usable place]`、`[booster category num]` | 移到顶层解析；使用地点按现有使用规则处理 | 客户端、70 均 Confirmed |

装备条目带修饰时，需要物品赋予支持"指定强化、增幅、品级"创建装备。查一下 `IItemGrantDomainService` 是否已有这个能力，没有就补。

### 8. `[cera package]` 的 `[package data selection]`（1,140）

- **事实**：
  - 这 1,140 个全是 `[cera package]`。
  - 本仓商城购买时**已经**按选择组展开（`CeraShopRuleService.ExpandAsync`），与 70、两套 C# 参照一致。所以问题只出在礼包已经进了背包之后。
  - 70 的 `[cera package]`/`[cera booster]` 不能在背包里开：只在商城购买、邮件包裹、作为奖励时展开，且后两种情况不带选择，只发 `[package data]`（Confirmed）。
  - A21 客户端对这两类在背包里怎么分派没查出来（`refs/a21-client.md`「查不出的」）。
- **方案**：
  - 所有把物品放进背包的入口（开礼包的奖励、邮件、GM 发放）遇到 `[cera package]`/`[cera booster]` 都按 70 递归展开，不让这两类成为背包里的物品。
  - 已经躺在玩家背包里的：先实机看 A21 右键使用时发不发请求、发哪种形态，再定选择组怎么处理（待裁定 3）。
  - `[cera booster]` 在本仓商城目前是当物品发放，和 70 购买时就展开不一致，一并按这条规则改（需要实机确认客户端能否在背包里开 `[cera booster]`）。

## 架构：先合并重复的事实

这次的缺陷有一半来自同一事实存了两份：

- 礼包内容由两个 PVF 读取器各解析一遍：商城用 `PvfCeraShopDefinitionSource`，开启用 `PvfPackageOpeningDefinitionSource`。
- 奖励物品的种类也判定了两次：商城物品源的 `CeraShopItemKind`，以及放置规则的 ItemKind/WorldClass。第 1 类就是这么来的。
- "什么是服务道具"只在商城里有。

按 `Document/RefactorPreferences.md`「同一事实有第二份快照」处理，第一步先收拢：

1. 一个**礼包内容定义源**，覆盖全部礼包标签，包括类别、修饰、`[charactor]`、选择组、时装扩展。商城展开、背包开启、邮件和 GM 发放都读它。
2. 奖励物品分类只认**放置规则**一家。
3. 一个**特殊奖励解析**，商城和开启共用。

开启领域服务仍按"魔盒 / 普通 / 装扮"三条边界分开（见 `protocol/patterns/flow-package-opening.md`），只是共用这三样内容事实。
