# 安图恩招募与编组规范

## 结果和范围

两名 A21 玩家能进入同一团本频道，完成建团、申请、审批和编组。招募中的小队编号是预定编组。以后开团准备和出战时的实际入队由后续功能交付。

## Requirements

| ID | 行为 |
| --- | --- |
| RQ-001 | 角色完成 12829 后可进入团本频道并抵达可招募的等待室。未完成任务时服务器拒绝进入，普通频道保持现有准入和位置行为。 |
| RQ-002 | 建团成功后，建团者成为团长。本人和同频道角色看到对应团号和团标题，名单初始只有团长。 |
| RQ-003 | 另一个角色可向同频道的团申请。只有有效申请的团长审批才可改变成员关系。拒绝、过期、重复应答和失效会话均不增加成员。批准后同一角色只归属一个团，每团至多 20 人，同账号不能有重复归属。 |
| RQ-004 | 团长可以调整本团成员的预定编组，团员可调整自己的预定编组。接收 A21 可表达的原始组号，按已确认的开放范围与单队容量处理；成功后双端显示相同。 |
| RQ-005 | 建团和入团与原普通组队的关系按[服务设计](../design.md#51-招募)交接。成员退团、断线与审批过期释放本阶段招募状态；同频道无在线团员后清理目录。 |
| RQ-006 | 招募入口、协议和 UI 用真实 A21 会话确认，证据区分服务端日志、线级样本和客户端画面。 |

## Acceptance Criteria

| ID | Covers | 通过判据 |
| --- | --- | --- |
| AC-001 | RQ-001、RQ-006 | 在 A21 上比较 12829 未完成及已完成角色的结果。已完成角色进入团本频道、等待室并打开建团入口；未完成角色被挡在流程之外。 |
| AC-002 | RQ-002、RQ-006 | 团长通过 A21 提交标题。两个独立账号的客户端看到同一个团，初始成员和团长一致。 |
| AC-003 | RQ-003、RQ-006 | 另一客户端发起申请，团长看到审批窗口。一次拒绝后名单未变，再次申请获批准后双端均出现新成员。有针对性的自动验证覆盖重复、失效申请、账号、频道与容量边界。 |
| AC-004 | RQ-004、RQ-006 | 团长调动申请者到一个可用组，两个客户端显示相同组号；记录 F–J 是可操作、被拒还是不可达，按实机结果限定实现范围。自动验证覆盖权限和超容。 |
| AC-005 | RQ-005 | 招募用例验证已有普通队时的交接、退出／断线后团员归属清理，以及普通组队与非团本频道的正常行为。 |

## Success Evidence

开发验证用隔离数据库、已登记的 dev PVF 和两个独立 A21 会话。记录客户端、PVF、服务构建、关键收发帧和每步画面／结果。空包和同号 CMD/NOTI 使用服务端日志确定。自动验证覆盖异常分支，实际频道和招募闭环以 A21 结果为准。正式用户测试按契约的服务与玩家库边界处理。
