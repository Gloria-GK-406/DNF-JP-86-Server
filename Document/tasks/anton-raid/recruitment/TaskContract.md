# TaskContract — 安图恩招募与编组

## Context

### Source Request

> 那就按修订后的设计开始用任务契约做吧。先把安图恩的招募流程跑通，能进团本频道、建团、申请入团和编组，再用 A21 实机确认这段流程。

### Current Situation

`feature/anton-raid` 的 `7f6f5ca67` 已整理 A21 指令与当前 dev PVF 的证据。JP86 已识别团本频道和团本城镇，尚未接通招募。A21 能接收攻坚目录、成员表和入团预检响应。申请预检后的请求顺序、城镇落点及编组 F–J 的可达性仍需双客户端验证。招募当前只维护编组目标，小队组建属于开团准备。

## Goal

两名真实 A21 角色能在 JP86 进入同一团本频道，由一人建团、另一人发起申请，团长批准后完成入团和编组。双方看到一致的团信息、成员及编组，并留下可复查的实机证据。

## Scope

### In

- 团本频道的角色准入和等待室到场，能到达建团入口。
- 建团、攻坚目录、申请预检、申请送达、批准与拒绝、成员及编组变化的客户端投影。
- 招募所需的权限、人数和同账号限制，以及退出、断线或陈旧申请的招募状态清理。
- 两个独立 A21 会话的取证、相关服务端验证、协议及验收记录。

### Out

- 开团准备和实际出战小队组建、扣票、进图、阶段机制、结算、掉线重入和跨频道招募。
- 功能 PR、合并与发布。

## Constraints

- 保留普通频道与普通组队行为。按修订设计独立处理招募中的攻坚成员关系，已有普通队离队沿用普通离队规则。
- 自动化与开发实机使用隔离服务和隔离数据库。正式用户测试按[新功能开发流程](../../../FeatureDevelopment.md#4-使用当前主干数据库准备用户测试)协调现行数据库与原服务。
- 按协议库规则区分 A21 静态证据、线上收发包与 UI 实机结果。对 F–J 等缺乏线上证据的行为，以本次实机结果确定并记录适用范围。
