# TaskContract：次数配额与直接事件投递

## Context

### Source Request

用户要求将消耗品、地下城、权益次数归拢，由事件订阅更新，并在需要立即更新的路径同步等待处理。用户确定命名：“叫DirectAsync怎么样？这不是为了事务做的入口，实际上就是说这是一个同步处理的事件投递。”
执行授权：“行，就按这个方式写任务契约和实施后部署吧。然后我再实际测试看看”。

### Current Situation

消耗品 Effect、权益服务及镜像任务/入场分别写次数表；镜像实际已持久化，但没有权威计数投影，客户端仍显示10。现有 PublishAsync 禁止事务内使用，无法承担与业务原子执行的直接订阅。EnqueueAsync 为持久化异步订阅，继续保留。

## Goal

实现明确区分直接与入队投递的事件服务，统一次数读写职责，保证成功消费与扣次原子、失败不扣次，并同步客户端权威次数，保留已有角色数据。

## Scope

### In

- DirectAsync 直接等待订阅者，允许事务内外使用，继承调用方事务，不自行开启事务。
- 收口消耗品次数/冷却、权益次数（含双倍罐总量和续期）、镜像入场/奖励次数。
- 次数事件同步处理；提交后通过 EventService 投影客户端；登录、选图等适当时机补发权威快照。
- 契约、实现、独立审查、自动测试、部署与实机测试清单。

### Out

- 全任务系统迁移、随机深渊、客户端补丁、新地下城功能、无关地图/PVF错误。
- PR、版本发布、推送合并、分支及工作区清理。

## Constraints

- 保留原始次数与数据库，禁止以清零代替兼容。
- 查询只读；写次数须参与当前可写事务；通知不得在未提交事务发送。
- 直接扣次订阅不能同时注册为持久化队列扣次订阅。
- 镜像0279为NOTI，消耗品021E为NOTI，权益036F为CMD快照；保留各自协议语义及宽度。
- 客户端收到 CMD 0x0025 成功回包会本地递增镜像入场数；当前服务端仅发加载完成 NOTI 0x001E，继续保留该方式，随后用 0x0279 权威快照校准，不额外发送触发递增的 ACK。
- 中文Markdown放Document；复用当前工作区，不改主干。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | DirectAsync 按序等待处理、继承事务，异常可使事务回滚；Enqueue仍异步可靠 | 事件与事务回归测试 |
| SC-2 | 三类次数写入由统一服务承载，业务事件触发扣次；失败/重复操作不多扣 | 结构搜索、原子性/边界/幂等回归 |
| SC-3 | 既有数据、冷却、每日重置、双倍罐续期总量兼容，查询不写 | 持久化与周期测试、现服数据只读对照 |
| SC-4 | 提交后同步权威次数，初始与重登恢复；协议字段/顺序不误判 | codec及投影测试、客户端静态证据；实机待用户验收 |
| SC-5 | 新版本部署到现服入口，回滚输入保留，服务健康且身份可复现 | 运行路径/hash/版本/监听/health/bootstrap与部署回执 |

## Assumptions

- 现有镜像/消耗品/权益限制规则保留，不借归拢任意更改额度或重置时刻。中央服务可按领域保留现有周期规则。
- 人工实机验收在部署后由用户执行，自动测试不能替代ClientVerified。
