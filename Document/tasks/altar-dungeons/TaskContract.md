# TaskContract：无尽与极限祭坛

## Context

### Source Request

“行，就这样实现吧。实现后部署一下，我再进行测试。注意这两个祭坛有每日挑战时间限制，所以需要注意一下。”

前文已接受两个独立领域服务管理无尽/极限祭坛，共用波次、调度、动态实体及协议投影能力的设计。GitHub #151、#152，排期总览 #150。

### Current Situation

当前分支 task/next-round-20261013，已有普通地下城、塔、大会、入场凭证消费、次数与 EventBus、奖励派发。尚无两个祭坛的专用运行闭环。当前普通 Cell 以活怪清零判定清房，不能直接用于尚有待刷波次的祭坛。

## Goal

两个祭坛能合法入场、按内容推进波次、完成或失败结算并退出，极限祭坛正确处理难度选择；每日挑战时间及次数限制有统一规则和客户端同步。实现部署后可供用户实机验收。

## Scope

### In

- 核对当前 PVF、上游、70与 A21 客户端的阶段、消息及每日挑战限制。
- 无尽祭坛11006与极限祭坛11007的独立领域服务、规则与内容源、共享波次与调度。
- 动态怪物登记、死亡去重、待刷波次清房门控、房间/轮次切换、难度选择与超时、结算和退出。
- 复用现有入场、次数、角色经验、奖励派发与 EventBus，并补必要的持久化和通知。
- 自动验证、独立结果审查、协议文档、本地结果提交、保留数据和回滚输入的部署以及测试清单。

### Out

- 山麓、婚姻、SAO和其他特殊副本实现；无关客户端补丁、PVF修改、PR/合并/发布。
- 自动化结果不替代用户的原生客户端实机验收。

## Constraints

- 两个玩法分别管理，通用组件不持有一份相互竞争的玩法进度。
- 必须核实每日挑战时间限制，不将其与每日次数混为一谈；未知值不得伪称原生规则。
- 命令、领域、规则、内容、协议保持现有分层；通知走 EventBus，实时推进不得依赖异步队列及时消费。
- 房间暂时无怪但仍有未来波次时不得提前清房、发出任务清图事实或通关；迟到调度和重复请求不得重复刷怪或发奖。
- 保留已有角色数据库及其他已验收玩法。部署使用独立产物，保留可回退的旧配置与数据库备份。
- 文档位于 Document，协议依据更新到 protocol。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 祭坛规则、每日挑战限制及协议顺序有依据，未验证项明确 | 当前内容/客户端/参考来源及规则记录 |
| SC-2 | 15轮无尽与7轮极限按内容推进，难度选择和时间调度闭合，不提前清房 | 领域状态与波次/时间/反例测试 |
| SC-3 | 入场、计次、收费及拒绝同步正确，奖励最多发放一次且满包可达 | 门禁/消费/持久化与重复结算测试 |
| SC-4 | 放弃、断线、过期调度安全，普通副本与架构回归通过 | 回归结果及独立完整结果审查 |
| SC-5 | 部署身份、监听和就绪可核对，保留回滚输入并提供测试列表 | 产物/数据库备份、部署验证及测试清单 |
