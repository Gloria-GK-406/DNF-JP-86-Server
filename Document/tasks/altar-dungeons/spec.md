# 无尽与极限祭坛规格

## Why and Outcome

用户能分别完成两个祭坛的入场、连续波次战斗、结算和退出。共享机制不把两个玩法揉成一个状态所有者，时间限制与每日次数有明确来源。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 无尽与极限分别由领域服务管理，以物理地下城实例为状态归属；共享不可变内容和波次计划 |
| RQ-002 | 入场沿用凭证/消费流程；每日挑战时间、次数及费用由规则提供并在正确时机持久化及同步 |
| RQ-003 | 怪物按阶段时间动态登记到共享Cell，网络编号唯一，死亡/掉落复用现有结算 |
| RQ-004 | 未生成波次、进行中的轮次/难度选择阻止普通清房与提前任务清图；仅机制允许时打开出口/最终通关 |
| RQ-005 | 极限正确选择难度与处理超时；旧Run/房间/阶段请求无效；退出取消调度 |
| RQ-006 | 祭坛专属排名/奖励/退出生命周期闭合，经验和物品只入账一次；满包被动奖励可邮寄 |
| RQ-007 | 协议按A21证据实现，事件与投影遵循现有事务/提交顺序；不直接依赖INotiBus |
| RQ-008 | 验证与独立审查通过后部署，保留数据库及配置回滚输入、给出原生客户端测试清单 |

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001 | 两个领域服务独立注册、拥有各自运行状态，规划器不查询角色/会话；以RunId避免多人成员各自推进一轮 |
| AC-002 | RQ-002 | 有效/无效时间、次数耗尽、费用不足及跨日可用性按已确认规则判断；不多扣疲劳或费用；UI查询读同一真源 |
| AC-003 | RQ-003,RQ-004 | 分批刷怪，某批清完但后续仍待刷时不清房；重复死亡只处理一次；最后一批和机制完成后才发清图事实 |
| AC-004 | RQ-005 | 合法难度与超时均可继续，重复选择与退出后的到期调度不再次刷怪，房间加载未完成不提前投影 |
| AC-005 | RQ-006 | 达到轮次或失败后生成固定结算结果，重复确认/调度不重复发奖，物品和经验增量与UI一致 |
| AC-006 | RQ-007 | codec有字段向量和依据；共享门控不影响普通图；命令/通知构造器架构检查通过 |
| AC-007 | RQ-008 | 产物与源码身份可核对、健康与监听通过、有旧库备份，给出包含时间/次数边界的实机测试集 |

## Evidence

### 离场与断线的边界

主动002A放弃结算离开者已完成轮次收益，剩余队员继续；0048整队退出须队长校验。网络断线按放弃本局未结算收益处理，不提供离线补偿，已提交入账不回退；当前Run移除后旧调度无效，多人离开的成员不再参与加载门控。此处“断线安全”指实例/旧任务隔离和不重复发奖，不承诺恢复进行中的祭坛或跨重启续打。
