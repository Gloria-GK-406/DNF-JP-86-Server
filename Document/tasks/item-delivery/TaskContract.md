# TaskContract: 统一奖励物品发放

## Context

### Source Request

“ok，就按这个模式写任务契约实现吧。重点在于要全面扫描奖励点，然后全替换。验收时候也将注意力放在检查是否所有的奖励发放点都被切换到新路径。”

### Current Situation

基线 4aec17baa083271f322012043511f9f2845112db。普通翻牌和部分塔结算会跳过满包物品；绝望之塔独自实现邮件回退；任务与礼包预检查可能提前拒绝满包。底层物品授予还被拾取、初始化等不同语义调用。

## Goal

系统奖励统一经过物品发放领域服务，能装入对应物品栏的先入库，剩余通过系统邮件交付；不得因满包丢失、重复生成装备或重复确认领取。

## Scope

### In

- 扫描整个生产代码的奖励制造者、授予调用及直接容器写入，记录迁移矩阵与明确例外。
- 统一服务支持批量奖励、现有装备实例、材料拆分及满包邮件；补齐奖励涉及的邮件类型能力。
- 替换全部系统物品奖励发放路径，包括翻牌、各塔、任务、教程及礼包，调整相应预检查、回值与通知。
- 发奖与所属用例共用事务；维持来源自己的防重复规则；事件用于提交后的通知。
- 回归测试及独立完整性复查，重点反向核查是否仍有绕过统一路径的奖励点。

### Out

- 改变地面拾取、购买、制作、容器移动与邮件领取的行为约定；这些行为明确分类，不能误接满包转邮件形成循环。
- 改变奖励抽取概率与经济数值；部署、改运行数据库、发布或主干合并。
- 称号簿解锁直接制造称号簿专属资产、史诗碎片及虚拟资源仍走各自领域；GM指定正文/附件的显式管理邮件及玩家邮件保持邮件投递语义。上述厂家须作为明确例外入矩阵，不能误标为普通移动或漏扫。

## Constraints

- Application 不引用 Protocol、Infrastructure 或 Persistence；协议投影不得进入发奖服务。
- 装备去向改变不得改变 UID 和已决定属性；特殊计数物品仍由对应领域管理。
- 满包是可恢复情况，配置无效和存储失败不能被吞掉或伪装成交付成功。
- 工作文档放 Document；保持当前工作区已有功能。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 全部系统奖励制造者已分类，需迁移者全部进入统一服务 | 完整扫描矩阵、修改后反向扫描、独立遗漏审查 |
| SC-2 | 装备、材料满包与部分容量不足都交付全部数量 | 实际存储测试，背包与邮件数量之和等于奖励数量 |
| SC-3 | 邮件托管与领取保留奖励实例、属性及支持类型 | 装备身份和属性往返测试，装扮/宠物涉及路径测试 |
| SC-4 | 失败不产生部分奖励或错误领取状态，重试不重复发奖 | 邮件失败回滚及来源防重复回归 |
| SC-5 | 正常入库、满包邮件均通过现有事件/投影同步 | 通知与结果测试；明确自动化证据不等于实机验收 |
| SC-6 | 全量迁移不被旧容量预检查阻断，非奖励行为保持约定 | 任务/礼包预检查和邮件满包领取回归；相关项目测试及构建 |
