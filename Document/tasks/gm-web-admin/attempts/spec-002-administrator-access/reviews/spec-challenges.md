# Spec-002 独立安全挑战

- Target：`../spec.md`，`state: ready`，contract revision 1（本轮读取版本）。
- Governing sources：根 `../../../TaskContract.md` 的 SC-2、SC-6 和身份/追踪约束；child `../TaskContract.md` 的 SC-1 至 SC-3。
- Attack scope：首次初始化、独立认证及权限接缝、会话失效、跨站/传输边界、限流与审计事实；审视后续模块是否能安全复用。未审视或执行玩家资产业务、真实部署。
- Evidence basis：当前工作区源码及 Spec；未运行构建、测试或真实环境探测。以下为待独立 reviewer 裁决的挑战，不是审批结论。没有发现必须先否定当前整体路线的高风险缺陷。

## CH-1: 新端点遗漏权限标记时，接缝是否仍然默认拒绝

- Risk: low-risk
- Failure and impact: 后续邮件或点券端点已挂到 GM 路由，却漏写权限元数据；若公共/私有分类依赖“仅有权限标记时才鉴权”，该端点就可能被匿名调用。Spec 已要求未来私有能力默认拒绝、显式指定权限，当前实现阶段可以用一个没有权限标记的测试端点确认这一事实，因此不需要现在扩大范围或指定完整机制。
- Evidence: `../spec.md:24` 限定匿名入口，`../spec.md:37` 声明一致接缝和显式权限；AC-003（第 51 行）只明确列举审计及身份，未明确遗漏标记的回归探针。当前 `Server/src/Dfo.Server.GmWeb/GmWebModule.cs:19-23` 使用一个无安全元数据的通用路由组，还没有鉴权默认边界。
- Minimum correction: reviewer 确认 RQ-004 包含“未分类的 GM API 不能自动成为匿名入口”，实现证据加入一个遗漏权限声明的端点探针即可；不要求增加未来业务端点。

## CH-2: 并发或容量淘汰是否能够绕过登录失败计数

- Risk: low-risk
- Failure and impact: 同一来源同时提交多次错误登录，如果每个请求先读取计数、最后才各自增加，可能全部在阈值前通过；容量达到上限后若直接淘汰该来源或组合，又可能重置攻击者的窗口。只验证顺序失败 5 次和最终字典长度，会留下仍可高频猜测口令的实现。既有要求已经承诺有效限流，此风险可在当前实现测试中廉价控制。
- Evidence: `../spec.md:40` 要求组合限制、同来源上限和限制存储增长；AC-006（第 54 行）覆盖顺序阈值、窗口及变换用户名，但没有明确并发和达到容量上限后的限制行为。此处尚无 GM 限流实现，没有证据声称已经存在缺陷。
- Minimum correction: 在 RQ-007 的现有边界内补充并发失败和容量饱和/淘汰场景证据，确认计数更新不会丢失、存储上限不能成为同来源重新获得猜测预算的手段；无需在 Spec 决定限流算法。

## CH-3: 认证状态与对应审计在持久化失败时是否保持一致

- Risk: low-risk
- Failure and impact: 登录先提交会话、随后独立写审计，审计写入失败时可能留下可用而无成功记录的会话；注销相反顺序可能产生“注销成功”的记录但旧 Cookie 仍有效。正常登录/注销与一条合成业务记录的共同事务测试，未必覆盖这两个具体认证路径。根目标要求访问有效且管理操作可追踪，但当前 Spec 的共同提交要求主要指未来邮件/点券，当前认证的失败边界可以进一步确认。
- Evidence: `../spec.md:36` 承诺登录和撤销状态，`../spec.md:41` 要求记录登录/注销及共同事务接缝；AC-007（第 55 行）的故意失败事务是合成业务记录。实际 `Server/src/Dfo.Server.Persistence/Database/SqliteDatabase.cs:83-94` 要求写入加入 ambient transaction，具备共同结算基础，但是否在认证用例中共同使用尚待实现。
- Minimum correction: reviewer 确认当前认证状态与其成功审计必须共同结算，或明确同样可追踪的失败处理语义；验证登录和注销在审计持久化故意失败时不会留下虚假的成功事实或未追踪的有效状态。无需增加资产业务。

## CH-4: 禁止响应携带会话秘密的表述与建立 Cookie 会话存在歧义

- Risk: low-risk
- Failure and impact: AC-002 如果按整个 HTTP 响应（包括 `Set-Cookie`）理解，成功登录就不能向浏览器传递可使用的会话凭据；若测试为了满足此句避开真实 Cookie，反而弱化跨请求验收。若按 JSON 正文、错误内容、日志和审计理解，则与其他要求一致。这是容易在 review 中澄清的验收边界歧义，而非当前认证路线不可行。
- Evidence: `../spec.md:28` 和 AC-005（第 53 行）要求会话 Cookie 与 TLS `Set-Cookie`；AC-002（第 50 行）又写“登录响应……不得含……会话秘密”。第 25 行的当前身份正文禁止原始令牌是合理且无需改变的。
- Minimum correction: 将成功登录所必需的安全 `Set-Cookie` 与 JSON 正文/错误响应/日志/审计区分，明确仅该受控 Cookie 传输通道可承载会话凭据；其他地方及数据库仍不得保存可直接重放的秘密。

## CH-5: 同源保护可能使已承诺的 Vite 本地开发登录失效

- Risk: low-risk
- Failure and impact: 浏览器在 Vite 端口打开页面并发送登录，`Origin` 是 Vite 地址；代理的 `changeOrigin: true` 则把后端 `Host` 改为 18081。若实现直接要求 Origin 等于后端 Host，文档中的前端开发路径会将合法登录/注销当跨站请求拒绝。反过来，为修复这一问题而接受任意本机请求自报的 Origin 或转发头，又会削弱既定访问边界。此场景具体且可复现，但选择一个受控开发接入办法属于实现细节，不需要否定 Spec。
- Evidence: `Web/gm-admin/vite.config.ts:7` 已设置本机代理及 `changeOrigin: true`；`Document/gm-web-admin.md:16` 将 `npm run dev` 作为开发使用方式；`../spec.md:28` 禁止信任自报转发来源，RQ-005（第 38 行）要求合法浏览器上下文和伪造跨站拒绝，AC-008 需要实际页面交互证据。
- Minimum correction: 在现有本地开发与发布边界内选择并验证可用的开发路径；至少记录 Vite 浏览器登录/注销与发布页面同源登录/注销均可用，且不通过全局接受任意 Origin/转发头放松生产检查。无需在 Spec 写代理实现方案。
