# 角色交易双端验收（#41）

功能分支为 `feature/player-trade-41`。使用两份 A21 客户端和两个不同账号，进入同一游戏频道的同一共享城镇区域。建议先准备金币、普通可交易可堆叠物品和一件可交易的密封装备。验证限次物品和晶体时记录原数量及剩余次数。实机结果待用户记录。

1. A 右击 B 发出邀请。B 先拒绝一次，两端应能立即重新发起。再接受一次，两端均应打开交易窗口。
2. A 放入可交易材料的一部分，B 核对名称和数量。A 撤回一部分，再撤回剩余，B 看到相同结果。B 放入少量金币，A 核对金额。
3. A 登记并尝试修改自己报价，已登记报价保持锁定。B 完成登记，两边确认后只有第二次最终同意才会完成交换。记录成交弹窗和双方金币、背包刷新。正常退出并重登，核对金币与实物。
4. 再测一次双向物品交换。普通密封装备应保留原强化、附魔和期限。对限次物品只转移部分数量并检查转移部分消耗一次，原处剩余数量和次数应正确。
5. 打开交易并报价后分别尝试主动取消、返回选角、切区及最后一方确认前断线。确认另一方退出交易，重新邀请有效，双方重登后资产没有变化。
6. 试放不可交易、锁定或次数已耗尽的物品，检查拒绝和窗口状态。用装满目标栏且无法合堆的接收方测试整笔拒绝。用交出一件装备后正好腾出一格的双方测试正常交换。
7. 用少量蓝色或无色晶体走共享材料栏；核对两个账号的减少和增加，且普通背包没有多出一件晶体。验证普通背包内拖动和组队邀请正常。

出现异常时记录双方动作顺序、频道、角色、物品 ID、数量和大致时间。抓包重点为 `000A/000B` type 1、`0013` 的交易栏坐标、`0018` 的操作值以及成交或取消后的双端刷新。目前使用上游的 `5/1/3`、空体登记完成通知及空映射结束候选；这些值是否复现 A21 原生结果需要在这里验收。

## 自动验证

- 使用 dev 通道 PVF 的双端 TCP 用例通过。第一方确认前与确认后均不提前扣款，普通堆叠可部分撤回。最后一方确认后成交，重复确认无二次扣付。
- 隔离 SQLite 第二方金币写入故障用例通过。普通材料、账号晶体与金币保持原数量。该用例验证故障时的资产回滚及连接保护。
- 协议注册、组队命令编解码与背包移位相关筛选通过 175 项。组队邀请作为原有分支回归，原生界面仍以实机验收为准。

## 实机环境

部署仅使用隔离目录和数据库。角色资产实测使用主干当前库经 SQLite backup API 获取的一致副本并单独校验，服务端、PVF、客户端和日志路径按实际启动参数核对。用户验收通过后才进入功能 PR。
