# Implementation Plan: 邮箱核心服务

## Planning Choice

采用 direct：同一邮箱资产闭环及同一工作区，由主执行者统一集成；可委派有明确文件边界的实现与最终独立审阅。

## Approach and Shared Decisions

内容与状态分离。保留现有三张邮箱表并做增量字段迁移，附件使用稳定 ID。装备引用 items 原行，寄出仅移除位置；普通容器 Clear 会销毁未在批次中幸存的原行，不能拿它充当寄存。新增窄的装备转交存储能力，先 flush 现有物品暂存写入，同一 SQLite 事务处理位置及附件。堆叠继续复用物品分类/容器规则，金币复用角色能力并严格检查全额入账。

## Work and Dependencies

- T-001 / RQ-001：公开不可变模型、Builder、异常与回执、邮箱服务/存储契约。规则和输入边界测试先行。
- T-002 / RQ-002/003/004：物品原实例转交接缝及规则校验；邮箱存储增量迁移与条件状态写入。所有资产变动加入既有事务，不引入消息队列。
- T-003 / RQ-002/004/005：实现发送、查询、阅读、逐附件领取、删除与时钟期限判定；失败不提交，重复竞争至多成功一次。
- T-004 / RQ-006：登录邮箱组装接统一服务读路径；旧记录保留，无法可靠恢复的旧附件应明确拒绝领取，禁止猜测创建装备。
- T-005 / RQ-001..007：真实持久化隔离测试：发送/领取守恒、失败/容量/越权/并发、重载、旧记录、期限和登录；运行相关库存与入场回归及 build。
- T-006 / RQ-007：完成业务用法与协议未闭合说明、独立审阅修复、fresh verification 后一次本地接受提交。

## Verification

资产错发/重复领取/丢失是有实际代价的潜在回归，已有测试没有邮箱行为；以真实 SQLite 资产前后对照作 oracle，支持内部重构。使用 test-driven-development，有意义的 RED/GREEN 证据记录在实施报告，后补测试不冒称 TDD。构建与针对性回归通过后不无理由重复全量测试。生产 DB 与进程不在测试范围。
