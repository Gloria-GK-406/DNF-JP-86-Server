### Current Situation

- 本服已有邮箱三张表、只读加载与登录NOTI0061投影，未形成完整写入服务，见[现状](../../outputs/mail-system-investigation/current-server.md)。
- 70与A21均区分信件身份与附件领取身份，但编号、字段不能直接照搬；核心服务不能把protocol字段作为领域事实。
- 现有角色、物品、背包和事务能力可复用；模板发放接口不能替代已有装备实例转交；金币增加接口可能按携带上限截断。
- 本任务先完成服务级闭环；A21完整附件编码、发信/打开请求体与客户端验收仍是独立工作。

## Goal

提供统一邮箱核心能力：调用方构造完整且不可变的邮件内容，通过一次发送操作完成校验和持久化；收件角色可以查询、阅读、领取与删除符合规则的邮件。寄出和领取期间装备实例、堆叠数量及金币不丢失、不重复，失败不产生部分结算；重启后状态保持一致。

## Scope

### In

- Builder或等价构造方式生成不可变Mail；邮件内容与投递后可变状态分开表达。
- Mail携带来源、收件角色、文字、附件及有效期信息；支持角色来源与内部系统来源。
- 统一Send能力：查询角色和物品领域事实，校验后持久化并返回稳定邮件ID；无效业务输入抛可区分的领域异常。
- 装备附件引用已存在的装备实例ID；可堆叠附件表达模板ID和正数量，覆盖材料及同类堆叠物；支持金币附件。
- 角色发送：校验物品归属及可寄送性，扣除堆叠数量/金币或移出装备所在槽，与创建邮件及附件在同一事务中完成。
- 系统发送：不扣角色背包；装备仍引用由物品系统合法创建的既有实例，禁止复制某角色装备冒充奖励。
- 装备寄存期间不占角色背包槽，邮件附件能定位原实例；领取后放入收件角色正确容器，保留完整实例事实。
- 按角色读取收件箱、单封内容及附件状态；领取、已读、删除与有效期检查具有一致的归属和状态校验。
- 领取附件时完成容量检查、资产入账和领取状态变更；多附件邮件可分别领取，重复领取不得重复入账。
- 邮件删除与附件领取分开；未领取有效附件的邮件不允许普通删除；到期附件不可再领。
- 持久化写路径、必要的兼容处理，以及现有登录读取接入统一业务事实，避免独立旧逻辑继续裁定有效期/可见性。
- 返回外层可用的操作结果/资产变化信息，不在邮箱核心中发送网络报文。
- 服务与真实持久化边界的回归验证、业务文档及研究边界说明。

### Out

- 本任务不以A21邮件UI可用为完成条件；新CMD/NOTI编解码、完整客户端实机闭环后续实施，不以服务测试冒充ClientVerified。
- 玩家邮资、特殊寄送配额、COD、自动退信、保存信件的特殊长期政策，不从70或旧实现直接套用。
- 任务助手每日人偶资格、调度与奖励生成；背包溢出邮件等其他系统的业务接入。
- 为邮件引入通用消息队列、额外所有权流转平台或复杂审计系统。
- 修改客户端/PVF、部署或重启运行服务、操作玩家现有资产、推送/合并代码。

## Constraints

- 用户确定的调用边界：外部组装Mail，统一邮箱发送操作完成业务校验与持久化；具体C#命名在Spec中统一，不把讨论中的拼写视为兼容要求。
- 装备以现有实例为凭证；不得用模板重建而丢失强化、附魔等信息。堆叠物按模板与数量处理，不要求每单位建立实例。
- 来源与收件人合法性以及资产归属由服务查询权威领域事实，不能信任调用方伪造的装备内容或余额。
- 寄出资产移除/扣减与邮件创建原子提交；领取资产入账与附件消耗原子提交。失败、重复请求及相互竞争的操作不能复制或吞掉资产。
- 邮件中的装备与原角色脱离背包关系，但不得成为无法归属到附件的孤立资产，也不得同时在多个背包或可领取附件中存在。
- 复用现有领域、持久化与用例事务分层；Application不引用Protocol/Networking/Infrastructure/Persistence。协议映射及通知留在外层。
- 现有表可调整，但须说明已有记录的兼容方式；不能为了新模型直接清空运行数据库。
- 70静态、A21静态、参照服实现和实机证据分别标注；不把尚未证实的报文布局固化进核心模型。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 邮件构造产物内容不可变；有效邮件经统一发送操作返回ID，非法结构或业务事实有明确失败结果 | 构造/校验测试与公开接口检查；无收件人、无效模板、非正数量、非法来源等代表性反例 |
| SC-2 | 角色发送装备、堆叠物和金币，寄件资产减少与收件邮件同时成功或同时不变 | 持久化集成用例；发送成功及处理中失败后的双方状态对照 |
| SC-3 | 装备从发送到邮件寄存再到领取保持同一实例及完整属性，寄存中不能再被原角色使用或再次寄出 | 带实例属性的装备往返用例，身份/属性/容器占用核对与重复发送拒绝 |
| SC-4 | 系统能给离线角色投递正文及合法附件，不错误扣除角色资产 | 系统投递后重新创建服务/会话查询，正文、收件人、附件完整且可继续操作 |
| SC-5 | 收件人能按附件ID领取；别人不能领取；已领附件不能重复入账 | 正常、多附件逐项领取、越权、重复及竞争领取用例；邮件ID与附件ID不混用 |
| SC-6 | 背包不足、金币不能全额容纳或领取过程失败时，资产与附件状态均保持原状 | 满背包、金币上限、失败回滚用例；不能以部分加金币后成功结束 |
| SC-7 | 已读、删除、到期与查询规则一致；普通删除不丢弃未领有效附件，到期后领取失败 | 服务操作及重新加载后的状态对照；到期边界与带未领附件删除反例 |
| SC-8 | 重启/重新加载后邮件与领取结果一致，登录读取不继续使用冲突的另一套规则 | 同一持久化数据重建服务后的读写对照与登录状态组装回归 |
| SC-9 | 核心服务与协议通知分离，现有物品/金币/入场能力未回归 | 分层检查、相关构建与回归测试；操作结果足够供后续协议层投影 |
| SC-10 | 实现与文档准确区分服务已完成和客户端尚未验证 | 服务接口与业务流程文档、验证结果及未闭合协议清单 |

## Assumptions

- 本轮以服务级资产和邮件状态闭环验收；客户端协议接入另行验收，不要求为未闭合wire设计临时猜测实现。
- 有效期作为邮件输入/规则事实表达，不默认采用70的15天；保存、退回、邮资等被排除的政策在需要时另行确定。
- 已到期邮件的物理清理可延后；到期判定必须即时生效，延后清理期间附件保持可追溯且不可再次领取。大批量清理和装备销毁政策不是本轮强制实现机制。
- 一次领取对应一个附件领取单位；该单位若含关联金币与物品，应整体成功或失败，不把多封邮件或全部附件强制捆为一次大事务。
