# TaskContract: 物品特性与容器准入集合

## Context

### Source Request

用户提出物品使用位类型、容器声明可接受类型，并选择子集判断；随后明确：“只按特性来分。比如账号共享，材料，装备这种大类。活动物品这种就不需要单独做flag了。然后消耗品里实际上也不需要分药品，礼盒什么的。只需要一个消耗品大类就行。”最终授权：“对，写个任务契约开始重构吧。”

### Current Situation

2026-10-03，基准 `c2d647e2e46395d4df542fa565d742be2c81470a`。业务容器已统一；槽位和仓库准入仍分别维护 kind 白名单。账号共享材料的模板特性与当前数量的所有者必须区分。

## Goal

物品提供粗粒度位特性，容器提供接受集合，以非空子集判断统一大类准入，保持现有交易、所有权、容量、固定槽位与持久化行为。

## Scope

### In

- 物品 record 的派生特性、统一分类、容器接受集合与准入规则迁移。
- 普通材料与账号共享材料、装备与消耗品等现有大类；覆盖当前特殊容器所需类别。
- 针对准入边界的回归证据、独立结果评审及一次本地接受提交。

### Out

- 活动、来源、品质、药品/礼盒子类标签；通用查询/标签框架。
- 改变账号共享目录、交易资格、所有权、协议布局或数据库模型。
- 部署、修改运行中数据库、推送、PR、合并与清理工作区。

## Constraints

- 特性为已有模板分类的派生投影；不新增可被调用者任意设置的 core 位字段或持久化第二真相。
- `(itemTraits & acceptedTraits) == itemTraits`，且 `None` 拒绝；它仅表示允许，不表示必需。
- 账号共享是物品模板特性；材料进入个人金库后数量仍由角色容器所有，不能按此 flag 跨角色扣款。
- Application 不引用 Infrastructure；所有更改在当前隔离 worktree；.NET 共享输出的测试串行。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | core 可读粗粒度特性，消耗品不分药品/礼盒；共享特性随模板而非位置变化 | 分类及真实 PVF 测试、代码审阅 |
| SC-2 | 业务容器声明接受集合，公共子集谓词取代重复大类白名单，空/未知类型拒绝 | 准入矩阵与调用路径审阅 |
| SC-3 | 仓库限制、固定槽、容量、UID、事务和所有权继续成立 | 相关应用、持久化及协议回归 |
| SC-4 | 完整实现经独立评审及新鲜验证后一次本地提交，可继续追溯 | review、verification、result 与 Git 状态 |
