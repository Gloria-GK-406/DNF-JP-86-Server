# Implementation Plan：统一容器与共享材料

## Planning Choice

底层容器身份确定后才能详细规划材料迁移与消费者改写。采用渐进 Task Unit，后续单元依据真实输出细化；一个 Spec 收口完整结果，避免多个独立半成品。

## Approach and Shared Decisions

- 复用 `IBusinessItemContainer`、`IItemDomainStore`、现有 SQLite 事务和实例身份结算，避免另建平行容器框架。
- 容器身份通用表达角色/账号归属与种类，调用方通过领域服务取得容器；账号种类不再只允许 AccountCargo。业务局部槽与 A21/既有存储绝对槽继续通过适配边界转换。
- 共享材料新增一个账号拥有的容器空间；11 种材料采用固定位置与专用数量限制，复用物品内容及变更结果。合法高余额不能因普通 PVF 堆叠上限被迁移截断。
- 全部材料入口收敛到统一发放/消耗/移位能力。仅“默认应该放哪”“允许从哪扣除”和协议展示具有材料专用规则。
- 优先保持现有 `items + item_slots`；先修正账号唯一约束和账号金库宽查询，再导入账号材料。迁移有一次性标记并在事务内执行；旧列停止写入，不采用长期双写。
- 旧角色/金库材料与账号余额若同时存在，先检测并明确报告；没有来源证据时不猜测合并。迁移不接触线上数据库。
- 操作者/会话鉴权继续在业务入口执行；容器所属者独立于当前打开它的角色。实例移动保持 UID，数量移动守恒。

## Verification

顺序运行共享 .NET 输出的构建/测试。每单元保留针对其真实风险的验证；完整结果运行 Application、Persistence、Protocol 相关回归，受影响网络路径单独跑 Networking 集成。新行为测试先观察有意义的 RED；接口重构用已有行为测试与静态审查。独立结果评审必须针对最终未提交 diff，之后完成新鲜验收证据并一次本地提交。

## Next Planning Boundary

先细化 T-001。以通用身份和账号查询的实际结果确定 T-002 的存储键与迁移参数，避免预先生成依赖未知接口的后续任务。
