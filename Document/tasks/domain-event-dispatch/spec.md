# Specification：事件服务统一入口与订阅分流

## Why and Outcome

业务组件描述已经发生的事实，订阅者独立消费；通知只是消费者之一。后续成就系统可订阅事实，而不修改邮件、地下城等原有领域实现。此次完成事件机制和现有通知入口的全面迁移，不实现成就规则。

## 重构前后的结构性变化

| 边界 | 重构前（ef00741d） | 重构后 |
|---|---|---|
| 业务服务 | 邮件、GM钱包、马战维护直接调用 INotificationBus | 发布领域事实/即时事件；不知道网络发送器，不直接调用通知总线 |
| Protocol/HTTP组件 | 大量 handler 直接调用通知总线；部分通知混有 CMD 回复 | 唯一事件服务入口；协议即时投影明确等待完成，业务事实走提交后订阅 |
| 事件机制 | 没有通用一对多可靠订阅 | 强类型事件信封、稳定类型/版本注册、多订阅组独立投递和完成状态 |
| 持久化 | 提交后通知回调仅 best effort | 业务事实与 outbox 同事务；可靠订阅的更新与完成标记同事务 |
| 通知 | 调用方直接决定发布；总线负责在线解析/组包/发送 | 仅通知订阅适配层调用总线；总线继续负责在线、精确会话、投递和既有重试 |
| 生命周期 | 通知重试有单独后台循环 | 新事件后台服务按订阅组消费，提交后 Channel 唤醒、失败定时重试、启动恢复 |

通知传输不迁入领域事件 payload；现有网络投影消息/handler/codec 保留在 Protocol，Application 不反向引用。

## 两种事件的语义

### 持久化业务事实

不可变 IDomainEvent payload + EventId/BatchId/OccurredAt/OriginInstanceId 信封。EnqueueAsync 只允许当前可写事务；记录事件和当时匹配的订阅投递关系，在全事务提交后只 TryWrite 唤醒，不等待消费者。回滚完全丢弃。邮件每一封都产生 MailCreated，包含真实 MailId/Recipient，不以提醒合并丢失事实。

Reliable 订阅不检查在线状态。每次处理在新 DI scope、新事务及现有 TransactionalExecutionGate 中执行，完成标记同事务；取消/失败回滚，之后独立记录下次重试，超过配置次数保持可诊断的停用记录。类型/版本不认识时保存记录并报告，不静默删除。

LiveOnly 订阅只消费本进程的新鲜事件，重启旧事件或过期事件跳过；同批同接收角色的邮件提醒合并。此类外部提示按 at-most-once 尝试：完成/合并标记在调用网络投影前提交，失败不让其它事实订阅重复，也不做旧公告补播。网络层自身的既有重试策略保持。

### 即时协议投影

现有通知负载中包含 Session、CMD reply、IGameServerMessage 的对象不能写入 outbox，亦不能当作成就事实。通过事件服务的具名即时投影方法及专门类型化投影订阅者分发，等待 NotificationDelivery；无事务发布前置、无后台补播、无持久化。协议回复的顺序、精确 session 失效校验、批次和返回投递结果保持。此方法与 EnqueueAsync 的名称、文档和测试明确不同，不能用即时投影代替应当持久化的事实。

马战实时阶段事件保留启动静默、开场/阶段/结束去重和失败不重放；不是查询响应，不因打开 UI 再次触发。它走类型化运行时订阅，通知适配器负责转换成 JoustLifecycleNotification。

## Scope

新增事件契约、注册、订阅、outbox、分发宿主；接入邮件事实和马战生命周期，迁移全部生产 INotificationBus 发布点；既有投影语义保持。无客户端/PVF/线级协议变更，无部署和运行数据库操作，无称号/成就规则实现。

## Requirements / Acceptance Criteria

| Requirement | Acceptance |
|---|---|
| RQ-001 结构和职责符合上述对照；发布组件不依赖通知投递实现 | AC-001 生产源码只有事件通知订阅适配器、通知机制及组合注册接触 INotificationBus；反射/源码架构判据同时证明会拒绝违规类型 |
| RQ-002 强类型事件独立 payload，多订阅者按稳定事件名称/版本与订阅 ID 注册 | AC-002 两种事件序列化恢复、同事件两订阅者独立接收；重复类型/版本/订阅映射启动失败，未知版本保留可诊断 |
| RQ-003 事实与业务一致提交，查询只读，唤醒不在提交回调里等待处理 | AC-003 SQL 同事务回滚与成功测试；只读/无事务 Enqueue 拒绝；持有命令 gate 的提交可返回且后台随后处理 |
| RQ-004 可靠订阅更新和完成标记一致 | AC-004 处理写数据后抛异常两者回滚；成功后重复 drain 不重复增加；事件 A 某订阅失败不重复执行已完成订阅 B |
| RQ-005 每个订阅组一个异步任务，独立唤醒，无工作挂起，重试按到期时间，启动恢复，停服保留未完工作 | AC-005 启动/提交唤醒/重试/取消/恢复集成测试；等待竞争中的落败等待被取消；失败不结束整体 worker；无每事件 Task.Run/Thread |
| RQ-006 邮件保留每封事实并合并同事务同角色提醒；离线不影响可靠订阅 | AC-006 两封同批邮件两个事实但一次提醒、不同批独立提醒；离线可靠消费者仍处理，重启旧提醒不播放 |
| RQ-007 即时投影等待执行，不混入可靠存储 | AC-007 登录、Party、Town、商城、开包、邮件操作等保留现有批次/ACK顺序、NotificationDelivery 和精确连接保护；投影不能加入可靠事件目录 |
| RQ-008 马战阶段事件只在阶段变化时发生 | AC-008 原有 Joust 维护与协议测试继续通过，查询不推进、不发阶段公告，恢复启动静默、失败不下次 tick 重放 |
| RQ-009 Persistence 只经 Abstractions 契约提供 outbox，建表在 Schema 唯一归属 | AC-009 项目引用保持；Schema 测试验证新增表、列、索引及重复初始化；恢复用临时库，不修改运行数据库 |
| RQ-010 全量调用迁移可逐项复核 | AC-010 迁移清单包含所有基线文件及分类；独立子代理检查无遗漏，记录实际问题和修复后复核 |
