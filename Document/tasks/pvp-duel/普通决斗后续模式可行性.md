# 普通决斗后续模式可行性

建议先做自由房接力战（模式 3），其次验证房内观战。已有 CH50 自由房个人战、团队战、快速加入和单人练习的实机结果。后续模式沿用 A21 客户端的战斗补正，范围以自由房的大厅读写、开局、出战、结算和回房为主。

总力战和综合匹配留在各自的流程里评估。现有个人战能容纳多座位，应先测实机支持的人数与 UI，再决定是否有独立「个人乱斗」入口需要接入。依据见 [PK 系统总览](PK系统总览.md)、[70 与参照服调研](research.md) 和 [A21 模式请求](../../../protocol/game/client-to-server/0x0036.md)。

## 接力战开发方案

1. **确认入口和最小交互。** 在隔离 CH50 用一位房主建普通房，检查模式列表并记录选择接力时的 `0x0036` 包体。核对客户端选择、房间模式与开局的公开入口。如果 CH50 不出现该选项，定位客户端显示条件，并验证已有决斗环境是否能显示。若只证实综合匹配入口，普通自由房阶段优先切到房内观战。
2. **接通首轮。** 继续由 `PvpRoomDomainService` 管房间和对局。普通房的座位、分队、准备、房间广播及 `0x002D` 开场可复用，接力只增加每队当前出战座位、候选成员和轮换截止状态。使用现有 `PvpDeadlineScheduler`，让待发轮换跟随当局 `PvpMatchId`，避免退出或再开后发出旧通知。首个探测场景核对开场与 `0x0070` 的顺序、双端倒计时和每队仅一人可出战。
3. **实现 KO、请求出战与断线。** 场上队员离场或阵亡后，如果同队还有存活候选，按实机证据补位。一队耗尽才冻结整场结果。候场成员的 `0x0070` 请求和 `0x0071` 通知可先确认标志翻转，再核对轮换优先次序。参照服的空附加条目可作为首轮探测用协议。完整玩法须确认主动请求、换人顺序、胜者血量、回合时钟、超时和断线规则。
4. **复用整场结算。** 每场使用同一个 `PvpMatchId`。回合交接在房间事务内更新，提交后由 `PvpBattle` 切片向本局成员投影。只有整场终局进入既有幂等结算和回房链。现有 `pvp_matches.battle_mode` 和 `pvp_match_results` 能存整场模式、阵营、胜负、击杀及逃离，首版预计无需升库。接力专属战绩字段的客户端展示需另行核对。

协议依据见 [空体请求 CMD 0x0070](../../../protocol/game/client-to-server/0x0070.md)、[出场 NOTI 0x0070](../../../protocol/game/server-to-client/NOTI-0x0070.md) 和 [请求通知 NOTI 0x0071](../../../protocol/game/server-to-client/NOTI-0x0071.md)。现有实现边界见 [决斗场](../../PvpDuel.md)。

## 验证顺序

1. 先取现有客户端的模式选择、开局和首次出场证据，再确定人数限制及轮换规则。
2. 自动化验证首轮、轮换、阵亡和断线、迟到或重复请求、终局仅结算一次、结束回房再开，以及个人战、团队战、练习和快速加入回归。
3. 实机至少要观察一名候场队友接替上场。若 A21 允许 2v2，可用 4 个客户端先覆盖轮换，最终再验证 3v3。若客户端只允许 3v3，则直接准备 6 个会话。验收记录双端场上成员、换人顺序、胜负和战绩变化。

## CH50 首版实机测试

1. 使用四个不同账号进入 CH50。A 建普通房，在房主的模式选项切到「擂台战」。B、C、D 依次进房，确认 A/C 与 B/D 分成两队，其他人准备后由 A 开始。
2. 观察倒计时结束后每队一人出战。按常规入座顺序，首轮是 A 与 B。可在 D 客户端试按空格，观察出战请求标志是否变化。
3. 让 B 先倒下，观察 D 是否接替、A 是否继续出战。让 D 再倒下，确认此时整场才结算，四客户端结果对应同一胜方，关闭结果后回到等待房。
4. 再开一局，首轮出战后让一名出战者断线，观察同队候场者能否补位。整场结算后重登看战绩，确认每局只记录一次。

若模式选项不存在、首轮一直等待、KO 后没有补位或出现重复结算，记录界面、动作与大致时间，便于对照 CH50 收发包。首版空附加列表、延时和申请优先顺序在 [决斗场规则](../../PvpDuel.md) 中有记录。

2026-11-23 首次实机已确认普通房能切到擂台模式，四人都能入座。部分客户端随后提示 P2P 连接不稳并自行退房，服务端同期没有开局记录，四条 Game TCP 连接仍在。隔离服启动配置关闭了 A21 UDP 探测，四端均上报 `NatType=5`，上报端口与本机实际 UDP 监听不一致。重新启用探测服务后，已用本机 UDP 探针确认同端口和换端口的回复均返回实际源端口。新会话的房内连通及实际出场待复测。

## 房内观战实机验证

1. 三个角色进入 CH50 的同一间普通房。一名来宾勾选「观战模式」，另一名来宾准备，房主开始决斗。
2. 观战者应随其他两人进入地图，能看到行动和 KO。结束后检查结果页只列参战角色，观战角色的决斗经验和战绩保持原值。
3. 让参战者先关闭结果页，确认房间可以回到等待。观战者返回后取消勾选并选择队伍，确认下局能作为参战者准备。再试一局中途退出观战，确认两名参战者继续对局。

服务端规则见 [决斗场](../../PvpDuel.md#房间-owner-与事务)，协议与证据边界见 [观战座位请求](../../../protocol/game/client-to-server/0x0034.md#房内观战)。
