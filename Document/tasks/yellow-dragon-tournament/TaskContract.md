# TaskContract：黄龙大会一期

## Context

### Source Request

“行，写任务契约，然后实现把。先看上游和client的逻辑制定实现计划。然后出一个专门的进入大会地下城服务来管理参赛人物变化和地下城实体。最后实现后你部署，我来测试”

前文约定先完成黄龙大会，再推进黑龙与两个祭坛。满背包翻牌奖励邮寄已由用户验收。

### Current Situation

当前工作区为 `.worktrees/despair-tower`，分支 `task/despair-tower`，接受基线 `711f489e8cdf33e22f95e07a2d140d217afc2e09`，代码干净。已有特殊地下城静态探索，但大会完整协议、轮次切换和结算尚未落地。

## Goal

让黄龙大会从合法入场、抽签、连续四轮战斗到结算退出形成可供原生客户端测试的完整流程；由专门大会领域服务持有参赛进度与地下城实体，遵循现有命令、规则、事件和奖励派发边界。

## Scope

### In

- 核实上游与 A21 客户端的大会协议、参赛者与轮次变化、奖励生命周期，形成证据与实施计划。
- 黄龙大会入场资格与收费、抽签和对手推进、战斗实体、合法击杀、失败/退出和结算。
- 必需的协议切片、注册、领域与规则服务，以及通关奖励派发和状态清理。
- 自动化回归、独立结果审查、保留数据与回滚输入的本地部署及实机测试步骤。

### Out

- 青龙/黑龙大会与祭坛的完整实现；不将其误标为已验收。
- 无关客户端补丁、PVF 变更、PR、合并、发布与工作区清理。

## Constraints

- 先研究上游与客户端，再定实施计划；上游近似实现不能替代客户端协议证据。
- 专门大会服务管理参赛人物变化和地下城实体；协议 handler 只驱动领域命令与投影。
- 经验只经角色实例修改，奖励复用统一派发服务，通知继续走既有 EventBus 投影。
- 保留现有角色数据和其他地下城流程；不能在第一轮击杀后触发普通地下城通关。
- 文档放在 `Document`；原生客户端行为由用户部署后测试，自动化通过不等于 ClientVerified。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 大会请求、回包与轮次状态具有可追溯依据，未知项明确 | 上游路径、客户端 RVA/字段读取和方案记录 |
| SC-2 | 合法入场后四轮推进，对手与实体保持一致；不重复收费或结算 | 领域与协议测试、状态转换断言 |
| SC-3 | 缺票/不合法请求安全拒绝；失败与退出清理运行态；奖励可达 | 反例与重复请求测试、奖励派发覆盖 |
| SC-4 | 普通地下城和既有架构回归通过，独立审查无未解决阻断项 | 构建、测试及审查记录 |
| SC-5 | 新运行包部署成功且可还原旧运行输入，用户可开始实机测试 | 源码身份、产物身份、数据库备份、监听与就绪证据、测试清单 |
