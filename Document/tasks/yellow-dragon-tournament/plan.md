# 黄龙大会实施计划

## Planning Choice

一个详细计划即可约束入场、单图四轮与领奖的耦合接口；并行只用于只读研究和文件边界独立的测试；产品按已交接边界串行写入。完成实现后交给新上下文独立审查。

## Approach and Shared Decisions

- 新增大会内容接缝、PVF source 和纯规则服务，读取DGN/MAP/AIC，冻结16队、四轮及四个连续actor编号。
- `ITournamentDungeonDomainService` 管理大会状态和统一DungeonRun；在现有入场CMD路由前判断黄龙，门禁与材料成本仍走 `IDungeonAdmissionDomainService`。布局附不可变大会计划，通用run拥有Cell；大会拥有比赛进度。
- 入场投影按布局分流为0183/0184，跳过001C/001D；通用加载流程沿用。死亡事务在写账前问大会是否合法，同一事务内推进轮次/扣疲劳/最后经验，提交后投影死亡再0185。
- 大会状态变化作为事务参与者提交，不在DB提交前可见；奖励领取与标记同一事务；最后通关事实走Quest/Event既有路径，不再触发普通结果屏。
- 现有10秒团灭窗口用于大会淘汰：超时投影边界转为大会失败结算，复活窗口不改变。放弃/回城沿用统一run结束，状态按run身份清理。

## Verification

使用 `test-driven-development` 评估后为四轮门控、一次领取与协议字段建立行为回归；解析/架构通过现有框架检查。研究脚本和文档用结构/引用检查，不写镜像实现的测试。序列化.NET构建测试，PVF设置为当前部署的 `artifacts/avatar-socket-text-20261011/Script.server.pvf`。所有产品变更通过独立审查与新鲜验证后一次提交。部署保留当前运行包与权威SQLite快照，验证精确可执行路径、程序集版本/哈希、监听归属与GM/Launcher就绪。

## 研究补充后的实施细节

客户端翻牌倒计时只推进UI，不会自动请求未选牌。按上游策略，首次有效01CA启动3秒期限，后台扫描按run与精确session租约调用同一选牌CMD，补领未选行；重复状态请求不延期，重复选牌返回当前成功状态。大会领域仍负责余额与领取标记，扫描器只做时间驱动与提交后协议投影。
