# 角色物品坐标边界设计

此页记录本轮已实现的坐标边界；客户端实机验收仍见文末清单。

## 三种坐标不能混用

| 层 | 地址 | 用途 |
|---|---|---|
| 领域 | 角色、store、业务container、局部index | 发放、移动、穿脱、拆合、数量与容量判断 |
| 持久化适配 | owner/list/index | 兼容当前SQLite已有位置数据，保留物品实例身份 |
| 协议适配 | wire list/index | 解释客户端请求与发送物品/角色投影 |

即使后两者目前某些数字相同，也不能用“协议映射函数”替代“存储映射函数”。`InventorySlotMappingRuleService` 是候选 A21 wire 表，`LegacyInventoryStorageCoordinates` 是旧 SQLite 位置适配。客户端穿戴宠物 `25`、神器 `26..28` 目前只有上游参考证据，尚非 A21 `ClientVerified`。

## 业务归属

- Item：普通穿戴、背包装备、消耗品、材料、任务物品、副职业材料、物品快捷栏。
- Avatar：装扮背包、装扮穿戴、装扮徽章材料。徽章材料旧存储在Main不改变此归属。
- Creature：宠物、宠物装备、宠物消耗品、已出战宠物及宠物装备穿戴。
- Medal：预留勋章与守护珠归属，当前不因此新增勋章玩法。

技能快捷键不属于物品container。个人/账号仓库未来以归属、准入及容量规则接入，本次不实现新仓库操作。

## 操作约束

1. `store.GetContainer(kind)`返回业务容器，调用者只交局部index。相同物理Main后端上的消耗品0与材料0是两个不同业务位置。
2. 旧持久化容器可以作为适配后端，但不能在领域调用方手工计算其offset。
3. 跨容器交换前同时校验两端目标准入；写入与清除在同一事务完成。失败不能保留半次操作。
4. 统一发放按模板解析归属，不能由掉落/翻牌/邮件/商城调用者一律指定Main。
5. 跨分区产出以业务位置作key。分解读取装备区，产生材料时取得材料容器，不能用来源container代表整个背包。
6. 业务回执和事件携带业务位置。协议通知组合器/编码边界集中投影为wire地址，保持收件人和消息顺序不变。
7. 未知槽位或不能解释的旧记录必须明确拒绝或报告，不能吞异常后静默隐藏。明确的非物品虚拟资源由其原有领域负责。

## 兼容检查

普通装备、装扮、宠物实例的附加属性和身份随物品移动保留。完整实例移动把来源业务槽交给存储适配；存储层在同一事务内按来源行解析 UID，同 core 的两件装备也可交换。堆叠拆合和原位属性更新仍保留原语义。旧绝对索引 `IItemContainer.MoveToAsync` 已移除。

入场前 `LegacyWornItemNormalizer` 按模板及 kind 检查穿戴宠物和神器，把旧位置归到当前候选物理位；先计算整个计划，目标碰撞或模板不符会整体拒绝，重复入场幂等。普通装备已正确存于物理 `12..24` 的位置不统一平移。历史上错误落在 `Main` 的宠物装备不在本轮自动修复；不能凭位置把 `Main` 记录改判为 `Pet`。迁移只通过隔离测试执行，未运行生产数据库。

协议事实及证据等级见[槽位证据](evidence/slot-evidence.md)，实机步骤见[验收清单](client-acceptance.md)。
