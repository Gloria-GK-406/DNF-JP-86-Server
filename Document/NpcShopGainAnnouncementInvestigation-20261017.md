# NPC购买“获得数量递增”调查（2026-10-17）

## 结论

ClientObserved：用户每次买1枚结婚礼炮，截图却连续显示获得2、3、4、5枚；后续从0买到3才播报1、再买第4枚播报2。生产日志全部相应交易count=1。问题来自通用BUY_ITEM回包与后续绝对背包同步之间的数量语义错误。

当前状态：已实现服务端修复并通过自动化，补正后的原生客户端提示仍待实机验收。原始静态证据与旧实现根因保留如下。

ClientStatic / Confirmed：

1. BUY_ITEM尾部@118的u8计数及随后8B元组被读取后，在RVA00D35E5E..00D35E6C按物品ID找到现有物品并调用vtable+40（absolute setter），其实现AEC940写入新数量；不能把本次购买量直接作为该字段含义。
2. 随后主记录Data经过00D35EFE..00D35F0C调用vtable+4C；该实现AE8FD0..AE9042明确读取旧值、add传入量、再调用setter。因此首记录本次增加量的原语判断成立。
3. NOTI000E的D7E965..D7E99C比较绝对新数量与当前客户端旧量，正差加入获得列表；D7F22C..D7F234把差额送125E480，125DA20通过dstr1179(0x49B)生成获得文字。
4. 旧版BuyItemResponseEncoder固定发送N=1、(购买商品ID,本次购买量)。每买1枚，尾表先把已有堆叠改为1，首记录再加1成为2；随后000E回填真实总量，差额逐次变大。例如原有5、本次买1：本地临时2，绝对回填6，被误报获得4。并非服务端每次发放了2/3/4枚。

旧实现：普通NPC商店均共用该编码器。礼炮触发了长期已有的问题；材料扣量独立由前置000E投影，商品绝对量与金币由事务和绝对通知维护。参照ServerS4A21同样把尾表命名PurchaseCountUpdate并填本次购买量，因此参照命名不能替代客户端消费链。

## 修复

CurrentImplementation：所有NPC购买ACK移除错误商品尾表，N=0，成功body长度119字节。堆叠商品先投影000E最终库存，
由原生正差计算产生获得提示，再以首记录Data=0确认购买；物品已存在，因此ACK只增加0，不创建零数量堆。
非堆叠商品保留原确认及完整物品核心同步流程。材料扣除仍先于商品入包；任务进度仍在库存及确认后刷新。

额外消费链（ClientStatic / Confirmed）：ACK `D365B8..D365D2` 把首记录Data用于UI限购累计，
`A2B9B0` 通过 `A2A870` 读已有数并相加后交给 `A2B820`。
所以限购商品还会在ACK之后发既有02CC绝对计数；`D1E0FF` 调用同一个 `A2B820` 覆盖该商品累计数，不清空其他商品。
累计数由交易内读取的旧数加本次成交数形成，只随成功限购更新后的回执发出，回滚不投影。
编码器及消息已提升到协议Game公共层，查询与购买切片复用，不跨切片调用。
