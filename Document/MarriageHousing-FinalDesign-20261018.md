# 婚房系统最终建议方案

日期：2026-10-18。对照源码基线：`f69639855bb0e15112c5d647722f9efa0b769226`。

本方案合并 [Claude 调查](MarriageHousingResearch-20261018.md) 与 [Codex 调查汇总](MarriageHousing-ResearchSummary-20261018.md)。本轮交付设计，没有实施、部署、恢复数据库或改变余额。文中的“采用”是待用户整体审阅的实施选择，不把设计默认值记成原服事实。

## 1. 最终范围与方向

婚房继续属于统一婚姻系统。第一期完成：原生进出婚房、夫妻私有场景、家具商店与装饰保管箱、摆放/收回/删除、房间属性、个人心意点、婚戒升级、爱情树、持久化和重登恢复。

爱情成长胶囊作为紧邻扩展单独验收，可在核心完成后同轮追加；不为它延迟核心婚房。访客、仓库扩容、普通装备/材料共享仓库、离婚资产清算、配偶传送和爱之摩伽陀副本不纳入这次核心范围。

内部按步骤实现与回归；没有阻塞时可以合包部署，由用户一次按流程验收，不要求每个内部步骤都停下来等待人工批准。具体实现与部署另从用户对本方案的后续指令开始。

## 3. 统一婚姻系统，查询与执行分开

不照搬“新增独立 H，只读关系，却同时负责扣关系心意点”的接口草案：它缺少经济写入的归属，也偏离本项目已经确定的统一婚姻系统方向。

采用以下结构，名称可随编码统一，但依赖边界不变：

```text
协议写用例 -> MarriageDomainService（partial 文件组织）
               -> CoupleLedger：阶段、个人心意点、双方共享婚戒等级
               -> HousingOperations（内部）：家具与树用例
                    -> HousingState：房间/家具/树持久状态
                    -> 库存生命周期、金币/道具消费、邮件等基础能力

城镇准入/选角/属性查询 -> HousingReadView
                         -> CoupleLedger 的只读接口
                         -> HousingState 的只读接口
```

- `CoupleLedger` 继续是关系阶段和婚姻经济的权威组件。关系写接口仍只交给婚姻主编排；婚前任务继续只读关系。
- 新的婚房写门面由婚姻主编排实现，内部按 `.Housing.cs/.Tree.cs/.Ring.cs` 拆文件，不另建一套婚姻事实。
- `HousingState` 是共享状态组件，其构造依赖只到 store、纯规则和必要时钟；不能到执行组件、完整婚姻服务或通用效果分发器。家具与树的 store 各有唯一构造器所有者。
- `HousingReadView` 必须独立实现，不能只是完整写服务的接口别名。准入、属性和商店余额查询不能为了读一份状态而构造整条写链。
- 扣点由 M 编排：校验关系与消费计划，扣个人钱包，再提交家具/戒指结果，全部处于同一事务。内部婚房组件不回调 M，也不绕过账本写余额。
- 架构回归保留“禁止 Func/Lazy/ServiceProvider 绕环、store 单一所有者、查询传递依赖不可达写主服务/效果分发器”。新增状态组件可以被多个只读调用方共用，这是有意的单向依赖。

## 4. 确定本期玩法规则

### 4.1 婚房准入、场景和返回

1. 只有当前有效 Married 关系中的本人或配偶可以进入，验证账号与角色归属；配偶离线也可进入。无访客模式，不依赖是否组队。
2. 采用稳定的关系房间身份。可用整数 `couple_no` 映射现有关系 GUID，避免把 GUID 塞入现有整数容器 owner；唯一性由数据库保证，查询不隐式分配编号。
3. `TownAreaKey` 或对应场景键增加实例维度，普通场景 instance=0，婚房 instance=couple_no。客户端仍使用 `town 101/area 0`。实例号由服务端关系推导，不能信客户端指定。
4. 同夫妻同频道互相可见；不同夫妻完全隔离；跨频道加载同一份家具/树资产，但人物在场与移动只在各自频道传播，不自动把人跨频道拉过来。
5. 入房前保存合法的返回位置；婚房运行位置不覆盖普通城镇持久位置。此规则必须覆盖移动、定期位置保存、退出和选角等全部写位置路径，不能只跳过一次 `SetUserArea` 写入。
6. 正常出口回来源安全位置；重登回入口前的合法普通位置，家具、树与戒指状态仍从库恢复。旧数据若已保存 `101/0`，恢复时必须做安全回落，不能先加入公共婚房区域。

已婚不是任意传送许可：进门仍核对原生门来源、当前场景和已有区域切换规则。私房内只有取得正确实例与准入身份后才启用夫妻共享在场，不向公共 `101/0/instance=0` 暴露成员。

现有婚姻准入函数对非教堂区域直接返回 true，不能替代婚房鉴权。普通传送前仍保留 PVF 区域声明、频道资格、当前位置与会话代际校验。

实例改动必须覆盖到达、离开、移动、名单、投影门、反向索引、队伍目录、强制位置、掉线与切角。仅在一个广播点加配偶过滤不算完成隔离。

### 4.2 个人心意点与旧余额迁移

**本方案推荐个人点数，每个已婚角色上限 999；婚房家具由双方共享。** 历史资料明确个人点数，当前 PVF 指南以“已婚角色每日登录 +1”描述收入，客户端也按角色更新余额。组合证据支持这项选择，但不宣称已经证明原服持久层。

- 新余额按 `(relation_id, character_id)` 保存，带 revision。查询返回操作者自己的余额；使用心意通只加使用者，家具/升级券只扣购买者；共享家具和共享戒指结果刷新双方。
- 已婚角色每日首次登录 +1，按项目现有每日周期服务处理。每日资格键按角色与周期去重，避免同日重登或改关系重复领取；满 999 不溢出。
- `10002606` 作为 PVF 费用符号映射到钱包，不再让通用材料扣除逻辑误认为必须有一堆真实背包材料。商店 UI 如何读取余额需沿客户端购买路径核对，不能只让服务端购买成功而面板不刷新。
- 购买升级券时按已确认 NPC 交易规则结算心意点与金币；使用券时消费券并升级，不因为同一份模板价格再重复收费。

**迁移政策：**结束每次启动取 `max(关系列,旧婚礼列)` 的对账方式，使用有版本标记的一次性迁移。旧共享列保留为审计兼容数据，不再作为新余额的回填源。不支持旧二进制继续写新经济数据；回退要恢复配套数据库备份。

本轮只读检查显示当前唯一已婚关系的共享余额为 **40**，旧婚礼列也存在非零记录。本次测试迁移建议按 **20/20** 分给双方，保留“旧共享余额 40 → 两个个人余额各 20”的审计记录。这是显式测试迁移政策，不是假称还原各人的历史贡献。实施前必须重新核对实际余额；若已变化，重做迁移清单，不能硬编码本次数字。本轮没有执行该迁移。

### 4.3 家具与装饰保管箱

- 专用关系表保存 40 格 `(slot,item_id,count,revision)`，独立表保存 28 个摆放锚点的 `(position_slot,item_id)`。不扩展全库普通物品 owner，不把家具伪装成某一方角色资产。
- 一期保管箱仅接纳 PVF 明确支持的婚房家具；种子、水壶、升级券仍用已有个人背包流程。普通道具、装备、带期限/独立附加状态物品不能因客户端可拖动就默认放行。
- 家具从商店购买后进入共同保管箱；摆放减一件并占目标锚点，收回反向增加，删除按真实槽位/模板/数量校验。没有证据前不开放个人背包与共同保管箱的任意存取桥。
- `03FD` 开启后持有服务器内部编辑租约，另一方按已读出的失败码拒绝；关闭、离开、切角、掉线精确释放。同一会话重复打开幂等成功，旧连接不能释放新连接的租约。
- 每次写操作仍校验当前会话、关系、编辑权和服务端状态版本。租约不代替数据授权；不要求原生客户端增加未证实的 token/revision 字段。
- 校验允许锚点、占用、窗户与窗帘互斥、库存数量/容量。壁纸/地板不能普通收回；替换旧件的最终去向须定向补查后开放，不能先静默销毁或凭空退还。

通用购买入口优先复用当前 NPC 交易协议，婚房家具/婚姻货币走专用业务分支；识别依据是服务端内容规则和商店身份，不信客户端报价。普通商店、其他材料兑换和获得数量播报要一起回归。

### 4.4 婚房属性与婚戒

- 房间装饰值按有效摆放家具的 PVF 费用汇总，使用当前七档表。采用已摆放价值，而不是余额、历史累计消费或保管箱中未摆放的价值；这是本次实现选择，需要双端对照验证。
- 属性只从当前事实派生，不直接永久加进基础属性。选角、换宠、回城、进副本后仍只能生效一次；客户端显示与服务端战斗属性的应用口径必须一起核对。
- 婚戒初始等级 0，共享等级存在关系账本。`03F4` 校验本人券槽、真实券 ID、当前级与目标级，禁止跳级/重复吞券；成功事务包含扣券和等级更新，另一方在线收到 `03D1`，离线重登恢复。
- 模板没有随机成功率，本服采用合法升级必定成功；不增加随机失败销毁机制。
- 决斗场的属性屏蔽单独按客户端/PVF限制验证，不能把普通副本的属性合成无条件套入所有场景。

### 4.5 爱情树采用可循环玩法

采用三种树、种植期限 30 天、普通水 +10、强效水 +20、成熟阈值 30。以下细节是明确的本服一期规则，未冒充全部由原服证实：

| 行为 | 本期规则 |
|---|---|
| 谁能操作 | 双方都可，配偶离线不影响；操作者必须在自己婚房。 |
| 每日浇水 | 一棵树夫妻合计 2 次，沿用每日周期服务；成功扣壶才计数。 |
| 成长 | 由浇水增加，满阶段后不再额外耗水；不按在线时长自动涨。 |
| 收获后 | **同一棵树继续存在，成长值清零，可继续浇水收获；不重置种植到期日，也不重置当日浇水次数。** 这是循环设计选择，需实机验收。 |
| 奖励 | 每个收获轮次双方各按 PVF 权重独立抽一次，各发一封系统邮件；结果和两封邮件在同一事务内落库。 |
| 到期 | 保留枯树，只允许查看/清理，清理后才能重新种植；不静默删除资产。 |

持久化 `planting_id、kind、planted_at、expires_at、growth、harvest_round、revision` 和每日浇水计数；收获唯一键至少包含 `(planting_id,harvest_round)`，每个轮次绑定双方奖励投递记录。重发、并发收获或重启只能回放同一轮结果，不能重抽、重发。

不用为树注册每秒写库的定时任务。读路径按时钟派生枯萎状态，写操作在锁与事务中再次判断；即使客户端时间不准，也不能绕过服务端期限。`03DE` 只是奖励展示，不能把它当实际发物品。

树快照最后一个 i8、完整种植/浇水失败回包和收割后的客户端刷新需先定向闭合。必要时使用隔离、可回滚探针；不得因字段未知就长期返回伪成功。

### 4.6 爱情成长胶囊的后续闭环

本轮发现的指南足以确定“已婚角色通关推荐地下城”是增长来源；不再将来源完全未知作为延期理由。核心婚房之后可接：可靠通关事件 → 按角色去重并加能量 → 满槽后原生按钮制作 → 赠送配偶 → 配偶领取 `10002910`。

推荐按配置每次 +2、满 10 可制作一个，持有/待领各按配置上限处理。指南没有要求必须与配偶同队，不能照搬婚前任务的固定搭档条件。推荐地下城判定、能量封顶、制作失败及领取空间不足要结合现有推荐图规则和客户端失败分支验收。这套状态与账号成长胶囊分离。

## 5. 交易与同步的统一约束

1. 共享资产写请求使用排序后的双方账号锁和一个事务；进入用例后重新核对当前关系、账号集合与精确会话。配偶离线时仍锁其账号身份，不要求在线会话存在。
2. 扣点/金币/材料、家具增加、摆放、婚戒升级、树奖励均原子提交。先做正常资格与容量检查；发生写后失败时必须回滚，再映射已确认的业务失败回包，不能穿透为网络断线，也不能半成功返回。
3. 请求重放复用现有结算身份与当前状态投影；新增 `ReplayProjectionNeeds` 时同步更新 `Validate` 白名单。树轮次、每日收入、邮件投递还必须有业务级唯一约束，不能只依赖网络序号。
4. 提交后再发通知。资产与属性更新按双方当前关系/精确会话投递；人物移动与名单按同一个场景实例投递，两类收件人规则不能混用。
5. 未婚及空状态保留既有 204 零 `03D8` 兼容。已婚非空房使用真实计数与条目；无树时使用可验证的无树状态，不能套旧上游有树常量。
6. `03FE` 的 7B 请求记录与 NOTI 的 11B 结果记录分别实现，不能公用同一个序列化布局。成功/失败回包按 handler 的实际消费门分开验证。
7. 含 14B 不透明区的请求按完整 15/28/24/20/19B 等长度校验，业务从 +14 读取；不检验未初始化的不透明字节，也不放宽实际槽位、数量、物品、身份和状态校验。

## 6. 内部推进与验收顺序

| 步骤 | 交付 | 必须通过的判据 |
|---|---|---|
| H0 | 入口定向取证、已婚准入、场景实例、返回位置、必要空房投影 | 未婚/旧关系被拒；同夫妻互见、两对夫妻不串；离开/重登正常；普通城镇与组队回归。 |
| H1 | 个人钱包一次迁移、每日收入、40 格保管箱、租约、家具购买与摆放/收回/删除 | 余额与家具共同提交；另一方刷新；容量/互斥正确；掉线释放；重放与重启不多发、不复活余额。 |
| H2 | 装饰值与属性、婚戒升级 | 摆放改变属性，未摆放不计；双方戒指同步；重复请求不吞第二张券；换宠/进本/回城不丢或叠属性。 |

H0/H1 之间可以有协议依赖，不按表格机械切断快照。内部每步保留独立回归与回退边界；没有阻塞时给用户一个包含 H0–H3 的完整测试版本。H4 若未闭合，独立留到后续，不改变核心婚房验收。

## 7. 实施前必须补的定向信息

## 8. 数据保护与本轮交付边界

进入实施前备份当时的在线一致性数据库，迁移先在副本上演练并审计；部署包、源码提交、数据库版本与配置一起记录。回退涉及新经济模型时，必须回退匹配的库，不只换二进制。
