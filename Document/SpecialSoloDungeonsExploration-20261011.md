# 特殊单人副本探索：大会、绝望塔与祭坛

日期：2026-10-11。范围：静态信息收集；没有修改业务代码、PVF、数据库或部署环境，没有新增实机验收。

## 1. 探索结论

这些玩法有独立协议和运行状态，不能只加入普通地下城入口。可以复用现有入场、角色、怪物、奖励、EventBus 与次数基础设施，但需要分别管理赛程、楼层进度和波次。

建议顺序：**黄龙／青龙大会 → 绝望之塔 → 无尽／极限祭坛**。领主之塔、守护者祭坛先核定当前日服版本入口与开放规则。

本轮最重要的发现：

1. **绝望塔的4473不是普通入场券。** 当前道具说明是突破每日挑战限制的“绝望之邀请函”；70原生对首次／重复进入有分支，并检查上次通关时间。不能照普通 required item 一律扣票。
2. **上游不是完整原生规范。** 上游大会非玩家对局是高强度必胜、同强度随机；70的 MakeNextRoundInfo 存在双方分别取随机数比较的路径。上游绝望塔保存最高通关层，但已定位的进度链没有完整呈现原生每日规则。
3. **祭坛需要服务端调度波次。** MAP有独立怪物模板和阶段时序；70明确注册毫秒定时器并发出怪物生成通知。不能在创建Cell时一次性生成所有未来波次。

## 4. 黄龙／青龙大会

### 内容与流程

黄龙战斗MAP17100，青龙17101，黑龙17102。黄龙MAP明确有15名候选敌人，包含类型、代码、强度、名字，以及左右出场位置。上游构建玩家加15个NPC的16强、16→8→4→2四轮赛程和玩家对手路径。

~~~text
入口／材料／疲劳检查 → 本局抽签和赛程
→ 下发赛程与第一轮地图 → 加载完成 → 本轮战斗
→ 本轮目标全部死亡 → 确认获胜 → 下一轮
→ 四轮夺冠，或玩家失败终止 → 按完成轮数结算 → 选牌 → 离场
~~~

服务端负责NPC对局结果、玩家下一轮对手、击杀合法性和奖励；客户端负责对阵表、入场表现和结算UI。普通boss房通关判定不能提前终止大会。

黄龙强度声明包括300／600／900。70在 MakeNextRoundInfo 中存在对双方分别调用 get_rand_int 后比较的路径；上游 PickNpcWinner 则是强度高者必胜，同强度随机。实施时应补完70强度输入与分支，或明确采用自主概率规则，不能把上游近似标为原生算法。

### 消耗与奖励

- 4726“黄龙入选资格”、4727“青龙入选资格”：道具说明可在小铁柱处购买；本轮没有验证本服商店已经售卖。
- 黄龙完成0—4轮的经验表：0／30000／50000／100000／200000。
- 青龙：0／100000／200000／300000／500000。
- 黄龙奖励3329“普通的曲玉”，青龙3323“华丽的曲玉”，数量1／2／3的声明权重60／35／5；还要经过result card规则，不能解释为每次必给。
- DGN有每轮疲劳字段，不能仅在入场按普通迷宫扣一次。失败、复活、退出涉及的扣除时点仍需对齐。

### 协议

| 方向 | Opcode | 内容 |
|---|---|---|
| NOTI | 0183 | TOURNAMENT_INFO，赛程／参赛信息 |
| NOTI | 0184 | TOURNAMENT_MAP_INFO，比赛地图 |
| NOTI | 0185 | TOURNAMENT_CLEAR_REWARD，结算 |
| CMD | 01CA | 奖励选择状态 |
| CMD | 01CB | 选择奖励卡 |

A21的0183起始读取已核实为u32加两个u8，匹配上游当前构包前缀；旧资料里的i16地下城ID不可直接采用。0184／0185也已核实存在读取入口，但本轮**没有闭合全部可变数组、失败回包和发送顺序**。

名字相似的0354—035A比赛广播不直接归入素喃大会，应按客户端处理族区分。

## 5. 绝望之塔

### 楼层结构与长期进度

etc/towerofdespair.etc提供“楼层—DGN—展示APC”映射，最高100层、最低70级，另有允许使用的物品列表。展示APC可为-1，不能要求每层都有单一展示APC，也不能用这个表代替实际MAP战斗内容。

~~~text
读取角色长期进度、今日状态 → 决定本次楼层
→ 检查每日规则与邀请函例外 → 加载本层MAP／APC
→ 失败：不推进通关层；重试按本版本规则检查
→ 通关：奖励与进度持久化 → 客户端更新 → 限制当日普通推进
~~~

“已通关楼层”“今日入场／额外推进”“上次通关日期”是不同事实，不能压成一个剩余次数。

### 4473与每日规则

当前4473说明：不受每日挑战限制，但当日最多挑战三层以内，进入消耗一个。etc的 enterable count=3 不能单凭字段名解释成“普通每天三次”或“三次失败重试”。

70的 CheckEnterable（0x086440EE）：
- 检查等级，取得TOD_UserState和入场计数。
- 计数大于0的分支检查lastClearTime与每日重置边界，并检查所需物品。
- 最后检查单人队伍条件。

另有 ResetDaily、IncreaseEnterCount、ClearLayer 分离操作；ClearLayer推进楼层并记录通关时间。这证明原生有角色进度与每日状态，而且不是无条件扣DGN门票。

**当前A21的免费失败重试、邀请函额外推进和失败后票消耗组合尚未完整闭合。** “每日一层”应作为待实现的明确产品规则，例外分支在实施前专门校准。

### 上游参考与不足

TowerOfDespairProgressService会在入场前把请求映射为角色下一层；仓储保存最高通关层，结算链把奖励和进度纳入持久化效果处理。

但nextFloor=min(100,highest+1)，不能据此推出100层后自动重置。已检查的进度仓储没有每日字段，通用特殊副本默认次数表也未列这100层；尚未定位到与70等价的完整每日门控。直接搬上游不等于实现每日一层。

### 协议与待补证

- NOTI015B USER_APC_INFO_TOD：楼层APC展示。
- NOTI015C TOD_CLEAR_REWARD：通关奖励。
- 入场结合普通入场／地图加载协议，由服务端决定实际楼层。
- 旧枚举的NOTI0392 TOWER_OF_DESPAIR_INFO在本轮使用的A21注册普查中没有找到对应登记，暂不列必发。**CMD0392是守护者祭坛开始，方向不能混淆。**

待确认：每日重置时刻、免费重试、额外票规则、100层大奖／兑换与周目重置、记录和成就衔接，以及复活／消耗品限制在A21的最终效果。

## 6. 无尽／极限祭坛

### 波次由服务端推进

MAP有独立的 blood monster／blood phase time；极限使用 ultimate monster／ultimate phase time。本轮采样确认是“怪物模板集合＋阶段调度”。

上游怪物行按10字段解析，无尽阶段按6字段、极限阶段按7字段解析，极限最后带A／B难度。包含轮次、模板索引、延迟、缩放和调度控制；控制位详细语义目前部分仍来自上游解释。

70的 BloodPhaseSpawn、BloodPhaseSpawnTimerResgister 明确调用 TimerQueue.InsertTimerInMilisecond，并发送BloodMonsterSpawnPacket、维护大轮／小轮。这不是客户端自主刷怪。

~~~text
入场与次数检查 → 初始化祭坛 → 地图加载完成
→ 准备轮次 → 定时调度各波 → 登记真实怪物实例并发生成通知
→ 所有计划波次已发完 且 当前存活目标归零
→ 下一轮／房间 → 全部完成后专用排名与奖励结算
~~~

只看当前怪物数为0会提前通关。与疑惑之村电梯分波有共性，但祭坛还有轮次、专用UI和结算，不能直接当同一业务处理。

无尽DGN三格地图、最大15轮，中间格含MAP候选池；极限固定MAP17030、最大7轮，另外需要难度选择等待、倒计时、选项校验和超时默认决策。

### 次数、奖励与强化边界

上游特殊副本默认表将11006／11007各设3；这是上游策略，未证明A21本版本数值相同。PVF的bloodclearreward.etc包含经验权重、入场次数权重、金币权重、极限难度得分等。

采样中的ultimate reward prob概率列为0，需结合加载规则和其他奖励来源验证，不能据此认定“完全没奖励”，也不能自行改成必掉史诗。

局内点数／强化有关的70符号与内容存在，但本轮未闭合其A21指令和上游实现，列为下一阶段追踪项。它与守护者祭坛“召唤、升级能量”不是同一套协议。

| 方向 | Opcode | 内容 |
|---|---|---|
| NOTI | 00D0／00D1 | 排名／奖励 |
| NOTI | 00D2／00D5 | 普通／特殊刷怪 |
| NOTI | 00D3／00D4 | 开始地图／祭坛信息 |
| NOTI | 00D6／00D7 | 最大时间／轮次间隔 |
| NOTI | 00EB | 通关计数相关信息 |
| NOTI | 0129 | 极限难度UI |
| CMD | 00FF／0102 | 怪物死亡／轮次UI准备完成，枚举身份待继续核实 |
| CMD | 013D | 选择极限难度 |
| CMD | 0048 | EPLP操作，按当前玩法分流 |

核心NOTI及013D已定位A21处理注册。00FF／0102这里只保留枚举层证据，不声称A21当前一定发送；入站布局与握手仍需闭合。

## 7. 领主之塔与守护者祭坛

**领主之塔**有8阶段加权随机MAP池，不是固定八张图。70检查开放schedule、等级及材料，并有独立CBossTower推进和奖励。

当前PVF worldmap指向Tower_cn.img，入场物品路径含chn，补给表也有领主邀请函残留。它们说明资源混有地区内容，不能直接裁定本日服当前周末开放时段。

上游本轮只定位到登录BossTowerBodyBuilder占位，未找到完整玩法handler；本服也有四字节基线消息，不能算玩法实现。核心NOTI0333—0336：信息、开始地图、奖励、EPLP。CMD04AE EVERYDAY_BOSS_TOWER不能仅按名字并入3505。

**守护者祭坛**是独立单位／资源／关卡玩法。70有StartGame、BuyItem、UpgradeGage、SummonUnit、ExchangeSlot、ResetStar和StageControl定时推进；A21有匹配处理注册CMD0392—039A、NOTI035B—0362。

它需要召唤槽、单位、能量／升级、暂停、关卡难度、星级与奖励状态。已登记的是12个普通关卡及生存关，更多未登记资源不能全部开放。入口、地区和活动可用性仍待确认。

## 8. 本服缺口与推荐结构

本服已解析 tournament dungeon、暴露DungeonEntryMode.Tournament，但未定位到大会、绝望塔、BloodAltar、领主塔、AdvanceAltar的完整生命周期及接线。普通入场和已有塔／其他副本基础设施存在，不代表这些模式可正确完成。

~~~text
协议切片解包 → CMD handler → 玩法领域服务 → 规则服务／PVF内容
                               ↓
                        玩法运行实例／进度存储
                               ↓
                     EventBus → 协议通知订阅者
~~~

- 大会：赛程、当前轮、对手、失败／夺冠、奖励选择。
- 绝望塔：长期进度、每日推进、票例外；实际战斗复用地下城基础设施。
- 祭坛：轮次、待发波次、已生成目标、存活集合、难度选择、专用结算。
- 已有UsageQuotas承载相应次数，避免再次分散每日计数；绝望塔楼层进度单独建模。
- 波次调度中的通用部分可进入房间机制；玩法轮次和奖励仍属于对应领域。定时回调检查本局／本房／代次，避免退出后旧任务继续刷怪。
- 关键入场检查与扣除同步收口；通关奖励与进度一致提交。事件用于事实与投影，关键判定不等待异步队列以后才更新。
- 当前没有证据显示这些玩法必须加client patch；先实现正确协议与状态，再根据实机差异判断。

## 9. 下一步建议

优先黄龙／青龙：候选池、赛程、奖励表、上游流程和A21核心处理器均已找到。写实施契约前需闭合赛程全包、轮次完成／加载握手、疲劳扣除和奖励ACK。

绝望塔优先每日一层、进度持久化、失败重试与普通层奖励，再决定额外票和100层周期。祭坛优先波次、完成判定和专用结算，再处理强化与排行。

最有价值的实机素材：
1. 大会入场到第二轮，以及一次失败／选牌。
2. 绝望塔失败后重试、同日通关后再入。
3. 极限祭坛难度选择与一轮波次完成。

本轮不需要部署探索代码。
