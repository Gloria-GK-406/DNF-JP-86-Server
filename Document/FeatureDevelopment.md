# 新功能开发流程

适用于 DNF-JP-86-Server 新功能，从资料收集到用户测试、Codex 审核和主干合并。
一般 bugfix 和纯文档修改按其任务范围执行；所有 PR 共用的审核、合并清理与版本规则见
[开发与发布约定](server-ci-release.md)。

## 1. 建立独立工作区

从最新 `main` 为功能建立新的 Git worktree 和功能分支，在该工作区收集资料、实现和验证。
记录主干基线、功能范围与验收目标，读取本仓 `AGENTS.md` 及涉及的专项约束。
任务资料优先使用 Markdown，放在该工作区的 `Document/tasks/<功能名>/`；
协议结论仍写入 `protocol/` 对应记录并更新 catalog，任务文档引用它，不另维护协议事实。

## 2. 收集证据并确定实现方案

按功能需要收集以下资料，逐项记录来源路径、版本或提交、相关符号、结论和未验证边界：

- **客户端探查：** A21 静态分析、构包／解包路径、界面行为与双向抓包；明确是否经过真实客户端确认。
- **70 服务端参考：** 相关入口、业务规则、状态变化、持久化和通知代码；标明版本差异及能否适用于 A21。
- **上游参考：** ServerS4A21 等上游的对应实现和调用路径；与本仓能力逐项对照。
- **本仓现状：** 现有 owner、接口、规则、事务、协议及同类实现，说明哪些能力可以复用、哪些需要扩展。

参考资料不适用或缺失时明确记录，不用猜测补齐。保留 `ClientStatic`、`WireCaptured`、
`ClientVerified`、`70Reference`、`CurrentImplementation` 与 `Unknown` 的区别；
置信度和来源标签遵循 [协议证据规则](../protocol/evidence.md)。参照代码不直接证明 A21 行为。

实现前阅读 [架构漂移审核规范](ArchitectureReview.md)、[架构与分层](Architecture.md)
及涉及的专项文档，检查周边同类路径后确定方案。方案至少说明职责归属、复用点、
状态所有权、事务与通知边界、协议证据、数据兼容、验证方法和用户测试顺序。
架构缺口或影响功能语义的证据不足需要用户决定时，使用提问工具主动询问，决定前不推进依赖部分。

## 3. 实现与自动验证

按方案在功能工作区实现，补充与行为风险相称的测试，更新相关开发说明及协议记录。
按 [构建与测试](BuildAndTest.md) 完成构建、相关自动测试和必要的集成验证，保留失败与跳过边界。
自动测试使用隔离数据库，不能用玩家库执行清库、夹具初始化或破坏性回归。
自动测试通过只证明其覆盖范围。功能分支不修改版本号，见 [版本规则](server-ci-release.md#版本规则)。

## 4. 使用当前主干数据库准备用户测试

自动验证通过后，将功能工作区的构建产物准备为用户可连接的测试服务，
使用**当前主干服务实际使用的数据库**保留用户现有账号、角色、资产与进度。
先从实际运行进程、启动参数及配置覆盖核实数据库绝对路径，不能只按仓库默认路径猜测，
也不能用功能工作区自动生成的空库或历史备份冒充当前主干数据库。

切换前记录原服务产物、提交、启动配置、数据库路径及恢复方式，并生成可验证的一致数据库备份。
SQLite 活跃库通过 backup API 备份，或停服后取得完整一致快照，不能忽略 WAL 只复制主文件。
保留实际 PVF 和部署配置；涉及迁移时先在备份副本上验证兼容性，再准备用户测试。
与原服务协调写入和端口占用，不让两个 Host 同时写该库；需要停现有服务且尚未获授权时，
主动请求操作授权，不因端口冲突擅自结束进程。数据库、备份、凭据不提交到 Git。

测试服务准备好后，向用户声明功能分支／提交、运行版本、连接方式、数据库路径及就绪情况，
并提供明确的**编号测试流程**：账号／角色和前置条件 → 逐步操作 → 每步预期 → 资产／持久化检查
→ 正常退出重登 → 相关回归。多人、跨日或重启等条件按功能列明，未满足项单独标记。
相关场景可参考 [E2E 验收目录](E2E-验收全测试集-20261027.md)，但本流程的用户测试使用当前主干库，
不套用该目录中专用自动回归基线库的重置步骤。

使用提问工具主动请用户按顺序测试并反馈，不以“等待用户确认”类 todo 反复触发 continuation。
用户明确反馈通过前，不创建功能 PR、不声称实机验收通过。
失败时修复、重新自动验证、更新测试服务和受影响步骤，再请用户复测；
在 `Document/tasks/<功能名>/` 记录真实结果、证据路径和未覆盖项。

## 5. 用户通过后创建 PR，等待审核并合并

用户测试通过后，提交并推送功能分支，创建面向 `main` 的 PR。
说明功能行为、实现方案、相关证据、自动验证及用户测试结果，附已执行的测试顺序和未覆盖项。

按 [Codex 审核闭环](server-ci-release.md#codex-审核闭环) 取得当前提交的审核通过；
架构审核标准见 [架构漂移审核规范](ArchitectureReview.md)。处理审核意见时，涉及行为的修复回到自动验证，
并请用户复测受影响步骤。目标 `main` 前进时重新核对冲突及受影响的验收；
旧提交的审核或测试结果不能自动覆盖新变更。

用户测试、Codex 审核及当前提交的必需 CI 均满足条件后合并到 `main`，
并按 [合并与清理](server-ci-release.md#合并与清理) 删除任务分支与功能工作区。
合并不自动修改版本号、创建 tag 或 Release。
