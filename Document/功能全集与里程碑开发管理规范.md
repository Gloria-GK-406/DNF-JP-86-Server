# 功能全集与里程碑开发管理规范

## 目的

本规范用于组织 DNF JP 86 服务端后续的游戏内容盘点与功能开发，解决以下问题：

- 在开始开发前能够看到目标版本应具备的完整功能范围；
- 不再依靠临时想到一个功能就实现一个功能；
- 每次只关注一个内聚、可端到端验收的功能循环；
- 区分“服务端已经实现”“协议已经确认”和“真实客户端已经验证”；
- 保留开发过程中发现但暂时不处理的问题，而不打断当前功能闭环。

本项目不采用固定周期的 Sprint。开发节奏以功能完成为驱动，而不是以周或日期为驱动。

## 四层管理结构

```text
功能全集 Capability Map
└── Milestone：一个完整的游戏系统
    └── Feature Cycle：一个内聚的功能循环
        └── Issue：可独立验收的玩家功能
            └── PR / TaskContract / 实现与验证检查项
```

### 功能全集

功能全集回答：**目标版本理论上应该具备哪些游戏系统和玩家能力。**

功能全集是项目范围的权威地图，不是待办事项列表。它应覆盖登录、角色、城镇、队伍、地下城、任务、技能、物品、装备、经济、社交、副职业等游戏领域，并明确哪些能力：

- 属于 A21 客户端；
- 纳入当前服务端目标；
- 延后实现；
- 明确不做。

功能全集只需要预先展开到 Milestone 和 Feature Cycle，不应一次性为全部细节创建大量 Issue。

功能全集的盘点来源至少包括：

- A21 客户端的菜单、窗口和玩法入口；
- CMD、NOTI 与业务流程协议索引；
- PVF 中的内容类型和规则；
- ServerS4A21 可供参考的功能面；
- 当前服务端的 Handler、领域服务、持久化与测试；
- 已有协议文档、调查记录、实机结果和 GitHub Issue。

协议数量不等于功能数量。协议是功能的输入、输出或证据，应归入对应玩家功能，不能直接把每条协议当作一个功能。

### Milestone

Milestone 表示一个完整的游戏系统，例如：

- 公会系统；
- 邮件系统；
- 好友系统；
- 拍卖行系统；
- 任务系统；
- 技能系统；
- 普通与循环地下城组队系统。

Milestone 不按时间切分。关闭一个 Milestone，意味着该系统在约定范围内已经形成可持续使用、可实机验证的整体，而不是只完成了一个入口或一条成功路径。

一个 Milestone 通常由若干 Feature Cycle 组成。过大的领域应继续拆分，例如“社交系统”不应作为单个 Milestone，而应拆为公会、好友、邮件等独立系统。

### Feature Cycle

Feature Cycle 是非时间型的功能循环，也是实际开发时的主要关注单位。它必须形成一个可以端到端执行和实机验收的玩家行为闭环。

例如“公会系统”可以拆成：

1. 公会创建与解散；
2. 搜索、申请与审核入会；
3. 成员退出、踢出与会长转让；
4. 公会等级、经验与贡献；
5. 公会技能与增益；
6. 公告、成员列表与在线状态。

任何时刻原则上只激活一个主要 Feature Cycle。当前循环完成实现、实机验证和文档收口后，再进入下一个循环。

Feature Cycle 不使用 GitHub Iteration 字段，因为 Iteration 天然带有时间周期语义。在 GitHub 中用带 `cycle` 标签的父 Issue 表示 Feature Cycle，并通过 Sub-issues 表示其组成。

### Issue

Issue 是最底层的计划与验收单元，描述一个玩家能够观察和验证的功能，而不是单纯描述某个类、数据库表或 Handler 的修改。

例如“搜索、申请与审核入会”循环可以包含：

- 搜索并展示公会列表；
- 提交入会申请；
- 会长查看申请列表；
- 接受或拒绝申请；
- 入会结果向相关成员同步；
- 重登后恢复公会关系。

每个功能 Issue 内部应按需要覆盖：

- 协议和客户端行为调查；
- 领域模型与规则边界；
- 持久化与事务；
- 客户端投影与通知；
- 成功、失败和拒绝路径；
- 单人、组队或并发边界；
- 重登、断线和恢复行为；
- 自动化检查与实机验收；
- 协议及业务流程文档更新。

只有当技术工作可以独立交付、独立延期或具有独立风险时，才拆成单独 Issue。避免把同一个功能机械拆成“建表”“写 Handler”“写测试”等无法独立验收的横向任务。

## GitHub 映射

GitHub 中按以下方式表达四层结构：

| 规划概念 | GitHub 表达 |
|---|---|
| 功能全集 | 仓库内 Markdown 权威清单 + GitHub Project 视图 |
| Milestone | GitHub Milestone |
| Feature Cycle | 带 `cycle` 标签的父 Issue |
| 功能单元 | Sub-issue |
| 代码交付 | 关联具体 Issue 的 PR 或提交 |
| 暂缓问题 | `bug`、`debt` 或 `investigation` Issue |

建议只把 Feature Cycle 父 Issue 直接加入 Milestone。这样 Milestone 的进度表示“功能循环完成了几个”，不会因某个循环拆出了更多小 Issue 而产生权重失真。父 Issue 自身负责展示 Sub-issues 的完成进度。

GitHub Project 不承担新的权威语义，只用于投影和查看：

- `Capability Map`：按领域查看完整系统覆盖；
- `Current Cycle`：只显示当前功能循环；
- `Known Gaps`：集中查看 Bug、Debt 和 Investigation；
- `Roadmap`：按 Milestone 查看系统完成顺序，不绑定日期。

## 状态必须分轴记录

一个功能不能只用“完成/未完成”描述。至少区分以下维度：

### 范围状态

- `In Scope`：纳入目标；
- `Later`：确认存在但延后；
- `Out of Scope`：明确不做；
- `Unknown`：尚未裁决。

### 实现状态

- `Not Started`：未实现；
- `Scaffold`：只有骨架或占位；
- `Partial`：部分路径可用；
- `Playable`：主要玩家流程可用；
- `Complete`：约定范围全部闭合。

### 证据状态

- `Unknown`：缺少权威证据；
- `StaticConfirmed`：客户端静态分析确认；
- `WireCaptured`：真实报文确认；
- `ClientVerified`：真实客户端端到端行为确认。

服务端存在实现或自动化测试，不得自动提升协议证据或客户端验证等级。

## 功能循环完成条件

Feature Cycle 只有同时满足以下条件才能关闭：

1. 约定的玩家入口、正常路径和退出路径可用；
2. 失败和拒绝路径不会破坏状态；
3. 持久化、重登和断线恢复符合该功能的业务语义；
4. 涉及多人时，成员权限、同步、离队和并发边界已验证；
5. 服务端领域状态只有一个权威来源；
6. 客户端收到的 CMD、NOTI 和界面变化符合已确认流程；
7. 对应测试、协议记录和业务流程文档已更新；
8. 当前循环不存在阻碍闭环的未解决问题。

开发中发现的问题按以下规则处理：

- 阻碍当前功能闭环：保留在当前 Feature Cycle，解决后才能关闭；
- 不阻碍当前范围：建立 Bug、Debt 或 Investigation Issue，移入 Known Gaps；
- 与当前系统无关：进入 Backlog，不扩大当前循环；
- 已取得调查结论：结论写入权威文档，Issue 只追踪仍未闭合的部分。

## 全集展开顺序

为了同时获得完整视野并避免 Issue 膨胀，按三步展开：

1. **全集盘点**：列出所有 Milestone 及其 Feature Cycle；
2. **启动 Milestone**：补全该系统的循环边界、依赖和完成定义；
3. **启动 Feature Cycle**：创建具体功能 Issue，并写明验收条件。

因此，项目的长期导航、当前开发焦点和实际交付分别由不同层负责：

> 功能全集负责导航，Milestone 负责系统，Feature Cycle 负责当前焦点，Issue 负责交付，协议和实机证据负责判定完成。
