# 任务进度事件入口

任务进度只有一份持久状态：角色进行中任务的 trigger。业务服务报告已成立的事实，不选择任务或直接修改 trigger；任务服务读取该角色的进行中任务及 PVF 定义，决定哪些通道改变。任务达标（trigger 为零）与交任务、发奖励仍是两个步骤。

## 已接入的事实

| 事实 | 来源与信任边界 | 任务服务处理 | 客户端投影 |
| --- | --- | --- | --- |
| `ClientQuestTriggerReport` | `SET_QUEST_TRIGGER`，客户端声明，需按任务类型和副本上下文校验 | 仅允许客户端计数的目标推进 | 原请求的 `0x0021` CMD 回复；这次变化不再触发 NOTI |
| `QuestEnemyDefeated` | 地下城确认并占用的死亡事实；同一次击杀在事务内交给各受影响角色 | 匹配进行中 `hunt enemy` 的地下城、难度、目标和通道 | 有进度变化时，向该角色发送一次 `0x023F` 活动任务快照 |
| `QuestEnemyDefeated`（含怪物阶级） | 同一已确认死亡事实 | 匹配 `hunt monster` 的四字段目标：副本、最低难度、精确怪物或普通／精英／Boss、目标通道 | 与同次击杀的其他任务变化合并为一次 `0x023F` |
| `QuestHoldingsChanged` | 拾取、击杀直发任务物品、接受任务的起始物品、交任务奖励或 NPC 购买已改变服务端持有量 | 从当前背包和金币重算 `seeking`，不按事件数量累加 | 有进度变化时，向该角色发送一次 `0x023F` 活动任务快照 |
| `QuestCleared` | 交任务的日志写入、奖励与经验在同一事务内成功 | 从已完成任务集合重算仍未完成的 `clear quest` 依赖；奖励引发的持有量变化一并重算 | 完成 CMD 后，若其他任务进度改变，再发一次 `0x023F` |

一次击杀可同时产生死亡事实和任务物品持有量变化；它们在同一事务中报告，最终只投影一份任务快照。NPC 购买成功后也在交易事务内按最终背包重算，拒绝购买不报告。拾取、购买的物品或金币若未改变任务进度，不发送任务快照。任务进度是角色私有投影，不向区域或全队广播；组队击杀逐个计算受影响角色。

接受 `clear quest` 时也会读取已完成集合算实际初值。接受 CMD 仍携带 PVF 声明初值；若两者不同，紧接着发送一次 `0x023F` 校正快照。因此“先完成依赖、后接任务”与“先接任务、后完成依赖”都不会留下永久错误的 trigger。

`0x023F` 是进行中任务的整份快照。因此后来因别的事实发送的快照可能包含曾由 `0x0021` 回复过的值；“不重复”指不为同一次 `SET_QUEST_TRIGGER` 变化再次主动通知，并不要求两种载荷永远不含相同任务。

## 尚未覆盖

- `hunt monster` 的推荐等级副本选择器（`-3`）、世界地图五字段目标，以及当前四字段以外的格式暂不计数；这些目标不能仅用副本 ID 和怪物阶级推出。完整四字段的普通目标已由服务端死亡事实计数。
- `clear map` 仍缺一次性、可归属到角色的地图通关事实；不能把 Boss 房间打开出口直接当作任务目标达成。其 `[int data]` 的单值目标既可能是副本 ID 也可能是地图 ID，双值还可能要求同行 APC，需要在结算路径核实。
- 除拾取、击杀直发、接任务起始物品、交任务奖励、NPC 购买和角色进入时已有的校准外，其余物品／金币变更路径（包括将来实现的邮件领取）尚未逐条接入 `QuestHoldingsChanged`。角色进入时的快照校准保留原路径。
- `hunt enemy` 的被动对象仍通过客户端 `SET_QUEST_TRIGGER` 上报，并受当前任务关联剧情副本的上下文约束；怪物／AI 死亡走服务端事实。其他混合类型的通道规则留待逐类核实。
- `0x023F` 的字段形状有静态证据，以上新推送路径经过服务端测试，但 A21 对所有任务类型的实机显示效果尚未验证。不要把测试或上游行为写成 `ClientVerified`。

以后新增事实应优先扩展 `IQuestProgressDomainService.ReportAsync` 的类型化输入，在任务服务内匹配 PVF；不要在各业务命令中新增任务 ID 分支或直接写 trigger。消息类型和推送时机由业务命令完成提交后的协议投影负责，任务服务不直接依赖网络发送器。
