# TaskContract: 普通地下城副本只挂在队伍上，人员只问队伍

## Context

### Source Request

处理 issue #202「副本参与者名单号称冻结，实际每次现查队伍」。Agent 说明现状后，用户回复：“理论上应当有一个队伍实例作为人员承载者。哪怕是单人也作为拥有一个虚拟队伍的单人队伍。然后副本和队伍关联而不是人。”随后确认：“这是对的，人物找副本也是先找这个人物是挂在哪个队伍，然后再看这个队伍在哪个副本里。按你说带方案来做吧。”在 Agent 报告改动规模后，用户选择：“#202 走 SDD：先写规格和分阶段计划给我审，再逐阶段实施。”

### Current Situation

代码基准 `1cff7218`（main），路径相对 `Server/src/`。

- 普通地下城副本由 `Dfo.Server.Application/World/DungeonRunDomainService.cs` 持有。副本聚合已绑定入场队伍的 `PartyKey`（单人为虚拟队伍键），但另外维护：入场快照 `entryParticipants`（含槽位、队长，除“入场队长”外无人读取）；可变集合 `ActiveParticipants`（`EndAsync` 时移除角色）；以及按角色到副本的索引 `runsByCharacter`。对外成员视图 `Participants` 为“队伍当前成员 ∩ 入场快照 ∩ ActiveParticipants”，槽位、队长取队伍实时值；未注入队伍服务时退回入场快照。
- 接口注释（`Dfo.Server.Abstractions/World/IDungeonRunDomainService.cs`）称副本拥有“frozen participants”，与实际行为不符。
- 队伍成员与 `ActiveParticipants` 两份“谁在本局”靠各离开路径的调用顺序保持一致：放弃副本、断线拆除先结束副本再退队；退队、踢人先改队伍再结束副本；整队退出、续选副本逐个成员结束副本而队伍保留。任一路径只改一边，`Participants.Single(...)` 或 `Leader` 会抛出异常。
- 运行中的队伍当前无法增员，原因是组队前置要求角色处在城镇区域，而入场会离开城镇区域；这一约束没有显式守护。
- 前一任务 `.rks-agent/tasks/party-key-dungeon-membership-refactor/` 已确立 `PartyKey` 为组队领域身份，其规格要求“运行中队伍只允许按已定义的退出语义缩减成员或更换队长；图外角色不能因加入该队伍就进入现有副本”，以及副本不因成员退出改绑另一支队伍。

## Goal

普通地下城副本只与一支队伍（真实或虚拟单人队伍）关联。副本成员、槽位与队长只由队伍回答；副本不再持有独立于队伍的可变人员名单，也不再维护按角色到副本的独立索引。由角色找副本时，先得到该角色所属的队伍，再得到该队伍的副本。副本只保留入场时确定的不可变事实（如入场队长）和每名成员在本局的运行状态。任何离开或结束副本的路径都不会让队伍与副本对“谁在本局”给出不同答案。游戏可观察行为保持不变。

## Scope

### In

- 普通地下城副本的成员、槽位、队长查询只来自队伍；删除副本内独立维护的可变成员集合、按角色到副本的索引，以及“无队伍服务时退回入场快照”的分支。
- 由角色得到其所属队伍（真实队伍或其虚拟单人队伍）的查询能力，供“角色 → 队伍 → 副本”查找使用。
- 个人离开副本的路径（放弃副本、断线拆除、退队、被踢）与离开队伍保持一致，并清理离开者在本局的运行状态；整队结束副本的路径（整队退出、续选副本、清场回城、全灭结束）结束整个副本且不改变队伍。
- 将“运行中副本绑定的队伍不能增员”从偶然成立变为被显式守护的约束。
- 更正描述副本成员的接口注释与相关仓库文档。
- 现有副本相关自动测试在新模型下继续覆盖原有行为，并补充覆盖上述离开、结束与增员约束的测试。

### Out

- 两塔、祭坛等各自独立的运行时成员管理，以及“是否在副本中”的占用登记（`DungeonParticipationDomainService`）。
- 本服务队伍依赖之外的可选依赖清理。
- 协议字段、数据库结构、客户端行为与 A21 实机验收。
- 推送、开 PR、合并、部署。

## Constraints

- 游戏可观察行为不变：协议帧、通知收件人、结算、掉落与翻牌归属、过图与入场结果保持现状。结构调整与任何行为修正须分开说明和验证。
- 运行中副本在生命周期内保持原 `RunId` 并绑定同一支队伍；成员退出不使其改绑或重建。
- 图外角色不能因加入运行中副本绑定的队伍而获得该副本的资格。
