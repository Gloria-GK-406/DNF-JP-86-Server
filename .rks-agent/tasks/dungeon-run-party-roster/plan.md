# Implementation Plan: 普通地下城副本只挂在队伍上，人员只问队伍

## Planning Choice

选 `task-units`：用户要求分阶段实施、每阶段单独验证并提交；后续阶段的细节依赖前面的产出——测试队伍替身的形状决定数百处测试怎么迁移，表征测试暴露的覆盖缺口决定结构切换要额外守住哪些顺序。各阶段共享同一个验收边界（Spec），没有可独立验收或回滚的子结果，不构成 Multi Spec。

## Approach and Shared Decisions

总路线：先钉住行为，再让测试显式表达队伍，最后切换结构。每一步都在“改动前后同一组断言都通过”的前提下推进，满足 Spec 的 AC-011。

现在就定下、后续阶段都依赖的决定：

- **BD-001 队伍键查询**：`IPartyService` 新增 `PartyKey KeyOf(CharacterId characterId)`。角色在真实队伍中返回该队伍键，否则返回 `PartyKey.Virtual(characterId)`。`PartyService` 与协议层装饰器 `PartyClientProjectionService` 实现它，测试替身一并补齐。不提供默认接口实现，避免新实现漏写时静默返回错误值。（RQ-003）
- **BD-002 测试队伍替身**：在 `Server/tests/Support/` 新增一个共享的测试队伍替身，实现 `IPartyService`，按 Application 与 Protocol 两个测试项目现有的方式链接引用。它支持：按入场名单组成真实队伍、退队、转让队长，以及为 AC-009 直接放入图外角色；其他成员抛 `NotSupportedException`。现有调用 `new DungeonRunDomainService()` 的测试改为经一个测试工厂得到“副本服务 + 替身”；多人入场前先在替身里组队；模拟“成员单独离开”的用例同时在替身中退队。单人入场不需要组队（虚拟队伍）。具体 API 名在对应 Task 中确定。
- **BD-003 副本索引**：副本服务以 `runsById` 和 `PartyKey → 副本` 两个索引定位副本；`Find(CharacterId)` 经 `KeyOf` 得到队伍键再查。删除 `runsByCharacter` 与 `ActiveParticipants`；`participantsByCharacter` 收窄为入场名单（角色 → 账号）。成员视图按 Spec“副本成员”的定义计算。每名成员的本局运行状态（进度、准备、死亡、翻牌等）仍按角色保存在副本内。
- **BD-004 结束接口**：
  - 个人离开保留 `EndAsync(CharacterId, DungeonRunId)`，语义改为“清理该角色本局状态”。前提是该角色已不再是副本成员；若副本只剩他一名成员（含单人虚拟队伍），则改为整局结束。
  - 新增整局结束入口（按 `RunId`），供整队退出、选图回城、入场中止、开新局复用；清场回城、全灭结束内部改用同一实现。
  - 两者共用一个逐人清理过程，承载 Spec RQ-008 的全部副作用。
- **BD-005 离开顺序**：放弃副本、断线拆除改为先退队、再清理副本状态。整队退出、选图回城改为调用整局结束。必须保持协议帧内容、顺序与收件人不变，由第一阶段的表征测试判定。
- **BD-006 增员守护位置**：放在协议层组队 CMD（发起邀请与接受邀请），在调用队伍服务前查询该队伍是否绑定副本，绑定则以既有拒绝原因拒绝。队伍服务不引用副本服务（RQ-007）。

## Work and Dependencies

| 工作包 | 交付结果 | 覆盖 | 依赖 | 为何单独成一阶段 |
|---|---|---|---|---|
| T-001 行为表征 | 盘点 Spec 列出的 11 条离开与结束路径（含转让队长、单人离开）在基准上的现有测试覆盖；对缺少协议帧、收件人或 RQ-008 副作用断言的路径补充表征测试，并在未改动的基准上通过 | RQ-008、RQ-010；AC-011 | 无 | 后续每一步“行为不变”的判据；必须先于任何结构改动提交 |
| T-002 队伍查询与测试显式化 | 按 BD-001 加查询；按 BD-002 建替身并迁移全部副本测试的构造；删除副本服务“无队伍服务”的构造路径与回退分支（RQ-002）。此时副本内部仍保留旧名单，全部既有断言与 T-001 表征照旧通过 | RQ-002、RQ-003；AC-003、AC-011 | T-001 | 测试先在旧结构下表达队伍，证明迁移本身不改断言；把数百处机械改动与结构切换分开 |
| T-003 结构切换 | 按 BD-003～BD-005 改副本服务内部与各离开路径的调用顺序；入场中止按当前成员比对；开新局前整局结束同一队伍的旧局；选图回城仅队长整局结束；补齐 AC-001、AC-004～AC-008、AC-010 的领域与协议测试 | RQ-001、RQ-004～RQ-006、RQ-008、RQ-009；AC-001、AC-002、AC-004～AC-008、AC-010、AC-012 | T-002 | 核心改动。副本内部与离开顺序必须同时切换：只改其一，就会出现“已清理状态但仍在队伍”的中间态，因此放在同一阶段，可在 Task 中再细分 |
| T-004 增员守护 | 按 BD-006 在组队 CMD 中加入守护，并补 AC-009 测试（含图外角色构造态） | RQ-007；AC-009 | T-003（依赖“队伍是否绑定副本”的查询） | 独立的协议层规则，回归面小 |
| T-005 注释与文档 | 更正 `IDungeonRunDomainService` 等接口注释；在 `Document/` 的相关专项文档中说明“副本成员由队伍回答、离开即退队、运行中队伍不增员” | RQ-011；AC-013 | T-003、T-004 | 文本收尾，最后确认与实现一致 |

每个工作包完成时：构建通过、与该包相关的测试通过，并做一次阶段提交。T-003 结束后先跑一次完整测试再进入 T-004。

## Verification

- 每个阶段：`dotnet build Server/86JP.Server.slnx` 无错误；按阶段运行副本、组队、离开路径相关测试（Application 的 `World`、`Parties`、`Sessions`，Protocol 的 `Party`、`DungeonEntry`、`DungeonSelection`、`DungeonClear`、`CardReward`、`GroundPickup`、`MonsterDeath`，以及大会、SAO、祭坛相关测试）。
- T-001 的表征测试在 T-002 与 T-003 后不改断言而通过，作为 AC-011 的证据。
- 最终：完整 `dotnet test Server/86JP.Server.slnx`（AC-014），随后由审查阶段对照 Spec 独立审查整体改动，再做完成验证。

## Next Planning Boundary

下一个单元是 T-001：先盘点现有测试对 11 条路径的覆盖（协议帧与收件人、RQ-008 各项副作用），再决定需要补哪些表征测试。T-002 的替身 API 细节，要等 T-001 确认测试中怎样构造多人副本与离开场景后再定；T-003 是否再细分为“领域内部”和“调用方顺序”两个 Task，视 T-002 后的测试改动面再定。
