# Routing Decision

任务：`entries-are-what-the-client-reads`
契约：`./TaskContract.md`（revision 1, state ready, SC-1..SC-8）

## SDD Readiness

**就绪。** 三件必要的东西都在手：

- **一手证据**：`vmp1-9.md` 第三节的字段表由另一个 agent 从客户端**解密后的调试字符串**
  逐字段回绑得出，是「客户端把哪个偏移当什么」目前唯一的一手来源。不是推测。
- **可执行判据**：全量套件在 `0dd8d630` 实测 2250/2/0 退出码 0；入场序列另有逐字节的字节锚
  `SelectCharacterAcceptedTranscriptTests`，任何非授权的字节变化会被它当场挡下。
- **实机回路**：改完可以真的连客户端验证（本轮已多次往返），不必只靠判据。

边界也是清楚的：装扮栏那条线的根因已经量到与本轮无关（不同的崩溃码、不同的调用链、
与记录内容无关），所以「哪些属于本轮」不是靠猜划出来的。

## Marginal Control Value

值得上 SDD，理由是**这次改动的错误代价不对称**：

- 改错的下场不是判据变红，而是**每一个连上来的客户端在进入游戏时崩溃**。本轮全程就是在
  为这件事做实机取证。判据全绿并不能证明没错——参照会话从来没发过带非零 `+0x2F` 计数的物品，
  所以现有用例根本走不到那条新路径上。
- 上一个成果正是在完整变更评审这一关被拦下：变化清单漏了 13 条新增生产拒绝，根因是
  **只从授权变化的起因往下游追、再加一次全量判据**，而全量判据全绿恰恰意味着没有用例
  走到那些新路径上。本轮的 SC-8 就是针对同一失败模式设的，它需要一次**独立的反向扫描**，
  这正是 SDD 的评审阶段能给而临场自查给不了的。
- 这次还有一个刚发生过的具体教训：准备阶段另一个 agent 在同一个主检出上按错误理解改了
  两个文件、判据一度红 5 条。独立任务 worktree 不是形式，是这次真的需要的隔离。

## Structural Selection

**Single Spec。** 三件事——定长化、夹紧计数、修记载——共享**同一个验收口径**：
「正常数据上逐值不变，唯二被授权的字节变化是时装尾块与计数夹紧」。按本仓上一轮根图立下的
规矩「各有独立的验收口径，才算不同成果；同一口径下的三段工作量属于一个成果」，它们是一件。

不是 Multi Spec：没有第二个互斥的验收口径。装扮栏那件确实有独立口径（它必须改变可观察行为），
但它**不在本轮范围内**，而且被外部依赖（另一个 agent 的反汇编）阻塞，不能现在建成子成果。

不是 Small：见上一节，代价不对称且需要独立反向评审。

## Controller Selection

**选定：`sdd-lite` / Profile `code-bugfix`。**

### 真正在保护什么

本轮的可信失败路径只有一条，而且它是**遗漏**而不是**做错**：

> `+0x2F` 的夹紧是一条**现有用例走不到**的新路径——参照会话从未发过带非零 `+0x2F` 计数的
> 物品。所以「全量判据全绿」对这条路径**什么都没证明**。上一个成果正是这样漏掉 13 条新增
> 生产拒绝，被完整变更评审拦下。

能挡住它的是两样：**一份把验收边界钉死的持久 Spec**（说清夹紧的语义、上界的依据、
时装珠宝数据的去向），加**一次对完整结果的评审**（含从代码出发的反向扫描，而不是核对条目）。
Lite 恰好就是这两样：spec → implementation → review → verification。

### 为什么更重的 Standard 不对

Standard 的独有控制是 `plan.md`——把有后果的共享决策、依赖顺序、跨会话排程提前解决。
本轮找不到能挂上去的东西：

- **夹紧上界取多少**（`0x0D` 给 10 dword、`0x0E` 给 49、记录余量给 13）确实是个有后果的
  决策，但它是**验收问题不是实施问题**——它属于 Spec 的「写出的值恒 `<=` 某界」，Spec 阶段
  就要定死，`plan.md` 加不上东西。契约的 Requires Confirmation 已经把「两个处理器取不到
  同一个值」设成停止点。
- **时装珠宝数据写不写**（SC-4）同样是验收分支，取决于本轮能不能取得证据，也在 Spec 里定。
- **没有跨层的顺序依赖**：生产改动集中在一个方法，判据与记载跟着它走。
- 「文件多、条目多、看起来重要」按选择规则明确**不构成**选 Standard 的理由。

### 为什么更轻的一档不对

比 Lite 更轻的做法是不留持久 Spec、靠一次确定性检查收口。这里不行：本轮**没有**一个便宜的
确定性检查能替代验收边界。判据全绿正是本轮那条失败路径的伪装色；能证伪的只有
「拿掉夹紧就会红」的变异验证和一次独立的反向扫描，两者都要先有写下来的验收条款才能对着做。

### 为什么不是 Governed

Governed 的硬性门槛（人身或系统安全、凭据与访问控制、隐私与受保护数据、财务法务合规、
不可逆的外部变更、无已证恢复手段的持久数据丢失）**一条都不沾**。本轮最坏的后果是
**客户端崩溃**——严重，但可逆：改动全部在本地未推送的任务分支上，回滚有证。
而且「独立挑战」这项控制在本仓的历史里已被证明**不是必需的**：上一个成果的 13 条遗漏
正是被**普通的完整变更评审**抓住的，说明这一档的评审强度对同一失败模式够用。
