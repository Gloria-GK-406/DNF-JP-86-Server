# TaskContract: 新物品期限与登录清理测试

## Context

Source Request：“新物品的过期时间未设定问题修复一下吧。然后历史物品的到期时间直接都定为昨天，我看看登录清理是不是正常。没问题吧？”

基准df570d87，task/next-round-20261013。运行0.2.5-scheduled-tasks.20261014+df570d87。已确认1123的马战礼盒490002925（固定日期）、勇者礼盒490003187（7天）、胶囊10100300（每日删除）实例ExpireTime=0。

## Goal

新创建限时物品按PVF生成正确的实例到期时间；让用户能用已持有的限时物品验证现有登录清理。

## Scope

- 固定日期、获得后N天、每日重置删除三种期限统一计算；永久物品保持永久。
- 新实例创建/发放及叠加前准备使用一致期限；既有物品移动、领取、分拆不重新续期，不改正确定制期限。
- 历史测试仅角色1123持有的限时物品（含已记录有效期限和PVF声明有限期但漏写期限），统一设为北京时间昨天的过去时刻。账号仓库、邮件和称号簿不做此次测试性改期。
- 备份数据库、列出目标和永久物品排除依据，只改期限字段，不直接删除。部署修复后保留目标供用户正常登录验证。
- 不接入六点清理任务、不迁移旧timer、不修改PVF旧活动日期、不改数据库结构、不改任务/马战玩法。

## Constraints

- 现有数据库和永久物品不得误删；数据操作需停服后核验数据库身份、完整性、备份及限定目标。
- 未知/非法期限不静默当永久或猜测删除；受影响物品报告并停止其改期。
- 同期限堆叠，不同期限不能合并导致续命或提前过期。
- 沿用当前工作分支；Tool/WireSmoke/__pycache__/保留，不纳入提交。

## Success Conditions

| ID | Outcome | Evidence |
|---|---|---|
| SC-1 | 三种期限正确生成，显式期限/永久物品保持语义 | 规则边界及真实PVF三种示例验证 |
| SC-2 | 发放、邮件、新建及堆叠保持期限且移动不续期 | 实际领域/SQLite回归和创建点审查 |
| SC-3 | 历史测试只改授权角色限时物品，无直接删除 | 改前清单、备份、改后字节差分和永久项不变 |
| SC-4 | 修复部署可用，登录清理仍统一读取实例期限 | 就绪/程序集身份/DB完整性与登录清理自动回归；实机由用户验证 |

| Capability | Evidence | Scope |

用户已回复“仅角色1123的限时物品”，范围已确定。日期为业务UTC+8；昨日具体时刻取昨日00:00即可证明已过期。已有永久哨兵不能仅因字段非零误判；只改有证据的限时物品。
