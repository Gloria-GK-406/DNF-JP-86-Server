# 物品发放期限

Before：客户端可读PVF期限，而服务端新实例常保留ExpireTime=0；旧登录清理因没有到期字段而跳过。
After：所有新建路径统一生成期限；投递前以最终期限选择可叠加对象，原实例移动不重新计算。

| ID | Requirement | Acceptance |
|---|---|---|
| RQ-001 | PVF期限解码为固定日期、N天、每日删除的只读定义 | AC-001：三种实际物品与非法值/永久声明读取测试 |
| RQ-002 | 缺省期限新实例以获得时刻计算，固定日期UTC+8、N天=N*86400、每日=PeriodStart(now)+1天，多约束取最早；正值显式期限保留 | AC-002：六点前/正点/后、跨年、永久、已有期限、绝对过去日期回归 |
| RQ-003 | 新实例与发放计划使用同一期限规则；堆叠必须期限相等；邮件/分拆保留原期限 | AC-003：实际投递/容器/邮件和SQLite测试，不仅验证辅助函数 |
| RQ-004 | 测试改期仅指定角色实际持有的有限期物品，只改期限，不删物品 | AC-004：备份/限定清单/逐字段差分/永久项未变、DB完整性；登录清理由用户实机验证 |
| RQ-005 | 原清理入口复用不分叉，本次无新增定时删除，运行版本可追溯 | AC-005：独立完整审查、回归和部署身份/就绪检查 |

Limits：不调整旧活动PVF，2016的马战礼盒新发仍然已过期；不承诺在截止瞬间在线删除。本次账户仓库/邮件/称号簿历史测试不改。永久物品的0或显式永久哨兵不能当过去时间删除。
