## 阻断项

### B1 闭环发包不补发：停顿期间少记了慢样本，p99 系统性偏低

- **缺陷**：`Agents.cs` 的 `PaceAsync` 写明 `No catch-up: ... resumes from now`；每条连接都是闭环（`RequestAsync` 要等回包或栅栏应答之后才返回）。服务端停顿 T 秒时，一条连接只留下 1 个慢样本。按目标速率，这条连接本应发出约 T×20 个包；同一连接上服务端按顺序处理，这些包也都会被拖慢。这些样本根本没有产生（coordinated omission）。延迟起点用的是实际发出时刻，不是计划发出时刻，所以这一缺口在任何数字里都看不出来。
- **证据**：A-1 的稳态窗里有多次 30 s 级停顿，实际速率只有 53.38 包/秒（目标 400）。但稳态「全部有回包请求」的 p99 是 **32.78 ms**，A-2 是 29.62 ms，都低于 RQ-091 (c) 的 50 ms 阈值。改造后所有入站包都进同一个执行器，执行器停顿时每条连接都只记 1 个样本。按 400 包/秒、120 s 约 48000 个样本计算，即使有一次 30 s 的全局停顿，也只多出约 20 个慢样本（0.04%），p99 不会变。对于 50–250 ms 的中等停顿，少记的倍数约为「停顿时长 × 每连接速率」（2–5 倍），足以把临界的 p99 从不达标翻成达标。`ramp` 的「p99 > 50 ms」规则同样建立在这个分布上，「实际速率 < 90%」只能兜住严重的停顿。
- **后果**：RQ-091 (c)(d)(e) 的 p99 判定和 (b) 的爬坡判定会系统性地偏向达标。改造后 (c) 的服务端入队等待也是由这个负载驱动的，同样会少记停顿期间本该入队的 CMD。
- **最小修正**：`PaceAsync` 保留计划时刻、不再重置为当前时刻，并另记「计划发出时刻 → 第一条回包」的延迟序列（标准的 coordinated-omission 校正）；或者把轻量包改成开环发送。README 写明 (c)(d)(e) 与爬坡用哪一个序列判定。在基线上至少把构成 B 再跑两次，让改造后有同口径的对照；A 可以只跑一次。

### B2 超时和被关闭的请求被当作「无回包」剔除，(f) 最长停顿和各分布的 max 偏小

- **缺陷**：`Sample.LatencyMs` 只对 `Replied` 的样本有值。`LatencyTable`、`steadyOverall`、(f) 的 `coldSamples`（筛选条件含 `s.Replied`）都把 `TimedOut`/`Closed` 却没有收到签名回包的请求排除在外，和 REQUEST_PEER 这种「协议上本来就没有回包」的请求混在同一个「无回包」计数里。RQ-090 的「没有回包的 CMD 不计入」指的是后一种，不是前一种。
- **证据**：统计 `final/baseline-1/samples.csv`：
  - 有 8 个 SELECT_CHARACTER 超时（等满工具的 60 s），2 个被关闭，另有 SELECT_DUNGEON、EPLP、CREATE_CHARACTER 超时或被关闭；
  - 其中 t=97.7 s 的 SELECT_CHARACTER（solo00）落在稳态窗 [60,180) 内，至少等了 60 s，但 baseline-1 的「稳态 SELECT_CHARACTER max」报的是 31064 ms；
  - 冷启动窗内有 2 个被关闭且无回包的请求（t=34.9 s 的 SELECT_CHARACTER、t=45.8 s 的 SELECT_DUNGEON），没有计入 (f)。
  
  B 两次没有这种情况，所以 B 的数字不受影响。
- **后果**：改造后一旦出现请求挂起或连接被关闭，(f)「最长单次停顿 ≤ 250 ms」和单类 max 仍可能显示达标。现在只有「错误」和「> 250 ms 请求」两个计数能看出来，而这两项并不在 RQ-091 的判定项里。
- **最小修正**：把超时或被关闭的请求作为截尾样本计入分布和 (f)，取值为「发出 → 关闭/超时」的时长，并标注为下界；也可以在每个分布旁并列「失败无回包」的计数和最大等待时长，并规定判定时一并考虑。「协议无回包」与「失败无回包」分开计数。A 的现有记录要注明 max 是截尾后的下界。不需要为此重跑 B。

### B3 出站字节最大值只在新建角色上测得，但被写成「最大」并定为 T-003 的下限

- **缺陷**：`outbound` 和负载里所有的选角，用的都是刚建好的 job 0 角色。选角序列里各帧的大小与角色数据有关：ITEM_LIST（NOTI 0x000D）是「头 5 字节 + 条目数 × 101 字节」，见 `protocol/game/server-to-client/NOTI-0x000D.md`。本次的 1520 B 正好是 5 + 15×101，也就是只有 15 个起始物品。背包、装扮栏、任务等都随游玩增长。
- **证据**：`outbound-frames.txt` 里首次选角最大的几帧：0x0164 30004 B、0x000D 1520 B、0x006C 808 B……；`baseline-summary.md` 的结论写的是「单条 CMD 对单个连接的最大出站字节是选角全序列，精确值 39376 B」，没有任何与数据相关的说明；主控方处置把「T-003 的发送队列上限取值不得低于 78854 B」带入后续 Task。
- **后果**：按 RQ-036，队列超过上限时会关闭连接。按 80 KB 定上限，一个背包较满的真实角色在选角时可能直接被断开，而合成负载和全部测试都测不到这种情况。
- **最小修正**：在 `baseline-summary.md`、`outbound.md` 的结论以及 Result、主控方处置中写明：39376 / 39427 B 是**新建角色的实测值**，选角出站量随容器条目数等数据增长，78854 B 只是下限的下限。同时给 T-003 带入一条约束：按容器容量上界推算选角出站量的上界，或者用一个容器装满的角色实测一次，再按 2 倍取下限。不需要在本 Task 内补测。

## 非阻断项

1. **爬坡时长请求被稀释，README 写的与实际不符。** README 说「速率靠每连接的目标速率提高，连接数与构成比例不变」。但双人组的组队/进本是按停留时间推进的，不随速率增加。`ramp-clean*.md` 每一档的「长请求样本」都是 5–6 个，从 400 档到 25000 档都一样；构成 B 在 2000 档时长请求只占约 0.017%。summary 对 B 已经写明，README 的这句话要改。另外，爬坡记录最好逐档写出实际构成。改造后用 A 判 (b) 时，单人的选角与跨区会随速率增长，双人组的进本不会。
2. **爬坡档末尾还在途的请求被漏掉。** `RampAsync` 在档结束时立即按 `Send ∈ [from,to)` 统计，而样本要在请求完成后才入队。档末尚未完成的请求（最慢的那批）既不计入本档，在下一档又被发出时刻过滤掉。修法是等在途请求收口后再统计，或者全部跑完后统一按档计算。
3. **(e) 灌包窗口固定为 32。** 改造后单执行器上，灌包连接在执行器队列里最多占 32 项，(e) 的结果直接取决于这个窗口大小。建议 M-2 再加跑一档更大或开环的灌包，并在记录里写明窗口大小对结论的影响。
4. **工具还测不到 (c) 入队等待。** README 说「改造后的 M-1/M-2 用同一命令行重跑，只换 `--host`」，但 (c) 需要解析执行器的入队/开始日志，工具目前没有这项功能，M-1 之前要补上。另外，改造后每个入站包都成为 CMD 并写开始/结束日志（RQ-054），Information 级控制台日志经管道输出，可能本身就成为被测瓶颈。日志配置应作为环境项记录。
5. **`DungeonFirst` 签名不比对 wire id。** 组队进本时请求者先后收到两条 519 B 的 NOTI 0x0002（`outbound-frames.txt` 第 688–689 行）。按 XO-1，第一条可能是队员的，README 写的「自己的完整 USERINFO」没有核实。两条通常在同一次读里到达，对计时影响很小，改一下说法即可。
6. **数字不一致。** Result 的 Checks 写「每次运行约 384 s」，而记录里的总时长是 321 / 274 s（host.log 跨度 A 约 323 s，B 约 276 s）。
7. **处置措辞有歧义。** 「A 中失败的命令、错误、> 250 ms 请求都应降到与 B 同一水平」：B 自身就有不达标项（(f) 573 ms、登录哈希命令 640 ms 级）。应明确判定依据是 RQ-091 的绝对阈值，「B 水平」只作诊断参照，避免把「与 B 持平」读成达标。
8. **长 CMD 单类样本量小。** SELECT_DUNGEON 稳态 35 个，多数命令只有几十个，p99 / p99.9 实际就是 max。工具抖动的结论只对聚合分布成立，不能推到单类长 CMD 上。summary 对命令时长已经说明，对单类端到端也应注明。
9. **端到端口径偏差。** RQ-090 写的是服务端口径「入站帧到达 → 第一条回包离开」，工具测的是客户端口径，多出两次本机回环和 TouchSocket 发送循环的时间，只会偏大。README 局限第 2、3 条已说明，可以接受。

## 已核实、不构成问题的项

- **30 s 停顿的归因**：
  - A 两次 host.log 各有 28 条 `database is locked`，B 两次为 0；
  - 失败栈落在 `SqliteItemDomainStoreSession.InsertAsync`，即事务的第一次写入，外层是 `TransactionalExecutionBehavior`，与「先读后写、在门内等满 30 s」的形态一致；
  - 失败命令开始约 4 s 后，日志里紧挨着出现 `SetUserAreaHandler` 的跨区记录（baseline-1 第 690–692 行）；
  - `TransactionalExecutionGate` 确认是 `SemaphoreSlim(1,1)`，`CharacterStateAccess.AloneAsync` 与 `CreatureRuntimeDomainService` 也确认在门外自开事务提交。
  
  环境方面的解释可以排除：
  - 各次运行先后进行，没有重叠（各 host.log 的起止时间见 scratchpad `final/*/host.log`）；
  - 每次运行用独立的临时目录和数据库；
  - 同一台机器、同一块磁盘、同一个工具下 B 没有停顿；
  - 环境探测在 t=60 s 才执行，而第一次停顿始于 t≈4 s。
  
  入口清单「不保证完整」也已如实标注，例如 Reliable 订阅消费方之类的门外写入口没有列出，但这属于 T-004 判据要覆盖的范围，不阻断本 Task。
- **SQLite `synchronous` 的取法**：服务端不设置这项 PRAGMA；工具用同样形式的连接串读取，两份原生库的 SHA-256 一致，compile_options 中 `DEFAULT_SYNCHRONOUS=2`、`DEFAULT_WAL_SYNCHRONOUS=2`，足以代表服务端。环境记录包含机器、磁盘（APFS/SSD、临时目录所在卷）、构建配置、SQLite 版本、journal_mode 与 synchronous，是完整的。
- **百分位**：采用 nearest-rank，实现正确。聚合样本（B 稳态约 4.7 万个）足以支撑 p99.9。
- **78854 B 的算术**：2 × 39427 = 78854，正确（口径问题见 B3）。浮动帧 0x0015 可能不在窗口内，已如实列入缺口。
- **抖动说明**：B 两次的 p50/p99 差 ≤ 0.02 ms，p99.9 为 27.89 对 27.39（约 1.8%），(f) 为 573.3 对 567.5，(d)(e) 的 p99 相同，与 raw JSON 一致。说 A 的差异来自停顿落在哪一秒、不是工具抖动，这个结论成立。
- **资源与并发**：每连接一条接收线程，Dispose 时随之结束；Host 退出时整树 kill 并删除临时目录；统计用 ConcurrentQueue 和 Interlocked；计时一律用 `Stopwatch`。没有发现泄漏或竞态导致的统计错误（爬坡档末尾的问题见非阻断第 2 条）。
