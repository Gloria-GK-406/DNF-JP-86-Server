# TaskContract: 玩法执行改为单执行器、协议级 CMD 与提交后发件箱

## Context

### Source Request

本会话按 issue 逐个重构，全部在分支 `task/refactor-session-20261021` 上完成后一次性推送。轮到 #182（「自取会话租约泛滥：56 个 Protocol 文件引用 SelectedSessionTransitionGate」）时，用户拿来台服 70 的 `df_game_r` 让 Agent 看原版怎么加锁，说：“说不定游戏本身不需要这么细粒度的锁呢……这探索结果可能会改变我们的一些结论”。

Agent 的静态分析结论：原版每个频道一个进程，游戏逻辑只有一个分发线程，按队列顺序处理客户端包、定时器和数据库回包；625 个包处理器内部不加业务锁；数据库线程也是逐条处理自己的队列；逻辑线程从不等待 I/O。据此，Agent 把本仓的锁按时序分了段，指出每次请求最多要过 8 道门，并且事务型命令早就被一个全进程单名额信号量串行化了。

随后用户依次提出，并与 Agent 对齐了以下方向：

- “那么也就是说必须要命令级的有序才能解决问题？……CMDExecutor。push CMD（CMD）这样的模式……CMD内部再根据channel做分流。”
- “不，这里的CMD直接把其他的都吸收了。命令变成唯一实体。不过这里的命令含义就是以协议为单位的了。要改的估计怕是很大。……早期的架构设计有点随意了。现在要还债了”
- “那Event后的NOTI以及CMD后的NOTI部分要怎么处理？Event组件应该是不能拆掉的。NOTI必然有两个源。要么就监听后再转CMD投递。完成全CMD的流程，就可以把投递NOTI也归拢到一起。”
- “那应该就要有CMD深度计数，不过这里无限连锁应该是程序设计错误，所以记录错误后直接掉线应该是正确处理流程。同时日志里记录CMD调用链信息。这样大部分锁都可以扔了？以及CMD处理链里的那个全局锁，个人锁什么的。”

期间用户还问过：“这里我有个疑问，就是直接上新的mysql的话，早期的这种内存缓存类似redis的东西还有多少意义？”Agent 的回答是：易失状态放内存，持久数据保持直接落库，单执行器配进程内 SQLite 最合适。用户没有再坚持换库。

用户的授权原话：“看着没问题了，模型也简化了很多。不过这个改动比较危险，走gov的sdd路线吧。写之前最好派子代理把相关信息都收集清楚。完成spec和plan的编写和验收后等待。我compact一下再开始执行。靠你了，opus”

### Current Situation

基准 `a02bce46`（#185 已封存）。五份现状调研在 `research/` 下（01 入口、02 处理器与命令、03 投递、04 锁与持久化、05 测试），要点如下：

- **执行模型**：同一连接的收包逐包 `await`，跨连接并发。每条消息开一个 DI scope，handler 在命令总线外编排；每次 `SendAsync` 又开一个 scope 走 8 层管线：0 日志、45 会话门共享借用、50 在线用户门、55 账号门、57 全局单名额事务门、58 结算检查、60 SQLite 工作单元、100 策略。
- **规模**：141 个 `ClientMessageHandler`，204 个命令处理器（Transactional 170、Direct 21、ReadOnly 9、Workflow 4）。23 个文件一次发多条命令；选角一条消息要发 15 条命令，且每段各有一个事务。
- **锁**：协议层约 105 处手写取门，涉及会话门、6 种投影/入场门、称号投影门（64 路信号量）、队伍按角色信号量与按代际的流门。另有在线用户门、账号门，以及被管线、事件分发器和自开边界的领域服务共用的全局事务门；应用层还有 190 处短 `lock(sync)`。
- **命令总线外的入口**：连接建立与断开、关连接后另一条流上的清理、登录会话维护、33 个后台服务（其中 5 个调度任务用 `Task.Run` 最多并发 4 个）、52 个事件订阅（Reliable 17、LiveOnly 22、Direct 13）、GM 的 Cera 提醒、效果账本重放、卡牌翻牌的延时 fire-and-forget、房间机制维护直改运行态、婚礼调度直改城镇区域等。这些入口有的改状态，有的写库，有的直接发包。
- **投递**：约 221 处按连接直发，92 处 `ProjectAsync`。约 15 处读取投递结果做业务决定，例如队伍 revision 水位线、每日配额「已送」标记、GM 未确认提示。另有十几处靠同步发送异常触发补偿、回滚、隔离或关连接，例如选角、进本、两塔、怪物死亡、清算。每收件人有 2 秒期限，失败进重试队列。handler 抛异常会导致断线。
- **判据**：命令处理器只能注入 `*DomainService` / `*DomainStore`（`CommandHandlerArchitectureTests`），这与「协议级 CMD 吸收投递」正面冲突。效果结算名单、物品槽位边界、嵌套 dispatch 禁令等判据也会受影响。
- **测试**：7872 个用例。20 个假总线直接 new handler；46 个发送替身采用「发送即记录」模型；有专门测门、测并发交错、测投递期限的用例。线级集成测试、codec 向量、选角 62 帧金样本可以原样作为「行为不变」的证据。

## Goal

服务端的玩法执行只有一个串行单位，就是**进程内唯一执行器上的一条 CMD**。所有会改游戏状态、写库或发出 NOTI 的工作，都从同一个入队点进入，按先进先出逐条完整执行：
- 一个入站协议对应一条 CMD；
- 定时器触发、领域事件消费、连接生命周期事件、GM 与 HTTP 写操作，也各自是一条 CMD。

CMD 产生的消息全部先进本条 CMD 的发件箱，执行完成、相关事务提交之后，才刷进每连接的发送队列。执行器不等待网络发送。

因此，玩法路径上不再需要按账号、在线用户、区域、副本局、塔局、角色取锁，也不需要「锁内复查、不一致就重试」。

除经审查的 Spec 逐条列出的有意变化外，协议行为、落线顺序与持久化结果不变。

## Scope

### In

- **执行器与唯一入队点**：一个进程内执行器，先进先出、单消费者，承载全部频道；分流键预留成一个函数，今天固定返回同一个执行器。执行器上的工作不等待网络发送。
- **重计算与背压**：
  - 不能让 CPU 密集的计算拖住整个执行器，例如口令哈希（PBKDF2，22 万次迭代）。这类计算在执行器外完成，结果再作为 CMD 进入执行器。
  - 单个连接或未认证的请求不能无限灌入队列。今天每条连接逐包等待，天然带有背压；新模型要有等价的背压或上限。
- **全部入口改为 CMD 入队**：
  - 入站协议；
  - 连接建立与断开，以及关连接引起的清理；
  - 登录会话维护；
  - 全部后台与调度服务；
  - 领域事件消费，包括 Reliable、LiveOnly 与重试；
  - GM 与 HTTP 写操作；
  - 延时计时器、效果账本重放、房间机制推进等今天在命令总线外改状态或发包的流程。
  
  启动期在开始监听前完成的一次性迁移和初始化，可以留在执行器外，但要逐项列明。
- **协议级 CMD**：
  - handler 只做解包与入队；
  - 具名判定、领域调用、多段提交、投递、补偿都并入该协议的 CMD；
  - CMD 之间共享的逻辑放进领域服务或应用服务；
  - 今天的细粒度命令按需要并入、改成应用服务或删除。
- **提交后发件箱与每连接发送队列**：
  - 统一今天两种来源的 NOTI：命令后的直接投递与事件后的投影；
  - 只刷出已提交的结果，保持单连接内的顺序，以及今天依赖的批次与必达语义；
  - 发送失败按逐目标隔离处理；
  - 跨连接顺序要求今天由代码保证的，要有等价保证，例如进本时跟随者先于领队、离开副本时同伴先于领队 ACK。
- **依赖投递结果或同步发送异常的行为**（关连接、隔离、补偿、回滚、已送标记、revision 水位线、未确认提示等）：逐项给出新的承接方式，并保住各自的保护意图。
- **CMD 调用链与深度上限**：每条 CMD 带根、父、深度。超限时：
  - 不再入队该链后续的 CMD，记一条带完整调用链的错误日志；
  - 链源头是客户端连接的，断开该连接；
  - 没有连接的链只记错误；
  - Reliable delivery 标为死信，不再重试。
  
  日志带调用链信息。
- **删除玩法路径上的锁**：
  - 会话门（含借用机制与 `LeaseSet` 类变体）、各投影门与入场门、称号投影门、队伍按角色信号量与流门；
  - 在线用户门、账号门、全局事务门，及其管线行为；
  - 「锁内复查、重试」循环；
  - 多账号排序加锁与相关声明。
  
  执行器外仍要访问的共享结构，按需保留或改为执行器内访问，并逐项说明。
- **保留并迁移**：
  - SQLite 事务（每段工作单元）；
  - #185 的具名判定；
  - 事务结果不确定时的会话隔离；
  - 登录被顶替的权威检查；
  - 效果账本的一请求一主结算约束；
  - 事件组件（事实记录、订阅登记、可靠性）。
- **判据**：
  - 「改状态、写库、发 NOTI 只在执行器上进行」的机器判据；
  - 「handler 只解包入队」「协议级 CMD 注入面」的判据，替换或重写今天冲突的判据；
  - 每条判据配一条证明它会拒绝的反例用例。
- **测试**：
  - 改写或替换受影响的测试，包括假总线、发送即记录的替身、门与并发交错测试、投递期限测试；
  - 新增执行器、发件箱、深度上限、入口覆盖的测试；
  - 用线级集成测试、codec 向量、选角金样本等证明行为不变；
  - 选角工作流补上经真实连接、覆盖整个序列的端到端证据，因为现有金样本不经过工作流。
- **吞吐与延迟测量**：给出执行器下命令耗时与吞吐的实测数字，并写明口径。
- **文档**：更新 `AGENTS.md`、`Docs/Agent/ArchitecturePhilosophy.md` 等描述执行模型、管线、handler 规则、投递与锁的文档。今天已过时的管线描述一并改正。

### Out

- 不按频道拆分执行器（只预留分流键）。
- 不删除短 `lock(sync)` 与 PVF 内容缓存的锁；它们的后续删除另行处理。
- 不改持久化模型：不引入内存权威副本或定时存档，不换数据库引擎，不改表结构。
- 不改协议字段、编码与客户端。
- 不处理 #209（写操作按数据库再查归属）与 #210（城镇区域租约区分）。
- 不合并、推送、开 PR，也不改动远端 issue；版本号按 AGENTS.md 在分支收尾时统一递增。

## Constraints

- **顺序保证没有例外**：
  - 任何会改游戏状态、写库或发 NOTI 的路径，都不得绕过执行器。
  - 执行器上的工作不得等待网络发送。
  - 执行器上的工作不得把 CMD 放进同一个执行器后等待它完成。
  - 由机器判据守住。
- **保住保护意图**：今天靠锁、复查、同步发送异常、投递结果实现的每一项保护，都要有新的承接方式和测试证据，不得静默消失。保护包括：不交错、不重复结算、失败时隔离或关连接、补偿、回滚、只在送达后推进状态。
- **可见行为变化须列明**：落线顺序、回包有无、断线时机、提示文字等客户端或 GM 能看到的变化，在 Spec 中逐条列出理由，并在最终汇报里说明。
- **纯搬迁与语义改动分开提交**；「行为不变」要有能失败的证据（依据 `Docs/Agent/RefactorPreferences.md` §3）。
- **一次到位、删净**：不留旧门、旧管线行为、转发层或 `[Obsolete]`。
- **单数据库写者**：迁移期间及之后，任何执行器外仍可能写 SQLite 的路径都要列明并说明为什么安全，避免「先读后写等满 30 秒」重新出现。
