## Goal

服务端的玩法执行只有一个串行单位，就是**进程内唯一执行器上的一条 CMD**。所有会改游戏状态、写库或发出 NOTI 的工作，都从同一个入队点进入，按先进先出逐条完整执行：
- 一个入站协议对应一条 CMD；
- 定时器触发、领域事件消费、连接生命周期事件、GM 与 HTTP 写操作，也各自是一条 CMD。

CMD 产生的消息全部先进本条 CMD 的发件箱，执行完成、相关事务提交之后，才刷进每连接的发送队列。执行器不等待网络发送。

因此，玩法路径上不再需要按账号、在线用户、区域、副本局、塔局、角色取锁，也不需要「锁内复查、不一致就重试」。

除经审查的 Spec 逐条列出的有意变化外，协议行为、落线顺序与持久化结果不变。

这个目标分两个结果交付，先 A 后 B，各自独立验收：

- **结果 A：单执行器、提交后发件箱与删锁。** 执行层面上，CMD 落为执行器上的一个作业：每个入口（一个入站协议消息、一次定时触发、一次事件消费、一次连接生命周期事件、一次 GM／HTTP 写操作）对应一个作业。出站消息先进发件箱，提交后才刷出；玩法路径上的门、信号量与重试循环已经删除；调用链与深度上限贯通全部来源。A 封存时，handler 在作业内编排细粒度命令的写法仍在，过渡机制也仍在：`ICommandBus.SendAsync` 在执行器上内联执行、请求级帧以 AsyncLocal 在作业内设置、细粒度命令及其管线。这些都逐项列明（SC-12），作为结果 B 的输入。
- **结果 B：协议级 CMD。** 编程模型上，命令成为唯一实体，以协议为单位：handler 只解包入队；具名判定、领域调用、多段提交、投递、补偿并入该协议的 CMD；细粒度命令并入、改成应用服务或删除；请求级上下文成为 CMD 的显式数据。结果 A 列明的过渡机制在 B 中删净。B 以 A 封存后的提交状态为起点。

## Scope

### In — 结果 A

- **执行器与唯一入队点**：一个进程内执行器，先进先出、单消费者，承载全部频道；分流键预留成一个函数，今天固定返回同一个执行器。执行器上的工作不等待网络发送。
- **重计算与背压**：
  - 不能让 CPU 密集的计算拖住整个执行器，例如口令哈希（PBKDF2，22 万次迭代）。这类计算在执行器外完成，结果再作为 CMD 进入执行器。
  - 单个连接或未认证的请求不能无限灌入队列。今天每条连接逐包等待，天然带有背压；新模型要有等价的背压或上限。
- **全部入口改为 CMD 入队**（在 A 中，每个入口是执行器上的一个作业）：
  - 入站协议；
  - 连接建立与断开，以及关连接引起的清理；
  - 登录会话维护；
  - 全部后台与调度服务；
  - 领域事件消费，包括 Reliable、LiveOnly 与重试；
  - GM 与 HTTP 写操作；
  - 延时计时器、效果账本重放、房间机制推进等今天在命令总线外改状态或发包的流程。

  启动期在开始监听前完成的一次性迁移和初始化，可以留在执行器外，但要逐项列明。
- **提交后发件箱与每连接发送队列**：
  - 统一今天两种来源的 NOTI：命令后的直接投递与事件后的投影；
  - 只刷出已提交的结果，保持单连接内的顺序，以及今天依赖的批次与必达语义；
  - 发送失败按逐目标隔离处理；
  - 跨连接顺序要求今天由代码保证的，要有等价保证，例如进本时跟随者先于领队、离开副本时同伴先于领队 ACK。
- **依赖投递结果或同步发送异常的行为**（关连接、隔离、补偿、回滚、已送标记、revision 水位线、未确认提示等）：逐项给出新的承接方式，并保住各自的保护意图。
- **CMD 调用链与深度上限**：每条 CMD 带根、父、深度。超限时：
  - 不再入队该链后续的 CMD，记一条带完整调用链的错误日志；
  - 链源头是客户端连接的，断开该连接；
  - 没有连接的链只记错误；
  - Reliable delivery 标为死信，不再重试。

  日志带调用链信息。
- **删除玩法路径上的锁**：
  - 会话门（含借用机制与 `LeaseSet` 类变体）、各投影门与入场门、称号投影门、队伍按角色信号量与流门；
  - 在线用户门、账号门、全局事务门，及其管线行为；
  - 「锁内复查、重试」循环；
  - 多账号排序加锁与相关声明。

  执行器外仍要访问的共享结构，按需保留或改为执行器内访问，并逐项说明。
- **保留**（在今天的位置原样保留，由既有测试守着）：
  - SQLite 事务（每段工作单元；提交点默认不合并、不拆分，A 期间若有合并或拆分，逐条列出理由）；
  - #185 的具名判定；
  - 事务结果不确定时的会话隔离；
  - 登录被顶替的权威检查；
  - 效果账本的一请求一主结算约束；
  - 事件组件（事实记录、订阅登记、可靠性）。
- **判据**：

## Constraints

- **顺序保证没有例外**：
  - 任何会改游戏状态、写库或发 NOTI 的路径，都不得绕过执行器。
  - 执行器上的工作不得等待网络发送。
  - 执行器上的工作不得把 CMD 放进同一个执行器后等待它完成。
  - 由机器判据守住。A 建立这些判据，B 不得削弱。
- **保住保护意图**：今天靠锁、复查、同步发送异常、投递结果实现的每一项保护，都要有新的承接方式和测试证据，不得静默消失。保护包括：不交错、不重复结算、失败时隔离或关连接、补偿、回滚、只在送达后推进状态。A 与 B 各自对自己改动所涉及的保护负责。
- **可见行为变化须列明**：落线顺序、回包有无、断线时机、提示文字等客户端或 GM 能看到的变化，在各自的 Spec 中逐条列出理由，并在各自的最终汇报里说明。
- **纯搬迁与语义改动分开提交**；「行为不变」要有能失败的证据（依据 `Docs/Agent/RefactorPreferences.md` §3）。
- **一次到位、删净**：每个结果在自己的边界内删净，不留旧门、旧管线行为、转发层或 `[Obsolete]`。A 封存时仍在的过渡机制必须逐项列明（SC-12），由 B 删除；B 封存后一项不留。
- **单数据库写者**：迁移期间及之后，任何执行器外仍可能写 SQLite 的路径都要列明并说明为什么安全，避免「先读后写等满 30 秒」重新出现。
- **先 A 后 B**：B 只在 A 封存之后开始，以 A 的提交状态为起点，不等外部审核；A 的验收不以 B 的任何工作为前提。A 封存之后不重开。
