## Detailed Plan

1. **事件图**：
   - 节点有三类：事件类型、订阅、源头；源头指入站或定时 CMD，以及关连接。
   - 边分四类：
     - 「事件 → 订阅」：从组合根中 `IEventService` 的订阅注册（`ProtocolModule`、`ApplicationModule` 等）收集；
     - 「订阅 → 事件」：读每个订阅处理器，以及它直接调用的领域服务，找其中发布的事件类型；
     - 「源头 → 首个事件」：收集哪些命令处理器或领域服务发布了该事件，归并为「入站 / 定时 / GM / HTTP」源头，只需证明存在；
     - 「关连接 → 生命周期 → 事件」：这是拆除路径上发布的事件。
   - Direct 订阅在调用方的 CMD 内执行，不构成新的 CMD，但其中发布的 `EnqueueAsync` 仍要沿边继续算。
   - 用一个一次性脚本或手工表求最长路径，路径长度按 CMD 个数计。检查图中是否有环；有环就是一项发现，要单独报告。
2. **结果**：在附录 A 末尾加一张表，列出最长链：每一跳的 CMD 类型、来源种类和代码位置，最后写出长度 L。按 RQ-052 给出常量下限 `max(2L, 8)`。
3. **附录 D**：
   - 在 `Server/src` 中检索英文注释和名称：`before the leader`、`Peers`、`must precede`、`ordering`、`first`、`then`、`after the`。
   - 再查 `GameExplicitMessageDelivery` 与 `SendBatchAsync` 的所有多收件人调用点，看其中有没有依赖先后顺序的写法。
   - 逐项判定。新项按 XO-n 编号补入附录 D，注明今天的位置，以及今天有没有测试守着。
