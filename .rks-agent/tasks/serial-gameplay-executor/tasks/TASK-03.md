2. **负载构成（合成）**：
   - 若干个虚拟玩家，每人依次执行：登录 → 建角 →（首次）选角 → 循环若干次「城镇移动、栅栏包 0x04DD 等轻量包，按固定比例穿插组队、进本、离本、离队、回选角、再选角」。
   - 比例和目标速率可以配置。默认值要让整体包速率在 400 包/秒附近，并且让选角、建角、进本这类长 CMD 的比例不为零。
   - 构成表写进记录。
3. **测量**：
   - 客户端为每个请求记录发出时间和第一条回包的到达时间，按请求类型聚合。只计「有回包的请求」，没有回包的另外计数（RQ-090 的注明项）。
   - 服务端命令时长：Host 以 Information 级别输出 `CommandLoggingBehavior` 的日志，工具在跑完后解析，按命令类型聚合。
   - 吞吐：逐步提高目标速率，直到 p99 端到端延迟超过 50 ms 或者出现错误，取此前的最高稳定速率作为「可持续吞吐」，并写明判定规则。
4. **场景 (d)(e)(f)**：
   - (d)：在 400 包/秒的背景负载下，同时发起 10 个登录，比较其他请求延迟的 p99；
   - (e)：一个连接以最高速率持续灌入轻量包，比较其余连接延迟的 p99；
   - (f)：Host 刚就绪时直接施加负载，记录前 60 秒每秒的 p99 和最长单次停顿。最长停顿定义为客户端看到的最大单请求延迟。
5. **最大出站字节**：按 Required check 3 统计。另外单独跑一次 TASK-01 的选角与组队进本序列，取精确值，作为 T-003 定发送队列上限的依据。
6. **记录**：
   - `verification/measurement/README.md`：口径、命令行、负载构成、环境；
   - `verification/measurement/baseline-<n>.md`：基线数字；
   - 原始数据存为 CSV 或 JSON，体积过大时只存聚合结果。
   - 与 RQ-091 阈值的对照写在基线记录的末尾。基线上，命令执行时长若有 p99.9 超过 100 ms 或 max 超过 250 ms 的，逐项列出，作为 M-1 的预警。

### Why

- **R2-B1**：领队和队员是两个玩家，基线上两条连接并行处理。共用一张节拍表时，领队在事务门后等待的时间会算进队员的样本。改成每连接一张表之后：
  - 队员在领队那一步等待期间照常发自己的包；
  - 组队、进本这类步骤算在发起它的领队连接上；
  - 队员的配合包不带节拍，它等领队的时间不进它自己的判定样本，与主控方处置一致。
- **A 的 (d) 不作对照**：A 从冷启动起就积压到停止，19200 个节拍未能发出，(d) 窗口反映的是之前的积压。
