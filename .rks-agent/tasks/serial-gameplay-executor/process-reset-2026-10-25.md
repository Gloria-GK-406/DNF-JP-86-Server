## 2. 证据规则（已由 `.gitignore` 执行）

**进 git 的只有人写的记录**：Task 文件、评审、Spec／Plan、迁移账（`migration-ledger.json` 和 `migration-baseline.json`）、探针工具脚本、测量摘要，以及证据目录里的 Markdown 摘要。

**不进 git**：
- `verification/evidence/` 与 `verification/logs/` 下的一切非 Markdown 文件；
- `*.trx`。

本目录的 `.gitignore` 会挡住这些文件。这类文件照常写在原来的目录里，它们只留在本机。

另外三条规则，`.gitignore` 管不到：

- **不复制文件当证据。** 要引用某份文件的旧版，写「路径 @ 提交号」，git 自己就能给出。不再存逐字节快照（例如 `spec-b5-before.md`、`plan-p6-before.md` 这类）。
- **不写字节数／SHA256 身份表。** 文件身份用提交号表示。原始证据需要指认时，写本机路径和一句结论，必要时给一个哈希，不要列表。
- **取证的正式形式是测试。** 旧行为要「钉住」，就在正式测试里写表征或回归用例，先在旧代码上跑出预期结果，迁移后再跑一次。用例留在仓库里，以后还能守住行为，这比一次性的 JSON 矩阵有价值。只有测试表达不了的东西，才用一次性探针；探针跑完，结论写进 Result，原始输出留在本机。

## 3. 每个 Task 的流程

每个 Task 由一个执行 agent 完成，再交给一个独立快审，一共两次 agent 调用；有返工时，再加一次复核。

1. **开工核对（主控，三句话）。** 写进 Task 文件开头：本 Task 承接 Plan 哪一行、迁移账里哪几行，上一 Task 留下了什么。这就是 on-drift 要求的简短目标核对；没发现偏离，就不做回顾性审查。
2. **合同和详细计划（一页以内）。** 写清楚：
   - 迁哪些消息和命令；
   - 用哪些测试钉住旧行为（新写的，或已有的）；
   - 有没有有意的行为变化（见 §4）；
   - 是纯搬迁还是语义改动。
3. **先钉旧行为。** 在旧代码上补齐表征或回归用例，并跑出预期结果：保持行为的用例应当是绿的，要修的缺陷用例应当是红的。
4. **迁移。** 根契约要求纯搬迁与语义改动分开提交。一个 Task 里两样都有时，分成两个提交；分不开的，就在 Result 里写明哪些改动不可分、为什么不可分。
5. **检查。**
   - 每个 Task：跑受影响的测试项目全部用例，再加上本 Task 的聚焦用例。
   - 每个功能簇收尾（Plan 的一行完成）：跑一次 8 项目正式全量。
   - 全量照旧加 `--logger "console;verbosity=detailed"` 和 `DFO_GAMEPLAY_ASSERTIONS`，日志落在 `verification/logs/`，只留本机。
6. **写 Result（一页以内）。** 只写四样：交付了什么、为什么这样选（只写非常规的选择）、检查结果（命令、通过数、失败数和失败身份）、遗留事项。
7. **独立快审。** 用 `reviewing-work` 做一次 Task 结果快审，评审文件一页以内，结论放在最前面。**不再给每个 Task 或每次修订生成对抗挑战。**
8. **提交。** 提交标题用 `serial-gameplay-executor: spec-002 TASK-NN <一句话>`，迁移账的更新与 Task 一起提交。署名行写实际完成提交的 agent，不冒用别人的署名。

**取消「只取证的 Task」。** 取证合并进迁移 Task 的第 3 步。

## 4. Spec 和 Plan 什么时候才改

- **保持原行为的迁移，不改 Spec，也不改 Plan。** 这是剩余工作的绝大多数情况。
- **有意的可见行为变化**（例如 B6 里租装备背包满时，改为回结果码 2）：在 Spec 的有意变化表里追加一行，写清楚协议、旧行为、新行为、理由和守护它的测试，随这个 Task 的结果快审一起审。不另做 Spec 修订，不做挑战。
- **正式修订 Spec**：只在要改变 RQ／AC 的验收边界、根契约约束或中心方案时才做。修订只做一次独立评审，不做对抗挑战。需要改根契约时，先停下来问用户。
- **修订 Plan**：只在功能簇的顺序或跨簇共享契约变化时才做。Task 的细节写在 Task 文件里，不回写 Plan。
- **对抗挑战只做一次**：在 spec-002 全部完成后，做完整结果评审时做（T-012 之后，封存之前）。

这是主控方对 spec-002 执行配置的调整，已记入 `attempts/spec-002-protocol-level-cmd/routing-decision.md` 末节。controller 和 profile 不变，变的只是各个门在什么时候触发。
