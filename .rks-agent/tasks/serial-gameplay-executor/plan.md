# Implementation Plan: 玩法执行改为单执行器、协议级 CMD 与提交后发件箱

## Planning Choice

选择 high-level Plan + Task Units。理由：
- 工作量跨越多次会话和 compact；
- 后面各步的细节取决于前面的结果。例如协议级 CMD 的归并方式，要等执行器接入、删锁之后才看得清；附录 C 的工作单元对照，要边改边填；
- Profile 要求按需的偏离复盘。

本 Plan 只定路线、共享决定、依赖顺序和覆盖关系；每个 Task 的细节在它临近执行时才写。

## Approach and Shared Decisions

### 路线：先装执行器、全部入口迁入，再删锁，再换投递，最后归并成协议级 CMD

每一步结束时，构建与全量测试都是绿的，系统可以运行。

1. **钉行为**：在基线上补齐表征测试，记录基线日志。
2. **建零件**：执行器、调用链、发件箱、发送端，作为独立组件，先不接线。
3. **纯搬迁**：全部入口迁入执行器。每个入口的现有逻辑原样作为执行器上的一个作业运行，行为不变。这一步之后，所有改状态的工作都已串行，门全部变成无人争用的。
4. **删锁**：删掉门、信号量、管线行为、重试循环和多账号声明。
5. **换投递**：发送改为发件箱 + 发送端，按附录 E 承接依赖投递结果的行为。
6. **调用链贯通与深度上限**。
7. **协议级 CMD 归并**〔改道 R3：移交子 Spec B〕：handler 退化为只解包入队，细粒度命令并入，按功能簇分批进行。
8. **收口**〔改道 R3：改为结果 A 的收口，依赖第 6 步，见修订记录 R3〕：判据全开、文档、最终测量。

这样排的原因：
- 第 3 步是纯搬迁，有表征测试和全量测试守着，风险最低，却一次性带来了串行；
- 第 4 步在串行之后删锁，删的是已经无人争用的东西，测试能立刻说明有没有删错；
- 第 5 步改语义；
- 第 7 步改结构〔改道 R3：移交子 Spec B〕；
- 每步的证据互不混淆（`RefactorPreferences` §3.2）。

### 共享决定（后续 Task 都依赖，现在定下）

- **分层**：
  - 入队点接口放在 `Dfo.Server.Abstractions`；执行器实现放在 `Dfo.Server.Application`。
  - `Networking` 仍然只依赖 `INetworkMessageDispatcher`；dispatcher 的实现改为入队，并等待 CMD 完成（RQ-005）。
  - 每连接的发送队列放在 `Networking`，它是传输层的职责。发件箱放在 `Application`，经 `Abstractions` 的接口把条目交给发送端。
  - 项目引用图不变。
- **命令类型沿用 `ICommand<TResult>` / `ICommandHandler<,>`**，不另造平行概念。`ICommandBus.SendAsync` 的含义改为：
  - 在执行器外调用时，入队并等待完成；
  - 在执行器上调用时，过渡期内直接内联执行，这样第 3 步搬进执行器的 handler 照常工作。这个过渡规则在第 7 步结束时删除〔改道 R3：删除移交子 Spec B；A 封存时它仍在，列入根 SC-12〕，之后在执行器上调用就是 RQ-003 定义的程序错误。
- **工作单元**：过渡期保留今天的 `UnitOfWorkBehavior`，每条内层命令一个事务，天然满足 RQ-024 的一对一。第 7 步归并时〔改道 R3：移交子 Spec B〕，CMD 内用显式的工作单元作用域代替被并入的命令。附录 C 在各个归并 Task 里填写。
- **发件箱的生效时机**：第 5 步之前，执行器上的作业仍直接 await 发送器。这在过渡期违反 RQ-037，所以按「过渡期规则」第 4 条套上期限。第 5 步把发送器在执行器上的实现换成登记发件箱，并按附录 E 逐项改写依赖。RQ-003 中「等待网络」的运行期检查在第 5 步结束时开启。
- **定时源**：后台服务保留 `BackgroundService` 外壳作为生产者，只负责按节奏入队，并按 RQ-006 合并。调度任务的每次尝试作为执行器上的作业运行；`Task.Run` 外壳与并发槽在 T-005 随锁一起删除。（措辞随 TASK-11 修正，与 TASK-08 裁定一致，要求不变）
- **事件**：`DomainEventDispatcher` 仍是生产者：它读取到期的 delivery，然后把消费入队成事件 CMD 并等待完成。组循环之间不再需要组门。
- **重计算**：口令哈希在执行器外完成，并发上限按处理器数设定；它的结果作为 CMD 的输入。第 3 步就落实。
- **请求级上下文（RQ-025）**：
  - **过渡期（第 3 步）**：dispatcher 今天在传输流上做的检查和设置的 AsyncLocal 帧，包括 `IsBlocked`、`IsSuperseded`、`CaptureAuthority`、`NetworkCommandAuthorization.Enter`、效果账本的 `DispatchAsync`，**整体移进执行器上的那个作业**，在作业里设帧，再调用 handler。这样不会因为 ExecutionContext 没跨过队列，而让保护静默失效。
  - **第 7 步**〔改道 R3：移交子 Spec B〕：把这些帧改为协议 CMD 的显式数据，「没有帧就放行」的分支改为程序错误，并按附录 H 迁移管线 45、58、60 号行为的非锁职责。
- **组装点（RQ-031(0)）**：第 5 步实现。工作单元作用域提供「提交完成」钩子，发件箱在这个钩子上，对该工作单元内登记的条目解析人群并组装。
- **Spec 复审残余的澄清（spec-review-r3 R-1、R-5、R-6）**：
  - 今天没有调用方在事务内发起关连接。第 5 步约定：关连接请求一律视为不属于任何工作单元，按 RQ-031(c)「一律执行」处理，这样 (b) 与 (c) 的措辞差异不会产生两种实现。
  - 附录 E 的 DR-7、DR-8 与附录 G 的 VC-5、VC-6，只针对传输层交付失败。组装失败走 RQ-031(d)：CMD 能看到逐收件人的组装结果，今天依据 Failed 做决定的 CMD 原样处理，包括 GM Cera 返回 unconfirmed、房间机制抛出等待重试、队伍投影在 CMD 内再试一次组装。第 5 步对这几处各补一条单元测试。
  - RQ-031(d) 的「与今天一致」指组装失败的处理；钱包变化与 PvP 参与者通知的传输重试被删除，由 VC-5 覆盖。
- **停机与等待关系（RQ-008、RQ-009）**：第 3 步落实。dispatcher 的完成信号定为执行器执行完毕；停机顺序为：TCP 服务和 Kestrel 停止接受 → 执行器排空 → 执行器停止。
- **预热**：第 3 步把执行器上会触达的 `Lazy` 内容源，例如成就目录、称号目录，加入 `GameServerStartupService` 的预热清单。
- **执行器的生命周期，不留旁路**：
  - 执行器是单例，第一次入队时启动消费循环，不依赖 `IHostedService` 的启动顺序。这样 `GmBootstrapService`、`JoustMaintenanceService` 在 `StartAsync` 里调用 `SendAsync` 也没有问题；自行组装容器、不启动托管服务的测试，也会自动用上执行器。
  - 停止按 RQ-009 执行。容器释放时，执行器停止消费循环，测试结束后不会遗留后台循环。
  - **不允许任何「执行器不在就内联执行」的旁路**。
- **过渡期规则（第 3 步到第 7 步）**〔改道 R3：A 封存时其中的内联规则与请求级帧仍在，列入根 SC-12，由子 Spec B 删除〕：
  1. **作业切分**：一个作业包住生产者的整段逻辑，包括它取的全部门、事务和信号量。执行器外的代码不再持有任何门。`SendAsync` 改为「执行器外入队并等待」这一语义翻转，是第 3 步的最后一个动作，排在全部持门者（后台服务、事件分发器、观察者、GM/HTTP、测试中先持门再发命令的写法）迁入之后。
  2. **门断言**：第 3 步给每种门加上过渡期断言：在执行器外取门，或者在执行器上取门时需要等待，都立即抛出。在单消费者下，执行器上的作业永远不该等门；一旦要等，说明执行器外还有持门者。这个断言在第 4 步随门一起删除。
  3. **「在执行器上」的判定**：用作业令牌表示，放在 AsyncLocal 里，作业结束时失效。从作业里分出去的工作（`TouchSocketNetworkConnectionCloser` 的分离关闭、卡牌计时器等 fire-and-forget）一律在 `ExecutionContext.SuppressFlow` 下启动，不继承令牌，也就不会被当成「在执行器上」去内联执行，或被误判为自我等待。完成信号用异步续延（`RunContinuationsAsynchronously`），等待方的后续代码不会跑在执行器上。第 3 步把这类分离点逐个列出。此外，传输层回调的入口（`NetworkPlugins` 的 Connected / Received / Closed，以及关连接器的回调）一律视为流边界，进入时清除作业令牌。这样，即使 TouchSocket 在发送失败时内联触发了关闭回调，回调也不会带着令牌被误判为自我等待。
  4. **过渡期的直接发送有期限**：第 5 步之前，执行器上的作业仍会直接 await 发送。这些发送一律套上 2 秒期限，不让一个不读包的客户端冻结执行器，也不形成 RQ-008 要排除的等待环。超时以发送异常的形式抛给调用方，与今天发送失败的路径相同，附录 E 的今天语义因此保持不变；同时关闭该连接。这是第 3 步唯一的语义例外：慢客户端会更早被断开，相当于提前落实 VC-8。
- **判据与测试的关系**：
  - 门断言与 RQ-061 判据**只按调用位置判定**，即看当前是否持有有效的作业令牌，而不是看「执行器是否已启动」。生产代码里没有关闭开关。
  - 判据挂在两类入口上：`Application` 的工作单元入口（写事务的开启）与附录 F 指定的玩法状态写入口。不经这两类入口、直接测 SQLite 存储的持久化单元测试（例如 Persistence.Tests 中直接操作存储的用例）不受影响。
  - 测试在执行器外开写事务、写附录 F 的入口、取门、调用 handler 时，统一用一个测试辅助（放在 `tests/Support`，链接进各测试项目），把测试体作为执行器作业运行。基线上约有 694 处直接 `.Begin()`（约 162 个文件）、`TestSessions` 被 32 个文件使用、23 个文件直接构造门，这些都改为经这个辅助运行。不另设豁免作用域。
  - 这部分改写计入 T-004，测试数量与断言不变，逐文件列出。
- **测试**：
  - 第 3 步就改写会在新语义下挂起或死锁的用例：测门本身的、先持门再发命令的、用 TCS 或门制造交错的（`research/05` §4）。要么删除并说明理由，要么改为经执行器驱动。
  - 「假总线 + 直接 new handler」的用例只测 handler 内部编排，经上面的测试辅助以作业身份运行，〔改道 R3：改写移交子 Spec B〕在第 7 步随所属功能簇改写之前可以保留。它们不能作为执行器、发件箱、顺序或入口覆盖的证据；这些证据一律经真实的 dispatcher 或执行器取得。
  - 「发送即记录」的替身在第 5 步改为记录发件箱或发送端的条目。附录 E 每一行的证据都必须经执行器和发件箱驱动取得。
- **发件箱的归属**：发件箱以执行器作业为单位（随作业令牌），不按 DI scope 注册，因为过渡期每次内层 `SendAsync` 都会开新的 scope。提交钩子挂在工作单元（`DomainTransaction`）本身，不挂在 `UnitOfWorkBehavior`，这样第 7 步改用显式工作单元后可以沿用〔改道 R3：显式工作单元移交子 Spec B〕。
