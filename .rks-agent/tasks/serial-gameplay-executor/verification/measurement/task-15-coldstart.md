## 拆分（§5 第 3 条）

**首次选角**
- P0 − P1 ＝ 391.6／430.4 ms：有界预热消掉的部分。
- P1 − P2 ＝ −2.7／−0.4 ms：C 类首次加载在选角里的份额在噪声以内。
- P2 的剩余约 104 ms：不是内容加载。依据有三条：
  1. 探针第 2 轮里，选角 CMD 下只剩 D 类读和按物品的落位读，没有 A、B 类首次加载；
  2. 把 C 类全部预热的 P2 仍是约 104 ms；
  3. 同一进程里，之后的每次选角只要约 3 ms。
- 剩余的来源推断为 JIT 与 SQLite 冷页，没有拆开测，交 M-1。

**首次进本**
- P0 − P1 ＝ 19.3／781.4 ms；
- P1 − P2 ＝ 5.2／5.9 ms，这部分是 C 类：副本、地图、房间的按键读；
- P2 的剩余约 52 ms。

**(f)**
- P0 527.6／860.5 → P1 133.6／137.6 ms。两次的最长停顿都是首次选角。

## 预算（主控方裁定第 1 条）与 C 类处置

**P1 相对 P0 的预算**：
- 就绪时长：+1838／+1359 ms，不超过 10 s；
- 就绪时 RSS：+66800 KiB（+9.6%）／+99632 KiB（+15.6%），不超过 25%。

**C 类规则**：P1 下首次进本 56.7／57.6 ms，不超过 100 ms；首次选角 101.7／104.3 ms，**略高于 100 ms**。按规则应当按「P1 − P2 份额」逐个家族加入预热。但所有家族全部加入的 P2 仍是 104.4／104.7 ms：选角的超出部分不是 C 类加载，加哪个家族都降不到 100 ms 以下，只会多付启动时长与内存。
- 所以 **C 类全部保持懒加载**，逐项写进附录 B 的「交 M-1」清单。
- 主控方在第二次停止后的裁定第 7 条中已接受这一处置：首次选角超出 100 ms 的部分交 M-1 判定。
