# Routing Decision

- TaskContract: `./TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 结构主张由项目所有者本人提出，并在三轮对话里逐步收窄到不再
  含糊——先是「CMD 只和领域服务交互」，再澄清「服务指的是 DomainService，规则服务在它里
  面」，最后钉死「store 只有第一种，其余都是问题」。所有者还接受了一处承接方提出的修正
  （快照是返回值不是依赖），说明边界已经被双方共同检验过而不只是被听懂。
- Requirement stability: 要求可以逐条枚举并独立核对。27 个命令处理器的 55 个构造器依赖已
  全部落到文件与行号；19 次落在白名单外的注入已分成两处硬违规、14 次命名问题、1 次应豁免；
  三个零消费方接缝、六个内存容器、三个真 store 都已具名。这不是「大概要改哪些地方」，是一
  张能对账的清单。
- Execution direction: 已知。目标形状在仓库里已有正例（`DungeonRunDomainService` 把容器私
  有化、只暴露领域动作），执行机制也已有半成品（`CommandHandlerArchitectureTests` 已在反射
  遍历构造器，只是目前只守一条黑名单）。所有者认可的三批分工给出了顺序。
- Remaining uncertainty: 只剩非语义的局部选择——白名单判据写成哪种断言、五个 `Application`
  内部服务是补后缀上提还是加门面。两者都不改变任务含义，留给 Spec 与 Plan。

## Marginal Control Value

- User precision signal: 明确偏精度。所有者主动要求走 SDD 而非直接改，并指定 multi-spec；
  同时要求「跑完了再和我说」，即执行期间没有人工检查点。
- Direct failure mode: 改名重构最典型的那种——改了一半却看起来完成了。这个仓库已经因同类
  错误吃过两次亏（经验通告的两个槽、频道比率的来源），两次都「看起来完全正常」。本任务还
  多一层：**判据对死件天然失明**，三个零消费方接缝全都自带测试，全量跑绿也给不出任何信号；
  「删干净了没有」这件事没有任何自动手段能回答。再加上一个具体陷阱：按字符串改名会误伤
  `IExpertStoreRegistry`（那里的 Store 指玩家摆的摊）。
- Useful control: 可枚举的成功条件加完整变更评审。前者把「全量」变成可核对的清单而不是感
  觉；后者是唯一能发现「删漏了一个死件」的手段。所有者要求无中途检查点，这使得把检查点前
  移到契约与评审里成为唯一的保护。
- Time-for-quality rationale: 值得。本任务的产出之一恰恰是一条**长期有效的机检约束**——它
  一旦立住，后续所有新代码都自动受约束，AGENTS.md 那张漂移了的 handler 白名单就是没有判据
  守护的反面教材。为一个要长期生效的不变量花一轮 SDD 的时间，收益是持续的而不是一次性的。

## Structural Selection

- Selected workflow: `multi-spec-workflow`
- Boundary evidence: 三批工作各有独立的验收边界与独立的回滚边界，任何一批单独完成都是可交
  付的成果。第一批（store 改名、白名单判据落地、退役死件）判据是「行为逐值不变 + 故意引入
  的违规会让判据变红」；第二批（三个注册表转领域服务）判据是「接口只剩领域动作且行为不
  变」；第三批（拆大聚合、角色实例收编等级/经验/SP）是**唯一带可观察行为变化**的一批，判据
  是「升级后报出的剩余 SP 是重算值」。第三批的行为变化不能与前两批的「行为逐值不变」共用
  一个验收口径——把它们塞进一个 Spec，会让前两批的行为保持判据失去意义。这是结构性的边界，
  不是工作量大小。
- Why Direct is insufficient: Direct 给不出「枚举核对」这个控制。而本任务的失败模式正是漏
  项，且其中一类（死件退役）判据完全看不见。
- Reroute conditions: 若第一批做完发现白名单无法在不改变现有 14 处命名的前提下立住，说明
  三批之间存在真实依赖而非仅有顺序偏好，第二、三批应合并重划边界；若第三批拆解大聚合时发
  现等级/经验/SP 无法与位置、在场等运行态分离，则该批的中心做法已被证伪，应回到 Multi Spec
  控制器重新界定而不是在批内硬推。
