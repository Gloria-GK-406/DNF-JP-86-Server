# Specification: 内存容器改说领域话

## Why and Outcome

上一个成果给命令处理器的注入面立了一条判据：只有接缝层里以 `DomainService` 或 `DomainStore`
结尾的接口能被注入。它当场暴露出一件事——会话容器 `ISelectedSessionDirectory` 被两个命令
处理器注入着，而它的接口是纯容器动词。为了让判据通过，上一个成果把它的三个动词逐字透传进了
一个领域服务。处理器做的还是同样三件容器事，只是隔了一层。

那份成果自己把这层壳记为必须收口的负担，理由值得原样保留：**一条可以被改名壳满足的白名单，
守不住它声称守的东西。**

对着代码看，这批容器的处境比预想的好。四个的字典都已经是私有字段，接口上暴露的也大多已经是
领域动词。缺的只是名字——`Registry` 与 `Directory` 在这个仓库的后缀分类法里说的是「容器」，
而它们做的事是领域的。名字说错了类别，判据就只能拒绝它们，于是就有人去加壳。

## Task Perspective

- Core outcome: 这几个接缝的名字说的和它做的是同一件事，于是命令处理器可以直接问它们，
  不必隔着一层问同样的问题。判据因此守住的是真的东西，而不是一层壳。
- Necessary support: `ISelectedSessionDirectory` 的动词要能以领域的说法重述——这是拆壳的前提。
  另有一处遗留的一词多义（一个叫 `Store` 却不是领域 store 的内存表）要一并消掉，否则
  `store` 在领域层仍有两种读法。
- Peripheral assurance: 行为逐值不变的证据；以及一条专门的检查，确认判据是靠代码变对了而
  通过，不是靠规则被放宽或豁免被扩充而通过。

## Scope and Non-Goals

### In Scope

- 会话、在场、摆摊、PvP 大厅四个接缝的类别与名字
- 上一个成果为通过判据而留下的透传壳
- 领域层中 `store` 一词残余的第二种读法

### Non-Goals

- 会话运行态聚合及其持有者——那是下一个成果的核心
- 入场背包租约那个带版本与脏标记的写回缓存
- 普通 socket 消息处理器的依赖面
- 任何可观察行为的改变

## Constraints

- 服务器对客户端的可观察行为逐值不变
- 既有测试的期望值与断言不得为迁就实现而改写；类型改名带来的符号更新除外
- 摆摊那个接缝的语义在改名后仍须能从名字读出——它的 `Store` 指玩家摆的摊，不是存储

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 会话、在场、摆摊、PvP 大厅四个接缝的名字表明它们是领域服务，其成员是领域动词而非容器操作，各自的内存容器不出现在接口上 |
| RQ-002 | 命令处理器直接向拥有会话的领域服务提问；不存在为让某个依赖通过注入面判据而设的逐字透传成员 |
| RQ-003 | 注入面判据仍然通过，且其判定规则与具名豁免清单未被放宽或扩充 |
| RQ-004 | 领域层中 `store` 一词只有一种读法：事务结算的真源。摆摊语义仍可仅凭名字读出 |
| RQ-005 | 服务器对客户端的可观察行为逐值不变 |
| RQ-006 | 仓库约定里关于这几个接缝类别的记载与代码一致 |

| AC-002 | RQ-002 | 拥有会话入场的那个领域服务，与注入它的命令处理器 | 对照改动前后的成员与构造器 | 透传成员不再存在，处理器直接向会话领域服务提问 |

## Assumptions

- 四个容器的字典已经是私有字段，接口成员也已多为领域动词，因此本成果主要是名字与类别的变更
- 基线自带一个偶发失败：某个跨事务读取用例会抛已释放的 SQLite 句柄异常，单独复跑其所在项目
  即恢复全绿
