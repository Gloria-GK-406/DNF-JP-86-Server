# Specification: 守住注入面

## Why and Outcome

命令处理器的注入面今天基本是干净的——27 个处理器里 17 个只用领域服务，负面清单上的东西一个
没有。但没有任何东西守着它。同一个仓库里另一张写在约定里、没有判据守护的白名单已经漂移到有
八个 handler 违反，那是现成的先例。

要让「命令处理器只够得到领域形状」这句话继续为真，它得先能被判定，再被判据守住。能被判定的
前提是类型自己说得清属于哪一类：今天「store」一词在领域层指三种不同的东西，而有四个被注入的
类型形状正确却没有能表明其类别的名字。

同一次清理里还有一批对不上号的东西：三个领域接缝没有任何生产消费方，一份角色状态副本写进去
之后从没被读出来过。它们与注入面无关，但共享同一种验收方式——判据对它们完全失明，只能靠人把
清单摊开逐个核对，而现在正在做的就是这件事。

## Task Perspective

- Core outcome: 命令处理器的每一个依赖都能仅凭类型说清自己是什么，判据守着这条，新的违反进
  不来。这是消费者要的东西：一条以后不必再靠人记住的约束。
- Necessary support: 名字得说出类别，否则判定只能退化成一张人工维护的清单——那种清单和没有
  判据是同一回事，只是失效得慢一点。这包括让领域 store 可辨认，以及让形状正确但名字没跟上的
  类型能被归类。同属必要支撑的还有对既有约定与代码冲突的裁决：判定规则不能建立在一句与代码
  矛盾的记载上。
- Peripheral assurance: 行为逐值不变的证据；退役没有消费方的接缝与只写不读的副本。后者不服务
  于注入面——它们从不出现在任何命令处理器的构造器上——而是与注入面共享同一种证据形态：判据
  看不见，只能枚举。它们和核心成果一起走，是因为这一次正好在枚举。

## Scope and Non-Goals

### In Scope

- 命令处理器依赖的可判定性，以及守住它的判据
- 领域层中「store」一词的歧义消除
- 形状正确但类别无法从名字读出的被注入类型的归类
- 没有生产消费方的领域接缝，以及只被写入从不被读出的角色状态副本
- 仓库约定中这套词汇表的记载，及其与代码既有冲突的消解

### Non-Goals

- 内存容器改说领域动作、把容器语义收进服务内部
- 会话运行态聚合的拆解，以及角色自身的数改由角色实例回答
- 普通 socket 消息处理器的依赖面——本 Spec 的判据只覆盖命令处理器
- 让直接调用领域写操作的 socket 处理器改经命令总线

## Constraints

- 服务器对客户端的可观察行为逐值不变
- 既有测试的期望值与断言不得为迁就实现而改写；类型改名带来的符号更新除外

## Definitions

| Term | Meaning |
|---|---|
| 领域 store | 领域状态的事务结算真源：被要一个会话、由事务收口。不是任何进程内的字典容器，也不是单张表的读写网关 |
| 实例 | 绑定到一个具体实体的可操作对象，方法不带该实体的标识，自身不持有状态，每次询问都现读 |
| 领域服务 | 编排一项业务能力的服务。规则判断由它在内部向规则服务索取，对调用方不暴露 |
| 快照 | 某一刻的不可编辑镜像。它是被交出来的结果，不是被注入的依赖 |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 命令处理器的每一个构造器依赖，都能仅凭其类型归入领域服务、领域 store、交出实例的工厂三者之一，或归入一张具名豁免清单，且豁免的每一项都写明理由 |
| RQ-002 | 归类不依赖一张需要人工逐条维护的类型清单：给某个命令处理器新增一个符合词汇表的依赖，无需改动判据本身即可通过。具名豁免清单是唯一例外 |
| RQ-003 | 没有命令处理器依赖比领域 store 更低层的持久化设施，也没有命令处理器直接依赖规则判断、档案内容或静态规则来源 |
| RQ-004 | 领域 store 这一类可仅凭类型名辨认；领域层中其余名字含 store 的类型，其各自含义仍能从名字读出而不与领域 store 混淆 |
| RQ-005 | 给某个命令处理器加入一个不属于词汇表且不在豁免清单里的依赖，会使判据失败 |
| RQ-006 | 不存在没有任何生产消费方的领域接缝；不存在被写入之后从不被读出的角色状态副本 |
| RQ-007 | 除上述结构变化外，服务器对客户端的可观察行为逐值不变 |
| RQ-008 | 仓库约定陈述了这套词汇表并指明违反时哪一条判据会失败；约定与代码之间关于跨层暴露的既有冲突不复存在 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 服务器的全部命令处理器 | 逐个检视其构造器依赖 | 每个依赖或落入三类之一，或出现在具名豁免清单中且该项写明了理由 |
| AC-002 | RQ-002 | 某个命令处理器与一个符合词汇表的新依赖 | 把该依赖加进它的构造器并运行判据 | 判据通过，且未曾改动判据本身 |
| AC-003 | RQ-003 | 服务器的全部命令处理器 | 逐个检视其构造器依赖 | 其中没有单表读写网关、没有持久化接缝、没有规则判断来源、没有档案内容来源 |
| AC-004 | RQ-004 | 领域层中名字含 store 的全部类型 | 只读它们的名字 | 领域 store 与其余含义彼此可区分，无需读实现即可分辨 |
| AC-005 | RQ-005 | 某个命令处理器 | 给它加入一个既不属于词汇表也不在豁免清单里的依赖并运行判据 | 判据失败；移除该依赖后判据恢复通过 |
| AC-006 | RQ-006 | 服务器的领域接缝与角色状态的各份副本 | 查找每个接缝的生产消费方，并查找每份角色状态副本的读出点 | 每个接缝至少有一个生产消费方；每份被写入的角色状态副本都有读出点 |
| AC-007 | RQ-007 | 与基线相同的输入 | 运行全量判据并审查测试改动 | 判据通过；用例数与基线的差额仅来自随死件一并移除的测试；既有用例的期望值与断言未被改写 |
| AC-008 | RQ-008 | 仓库约定中关于领域分层与命令处理器能力的记载 | 逐条对照代码事实 | 词汇表在记载中，违反时会失败的判据被指明，且没有与代码矛盾的陈述 |

## Assumptions

- 退役没有消费方的接缝会连同它们各自的测试一并移除，全量用例数因而低于基线。这是预期结果，
  按 AC-007 以逐条对账代替计数比较
- 基线自带一个偶发失败：某个跨事务读取用例会抛已释放的 SQLite 句柄异常，单独复跑其所在项目
  即恢复全绿。它不属于本 Spec 引入的回归
