# TaskContract: 角色自己回答自己的数

## Context

### Source Request

来自根任务 `commands-reach-only-domain-shapes` 的第三个也是最后一个有界成果。根契约要求
「靠领域服务、领域 store 和实例能拼出所有的业务结果」，并把会话运行态聚合列为要拆的东西。
本成果做其中与角色自身相关的那一半。

### Current Situation

基线 `68a12119`（spec-001、spec-002 已接受）。

`SelectCharacterResult` 自称是「Select Character 这个用例的应答信封……并不使其成为角色状态」，
实际被 `ISelectedSessionRuntimeDirectory` 长期持有、16 处读、9 处 `with` 后写回。它同时占了
实例的行为、store 的存储位置与快照的类型形状。

其中角色自己的三个数是这样的：

**等级与经验**是实时的。`ICharacterExperienceDomainService.AwardAsync` 在给经验的那一刻从
`characters` 表读出、算完立即写回，调用方拿不到陈值——这是上一轮修过的一个缺陷，它的注释
明说「不是把某条通用原则应用一遍，而是这条具体的错：一个任务交两次写了同一个总额两次，因为
它加上去的那份副本是入场时的快照」。发帧时会话里的 `Progression` 与 `Extras.CharacterExperience`
被同步更新，所以这两个字段目前是对的。

**剩余 SP/TP 不是。** `result.CharacterEntry.Skills.ProtocolMirror` 在入场时由
`SelectCharacterPreparationService.CompleteSkillProjectionAsync` 算一次，此后**永不重算**。
四个发 `ExperienceNotification` 的地方全部回推这份入场值。而剩余 SP 是等级派生的：
数据库里根本没有「剩余 SP」这一列，它每次都是
`总量（按等级累加档案的 SP 表）+ Bonus（DB）− 已花费（遍历已学技能 × 档案成本表）` 现算出来的。

后果是实机可见的：**升级之后客户端拿到的剩余 SP 仍是登录那一刻的值**，要重登才对。所有者在
实机测试里报告过这一条，它正是这一整轮工作的起点。

### 为什么这一批的验收口径与前两批不同

前两批的口径是「行为逐值不变」。本批**必须**改变一处可观察行为——升级之后报出的剩余 SP 从
入场陈值变为按新等级重算的值。把它们放进同一个 Spec，会让前两批的行为保持判据失去意义。
这是根契约把它单列为一个成果的原因。

## Goal

角色自己的数——等级、经验、剩余 SP/TP——由角色实例回答，现读现算，不再从入场镜像取。
升级之后客户端看到的剩余 SP 是按新等级算出来的，而不是登录那一刻的。

## Scope

### In

- 角色实例能回答等级、经验与剩余 SP/TP，每次询问都现读现算
- 发经验帧的地方改为向角色实例取这三个数，不再读入场镜像
- 入场镜像不再作为这三个数的取数来源
- 仓库约定记下这条：角色自己的数从角色实例问，不从会话快照读

### Out

- 会话运行态聚合中**与角色自身无关**的部分：坐标、在场、世界内容、背包投影、账号侧状态。
  它们仍留在会话里，本成果不动
- HP/MP 等派生属性随等级成长。档案的成长段未被读、`character_stats` 无更新通路、无重算时机，
  三层都缺，是独立功能而非取数来源的归位
- 升级后补发角色面板帧（`NOTI 0x0002 USERINFO` 子类型 1）。经验帧本就带 SP/TP 四个字段，
  本成果改的是这些字段的取数来源，不新增任何协议帧
- 投影器成为出帧常态
- `IEntryInventoryLeaseRegistry` 那个带版本与脏标记的写回缓存

## Constraints

- 只允许一处可观察行为变化：升级之后报出的剩余 SP。除此之外行为逐值不变
- 不新增任何协议帧，不改任何帧的字节布局
- 现有测试的期望值与断言不得为迁就实现而改写；类型改名带来的符号更新除外
- 注入面判据的判定谓词与豁免清单不得放宽或扩充。判据的反例目前锚在
  `ISelectedSessionRuntimeDirectory` 上——若本成果动到它，反例必须换一个**仍被规则拒绝的真
  容器**作为锚点，而不是顺手放宽规则
- 判据命令必须带 `PVF_ARCHIVE_PATH`

## 契约修订（revision 1 → 2，控制者裁决，需所有者知悉）

**改的是什么**：C-2 原文是「生产代码里不存在从入场镜像读取**这三个数**的路径」。现改为按
「会不会变陈」来界定。

**为什么**：独立评审指出实现只做到了剩余 SP/TP 一处，入场序列之外仍有若干处从会话读角色等级，
因而 C-2 字面未达成。核查之后我认为**字面要求本身写宽了**：

四条能改变等级的路径——击杀、副本结算、交任务、教学升级——**全都把新等级写回会话**
（`Progression = new CharacterProgressionState(...)`）。也就是说会话里的等级是被维护的，它不会
变陈。没有任何东西维护的只有技能点镜像，那正是实机缺陷的所在，也正是这一轮修的东西。

把那些读等级的地方也改成读库，是为了满足我自己写下的一句话而给热路径（翻牌、进本、接任务）
各加一次数据库读，去取一个本来就正确的值；其中教学升级那一处的等级还是写入命令的**判断入参**，
改它有带出第二处可观察行为变化的风险，而本 Spec 明令只允许一处。

**一处我判错、被评审纠正的依据，记在这里而不是删掉。** 我曾以为 `DungeonClearSlice` 结算翻牌
时读会话等级是「改了反而错」的反例，理由是它旁边写着「取在授予之前」。评审核后指出这不成立：
结算（第 624 行）与授予（第 680 行）是同一方法里顺序 `await` 的两步，结算严格在前，所以那一刻
**库里的等级就是通关时的等级**——改成向角色实例读，取回的是同一个值，卡面档次不会变。那条注释
说的是方法内的先后，不是读哪个存储。

这条依据作废，收窄靠的是下面三条，各自独立成立。把它留在这里，是因为一份用来支撑范围决定的
记载里出现过一句比代码强的论断，本身就是这个 Spec 要禁的那类错误——删掉它比留着更容易让人
再犯一次。

**所以这是一次收窄，由控制者做出，理由如上。** 所有者批准这一批时的说法是「`ICharacter` 收编
level/exp/SP」——这一点已经做到：实例能回答三者，且 `ICharacter` 内部唯一一处从镜像读等级的地方
（道具等级门槛判定）已经改为问自己。没做的是把与缺陷无关、且本就不陈的调用点一并重指。

**这条要在交付汇报里明说，不能埋在产物里。**

## Assumptions

- 剩余 SP 的三个输入都已有可达的取数点：等级与职业成长类型在角色行上，已学技能在技能表上，
  加成在入场表上，规则在 `ICharacterEntryPreparationRuleService.SkillPointsAsync`
- 等级与经验目前是对的（发帧前会话被同步更新），本成果把它们的取数来源一并归位是为了消除
  「同一个数有两处可读」的分叉，而不是在修一个现存缺陷
- 基线自带一个偶发失败：`OutsideTransactionTests.ReadingACharacterOutsideAUseCaseIsAllowed`
  会抛已释放的 SQLite 句柄异常，单独复跑其所在项目即恢复全绿
