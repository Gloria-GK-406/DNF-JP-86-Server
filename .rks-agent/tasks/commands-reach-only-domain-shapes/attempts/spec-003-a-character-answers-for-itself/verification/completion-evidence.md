## 契约修订与一次自我纠错

C-2 与 RQ-003 原文写的是「这三个数」。独立评审指出实现只做到剩余 SP/TP 一处，字面未达成。
控制者核查后认定**字面要求本身写宽了**：没有任何东西维护的只有技能点镜像，会话里的等级由每一条
改变它的路径写回。故按「结果与机制分离」把两处重述到证据支持的层面，契约升 revision 2，理由与
「这是一次控制者做出的收窄」写在契约正文，并要求在交付汇报中向所有者明说。评审判定该修订成立。

**修订依据里我曾写下一句错的论断**：我以为副本结算读会话等级是「改了反而错」的反例。评审核后
指出结算与授予是同一方法里顺序 `await` 的两步，那一刻库里的等级就是通关时的等级，改成读库取回
同一个值。该论断作废，收窄靠其余三条独立成立。**这句错误连同它的订正一并留在契约里而不是删掉**
——一份用来支撑范围决定的记载里出现过比代码强的论断，本身就是这个 Spec 要禁的那类错误。

## 执行期的两次异常

实现与整改阶段各有一个子代理因 API 错误中途终止（一次在做变异验证时，一次在写判据时）。两次都
按同一套处置：扫描变异标记与残留文件、跑全量、**逐项核验它声称交付的东西是否真的在**，未完成的
部分由控制者接手做完。第一次中断时未跑完的变异验证由控制者重做。

## 留给后续成果的

- `ICharacter.ProgressAsync` 与新服务对同一 level 列的越界策略不一致（一个夹取、一个抛）
- `FindProgressAsync` 缺 `delete_flag` 条件，而新增的 `FindStandingAsync` 有
- 每次击杀无条件多 3 次 SQLite 读；缓存挡的是归档解析而不是数据库
- 新服务未校验负数加成，入场装配有校验
- 自由决斗频道的 SP 语义：入场镜像是 `(65535×4)`「不限点数」，新服务只答 PVE 账本。默认
  `FreeDuelEnabled: false` 使该分支不可达，已在实现上写下 remark
- 这个仓库把 CS9113（主构造器参数未读）当**错误**，所以「加了接口只挂着不接线」连编译都过不去
