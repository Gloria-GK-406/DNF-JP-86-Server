# Specification: 角色自己回答自己的数

## Why and Outcome

登录之后，服务器给客户端报过一次角色的剩余技能点。此后玩家升了级，那个数字再也没有变过——
要退出重登才对。所有者在实机里发现了这一点，这一整轮工作就是从那里开始的。

原因不是哪一段算错了，而是这个数**没有主人**。数据库里没有「剩余 SP」这一列：它每次都要用
等级去档案里累加总量、加上库里的加成、再减去遍历已学技能算出的花费。入场时算过一次，结果
放进会话的一份镜像；此后四个发经验帧的地方都从那份镜像取，而没有任何东西负责在等级变化时
把它重算。

等级和经验没有这个毛病：给经验的那一刻从库里读出、算完立即写回，而四条能改变等级的路径
**全都把新等级写回会话**。所以会话里的等级是被维护的，它不会变陈——没有任何东西维护的只有
技能点镜像。**这一轮修的就是那一个**；等级与经验一并让角色实例能回答，是为了让「角色自己的数
问角色」这条路存在，而不是因为它们也错了。

## Task Perspective

- Core outcome: 角色自己的数由角色实例回答，问的时候才算。玩家升级之后看到的剩余技能点是
  按新等级算出来的——这是消费者要的东西，也是这一轮唯一被授权改变的可观察行为。
- Necessary support: 剩余 SP 的三个输入要有明确归属。算法已经存在于入场准备里，换位置时若
  不定归属，同一个算法会留下两份实现，而两份实现迟早分叉——那正是本轮要消灭的毛病。
- Peripheral assurance: 一条能在实现被改坏时变红的判据；以及「除那一处外行为逐值不变」的
  证据。这一批失去了「判据数字不变」这道护栏，所以改动的期望值必须逐条能对应到那一处变化。

## Scope and Non-Goals

### In Scope

- 角色实例回答等级、经验与剩余 SP/TP
- 会在入场之后变陈的那个数（剩余 SP/TP）的取数来源从入场镜像转到角色实例；角色实例内部也不再从镜像读自己的等级
- 剩余 SP/TP 算法的唯一归属
- 仓库约定里关于「角色自身的数从哪里问」的记载

### Non-Goals

- 会话运行态里与角色自身无关的部分：坐标、在场、世界内容、背包投影、账号侧状态
- HP/MP 等派生属性随等级成长——档案成长段未读、无更新通路、无重算时机，三层都缺，
  是独立功能而不是取数来源的归位
- 升级后补发角色面板帧。经验帧本就带 SP/TP 四个字段，本 Spec 改的是这些字段的取数来源
- 投影器成为出帧常态

## Constraints

- 只允许一处可观察行为变化：升级之后报出的剩余 SP。除此之外逐值不变
- 不新增任何协议帧，不改任何帧的字节布局
- 既有测试的期望值与断言不得为迁就实现而改写，除非该改写正对应上面那一处被授权的变化
- 注入面判据的判定规则与具名豁免清单不得放宽或扩充

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 角色实例能回答自己的等级、经验与剩余 SP/TP，每次询问都从存储与规则现算，不持有跨询问的缓存 |
| RQ-002 | 剩余 SP/TP 的算法在服务器里只有一处实现 |
| RQ-003 | 凡在入场之后会变陈的角色自身数值，生产代码不再从入场镜像取它；角色实例内部也不再从镜像读自己的等级。等级与经验的会话副本由每一条改变它们的路径写回，因此不属于陈值，不在此列 |
| RQ-004 | 升级之后报给客户端的剩余 SP 是按新等级重算的值，而不是登录那一刻的值 |
| RQ-005 | 除 RQ-004 之外，服务器对客户端的可观察行为逐值不变；不新增协议帧，不改任何帧的字节布局 |
| RQ-006 | 命令处理器的注入面判据仍然通过，且其判定规则与具名豁免清单未被放宽或扩充 |
| RQ-007 | 仓库约定记下角色自身的数从角色实例问，不从会话快照读 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 一个正在被玩的角色 | 连续两次向角色实例询问同一个数，其间存储中的值变了 | 第二次的答案反映变化后的值 |
| AC-002 | RQ-002 | 服务器全部代码 | 查找剩余 SP/TP 的计算 | 只找到一处实现，其余位置都向它提问 |
| AC-003 | RQ-003 | 服务器全部生产代码 | 枚举入场镜像与会话进度字段的读取点 | 入场序列之外没有一处从镜像取剩余 SP/TP；角色实例内部不从镜像读等级；仍读会话等级的地方各自说明为何它不陈 |
| AC-004 | RQ-004 | 一个刚好跨过等级门槛的角色 | 让它升级，观察随后报给客户端的剩余 SP | 是按新等级算出的值；若把重算改坏，该判据失败 |
| AC-005 | RQ-005 | 与上一成果相同的输入 | 运行全量判据并审查测试改动 | 判据通过；改动的期望值逐条对应到 AC-004 那一处变化，没有第二处 |
| AC-006 | RQ-006 | 注入面判据及其判定规则与豁免清单 | 运行判据并检视其 diff | 通过，且判定规则与豁免清单未被放宽或扩充 |
| AC-007 | RQ-007 | 仓库约定 | 读它关于角色自身状态取数来源的记载 | 记载与代码一致 |

## Assumptions

- 剩余 SP 的三个输入都已有可达的取数点：等级与职业成长类型在角色行上，已学技能在技能表上，
  加成在入场表上，规则在既有的入场准备规则服务上
- 等级与经验目前是对的；把它们一并归位是为了消除「同一个数两处可读」，不是在修现存缺陷
- 基线自带一个偶发失败：某个跨事务读取用例会抛已释放的 SQLite 句柄异常，单独复跑其所在项目
  即恢复全绿
