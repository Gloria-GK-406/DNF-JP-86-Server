# spec-002 路由决策

## SDD 就绪

意图与范围稳定：要退役的四个构造已逐一点名，行数、位置、注册处、调用方都已核实。
结果可观察：`Server/src/` 下零命中、全量减量恰为被删三个测试文件的 23 条。
中心执行方向已知：先证明无调用方，再删，再让五个把它当替身的测试另有着落。

## 用户的精度信号

用户明确要求「按 multispec 来跑」，且第二个 spec 的措辞是「退役掉大量无用的东西」——
关心的是东西真的没了，不是过程有多重。spec-001 的八个任务单查出四处真实回归，
说明这个仓库里「看起来只是搬家」的改动确实会藏东西；但那是拆分，这是删除，
删除的危险面窄得多：要么删错了东西（有调用方），要么删的时候顺手放宽了测试。

## 直接做会漏掉什么

具名的失效方式只有两个，且都不需要重排序来防：

1. **删掉了其实有人用的东西**——由 C-3「删之前先证明无调用方，证明写进记录」挡住。
2. **借退役之名放宽断言**——由 SC-C「五个文件的 `Assert.` 增删逐条交代」挡住。

两者都是清点，不是排序问题。这次没有 spec-001 那种「错误次序不产生红灯」的危险：
删掉一个有人用的类型会立刻编译失败。

## 为什么是 sdd-lite 而不是 sdd-standard

spec-001 选 standard，是因为它有三条不产生红灯的次序失效（规则在覆盖不足时先被搬走、
载体协议按错误直觉提取、建表集中化未复现 DI 顺序决定的并集），需要一份 durable 的排序把它们钉死。
这次没有任何一条对应物：删除的次序不影响结果，编译器会当场发现删错。
再上一层 governed 更没有理由——没有需要控制器裁决的独立接受边界。

而比 lite 更轻（直接做、无 spec 工件）也不合适：本 Spec 是 multi-spec 的子 Spec，
需要一份可封存的结果与证据回给父控制器，SC-6 的进度要靠它举证。

## 重新路由的条件

若清点发现四个构造中任何一个其实有生产调用方，退役就不再是删除而是替换，
中心方向随之改变——那时停下，回到父控制器重新决定。
