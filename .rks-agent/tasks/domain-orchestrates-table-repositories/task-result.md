## 做成了什么

**spec-001**：九个既跨多表、又在里面做业务判断的仓储被拆开，删掉 3143 行；
换成 58 个单表仓储——每个只做增删改查、只提一张表、不自己开连接也不自己开事务。

## 一路查出的真实缺陷

拆分本身不产生红灯，所以每一步靠「与被删代码逐条对照」找问题。五处都是这样查出来的：

1. 64 KiB blob 上限被丢掉（T-004）。
2. 账号写入的「必须命中恰好一行」守卫被丢掉（T-005）——账号行不存在时，
   幸运星会被结算成已发放并写下 `{"granted":true}`，原本这条是死信。
3. 货柜多读了时装明细（T-006）——账号货柜从不读时装明细表。
4. 全新库上选角必抛（spec-001 评审）——`dungeon_persistent_effect_outbox` 是全库唯一一张
   生产代码读写却无人声明的表；旧代码靠问一句 `sqlite_master` 绕过，拆分时以错误的前提删掉了那一问。
5. 建角的 `INSERT … RETURNING` 走了读路径，是全仓唯一一条能在用例边界外落地的持久写。

另有一处：spec-002 里我删掉的两个测试文件中，有四条断言证的是仍然存在的东西，被评审拦下并搬回。

每一处都有新增用例钉住。

## 需要用户裁决的一件事

并发「先读后写」的第二个用例会等满 30 秒再失败。这是 deferred 事务换来快照隔离的代价：
两个用例都先读、一个先提交之后，另一个手里的视图已过期，数据库拒绝在其上写；
等待帮不上忙，但从连接看这就是「库忙」，于是按 `Microsoft.Data.Sqlite` 的默认超时等满 30 秒才抛。
全仓没有设过这个超时，也没有在 BUSY 上重试。真正的解法是「整条用例重来」，
属于派发用例的那一层，不在这两个 Spec 的边界内。已写入 `AGENTS.md`。
