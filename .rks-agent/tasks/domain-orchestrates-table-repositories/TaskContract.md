# TaskContract: 领域层编排按表仓储

## Context

### Source Request

「你让领域服务自己编排 repository，repository 按表建立如何？这样 repository 的逻辑就很干净。后面我们做什么 ORM 之类的也更简单。一般来说很多 repository 可能都只需要增删改查。我们都用了 sqlite 了，也不需要考虑太大的吞吐量。能保证上百人并发就很不错了。」

随后：「按 multispec 来吧，第一个干掉除了 item 以外的大部分问题。然后第二个 spec 完成 item 的切分，退役掉大量无用的东西。最后就是干净的领域层通过操作 repository 完成业务逻辑。」

### Current Situation

持久层刚独立成 `Dfo.Server.Persistence` 项目，与基础建设层并列，只依赖 Abstractions 与 Data，且项目内全部类型为 `internal`。项目边界清楚了，内部形状还没有。

今天的持久化实现有两种形状并存：

- 物品与人物走存储协议（`IDomainStore` / `IStoreSession`），会话由 `SqliteDatabaseParticipant` 按连接串归并，连接与事务归它独占。
- 其余九个仓储各自 `new SqliteConnection` 再 `BeginTransactionAsync`，共 26 处自开连接落在用例边界之外。它们各自提交，互不知晓。

两条后果已确认：

一、**跨表组装住在持久化实现里。** 一次入场装载读 31 张表拼成 `CharacterEntryStorageRecord`，这段编排是 SQL 层的私产，领域层拿到的是成品。仓储因此不是仓储，是"某个业务场景的取数过程"，既无法复用也无法被自动化。

二、**边界外的读没有一致快照。** 自开连接意味着每次读都是独立事务，一次入场装载的多次读之间，别人的提交可以插进来。今天没暴露只因并发低。

用户要的成果是"领域层与持久层分界清晰，领域服务编排仓储完成业务"。仓储退回到"一张表的增删改查"这一层，编排上移到领域层，是达成该成果的路径，也是后续引入 ORM 或代码生成的前提——今天每个仓储各写各的 SQL，自动化没有下手的地方。

## Goal

领域层与持久层分界清晰：仓储只表达单表的读写，一次用例内的所有持久化访问共用同一连接与事务，跨表组装与业务编排归领域层所有。

## Scope

### In

- 九个仓储按表拆分，每个仓储的职责不超出一张表的增删改查。
- 持久化实现不再自开连接，一次用例内的读与写共用同一连接。
- 跨表组装从持久化实现移入领域层，且集中在单一处，不得散入各调用方。
- 物品路径的载体随之收敛。
- 退役已确认无生产调用方的内存载体构造及其测试。

### Out

- **不做泛型 `Repository<T>` 与 attribute 字段映射。** 已判定它在本库会漏：BLOB 列、条件写（乐观并发的 `WHERE` 谓词）、跨表投影三处都表达不出来。
- **不拆 BLOB 列。** `hotkey_slots`、`main_game_option`、`item_core` 等以字节形式存储所造成的语义困惑，记为技术债，本任务不处理。
- **不接入塔背包。** "角色记录当前用哪个背包、按 id 找背包、进塔时清空"是退役内存载体之后的替代形态，本任务只做退役，不做接入。
- 不改变数据库的表与列。
- 不为既有数据编写回填、修复或迁移路径。

## Constraints

- 对外可观察行为一字不变。协议帧的字节与时序、以及既有测试的语义，只允许因类型或依赖变化作机械调整。
- 一次用例内的多处持久化改动必须全有或全无；不得因拆分而退化为逐条提交。
- 跨表组装移入领域层后必须集中在单一处。散入多个调用方等于把存储结构泄漏到各处，与本任务目标相反。
- 存储实现不得自建表。建表归属已集中，拆分不得重新引入 DDL 副作用。
- 开发阶段擦库不迁移：不得为既有数据编写回填、修复或迁移路径。
- 不得改动 `Tool/` 与 `.worktrees/legacy-reference/`。
- C# 文件为 CRLF、无 BOM UTF-8；net10.0，TreatWarningsAsErrors。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 每个仓储的读写不越出单张表 | 逐仓储清点其 SQL 所触及的表，每个仓储恰好一张 |
| SC-2 | 持久化实现不自开连接 | 用例边界之外新建数据库连接的处数为零；今天为 26 |
| SC-3 | 一次用例内的多次读看到同一份快照 | 构造一次跨多表的读，在两次读之间由另一条连接提交改动，该次用例的两次读结果一致 |
| SC-4 | 一次用例内的多处改动全有或全无 | 令其中一处在写出阶段失败，用例结束后全部改动均不可见 |
| SC-5 | 跨表组装归领域层且只有一处 | 组装代码位于领域层；持久化实现中不再出现跨表拼装；该组装在领域层的定义处唯一 |
| SC-6 | 已确认无生产调用方的内存载体构造已退役 | 退役目标在生产代码与测试中均零命中，且退役未改变任何对外可观察行为 |
| SC-7 | 对外可观察行为一字未变 | 协议编解码用例与既有帧序列金样全部通过；全量结果不低于基线加本次新增 |

## Requires Confirmation

- 合并、推送、PR、分支或工作树清理。
- 任何超出上述 Scope 的范围扩张，包括拆 BLOB 列与接入塔背包。

## Assumptions

- 内存载体（`MemoryItemStore` 与其容器、工厂、工厂契约）在生产代码中无调用方，仅在测试中被构造。已核实：`CreateTransient` 全仓仅有接口声明、工厂实现、DI 注册三处，无业务调用。因此退役它不改变任何对外可观察行为。若执行期发现存在未被识别的生产调用方，退役范围须重新评估。
- 按表拆分带来的往返次数增长不构成性能问题。用户已就吞吐量给出边界（"能保证上百人并发就很不错了"），本地 SQLite 同连接下数十次简单查询为毫秒量级。
