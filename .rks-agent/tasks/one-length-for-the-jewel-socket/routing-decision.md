# Routing Decision

任务：`one-length-for-the-jewel-socket`
契约：`./TaskContract.md`（revision 2, state ready, SC-1..SC-8，含 Contract Amendment C-1）

## SDD Readiness

**就绪，而且本件的「对错」在开工前就已经判定完毕。**

- **正确值有出处**：18 读自上游 `ItemListProtocolWriter.cs` 的 `A21AvatarJewelBytes`，
  三条写法（`ItemListProtocolWriter.cs` 的 `WriteAvatarEntry126:89` 与 `WriteNoti2AvatarBlock:193`、
  `MailboxHandler.cs:1127`）引用的是同一个常量。
  本轮逐行读出，不是推断。
- **要改的位置有两处，覆盖三条帧**：`WriteNoti2EquippedItem`（`Entry.cs:152`）被两个调用方共用，
  改它即覆盖 NOTI `0x0002` 子类型 1 与消息 `0x019F`；`WriteMailboxAvatarDetail`（`Entry.cs:762`）
  覆盖消息 `0x0061`。第三条是**写 spec 前的扫描新发现的**，已由契约修正案 C-1 收进范围。
- **受影响的既有判据已点名**：`SelectCharacterPayloadCodecTests` 里那一个用例，
  它在时装槽放了珠宝槽为 `0..29` 的时装并逐偏移断言，必然要改；其余不该动。
- **有可执行判据**：全量套件在 `d94e1841` 本轮实测 2281/2/0，退出码 0。

**一处已知的、写进契约的验收限制**：实机在原理上分辨不了 18 与 30（块自描述长度，
且已测过的珠宝槽全为零）。所以本件**不做实机验证**，验收只能靠「与上游一致」
加「三条路互相钉住」。这不是遗漏，是契约 Scope Out 与 Assumptions 里明写的判断。

## Marginal Control Value

值得上 SDD，但保护的东西与前两件都不同：**这次风险几乎全在记账，不在改代码本身。**

- **改代码是一行量级的**：把 `writer.Write(30)` 与整段 `JewelSocket` 换成共用的
  18 字节写法。这一步几乎不可能写错，写错了新判据当场会红。
- **真正会出事的是「还有哪里也说了 30」**。本仓在上一件里同一类失误连犯**五次**，
  且**五次没有一次是自查发现的**（记在 `the-container-decides-the-entry-shape` 的 C-1 补充）。
  错法有三层：只顺着起因往下游追；只搜数字不搜说法；**搜索集本身没被检查**。
  本件天然踩在这三层上——`30` 这个数在仓内以多种形态存在（存储长度 30 也是 30，
  但它是对的，**不能一起改**），而「那条穿戴路径本轮未改动」是一句将被本轮推翻的**说法**，
  按 token 搜不到。需要一份写下来的验收条款，让评审有东西可对。
- **扫描已经证明这不是杞人忧天**：契约 revision 1 照抄 issue #9 写的「两条路」，
  开工前按 SC-8 做的全仓扫描当场找出**第三条**（邮件附件，消息 `0x0061`）。
  漏的那条名字里没有"NOTI-2"，按说法搜不到，只有按**这个数**搜才会现形。
  这一次是自己抓住的，但它恰好说明本件的风险面在哪。
- **另一条是「为迁就实现改断言」**：本轮必须改动一个既有用例里成串的偏移断言
  （长度 347、偏移 206/210/244/246/276/277/300）。这恰好是最容易顺手多改一处的地方，
  而多改的那一处不会有任何东西发红。契约把它列成硬约束，需要独立评审逐条核
  「每一处改动都正对应被授权的 12 字节」。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Rationale: 三件事——改写法并共用常量、重锚受影响的既有断言、更正两份协议文档——
  共享同一个验收口径：「只有时装槽上时装条目的珠宝运行缩短 12 字节，其余逐值不变」。
  按本仓规矩，同一口径下的多段工作量属于一个成果，不是三个。没有第二个互斥口径：
  issue #10 与 #11 各有独立口径（前者必须改变移动行为，后者被外部输入阻塞、
  需所有者实机逐件量），**都不在本轮范围**，因此不构成 Multi Spec 的边界。
- Reroute conditions:
  - 若「三条路共用一处」在不违反切片架构的前提下做不到（契约 Requires Confirmation 第三条），
    则结构性假设不成立，回到路由重议；
  - 若发现颜色运行或 else 分支也与上游不一致，那是**第二个验收口径**（另一处授权外的字节变化），
    必须停下另立成果，不得并进本轮；
  - 若字节锚 `SelectCharacterAcceptedTranscriptTests` 变化（SC-5 预期它不变），
    说明改动波及了未预期的路径，回到路由重议范围。

## Controller Selection

- Controller: `sdd-lite`
- Profile source: `code-bugfix`
- Rationale:

**保护的两条失败路径都不是「代码写错」**，一是「30 这个说法还留在别处没清干净」，
二是「顺手多改了一处既有断言」。挡住这两条需要且只需要两样东西：一份把验收边界
（哪 12 字节可以变、哪些必须不变）钉死的持久 Spec，加一次对**完整**结果的独立评审。
`sdd-lite` 的 spec → implementation → review → verification 恰好就是这两样。
本仓的历史也支持这个档位：前述五次遗漏与更早两次（漏 13 条新增拒绝、把「零覆盖」的
理由写成假话），**全部**是被普通的完整变更评审抓住的。

**为什么更重的 `sdd-standard` 不对**：Standard 的独有控制是 `plan.md`——提前解决实施决策
以免返工。本件没有可挂的实施决策：正确值已由上游给定，改动点是一个方法，
两个调用方无须改动，不存在跨层顺序依赖。契约里唯一的设计自由度（常量与写法提取到哪里）
只有一个明显答案（`Protocol/Game/` 的 endpoint 层，切片今天已经在调它），
写成 plan 只是把 spec 抄一遍。**文件多、条目多按选择规则明确不构成理由。**

**为什么更轻的一档不对**：更轻是不留持久 Spec、靠一次确定性检查收口。这里不行——
本件**没有**能替代验收边界的确定性检查：全量判据在改动前后都能全绿
（发 30 也对齐、也不崩），实机在原理上分辨不了两个长度。能证伪的只有
「把任一路改回 30 就会红」的对照判据与一次从代码出发的反向扫描，
两者都要先有写下来的验收条款才能对着做。

**为什么不是 `sdd-governed`**：Governed 的硬性门槛一条都不沾——不涉及安全、凭据、隐私、
财务法务、不可逆外部变更、或无恢复手段的数据丢失。最坏后果是多发 12 字节落在
客户端相邻局部上，可逆，改动全在本地未推送的任务分支上。而「独立挑战集」这一档控制
在本仓已被证明对同一失败模式不是必需的。
