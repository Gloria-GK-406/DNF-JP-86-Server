# Specification: 珠宝槽在线上只有一个长度

## Why and Outcome

时装的珠宝槽存 30 字节，A21 只把**前 18** 发上线。本仓有三条路径把它写上线，
其中一条发 18（对），两条发 30（错）：

| # | 路径 | 帧 | 今天 | 应为 |
|---|---|---|---|---|
| P1 | `GameInventoryItemEntry.WriteAppearanceBlock` | NOTI `0x000D` / `0x000E` | **18** | 18 |
| P2 | `StateSynchronizationPayloadCodec.WriteNoti2EquippedItem` | NOTI `0x0002` 子类型 1；消息 `0x019F` | **30** | 18 |
| P3 | `StateSynchronizationPayloadCodec.WriteMailboxAvatarDetail` | 消息 `0x0061` | **30** | 18 |

消费者是 A21 客户端。它按块自带的 u32 长度读，所以三个长度都能解析、都不崩——
**这正是问题不会自己暴露的原因**，也是本 Spec 的验收必须绕开「跑一下看崩不崩」的原因。

要交付的结果是：**这个长度在仓内只有一个定义，三条路都读它**。
不是「把两处的 30 改成 18」——那样改完，仓内仍有三处各自表达同一个数，
下一次谁改动其中一处，另外两处照样不会跟上。这次的债正是这么欠下的。

## Scope

**做**：P2 与 P3 改为发 18；三条路共用一处长度定义与一处截断/补零写法；
新增能证伪的判据；重锚唯一受影响的既有用例；更正两份协议文档。

**不做**：不改存储侧的 30（存储确实是 30，`SocketCount 5 × EntrySize 6`）；
不改颜色运行；不改 P2/P3 的其余任何字段；不新增协议帧；
**不做实机验证**（见 `NA-001`）；不碰 issue #10 / #11。

## Definitions

- **珠宝运行（jewel run）**：写在条目里的 `u32 长度 L` 加紧随其后的 `L` 个字节。
  三条路的形状相同：`u32 L + L 字节`，随后是颜色运行 `u32 4 + u16 Color1 + u16 Color2`。
- **存储珠宝槽**：`InventoryAvatarDetailState.JewelSocket`，恒 30 字节
  （`CHECK(avatar_jewel_socket IS NULL OR length(avatar_jewel_socket) = 30)`）。
- **线上珠宝长度**：珠宝运行的 `L`，A21 为 18。本 Spec 要收敛的就是它。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 线上珠宝长度在仓内**只有一处定义**，值为 18，三条路（P1/P2/P3）都读它。 |
| RQ-002 | 「从存储珠宝槽截取前 `L` 个字节、不足则补零」这个写法在仓内**只有一处实现**，三条路都用它。 |
| RQ-003 | P2 的时装条目（`ItemKind == 8` 且槽位 `0..11`）珠宝运行为 `u32(18) + 存储的前 18 字节`。 |
| RQ-004 | P3 的时装附件珠宝运行为 `u32(18) + 存储的前 18 字节`。 |
| RQ-005 | P2 的非时装条目在时装槽仍写 `u32(0)` 且不跟任何字节——**这一支不变**。 |
| RQ-006 | 颜色运行在三条路上都保持 `u32(4) + u16 + u16`，逐字节不变。 |
| RQ-007 | 存储侧的 30 保持不变：存储校验、建表约束、装配层校验、以及以 30 为长度的判据夹具，一个都不动。 |
| RQ-008 | 除 RQ-003 与 RQ-004 各自缩短 12 字节外，所有帧逐字节不变。 |
| RQ-009 | 受影响的既有断言只有一个用例；对它的每一处改写都能归因到 RQ-003，且不得顺带改动别的断言。 |

### RQ-001 与 RQ-002 的边界

「只有一处」指**本仓生产代码**。判据里可以为了断言而再写一次 18，但那必须是
**从生产常量读出来的**或**故意写死用来对照的**，不能是第三个独立事实源。
Spec 不规定这一处放在哪个类型里——`Protocol/Game/` 的 endpoint 层已是既有通路
（`StateSynchronization` 切片今天就在调 `GameInventoryDelivery`），但具体形态归实现决定。

### AC-003 场景

```gherkin
Given 一个助战角色，其 Equipment 容器的槽位 2 放着一件 ItemKind == 8 的时装
  And 该时装的存储珠宝槽是 30 个互不相同、可分辨的字节（例如 0x00,0x01,…,0x1D）
When 编码消息 0x019F（EncodeSupportCharacter）
Then 该条目里珠宝运行的长度字段是 18
  And 其后的 18 个字节逐字节等于存储珠宝槽的第 0..17 字节
  And 存储珠宝槽的第 18..29 字节不出现在这一帧的任何位置
```

**「不出现」这半句是必需的**：只断言前 18 字节相等，无法排除实现把 30 字节全写了
而后 12 字节恰好排在别处。用可分辨填充加「后 12 字节不在帧内」才能同时排除
「发了 30」「截了后 18」「补的零」三种错法。

同一条件在 `EncodeExtendedUserState`（NOTI `0x0002` 子类型 1）上必须得到同样结果，
因为两个调用方共用同一个写法——**判据要对两个调用方各测一次**，而不是只测一个就
声称覆盖了两条帧：共用是今天的实现事实，不是被 Spec 保证的性质。

  And 其 DetailJson 的 Avatar.JewelSocket 是 30 个互不相同、可分辨的字节

### AC-011 收敛判据

这是本 Spec 唯一能真正保住 RQ-001 的判据，其余判据都只能证明「今天的值是 18」。

要求：**一条判据把三条路的珠宝运行长度放在一起比较，断言三者相等**，而不是分别断言等于 18。

理由：分别断言 18 的判据，在「有人把三处都改成 20」时**不会红**——它证明的是数值，
不是收敛。而本件要保的正是收敛：这个数将来若要改（例如查清了 A21 其实发别的长度），
应当改一处而三条路一起动；判据要能在「只动了其中一条」时立刻红。

该判据必须满足：

1. 三条路各用同一份可分辨的 30 字节存储珠宝槽，各自编码出真实的帧字节；
2. 从三份输出里**各自解析出珠宝运行的长度字段**（读那个 u32），断言三者相等；
3. 变异验证：把任一条路单方面改回 30，该判据必须红。**三条路各做一次**，
   每次指名是哪一条判据、报什么错，还原后确认恢复绿。

变异验证按契约用**文件级备份 + `sha256sum`** 做，禁止任何 git 还原类命令。

## Assumptions and Non-acceptance

| ID | |
|---|---|
| AS-001 | **18 来自上游源码读出**：`ItemListProtocolWriter.A21AvatarJewelBytes`，被上游三处引用（`ItemListProtocolWriter.cs:89`、`:193`、`MailboxHandler.cs:1127`）。不是实机测得。 |
| AS-002 | 存储 30 字节 = `SocketCount 5 × EntrySize 6`，A21 只发前 3 个孔。上游 `WriteFixedBytes` 从 30 字节列里截前 18。上游读出。 |
| AS-003 | 颜色是 `ushort`：`InventoryModels.cs:155-156` 声明为 `ushort`；既有判据在相隔 2 字节处各读一个 u16 并通过，独立佐证。**不要"修"它。** |
| AS-004 | 时装槽边界 `0..11`（`Entry.cs:296`）。本轮不改。 |
| NA-001 | **实机不作为验收手段，这是原理性的。** 珠宝运行自带长度，客户端按它给的长度读，所以 18 / 30 / 任意值都对齐、都不崩；且已实机测过的时装珠宝槽全为零，18 个零与 30 个零无从分辨。上一个成果「11 件时装全过」证明的是**形状机制**成立，不是这个长度正确。**任何交付物都不得把「不崩」写成本件的证据。** |
| NA-002 | 「多发 12 字节会落在客户端目标缓冲之后」由**静态反汇编量得、未实机验证**，是动机不是依据。本件的依据是 AS-001。 |
