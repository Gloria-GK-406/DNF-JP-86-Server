# Spec: Item rules in the bag

## Outcome

背包实例对外提供三个领域动词——**放入**、**补充**、**移动**——每个都在内部完成判定并执行，
并把「落在哪里、放进多少、或者为什么没放」交回调用方。调用方不再持有物品规则，也不再自己把
到货判决翻译成写入。

对外协议行为一字不变。

## What must become true

### RQ-1 背包能放入一件到货的物品

给定一件物品的编号与数量，背包自行查出它的摆放声明、算出它落在哪个格子、并写下去。

三种结果，缺一不可：

| 结果 | 何时 | 携带 |
|---|---|---|
| 放下了 | 有可落之处 | 落在哪个格子、这次放进多少、该格子放完之后共有多少 |
| 放不下 | 该物品的格子带里没有空位，且没有可续的堆 | 无 |
| 不认识这件物品 | 档案里查不到它的摆放声明 | 无 |

「放下了」必须同时覆盖续在已有堆上与占用一个空格两种情形，且两种情形下的三个数都要正确——
续堆时「这次放进多少」小于「共有多少」，占空格时两者相等。

判定用的是今天已有的授予规则（认叠加上限、装不下的部分溢出到新格），不是新规则。

### RQ-2 背包能执行一次每日补充式的到货

补充与放入是两条规则，不能互相替代：补充并入任一已有堆而不看叠加上限（数量已由上游规则算过），
放入则把堆填到叠加上限为止再溢出。

补充的格子带与物品类别由调用方给出——它们来自每日补充规则，是数据不是规则；
选哪个格子、并到哪个堆、写什么，由背包决定。

结果的三种形态与 RQ-1 相同。

### RQ-3 背包能在自己内部移动一件物品

给定来源格、目标格与数量，背包自行判定这是一次搬移、拆分、交换还是并堆，并执行；
或者说出它为什么不做。

必须保留今天全部五种拒绝，逐条可构造：

- 两个格子都是空的
- 该物品不能占用它被拖到的那个格子
- 并堆会超出该物品的叠加上限
- 只拖了一部分却要求交换
- 被顶开的那件不能占用被腾出的格子

以及今天两种非拒绝的结果：搬成了（携带实际移动的数量与物品编号），
以及「两端是同一个格子」这种什么都没发生但不算失败的情形。

今天存在的「来源格是空的则两端对调」这一读法必须保留：客户端在指定它想填的格子时会这样发送。

### RQ-4 把到货判决变成写入的那一段，在整个代码库中只有一处

今天教程奖励与每日补充各写了一份。改动后只剩一份，两条路都经由它。

### RQ-5 协议工程不再持有物品规则

摆放声明、格子带、到货这三类规则服务不再被 `Dfo.Server.Protocol` 引用。
移动的命令处理器只剩：把请求转成命令、把结果翻成客户端码。

### RQ-6 三处调用方的对外行为逐条不变

改动后必须仍然成立：

| 调用方 | 遇到「放不下」 | 遇到「不认识这件物品」 | 成功时 |
|---|---|---|---|
| 教程奖励 | 该件被排除在回执之外，其余各件照常处理 | 同左 | 回执里是落点、物品编号、这次放进多少 |
| 每日补充 | **抛出**，整个入场失败 | 不适用（补充规则自带类别；类别为 0 时今天抛，须保留） | 提交记录里是容器类型、落点、物品编号、这次放进多少、共有多少 |
| 移动物品 | 不适用 | 按「不能占用该格子」拒绝，与今天一致 | 回执里是实际移动的数量与落点 |

教程奖励的「一步声明多件时，后一件看得见前一件已经写下的东西」必须保留。

### RQ-7 每日补充改走背包后，行代理键的变化不外溢

每日补充今天用行代理键定位要更新的堆；改走背包后写入按格子定位，代理键会变。
必须有一条用例证明：代理键变了，而对外投影不变。

### RQ-8 两处与本裁定相反的注释被订正

- `IItemContainer` 的接口注释今天写着复合动作的拼装属于上层，并以「其下的存储也要被告知」为由。
  该理由今天已不成立。注释须改为说明现在的划分：判定与拼装在背包内，存储仍只知道读与写。
- `ItemContainers.cs` 中说那些问题「是协议的问题」的那一句，须改为它们现在的归属。

`ItemContainerOperations` 本身继续不作任何判定——这一点在两处注释中都要说清楚，
因为它正是「拼装不需要存储知情」的现成证据。

## Boundaries

- 不实现跨容器移动。请求里的非主列表仍按今天拒绝。
- 不改动客户端错误码及其翻译。移动的拒绝原因在领域里说，翻成哪个码仍在协议里决定。
- 不改动持久层形状，不让背包自建表或自持数据库。
- 不为这三个动词另开「能不能做」的查询。
- 不改动三份整记录表征用例的期望值。
- `ItemContainerOperations` 继续不判定。

## Known coverage gap this Spec must close first

教程奖励的落位行为今天**没有直接用例**——它只在 `ExitFlushHandlerTests` 中作为协作者出现。
它的两条只写在注释里的语义（「装不下则排除在回执之外」、「后一件看得见前一件」）
因此没有任何守卫。迁移之前必须先为今天的行为立用例，否则迁移把它们改掉不会有东西变红。

每日补充相反，`SqliteEntryInventoryMutationRepositoryTests` 已用真库钉住它，可直接作为迁移的判据。
