# Spec: The character instance

## Outcome

人物仓库交出一个**可操作的人物**，而不只是一份快照。它按需交出，没有自己的生命周期——
一个角色恰好一个实例，而一个不持状态的实例没有什么可以在选人时准备、也没有什么可以在退出时释放。
「这个角色能不能用这件物品」由它回答；它供身份，规则服务作判决，判决那一半不再解析任何身份。

对外协议行为一字不变。

## What must become true

### RQ-1 有一个可操作的人物，由仓库交出

它由人物侧的仓库交出，按角色定位，不缓存状态：每次回答都读当下。

它**不需要一套自己的生命周期**。背包要注册，是因为一个角色可以持有同一类型的多个背包并在其间
切换，注册表承载的是「当前用哪一个」；人物没有这回事，一个角色恰好一个实例，而一个不持状态的
实例没有什么可以在选人时准备、也没有什么可以在退出时释放。它只在角色被选中时能回答问题——
那不是生命周期，那是它读到的东西恰好只在那时存在，与今天一模一样。

### RQ-2 「能不能用这件物品」由人物回答

用消耗品的用例向人物提问，不再收一个替它找角色的服务。
提问的结果与今天完全一致，含六种判定与它们的先后。

### RQ-3 判决那一半是纯的

作判决的规则服务只吃它要比较的东西——档案的声明、等级、职业族、所在地、是否在冷却——
吐一个判决。它的签名里不出现 `CharacterId` 或 `AccountId`，它不查目录也不读库。

清点全仓的规则服务，此后没有一个签名带身份。仓库类与注册表不在此列：带身份是它们的本分。

### RQ-4 六种判定与它们的先后逐条不变

必须逐条可构造：不是可用物品、等级不足、职业不符、所在地不允许、冷却中、角色状态不可得，
以及允许。

**先后也必须不变**：永久性的原因先问，冷却最后问。把冷却报在等级前面，是打发玩家去等一件
等到了也用不了的东西。这一条**已经有守卫**——见下方「一处已核实的判断更正」。

### RQ-5 「所在地读不到就按村庄算」这条宽松默认保留

在场记录缺失时算村庄，不算未知。这是刻意的：地下城尚未开服，正在游戏的人就在城镇。
这一条**也已经有守卫**——见下方「一处已核实的判断更正」。

### RQ-6 设计文档的未决项之一被裁定

`Docs/Refactor/DomainInstanceDesign.md` 留了「人物实例是否就是运行时会话态」。
本成果有实物在手，须给出裁定、理由、以及它依赖的前提；不得留成待办。

## Boundaries

- 不改快照的形状。
- 不给人物加写入动词。
- 不搬动物品使用的效果应用。
- 不改客户端错误码及其翻译。
- 不改判定所读的权威来源：今天读运行时目录，改后仍读它。
- 三份整记录表征用例的期望值不改。

## 一处已核实的判断更正

这份 Spec 起初写着两条规则「只活在注释里、没有任何断言」，并要求迁移前先补用例。
**那个判断是错的，已实测推翻**，因此这里不补冗余用例，改为记下证据：

| 规则 | 故意改坏 | 结果 |
|---|---|---|
| 永久性的原因先问、冷却最后问 | 把冷却检查提到等级检查之前 | 红 `ItemUsabilityDomainServiceTests.A_permanent_reason_is_reported_ahead_of_one_that_will_expire` |
| 在场记录缺失按村庄算 | 把默认翻成地下城 | 红两条：`ItemUsabilityDomainServiceTests.An_item_only_usable_in_a_dungeon_is_refused_in_town` 与 `UseStackableHandlerTests.An_item_only_usable_underground_is_refused_in_town` |

两次都逐字节复原。这两次真改真跑同时充当 AC-8 要求的可证伪演示中的两次：
它们证明的正是迁移最可能无声改掉的两件事。
