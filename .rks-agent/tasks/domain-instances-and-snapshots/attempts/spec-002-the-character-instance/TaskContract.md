# TaskContract: The character instance

## Context

### Source Request

父控制器在 `child_modeling` 阶段派生的第二个子成果。根授权：
「既然你有更好的想法，那就按你的跑吧。重构结束后再找我」。

### Current Situation

人物仓库（`ICharacterDomainService`）今天只交出**快照**——`ActiveCharacterState`，一个没有行为的
record。因此「这个角色能不能用这件物品」写不成 `character.CanUse(item)`，只能写成一个收着
`CharacterId` 的服务：`IItemUsabilityDomainService.CanUseAsync(characterId, itemId, ct)`
（`ItemUsabilityDomainService.cs:28`）。

那个服务因此同时做两件事。它先**解析身份**——按角色找会话、按会话找运行时目录、取出
`ActiveCharacterState`（`:71`）——再按档案的声明比较四件事：等级、职业、所在地、冷却。
全仓的规则服务里，只有它的签名带身份。

`Docs/Refactor/DomainInstanceDesign.md` 已裁定：仓库交出快照与实例两种产物（R-5），
实例是入口而非容器（R-3），有注册的实例在选人时造、没有注册的按需造（R-4），
规则服务不解析身份、不读库（R-6）。

该文档还留了一处未决项：**人物实例是否就是运行时会话态**。
`ISelectedSessionRuntimeDirectory` 已经按选人持有一份内存里的 `ActiveCharacterState`，
而可用性判定读的正是它而不是库。本成果有实物在手，须裁定它并写回文档。

## Goal

人物成为一个可操作的实例：由人物仓库交出，且只在角色被选中时能回答问题；
「这个角色能不能用这件物品」经由它表达；随之，全仓最后一个签名带身份的规则服务
拆成「实例供身份、规则服务作判决」两半，判决那半不再解析任何身份。

对外协议行为一字不变。

## Scope

### In

- 人物实例类型，及交出它的仓库接缝。它只在角色被选中时能回答问题，未被选中时的答案与今天一致。
- 物品可用性判定经由实例表达；`UseStackableCommandHandler` 改为向实例提问。
- 可用性的规则比较提取为一个**纯**规则服务：签名里不出现身份，不读库、不查目录。
- 裁定设计文档的未决项「人物实例是否即运行时会话态」，写回文档并说明理由。
- 随上述改动而来的测试改写与新增。

### Out

- 快照重塑（`ActiveCharacterState` 改为一组领域记录）——那是下一个成果。
- 人物的写入动词（等级、经验、位置）。今天没有调用方需要它们经由实例表达，
  凭空加上去是替将来的用例猜形状。
- `ItemUseEffectDomainService.ApplyAsync` 的归属（设计文档未决项之三）。本成果只在有实物时记录判断，
  不搬动它。
- 跨实例操作。
- 客户端错误码及其翻译。

## Constraints

- **C-1** 六种可用性判定的结果逐条不变，且各自仍可构造：不是可用物品、等级不足、职业不符、
  所在地不允许、冷却中、角色状态不可得。
- **C-2** 三份整记录表征用例的期望值不得修改。
- **C-3** 判定的**先后次序**不得改变。永久性的原因先问、冷却最后问，这是刻意的：
  把冷却报在等级前面，会打发玩家去等一件等到了也用不了的东西。
- **C-4** 不得为实例的判定另开与执行并行的查询之外的第二套规则。
  可用性本身是一个「做之前就要答案」的判定，可以继续以查询形式存在。
- **C-5** 实例不缓存状态，只持身份与依赖（R-1）；不自建表、不自持数据库（R-7 的落地方式沿用背包）。
- **C-6** accept 时构建零警告、全量测试通过。
- **C-7** 删除任何测试文件前逐条核对其断言证的是不是即将消失的东西。
- **C-8** 沿用根契约 C-7 的既有项目约束。

## Assumptions

- 可用性判定今天读的是运行时目录里的 `ActiveCharacterState`，不是数据库。本成果**不改变谁是权威**；
  改变权威会改变行为，且属于快照重塑那一块的问题。此假设由 SC-B4 的六条用例钉住。
- **修订说明（revision 2）**：本契约 revision 1 曾要求人物实例「在选人时造、退出时清」，
  照搬背包的生命周期。建模落地时判定那条要求没有依据：背包需要注册，是因为一个角色可以持有
  同一类型的多个背包并在其间切换，注册表承载的是「当前用哪一个」；人物没有这回事，
  一个角色恰好一个实例。实例又不持状态（R-1），所以注册表只会带来一套没有用途的生命周期，
  并迫使每个调用方处理一个不可能发生的「取不到实例」。设计文档 R-4 给的理由是分配开销，
  而同一文档的规模前提写明「性能不是裁判」。故改为按需交出，并同步修订 R-4。
- 全仓签名带身份的规则服务只有可用性判定一处。已核实：槽位、到货、每日补充三个规则服务的签名都不带身份；
  按表仓储与容器注册表带身份，但它们是仓库类而非规则服务。此假设由 SC-B3 的逐个清点钉住。
