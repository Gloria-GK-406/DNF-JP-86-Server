# Spec: The snapshot in domain shape

## Outcome

以协议段命名的记录在领域里**不再存在**——不是搬走，是没有了。存储侧按概念承载，
入场侧按概念承载，而把这些概念摆成包里那一长串字段、并把每个值收窄到它在线上的宽度，
是编解码器写字节时做的事。

下发帧一字节不变。

## What must become true

### RQ-1 存储侧按概念承载

`CharacterProfileStorageRecord` 不再持有两个按段序拍平的记录，而是持有它们本来就来自的那些概念：
运营态、设置、PvP、专家职业、派生数值、公会站位，以及角色本体自己的那几样
（技能树序号、名牌物品与到期、管理等级）。

`CharacterEntryAssembly` 不再有把四张表拍成一个记录的方法。它现在把每张表映射成它自己的概念。

### RQ-2 入场侧按概念承载

`CharacterPublicEntryState` 同样不再持有段记录。它持有同一组概念——**与存储侧完全相同的那一组**。

这一条比本 Spec 起初写的要少做一件事，如实记在这里：起初写的是入场侧「用领域的类型，
0 与非 0 已经变成真假」。实施时判定那样做会把两族记录又拆回两族——存储侧的行是整数，
入场侧若改成真假就不能共用同一个记录，而共用正是删掉那 45 字段按位复制的前提。
所以 0 与非 0 留作整数，在写字节的那一行变成 0 或 1 的字节。
代价是入场侧的八个字段由 `bool` 退回 `int`，比基线弱了一点自证性；换来的是两族合一。

### RQ-3 段布局与位宽收窄发生在编解码器

哪个字段、什么次序、收窄到几个字节，全部在写字节的地方。今天有一段 45 字段的按位复制专做收窄，
它消失：收窄跟着字段一起进入 `writer.Write(...)` 那一行。

**收窄是行为不是格式**：值超出该字段的宽度时今天会抛，改后仍在同一个概念上抛。

### RQ-4 领域服务按名字读事实

`SelectCharacterPreparationService` 与选人处理器不再写 `entry.Public.Subtype1.Progress1`，
而是从它所属的概念上读。

### RQ-5 下发帧一字节不变

三份整记录表征用例的期望值与协议编解码用例的期望字节都不改。

## Acceptance

| ID | Condition | Evidence |
|---|---|---|
| AC-1 | RQ-1 成立 | `CharacterProfileStorageRecord` 的每个成员可指出其概念；装配器里没有按段拍平的方法 |
| AC-2 | RQ-2 成立 | `CharacterPublicEntryState` 的每个成员可指出其概念 |
| AC-3 | RQ-3 成立 | 全仓搜索 `Subtype0` / `Subtype1` 命名的记录类型，**零命中**；收窄语句全部在 `Dfo.Server.Protocol` |
| AC-4 | RQ-4 成立 | 两处调用点按名字读 |
| AC-5 | RQ-5 成立 | 两组期望值 `git diff` 为空；全量通过 |
| AC-6 | 结果是绿的 | 构建零错误零警告 |
| AC-7 | 可证伪 | 至少四次先红后绿：字段错位一格、收窄丢失、真假转换反向、装配取错概念 |

## Boundaries

- 不改下发帧任何字节或字段次序。
- 不改持久层形状。
- 不动物品侧与账号侧的快照。
- 不改客户端错误码。
- 三份整记录表征用例与协议编解码用例的期望值不改。

## What this Spec relies on

78 个字段在两次搬运中按位置对应，错一格不会有编译错误——相邻字段常是同一种整数类型。
唯一挡住它的是三份整记录表征用例：它们逐字段断言，错位就会红。
因此本 Spec 的每一步都以「那三份用例的期望值一字未改而全绿」为判据，而不是以编译通过为判据。
