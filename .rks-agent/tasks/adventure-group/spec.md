# Specification: 冒险团按账号派生、通关经验加成与升级推送

## Why and Outcome

A21 客户端已经有完整的冒险团界面、四维加成和升级动画，但服务端一直给它 0。本 Spec 交付的结果是：
- 服务端从账号现有角色的等级现算出冒险团等级与点数，并由唯一的冒险团领域服务对外提供；
- 发包、通关经验加成、升级推送都从这个领域服务取值；
- 不再使用的 `characters.manage_level` 列随 schema v5 删除。

数据的使用方有三个：
- 客户端：冒险团窗口、查看他人、结算面板、升级动画；
- 经验结算；
- 实机验收：由用户执行。

## Definitions

规则表全部来自 PVF `etc/linksystem/charactermanage.etc`，只经冒险团规则服务读取。下文记号：

| 记号 | PVF 段 | A21 内容 |
|---|---|---|
| `bonus[i]` | `[point bonus]` 第 i 级的点数 | i=40..70 为 100+5(i−40)；i=71..100 为 260+10(i−71)；表外为 0 |
| `T[k]` | `[manage level point]` 第 k 个阈值（k=1..10） | 1375 5425 10850 21700 37975 54250 75950 101575 133725 175350 |
| `M` | `[manage level max]` | 10 |
| `E[k]` | `[exp bonus]` 第 k 级的经验加成率 | k=1..10 均为 10% |

- **角色点数** `P(L) = Σ_{i=1..L} bonus[i]`。例：P(39)=0，P(40)=100，P(50)=1375，P(70)=5425，P(86)=10785。
- **账号角色集** 是该账号 `delete_flag = 0` 的全部角色，取其当前等级。
- **账号点数** `S = min(Σ P(L_c), T[M])`，c 取遍账号角色集。
- **冒险团等级** `G = max{ k ∈ 1..M : S ≥ T[k] }`；没有满足条件的 k 时 G = 0。
- **通关经验加成率** `R(c)`：取 G 和账号角色集中的最高等级 `Lmax`。G = 0 或 `L_c ≥ Lmax` 时 R(c) = 0，否则 R(c) = E[G]。同级也算最高，所以只有账号内存在等级严格更高的其他角色时才有加成。
- **冒险团分量**：通关结算中按 `floor(通关基础经验 × R(c))` 得到的独立经验项。通关基础经验与现有成长契约、秘药、黑钻等通关加成使用的基数相同，不含评价加成。
- **世界中**：账号当前会话已选定角色，并且该角色处于城镇或副本，不在选人界面。

## Scope

**包含**：
- 冒险团规则服务与领域服务；
- 在通关结算中加入冒险团分量；
- 四处发包填值；
- `0x01A0` 升级推送；
- schema v5 删列及其迁移；
- 迁移说明文档；
- 协议资料库更新；
- 在主干库备份副本上的用户测试准备与结果记录。

**不包含**（契约 Scope Out）：
- 金币加成；
- 击杀经验、任务经验，以及死亡之塔、迷妄之塔结算的冒险团加成；
- 支援兵与佣兵记录；
- 冒险团名、冒险团仓库、冒险团称号；
- AdventurerMaker；
- `0x0466`；
- subtype2 写非零值；
- 服务端在属性块中计入冒险团四维；
- 合并、推送、PR；
- 在原主干库上原地迁移；
- 改动用户角色进度。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 冒险团规则服务从 PVF 解析 `bonus`、`T`、`M`、`E`（金币表可以解析但不使用），并按 Definitions 计算 P、S、G、E。PVF 中 `[manage level max]` 缺闭合标签、`[contents revision]` 以开标签结尾，这两处都不能导致解析失败或取值偏差。规则服务不查询角色或账号状态。 |
| RQ-002 | 冒险团领域服务是唯一 owner，对外回答两个问题：<br>(a) 账号 → (G, S)；<br>(b) 角色 → R(c)。<br>每次查询都从账号角色集的当前等级现算，不持久化任何冒险团状态，包括已推送等级等进度。其他代码不得自行计算 G、S、R。 |
| RQ-003 | 普通通关结算（含绝望之塔、镜像副本等走普通通关结算的场合）：在角色获得的经验中加入冒险团分量，在经验分解中作为独立一项，并写入 NOTI `0x0023` body+45。 |
| RQ-004 | 领主之塔通关结算：同样加入冒险团分量，但沿用现有处理，即不发 `0x0023`、合计封顶 1,100,000、按加成项顺序扣减剩余额度。触及封顶时冒险团分量可能被截短，合计不得超过封顶。 |
| RQ-005 | 不受冒险团加成影响的结算：死亡之塔/迷妄之塔结算、击杀经验、任务经验。 |
| RQ-006 | 发包填值：<br>• USERINFO1（NOTI `0x0002` subtype1）尾部写本账号的 G（u8）和 S（i32）；<br>• subtype3 +3 写被查看角色所属账号的 G；<br>• `0x01BA` 的应答和入场批次推送写 `01, G, S, 00`；应答按连接的已登录账号取值，选人界面（尚无已选角色）的询问也一样，未登录的连接写 0；<br>• subtype2 头部 +5、+6 在选人界面和入场批次两条路径都写 0。 |
| RQ-007 | 升级推送：<br>• 任一路径使某角色等级从 before 变为 after 时，令 a = 账号角色集中该角色取 before 时的 G，b = 该角色取 after 时的 G；<br>• b > a，且账号此时处于世界中，则向该账号会话推送 b−a 帧 NOTI `0x01A0`（空 body）；<br>• 其余情况不推送，包括 b ≤ a、不在世界中、角色已删除；<br>• 每次等级变更最多推送一次，事件重放、重启补投、重复投递都不得多推；<br>• 推送不能与同一时刻发出的、带新 G 的 USERINFO1 或 `0x01BA` 叠加，导致客户端多加级。 |
| RQ-012 | 登录进入世界时，客户端不出现冒险团升级提示；冒险团真正升级（RQ-007 推送）时提示照常出现。先查明客户端出现该提示的条件，并在协议记录中写明证据来源与置信度，再按查明的条件修正服务端行为。若查明无法由服务端消除，停下交用户决定（契约 Requires Confirmation）。 |
| RQ-008 | schema v4 → v5：<br>• 新建库为 v5，`characters` 表没有 `manage_level` 列；<br>• `Tool/DbMigrate` 有 v4→v5 步骤，迁移后的结构与新建库一致，原有数据不丢；<br>• 服务端代码不再读取或传递该列（契约 SC-6 的允许清单除外）；<br>• `Document/DatabaseSchemaMigration.md` 写明 v4→v5 的内容与升级方式。 |
| RQ-009 | 协议资料库：<br>• `0x01BA`、`NOTI-0x0002`、`NOTI-0x0023`、`NOTI-0x01A0` 的人工区写明字段含义、证据来源、置信度与实现状态；<br>• `catalog.md` 同步更新；<br>• 没有实机样本的结论不标 ClientVerified。 |
| RQ-010 | 用户测试：<br>• 取当前主干库的一致备份，在副本上执行 v4→v5 迁移，用副本启动本分支的测试服；<br>• 测试服使用 agent 端口段，或经用户同意使用默认端口；<br>• 给出编号测试流程，开头写明在副本上进行、进度不回写主干库；<br>• 流程列明双客户端前置：第二个账号、同频道同城镇、第二客户端目录及其 `ClientHack.ini [ServerRedirect]` 与启动器指向；<br>• 每步写出预期值，预期值由领域服务规则对副本中实际角色等级算出；<br>• 用户反馈的结果、证据路径与未覆盖项记入 `Document/tasks/adventure-group/`。<br>测试中如有任一显示项与预期不符（例如查看他人的冒险团等级），记录现象并交回用户裁定，不自行改协议含义。 |
| RQ-011 | 构建无警告，全部测试通过。 |

## Constraints

- 契约 Constraints 全部适用：单一 owner；不持久化；PVF 只经规则服务读取；规则以 70 为准，只有两处例外；schema 改动的三件事在同一改动里完成；证据标签。
- 推送靠"事件只处理一次"或等价机制保证不重复，不能靠持久化冒险团等级（RQ-002）。

## Assumptions

沿用契约 Assumptions：
- `0x01A0` body 为空；
- 客户端收到 `0x01A0` 时给等级加 1；
- USERINFO1 和 `0x01BA` 两处都要填值；
- subtype2 写 0 是安全的；
- 会话中途等级下降不推送；
- `characters.level` 与权威等级一致。

实机证伪任何一条时，按契约 Requires Confirmation 交回用户。
