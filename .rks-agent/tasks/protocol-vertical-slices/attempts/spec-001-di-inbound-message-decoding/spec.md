# Specification: DI-Driven Inbound Message Decoding

## Why and Outcome

入站字节到类型化消息的映射目前由两处集中分支承担：每接入一个协议就要在其中增加一个分支，每退役一个协议就要在其中删除一个分支。协议目录预期增长到 600 以上，这两处将成为所有协议接入的必经修改点，也是唯一一处"忘了改就静默丢包"的地方。

变更后，一个入站协议的解码由该协议自己的解码单元与一条注册承担；接线不再是对共享分支的修改，而是对注册集合的增补。同时，"某个已接线协议没人处理"这一缺口从运行时收到该消息才暴露，提前到启动即暴露；而"目录中登记了但尚未接线"变为合法状态，因为目录要承担协议全量清单的角色，其成员数必然远大于已接线数。

现有 14 个入站协议的解码结果与丢弃行为在变更前后逐字段一致——本次变更不改变任何一个字节的含义。

## Task Perspective

- Core outcome: 入站协议的接线成为一处局部注册，使协议数量的增长不再推高任何共享代码的修改面。消费者是后续持续接入协议的开发者，其需要的是"新增协议时不必读懂也不必触碰其他协议的接线"。
- Necessary support: 解码结果与丢弃语义逐字段保持不变；传输层与领域编排层之间的编译期分层不因新增的注册接缝而放宽。若不成立，结构收益会以线级不兼容为代价。
- Peripheral assurance: 启动期的接线缺口检查与目录登记宽容度，虽本身是防护性控制，但 TaskContract 将其列为必须交付的可观察控制（CSC-5、CSC-6），故作为要求而非仅作为证据；回归测试基线保留在证据中。

## Scope and Non-Goals

### In Scope

- 入站线上帧键到类型化消息的映射方式。
- 现有 14 个入站协议的解码接线。
- 启动期对"已接线协议缺少处理器"的检查，以及对"目录已登记但未接线"的容忍。
- 未识别入站帧的丢弃行为。

### Non-Goals

- 出站消息的编码与发送。
- 协议相关代码的目录归属与项目划分。
- 任何协议的字节语义、长度校验规则与解码失败时的异常类型及措辞。
- 消息类型目录的成员集合与取值。
- 类型化消息的字段构成，以及消息处理器与命令的行为。
- 帧头的拆包与组包。

## Constraints

- 解码失败与不识别一律不得升级为可观察的对外反应：不抛出到连接处理之外、不产生新的日志、不回送任何字节。
- 传输层不得获得对领域编排层的编译期依赖。
- 不得以放宽类型、放宽可见性要求或抑制编译诊断的方式达成结构目标。

## Definitions

| Term | Meaning |
|---|---|
| 线上帧键 | 由帧头决定的入站消息身份：Game 端点为 command 与 type 的组合，Channel 端点为消息号。取值范围开放，客户端可发送任意值。 |
| 消息类型目录 | 服务端自行定义的语义消息清单（`ClientMessageType`）。取值范围封闭，是协议的全量登记处，其成员数可大于已接线协议数。 |
| 解码单元 | 承担单个线上帧键解码职责的单元。输入为帧元数据与帧体，输出为一条类型化消息或"不产出"。 |
| 接线 | 一个协议同时具备解码单元与消息处理器的状态。仅在目录中登记不构成接线。 |
| 静默丢弃 | 服务端对该帧不产生任何可观察反应：不抛出、不记日志、不回送字节，连接保持。 |

## External Behavior and Data Rules

- Game 端点仅接受 command 为 `0x01` 的帧；其余 command 的帧不产出消息。
- 线上帧键与消息类型不是一一对应：单个线上帧键可依帧体内容产出不同的消息类型，也可不产出消息。`GET_USERINFO`（type `0x0008`）即依帧体 mode 字节分流。
- 一条已产出的消息携带其消息类型，处理器的选择依该类型进行。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 入站线上帧键到类型化消息的映射由逐协议的解码单元注册提供，不存在随入站协议数量增长而必须修改的共享消息构造分支。 |
| RQ-002 | 接入一个新入站协议的解码只需增加该协议自己的解码单元与其注册，不修改任何既有协议的解码单元、既有注册项或共享映射代码。 |
| RQ-003 | 现有 14 个入站协议的解码结果与变更前逐字段一致，包括各协议的长度校验判定与解码失败时的异常类型及措辞。 |
| RQ-004 | `GET_USERINFO` 依帧体分流的行为保持：仅当 mode 为 `0x02` 且 target 为无目标哨兵 `0xFFFF` 时产出账号花名册请求，其余组合与非法长度均不产出消息。 |
| RQ-005 | 未注册的线上帧键、command 非 `0x01` 的 Game 帧、以及解码单元不产出消息三种情形，均被静默丢弃。 |
| RQ-006 | 已产出的消息携带消息类型目录中的身份，处理器依该身份被选中。 |
| RQ-007 | 消息类型目录中只登记而未接线的成员不导致启动失败。 |
| RQ-008 | 已注册解码单元申报的产出消息类型若无对应处理器，启动即失败，且失败信息指名缺失的消息类型。 |
| RQ-009 | 传输层与领域编排层之间的编译期分层不放宽，两者仅经既有接缝相连。 |

## Assumptions

- 帧体在派发前的同步路径上可读，故解码单元以只读方式接收帧体不改变现有生命周期假设。
- Channel 端点的四个协议不解码帧体，其解码单元仅依消息号构造消息。
- 现有各协议解码向量测试足以判定"逐字段一致"，无需为此新增等价性测试。
