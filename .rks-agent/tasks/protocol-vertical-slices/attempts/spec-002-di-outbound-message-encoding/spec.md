# Specification: DI-Driven Outbound Message Encoding

## Why and Outcome

出站方向仍保留着入站已经消除的那个形状：一处集中的按消息分支，每接入一条出站消息就要在其中增加一支。它比入站那两处更糟一层——编码与端点校验写在同一个模式里，于是"这条消息编成什么字节"和"这条消息允许发往哪个端点"这两件互不相干的事被同一个分支同时决定，谁也无法单独复核。

变更后，一条出站消息的编码由该消息自己的编码器承担，端点归属由编码器声明并由一处统一判定执行；发送方只做查表、校验与发送。投递多帧的选择字符路径不再靠对消息类型的特判进入，而是由它本来就有的独立入口承接。

现有九条出站消息与投递路径产生的字节、帧数与次序在变更前后逐字一致。

## Task Perspective

- Core outcome: 出站消息的接线成为一处局部注册，且编码与端点校验分离为两件可各自复核的事。消费者是后续持续接入协议的开发者。
- Necessary support: 字节、帧数、投递次序与失败隔离语义逐字保持；端点校验不得被削弱；分层不放宽。
- Peripheral assurance: 未注册消息的显式失败与跨端点拒绝，由 TaskContract 列为必须交付的可观察控制（CSC-4、CSC-5），故作为要求；回归基线保留在证据中。

## Scope and Non-Goals

### In Scope

- 出站类型化消息到帧的编码方式，以及编码器的端点归属。
- 现有九条出站消息的编码接线。
- 多帧投递路径的进入方式。
- 跨端点发送与未注册消息的失败行为。
- 承载登录成功体编码的那份代码与其入站解码职责的分离。

### Non-Goals

- 入站解包（已完成）。
- 协议相关代码的目录归属与项目划分。
- 任何出站字节布局、加密参数、组帧规则与投递次序的改变。
- 出站消息类型目录的成员与取值；本变更不删除它，也不使其成为派发键。
- 补齐登录失败体的编码；它继续保持为抛出。
- 消息处理器、命令与领域服务的改动，包括投递的调用点。

## Constraints

- 端点校验不得放宽：跨端点发送必须继续被拒绝，且拒绝信息须同时指明消息与端点。
- 投递路径中 best-effort 目标的失败必须继续只终止该目标自身的剩余批次，不影响后继目标；取消异常继续原样上抛。
- 登录失败体必须继续抛出而非产生字节。
- 传输层不得获得对领域编排层的编译期依赖。
- 不得以放宽类型、放宽可见性要求或抑制编译诊断的方式达成结构目标。

## Definitions

| Term | Meaning |
|---|---|
| 出站消息 | 由服务端代码构造的类型化消息，其 CLR 类型在构造点静态已知。 |
| 编码器 | 承担单条出站消息编码职责的单元。输入为该消息与所需配置，输出为一至多个待发送的帧。 |
| 端点归属 | 一条出站消息允许被发往的端点。由编码器声明，与编码逻辑分离。 |
| 投递 | 多帧且多接收者的发送策略：先向直接连接投必达批次，再向若干目标尽力投递。它决定次序与失败隔离，不决定字节。 |

## External Behavior and Data Rules

- 一条出站消息或产出单帧，或产出有序多帧；两者在发送上无差别，按产出顺序依次写出。
- 出站消息类型目录中存在两个不同消息共用同一目录值的情形，因此目录值不能唯一标识一条出站消息。
- 投递的必达批次先于尽力批次；与必达连接相同的尽力目标被跳过。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 出站消息到帧的编码由逐消息的编码器注册提供，发送路径中不存在随出站消息数量增长而必须修改的共享编码分支。 |
| RQ-002 | 接入一条新出站消息只需增加该消息自己的编码器与其注册，不修改任何既有消息的编码器、既有注册项或共享发送代码。 |
| RQ-003 | 现有九条出站消息产生的字节、帧数与帧序与变更前逐字一致。 |
| RQ-004 | 端点归属由编码器声明并由一处统一判定执行；向不匹配的端点发送被拒绝，拒绝信息同时指明消息与端点。 |
| RQ-005 | 发送一条没有注册编码器的消息时显式失败，失败信息指明是哪条消息。 |
| RQ-006 | 多帧投递路径经其自身入口进入，发送路径不再对投递消息的类型作特判；投递的次序、尽力批次的失败隔离与投递前的空值校验语义不变。 |
| RQ-007 | 承载登录成功体编码的代码与其入站解码职责分离，使入站部分不再依赖传输层配置。 |
| RQ-008 | 登录失败体继续抛出而非产生字节。 |
| RQ-009 | 传输层与领域编排层之间的编译期分层不放宽。 |

## Assumptions

- 出站消息由服务端代码构造，其 CLR 类型在构造点静态已知，因此按 CLR 类型索引编码器不引入动态查表风险。
- 投递是发送策略而非编码，因此不进入编码器注册集合。
- 编码器可能需要配置与密钥来源，因此是可注入依赖的实例而非静态过程。
