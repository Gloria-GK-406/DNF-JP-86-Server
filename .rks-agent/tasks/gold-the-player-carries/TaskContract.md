# TaskContract: 玩家身上的金币

## Context

### Source Request

用户在实机测试中报告：翻牌得到的金币当场显示正常，**重新登录后角色身上的金币直接是 0**。随后要求先系统性查清原因，再决定怎么做。

查清之后用户定下了做法与命名，并授权执行：

> 「对，没问题。……用 multi spec 的 sdd 跑吧。先重命名，然后是重构和实现角色金币的问题。」

命名与形状的决定同样出自用户：

> 「Gold应该就指代金币，金色晶块部分都用Cube结尾吧。比如GoldCube。长一点但是不容易搞混。然后就是IAccountCargoGlod和ICharacterGold？或者直接放到character的instance里会不会更好？直接getchar，然后char.addglod，当做char的一部分。」

以及关于注释权威性的一条：

> 「注释这个，你不用当真理。看看就行。……注释只是一个有一定参考价值的文字，不是铁律。一切以代码设计为主。」

### Current Situation

这个游戏有**两笔互不相同的钱**，本服务端把玩家所有的收入都记进了错的那一笔。

**随身金币**是玩家背包上显示的那个数字，角色级，每个角色各自一份。它在客户端的表示是主背包容器（listType=0）的虚拟槽位 0，itemId 固定为 0。**账号金库金币**是账号级的另一笔，一个账号下所有角色共用，只有打开账号金库才看得到。两者靠 `DEPOSIT_MONEY` / `WITHDRAW_MONEY` 互相搬运——存在搬运协议本身就证明它们是两笔账。

本服务端只实现了金库那一笔（`account_cargo_state.value32`）。翻牌收益、地面捡钱都进金库，付费翻牌的费用也从金库扣。随身金币从来没有任何一处写过，所以每次登录读出来都是 0。**钱没有丢，它在金库里躺着，玩家看不到也花不到。**

随身金币的读端与两个协议帧（登录全量帧、变更帧）本仓都已存在，且经与参照服务端逐字节比对确认正确——存储偏移、槽位分段、帧内偏移三处全部一致，真实物品从槽 3 起因而与虚拟槽不冲突。**缺的只是写路径**：没有人往槽 0 写过值，建角色时也不建这一行。

之所以会这样，是因为一个假前提被写进了注释并当成了事实。`IAccountMoneyService` 的文档声称金库那个字段就是「客户端显示的钱包」，并声称一个账号下所有角色共用一个钱包——后者与参照服务端相反；前者引用的客户端证据确有出处，但描述的是参照服务端修理回包里的金币，那笔钱读的是角色主背包槽 0，与金库无关。这个假前提随后被记进了 `Docs/新功能接入规范.md` 的取证表：当时正确记录的「角色金币既没有落库路径，也没有告诉客户端金币变了的帧」被答成了「已有」。后续的翻牌任务全部建立在它之上。

同一个误解还留下了大范围的命名漂移。`purse` 一词全仓 79 处、10 个文件（源码 17 处、测试 62 处），一律指金库；而在这个游戏里 purse 就是随身金币。**其中 62 处在测试里**，包括类名与用例名——这是最硬的一道锁：改了实现不改测试名，下一个人会以为随身金币已经有回归覆盖。

此外还有一整条限额链（角色表的携带上限两列 → 上限等级规则 → 发给客户端的上限升级等级帧）限着一个本仓不存在的量：**服务端已经在告诉客户端「你的随身金币携带上限是多少」，而随身金币本体一个字节都没发过。**

## Goal

玩家在游戏里赚到的钱，就是他在背包上看到的那个数字，并且重新登录后仍然是它；而这两笔钱在代码里从名字上就分得开，使同一类误解不会再次发生。

## Scope

### In

- 随身金币成为本服务端真实持有的一笔钱：能被写入、能跨会话保留、能随变更告知客户端。
- 玩家赚钱的既有路径改为进入随身金币，玩家花钱的既有路径改为从随身金币支出。
- 携带上限对随身金币真实生效。
- 两笔钱的命名各自归位，使读代码的人能从名字判断面对的是哪一笔。
- `Gold` 一词在本仓只用于指代金币。
- 与这两笔钱有关的仓库文档记录与事实一致，不再把未实现的东西记作已有。

### Out

- 存款与取款（`DEPOSIT_MONEY` / `WITHDRAW_MONEY`）这一对协议：本仓两个都未接线，属独立功能。
- 拍卖行，以及角色表上的拍卖出价上限。
- 金库中已有金额的迁移：测试期间赚到的钱留在金库不动。
- 除既有赚钱与花钱路径之外的新金币来源或去向。

## Constraints

- 命名由用户定下，不再作为开放问题：`Gold` 只指金币；金色魔方碎片改用 `Cube` 结尾的名字；黄金牌（`GoldCard`）沿用档案自己的词，但牌面永不写作裸 `Gold`；`IAccountMoneyService` 更名为以「账号金库金币」为名；`purse` 一词全仓弃用，金库一侧统一说 cargo gold，随身一侧就说 gold。
- 随身金币挂在既有的角色对象上（`ICharacterDomainService.Get(characterId)` 取得的 `ICharacter`），而不是另立一个与金库并列的服务。用户选择它的理由是两侧签名天然不同形——角色对象已绑定角色因而不带 id 参数，金库一侧必须显式给出账号 id，因而传错在编译期就会被挡住。
- 随身金币的增减必须只有一个入口，携带上限在该入口上生效。参照服务端的失败正在于此：其业务层不收敛，约四十处各自计算并写入，导致携带上限形同虚设、超限行为出现三种互不一致的处理。
- 命名与文档的归位必须行为逐值不变，以既有全量判据为护栏。
- 注释在本仓不具权威性，一切以代码设计为准。既有注释与本任务的设计冲突时改注释，不得为迁就注释扭曲设计。
- 遵守 `AGENTS.md` 的分层：handler 不得操作业务语义，须经命令或领域服务；规则输入只经规则服务进入本服务器；规则服务不查世界状态。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 玩家赚到的金币显示在背包上，重新登录后仍然是那个数 | 实机：进副本赚钱、记下数字、退出重新登录、核对显示一致 |
| SC-2 | 玩家花钱的既有路径从他看得见的那笔钱里扣，且扣完的余额与显示一致 | 实机：付费翻牌前后各记一次显示金额，核对差额等于价格 |
| SC-3 | 携带上限对随身金币真实生效，超出上限的入账有确定且一致的处理 | 判据覆盖入账触及上限的情形，并证明处理方式在所有入账路径上相同 |
| SC-4 | 新建的角色带有一笔确定的随身金币起始值，而不是靠读取缺省得到 0 | 判据：新建角色后随身金币可被读出，且与「从未写过」可区分 |
| SC-5 | `purse` 不再在本仓指代任何一笔钱 | 全仓检索该词无残留，测试的类名与用例名一并归位 |
| SC-6 | `Gold` 在本仓只出现在指代金币之处 | 全仓检索 `Gold`，每一处命中或为金币，或为档案自有的黄金牌用语 |
| SC-7 | 两笔钱在代码中可从名字区分，且不能互相误用 | 金库一侧与随身一侧的调用形态不同形，误用在编译期被拒 |
| SC-8 | 仓库文档不再把随身金币记作已实现，与两笔钱有关的记述与代码一致 | 逐条核对受影响的文档记述与当前代码 |
| SC-9 | 命名与文档的归位没有改变任何行为 | 全量判据在归位前后计数不低于基线 1993 通过 / 2 跳过 / 0 失败，且该次改动不修改任何断言或期望值 |

## Assumptions

- 随身金币在客户端的位置与在存储中的格式，以参照服务端 ServerS4A21 与本仓协议文档一致的部分为准；两者在存储偏移、槽位分段与帧内偏移三处已核对一致。
- 本仓的容器写入随命令事务提交，因此不需要参照服务端那套脏集合加定时落库的机制——后者的存在是因为它的内存背包与数据库是两份数据，本仓不是。
- 全量判据的两个 skip 是档案已加载的证据；缺少 `PVF_ARCHIVE_PATH` 时读档案的判据会静默跳过而非报红，因此判据必须带该环境变量运行才算数。
