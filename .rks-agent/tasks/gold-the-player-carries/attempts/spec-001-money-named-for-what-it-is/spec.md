# Specification: 两笔钱各自叫对名字

## Why and Outcome

这个游戏有两笔互不相同的钱。本服务端只实现了其中一笔——账号金库金币——却用另一笔的名字称呼它。

`purse` 一词在仓库里出现七十九处、分布在十个文件中，一律指账号金库；而在这个游戏里 purse 就是玩家背包上显示的随身金币。其中六十二处在判据里，包括类名、字段名、方法名、用例名与临时文件名。**判据名是其中最硬的一道锁**：改了实现却留下这些名字，下一个人会以为随身金币已经有回归覆盖。

误称还带来了两条写进文档的假断言：一条声称金库那个字段就是「客户端显示的钱包」并引客户端取值器为证——该引用确有出处，但描述的是参照实现修理回包里的金币，那笔钱读的是角色主背包的第一个虚拟槽位，与金库无关；另一条声称「一个账号下所有角色共用一个钱包」，它对金库成立、对随身金币是错的，而它正是用来论证「这笔钱应当是账号级」的。本仓自己的协议记述把该字段写作「金库内金币」，与这两条直接冲突。

这个假前提随后被记进了仓库的接入规范：当时正确记录的「角色金币既没有落库路径，也没有告诉客户端金币变了的帧」被答成了「已有」，并点名金库服务作为证据。此后所有相关工作都建立在它之上，直到玩家在实机上发现金币重登归零才暴露。

同一个词还被借给了两类不是钱的东西——账号持有的六种魔方碎片中的金色那种，以及付费翻牌的牌面种类——而真正的金额就夹在它们中间。与此同时，主背包前三个虚拟槽位各自承载什么，仓库里没有任何一处说明过；随身金币未来就住在第一个槽位上。

交付后必须成为真的：**读这段代码的人能从名字判断自己面对的是哪一笔钱，仓库的记述与代码正在做的事一致，而服务器的行为一个值都没有变。**

## Task Perspective

- Core outcome: 下一个读这段代码的人——包括随身金币的实现者——能仅凭名字判断自己面对的是哪一笔钱，并且不会从仓库记述里读到一个假的既成事实。
- Necessary support: 服务器行为逐值不变。本次改动只触及名字与文字，既有的能力与数值是要被保护的资产，不是要被改进的对象。
- Peripheral assurance: 全量判据、全仓词项检索与逐处核对。它们证明结果，本身不是结果。

## Scope and Non-Goals

### In Scope

- 账号金库那笔钱在标识符与记述两个层面都表明自己是金库的那一笔。
- `purse` 一词退出仓库对两笔钱的称呼，判据的类名、字段名、方法名、用例名与临时文件名一并归位。
- `Gold` 一词只用于指代金币；当前借用它的非货币概念改用能表明自身的名字。
- 主背包前三个虚拟槽位各自承载什么，成为可从代码本身读到的事实。
- 与这两笔钱有关的仓库记述与当前代码一致，不再把未实现的东西记作已有，也不再描述已经不存在的结构。

### Non-Goals

- 随身金币的任何写入能力、存储或协议改动。
- 携带上限链的功能性改动。它限着一个尚不存在的量，本 Spec 只在名字与记述层面处理它，让它读起来是「随身金币的携带上限」；使它真正生效属于后续结果。
- 承载点券那一组账号级价值的「钱包」类型的改名。它没有对任何一笔金币作出错误断言——它装的东西确实是账号级的价值，只是不含金币；把它一并改名会扩大改动面而不消除任何一条假陈述。两笔金币的名字一旦各自明确，它带来的歧义即随之消解。
- 协议层记述。经核对该层没有漂移。
- 与钱无关的命名整理。

## Constraints

- 命名方向由任务授权方定下：`Gold` 只指金币；魔方碎片一侧的六个名字统一带上表明自己是碎片的后缀，六个一并处理以保持对称；黄金牌沿用档案自己的用语，但牌面不得写作裸 `Gold`；账号金库那笔钱以「账号金库金币」为名；`purse` 全仓弃用，金库一侧统一以「金库金币」称呼，随身一侧的称呼留给后续结果。
- 服务器行为必须逐值不变，且本次改动不得修改任何判据的断言或期望值。
- 注释在本仓不具权威性。既有注释与代码事实冲突时改注释，不得为迁就注释而扭曲设计或保留错误陈述。
- 遵守仓库既有的分层与命名约定。

## Definitions

| Term | Meaning |
|---|---|
| 随身金币 | 玩家背包上显示的那个数字。角色级，同一账号下每个角色各自一份。在客户端表示为主背包容器的第一个虚拟槽位，其物品标识恒为零。本仓目前只有读出与下发的路径，没有任何写入路径，因此它实际上尚未实现。 |
| 账号金库金币 | 只有打开账号金库才看得到的那笔钱。账号级，同一账号下所有角色共用。在客户端表示为账号金库容器帧头中、选择键与条目数之间的那个三十二位整数。本仓已完整实现。 |
| 两笔钱的关系 | 客户端有一对专门的存入与取出协议在两者之间搬运金额。存在搬运协议本身即证明它们是两笔独立的账。 |
| 主背包虚拟槽位 | 主背包容器开头的三个位置，承载的是计数而非物品：第一个是随身金币，第二个是复活币，第三个是胜点。真实物品从第四个位置起，因此两者不冲突。 |
| 黄金牌 | 通关翻牌中付费的那一行牌面。这是游戏档案自己的用语，指牌面种类而非金额。 |
| 魔方碎片 | 账号持有的六种颜色的碎片，其中一种是金色。它们是道具计数，不是货币。 |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 仓库中不存在以 `purse` 指代账号金库那笔钱的标识符、注释或判据名，判据的类名、字段名、方法名、用例名与临时文件名同样不存在这种用法。 |
| RQ-002 | 承载账号金库那笔钱的接口、实现、存储层与其消费方，其名字表明所指的是账号金库里的金币。 |
| RQ-003 | 关于账号金库那笔钱的记述不再声称它是玩家显示的随身钱包，也不再声称同一账号下所有角色共用一笔随身的钱。 |
| RQ-004 | `Gold` 一词只出现在指代金币之处；魔方碎片一侧与牌面种类一侧的名字各自表明自己不是金币。 |
| RQ-005 | 主背包前三个虚拟槽位各自承载什么，可以从承载它们的类型、装配处或编码处本身读到，无需查阅仓库以外的文档。 |
| RQ-006 | 仓库记述不再把随身金币记作已经具备落库路径或变更通知，也不再点名账号金库那笔钱作为其证据。 |
| RQ-007 | 与这两笔钱有关的其余仓库记述与当前代码一致：不再描述已被折叠掉的存储结构，也不再把随身金币的携带上限归属到不含金币的那一组账号级价值上。 |
| RQ-008 | 取用账号金库那笔钱时必须显式指明是哪个账号，使其调用形态与一个已绑定到单个角色的调用形态不可互换。 |
| RQ-009 | 服务器的可观察行为逐值不变，且判据的断言与期望值未被改动。 |

## Assumptions

- 三个主背包虚拟槽位的承载物依次为随身金币、复活币与胜点。该事实已与参照实现及本仓的一份工具记述核对一致，是 RQ-005 的依据。
- 全量判据中的两个跳过用例出自缺少游戏档案时的守卫，是档案已被加载的证据；判据必须在档案可达的条件下运行，其计数才具有意义。
- 账号金库那笔钱当前的调用形态已经要求显式提供账号身份，因此 RQ-008 是一条保持性要求，用于防止改名过程中它被顺手简化掉。
