# TaskContract: 两笔钱各自叫对名字

## Context

### Source Request

来自根契约 `../../TaskContract.md`（revision 1）的第一个有界结果。根授权原话：

> 「对，没问题。……用 multi spec 的 sdd 跑吧。**先重命名**，然后是重构和实现角色金币的问题。」

命名方案由用户在同一轮对话中定下：

> 「Gold应该就指代金币，金色晶块部分都用Cube结尾吧。比如GoldCube。长一点但是不容易搞混。」

### Current Situation

本服务端只实现了两笔钱中的一笔——账号金库金币——但把它命名成了另一笔。`purse` 一词在本仓 79 处、10 个文件中一律指金库，而在这个游戏里 purse 就是玩家背包上显示的随身金币。**其中 62 处在测试里**，包括类名与用例名。

这不只是叫法问题。一个假前提被写进了金库服务的文档：声称该字段就是「客户端显示的钱包」，并声称一个账号下所有角色共用一个钱包。后者与参照服务端相反；前者引用的客户端证据确有出处，但描述的是参照服务端修理回包里的金币，那笔钱读的是角色主背包槽 0，与金库无关。

这个假前提随后被记进了仓库文档的取证表：当时正确记录的「角色金币既没有落库路径，也没有告诉客户端金币变了的帧」被答成了「已有」。此后所有相关工作都建立在它之上，直到玩家实机发现金币归零才暴露。另有两处文档腐烂：一份对随身金币的描述完全正确但描述的是本仓不存在的旧系统，与前者直接打架；一处注释还在描述一张已被折叠掉的表。

`Gold` 一词同时还被用在两类非货币的东西上——金色魔方碎片，以及付费翻牌的牌面种类——而真正的金额就夹在它们中间。

随身金币的实现要在这之后进行，它依赖这里确立的名字。**在两笔真钱同时存在之前把名字理顺，比之后在两笔钱之间动刀安全得多。**

## Goal

读代码的人能从名字判断自己面对的是哪一笔钱；仓库文档不再把未实现的东西记作已有；而这一切没有改变服务器的任何行为。

## Scope

### In

- 金库那笔钱的名字说明它是金库的。
- `purse` 一词退出本仓，包括测试的类名与用例名。
- `Gold` 只用于指代金币；当前借用该词的非货币概念改用能表明自身的名字。
- 拔除金库服务文档中关于「客户端显示的钱包」与「全账号共用一个钱包」的断言。
- 修正与这两笔钱有关的走样文档记述，使其与当前代码一致。
- 说明主背包前三个虚拟槽位各自是什么——它们承载随身金币，而本仓目前没有任何一处说过。

### Out

- 实现随身金币的任何写路径、存储或协议改动。
- 改变任何既有行为、判据的断言或期望值。
- 携带上限链的功能性改动（它限着一个尚不存在的量，这属于下一个结果）。
- 与钱无关的命名整理。

## Constraints

- 命名由用户定下，不作为开放问题：`Gold` 只指金币；金色魔方碎片改用 `Cube` 结尾的名字，六个碎片字段一并处理以保持对称；黄金牌沿用档案自己的词，但牌面不得写作裸 `Gold`；金库服务更名为以「账号金库金币」为名；`purse` 全仓弃用，金库一侧统一说 cargo gold。
- 行为必须逐值不变。
- 注释在本仓不具权威性，与代码设计冲突时改注释。
- 遵守 `AGENTS.md` 的分层与命名约定。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| CSC-1 | `purse` 不再在本仓指代任何一笔钱 | 全仓检索该词无残留，测试的类名、用例名与临时文件名一并归位 |
| CSC-2 | `Gold` 只出现在指代金币之处 | 全仓检索 `Gold`，逐条判定每一处命中或为金币、或为档案自有的黄金牌用语 |
| CSC-3 | 金库那笔钱的名字与文档都说明它是金库的，不再声称自己是玩家显示的钱包或全账号共用一个钱包 | 该服务及其实现、存储层、两个消费方的名字与文档逐处核对 |
| CSC-4 | 与这两笔钱有关的仓库文档记述与当前代码一致，不把未实现的东西记作已有 | 逐条核对受影响的文档记述与代码现状 |
| CSC-5 | 主背包前三个虚拟槽位各自承载什么，在代码中可读到 | 从槽位的定义处出发能读出「槽 0 是随身金币」而不必查外部文档 |
| CSC-6 | 服务器行为逐值不变 | 全量判据计数不低于 1993 通过 / 2 跳过 / 0 失败，且本次改动不修改任何断言或期望值 |
