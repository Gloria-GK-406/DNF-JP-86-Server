# Routing Decision

- TaskContract: `.rks-agent/tasks/gold-the-player-carries/attempts/spec-002-gold-the-character-keeps/TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 结果由玩家自己定义且可当场观察——「背包上那个数字是对的，重登还在，花钱扣的是它」。根因已查到字节层面，形状（挂在角色对象上、单一入口）由授权方亲自选定，这两项原本最容易返工的决定都已封死。
- Requirement stability: 可枚举。写路径、建角色起始行、携带上限落点、三个收支路径改向、变更通知，每一条都有明确的观察方式，且七条成功条件各自独立可核。
- Execution direction: 已知。读出路径、两个协议帧、存储格式都已具备并逐字节核对过；写入用既有的容器写，随命令事务提交。参照实现的失败模式（业务层不收敛导致上限失效）已查明并写入约束。
- Remaining uncertainty: 三个非语义的局部选择——建角色的起始金币取什么值、超上限时截断还是拒绝、变更通知在哪几条路径上发。它们不改变结果含义，留给 Spec 定，且都能从参照实现与档案取证。

## Marginal Control Value

- User precision signal: 明确偏精度。授权方拒绝了「先按上游改了再说」，坚持先系统性查清协议与结构；发现根因后主动要求走 SDD；并接受了「拆两步、第一步行为零变化」这条更慢但更安全的路径。
- Direct failure mode: 这一步动的是**玩家能直接看到的数字**，而错法有两类都不会报红。其一是**落点错**——上一次事故正是这样：钱写进了另一笔账，判据全绿、客户端当场显示还正常，只有下一次登录才暴露。其二是**上限失效**——参照实现的现成教训：内存层收敛了但业务层四十处各自写入，于是携带上限形同虚设、超限行为三种并存、金库取款一路能把余额顶到上限之上。这两类都要玩家事后发现，检测成本高、信任损失大。
- Useful control: 一份把「玩家能观察到什么」写死的 Spec（每条收支路径与上限行为各一条可独立核对的要求），加一次针对完整结果的独立评审。判据能证明代码做了什么，证明不了**做到了玩家看得见的哪一件事**——那要靠实机核销，而实机核销要有清单才不会漏。本仓在同类工作上，独立评审已多次抓到自查漏掉的东西，包括 `spec-001` 里那条复合断言翻转。
- Time-for-quality rationale: 值。这是整个根任务的核心结果，也是唯一需要授权方本人配合实机验证的一段；一次没做对就要再占用他一次。相对于此，写清单的时间是小头。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: 一个连贯的验收边界——「玩家身上的钱是真的」，一个 oracle（实机观察加全量判据），一个回滚边界。七条成功条件互相依赖：只做写路径而不改三个收支路径，交付的是一个永远显示 0 的钱包，CSC-1 无从观察；只改收支路径而无写路径则根本无处可写。没有任何两部分能各自独立地被接受或回滚。
- Why Direct is insufficient: Direct 无法廉价提供「玩家看得见的那件事真的成立」的证据。两类失败都在判据全绿时发生，且都要等玩家事后发现。
- Why Multi is unnecessary: 只有一个可接受结果。把写路径与收支改向拆成两个 Spec，前者交付的东西玩家看不见、也无法验收。
- Reroute conditions: 若随身金币无法挂在既有角色对象上——例如现有可变租约对该容器的排除构成硬阻碍且无法在本 Spec 内解决——则中心方案失效，须退回根控制器重新定形状，而不是在 Spec 内改成一个平行服务。若实机验证发现客户端对变更帧是赋值而非累加（与当前假设相反），则通知这一侧的验收边界失效，须退回重定。若发现携带上限的真实来源不在角色属性表那两列而在档案，则该条要求的取证方式改变，Spec 相应修订。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-feature`
- Why this is sufficient: Standard 的独有控制是 `plan.md` 带来的前置裁决与依赖排序，而本 Spec 有一个**必须先定、定错要成批返工**的决定：随身金币的写入怎么落。它住在主背包槽 0，即 `items` 表一行的 `item_core` 里；而 `IItemStoreSession` 是工作单元（内存决定写入、提交时落库），因此经容器写它必然是「读出当前值→加减→写回」。账号金库那一侧当初**刻意避开**了这个形态——加法与「够不够扣」都压进单条 SQL，其注释写明理由是两次同时应答的拾取不能各自读到同一个总额再各自加。是否可以在随身金币上重新采用读-改-写，取决于一个尚未查证的事实：同一角色的命令是否已被 `UserExecutionGate<CharacterId>` 串行化。**随身金币是角色级、金库是账号级跨角色共享，两者的竞态条件本就不同**，所以不能直接照搬任一侧的结论。这个决定往下决定三个收支路径的形态、携带上限的落点、以及变更通知怎么发。另有两个耦合决定同样需要前置裁决：`CharacterItemLeaseState` 明确把 virtual resources 排除在唯一可变租约之外，须指定变更所有者；以及超上限时截断还是拒绝（参照实现三种并存，本仓要一致，而这个选择影响每一条入账路径的返回形状）。
- Why lighter is insufficient: `sdd-lite` 把实现规划折进实现方法里，适合「没有需要前置裁决的决定」的任务——`spec-001` 正是如此，命名方案已被用户定死。这里不是：上面那个写入形态的决定必须在动第一个调用点之前落地，否则三个收支路径会按一种形态写完再按另一种重写。Lite 的完整结果评审能发现它写错了，但那时返工面已经是整个 Spec。
- Why heavier is unnecessary: `sdd-governed` 的独有控制是独立质询、独立产物批准与审计强度证据，需要一条 Standard 保护不足的高后果逃逸路径。本 Spec 没有硬性下限：不触及安全、凭据、授权、隐私、合规，也没有不可逆的外部变更。金额是私服测试环境的游戏内货币；改动在隔离工作区内，回滚边界清晰（父控制器持有已接受基线 e4f29e1d）；最坏情况是玩家金币显示错误，可由实机验证当场发现并回滚。用户可见的精度信号已由 Spec 的可核对要求与一次独立评审满足。
