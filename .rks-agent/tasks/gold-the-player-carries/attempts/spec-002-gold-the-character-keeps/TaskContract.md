# TaskContract: 角色身上的金币

## Context

### Source Request

来自根契约 `../../TaskContract.md`（revision 1）的第二个有界结果，承接已接受的 `spec-001`（基线 `e4f29e1d`）。根授权原话：

> 「对，没问题。……用 multi spec 的 sdd 跑吧。先重命名，**然后是重构和实现角色金币的问题**。」

形状由用户在同一轮对话中定下：

> 「或者直接放到 character 的 instance 里会不会更好？直接 getchar，然后 char.addglod，当做 char 的一部分。」

### Current Situation

玩家在游戏里赚到的钱进的是**账号金库**，而他背包上看到的那个数字来自另一笔钱——角色随身金币——本服务器从来没有写过它。所以每次登录读出来都是 0。钱没有丢，在金库里躺着，玩家看不到也花不到。

`spec-001` 已经把两笔钱的名字分开了，也把那条把它们混为一谈的假前提从代码与文档里拔掉了。剩下的是**让随身金币真的存在**。

好消息是缺口比看上去窄。随身金币的读出路径与两个协议帧本仓都已具备，并已与参照实现逐字节核对一致：

- 它在客户端是主背包容器的第一个虚拟槽位，物品标识恒为零；真实物品从第四个位置起，两者不冲突。
- 登录时的全量帧与变更时的增量帧都已实现，金额在两个帧里的偏移都与参照实现相同。
- 存储格式相同：金额写在物品核心的同一个偏移上。
- 变更通知帧甚至已经在用了——地面拾取金币时确实会发出它，而且它作用的正是随身金币。

**缺的是写入。**没有任何一处往那个槽位写过值，建角色时也不建那一行。这也解释了事故里最反直觉的一环：捡钱当场显示完全正常，因为服务端记进金库、客户端把增量加在随身金币上，两边各自成立，只有下一次登录会揭穿。

携带上限这条链也已经存在并在向客户端下发——角色属性表上有两个上限列，规则服务把它们折算成升级等级发出去——但它限着一个不存在的量。它是现成的接入点。

参照实现在这件事上有一个明确的失败可供避开：它的内存层收敛到单一写入口，业务层却不收敛，约四十处各自计算并写入，于是携带上限形同虚设，超限行为出现三种互不一致的处理（截断、拒绝、照加），其中金库取款一路完全不查上限，可以把随身金币顶到上限之上。

## Goal

玩家赚到的钱就是他背包上看到的那个数字，重新登录后仍然是它；他花钱时从这笔钱里扣；而这笔钱只有一个出入口，携带上限在那里生效。

## Scope

### In

- 随身金币成为本服务器真实持有的一笔钱：能被写入、跨会话保留。
- 增减随身金币只有一个入口，且该入口挂在角色上而非另立一个与账号金库并列的服务。
- 携带上限在该入口上真实生效，超出上限的入账有确定且一致的处理。
- 新建角色带有一笔确定的随身金币起始值，而不是靠读取缺省得到零。
- 玩家赚钱的既有路径改为进入随身金币：通关翻牌的收益、地面拾取的金币。
- 玩家花钱的既有路径改为从随身金币支出：付费翻牌的费用。
- 随身金币变化时客户端被告知，且它显示的数字与服务器所存的一致。

### Out

- 存款与取款（`DEPOSIT_MONEY` / `WITHDRAW_MONEY`）这一对协议：本仓两个都未接线，属独立功能。
- 账号金库中已有金额的迁移：测试期间赚到的钱留在金库不动。
- 拍卖行，以及角色属性表上的拍卖出价上限。
- 除上述赚钱与花钱路径之外的新金币来源或去向，包括邮件附件金币的领取、卖装备的收入。
- 复活币与胜点这两个相邻的虚拟槽位。
- 账号金库那笔钱的行为改动：它保持现状，只是不再承接这些收支。

## Constraints

- 随身金币挂在既有的角色对象上，由角色服务取得；增减方法不带角色标识，因为对象已经绑定到一个角色。这与账号金库一侧必须显式给出账号标识的调用形态天然不同形，误用在编译期即被拒。此形状由任务授权方选定。
- 增减必须只有一个入口，携带上限在该入口上生效。参照实现的失败正在于业务层不收敛。
- 不照抄参照实现的落库机制。它的脏集合加定时落库是因为其内存背包与数据库是两份数据；本仓的容器写随命令事务提交，更简单也更不易丢钱。
- 承载随身金币的容器被现有的可变租约明确排除在外，须为它指定明确的变更所有者。
- 注释在本仓不具权威性，一切以代码设计为准。既有注释与本任务的设计冲突时改注释。
- 遵守 `AGENTS.md` 的分层：handler 不得操作业务语义，须经命令或领域服务；规则输入只经规则服务进入本服务器；规则服务不查世界状态；凡能触达持久写的命令一律事务化。
- 既有行为除本契约 In 范围内明确改变的收支落点外不得变化。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| CSC-1 | 玩家赚到的金币显示在背包上，退出重新登录后仍是那个数 | 实机：打一把、记下显示的数字、退出、重新登录、核对一致 |
| CSC-2 | 玩家花钱从他看得见的那笔钱里扣，差额等于价格 | 实机：付费翻牌前后各记一次显示金额，核对差额 |
| CSC-3 | 增减随身金币只有一个入口，携带上限在那里生效，超限入账处理一致 | 判据覆盖触及上限的入账；且不存在绕过该入口的写入路径 |
| CSC-4 | 新建角色的随身金币可被读出，且与「从未写过」可区分 | 判据：新建角色后该槽位有确定的起始值 |
| CSC-5 | 两笔钱不能互相误用 | 两侧调用形态不同形，误用在编译期被拒 |
| CSC-6 | 随身金币变化时客户端被告知，且所告知的与所存的一致 | 实机观察配合判据：变更后客户端显示的数字与服务器所存相同 |
| CSC-7 | 范围外的既有行为不变 | 全量判据不低于 1993 通过 / 2 跳过 / 0 失败，新增判据可增加计数 |

## Assumptions

- 随身金币在客户端的位置、存储格式与两个协议帧的帧内偏移，已在 `spec-001` 期间与参照实现及本仓协议记述核对一致，本契约据此不再重新取证。
- 变更通知帧对客户端是累加而非赋值。证据在参照实现且闭合：它写入的是本次拾取的增量而非余额，而落库走另一条路径写入该槽位；若客户端是赋值，参照实现自己的显示在第二次拾取后就会崩坏。
- 全量判据的两个跳过是档案已加载的证据；判据必须在档案可达时运行才算数。
