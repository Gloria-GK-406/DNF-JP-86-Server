# Specification: 角色身上的金币

## Why and Outcome

玩家在游戏里赚到的钱进的是账号金库，而他背包上看到的那个数字来自另一笔钱——角色随身金币——本服务器从来没有写过它。所以每次登录读出来都是 0。钱没有丢，在金库里躺着，玩家看不到也花不到。

前一个结果已经把两笔钱的名字分开，也把那条把它们混为一谈的假前提从代码与记述里拔掉。剩下的是**让随身金币真的存在**。

缺口比看上去窄。随身金币的读出路径与两个协议帧本服务器都已具备，并已与参照实现逐字节核对一致：它在客户端是主背包容器的第一个虚拟槽位，物品标识恒为零，真实物品从第四个位置起因而不冲突；登录时的全量帧与变更时的增量帧都已实现，金额在两个帧里的偏移都与参照实现相同；存储格式也相同。变更通知帧甚至已经在用——地面拾取金币时确实会发出它，而且它作用的正是随身金币。

**缺的是写入。**没有任何一处往那个槽位写过值，建角色时也不建那一行。这也解释了事故里最反直觉的一环：捡钱当场显示完全正常，因为服务端记进金库、客户端把增量加在随身金币上，两边各自成立，只有下一次登录会揭穿。

交付后必须成为真的：**玩家赚到的钱就是他背包上看到的那个数字，重新登录后仍然是它；他花钱时从这笔钱里扣；而这笔钱只有一个出入口，携带上限在那里生效。**

## Task Perspective

- Core outcome: 玩家身上的钱是真的——赚到的显示出来、跨会话保留、花掉时从它扣。消费者是玩家本人，他用眼睛验收。
- Necessary support: 增减只有一个入口且携带上限在那里生效（否则会复现参照实现那种上限形同虚设、超限行为三种并存的结局）；两次同时发生的增减不能互相覆盖（否则玩家会莫名其妙变穷，且事后无法重建）；新建角色带确定的起始值（否则「零」与「从未写过」分不开，日后查账无从下手）；变更时告知客户端（否则玩家要重登才看得到自己赚了钱）。
- Peripheral assurance: 判据与实机核销。它们证明结果，本身不是结果。

## Scope and Non-Goals

### In Scope

- 随身金币成为本服务器真实持有的一笔钱：能被写入、跨会话保留。
- 增减随身金币只有一个入口，且该入口挂在角色上而非另立一个与账号金库并列的服务。
- 携带上限在该入口上真实生效，超出上限的入账有确定且一致的处理。
- 新建角色带有一笔确定的随身金币起始值。
- 玩家赚钱的既有路径进入随身金币：通关翻牌的收益、地面拾取的金币。
- 玩家花钱的既有路径从随身金币支出：付费翻牌的费用。
- 随身金币变化时客户端被告知，且它显示的数字与服务器所存的一致。

### Non-Goals

- 存款与取款这一对协议：本服务器两个都未接线，属独立功能。
- 账号金库中已有金额的迁移。测试期间赚到的钱留在金库不动。
- 拍卖行，以及角色属性表上的拍卖出价上限。
- 除上述赚钱与花钱路径之外的新金币来源或去向，包括邮件附件金币的领取与出售装备的收入。
- 复活币与胜点这两个相邻的虚拟槽位。
- 账号金库那笔钱的行为改动。它保持现状，只是不再承接这些收支。

## Constraints

- 随身金币挂在既有的角色对象上，由角色服务取得；增减方法不带角色标识，因为对象已经绑定到一个角色。这与账号金库一侧必须显式给出账号标识的调用形态天然不同形。此形状由任务授权方选定。
- 增减必须只有一个入口，携带上限在该入口上生效。
- 不照抄参照实现的落库机制：它的脏集合加定时落库是因为其内存背包与数据库是两份数据，本服务器不是。
- 注释在本仓不具权威性，与代码设计冲突时改注释。
- 遵守仓库既有的分层与事务约定。
- 范围外的既有行为不得变化。

## Definitions

| Term | Meaning |
|---|---|
| 随身金币 | 玩家背包上显示的那个数字。角色级，同一账号下每个角色各自一份。在客户端表示为主背包容器的第一个虚拟槽位，其物品标识恒为零。 |
| 账号金库金币 | 只有打开账号金库才看得到的另一笔钱。账号级，同一账号下所有角色共用。本服务器已完整实现，本 Spec 不改变它的行为。 |
| 携带上限 | 一个角色最多能带多少随身金币。角色属性表上已有该值，规则服务已把它折算成升级等级发给客户端，但被限的量此前并不存在。 |
| 起始值 | 新建角色时随身金币的确定数额，与「从未写过因而读作零」是两回事：后者无法与真的持有零区分。 |
| 单一入口 | 服务器内增减随身金币的唯一途径。任何绕过它的写入都会使携带上限失效，这正是参照实现的失败所在。 |

## External Behavior and Data Rules

- 客户端对变更通知帧是**累加**而非赋值：帧里带的是本次变动的数额，客户端把它加到自己正在显示的数字上。因此服务器所存与客户端所显示只在两者一致时才成立，任何一次未通知的变动都会让二者错开直到下一次登录。
- 登录时客户端从全量帧取得随身金币的**绝对值**，这是二者重新对齐的唯一时机。
- 随身金币是有符号 32 位整数所能表示的量，且不得为负。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 角色持有的随身金币被服务器保存；退出并重新登录后，读出的仍是退出前的数额。 |
| RQ-002 | 玩家赚钱的既有路径把所得记入随身金币：通关翻牌的收益与地面拾取的金币。 |
| RQ-003 | 玩家花钱的既有路径从随身金币支出；持有不足时该次花费被拒绝，且拒绝不改变持有额。 |
| RQ-004 | 服务器内增减随身金币只有一个入口，不存在绕过它的写入路径。 |
| RQ-005 | 携带上限在该入口上生效，且超出上限的入账处理在每一条入账路径上相同。 |
| RQ-006 | 两次同时发生的增减都被计入，任何一次都不会因另一次而丢失。 |
| RQ-007 | 新建角色的随身金币有确定的起始值，且该状态与「从未写过」可以区分。 |
| RQ-008 | 随身金币变化时客户端被告知；客户端据此显示的数字与服务器所存的相同。 |
| RQ-009 | 随身金币与账号金库金币不能互相误用：取用后者必须显式指明账号，取用前者不必也不能指明角色。 |
| RQ-010 | 范围外的既有行为不变。 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001, RQ-002 | 一个角色，记下它当前显示的金币 | 打一把地下城并翻开一张牌，然后退出重新登录 | 背包上显示的数字比记下的多了那张牌所付的数额，且重新登录后仍是它 |
| AC-002 | RQ-002 | 一个在副本里的角色 | 拾取地面上的一堆金币 | 显示的数字增加了拾取的数额，重新登录后仍是它 |
| AC-003 | RQ-003 | 一个持有额高于付费翻牌价格的角色 | 付费翻开一张牌 | 显示的数字减少了恰好该价格；持有额不足时该次翻牌被拒绝且数字不变 |
| AC-004 | RQ-004 | 交付后的服务器 | 有人查找所有改变随身金币的位置 | 每一处都经由同一个入口，没有旁路 |
| AC-005 | RQ-005 | 一个持有额已接近携带上限的角色 | 一次入账使总额将超过上限 | 结果按一种确定的处理落定，且换一条入账路径做同样的事得到同样的处理 |
| AC-006 | RQ-006 | 一个角色，两次增减同时到达 | 两次都被应答 | 两次的数额都反映在最终持有额里 |
| AC-007 | RQ-007 | 一个刚建好的角色 | 读出它的随身金币 | 得到确定的起始值，且这一状态与从未写过可区分 |
| AC-008 | RQ-008 | 一个正在游戏中的角色 | 它的随身金币发生一次变化 | 客户端显示的数字随之变为服务器所存的数额，无需重新登录 |
| AC-009 | RQ-009 | 交付后的服务器 | 有人试图把只知道角色身份的调用点接到账号金库那笔钱上，或把知道账号的调用点接到随身金币上 | 两者都不成立 |
| AC-010 | RQ-010 | 交付前后的同一套判据 | 在交付后的服务器上完整运行 | 通过、跳过与失败的计数不低于交付前 |

## Assumptions

- 随身金币在客户端的位置、存储格式与两个协议帧的帧内偏移，已在前一个结果期间与参照实现及本仓协议记述核对一致，本 Spec 据此不再重新取证。
- 变更通知帧对客户端是累加而非赋值。证据在参照实现且闭合：它写入的是本次变动的数额而非余额，而落库走另一条路径写入该槽位；若客户端是赋值，参照实现自己的显示在第二次拾取后就会崩坏。
- 全量判据中的两个跳过用例出自缺少游戏档案时的守卫，是档案已被加载的证据；判据必须在档案可达的条件下运行，其计数才具有意义。
- 实机验证需要授权方本人操作客户端，因此 EV-001 与 EV-004 的取得时机不由本服务器决定。
