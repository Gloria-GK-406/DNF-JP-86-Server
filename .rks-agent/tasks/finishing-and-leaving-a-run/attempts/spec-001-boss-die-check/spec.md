# Specification: 打死 boss 之后，结算界面出得来

## Why and Outcome

打死 boss 之后，玩家站在空的 boss 房里，没有修理商，也没有回城的入口。结算本身是走到了——`SET_PLAY_RESULT` 收到了，经验也付了 662——但那一屏该有的东西没出来。

同一刻服务端日志里有一帧客户端发来、我们没有处理器的 `CMD 0x0075`。

结果要变成这样：打死 boss 之后结算界面出现，修理商在场，回城入口可用；并且 `0x0075` 在这条链路里是什么、我们为什么这样应对它，写得清清楚楚——不管结论是「要回一帧」「它是触发器」还是「可以忽略」。

## Task Perspective

- Core outcome: 玩家在打完 boss 之后看得到结算界面并能继续操作。
- Necessary support: 弄清楚客户端摆出那一屏的条件；`0x0075` 至少被解码到能说出它是什么。
- Peripheral assurance: 没有 run、已结算、帧不可解时不卡死也不重复触发；既有的清关判定不被改动。

## Scope and Non-Goals

### In Scope

- 客户端摆出结算界面的条件，以及为满足它服务端要做什么。
- `CMD 0x0075` 的解码与其在链路中的角色，以及该结论的依据。
- 上述行为在异常输入与异常时序下的表现。

### Non-Goals

- 离开副本回到城镇。
- 翻牌。
- 结算屏上的数字。
- 清关判定本身（"boss 房的怪都死光"这条规则不改）。
- 副本机关型的清关条件。

## Constraints

- 权威是客户端与实机。参照服务端对这一帧不发应答、且用它来**触发**清关，而我们的顺序相反——它是线索，其字节不可照抄。
- 已验证的线级字节不得改变。
- **一个只让日志变干净的应答满足不了本 Spec。** 每一条应答都要能说出客户端拿它做什么——依据是
  客户端的构包点与应答 handler，不是「警告消失了」。最终的实机确认属根契约 SC-1，由四件全部
  做完后那一次会话给出；本 Spec 不得以任何方式代替它宣布界面出来了。
- 结论要写下来，下一个人不该重新推一遍。

## Definitions

| Term | Meaning |
|---|---|
| 结算界面 | 打死 boss 后客户端摆出的那一屏：修理商在场、回城入口可用 |
| 清关判定 | 服务端认定本局可以结束的规则，当前是"boss 房声明的敌对角色全部被报告死亡" |

## External Behavior and Data Rules

- 现有顺序：服务端自行判定清关 → 发 `NOTI 0x001F ENABLE_CLEAR_DUNGEON` 与 `NOTI 0x0117 SECRET_SHOP_NPC(1000)` → 客户端发来 `CMD 0x0075`。
- 参照服务端的顺序相反：客户端先发 `0x0075`，服务端据此判定并**由此触发**清关；它对这一帧本身不回应答。
- 捕获到的一次 `0x0075` 体（39 字节）：`0100E90E000000000000000000010000002F0200000000000071020D0192013E010A0008001100`。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 客户端在结算处等待应答的那一帧被服务端应答，且服务端为它准备的应答是客户端会接受的形状 |
| RQ-002 | `CMD 0x0075` 被服务端识别与解码，不再落入未处理帧 |
| RQ-003 | 服务端对 `0x0075` 的应对方式有明确结论，并在代码或文档中写明其依据 |
| RQ-004 | 本局没有 run、或已经结算过时，`0x0075` 不会触发第二次清关或第二次发奖 |
| RQ-005 | `0x0075` 的体不可解或不指向本局的 boss 时，本局不卡死，服务端不据此改变任何状态 |
| RQ-006 | 既有的清关判定与结算路径的可观察行为不变 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 结算卷轴已画完，客户端发来它等待应答的那一帧 | 服务端处理它 | 服务端在同一 type 上回一帧，其形状与客户端的读取行为相符 |
| AC-002 | RQ-002, RQ-003 | 客户端发来 `0x0075` | 服务端处理它 | 不再记为未处理帧；其角色的结论可在代码或文档中读到 |
| AC-003 | RQ-004 | 本局已经结算过 | 再次发来 `0x0075` | 不触发第二次清关，不产生第二次发奖 |
| AC-004 | RQ-004 | 角色不在任何 run 中 | 发来 `0x0075` | 被拒绝，服务端状态不变 |
| AC-005 | RQ-005 | `0x0075` 的体不可解，或指向不属于本局的角色 | 服务端处理它 | 被拒绝，本局仍可正常结算 |
| AC-006 | RQ-006 | 与改动前相同的一局 | 打完并结算 | 清关判定的时机与结算帧的内容与改动前一致 |

## Assumptions

- 取证的结论是：结算界面停住的地方是 `CMD 0x0045 SCORE_SCROLL_STATE` 未被应答，而不是
  `CMD 0x0075`。后者在实机上未被应答时，客户端照样走完了 `SET_PLAY_RESULT` 与结算帧。
- 应答 `0x0045` 之后客户端是直接收尾，还是转去问翻牌链（`0x0046`/`0x0047`），静态分析断不了——
  分支条件里有一个查表的 id 尚未确定。若实机显示它转去翻牌，则「回城入口可用」要等第四个子成果
  一起才看得到，这在根契约的终验里体现，不改本 Spec 的边界。
