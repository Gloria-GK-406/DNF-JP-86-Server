# spec-003-floor-quantities 结果

## 交付了什么

* 房间描述帧掉落记录 `+7` 的 `u32` 不再无条件写实例判别值：**堆叠物写档案声明的数量，
  装备写实例判别值**，由 `FloorPieceValues` 按物品种类决定。
* 档案里那个一直没被读的数量字段现在读了（`.map` 的 `[special passive object]`，组号之后那个整数）。

## 判据强度

三个变异全部被抓住：恒写判别值（即原缺陷）、恒写数量、以及**无视档案声明恒写 1**。
最后一条最初活了下来——所有既有判据都通过——因为教学副本每一条都声明 1。补了一条读真档案的
判据：副本 144 的 boss 房 55611 声明 `[item] 组1 数量3`，读出来必须是 3。

## 未做与存疑

`+7` 的双重语义取自两处互相印证的证据（上游 `DropInfo.PacketValue`、本仓库 `value` 列的语义），
**尚未从客户端反汇编直接确认**——`START_MAP` 的 handler 很大，掉落块的读取落在跟不进去的子调用
里。实机截图仍是根契约 SC-3 的判据。
