# TaskContract: 打完一局能拿到该拿的，也能走得出去

## Context

### Source Request

用户 2026-08-29 实机验收 `dungeon-run-experience` 后报告：

> 1.在副本回到城镇不好用 2. 在副本掉落了巨多数量的材料。可能数十万，完全不正确。3.杀死boss后应该有修理商出现，并且展示回城UI 4.打死boss后的翻牌子没出现 其余的频道经验加成是对的，最终boss结算也有了

随后指示：「合并工作区，清理main基线到干净。起一个新的sdd来实现。可以用multispec，写完任务契约和spec等待吧。我压缩一下上下文再一次性跑完。翻牌子那个记得实现领域服务，不能在报文handler直接处理。」

### Current Situation

经验系统已经完整（`c5a36a1d`，实机确认：频道 10 `award=75 (base 72 + channel 3)`、频道 11 同图 `award=72`、结算 `clearBase=552 rankBonus=110`）。**卡住的是它前后的那一圈**：打完 boss 之后玩家出不去，捡起来的材料显示成几十万。

那次会话的服务端日志把三条的成因摆得很清楚——三个客户端发来、我们**根本没有处理器**的帧：

| 帧 | 上游名字 | 何时出现 | 对应用户报告 |
|---|---|---|---|
| `CMD 0x0075` | `BOSS_DIE_CHECK` | 我们发出「boss 房已清、开门」之后立刻 | 第 3 条：修理商与回城 UI 不出现 |
| `CMD 0x0045` | `SCORE_SCROLL_STATE` | 结算帧发完之后 | 第 3、4 条：整条收尾链停在这里 |
| `CMD 0x002F` | `DROP_ITEM` | 副本中途 | 用户没报，但同属这一圈的缺口 |

（**这张表在 2026-08-29 取证后被订正过一次。** 原表把 `0x0045` 写成上游 `GameProtocolHandler.cs:664`
处的**处理器名** `CARD_START_REQUEST`；客户端自己的 type 名是 `SCORE_SCROLL_STATE`。同一次取证还
查明第 1 条走的根本不是 `GIVEUP_GAME`，见下。**上游只是线索，不是权威**——这个仓库已经三次
因为照抄上游命名而错，权威是客户端反汇编与实机。）

另外两处不是缺处理器，是现有实现不对：

* **离开副本回到城镇**：**本条的成因在 2026-08-29 被取证推翻。** 原判读是「`GiveUpGameHandler` 只回一个字节的 ack、不推城镇状态」。上游一次完整通关的抓包里**根本没有 `CMD 0x002A GIVEUP_GAME`**——客户端用 `CMD 0x0048 EPLP_COMMAND` 离开，而本仓完全没有这个 type。`Docs/ProtocolScaffoldDissonances.md` 第十四条记的那件事仍然成立，但不是本条的成因。
* **地面掉落的数量**：`Server/src/Dfo.Server.Protocol/Game/DungeonEntry/DungeonEntrySlice.cs:279`，房间地面掉落记录里物品 id 之后那个 `u32` 写的是 `DropInstance(...)`——一个 31 位伪随机判别值。**对装备是对的**（区分同款的两件，`GroundPickupSlice.CarryOverAsync` 依赖它），**对堆叠物就是错的**：客户端把那个位置读成数量。用户捡到的是 `item 10088621`。

## Goal

一局副本能正常收尾：打死 boss 之后结算界面该出的都出得来，翻牌能翻，走得回城镇；地上躺着的东西显示的数量就是它真正的数量。

## Scope

### In

- 应答 `BOSS_DIE_CHECK`，使结算界面（含修理商与回城入口）在实机上出得来。
- 离开副本后把角色真正放回城镇，而不是让客户端自己重连去问。
- 地面掉落记录中数量与实例判别值的区分，使堆叠物显示真实数量、装备仍能被区分。
- 翻牌奖励：**作为领域服务实现**，含奖励的决定、一次性、以及结算帧里对应字段的如实填写。
- 上述每一项的失败与边界行为。

### Out

- `CMD 0x002F DROP_ITEM`（往地上丢东西）。同一圈的缺口，但它是"放下"而不是"收尾"，与本任务四件的验收边界无关；记录待办。
- 掉落**内容**的生成规则（怪物掉什么、按什么概率）。本任务只管已经躺在地上的东西怎么被正确描述。
- 结算的金币、卡片以外的奖励物品。
- 结算侧的频道奖励与账号权益加成——需要先测出结算帧那 23 个固定槽的语义，见 `Docs/ExperienceNoticeSlots.md` 第七节。
- 组队。

## Constraints

- **翻牌必须实现为领域服务，不得在报文 handler 里直接处理**（用户明确要求）。奖励的决定、一次性与持久化归领域，handler 只负责收发。
- 权威是客户端反汇编与实机表现；`ServerS4A21` 与 `S4A21ClientPatch` 只有线索价值。本仓库已两次因照抄上游命名而错（经验通告的两个槽、频道加成的比率来源），第三次不可再犯。
- 已验证的线级字节不得改变。新增的只能是原本没有回应的请求现在有了回应，以及原本恒零/恒错的字段现在带上正确值。
- 每一件都要能在实机上看见其"生效"与"不生效"两面，或说明为什么看不见。
- 装备的实例判别值不得因修掉数量而丢失——`GroundPickupSlice` 依赖它把地上那件与背包那件对上。

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 打死 boss 后结算界面出得来，修理商在场 | 客户端的 `BOSS_DIE_CHECK` 得到应答（日志中不再是 `Unhandled Game frame`）；实机截图 |
| SC-2 | 结算完成后能走回城镇，客户端不需要重连 | 离开副本后日志中不再出现新的登录握手；实机确认人回到城镇 |

| SC-5 | 打死 boss 后能翻牌，翻到的东西进背包，同一局不能翻两次 | 领域服务的单测（决定、一次性、落库）；实机截图 |

| SC-8 | 全套测试通过，构建零警告零错误 | `dotnet build` 与 `dotnet test` 输出 |

- 合并回 main、删除任务工作树与分支：本任务的授权不含收尾，与上一个任务一样要单独确认。

## Assumptions

- 三个未处理帧的上游名字（`BOSS_DIE_CHECK` / `CARD_START_REQUEST` / `DROP_ITEM`）指示了它们大致是什么，但每一件的**应答内容**都要自己定：从客户端反汇编读它期待什么，或用实机试出来。不照抄上游的应答字节。
- 地面掉落记录里那个 `u32` 的双重语义（装备的实例判别值 / 堆叠物的数量）是从"装备能对上、材料显示成几十万"这两个观察推出来的，尚未从客户端反汇编确认。若反汇编显示是别的结构，以反汇编为准。
- **一件顺带可以看的遗留**：结算屏上「通关经验 552」与「评分奖励 110」两栏的对应关系仍未确认——结算帧头两个字段的含义取自上游命名，未经实测。它属 `dungeon-run-experience` 的遗留，不是本任务的判据；但本任务会把玩家送进结算屏，届时顺带看一眼即可。
