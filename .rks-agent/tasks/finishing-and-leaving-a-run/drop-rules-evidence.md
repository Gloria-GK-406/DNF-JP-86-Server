# 掉落规则：怪物掉落与翻牌掉落（2026-08-29 取证）

结论先行：**两者是同一台机器，喂不同的表。** 重建一次，两处都有了。

## 一、档案里的四份东西

| 文件 | 给什么 |
|---|---|
| `Etc/ItemDropInfo_Monseter.etc` | **怪物掉落的费率表** |
| `etc/itemdropinfo_clearreward.etc` | **翻牌掉落的费率表** |
| `Etc/ItemDropInfo_Common.etc` | 只有一段 `[gold drop ref table]`：每级的金币基数与浮动百分比 |
| `Etc/ItemDictionary/ItemDictionary.etc` | **物品索引**（1.25 MB，一物一行） |

### 怪物费率表的形状

```text
[drop prob count] 10
[drop prob]   每段 7 个数：低级 高级 金币率 类型1率 类型2率 类型3率 ?
              1 15 986 60 250 0 0 | 16 23 750 30 210 17 15 | … | 81 200 750 10 135 8 5
[basis of rarity dicision]        7 个稀有度门槛 × 4 组（按怪物档次）
[party member drop bonusrate]     4 个 × 5 组
[dungeon difficulty drop bonusrate] 5 个 × 5 组
[monster type drop bonusrate]     4 个 × 5 组   ; 1 2 3 6.6 | 1 2 3 4 | 0.2 2 7 16.8 | …
[item drop ref table]             等级 → (下探, 上探) 品级带
```

三种类型各掷一次：**类型 1 出堆叠物、类型 2 出装备、类型 3 再出堆叠物**。
每一掷：等级 → 品级带；按门槛掷稀有度；从 `(品级, 稀有度)` 桶里按权重抽一件。

翻牌费率表是同样的骨架，只是换了名字：出现概率按 profile×等级段、难度/组队/探索度加成、
同一张 `[item drop ref table]`、外加 `[drop item type prob] 0 9500 0 500`（装备 95% / 时装 5%）。

## 二、物品池不用我们自己建

`Etc/ItemDictionary/ItemDictionary.etc` 一物一行，列义（依上游解析，自洽可核）：

```text
[0] itemId   [1] rarity   [2] grade   [3] ?   [4] equipCategory   [5] genRate   …   `名称`
筛选：genRate > 0、grade > 0、rarity ≤ 5、equipCategory/1000 ∈ {10,11,12}
分桶：grade*10 + rarity，桶内按 genRate 加权
```

**这就是我先前以为要扫一万个 `.equ` 才能建出来的那份索引。** 它是一个普通内容源，
和本仓已有的那些没有区别。

堆叠物侧同理：`stackable/stackable.lst` + 每个 `.stk` 的 `[grade]` / `[rarity]` /
`[creation rate]`，同样按 `(品级, 稀有度)` 分桶加权。

## 三、还有一层：怪物自己的掉落池

怪物文件（`monster/monster.lst` → `.mon`）里的 `[item]` 段是 `(itemId, weight)` 对，
即这只怪特有的掉落。与上面的通用掷法叠加。

## 四、上游编的那一块，不要抄

`AreaMaterialDropProvider` 是**硬编码**的：手写的副本→材料映射加一个固定 25%。

```csharp
for (int d = 144; d <= 149; d++) map[d] = 10088620;   // 亚诺法森林 → 精灵气息
for (int d = 150; d <= 155; d++) map[d] = 10088624;   // 漂流洞穴 → 浮游石原石
…
private const int DropRatePercent = 25;
```

**没有找到档案来源。** 物品 id 也许是真的，那个映射与 25% 不是。
`etc/itemdictionary/(f)independentdropinfo.etc` 里有 `[item table]`（5221 条物品→列表）
与 `[monster table]`（物品↔怪物，带等级段），**可能**是它的正主，尚未证实。

## 五、由此得出的重建方式

一台机器，四个零件：

1. **费率表内容源** —— 两个实例：怪物表、翻牌表。纯数据。
2. **物品池内容源** —— `ItemDictionary.etc`（装备）+ `stackable.lst`/`.stk`（堆叠物），
   都按 `(品级, 稀有度)` 分桶加权。
3. **纯抽取规则** —— 等级→品级带、掷稀有度、桶内加权抽一件。无状态、可单测。
4. **可复现随机源** —— 由本局 seed 派生。

怪物掉落与翻牌奖励的差别**只在于喂哪张费率表、以及什么时候触发**。

## 七、稀有度判定：算法查明（社区文档 + 本档案 + 上游代码，三方互证）

社区的 PVF 爆率解析给出解码规则（`heihuo000/86nut` 知识库，DAF 学院《爆率文件解析（完全版）》）：

> 每组数据有 6 个数，前 5 个分别表示 白装、蓝装、紫装、粉装、史诗 的爆率参数（A B C D E），
> 最后一个为爆率基数 X，**X = E + 1**。
> 摇一个 X 以内的随机整数 n（0 < n ≤ X−1）：
> n ≤ A 白装；A < n ≤ B 蓝装；B < n ≤ C 紫装；C < n ≤ D 粉装；D < n ≤ E 史诗。
> **爆率参数后一位要大于等于前一位；与前一位相同时该档爆率为 0。**

**A21 的每组是 7 个数**，多一档。用「最后一个 = 前一个 + 1」这条不变式核对，我们文件里每一组都成立
（`… 1000001 1000002 1000003`，`1000003 = 1000002 + 1`），所以是**六档 + 基数**：
白、蓝、紫、粉、史诗、传说。

### 本档案算出来的实际概率（摇点 1..1000002）

| 表 | 门槛 | 白 | 蓝 | 紫 | 粉 | 史诗 | 传说 |
|---|---|---|---|---|---|---|---|
| 怪物（第 1 组） | `700000 964900 990000 1000000 1000001 1000002 1000003` | 70.00% | 26.49% | 2.51% | 1.00% | 0.0001% | 0.0001% |
| 翻牌 | `500000 799900 999900 1000000 1000001 1000002 1000003` | 50.00% | 29.99% | **20.00%** | 0.01% | 0.0001% | 0.0001% |
| 可破坏物 | `700000 944900 999900 1000000 1000001 1000002 1000003` | 70.00% | 24.49% | 5.50% | 0.01% | 0.0001% | 0.0001% |

翻牌出紫的概率是打怪的八倍——与「翻牌容易出紫」的手感一致。

### 上游把史诗和传说做没了

`MonsterDropConfig.RollRarity` 写死 `lcg.Next(1000000) + 1`（摇点 1..1000000），
而基数说的是 1..**1000002**。于是门槛为 `1000001` 的史诗与 `1000002` 的传说**永远摇不到**——
n 最大 1000000，在粉那一档就停了。

**基数必须从表里读，不能写死。** 这正是不能照抄上游的又一例。

（上游还有一处：`_rarityThresholds[0, r]` 恒取第 0 组，忽略了表里的 4 组。）

## 十、深渊：两件不同的「独立」

### 1. 深渊有自己的爆率表，结构也不一样

`etc/itemdropinfo_monster_hell.etc`：

```text
[drop prob count] 2
[dungeon difficulty drop prob]        ← 注意标签名：按**难度**分，不是按物品类型分
1 44   0 0 0 0 0                      ← 45 级以下：全零，深渊不出东西
45 200 335 875 1000 1400 1000         ← 45 级以上：五个难度各一档
[basis of rarity dicision]
2
0 599000 993000 993000 1000000 1000001 1000001
0 800000 1000000 1000000 1000001 1000002 1000001
```

按「最后一个是基数 X、摇点 1..X−1、相邻相同则该档为 0」这套规则读（X = 1000001，摇 1..1000000）：

| 组 | 白 | 蓝 | 紫 | 粉 | 史诗 | 传说 |
|---|---|---|---|---|---|---|
| 第 1 组 | **0%** | 59.90% | 39.40% | **0%**（C=D） | **0.70%** | 0%（F > X−1） |
| 第 2 组 | **0%** | 80.00% | 20.00% | **0%**（C=D） | 0%（E > X−1） | 0% |

**深渊的史诗是 0.7%，普通怪物是 0.0001%——差七千倍。** 而且深渊里白装和粉装都被关掉了
（把门槛设成与前一位相同即为 0，正是社区文档说的那条规则）。两组大概对应常态/非常态，未确认。

**所以「深渊爆史诗的概率是独立的」——是的**：它走的是另一张表、另一套门槛、另一个概率轴
（按难度而不是按物品类型）。

### 2. 另有一个真正叫「独立掉落」的机制，它连稀有度阶梯都不走

`etc/independent_drop.etc`（A21 里 313 KB），外加一整个 `etc/independentdrop/` 目录
（按 boss 分文件：`101_bakal_normal.etc`、`102_bakal_expert.etc` …）。

```text
[independent drop]
0 20 0 1000000 1000000 1000000 1000000 1000000 1 1 1 1 1 0 0 -1 1
[list]
14400 1000
[/list]
```

按社区教程（DAF 学院《怪物独立爆率修改教程》）：怪物代码、**五个难度各一个掉落几率**
（1000000 = 100%）、五个数量、然后 `[list]` 里是 `(物品代码, 几率)`，**10000 = 100%**。

**它不掷白蓝紫粉**——它直接掷「这一件specific物品掉不掉」。这就是特定 boss 稳定掉特定东西的做法。

**这同时是「特产材料」的档案来源。** 上游的 `AreaMaterialDropProvider` 是手写映射加固定 25%；
档案里本来就有这个机制。（尚未逐条核对 10088620/10088621 是否在其中。）

## 十一、爆什么东西：四道闸

### 闸 1：掉不掉

`[drop prob]` 按等级段给出**金币 / 类型1 / 类型2 / 类型3** 各自独立的几率，各掷各的。
**四个都没中就是不爆东西**——「不爆」不是一个结果，是几次都没中。

### 闸 2：爆哪一类

中的是哪个类型槽：

| 槽 | 取自 |
|---|---|
| 类型 2 | **装备** —— `Etc/ItemDictionary/ItemDictionary.etc` |
| 类型 1 / 类型 3 | **堆叠物** —— `stackable/stackable.lst` + 各 `.stk` |

翻牌那边还多一次细分：`[drop item type prob] 0 9500 0 500` → 装备 95% / 时装 5%。

### 闸 3：哪些东西有资格进池子 —— 物品自己的 `[creation rate]`

**42272 个堆叠物里只有 787 个声明了 `[creation rate]`**（762 个是 1000，13 个是 0，其余零星）。

```text
41485  (absent)     ← 没声明就进不了通用掉落池
  762  1000
   13  0
    4  700   2  750   2  800   2  850   2  900
```

**这是档案自己的闸。** 装备侧同理：`ItemDictionary.etc` 的 `genRate > 0`。

### 闸 4：是什么类别 —— 物品自己的 `[stackable type]`

A21 的 42272 个堆叠物分 19 类，前几名：

```text
9268 [recipe]  设计图      5940 [material expert job]   5151 [booster]  增益
2815 [booster selection]   2795 [waste]  消耗品          2481 [etc]
2091 [material] 材料       1569 [upgradable legacy]     1268 [quest] 任务
1259 [enchant waste]       1229 [avatar emblem] 徽章     ...
```

### 抽样结果：通用池里的堆叠物主要是设计图，材料不在里面

| 物品 | 名称 | `[stackable type]` | grade/rarity | `[creation rate]` |
|---|---|---|---|---|
| 10087807 | (魔法封印) 钢铁念珠 **设计图** | `[recipe]` | 57 / 2 | **1000** |
| 10088621 | 遗留的水晶碎片 | `[material]` | 1 / 1 | **无** |
| 10088620 | 精灵气息 | `[material]` | 1 / 1 | **无** |

**材料没有 `[creation rate]`，进不了通用掉落池。** 它们走另外两条路：房间可破坏物的声明
（用户捡到的 10088621 正是这一条），或 `independent_drop.etc` 的独立掉落。

**这解释了游戏体感：打怪掉设计图，材料靠特产 / 独立掉落。**

### 上游这一段又是编的

`MonsterDropConfig.LoadStackablePool` 按**目录名**排除：
`cash/ quest/ recipe/ temp/ event/ emblem/ monsterCard/`。这是手写启发式，不是档案规则。
而且它排 `recipe/` 想排掉设计图，但能掉的那些设计图放在 `stackable/` 根目录
（`10087807.stk`），根本不在 `recipe/` 下——排了个空。

真正的闸是 `[creation rate]`，它自己也用了，两道并存。

## 十二、结构更正：不是多选一，是并列的独立产出者

一次击杀跑的是**一串互不排斥的产出者**，每个各掷各的、各自可能贡献 0 件或多件，
全部汇进同一个列表：

```text
掉落列表 = []

1. 金币        if 金币率 > 掷(分母):            加金币（数额另按等级表 + 浮动）
2. 类型 1      if 类型1率 > 掷(分母):           掷稀有度 → 等级→品级带 → 桶里抽一件【堆叠物】
3. 类型 2      if 类型2率 > 掷(分母):           掷稀有度 → 等级→品级带 → 桶里抽一件【装备】
4. 类型 3      if 类型3率 > 掷(分母):           掷稀有度 → 等级→品级带 → 桶里抽一件【堆叠物】
5. 怪物自有池  if 怪物掉落率 > 掷(分母):        **按权重**从该怪 [item] 段里选一件（不掷稀有度）
6. 独立掉落    IndependentDropSystem            按 independent_drop.etc 逐件掷
7. 世界掉落    WorldDropSystem                  另一套
8. 次元掉落    DimensionDropSystem              由调用方追加
```

**「不爆东西」不是一个选项**，是上面每一条都没产出的结果。反过来，一次击杀完全可以
同时掉金币 + 一件装备 + 两件堆叠物 + 独立掉落的东西。

**横向并列，纵向才细化**：只有在通用那三个类型槽里，才有「掷稀有度 → 品级带 → 桶里加权抽」
这一层。怪物自有池是另一种：**一道闸 + 组内按权重选一件**，不经过稀有度。

每个产出者还各自受 `DungeonDropPolicy` 的开关控制（副本可以单独关掉某一路）。

### 对 `[special passive object item]` 权重的旁证

怪物自有池用的正是 `(itemId, weight)` 这个形状，用法是**权重选一件**。
`.dgn` 的 `[special passive object item]` 是同样的形状（144 是 `10088621 2000` / `10149508 5000`），
**大概率也是组内选择权重**，而不是出现概率——现在有了结构上的旁证，但仍未直证。

## 十三、上一节哪些是定死的，哪些只是读法

被问到出处，逐条分开。

### 定死的

| 事实 | 由什么定死 |
|---|---|
| **一次击杀可以掉多件** | **客户端**。`NOTI 0x0026` 的 handler（RVA `0x00D54840`）读 `u16 actor` + `u8 计数`，然后按计数**循环**读掉落记录（回跳 `0x00D55076 → 0x00D54DFF`），最后一个 `u8`。「一次只出一件」被排除。 |
| `[drop prob]` 每段给出**四个各自独立的数**（金币 + 三个类型槽） | 档案文件本身 |
| 稀有度是另一套阶梯 | 档案 `[basis of rarity dicision]` + 社区文档的解码规则 |
| 池子资格由物品自己的 `[creation rate]` / `genRate` 决定 | 档案 |
| 独立掉落是**另一条**不走阶梯的路 | 档案 `etc/independent_drop.etc` + 社区教程 |

### 只有上游源码这一个来源 —— 是读法，不是证据

| 说法 | 出处 |
|---|---|
| 四个率是**独立掷**而不是一个互斥分布 | `DropGenerator.GenerateMonsterDrops` 的四个并列 `if` |
| 分母 = 10000 | `private const int DropDenominator = 10000;` **档案里没有这个数** |
| `MobItemDropRate = 1000` | 同样是写死的常量 |
| 类型槽 1/3 → 堆叠物、2 → 装备 | 上游的映射 |
| 产出者的顺序与 `DungeonDropPolicy` 开关 | 上游的结构 |

**而上游在这一族文件里已经被抓到三处编造**：区域材料硬编码映射 + 固定 25%、堆叠物按目录名过滤、
稀有度分母写死导致史诗与传说永远摇不到。**它的结构和它的数值一样不可信。**

### 这个差别有多大

按上游的数（等级 1–15：金币 986、类型1 60、类型2 250、类型3 0，分母 10000）：

* 互斥分布：出东西的概率 = 1296/10000 = **12.96%**
* 独立掷：1 − (1−.0986)(1−.006)(1−.025) = **12.64%**

**「出不出东西」这一项两种读法几乎看不出差别（差 0.32 个百分点）。**
真正能分辨的是「能不能同时掉两件」——独立掷下金币与装备同时出现约占 0.25%（四百次击杀一次），
互斥分布下永远为 0。**要一份真实服务端的击杀样本才能判**，我们没有。

### 结论

**这一条我给不出定死的证据。** 客户端只画结果，答得了「能带几件」，答不了「怎么算」。
可取的做法是：按「并列独立产出者」实现（协议的计数列表正是为这个而设），
把这一处读法**收在一个地方并写明它是假设**，日后有真服样本时只改那一处。

## 十四、玩家记忆解开了第 7 个数，也给了「独立掷」一个档案侧论据

用户（2026-08-30）凭实际游玩回忆：**普通图一只怪一般就是给钱、或者爆件装备，没见过一次爆好几个；
boss 和精英好像有。**

### 先解开悬案：`[drop prob]` 每行第 7 个数是第 4 个物品类型

三张加成表都是 **5 组**：

```text
[monster type drop bonusrate]        5 组 × 4 档怪
[dungeon difficulty drop bonusrate]  5 组 × 5 难度
[party member drop bonusrate]        5 组 × 4 队伍人数
```

而 `[drop prob]` 每行去掉 `low high` 正好剩 **5 个率**。**一组对应一个率**，数目严丝合缝：

```text
[drop prob] 行 = 低级 高级 | 金币率 类型1 类型2 类型3 类型4
```

先前记为「未查明」的第 7 个数，是**类型 4 的率**。

### 怪物档次加成里，装备那一组是 0.2 / 2 / 7 / 16.8

```text
[monster type drop bonusrate]
金币   1    2   3   6.6
类型1  1    2   3   4
类型2  0.2  2   7   16.8     ← 装备
类型3  1    2   3   4
类型4  1    2   3   4
```

**普通怪的装备率要乘 0.2，boss 要乘 16.8——相差 84 倍。**

### 按档案自己的数算出来的结果，和玩家记忆逐条对上

等级 81–200 段（金币 750、类型2 135，分母按上游的 10000）：

| 档次 | 金币 | 装备 | 出东西 | **金币+装备同时出** |
|---|---|---|---|---|
| 普通 | 7.50% | 0.27% | 7.96% | **0.02%（约 1/4938）** |
| 精英 | 15.00% | 2.70% | 17.67% | 0.41%（约 1/247） |
| 命名 | 22.50% | 9.45% | 30.31% | 2.13%（约 1/47） |
| boss | 49.50% | 22.68% | 61.31% | **11.23%（约 1/9）** |

等级 1–15 段更极端：普通怪同出 1/2028，boss 同出 **1/4**。

**「普通怪没见过一次爆好几个、boss 和精英有」——正是这张表算出来的样子。**

### 这构成对「独立掷」的论据

互斥分布下，怪物档次加成只能改变**掉的是哪一样**，永远改变不了**掉几样**——
那样「boss 会一次掉好几件」就无从解释。**独立掷才能同时解释两头。**

仍需说明的强度：组的顺序（金币在前、类型依次）与档次顺序（普通/精英/命名/boss）
是由数目吻合与数值递增推出来的，文件本身没写；分母 10000 仍是上游的常量。
但结论对这些不确定并不敏感——它由 0.2 与 16.8 这 84 倍的差距驱动。
