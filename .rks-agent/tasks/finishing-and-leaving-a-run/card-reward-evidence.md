# 翻牌奖励：取证汇总（2026-08-29）

用户要求「先收集一下相关信息我们再看看怎么做」。本页是收集结果，不含实现决定。

## 一、你记的那三种牌子，档案对得上

`etc/itemdropinfo_clearreward.etc` 里三side 各有各的表：

| 牌子 | 上游叫法 | 花费 | 给什么 |
|---|---|---|---|
| 普通（免费） | `CardRewardSide.Free` | 0 | **金币 + 装备**，两样一起给 |
| 黑钻免费牌 | `[pcroom card blank item]` | 0（需黑钻） | `50 7454 1` → 物品 7454「钻石硬币」×1 |
| 黄金牌（付费） | `CardRewardSide.Paid` | `[gold card cost table]`，按等级：1 级 100、5 级 580、86 级 10300 | **装备**（空牌时给 `[gold card blank item]`） |

`[gold card blank item]` 在这份 A21 档案里是 `10002120`「幽灵赛丽亚的痕迹」——一个 2013 年的
活动残留物，不是通用兜底。**这一条不能直接拿来当奖励**。

## 二、协议那一半已经定死（两边互证，逐字节）

| 交换 | 请求 | 应答 |
|---|---|---|
| 卷轴 | `CMD 0x0045`（0B） | `CMD 0x0045 [01]` **加** `CMD 0x0046` 版式（17B） |
| 版式 | `CMD 0x0046`（0B） | 同上那 17B |
| 翻牌 | `CMD 0x0047 [cardType, cardIndex]` | `CMD 0x0047`（33B） |
| 发货 | — | `NOTI 0x000E` 背包变化 |

版式 17B = `01` + `u16 0x0001` + 7×`u16 0xFFFF`；抓包里就是
`01 01 00 FF FF FF FF FF FF FF FF FF FF FF FF FF FF`，与上游 `BuildCardLayoutAck` 逐字节相同。

33B 应答 = `01` + 8 组 4 字节；第 0 组 `free?00:FF, paid?00:FF, 00, 00`，第 1–3 组
`FF FF 00 00`，第 4–7 组 `FF FF FF FF`。抓包与上游 `BuildCardInfoAck` 也逐字节相同。

`cardType` 0=免费 1=付费（>1 丢弃），`cardIndex` 0..3（>3 丢弃），**只有 index 0 真发奖**。

## 三、奖励内容需要的东西，逐项点清

### 已经在档案里、可以直接读

* `etc/itemdropinfo_clearreward.etc`：出现概率（按 profile × 等级段）、难度加成
  `0 600 1000 1400 1200`、组队加成 `1 1.2 1.4 1.6`、金币难度倍率 `1.02 1.38 1.6 1.9 2`、
  稀有度门槛 `500000 799900 999900 …`、探索度加成 `1 2000 2 3000 3 4000 4 5000 5 6000`、
  装备品级带 `[item drop ref table]`（三元组「等级 下探 上探」，1 级是 `0 3`）、
  物品类型概率 `[drop item type prob] 0 9500 0 500`（类型 2 普通装备 95%、类型 4 时装 5%）。
* `Etc/ItemDropInfo_Common.etc` 的 `[gold drop ref table]`：每级的怪物金币与浮动百分比
  （1 级 17/13%，5 级 44/13%…）。

### 本仓没有、要新建的

1. **装备掉落池索引。** 上游扫全部 `equipment/*.equ`，取 `[grade]`、`[rarity]`、`[creation rate]`，
   按 `grade*10+rarity` 分桶、按 creation rate 加权。本仓已经会从 `.equ` 读 `[durability]`，
   所以读法在，缺的是这份全量索引与缓存。**这是最大的一块。**
2. **角色金币的写入路径。** 本仓的金币只在进场投影里被读过一次，**既没有落库路径，也没有告诉
   客户端金币变了的帧**。免费牌给金币、黄金牌扣金币，两边都要它。
3. **可复现的随机源。** 上游用 `DnfLcg`，同一局重问要给同样的牌。
4. **怪物档次计数。** 金币按 `普通 + 2×精英 + 4×boss` 加权，本仓不分档次（这一条在上一个任务里
   就记为待办）。不做的话金币会偏低——是有界的偏差，不是瞎编的数。

## 四、由此可见的几条路

* **只发装备**：绕开金币那一整块，但要先建装备池索引。是「一般是装备」这句话的最短路径。
* **只发金币**：绕开装备池，但要新建金币写入与投影。
* **两样都发**：上游免费牌的真实行为，两块都要。
* **先只让牌能翻、不发东西**：最快，但玩家拿不到东西。

## 五、还没查的

* 副本自己的 `.dgn` 有没有覆盖这些表的声明（本页只查了全局 etc）。
* 「材料」类奖励从哪来——你提到别的副本会发材料，全局表里的类型概率只列了装备与时装两类，
  材料可能走副本自己的声明或另一张表。
* 客户端对 `NOTI 0x000E` 的读取方式（本仓已有背包变化帧，但没在翻牌这条路上验过）。

## 六、翻牌对物品种类没有约束（2026-08-29 追查）

问题：不发装备、发消耗品，客户端接不接受？**接受。** 三条互不依赖的证据：

### 1. 牌面上的物品只能从 `CMD 0x0047` 应答的 `(id, count)` 对来

`CMD 0x0047` 应答处理器（RVA `0x00D05250`）**按槽循环**，每槽读 `a(u8) b(u8) c(u8)`，
其中 **`c` 是其后 `(u32 id, u32 count)` 对的条数**；每读到一对就调

```text
setSlot(id, count, slot, 3)   ; 0x021F8DC0，kind 3 = 物品
setSlot(amount, 1, slot, 4)   ; id == -1 且标志成立时，kind 4 = 金币
```

`setSlot` 进门就拿 id 去做一次字符串表格式化（`0x00AE9BF0`，压的是串号 `0x3B` / `0x12B`）——
**这就是「你翻到了 X」那一面**。

**上游只在付费那一支填这些对，免费牌写 `c = 0`。** 所以抓到的那次免费翻牌里一个 id 都没有：
在上游驱动下，免费牌的牌面**根本不显示翻到了什么**，东西只是经
`NOTI 0x000E UPDATE_ITEM_LIST`（`u8 列表类型 + u16 条数 + 条目区`）出现在背包里。

**但读取端是按槽统一的，不分免费/付费**——免费槽照样能带对。想让免费牌把东西显示出来，
发 `c ≥ 1` 加一对即可。**（这一条是从读取端的对称性推出来的，没有见过真实服务端的免费牌应答
带对的抓包。）**

### 2. 真发 id 的那一支也不查种类

只有付费（黄金）牌会写 `(u32,u32)` 对。处理器拿到之后：

```text
if (id == -1 && flag)  setSlot(count, 1,  slot, 4)   ; kind 4 = 金币
else                   setSlot(id,    count, slot, 3) ; kind 3 = 物品
```

`setSlot` 是 `0x021F8DC0`，进去第一件事就是拿 id 去查表格式化。**整条路上没有一处检查这件东西
是装备还是堆叠物**，唯二的校验是槽序号 `> 7` 丢弃、以及一个与种类无关的标志位。

### 3. 档案自己就把堆叠物放在牌上

`[gold card blank item]` 是 `10002120`，`[pcroom card blank item]` 是 `7454`——两个都是
`.stk`（堆叠物），不是 `.equ`。游戏自己的数据就在用消耗品当牌面奖励。

### 由此可见

牌面显示与物品种类无关：显示走的是 id → 字符串表，`setSlot` 全程不问这是装备还是堆叠物。

发消耗品/材料**比发装备便宜**：走的是本仓已有的背包到货路径，**完全绕开装备掉落池索引**
（第三节里最大的那一块）。剩下的问题只是「发哪一件、发几个」——也就是你说的那个按副本产出的
规则服务。

**未证的一点**：以上证明的是没有种类检查与送达路径通用，**没有证明牌面把堆叠物的图标画得对**。
那是 UI 问题，一次实机翻牌即可确认。

## 七、时序：内容什么时候定、什么时候还、什么时候进包

```text
结算时     服务端处理 SET_PLAY_RESULT，此刻就把本局的牌面内容算出来并**留在服务端**
           （上游 DungeonSettlementHandler:873 建 run.CardRewards = [免费金币, 免费物品, -, -,
             付费金币, 付费物品, -, -]）

摆牌       SEND CMD 0x0045 [01]
           SEND CMD 0x0046 (17B) = 01 + u16 0x0001 + 7×u16 0xFFFF
           **这一帧里没有任何物品** —— 只说有哪几个位置。牌是背面朝上的，客户端此刻确实不知道
           牌里是什么。客户端对本帧的处理器也只读 u16，读不到 id。

点击       RECV CMD 0x0047 [cardType, cardIndex]
           客户端的点击构包点 0x00704460 是个两参小函数：
               WriteU8(0)            ; cardType 写死 0 = 免费
               WriteU8(arg)          ; cardIndex
           **点击这条路永远发免费牌**；付费牌走另一个构包点（0x00D10DFF，只写一个字节，
           形状不同，普查因此标 divergent）。

翻开       SEND CMD 0x0047 (33B) —— **内容就是在这一帧还回去的**
           每槽 (id, count) 对 → setSlot(id, count, slot, kind) → 字符串表格式化 = 牌面

发货       SEND NOTI 0x000E UPDATE_ITEM_LIST —— 同一次交换里紧接着发
           上游：先标记该位置已翻（FreeCardSlots[index] 由 0xFF 改 0x00，同一位置不能翻两次），
           再发 0x0047 应答，**然后**才 DeliverCardRewards 把东西写进背包并推 0x000E。
```

**所以：内容在结算时就定了、留在服务端；点击时连同应答一起还给客户端，并在同一次交换里入包。**
不是点击时才现算——现算的话重连或重放会给出不同的东西。

### 上游的一个可疑简化

四个免费位置各能翻一次（`TrySelectCardSlot` 按位置去重），但**只有 `cardIndex == 0` 真发奖**；
`BuildCardInfoAck` 也只给 index 0 填奖励明细，其余位置恒写 `FF FF 00 00`。也就是说在上游那里，
你点哪一张都行，但只有第 0 张有东西。

**客户端不强制这一点**——它按槽统一读 `(id,count)` 对，任何位置都能带。所以「奖励按你选的那张
决定」还是「永远只有一张有货」，**没有证据可断**，要么实机试，要么就自己定一条规则。

## 八、33 字节应答的真实形状：它本来就是为「亮出其余几张」设计的

用户（2026-08-29）描述的实际玩法：**四张选一张，选中的可能有货可能没货；老版本翻完之后会把其余
几张的内容也亮出来，有时其余那几张也有货；每轮只能翻一个。**

客户端支持这一套，上游不支持。逐条对上：

应答是 **8 条记录**，每条 4 字节起：

| 字段 | 客户端怎么用 |
|---|---|
| `a` u8 | `0x021EF990(记录序号, a)`；`a == 0xFF` 直接返回，否则拿它去查（同一个 `[0x3B3DFB8]` 对象的 `+0xB68` 虚调用，与客户端 1 字节 `0x0047` 写出去的那个字节同源） |
| `b` u8 | **内容归属的牌位序号**，`> 7` 就跳过这条的对 |
| `c` u8 | 其后 `(u32 id, u32 count)` 对的条数，`<= 0` 不读 |
| 对 ×c | `setSlot(id, count, b, 3)` |
| 尾 u8 | 又一个按记录序号存的标志 |

`b` 是牌位序号而不是布尔，依据是那个门函数的寻址：

```text
0x021EF720(b, 3):  addr = this + 0x1E8 + 100*b + 60
                   return ([addr+8] - [addr+4]) / 68      ; 一个 68 字节元素的 vector 的长度
```

即「牌位 `b` 的第 3 类内容列表里已经有几条」。客户端**在该列表非空时跳过这一对**——
所以牌位一旦亮出来就不会被覆盖。这是幂等保护，不是免费/付费的门。

**上游那句 `paidSelected ? 0x00 : 0xFF` 写进的正是这个 `b`**，于是它永远只会指向牌位 0
（付费选中时）或者哪也不指（0xFF）。这就是上游「只有第 0 张有货」的来历——**是它的简化，
不是协议的限制**。

### 由此可做而上游做不到的

* **一次应答亮出四张**：给四条记录各填自己的 `b` 与 `(id,count)`，空牌就 `c=0`。
* **奖励跟着玩家选的那张走**：`b` 填玩家点的那个序号即可。
* **其余牌可以有货**：正是老版本的行为。
* 牌位内容一经亮出不可改（客户端自己拦），所以服务端也该照此设计——**内容在结算时定死**，
  点击只是揭示与发货。

**仍属推断的一点**：`b` 是牌位序号这个读法来自寻址结构与 `> 7` 的上界，不是实测。一次实机
（应答里给牌位 2 填一对，看是不是第 3 张亮起来）即可确认。

## 九、奖励来源是两层：副本声明覆盖全局表

普查 1047 个 `.dgn`：

| 声明 | 有几个副本 | 含义 |
|---|---|---|
| `[result card]` | **4** | 副本自己指定牌面产出 |
| `[gold card use] 0` | 5 | 该副本关闭付费（黄金）牌 |
| `[boss item drop list]` 等 | 5 | 怪物掉落覆盖，与牌面无关 |
| 以上都没有 | 1043 | 全走全局表 |

副本 120（黄龙大会）的 `[result card]`：

```text
[reward item rate]
3329 60 1   3329 35 2   3329 5 3      ; (物品, 权重, 数量)
[/reward item rate]
0 0 0 100  1 70 0 30  2 80 0 20  3 90 0 10  4 100 0 0  5 0 100 0   ; 按评级的概率分布
```

**这就是「按副本的产出规则」长什么样**：指名物品、按权重给数量、再按通关评级分概率。

**但副本 144 没有这一段**——它对牌面什么都不声明，全落到全局表上。而全局表的物品侧是
`[drop item type prob] 0 9500 0 500`，即**类型 2 普通装备 95% / 类型 4 时装 5%**，
**没有材料这一支**。

所以：**对副本 144，档案说的是「免费牌给装备」。** 发材料客户端确实收，但那是我们编的，
不是这个副本的数据说的。材料要么来自副本自己的 `[result card]`（144 没有），要么另有出处
（未查明）。

## 十、本仓的掉落现状（2026-08-29 核实）

**两件不同的事，只做了一件。**

| | 状态 |
|---|---|
| **房间可破坏物的掉落** | **有**。`.map` 的 `[special passive object]` 给组号，`.dgn` 的 `[special passive object item]` 按组给物品。副本 144 声明 `0 -1 1 10088621 2000` 与 `1 -1 1 10149508 5000`——**10088621 正是用户捡到的那件**。「依旧会掉落东西」掉的是这个。 |
| **怪物击杀掉落** | **没有**。`MonsterDeathSlice` 里 `writer.Write((byte)0); // no drops`，恒零，注释写明是有意的：没有内容模型就不发明掉落。 |

### PVF 的掉落概率表，本仓一处都没用

全仓搜 `itemdropinfo` / `drop item type prob` / rarity / creation rate：**零命中**。
`etc/itemdropinfo_clearreward.etc` 与 `Etc/ItemDropInfo_Common.etc` 从未被读过。

更小的一处也没用：`[special passive object item]` 每条目带一个权重（144 是 2000 / 5000），
本仓 `PvfDungeonRoomDropSource` **读组号、丢权重、只取组里第一条**（上游同样整个丢掉）。
144 每组只声明一条，所以目前没丢东西——但那个 2000/5000 是什么意思
（组内选择权重？还是「这个物件有多大概率真的出东西」？）**没有结论**。
如果是后者，本仓现在是「必出」，偏高。
