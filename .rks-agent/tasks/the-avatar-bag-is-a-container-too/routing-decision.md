# Routing Decision

任务：`the-avatar-bag-is-a-container-too`
契约：`./TaskContract.md`（revision 1, state ready, SC-1..SC-8）

## SDD Readiness

**就绪。根因已定位到一行，正确形态有上游可对。**

- **根因是「少绑了一个容器」而不是「逻辑写错了」**：
  `SelectCharacterEntryInventoryDomainService.BindContainers:74` 的数组字面量只含 main 与 equipment，
  于是凡沾装扮栏的请求在 `MoveItemSpaceSlice.cs:280` 被拒为 `ListNotServed`，
  而那一句在读到物品之前执行。这是本仓代码读出的，不是推断。
- **有一次同形态的先例可照**：2026-08-26 装备栏没绑，玩家把护肩拖到肩甲槽被同样拒绝。
  修法与它的记载都在同一个方法的注释里。
- **正确形态有上游可对**：装扮栏区间 `0..209`、只接受时装、且上游服务装扮栏↔装备栏
  （其拦截只针对受限助战角色）。三条都是本轮逐行读出的。
- **有可执行判据**：全量套件在 `7147d2e9` 实测 2289/2/0；入场序列另有逐字节的字节锚。
- **一个可能的坑已排除**：`SnapshotAsync` 对非主背包容器会抛，但生产里没有调用方，
  绑定装扮栏踩不到它。

**一处已知的、写进契约的验收限制**：本件做完之后，把时装拖到装扮槽**仍会被拒**，
因为槽位映射是 issue #11。**这不是失败**，而是本件成果的表现形式：
拒绝理由从 `ListNotServed` 变成 `NotWearable`，且日志此时带得出 `{ItemId}`。
SC-4 把这一点写成了必须钉住的条款，免得后来的人把它当成没做完。

## Marginal Control Value

值得上 SDD，保护的是两条**都不是「代码写不出来」**的失败路径。

- **第一条：放行放得太宽。** 最省事的写法是把 `MoveItemSpaceCommandHandler` 改成
  「任意容器到任意容器」，那样所有判据都会绿——因为**没有任何现存用例会去拖个人货柜或宠物栏**。
  这与本仓吃过亏的那次一模一样：「全量判据全绿恰恰意味着没有用例走到那些新路径上」。
  SC-6 因此要求**反向**钉住「仍然不服务的列表对继续被拒」，而不是只钉正向。
- **第二条：准入规则悄悄偏离上游。** 装扮栏该收什么、区间多大，本仓今天没有任何答案，
  实现时很容易顺手写一个「看起来合理」的规则。契约把上游读数定为默认，
  并要求任何偏离都写明理由——这类「凭合理性造规则」在本仓已经出过事
  （把上游**服务器**的行为当成**客户端**的行为，见 `the-container-decides-the-entry-shape` 的 C-2）。
- **第三条是记账**：本仓同一族记载失误已 8 次，且**无一次由自查发现**。本件要新增
  一个容器绑定与若干条列表对，正向与反向都必须被独立扫过一遍。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Rationale: 三件事——绑定容器、服务列表对、定准入规则——共享同一个验收口径：
  「涉及装扮栏的移动不再被拒为 `ListNotServed`，其余移动行为逐值不变」。
  按本仓规矩，同一口径下的多段工作量属于一个成果。
  issue #11（槽位映射）有**互斥**的验收口径（它要改变「能不能穿上」这件事本身，
  且输入来自实机测量），已写进 Scope Out，不构成本轮的边界。
- Reroute conditions:
  - 若服务这些列表对必须把处理器改成「任意容器到任意容器」，那是宽得多的变化，回到路由重议；
  - 若装扮栏↔主背包要求改动主背包的 band 规则，那会波及所有物品的移动，回到路由重议；
  - 若绑定装扮栏之后别的路径开始行为不同，说明「绑定是局部的」这个结构性假设不成立。

## Controller Selection

- Controller: `sdd-lite`
- Profile source: `code-bugfix`
- Rationale:

**要挡的两条失败路径都是「边界画错」而不是「代码写错」**：放行放得太宽（反向没人看）、
准入规则凭合理性自造。挡住它们需要且只需要两样：一份把验收边界
（哪些列表对该服务、哪些必须继续被拒、准入规则以什么为准）钉死的持久 Spec，
加一次对**完整**结果的独立评审。`sdd-lite` 的
spec → implementation → review → verification 恰好是这两样。
本仓的历史也支持这个档位：历次遗漏——漏 13 条新增拒绝、把「零覆盖」的理由写成假话、
以及最近一件的四轮记账问题——**全部**是被普通的完整变更评审抓住的。

**为什么更重的 `sdd-standard` 不对**：Standard 的独有控制是 `plan.md`，
用来提前解决会造成返工的实施决策。本件的实施路径已由现成对照给定：
装备栏怎么绑、`PutOnAsync` / `TakeOffAsync` 怎么写，都在同一个文件里摆着，
照它加一路即可。唯一的真设计题（装扮栏准入规则）已在契约里定了默认答案（取上游读数），
写成 plan 只是把 spec 抄一遍。**文件多、条目多按选择规则明确不构成理由。**

**为什么更轻的一档不对**：更轻是不留持久 Spec、靠一次确定性检查收口。这里不行——
本件**最危险的错法恰恰能让全量判据保持全绿**（放行所有列表对，没有用例会发现）。
能证伪它的只有「反向钉住仍应拒绝的情形」，而那要先有写下来的验收条款才能对着做。

**为什么不是 `sdd-governed`**：硬性门槛一条都不沾——不涉及安全、凭据、隐私、
财务法务、不可逆外部变更、或无恢复手段的数据丢失。最坏后果是玩家能把东西拖到
不该去的格子里，可逆，改动全在本地未推送的任务分支上。
「独立挑战集」这一档控制在本仓已被证明对同一失败模式不是必需的。
