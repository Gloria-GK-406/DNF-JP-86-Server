# Routing Decision

- TaskContract: `.rks-agent/tasks/flipping-a-clear-reward-card/TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 目标是玩家通关后能翻牌并拿到东西，可观测且不含歧义。
  三处会改变任务语义的分歧已由用户当场定死：牌面归属（四张各有各的、翻一张全亮出）、
  范围（免费牌与黄金牌都做）、金币（金币与装备都发）。物品类型早先已定只出装备。
  剩下的都不再改变「要做成什么」。
- Requirement stability: 可枚举且可逐条核对。协议侧三个交换的字节形状已逆向到逐字节
  并与抓包互证；内容侧所依赖的档案表已经查明，各段读法与社区文档、上游源码三方互证。
  每一处档案读数都可以单独成为一条可检查的要求。
- Execution direction: 已知。分层与落点由刚建立的四层结构给定，操作顺序写在
  `Docs/新功能接入规范.md`；装备池、金币路径、随机源与抽取纯规则都已存在，
  本任务主要是新增一个内容源、一个规则服务、一个持牌面状态的业务服务与一个协议切片。
- Remaining uncertainty: 只剩不改变任务语义的局部选择，加两条已在契约 Assumptions 里
  具名的证据缺口（黄金牌请求形状未实证、应答里牌位归属字节的读法未实机确认）。
  两者都不改变要交付什么，只决定日后若被推翻，改动落在哪一处。

## Marginal Control Value

- User precision signal: 偏精确。用户此前明确拒绝「盲目推进度」、要求先看结构是否合理；
  在上一个任务里被示以代价后仍选择完整满足要求而非拆分；本次主动要求走 SDD，
  并在被问到三处分歧时逐条给出决定而不是让我自行发挥。
- Direct failure mode: **产出一个看起来完全正常的错数字，且没有任何东西会发现它。**
  上一个任务有 1690 条既有判据当行为 oracle 钉住「行为不许变」；**新功能没有这种 oracle**，
  正确与否只能靠每一处档案读数自己站得住。而这一族档案恰好已被证明会让错误隐形：
  上游在同一批文件里有三处编造，其中稀有度分母写死一百万（档案声明的基数是 1000003），
  使史诗与传说两档永远摇不到，代码表面毫无异样——上游自己都不知道。
  Direct 之下，最省事的做法正是照着上游那份现成实现写，也就正好会把这个陷阱抄进来。
- Useful control: 一份把每一处档案读数拆成独立可核对要求的 Spec，加上对读数出处的
  独立评审。前者让「哪一档稀有度掷不出来」成为一条会被单独检查的验收；
  后者由不共享我的结论的评审者去比对档案，正是能抓住上游那个分母陷阱的控制。
  计划阶段另有价值：多处新读法共享同一批档案段落，归属先定才不返工——
  与上一个任务选 standard 的理由同源。
- Time-for-quality rationale: 错数字的代价是长期且难发现的（玩家永远拿不到高档奖励，
  而没有任何报错），而识别它的成本只是把读数逐条列出来给人核对。同一套控制在上一个
  任务上跑通过一遍，团队与仓库都已熟悉，边际时间成本低。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: 一个验收边界——翻牌这件事要么能用要么不能用。免费牌与黄金牌看似
  可分，但它们共用同一个内容源、同一个规则服务、同一个持牌面状态的业务服务和同一个
  协议切片，付费只是同一用例的一个分支；拆开会让几乎每个文件都变成共享所有权。
- Why Direct is insufficient: Direct 给不出「每一处读数被单独列出来、由独立的人比着档案
  核一遍」这件事，而这正是唯一能发现无声错数字的手段——没有 oracle 时，评审就是 oracle。
- Why Multi is unnecessary: 只有一个连贯的验收与回滚边界。文件数与工作量不构成 Multi 边界，
  且证据不完整时应优先一个连贯的 Single Spec 而不是发明子 Spec。
- Reroute conditions: 若实机确认推翻「应答里那个字节是牌位序号」的读法，
  「四张全亮出」这一整个玩法失去依据，须回到意图对齐重定范围；
  若黄金牌的请求形状经实证与现有读法不符且改动超出解包这一处，同样回到对齐；
  若黄金牌被发现有自己独立的验收与回滚边界（例如需要单独的付费结算体系），
  改走 Multi。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-feature`
- Why this is sufficient: 有一簇互相牵制的实现决定，必须在写代码之前定在纸上——
  规则服务的接口形状（一次产出四张牌还是一张一张）、每局牌面状态的归属
  （挂在既有的本局状态上还是自成一个注册表）、以及免费牌与黄金牌共不共用一个规则服务。
  三者互为约束，且每一个的消费方都是它上面那一层：状态的家选错，业务服务、协议切片
  与它们的判据要一起重做。显式的 Plan 把这三个决定提前到纸面上，是 Standard 相对 Lite
  真正多出来的那件东西。配套的完整变更评审与新鲜验证则守住主要风险
  ——没有 oracle 时，比着档案核读数的独立评审就是 oracle。
- Why lighter is insufficient: Lite 的完整结果评审能发现上述三个决定选错，但那是在末尾
  发现，正是「错误在最终评审能便宜纠正之前就已扩散」的形状。Lite 也不提供跨会话的
  持久任务单元，而本任务的层数与判据量使它大概率跨会话。
- Why heavier is unnecessary: Governed 多出来的是独立挑战、独立产物批准与审计强度证据。
  本任务不触及人身或系统安全、凭据与访问控制、隐私或受保护数据、财务法务合规后果、
  不可逆的外部变更，也没有可信的持久数据丢失路径——它是单机私服里一个内部玩法功能，
  可回滚性好。普通评审加新鲜验证已足以守住它的失败路径，独立挑战那一层挣不回时间。
