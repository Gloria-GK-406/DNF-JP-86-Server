## 二、稀有度第六档的叫法，改完（**改了三处，控制器点名的是两处**）

先自己重核了控制器给的读法，结论一致：

- `RarityLadder.Basis => Values[^1]`、`BandCount => Values.Count - 1`、
  `HighestRoll => Basis - 1`（`DropRateContent.cs`）——**末位是基数不是门槛，七个数六档**。
- `DropRarity`：`Epic = 4`、**`Chronicle = 5`**、`Legendary = 6`（`DropRules.cs`）。
- 那一组七个数我是从判据的权重反推出来的，不是抄的：
  `ClearRewardRarityLadderTests` 断言 `WeightOf` 依次为
  500000 / 299900 / 200000 / 100 / 1 / 1，累加即
  `500000 799900 999900 1000000 1000001 1000002` + 基数 `1000003`；
  同判据另断言 `BandOf(1000001) == Epic`、`BandOf(1000002) == Chronicle`。
- 百分数按 `HighestRoll = 1000002` 复算：50.00 / 29.99 / 20.00 / 0.01 / 0.0001 / 0.0001，
  **与原文逐个相符——错的确实只有名字。**

## 四、第七处：**有**

第 6 处（`新功能接入规范.md:211-212`）是同一条陈述的第三份拷贝：

  「It is a separate reader from `PvfDropRateTableSource` **rather than another path handed to
  it**」，它自己声明并读了全部 16 段，含稀有度阶梯（`ReadLadder`）与
  `[item drop ref table]`（`ReadGradeBands`）——两个函数都是它自己的，不是借来的。

  不报任何错（`The_grade_bands_share_the_monster_tables_below_column_and_differ_above_at_80_to_89`）。
- 真正被复用的是 `RarityLadder` / `ItemGradeBand` 两个**记录类型**，以及抽取那一层的
  `DropRules`——不是「各段的读法」。

**没核末尾那句**。这正是 B1 立下的规矩（「一句话里一半真一半假」）反过来咬人的样子：
B1 教的是「不要把对的那半删掉」，这里犯的是它的镜像——「不要因为有一半对就整格放过」。

建议改法（**未执行**）：保留前两句，把末句改成
