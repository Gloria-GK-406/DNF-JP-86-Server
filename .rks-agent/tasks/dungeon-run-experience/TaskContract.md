# TaskContract: 副本跑动的经验补完

## Context

### Source Request

用户 2026-08-28：「好，后续的按你的想法实现。完全实现后叫我来测试吧。依旧是sdd流程」

「后续的」指上一轮交付结束时列出的、按该顺序挂着的三件：kind 补齐九个成员 → 频道-副本区间的真实加成规则 → 通关结算闭合。用户此前对第二件给过内容：「赛丽亚祝福那个就是频道奖励。不过我们还没完成。不同频道刷不同范围的图是有经验加成奖励的。」

### Current Situation

击杀经验已经落地（`2959938d`），配置化已经落地（`ff413e0e`），基线 `main = ff413e0e` 干净，1501 passed / 2 skipped / 0 failed。当前状态与本任务相关的三处缺口：

1. **通告只会画一行。** `NOTI 0x0025` 有十四个加成槽，2026-08-28 的实测（`Docs/ExperienceNoticeSlots.md`）已经把每个槽的客户端叫法、参不参与基础值扣减逐个测了出来——九个可用、两个不可用、三个惰性。代码里 `ExperienceBonusKind` 只有 `Unlisted` 与 `SeriaBlessing` 两个成员，其余七个可用槽没有建模，付了也只能进 `Unlisted`，被客户端算进基础值。

2. **频道奖励是一个拟合出来的常数。** `ExperienceChannelPolicy.Measured = 0.05` 是从一次抓包的四个样本反推的，代码里写着「档案没有声明，属服务端政策」。这句话是错的：`channel_info.etc` 的 `[server]` 段每一行都声明了 `频道号 / 显示名 / 频道类型 / 副本组名 / 经验加成百分比`，`[dungeon]` 段声明了每个组包含哪些副本。抓包那一局在副本 144 上拿到 5%，而 144 正在 `[granfloris]` 组里、该组所属频道那一行写的正是 `5`。所以这是档案内容，不是我们的政策，而且它有归属条件——跑组外的副本不该拿到。

3. **通关不发经验。** `CLEAR_DUNGEON_REWARD` 现在是 274 个零字节，`SetPlayResultHandler` 发的经验帧只回报角色当前的存量。清完一个副本一分不涨，结算屏上每个数字都是零。

## Goal

一次副本跑动的经验系统闭合：每一笔支付都走到客户端能为它单列一行的那个槽上、明细与总数自洽；频道奖励按档案声明的「频道 → 副本组」归属发放；通关结算通过与击杀、交任务同一条发放件付清，并在结算屏上如实报出它付了什么。

## Scope

### In

- 按 `Docs/ExperienceNoticeSlots.md` 第四节的实测结论建模可申报的加成种类，并让经验帧把每一种送到它自己的槽位。
- 从 `channel_info.etc` 读频道与副本组的归属和百分比，按当前连接所在的频道与本局副本决定频道奖励。
- 通关结算的经验：基数、与之相关的加成、发放、跨等级线的后果，以及结算帧里对应字段的如实填写。
- 上述三件各自的失败与边界行为（无归属、无声明、读不到、算不出）。
- 让用户能在实机上把这三件都看见所需的部署配置。

### Out

- 组队。全程按单人算，与击杀路径现状一致。
- 疲劳值、秘药、公会、冒险团、网吧、成长胶囊等还没有来源的加成——**建模其种类，但不发明其规则**，没有来源就不支付。
- 掉落、金币、结算卡片、评分等级的判定。
- PVF 内声明的倍率的配置化（用户明确划出去）。
- 上游当前版本与我们不一致的等级差惩罚表——只记录，不在本任务内改动。

## Constraints

- 权威是客户端反汇编与档案本身；上游实现只有参考价值，其自测常量基本不算证据。
- 已验证的线级字节不得改变。新增的只能是原本恒为零的槽位现在带上真实值。
- 发放路径唯一：通关结算不得出现第二份「加经验、跨等级线、落库」的实现。
- 档案声明的数从档案读，不进服务端配置；服务端自己定的数继续可配置。
- 不可用的两个槽（`+0x2F` 画而不减、`+0x33` 减而不画）任何情况下都不得被写入。

## Assumptions

- 一个连接所在的频道由监听端口决定，`ChannelEntryIdentity` 已经在做这件事，本任务沿用而不另立一套。
- 抓包那一局所在的频道，其副本组包含 144。日志只记了 `channel=3`（金额）没记频道号，所以这条是从「144 在 `[granfloris]` 组、该组那一行写 5、5% × 62 = 3」三者相合推出的，不是直接读到的。
- 通关结算的基数取自 `n_quest/questParameter.etc` 的 `[exp reward table]`，与交任务共用一张表——这是上游的做法，本任务按同一张表实现，若实机数字对不上则该子成果按证据不足处理。
