# TaskContract: 每一笔加成走到客户端为它画的那一行

## Context

### Source Request

根契约 `.rks-agent/tasks/dungeon-run-experience/TaskContract.md` 的第一个稳定成果，由根控制器切出。

### Current Situation

`NOTI 0x0025` 的十四个加成槽在 2026-08-28 被逐个实测过，结论写在 `Docs/ExperienceNoticeSlots.md`：九个槽既被客户端单列成一行、又被它从增量里扣掉（可用）；`+0x2F` 画而不减、`+0x33` 减而不画（不可用，写进去玩家看到的明细就不平）；`+0x22`、`+0x37`、`+0x47` 既不画也不减（惰性）。

代码里 `ExperienceBonusKind` 只有 `Unlisted` 与 `SeriaBlessing` 两个成员。帧编码把频道那一笔单独作为一个 `uint` 参数传进去，其余十三个槽写死为零。任何别的加成——已经在跑的黑钻，以及后面要接的每一种——都只能落进 `Unlisted`，被客户端算进「基础」。总数仍然正确，但明细把它归给了这次击杀本身。

那份实测文档第六节把建模约束写死了，本成果就是把它兑现。

## Goal

经验通告能为它支付的每一笔加成单列一行：可申报的加成各自落到实测确定的槽位上，无处可报的明确走基础值，两个会让明细算不平的槽任何情况下都不被写入。

## Scope

### In

- 按实测结论建模可申报的加成种类，每一种带上它的偏移与客户端叫法。
- 经验帧按种类填槽，一次支付多笔时各归各位。
- 同一种类被多笔加成同时命中时的合并。
- 无处可报的加成的既有行为（进基础值）保持不变并写下来。
- 两个不可用槽的阻挡。

### Out

- 新增任何加成来源。本成果只改「已支付的加成怎么申报」，不改「支付什么」。
- 频道奖励的归属规则（下一个成果）。
- 通关结算（第三个成果）。
- 三个惰性槽的语义探查——这条通告探不了它们，文档已记明。

## Constraints

- 帧长仍是 83 字节，除加成槽外每个字段的偏移与取值不变。
- 每个种类的偏移与叫法必须能追到 `Docs/ExperienceNoticeSlots.md`，不得取自上游命名。
- 探针模式（`Experience:LabelProbe`）的行为不变。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 实测表中标「可用」的九个偏移各有一个种类与之对应，且只有这九个 | 测试逐个断言种类到偏移的映射与实测表一致 |
| SC-2 | 支付了某种类的加成时，帧在该偏移上带该金额；未支付时该偏移为零 | 编解码测试对每个种类各一例 |
| SC-3 | 同一种类被多笔加成命中时，该槽带的是它们的和 | 编解码测试 |
| SC-4 | 无处可报的加成不写入任何槽，其金额仍计入总数 | 测试断言所有槽为零而总数含该笔 |
| SC-5 | `+0x2F` 与 `+0x33` 在非探针情况下恒为零，且没有任何种类能指向它们 | 测试断言这两个偏移为零；种类映射测试证明二者不在映射内 |
| SC-6 | 除加成槽外的线级字节与本成果之前逐字节相同 | 既有编解码测试仍然通过，未经修改 |
| SC-7 | 全套测试通过，构建零警告零错误 | `dotnet build` 与 `dotnet test` 输出 |
