# Specification: 每一笔加成走到客户端为它画的那一行

## Why and Outcome

客户端算「基础」的办法是：拿这一帧报的总数减去自己记着的存量得到增量，再从增量里逐个扣掉帧里申报的加成行。所以一笔付了却没申报的加成，不是「少画一行」——它被算进了基础值，玩家看到的是这次击杀本身值那么多。

现在能申报的只有一种。别的加成付出去就消失在基础值里，而 2026-08-28 的实测已经把九个槽的客户端叫法和扣减行为逐个测了出来。

结果要变成这样：一次击杀之后弹出的通告里，服务端付的每一笔可申报的加成各占一行、各带自己的金额，行的和加上基础值等于宣布的总数；无处可报的那些老老实实进基础值；两个会让这个等式不成立的槽一个字节都不动。

## Task Perspective

- Core outcome: 通告能把服务端付的每一笔加成分别说清楚，而且明细自洽。
- Necessary support: 可申报的加成种类必须与实测出来的槽位一一对应；两个不自洽的槽必须在结构上无法被指向，而不是靠人记得别填。
- Peripheral assurance: 每个种类在代码里带着它的偏移与客户端叫法的出处，好让下一个人不必重跑一局游戏来确认。

## Scope and Non-Goals

### In Scope

- 可申报的加成种类的集合，以及每一种对应的通告行。
- 一次支付含多笔加成时，各笔按种类分别申报。
- 同一种类被多笔加成同时命中时的合并。
- 无处可报的加成的申报方式。
- 两个不自洽的槽的阻挡。

### Non-Goals

- 新增任何加成来源。本 Spec 只改「已付的加成怎么申报」，不改「付什么、付多少」。
- 频道奖励在什么条件下支付。
- 通关结算。
- 三个惰性槽的语义。

## Constraints

- 通告帧仍是 83 字节；除加成槽外每个字段的偏移与取值不变。
- 每个种类的偏移与客户端叫法必须能追到 `Docs/ExperienceNoticeSlots.md` 的实测表，不得取自上游命名。
- 测量开关（`Experience:LabelProbe`）打开时的行为不变。

## Definitions

| Term | Meaning |
|---|---|
| 可申报 | 客户端既为它单列一行、又在算基础值时把它扣掉。实测表里九个偏移满足这一条 |
| 不自洽的槽 | 画与减只占其一的槽：`+0x2F` 画而不减，`+0x33` 减而不画。任何一个被写入，玩家看到的明细就不再平 |
| 惰性槽 | 既不画也不减的槽：`+0x22`、`+0x37`、`+0x47` |
| 无处可报 | 一笔已支付、但服务端还没有认定它属于哪一行的加成 |

## External Behavior and Data Rules

- 客户端画出的行名与偏移，以 `Docs/ExperienceNoticeSlots.md` 第四节的实测表为准：`+0x05` 队伍奖励、`+0x15` 疲劳值Buff、`+0x1A` 赛丽亚的祝福奖励、`+0x1E` 成长之契约奖励、`+0x26` 疲劳值燃烧奖励、`+0x2A` 网吧奖励、`+0x43` 极速成长Buff奖励、`+0x4B` 赛丽亚的欢迎、`+0x4F` 公会奖励。
- 无处可报的加成仍计入帧报出的总数，因此仍被客户端算进基础值。总数正确，归属含糊。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 可申报的加成种类恰好覆盖实测表标「可用」的九个偏移，一一对应，不多不少 |
| RQ-002 | 每个种类记着它的偏移与客户端叫法，以及这两项的实测出处 |
| RQ-003 | 一笔加成被认定为某个种类时，通告在该种类的偏移上带这笔的金额 |
| RQ-004 | 没有任何一笔被认定为某个种类时，该种类的偏移为零 |
| RQ-005 | 同一种类被多笔加成命中时，该偏移带的是这些笔的和 |
| RQ-006 | 一笔无处可报的加成不写入任何加成槽，其金额仍计入帧报出的总数 |
| RQ-007 | `+0x2F` 与 `+0x33` 在非测量模式下恒为零，且没有任何种类可以指向它们 |
| RQ-008 | 除加成槽外，通告帧的每个字段与本成果之前逐字节相同，帧长仍为 83 |
| RQ-009 | 测量模式打开时，十四个槽仍各带其约定的探针值，行为不变 |

## Assumptions

- 实测表本身是对的。它由两轮不同填充值互相印证（第二轮的位掩码回代第一轮，基础值与截图分毫不差），本 Spec 不重测。
