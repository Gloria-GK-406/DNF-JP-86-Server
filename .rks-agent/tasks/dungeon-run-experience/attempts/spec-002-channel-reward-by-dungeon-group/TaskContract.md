# TaskContract: 频道奖励按档案声明的副本归属发放

## Context

### Source Request

根契约 `.rks-agent/tasks/dungeon-run-experience/TaskContract.md` 的第二个稳定成果。用户对它给过内容：「赛丽亚祝福那个就是频道奖励。不过我们还没完成。不同频道刷不同范围的图是有经验加成奖励的。」

### Current Situation

`ExperienceChannelPolicy.Measured = 0.05` 是从 2026-08-27 抓包的四个样本反推出来的常数：62 付 65、72 付 75、126 付 132、146 付 153，四次都恰是 `floor(基数 × 0.05)`。代码里现在写着「档案没有声明它，属服务端政策」，并把它做成了 `experience.json` 的一个可配置项。

**那句话是错的。** `channel_info.etc` 的 `[server]` 段逐行声明了 `频道号 / 显示名 / 频道类型 / 副本组名 / 经验加成百分比`，`[dungeon]` 段声明每个组含哪些副本。抓包那一局在副本 144 上，144 在 `[granfloris]` 组里，绑到该组的那一行写的正是 `5`。这个文件本仓已经在发（`Resources/Channel/channel_info.etc`，启动即读入内存整份发给客户端），只是从没被解析过。

于是现在的实现有两个各自独立的毛病：**比率来源错了**（服务端政策 vs 档案内容），以及**归属条件根本不存在**——不论跑哪个副本、连在哪个频道上，一律付 5%。我们唯一配置的频道是 11（`[sky_catle]`，组内为 156–160、2010、242），而实机测试跑的 144 并不在其中，所以现在这 5% 每一次都付错了。

### Anti-Goal

上游当前版本已经把频道加成整个删掉了（`ExpNotificationBuilder` 把 `+0x4B` 叫 `RemovedChannelExpOffset`，注释写「当前版本没有频道经验来源」）。**不要跟随。** 档案里这条规则明明白白写着，实机也测到过它发钱；上游删掉它是上游的取舍，不是证据。

## Goal

频道奖励由档案决定而不是由我们决定：本局副本属于所连频道声明的那个副本组时，按该频道那一行声明的百分比支付；不属于则不付。比率不再是服务端的一个可调项。

## Scope

### In

- 解析 `channel_info.etc` 的 `[dungeon]` 组与 `[server]` 行，得到「频道 → 副本组 → 百分比」。
- 击杀时按当前连接所在的频道与本局副本决定是否支付、支付多少。
- 频道未声明、副本不在组内、行残缺、文件读不到等各情形的行为。
- 把频道比率从服务端配置里撤出。
- 部署配置：让这条规则在实机上正反两面都看得见。

### Out

- 通关结算的频道加成。结算此刻一分不发，没有可加的基数；那是第三个成果的事。
- `[server]` 行里除频道号、类型、组名、经验百分比之外的字段（等级区间、人数上限等）。它们与经验无关。
- `[dungeon]` 组与副本内容的其它用途（例如按频道限制可进入的副本）。
- 频道类型（`channelType`）对经验的影响——档案里有这一列，但没有任何证据说明它参与经验计算。

## Constraints

- 权威是档案本身与实机；上游当前已删除此功能，其取舍不构成证据。
- 已验证的线级字节不得改变。
- 解析失败不得引入新的启动失败，也不得让击杀发不出经验：解析不出来就是没有频道奖励，其余加成照付。既有行为是脚本文件读不到时服务端拒绝启动，本成果不动它。
- 抓包的四个样本必须仍然能被复现出来。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 本局副本属于所连频道声明的副本组时，按该行声明的百分比支付频道奖励 | 解析与归属的自动化测试；四个抓包样本在「组内」条件下仍复现 65/75/132/153 |
| SC-2 | 副本不在该频道的组内时不支付 | 自动化测试：同一副本在组内频道与组外频道上的两种结果 |
| SC-3 | 频道在 `[server]` 段中没有行、或该行残缺、或百分比越界时不支付 | 各情形的解析测试 |
| SC-4 | 频道脚本解析不出任何频道行时服务端照常启动，击杀照常发经验，只是没有频道奖励（文件读不到时服务端本来就拒绝启动，那是既有行为） | 不可解析文本的测试 + 一次实际启动 |
| SC-5 | 频道比率不再是服务端配置项；`experience.json` 缺席与否都不改变它 | 配置测试；`experience.json` 中该键已移除 |
| SC-6 | 支付出去的频道奖励仍落在 `+0x1A`（赛丽亚的祝福奖励）那一行上 | 编解码/端到端测试 |
| SC-7 | 部署能让这条规则正反两面在实机上被看见 | 配置里同时存在「本局副本在组内」与「不在组内」的两个频道，并写明各自跑什么图会看到什么 |
| SC-8 | 全套测试通过，构建零警告零错误 | `dotnet build` 与 `dotnet test` 输出 |

## Assumptions

- 抓包那一局所连频道的副本组包含 144。日志只记了金额 `channel=3`、没记频道号，所以这条由「144 在 `[granfloris]` 组、绑该组的行写 5、5% × 62 = 3」三者相合推出，不是直接读到的。若后续实机与之矛盾，以实机为准。
- 一个连接所在的频道由监听端口决定，`ChannelEntryPolicy` 已经在做这件事，本成果沿用。
