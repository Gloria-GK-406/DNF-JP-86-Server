# 路由决策：monster-drop-rates

## SDD 为什么值这个时间

**就绪。** 目标、范围、判据都稳定：`Docs/DropRates.md` 已经把整套规则连同证据等级写完，
用户也已定下分期（一期怪物、二期翻牌）。没有需要先澄清才能动手的语义。

**用户的精度信号。** 用户要求「先在 docs 写完整的爆率系统文档，然后再起 sdd」，并要
「任务契约和 spec，plan」——三样都要。这是明确的偏精度而非偏速度。

**Direct 会怎么失败。** 具体的、有先例的：**照抄上游的一行常量**。
上游 `RollRarity` 把分母写死成 1000000，使史诗与传说永远摇不到；`_rarityThresholds[0, r]`
恒取第 0 组，使装备用错门槛。两处**各只有一行，代码看起来完全正常**，而后果是概率错几个数量级
且不会有任何报错。直接实现时最可能的路径就是「参考上游写一遍」，然后把这两行一起带进来。

**哪个控制能挡住它。** 两个：
1. **Spec 把「分母从表读」「门槛按类型槽取」写成可观察要求**，使它成为验收条件而不是实现细节。
2. **对真档案的判据**：断言副本 144 相关等级段的具体数值、断言史诗与传说不是 0——
   自洽的错读通不过具体数值。

**为什么值。** 这套东西一旦读错，表现是「概率不对」，而概率不对**没有任何自动信号**——
不崩、不报警、测试全绿，只有玩家几个月后觉得不对劲。这正是前置约束比事后发现便宜得多的形状。
上一个任务的评审已经用变异证明过同一件事：注册键改成 `0x0099` 全套仍绿。

## 结构边界

**Single Spec。** 一个验收边界：「怪物死了会按档案掉东西」。

内容源、纯规则、领域服务、线级四者**不是独立可验收的成果**——费率表读出来了但没人用，
对玩家、对判据都不构成一个可交付的结果；它们的价值只在合起来那一刻兑现。
把它们拆成四个子成果会得到三个「读了但没用」的中间态，各自还要一次评审与一次验收提交。

依赖是线性的（源 → 规则 → 服务 → 线级），没有需要分头推进再合流的地方。
**次序问题用 Plan 的有序任务解决，不用 Spec 的边界解决。**

上一个任务是 Multi Spec，因为那四件分属三个互不相干的子系统、失败互不牵连。这一件相反。

**重新路由的条件**：若实现中发现怪物档次判定需要另建一套怪物内容模型（而不是从已有的
actor 声明里读出来），那是一个独立的验收边界，应停下改走 Multi Spec。

## Controller Selection

**`sdd-standard` / `code-feature`。**

需要 Plan 的理由是**次序本身有风险**：内容源要先对着真档案立住，规则才有东西可验；
规则立住之前写领域服务，就只能拿桩去验，而桩正是「自洽的错」的温床。
Plan 把这个次序写成有序任务与检查点，使它成为可核对的东西而不是执行时的记忆。

用户也直接要了 plan。

**为什么不是更轻的 `sdd-lite`**：它没有 Plan 阶段，上面那个次序约束就只能活在执行者脑子里。
本任务的实现要跨若干个上下文窗口（用户明确会压缩上下文后再开始），Plan 是那时唯一还在的次序记录。

**为什么不是更重的**：不需要对抗式的 Spec/Plan 评审，也不需要多阶段拓扑——
规则的正确性由对真档案的判据保证，那比再加一轮评审直接。
