# TaskContract: 怪物死了会按档案掉东西

## Context

### Source Request

用户 2026-08-30，在 `finishing-and-leaving-a-run` 封存之后：

> 第一期先完成怪物的爆率服务吧。然后二期补翻牌子。先在docs写完整的爆率系统文档，然后再起sdd。

文档已写：`Docs/DropRates.md`。本任务是它第十三节「分期」的第一期。

### Current Situation

**本仓的怪物击杀不掉任何东西。** `MonsterDeathSlice` 里那一行是有意的：

```csharp
writer.Write((byte)0); // no drops
```

注释写明理由——没有内容模型就不发明掉落。现在内容模型查清了。

`Docs/DropRates.md` 记录了整套规则的取证：五张同构的费率表、稀有度的累积门槛算法、
两个物品池（`ItemDictionary.etc` 与 `stackable.lst`）、入池资格由物品自己的 `[creation rate]`
决定，以及六条互不排斥的产出路径。

**同一台机器也是翻牌、可破坏物、深渊、独立掉落的机器**，所以本期建的东西二期直接换一张表就能用。

### 这件事最大的风险不是写不出来，是抄错

上游 `ServerS4A21` 在这一族文件里有四处编造，其中两处**各只有一行、看起来完全正常**：

* `RollRarity` 把分母写死成 1000000，而基数说的是 1000002——**史诗与传说永远摇不到**
* `_rarityThresholds[0, r]` 恒取第 0 组——装备用了错误的门槛，紫由 10% 变 2.51%、粉由 0.05% 变 1%

四处的清单在 `Docs/DropRates.md` 第十二节。**它们是本任务最可能被复制进来的缺陷。**

## Goal

在副本里杀死一只怪，它按档案声明的规则掉出金币与物品，掉出来的东西躺在地上，能被捡起来。
掉什么、掉几件、什么品质，全部由档案决定，一个数都不是编的。

## Scope

### In

- 费率表的读取（怪物表；结构与其余四张相同）。
- 稀有度判定：累积门槛 + 基数，含「门槛相同即该档为 0」。
- 物品池：装备取自 `ItemDictionary.etc`，堆叠物取自 `stackable.lst` + 各 `.stk`；
  入池资格与 `(品级, 稀有度)` 分桶、桶内加权。
- 抽取规则：等级→品级带→桶内加权取一件。纯函数。
- 通用阶梯的门：五个率 × 档次/难度/组队倍率，各自独立掷。
- 怪物掉落领域服务：编排上述各件，产出本次击杀的掉落。
- 掉落落地：`NOTI 0x0026` 的掉落记录、本局的场景槽编号、以及既有拾取路径对它的支持。
- 可复现的随机源：同一局同一间房重问给同样的结果。
- 爆率增强的接缝：只留改率那一条，一期是永不增强的空实现。

### Out

- **翻牌**（二期）。本期只保证同一台机器换一张费率表即可用，不实现翻牌那一侧。
- **独立掉落**、**世界掉落**、**次元**、**深渊**、**可破坏物打破时的另掷**——各自是后面的一件。
- **怪物自有掉落池**（`.mon` 的 `[item]` 段）：它是另一条产出路径，本期不做。
- **补偿/保底的实现**：只留接缝，不实现。它是独立的一大块，跨局、要持久化。
- **金币进角色账户**：本仓没有金币写入路径。金币可以落地，但拾取金币不在本期。
- 怪物档次（普通/精英/命名/boss）的判定来源——本仓尚未对怪物分档，见 Assumptions。

## Constraints

- **权威顺序**：客户端反汇编与实机 > 档案 > 社区文档 > 上游源码。
  凡是只有上游一个来源的读法，代码里必须写明它是读法而不是事实。
- **分母、门槛、倍率、池子资格一律从档案读，不得写死。** `Docs/DropRates.md` 第十二节那四处
  是明确的反面清单。
- 已验证的线级字节不得改变。新增的只能是原本恒为零的掉落条数现在带上真实内容。
- 同一局同一间房被重新描述时，掉落必须与第一次一致——本仓已有的两处（actor 运行号、
  地面掉落编号）都是这么做的，掉落不得例外。
- 判据必须能分辨「读对了」与「读了个自洽的错」：对着真档案断言具体数值，不是断言自洽。

## Assumptions

三条假设在执行期间被证据推翻，原文与结论并列保留——**下面这三条是本任务里唯一被写下来又被
自己的取证推掉的判断，它们比结论本身更值得记住**。

- ~~**怪物档次尚未在本仓建模。**~~ **不成立：已经建模了。**
  `PvfDungeonRoomActorSource.RankOf` 把地图的引号词读成
  `[normal]→0 / [champion]→1 / [super champion]→2 / [boss]→3`，存进 `ActorType`；
  与 `[monster type drop bonusrate]` 的 4 档一一对应。档次倍率取得到真值，
  **不需要「按普通处理」的缺省，也就没有那个偏低的有界偏差。**
- ~~`NOTI 0x0026` 的 48 字节布局尚未用带掉落的真实帧验过。~~ **已经验过了。**
  上游两个抓包共 6 帧带掉落，按 `3 + 48n + 4` 全部整除，编码器现在逐字节复现其中两帧。
  金币是物品号 0、金额写在数量字段，也由同一批帧坐实。
- ~~装备池取自 `ItemDictionary.etc`。~~（写在 Context 与 `Docs/DropRates.md` 第五节里的前提）
  **那是图鉴 UI 的索引，不是掉落池**，且它的列义与上游的读法对不上五处。
  真正的闸是 `.equ` 自己的 `[creation rate]`，与堆叠物同一条规则。这是上游的第五处编造。

仍然成立的：

- 以下读法**只有上游一个来源**，已在代码里标注（`Docs/DropRates.md` 第十一节）：
  五个率是独立掷而非互斥分布（现有抓包旁证：一帧同时给金币与物品，互斥分布下不可能）；
  类型槽 1/3 → 堆叠物、2 → 装备、4 → 时装的映射；
  `[basis of rarity dicision]` 四组对应四个类型槽。
- **五个率的分母档案里根本没有**，既不是读法也不是事实，是服务端政策：
  做成配置项 `DropRates:RateBasis`，默认 10000，规则吃传入的基数、不认识任何字面量。
  稀有度那个基数是另一回事，它在表里，必须读——写死正是上游的错。
