# Specification: 人物持久化收敛到统一存储协议

## Why and Outcome

物品的持久化在上一轮已经收敛：业务代码不知道道具落在数据库还是内存，一次用例内的多处改动共同成败，持久实现里不夹带规则。人物与任务两块一件也没有——写路径以业务动词表达、三处规则住在持久实现里、每个写入方法自己开连接自己提交。

后果是一条今天走不通的路：一次用例里既动道具又动人物状态时，两者无法共同成败。而这不是「还没接上」，是现有协调器已经堵死的——它按载体身份去重参与者，并且只允许一个参与者的提交阶段仍可能失败。再加一个独立的人物持久参与者，两种接法都会被拒绝。

本次要变成真的事：同一个数据库上人物与物品的改动在一次用例中全有或全无；人物的持久化以「某个位置现在是这个值」表达而不是以业务动作表达；三处规则离开持久实现；建表不再是任何读写组件的构造副作用。对外可观察行为一字不变。

## Task Perspective

- Core outcome: 一次用例内针对同一数据库的人物改动与物品改动共同成败，且业务代码既不书写事务也不因载体分支。这是消费者——写用例的人——真正拿到的能力。
- Necessary support: 人物持久化以数据动词而非业务动词表达；三处业务规则离开持久实现；事务边界之外改动持久人物状态以失败暴露；建表归属明确到每张表只有一处定义，使存储实现不必依赖构造顺序才能拿到表。
- Peripheral assurance: 消失清单的零命中核对、全量测试保持绿、帧字节逐字比对、实机走查。它们证明结果，不构成结果。

## Scope and Non-Goals

### In Scope

- 人物的持久化改动与物品的持久化改动在一次用例内的共同成败。
- 人物持久化的表达方式：以位置与值表达，不以业务动作表达。
- 三处业务规则的归属：过期专家契约的技能上限回收、地下城持久效果的恢复与经验发放、金币上限等级的解析。
- 事务边界之外改动持久人物状态的失败暴露。
- 建表归属：每张表在代码库中只有一处定义，且有效列集不取决于组件构造顺序。
- 协议层不再直接持有人物持久化契约。

### Non-Goals

- 任务不成为独立聚合。任务继续作为人物状态的一部分，本次只随人物持久化改造其唯一写入点。
- 账号侧的读写路径不改。其表定义参与归属集中化，读写方式维持现状。
- 已建表但生产代码从未写入的那些人物表不获得写入能力，只参与建表归属集中化。
- 世界、频道、在线用户、会话等其余领域的持久化不改。
- 人物读路径的分层不重做。
- 跨数据库的共同成败不在本次范围内。
- 对外可观察行为不做任何改变。

## Constraints

- 对外可观察行为一字不变：帧字节与时序均不变。
- 既有测试语义不得修改，只允许因类型或依赖变化做机械调整。
- 保证必须明示：一次用例中提交阶段仍可能失败的参与者最多一个；无法共同落定的组合以失败暴露，不降级为非原子。
- 存储实现不得自建任何表。
- 开发阶段的策略是重建而非迁移：不得为既有数据编写回填、修复或迁移路径。
- 规则迁出前，被迁出行为须已有覆盖；覆盖不足时先补覆盖再迁。
- 不得改动 `Tool/` 与 `.worktrees/legacy-reference/`；客户端可执行文件与 DLL 不得手工编辑。
- 协议文档目录不得出现凭据、令牌、聊天隐私或个人可识别信息。

## Definitions

| Term | Meaning |
|---|---|
| 载体 | 状态实际存放的地方。持久载体的内容跨进程存活，易失载体的内容随进程结束而消失 |
| 会话 | 一次用例针对一个载体的读与写。写在会话内暂存，对本会话自己的读立即可见，对其他人只在用例落定时才可见 |
| 参与者 | 一次用例中共同决定成败的一方。以「准备 / 提交 / 回滚」参与，可失败的动作全部发生在准备阶段 |
| 数据动词 | 只说明某个位置现在是什么值的操作，例如写入与清空 |
| 业务动词 | 携带业务含义的操作，例如「回收过期契约的技能等级」「复活装备中的宠物」 |
| 位置 | 一处状态在其载体中的地址。由归属者、段与键共同确定，同一位置在两次表达中必须相等 |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 一次用例内针对同一数据库的人物改动与物品改动是全有或全无：用例正常结束时全部可见，用例在改动之后失败时一处也不可见 |
| RQ-002 | 一次用例中提交阶段仍可能失败的参与者最多一个；同一数据库上的人物状态与物品状态共用这一个位置，不因人物状态加入而出现第二个 |
| RQ-003 | 无法共同落定的组合以失败暴露，不降级为非原子 |
| RQ-004 | 业务代码不表达事务：涉及人物状态的用例在不书写任何开启、提交、回滚或事务对象的前提下获得 RQ-001 的保证 |
| RQ-005 | 业务代码不因载体分支：同一段人物状态操作逻辑作用于持久载体与仅存内存的载体时走同一条路径，除持久性本身外可观察结果相同 |
| RQ-006 | 人物的持久化以数据动词表达：持久化契约上不出现业务动词，新增一种人物状态改动不需要在持久化契约上新增一个方法 |
| RQ-007 | 在用例边界之外改动持久人物状态以失败暴露，不静默完成 |
| RQ-008 | 人物的持久化机制中不含业务规则：过期专家契约后技能等级降到何值、地下城持久效果是否可提交与发放多少经验、金币上限等级取何值，均不由持久化机制决定，且可在不涉及数据库的情况下被检验 |
| RQ-009 | 建表不是任何读写组件的构造副作用；每张表在代码库中只有一处定义；一张表的有效列集不取决于组件的构造顺序 |
| RQ-010 | 协议层不直接持有人物的持久化契约 |
| RQ-011 | 本范围内每一处人物写入均以「位置与值」表达；若某一处无法如此表达，该事实被记录，且不引入业务动词或绕过会话的旁路 |
| RQ-012 | 对外可观察行为逐字不变：角色选择、进入频道、道具移动与道具使用的帧字节与时序，与改动前一致 |

## Assumptions

- 「位置与值」足以表达本范围内那 10 处人物写入，位置由归属者、段与键确定，写入携带整行。该前提已按现有写入点核对，但未被穷尽证明。
- 三处规则迁出后行为等价，且其现有覆盖足以证明等价。若覆盖不足，先补齐覆盖再迁。
- 已建表但从无写入的那些人物表在本范围内确实无需写入能力；若发现某张实际有写入路径，应记录并纳入。
- 建表归属集中化后，读写组件不再于构造时建表不会破坏既有测试夹具。上一轮已出现过夹具依赖构造副作用的先例，故此项须在实施早期验证。
- 一张表今天真正生效的列集是「首个建表者的列集，加上事后补列所加的列」的并集。集中化须复现该并集而不是任取一处定义。
