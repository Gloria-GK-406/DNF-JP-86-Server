# Routing Decision

- TaskContract: `./TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 目标形状由用户一句话定死——「我们要把仓储层的抽象和 IItemStore 一样回收才对」——且该方向是在 Agent 提出反对意见（人物是 31 张异构表，不宜照抄物品的寻址词汇）之后被用户明确重申的，因此不是未经检验的初始表述。可观察结果明确：对外行为一字不变，加上一份可逐条核对的消失清单（业务动词、持久实现中的三处规则、仓储中的 CREATE TABLE）。
- Requirement stability: 八条成功条件全部可枚举且可观察，其中 SC-1、SC-3、SC-5 可由自动化用例直接证伪，SC-2、SC-4、SC-6、SC-7 可由零命中核对证伪。约束均有出处：用户决定、上一轮实测、或代码库中已量化的缺陷（58 处 CREATE TABLE / 51 张表 / 6 张多定义）。
- Execution direction: 中心方向已知。上一轮已交付可照抄的形状（准备/提交/回滚参与者、暂存会话、载体无关容器），且本任务最关键的设计约束已在契约前用代码验证到位：`Enlist` 按连接串去重并限定至多一个可失败参与者，因此「一个数据库 = 一个参与者、对外多个具类型会话」不是待定的选型，而是已被现有协调器逼出来的唯一解。
- Remaining uncertainty: 仅剩非语义的局部选择——协议的具体泛型签名、会话在存储上的暴露方式、集中化建表组件的落点。契约中已记录的实质前提（按键寻址是否足以表达那 10 张表的写入）带有反例时的处置办法。

## Marginal Control Value

- User precision signal: 用户本轮主动否决了 Agent 的「不宜照抄」结论并要求统一，随后在被明确列出「范围三选项 / 流程二选项」时选了最大范围加 SDD 治理流程，而不是更快的直接实现。既往同类任务的表述是「用 sdd 来跑，只是为了实现别漂移」。
- Direct failure mode: 这一刀的危险不在难度而在次序，且错误次序不产生红灯。三处业务规则若在覆盖不足时先被搬走，行为改变是静默的；载体协议若按「一个 store 一个参与者」的直觉提取，第三步会发现目标原子性根本不可达而返工，且该返工发生在协议已被物品侧消费之后；建表集中化有静默分歧模式——`accounts` 今天有三处列集互不相同的定义（7 列 / 12 列 / 更多），`CREATE TABLE IF NOT EXISTS` 意味着先构造者胜出、其余静默失效，另有 5 处 `ALTER TABLE` 与 4 处 `PRAGMA table_info` 事后补列，故「今天真正生效的 schema」由 DI 构造顺序决定，集中化若未正确复现该并集，后果是远离改动点的运行期失败。
- Useful control: 一份 durable 的实施排序与依赖映射，把「规则外迁先于会话化」「载体协议须先满足单参与者约束再被消费」「集中化前须先测出今天生效的并集」三条次序钉在纸上；加上完整结果评审与新鲜验证。
- Time-for-quality rationale: 上述三条失效全部属于「不做也能跑绿」的性质，完整结果评审在改动铺开之后才介入，纠正成本远高于事先排序。用户又已预期实施跨会话（本轮已压缩过一次上下文），排序留在会话里等于没有。为此多付一个 plan 阶段是划算的；同一判断在上一个根任务上已被验证。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: 四步共享同一个接受与回滚边界，任一半单独交付都不成立。规则未外迁就会话化，会把规则原样搬进新会话，等于没做；载体协议未提取就建人物存储，会造出第二套互不相通的协议；人物存储若不与物品存储合为同一个参与者，契约的 SC-1 根本不可达（已验证两条路都撞墙）；存储零 DDL 而建表未集中化，则表不存在。
- Why Direct is insufficient: Direct 给不出「新增的保证被删掉后仍然全绿」这条检验，而本任务的核心交付（同事务原子性、事务外改动抛出、持久实现中无规则）全部是这类保证。
- Why Multi is unnecessary: 只有一个连贯的接受边界。范围外的四项（任务独立聚合、账号侧读写改造、21 张无写入表的会话、其余领域持久化）都已在契约中显式排除，各自是将来独立的一刀。
- Reroute conditions: 若按键寻址被证明不足以表达那 10 张表的写入，回契约层重议并重新评估结构；若三处规则的现有覆盖不足以证明外迁前后等价，补覆盖会成为一个独立的接受边界，届时重新考虑 Multi；若集中化被证明必须触及账号或世界侧的读写路径而不只是表定义，同样回契约重议。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-refactor`
- Why this is sufficient: 需要的额外控制只有一项——durable 的实施排序与依赖映射，用来挡住上面那三条不产生红灯的次序失效。`code-refactor` Profile 的其余绑定（TDD 实施、完整结果评审、新鲜验证）正对本任务「对外行为一字不变」的性质，基线 944 通过 / 2 跳过 / 0 失败可作回归判据。
- Why lighter is insufficient: `sdd-lite` 无 plan 阶段，次序只能留给实施阶段临场决定。而本任务里错误的次序不产生红灯：规则在覆盖不足时被搬走照样全绿，载体协议按直觉提取照样全绿（问题要到第三步才暴露），集中化漏掉某个 ALTER 补的列在测试夹具里也可能照样全绿。Lite 的完整结果评审保护的是「要求被遗忘」，保护不了「中间态曾经不正确」与「早期抽象选错并已被消费」。
- Why heavier is unnecessary: 逐条核对 Governed 的硬性门槛均不成立。不触及人身或系统安全；不改变凭据的校验、存储方式或访问控制——`accounts` 表虽含 `password_hash` 列而参与建表集中化，但本任务只搬动 CREATE TABLE 文本的归属，不触碰任何认证逻辑，属有关键词而无实质触及；不涉及隐私或受保护数据；无资金、法务、合规后果；不产生不可逆的外部变更；目标是本机开发库，项目已定「开发阶段擦库不迁移」，不存在缺乏恢复手段的持久数据丢失路径。范围内的失效由 SC-1、SC-3、SC-5 的自动化用例直接证伪，普通评审加新鲜验证已经够。
