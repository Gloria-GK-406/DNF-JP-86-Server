# Specification: 角色关系系统与好友第一批（好友 + 黑名单）

## Why and Outcome

玩家要在 A21 客户端里正常使用好友与黑名单：加删好友、看到好友在线与否及在哪个频道、好友状态变化即时可见；拉黑后不再被对方打扰。服务端为此建立一个统一的角色关系 owner，以后最近联系人、师徒也放进来；它只保存关系与关系规则，不发任何消息，推送由调用方完成。

## Definitions

- **角色 ID**：`characters.character_id`。TaskContract 中的「角色仓库 ID」「角色 ID」都指它。
- **关系**：有向的 `(owner, target, kind)`，owner 与 target 都是角色 ID。本期 kind 只有「好友」「黑名单」。
- **好友**：A→B 表示 A 把 B 加为好友；B 是否把 A 加为好友是另一条独立关系。
- **观察者**：对角色 X 而言，所有存在「好友」关系 `O→X` 且当前在线的角色 O。
- **在线状态**（好友列表中的显示）：同频道在线、其他频道在线（显示频道号）、离线。频道指玩家所连的游戏监听端口对应的频道。
- **有效角色**：存在且 `delete_flag=0` 的角色。

## Scope

范围与排除项以 TaskContract「Scope」为准，这里不再重复。本 Spec 补充两项范围上的明确化：

- 黑名单对聊天的过滤覆盖第一批的全部聊天频道（见 RQ-041）。
- 角色被删除时，在线观察者的好友列表随即更新，不用等重登（见 RQ-050）。

## Requirements

### A. 客户端证据（实现所依赖的事实）

| ID | Requirement |
|---|---|

| RQ-002 | 查明客户端自身是否限制好友数与黑名单数，以及具体数值。 |
| RQ-003 | 查明好友条目末尾 4 字节（参照中上游写 0、第三方写角色 ID）是否被客户端读取，以及用途。 |
| RQ-004 | 查明收到全量好友列表时客户端是否清掉黑名单显示。 |
| RQ-005 | 查明客户端靠什么把「同频道在线」与「离线」区分开（两者在列表里的频道字段都是 0）。参照的做法是额外发送该角色的 USERINFO；须查明这样做会不会让该角色出现在不同区域的场景里。 |

### B. 角色关系领域服务

| ID | Requirement |
|---|---|
| RQ-010 | 好友与黑名单关系由**一个**角色关系领域服务持有，不按 kind 拆成多个服务或多个 owner；对外分为只读接口与写接口两个契约，只需读取的调用方（聊天、在线推送、协议列表构建）只依赖只读接口。 |
| RQ-011 | 持久化的关系只含角色 ID、kind 及时间等非身份属性，不保存角色名或其他角色快照；展示所需的名字、等级、职业、转职在读取时按角色 ID 取当前值。 |
| RQ-012 | 关系服务不发送网络消息，不登记通知或投影，不发布领域事件；写操作返回具名结果（成功，或带原因的拒绝），调用方据此自行推送。 |
| RQ-013 | 添加好友规则：owner 与 target 都须是有效角色；不能添加自己；target 已在 owner 的好友中时，视为成功且不产生第二条；owner 好友数达上限时拒绝。target 是否在线不影响结果；不需要 target 同意；不改变 target→owner 方向。 |
| RQ-014 | 删除好友规则：只删除 owner→target 这一条；关系不存在时拒绝。 |
| RQ-015 | 黑名单添加规则：目标须是有效角色，不能拉黑自己；已在名单中时拒绝（重复）；名单达上限时拒绝（已满）；目标不存在或已删除时拒绝（不存在）。删除不存在的关系时拒绝。好友关系与黑名单关系互不影响。 |
| RQ-016 | 上限：客户端有自身上限时与之一致；客户端没有可见上限时，好友与黑名单各 64。上限是关系服务内的规则，调用方不另行判定。 |
| RQ-017 | 只读能力至少包括：某角色某 kind 的关系列表（只含有效角色，带加入时间）；把某角色加为好友的角色集合（反查）；两个角色之间某方向的黑名单是否存在。 |
| RQ-018 | 角色删除时，该角色作为 owner 或 target 的全部关系一并清除，且返回受影响的 owner 集合，供调用方推送。删除后，任何读取都不再出现该角色。 |
| RQ-019 | 关系 kind 是关系服务内的封闭取值；以后新增最近联系人、师徒时，在同一 owner 与同一存储中增加 kind，不新建关系 owner。 |
| RQ-020 | 关系写入经该服务的业务事务完成，持久化成功即生效；服务端重启后关系不丢失。所有写入（包括以后的 GM 写入）只经写接口。 |

### C. 协议行为

DSTR 指 `[len:u32][UTF-8 字节]`。下面的布局是参照布局，最终以 RQ-001 的证据为准。

| ID | Requirement |
|---|---|
| RQ-030 | CMD `0x0122` 添加好友。请求 `[uid:u16][server:u8][name:DSTR]`，uid 只作提示、不参与判定，按名字精确查找有效角色。应答：成功 `[1:u8]`；失败 `[0:u8][err:u8]`，目标不存在或已删除为 `0x15`，自己已满为 `0x04`，添加自己与其他失败为 `0x01`。畸形请求（截断、尾随数据、名字为空或超长、server≠1）按失败应答处理，不落库，连接保持。 |
| RQ-031 | 添加成功后，按 RQ-036 的顺序向操作者推送更新后的全量列表；目标不收到任何消息。 |
| RQ-032 | CMD `0x0123` 删除好友。请求 `[server:u8][name:DSTR]`。成功应答 `[1:u8]`；失败一律 `[0:u8][0x05:u8]`。成功后依次推删除通知、全量列表（RQ-036）。 |
| RQ-033 | NOTI `0x0111` 全量：`[0:i32][count:u32]`，后接 count 条 `[server:u8=1][ch:u16][name:DSTR][level:u8][job:u32][grow:u8][bl:u8=0][tail:i32]`。ch 取值：同频道在线为 0，其他频道在线为该频道号，离线为 0；tail 按 RQ-003 的结论取值，没有结论时写 0。没有好友时也发送 count=0。 |
| RQ-034 | NOTI `0x0111` 删除：`[2:i32][count:u32]`，后接 count 条 `[server:u8=1][name:DSTR]`。 |
| RQ-035 | NOTI `0x0112` 上下线：`[ch:u16][server:u8=1][name:DSTR][bl:u8]`。上线时 ch 为其所在频道号，下线时为 0；bl 表示接收者是否把该角色加入了黑名单。 |
| RQ-036 | 推送全量好友列表之后，若 RQ-004 证实客户端会清掉黑名单显示，紧接着补发该玩家的黑名单（RQ-039 的列表应答）；否则不补发。同频道在线好友的显示按 RQ-005 的结论补足所需消息。 |
| RQ-037 | CMD `0x0076` 拉黑、`0x0077` 解除。请求 `[name:DSTR]`。成功应答 `[1:u8][name:DSTR]`。拉黑失败 `[0:u8][err:u8]`：重复为 74，目标不存在为 76，已满为 78，其他失败（含拉黑自己、畸形请求）为 0。解除失败为 75。 |
| RQ-038 | 登录进入游戏时，替换现有空基线，发送该角色的真实全量好友列表（RQ-033），并按 RQ-036 处理黑名单与同频道显示。 |
| RQ-039 | CMD `0x0078` 黑名单列表：请求为空。应答 `[1:u8][count:u8]`，后接 count 条 `[name:DSTR][年-1900:u8][月 0 起:u8][日:u8]`，日期为加入时间换算成的服务器本地日期。名单为空时 count=0。 |
| RQ-040 | 所有名字字段的字节上限与证据记入协议页；本期新增的扇出消息中，名字来自数据库中的有效角色名，长度有界。 |

### D. 黑名单生效

| ID | Requirement |
|---|---|
| RQ-041 | 聊天投递时，若收件人把发言者加入了黑名单，就不投递给该收件人。适用于第一批的全部聊天频道：区域（mode 3/45/46）、队伍（2/9）、私聊（1/7）、频道喇叭（13）、服务器喇叭（11/12/57）、1:1 窗口内发言（43）。喇叭照常扣除，其他收件人照常收到；私聊目标拉黑了发言者时，按「目标不可达」静默处理，不回错误。只有发言者自己拉黑了收件人时，不影响投递。 |
| RQ-042 | CMD `0x01A3` 建立 1:1 对话时，若任一方把另一方加入了黑名单，不建立会话，只给发起方发结果码 77 的 NOTI `0x016A`，对方不收到任何消息。 |
| RQ-043 | 解除拉黑后，RQ-041、RQ-042 的限制立即消失。 |

### E. 在线推送

| ID | Requirement |
|---|---|
| RQ-050 | 角色 X 进入游戏（选角完成）时，向 X 的每个观察者发 NOTI `0x0112` 上线；与 X 同频道的观察者另按 RQ-036 补足同频道显示所需消息。 |
| RQ-051 | X 离开游戏时（正常退出、断线、回到选人、换频道导致的旧会话结束），向 X 的每个观察者发 NOTI `0x0112` 下线。下线通知与现有离场通知（USER_LEAVE）的先后，按客户端证据确定。 |

| RQ-055 | 推送内容反映触发它的那次变化提交之后的关系与状态；同一接收者先后收到的两份列表中，后一份反映较晚的状态。已经下线或换了会话的接收者不再收到针对旧会话的推送。 |

## Amendments

（实现中采纳的 RQ-001 证据所引起的修正，记录在这里。）

### AM-1（2026-11-12，TASK-01 客户端证据）

依据 [research/client-evidence.md](research/client-evidence.md)（ClientStatic，A21 b1 解包 exe 静态反汇编）。
各协议布局与参照一致，没有出现需要确认或另一套协议的情况；以下取值与约束推翻或补充参照：

- **RQ-032**：`0x0123` 应答 handler（VA `01119950`）只对 reason `0x15` 弹提示（44451「列表中不存在该角色，
  重连后刷新」），参照用的 `0x05` 客户端静默。删除失败改为 `[0:u8][0x15:u8]`。
- **RQ-040 / RQ-037 / RQ-039**：`0x0077` 成功应答与 `0x0078` 列表条目的名字，客户端只收 1–30 字节
  （`ReadDStrW` 缓冲 `0x1F`）；`0x0111`、`0x0112`、`0x0076` 成功应答只收 1–255 字节。超限时客户端只消耗长度字段，
  其后错位。服务端所发名字须落在对应范围内；超限时如何处理由实现单元决定。
- **RQ-033**：同一份列表里 `(server,name)` 不得重复，否则客户端从重复项起丢弃整表其余部分；tail 读入后不被使用，写 0。
- **RQ-030 / RQ-037（只记录，不改要求）**：`0x0122` 的 `0x01` 与 `0x0076` 的 `0` 在客户端都没有提示；客户端另有
  `0x0122` 的 `0x07`（跨服务器群）、`0x5A`（GM），`0x0076` 的 `3`（只能拉黑在线者）、`0x5A`。
- **RQ-005 / RQ-036 / RQ-050**：好友栏的「同频道在线」= 接收者本地角色表里有该角色（USERINFO subtype 0 建立、
  USER_LEAVE 删除），参照补发 subtype 0 的做法在机制上成立；但 subtype 0 发给不同区域的接收者时会不会让该角色
  出现在其场景里，静态未定，需实机（最便宜的验证方法见研究记录）；RQ-036、RQ-050 的同频道补发取决于这一结果。
- **RQ-051**：`0x0112` 与 `USER_LEAVE` 的先后不影响客户端；凡是持有该角色 CNUser 的观察者都必须收到 `USER_LEAVE`，
  否则好友栏停在在线。
