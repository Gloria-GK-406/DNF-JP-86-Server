# TaskContract: 角色关系系统与好友第一批（好友 + 黑名单）

## Context

2026-11-12 对话中逐步形成，按时间顺序摘录用户原话：

1. 「我们这里继续完善好友系统，先看看70server和上游做的怎么样，并且在DNF-第三方的路径也有一个可以参考的服务端……上游的代码好久也没更新了，拉一下后，最后给我一个可行性方案」
2. 「打包的那个为了后续方便，你不如直接翻译成源码吧。反正是C#的，恢复效果会好很多。便于后续参考」

### Current Situation

基线 `origin/main@17eb734d4`（0.3.0）。本仓没有好友与黑名单：选角时只发空的 NOTI `0x0111` 基线（`CrossServerFriendBaselineMessage`）；CMD `0x0078` 只收不回（`UnansweredReports`）；`0x0122`、`0x0123`、`0x0076`、`0x0077` 没有解包器。角色删除是软删除（`characters.delete_flag`），本仓没有角色改名。数据库结构版本 4。聊天单入口与 1:1 对话（#312）已合并，并为黑名单预留了发送前检查点，1:1 建会话的黑名单结果码 77 约定随黑名单一起做。

调研结论（工作区文档 `E:\Project\DNF\Document\好友系统可行性方案-20261112.md`）：
- A21 使用统一服好友协议 `0x0122`/`0x0123` 与 NOTI `0x0111`/`0x0112`；旧式 `0x003C`/`0x003D`、NOTI `0x0034`/`0x0038` 的客户端 handler 是众多 type 共用的默认 handler `0x01E31720`（ClientStatic，High）。`0x0122` 已有一份 UI 真实样本，与参照布局一致。
- 70、上游 ServerS4A21（`1870c85`）、第三方商业端（反编译于 `E:\Project\DNF\Research\third-party-s4a21-v3.3\decompiled\`）三方一致：好友单向、不需对方确认、可加离线角色；上限 70 为 32，上游与第三方为 64；黑名单上限 70 为 10，上游与第三方为 64（70Reference / 参照实现）。
- 本仓线上文本为 UTF-8，与第三方一致。

## Goal

玩家在 A21 客户端的好友界面可以按名字添加、删除好友，看到好友的等级、职业与在线状态（同频道、其他频道、离线），好友上线、下线、升级或转职时无需重登即可看到变化；可以拉黑、解除拉黑并查看黑名单，被拉黑的一方无法与拉黑者建立 1:1 对话，其聊天消息也不会送达拉黑者。关系由一个统一的角色关系领域服务保存：只存角色仓库 ID，包含关系的业务规则，不主动推送，其他功能经它读取后自行行动；结构上能在以后容纳最近联系人与师徒，但本期只实现好友与黑名单两种关系。

## Scope

### In

- 补齐实现所需的 A21 客户端证据：上述协议的读取布局、客户端自身的好友与黑名单上限、好友条目末尾 4 字节的用途、全量好友列表是否清掉客户端黑名单显示；结论写入 `protocol/` 并标注证据。
- 统一的角色关系领域服务与持久化：好友、黑名单两种关系；关系的业务规则（不能对自己、目标须存在且未删除、上限、重复添加与删除的处理）由该服务持有；读接口与写接口分开。
- 好友协议：CMD `0x0122` 添加、`0x0123` 删除及其应答；NOTI `0x0111` 全量与删除通知（登录时发真实列表，替换现有空基线）；NOTI `0x0112` 上下线通知；同频道好友的角色信息与离开通知。
- 黑名单协议：CMD `0x0076` 添加、`0x0077` 删除、`0x0078` 列表及其应答（`0x0078` 从只收不回改为应答）。
- 在线关系推送：好友上线、下线（含断线、回选人、换频道）、升级、转职时，通知把该角色加为好友的在线玩家；按客户端证据处理全量好友列表与黑名单显示的先后关系。
- 黑名单生效：1:1 对话建立时任一方拉黑另一方即拒绝（给发起方结果码 77）；聊天投递（含私聊与 1:1 窗口内发言）不送达拉黑了发言者的收件人。
- 删除角色时清理该角色作为任一方的关系，删除后的角色不出现在任何人的好友或黑名单里。
- 数据库结构升级及旧库迁移。
- 自动测试；使用当前主干实际数据库准备用户测试服并提供编号测试流程。

### Out

- 最近联系人（`0x02A3`）与团队最近玩家（`0x0334`/`0x02F0`）。
- 师徒关系及其任何业务。
- 好友确认流程、亲密度、分组、备注、推荐、礼物、决斗好友（PVP_BUDDY 系列）、旧式 `0x003C`/`0x003D`。
- 查询并跟随好友所在频道（`0x0323`）。
- 黑名单在组队邀请、交易、决斗邀请、邮件上的生效。
- 婚姻关系的任何改动。
- 角色改名（本仓没有该功能）。
- 推送、创建 PR、合并、版本号修改。

## Constraints

- 好友与黑名单（以及将来的最近联系人、师徒）由同一个角色关系领域服务保存，它是这些关系的唯一 owner；其他功能（聊天、在线推送、协议、GM）只经它读取或写入，不另存关系副本（请求 3、5；`Document/Architecture.md`）。
- 关系只以角色仓库 ID 记录，不保存角色名；名字只在协议入口解析为 ID，展示时按 ID 读取当前角色信息（请求 3）。
- 关系领域服务包含关系的业务规则，但不发送任何网络消息、不发布推送；推送与其他行为由调用方根据它的结果和查询完成（请求 4）。
- 婚姻不并入关系系统（请求 4）。
- 遵守仓库分层与架构规则（`AGENTS.md`、`Document/Architecture.md`、`Document/ProtocolCommands.md`、`Document/EventsAndNotifications.md`、`Document/DatabaseSchemaMigration.md`）：包体布局只在 Protocol 层出现。
- 用户测试使用当前主干服务实际使用的数据库；切换前做一致备份；数据库与备份不提交到 Git；协议结论标注证据标签，没有实机确认的不标 ClientVerified（`Document/FeatureDevelopment.md`、`protocol/evidence.md`）。
