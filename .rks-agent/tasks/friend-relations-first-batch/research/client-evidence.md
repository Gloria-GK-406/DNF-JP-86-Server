## RQ-001 读取布局

### CMD `0x0122` 添加好友

**请求**（构包 `01A2D180`，`MakeHeader` 调用点 `01A2D31C`）：`u16 uid, u8 server, dstr name`
（`01A2D329 WriteU16`、`01A2D336 WriteU8`、`01A2D343 WriteDString`）。ClientStatic / Confirmed。

- uid：本地角色表按 `(server,name)` 查到就写其 uid（`01A2D2FB` → `00CBCEC0` 取 `+8`），查不到写 `0xFFFF`（`01A2D2F6`）。High（服务端只能当提示）。
- server：调用参数为 0 时取自身的服务器群（混淆全局 `03A5AFD8`）。样本 `02 00 01 04 00 00 00 31 31 32 33` 中 server=1（WireCaptured）。
- 发送前的本地拦截见 RQ-002。

**应答 handler** `01119880`（RVA `00D19880`）：

- `ok≠0`：**一个字节都不读，什么也不做**（`01119887 jne 011198DE` 直接返回）。Confirmed。成功后的列表变化只能靠服务端推 `NOTI 0x0111`。
- `ok=0`：`reason−4` 查跳转表（`01119895`，表 `011198E0`/`011198F4`），只有四个值有文字，其余静默。Confirmed。

| reason | 字符串 | 文字（日） |
|---:|---:|---|
| 4 | 807 | 友達数を最大まで登録しました（已满） |
| 7 | 44450 | 一般チャンネルでは同じサーバー群のみ友達に登録できます（跨服务器群） |
| 0x15 | 44453 | 該当キャラクターが存在しません（角色不存在） |
| 0x5A | 6424 | GMに向かってのその行動は禁止されています（对 GM） |
| 其他（含 0x01） | — | 静默 |

### CMD `0x0123` 删除好友

**请求**（构包 `01A2D390`，调用点 `01A2D4C6`）：`u8 server, dstr name`。本地不是好友时不发送，弹 398
「対象が友達に登録されていません」（`01A2D3C8 → 01A2D3D3`）。Confirmed。

**应答 handler** `01119950`：`ok≠0` 不读不做；`ok=0` 且 `reason=0x15` 弹 44451「リストから削除する対象の
キャラクターが存在しません。再接続時、リストが更新されます。」；**其他 reason（含参照用的 `0x05`）静默**
（`01119959 cmp [ebp+0x10],0x15`）。Confirmed。

### CMD `0x0076` 拉黑

  并弹 44429「%sさんを遮断リストに登録しました」。Confirmed。
- `ok=0`：Confirmed。

| reason | 字符串 | 文字（日） |
|---:|---:|---|
| 78 (0x4E) | 4759 | ブラックリストを最大まで登録されました（已满） |
| 74 (0x4A) | 4760 | 相手がすでにブラックリストに登録されています（重复） |

### CMD `0x0077` 解除拉黑

**请求**（构包 `01A2D6B0`，调用点 `01A2D72F`）：`dstr name`；本地不在黑名单时不发送，弹 398。Confirmed。

**应答 handler** `011243E0`：`ok≠0` 读 `ReadDStrW(buf, 0x1F, GetStr(810))`（`01124424`，**名字须 1–30 字节**），
以自身服务器群调 `01A2D750` 清除黑名单标志并弹 44454「%sさんの遮断を解除しました」。
`ok=0` 且 `reason=75 (0x4B)` 弹 44451；其他静默。Confirmed。

### CMD `0x0078` 黑名单列表

**请求**：空 body（机器区已闭合）。

**应答 handler** `0111F800`：`ok=0` 什么也不读（`0111F816 je 0111F93C`）。`ok≠0`：Confirmed。

```text
0111F826  ReadU8  count
0111F835  [03A5C994]->+0 = 0           ; 关掉逐条提示
  循环 count 次：
0111F86A  ReadDStrW(name, 0x1F, GetStr(662))   ; 名字须 1–30 字节
0111F875  ReadU8  → tm_year   ([ebp-0x54])
0111F880  ReadU8  → tm_mon    ([ebp-0x58])
0111F88B  ReadU8  → tm_mday   ([ebp-0x5C])
          mktime(&tm)  (02C675BD)        ; 时分秒为 0
          找人取服务器群（同 0x0076），调 01A2F4B0 写入名单
0111F936  [03A5C994]->+0 = 1
```

布局 `[1][count:u8] × {dstr name, u8 年-1900, u8 月(0 起), u8 日}` 与参照一致。**不清空原有黑名单节点**，
只按名合并；名单里没有、本地却有的条目保持不动。

### NOTI `0x0111`

handler `01161580`：`ReadU32 subcmd`（`0116158F`），`subcmd>4` 忽略，否则按跳转表 `01161630` 调用
`[03A5C994]` 的方法。Confirmed。

| subcmd | 方法 | 作用 |
|---:|---|---|
| 0 | `01A31EA0` | **重建**：只保留临时遮断节点，其余（好友、黑名单）全删，再按 subcmd 1 的格式读入；期间不弹提示 |
| 1 | `01A2FEC0` | 增量添加；每条弹 44448「[%s]%sさんを友達に登録しました」 |
| 2 | `01A2E4B0` | 删除；每条弹 44449「[%s]%sさんを友達から削除しました」 |
| 3 | `01A2ED90` | 就地更新 ch/level/job/转职，不动三个标志 |
| 4 | `01A2F0A0` | 改名：`u32 count × {u8 server, dstr 旧名, dstr 新名}` |

**subcmd 0/1 的 body**（`01A2FEC0` + 条目读取 `01A2C600`）：

```text
01A2FEF8  ReadU32 count       ; 有符号，<0 即放弃
  每条：
01A2C647  ReadU8  server      ; ≥0xFA 则放弃本条及其后全部
01A2C669  ReadU16 ch          → +0x24
01A2C698  ReadDStrW(name, 0x100, NULL)   ; 名字须 1–255 字节
01A2C6D5  ReadU8  level       → +0x26
01A2C6DE  ReadU32 job         → +0x28
01A2C6F3  ReadU8  转职        → +0x2C（经 019DAFB0）
01A2C723  ReadU8  bl          → +0x2E = (bl≠0)
01A2C742  ReadU32 tail        → +0x38
```

即 `[subcmd:u32][count:u32] × {u8 server, u16 ch, dstr name, u8 level, u32 job, u8 grow, u8 bl, u32 tail}`，
与参照布局一致。Confirmed。

读一条后调插入 `01A2FCD0`：**该 `(server,name)` 已是好友（`+0x2D≠0`）则返回失败，整张表其后的条目都不再读**
（`01A2FD24` → `01A2FD7B xor al,al` → `01A2FF8B je 01A300DC`）；已存在但不是好友的节点（例如只在黑名单里）
只把 `+0x2D` 置 1，**线上的 ch/level/job/bl 不写入**（`01A2FE08`）；不存在则整条插入。Confirmed。

**subcmd 2 的 body**（`01A2E4B0`）：`[2:u32][count:u32] × {u8 server, dstr name(1–255 字节)}`；
每条调 `01A2DD70` 清好友标志（并清角色表里该角色的好友记号 `+0x19`），**目标不是好友则返回失败、其后条目不再读**
（`01A2E56A` → `01A2E571 je 01A2E502`）。Confirmed。

### NOTI `0x0112`

handler `0116F000`，Confirmed：

```text
0116F03D  ReadU16 ch
0116F056  ReadU8  server
0116F083  ReadDStrW(name, 0x100, NULL)   ; 1–255 字节
0116F097  ReadU8  bl
0116F133  [03A5C994]->01A2BFF0(server, name, {ch, bl≠0})
```

`01A2BFF0` 找到节点就**覆盖 `+0x24 ch` 与 `+0x2E` 黑名单标志**（`01A2C0C6`、`01A2C0DD`），找不到返回 0；
handler **不看返回值**，随后无条件在聊天框打一行：

| 条件 | 字符串 | 文字 |
|---|---:|---|
| ch=0，server=自身群 | 670 | %sさんがゲームを終了しました。 |
| ch=0，server≠自身群 | 19247 | [%s]%sさんが退場しました。 |
| ch≠0，server=自身群 | 671 | %sさんが %d チャンネルに接続しました。 |
| ch≠0，server≠自身群 | 19248 | [%s]%sさんが%dチャンネルに接続しました。 |

布局 `[ch:u16][server:u8][name:dstr][bl:u8]` 与参照一致。推论（High）：发给非观察者也会打出这行字，
所以只能发给观察者；`bl` 必须如实反映接收者是否拉黑了对方，写 0 会把客户端已有的黑名单标志清掉。

## RQ-002 上限

- 好友：`01A2D1A7 call 01A2B430`（数 `+0x2D` 节点）`; cmp eax,0x40; jl` → **64 人**，满了弹 396
  「友達を最大数まで登録しました」且不发请求。ClientStatic / Confirmed。
- 黑名单：`01A2D574 call 01A2B4B0`（数 `+0x2E` 节点）`; cmp eax,0x40` → **64 人**，满了弹 44430 且不发请求。Confirmed。
  好友节点被拉黑同样计入。
- 黑名单另有等级门槛：`01A2D53C–01A2D549` 取自身对象虚函数 `+0x360` 的值，`≤20` 时弹 70526
  「Lv21 未満…ブラックリスト機能を使えません」（日文表此条乱码，中文表为「未满Lv21的用户，不能使用黑名单功能」）且不发请求。
  ClientStatic / High（虚函数返回值即等级是由字符串推断的）。
- 接收方向没有条数上限：`0x0111` 的 count 是 u32，`0x0078` 的 count 是 u8（最多 255）。
- 重复：本地已是好友不发 `0x0122`（弹 397）；本地已拉黑不发 `0x0076`（弹 44431）。Confirmed。

结论：客户端自身限制 **好友 64、黑名单 64**，与 RQ-016 的默认值一致。

## RQ-003 末尾 4 字节

`01A2C742 ReadU32` 读入后只存到条目 `+0x38`（`01A2C74D`），之后只被条目复制函数原样拷贝
（`01A2B91A`、`01A2B9EB`）。ClientStatic / Confirmed（读取与存放）。

在好友/黑名单类（`01A2A000–01A34000`）与好友窗口绘制区（`02480000–0248A000`）扫描 `+0x38`/`+0x68` 的读取，
没有任何使用；条目读取后的日志调用（`01A2C888` 起）也只用 server/name/ch/level/job/grow。
ClientStatic / High（没有消费者；扫描是按区域做的，不是全程序数据流）。

结论：客户端读这 4 字节但不用；写 0 或角色 ID 对显示无影响（High），按 RQ-033 写 0。

## RQ-004 全量列表是否清掉黑名单显示

是。subcmd 0（`01A31EA0`）：

```text
01A31EEF..   遍历 this+8 的 map
01A31F62     cmp byte [node+0x5F], 0     ; 条目 +0x2F 临时遮断
01A31F68     je  跳过                      ; 不是临时遮断 → 不保留
01A31FB3     插入临时 map（只有临时遮断节点）
01A32047..   清空原 map，与临时 map 交换
01A320DB     this+0 = 0；call 01A2FEC0 读新表；this+0 = 1
```

ClientStatic / Confirmed。黑名单节点（`+0x2E`）与好友节点一起被清掉；`0x0078` 应答写入的就是这张 map
（`0111F91B → 01A2F4B0 → this+8`），所以收到全量列表后黑名单页变空，直到再收到 `0x0078` 应答。
被拉黑的好友在新表里的黑名单标志只取线上 `bl` 字节，加入日期丢失（`+0x30` 为 0）。

推论（High）：RQ-036 的「全量后补发黑名单列表」是必要的；补发时 `0111F835` 先关提示，不会逐条弹框。

## RQ-005 同频道在线与离线如何区分

好友行绘制 `024831B0`（唯一调用者 `02483B57`，`esi` = 条目）：

```text
02483203  ecx = [03A5C980]                  ; 角色表
0248320D  call 019E2B50(entry.server, entry.name)   ; 按 (服务器群, 名字) 找角色
02483212  [ebp+0x10] = 找到的角色或 0
02483219  找到且未拉黑 → 用该角色对象画头像（虚调用 +0x308）
0248327B  否则：ch=0 或被拉黑或临时遮断 → 名字灰色（0xFF808080）
024834E5  cmp byte [esi+0x2E],0 / jne 跳过   ; 被拉黑：不显示在线
024834FF  cmp [ebp+0x10],0 / jne 显示        ; 本地角色表里有这个人
02483505  cmp word [esi+0x24],0 / jbe 跳过   ; 或 ch>0
0248352E  push 25000「接続中」               ; 在线字样
```

ClientStatic / Confirmed。显示规则：

| 条件 | 显示 |
|---|---|
| 被拉黑（`+0x2E`） | 灰色，无在线字样 |
| 角色表里查得到 | 在线（头像来自角色对象），视为同频道 |
| 查不到且 ch>0 | 在线，名字正常色 |
| 查不到且 ch=0 | 离线，灰色 |

**角色表 `[03A5C980]` 是什么**（ClientStatic / Confirmed）：

- `019E5490 GetOrCreate(uid)` 新建 0x580 字节的 CNUser 放进 `this+4`；`019E2EF0` 按 uid 查；`019E3440` 删除。
- USERINFO 的 subtype 0 每条记录（`013E7340`）读 uid 后调 `013E27E0`，查不到即 `GetOrCreate`（`013E2801`）。
- 同一记录在 64 字节尾块里读一个 u8（`013E7CE7`），写入 CNUser `+0x374`（`013E7CF9 → 019DB4A0`）；
  `019E2B50` 用它（`018A8030` 读 `+0x374`）与好友条目的 server 比较。读取点与写入点 Confirmed。
  它在尾块中的偏移是 **+55**：按 `013E75CB` 起的读取顺序逐个累加宽度，并用参照已知的锚点
  （+23 副职业、+39 名誉、+47 状态位、+59 mood、+61 技能树）对齐得出，High。参照常量块
  `A21AfterAliveNoGuild[55]` 为 `0x01`（UpstreamReference），本仓
  `StateSynchronizationPayloadCodec.Entry.cs` 的 `SubtypeZeroFixedTail[55]` 同为 `0x01`，
  所以 CNUser 的服务器群是 1，与好友条目 server=1 一致。改动这个字节会让好友栏查不到同频道的人。
- `NOTI 0x0006 USER_LEAVE`（handler `0118C420`）读 u16 uid 后调 `019E3440` 删除 CNUser（`0118C5AB`）。

所以「同频道在线」= 接收者本地有该角色的 CNUser，且其服务器群与条目 server 相同。参照「补发该角色的
USERINFO subtype 0」的做法在机制上成立：它让 CNUser 出现，`USER_LEAVE` 让它消失。

**未定，需实机**：只为显示在线而发 subtype 0 时，该角色会不会出现在接收者当前场景（不同区域/城镇）。
静态只证到 subtype 0 创建 CNUser；场景里的角色实体与位置在本仓的城镇流程中由随后的 `0x0017`/`0x0018`
（带 town/area/坐标）建立，`0x0017` handler（`011922A0`）按 uid 找 CNUser 后再比较 town/area，但 subtype 0
本身是否也生成场景实体没有追完（`013E7340` 约 950 条指令，含多个虚调用）。subtype 0 没有「不入场景」的
subtype 可选（handler `013E91E0` 只有 0/1/2/3/4/6/7 七支，只有 0 创建 CNUser 的路径已确认）。

最便宜的实机验证：A、B 同频道、不同区域（或不同城镇），A 已加 B 为好友。服务端只给 A 发 B 的 subtype 0
（不发 `0x0017`/`0x0018`），看 A 的场景是否出现 B，以及 A 的好友栏 B 是否转为在线；再给 A 发 `USER_LEAVE(B)`，
看好友栏是否转灰。这一步可直接并入 T 单元的用户测试流程。

## RQ-051 下线通知与 USER_LEAVE 的先后

- `0x0112` 的处理（`0116F000` → `01A2BFF0`）只改好友条目的 ch 与黑名单标志并打一行字，**不查角色表**。
  ClientStatic / Confirmed。所以先后不影响 `0x0112` 本身。
- 但 ch=0 的条目只有在角色表里**查不到**时才显示离线（RQ-005）。同频道的好友下线，若接收者本地仍有其
  CNUser，就一直显示在线，直到收到 `USER_LEAVE`。High。
- 结论：两者先后无所谓，**都要发**；凡是曾因好友功能或同区可见而拿到该角色 subtype 0 的接收者，都必须收到
  `USER_LEAVE`，否则好友栏停在在线。参照「先 `0x0112` 再 `USER_LEAVE`」的顺序可以沿用。

## 其他发现

- **CMD 未请求也会被处理**：CMD 分发 `01637680` 只在写出器标志 `[writer+0x2BD068]`（`0274CA10`）置位时丢弃
  type≠3 的帧，不按「是否有待答请求」匹配。所以服务端主动发 `0x0078` 应答可以被接收。ClientStatic / High（该标志含义未追）。
- **临时遮断与重建的冲突**：临时遮断节点在 subcmd 0 中保留；若它同时是好友，新表里同名条目插入失败，
  **该条之后的好友全部读不进来**（见上「插入」）。临时遮断只在客户端，服务端无从得知。ClientStatic / Confirmed（逻辑）；
  实际触发需要玩家先对好友做临时遮断。
- **增量形态可选**：subcmd 1 只增不清，并弹「已登录为好友」提示；subcmd 3 只就地更新 ch/level/job/转职，
  不碰黑名单标志。参照全部用 subcmd 0。ClientStatic / Confirmed（行为）。
- 本地屏蔽判定 `01A2C550(server,name,含临时?)`：永久黑名单 `01A2C2A0`（`+0x2E`）、临时遮断 `01A2C3E0`（`+0x2F`），
  被 `0106B693`、`0164B95A`、`023CF911`、`0259C42D`、`0259C745` 调用；这些调用者的用途未追。
