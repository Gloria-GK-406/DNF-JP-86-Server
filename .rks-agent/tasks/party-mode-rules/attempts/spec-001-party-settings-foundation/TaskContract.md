# TaskContract: 队伍设置模型与 `0x000C` 基础闭环

## Context

### Source Request

根任务要求首先完成“一个高精度的初始版本规则服务和相关业务逻辑”，再逐类解析 Normal、Story、
Cycle 的细节。用户允许在已授权边界内自由选择工作方式，但要求中途只有强证据证明架构不合理时才先
重构。

2026-09-12 实机看到客户端把设置块 `[1]` 置为 `1` 后，用户补充当前产品决策：

> “回归玩家这个，直接都设置为没有。默认是 0 就好了。我们暂时不做回归玩家相关的东西。”

因此该字节不再属于“未知且无损保存”的集合，而是服务端拥有的禁用开关：输入可兼容接收，领域保存和
后续通知必须统一规范化为 `0`。此决策只作用于队伍设置块，不扩大为角色持久化中的其他回归玩家字段。

### Current Situation

当前接受基线 `d717f1b0538793c86f347fce784acaaa2eab3c49` 已有城镇组队生命周期，但创建队伍时只生成
默认 12 字节设置块，C2S `0x000C` 未注册也没有领域设置命令。上游可作为行为线索，客户端静态证据
给出类别和模式目标字段线索；JP-86 尚缺把这些线索收敛为保守共享模型的实现与当前证据记录。

## Goal

建立可承载三类队伍但不预判其玩法差异的类型化设置模型和集中规则服务，完成已确认 `0x000C`
创建/编辑形状到原子领域变更及 type-1 设置通知的基础闭环，并保持现有默认普通队伍和所有已验收组队
行为不回退。

## Scope

### In

- 先取证上游 `SET_PARTY_INFO`，再定位并记录当前 A21 客户端的构包、类别和设置读取边界。
- 增加能区分 Story、Cycle、Normal 与非法类别的类型化设置模型；除产品明确禁用的 `[1]` 外，对尚未
  解释的字段保持无损、保守。
- 增加共享队伍设置规则服务，只承载当前证据支持的类别、容量、标题/目标形状及默认值不变量。
- 严格解码当前证据支持的 `0x000C` 创建/编辑请求，并通过 Command/领域服务实施队长授权、当前会话、
  容量和状态校验。
- 成功变更后向正确的当前成员投影 type-1 队伍设置刷新；失败不通知、不污染状态，旧代际/迟到更新
  不能覆盖新状态。
- 把现有队伍创建默认设置迁移到同一模型/规则边界，同时保持客户端当前默认普通队伍表现。
- 补齐自动化测试与协议来源记录，为后续 Normal 子规格提供稳定接口和明确未知项。

### Out

- Story、Cycle 或 Normal 的模式特有副本目标、进入资格、返回、奖励或玩法规则。
- 因方便而为后续模式预建未被证据要求的策略层、继承层次或通用 DSL。
- 没有当前 A21 可归因证据时把 `0x000C` 或 type-1 通知标为 `ClientVerified`。
- 与本基础闭环无关的组队 UI、P2P/UDP、中继和副本战斗实现。

## Constraints

- 以当前 A21 客户端/真实样本为协议权威；上游实现只能作为定位与对照，冲突必须记录。
- handler 调 Command 实施业务并在成功后发布 Event/Notification；Command 调领域实例和领域服务；
  规则服务提供设置规则；Application 不得引用 Infrastructure。
- 原始设置中的未解释字段必须无损保留或被明确拒绝，不能被默认清零、重排或赋予猜测语义；唯一例外是
  用户明确要求暂时禁用的队伍回归玩家标志 `[1]`，它由规则服务强制规范化为 `0`。
- 当前任务只形成后续逐类实现所需的最小稳定扩展点；局部适配优先，除非取证出现根契约定义的强重构
  信号。
