# Specification: 队伍设置模型与 `0x000C` 基础闭环

## Why and Outcome

当前服务端能通过邀请形成队伍，却把 `NOTI 0x0009` 的默认信息块类别写成 `0`；当前 A21 客户端把
该值解释为 Story，而服务端实际提供的是通用/Normal 行为。同时客户端的
`SET_PARTY_INFO (0x000C)` 没有服务端入口，玩家创建或编辑队伍设置时无法形成受约束的状态转移。

本结果要让队伍设置成为领域事实而不是 encoder 常量：已确认字段类型化，除用户明确禁用的回归玩家
标志外未解释字节保持无损，所有
共享判断集中在一个规则服务中；`0x000C` 只接受当前 A21 证明的完整形状，经当前会话与队长权限校验后
原子创建或更新队伍，再投影客户端能读取的设置通知。它只建立后续三类模式的可靠底座，不宣称任何一类
模式的副本玩法已经完成。

## Scope

包含设置模型、规则服务、`0x000C` codec/handler/Command、队伍创建或设置更新、通知投影、并发与会话
代际保护、默认 Normal 修正、自动化回归和协议资料。Story/Cycle/Normal 的目标含义、进入规则、任务
共享、奖励、匹配/P2P 与副本战斗均留给后续规格。

## Definitions and Evidence Boundary

- `PartyCategory` 的当前 A21 wire 映射为 `Story=0`、`Cycle=1`、`Normal=2`；任何其他值非法。
- 规范化信息块长度为 12 字节。`[1]` 是客户端队伍 UI 的回归玩家/赛丽亚祝福图标开关；当前产品明确
  不实现该玩法，因此服务端兼容接收任意输入但在领域保存前强制为 `0`。`[9]` 是类别，`[10..11]` 是
  按类别解释的 little-endian `u16` `ModeTargetRaw`；其余未解释字段必须无损保留。
- 候选 create 形状是直接 12 字节；候选 edit 形状是 2 个前导设置字节、little-endian `i32`
  raw-dstr 长度、该长度的原始标题字节、10 个尾部设置字节。实现接受它们的前提是当前 A21 构包/样本
  与消费路径证明该布局；若证据冲突，必须在实现前修订 Spec 或回到根控制器，不能“兼容两套猜法”。
- `ClientVerified` 只授予能由当前帧样本、发送/读取记录和客户端结果归因的消息；上游源码和静态反编译
  分别只能提供代码事实与高置信协议证据。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 队伍快照必须持有不可变、类型化的 12 字节设置；已知类别/目标/回归玩家标志可读取，除 `[1]` 的明确归一化外未知字段可无损往返，调用者不能修改已发布快照。 |
| RQ-002 | 新队伍默认设置必须是 `Normal`，容量与现有 1..4 人不变量一致；修正默认类别不得改变当前邀请、名册或离队的其他 wire 字节。 |
| RQ-003 | 一个队伍模式规则服务必须成为设置合法性、默认值、`[1]=0` 归一化和共享变更规则的唯一业务来源；协议层不得复制这些规则。 |
| RQ-004 | `0x000C` decoder 只接受已被当前 A21 证据确认的 create/edit 精确形状，并拒绝负长度、溢出、截断、尾随、非法类别、非法 UTF-8/原始标题边界以及不一致字段。 |
| RQ-005 | 当前选中角色在无队时可通过合法 create 请求创建以自己为队长的单人队并应用设置；已有队伍时请求只修改同一队伍，不隐式换队。 |
| RQ-006 | 只有当前代际的队长可修改设置；无队、非队长、旧会话、非法容量、容量小于当前成员数或规则拒绝时，队伍、邀请和通知状态完全不变。 |
| RQ-007 | 设置创建/更新与 revision 推进必须在同一领域原子边界内完成；并发更新具有确定顺序，迟到旧结果不得覆盖后来状态。 |
| RQ-008 | 新建成功投影当前 A21 要求的完整队伍状态；既有队伍更新成功向更新时仍属于该代际的成员投影 `NOTI 0x0009 type=1`，两者都必须携带归一化后的 `[1]=0`；通知在领域锁外发送并以不可变结果为依据。 |
| RQ-009 | 任何协议错误响应、队名回落、标题编码或 type-1 body 细节都必须由当前 A21 的构包/解析/运行时证据决定，不复制上游未经验证的选择。 |
| RQ-010 | 现有组队功能、分层规则和协议资料不得回退；本结果必须明确列出留给 Normal/Story/Cycle 后继规格的未知项。 |

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001, RQ-002 | 给定默认建队或任意合法 12 字节设置，值对象自身可 byte-exact 往返；领域接受后 `[1]` 恒为 `0` 且其他 11 字节不变；未知类别被拒绝；默认 `[9]` 为 `2`，除预期类别修正外既有完整名册向量不变。 |
| AC-002 | RQ-003 | 规则服务测试覆盖默认设置、三个已知类别、未知类别、容量 1..4、容量低于成员数、`[1]=0` 归一化与其余未解释字节保留；生产搜索/架构测试证明 handler/Command 不另写同一判断且 Application 无 Infrastructure 引用。 |
| AC-003 | RQ-004 | 对每个被确认形状至少有一个真实样本或当前客户端构包证据和 byte-exact GREEN；对每个长度/编码/类别边界有拒绝测试，decoder 不读越界、不接受尾随且不产生部分请求。 |
| AC-004 | RQ-005 | Given 当前会话无队，When 合法 create，Then 只创建一支以请求者为队长的一人队并保存规范设置；Given 已在队，Then 保持 party identity，仅走设置更新。 |
| AC-005 | RQ-006 | 非队长、已替换会话、容量非法/过小、规则拒绝与同角色竞态逐项返回确定失败；前后 snapshot/revision、邀请和已发布通知完全相同。 |
| AC-006 | RQ-007 | 两个同时设置请求在账户/队伍 gate 下串行化；每个成功结果 revision 单调增加，发送较晚启动但来自旧 revision 的投影被丢弃。 |
| AC-007 | RQ-008 | 新建成功的消息集合、顺序和 audience 与客户端读取契约一致，设置 `[1]=0`；更新成功对每个仍为当前成员的连接只形成一份同 snapshot、`[1]=0` 的 type-1 设置通知，离队/换代接收者不收旧设置。 |
| AC-008 | RQ-009 | type-1 encoder 有字节向量固定 block count、party id、type、标题分支、12 字节规范设置和尾部边界；协议错误/成功响应仅在对应客户端 handler 或实帧证据存在时实现并记录。 |
| AC-009 | RQ-010 | Party、Protocol 和生命周期聚焦测试通过；全量适用测试逐条无 Failed/Other；Release solution build 为 0 warning/error，Application 分层断言通过。 |
| AC-010 | RQ-010 | `0x000C`、`NOTI 0x0009`、index、catalog、样本/trace 互相一致，分别标记 Confirmed/High/Hypothesis/Implemented/ClientVerified，并有清晰 Successor Guidance。 |

## Success Evidence

- `EV-001`（AC-003/AC-008）：上游 `origin/master` 定位记录、当前 A21 构包/解析反编译、真实 C2S/S2C
  样本或等价逐帧记录，三者明确区分。
- `EV-002`（AC-001..AC-008）：模型、规则、codec、Command/领域、并发/代际与通知的 RED/GREEN 记录；
  最终测试必须逐条解析结果，不能只引用进程 exit code。
- `EV-003`（AC-007/AC-010）：最小当前 A21 create/edit UI 流程和可归因的帧记录；若当前客户端操作
  必须由用户完成，本子规格在证据到位前保持未完成而不伪造结论。
- `EV-004`（AC-009）：新鲜 Release build、聚焦回归、全量适用测试和 `git diff --check`。
- `EV-005`（AC-010）：独立完整结果审查，确认没有提前实现或声称三种模式特有语义。
