# Routing Decision

- TaskContract: `./TaskContract.md`
- Contract revision: `1`

## SDD Readiness

目标、顺序、范围和证据边界已经稳定：先建立保守而精确的共享规则与 `0x000C` 闭环，再按
Normal、Story、Cycle 逐类补齐，最后用全部证据复审建模。各阶段的具体客户端语义仍可在已授权范围内
通过逆向和抓包选择，但不会改变任务目标；每个根成功条件都有可观察证据。

## Structural Selection

- Selected workflow: `multi-spec-workflow`
- Rationale: 用户明确偏好高精度、分阶段收集证据并允许证据驱动的建模修正。若直接一次实现，最具体的
  失败路径是把上游的 12 字节原样存储误当成三类模式的共同业务语义，后续客户端证据出现时既难区分
  哪些结果已验收，也容易让未确认规则污染已稳定的普通组队。持久化的逐规格验收、单一接受基线和最终
  整体审查能直接降低这个风险，且该任务跨越初始模型、三个可独立验收的模式结果和最终建模决策，新增
  控制成本相对于预期返工是值得的。选择 Multi Spec 是因为初始能力、Normal、Story、Cycle 和最终审计
  均有独立的证据、接受与回退边界；它们应串行积累，而不是由一个不可分割的 Spec 一次接受。
- Reroute conditions: 若客户端证据证明三类并非独立规则边界、类别映射本身错误，或第一个子规格无法在
  不预先决定后续模式语义的情况下建立稳定共享模型，则回到根评估并收窄/重排后续结果；若任务不再有
  两个以上独立可接受结果，则重新评估 Single Spec。任何超出契约范围的副本玩法或外部系统变更先停下
  获取新授权。
