# TaskContract: A21 三类队伍模式规则与业务闭环

## Context

### Source Request

用户确认按以下顺序推进：

> “先做一个高精度的初始版本规则服务和相关业务逻辑。然后再按类型解析每个不同组队的细节实现。
> 最后当全部信息收集完毕后再看一次建模是否正确，决定重构。”

并补充决策边界：

> “大部分情况下是没有尖锐的矛盾，通过局部妥协就能写完……中间有强烈信号证实了架构设计是不合理的
> 时候，就要……直接做重构再继续开发。”

用户随后授权执行：

> “ok，那可以先把现在的工作分支合并，工作区清理都做完后开新的任务契约。我们开始工作吧。
> 这个任务契约和确定性的不同，你可以有更高的自由度来选择工作方式。任务契约中的持久化文件只是
> 记录工作工过程的载体而非传统流程的限制。”

### Current Situation

`town-party-lifecycle` 已把当前 A21 城镇邀请、接受、名册、实时状态、详情查询和离队生命周期纳入
`main`。现有队伍通知只投影默认 12 字节设置块；C2S `0x000C SET_PARTY_INFO` 尚无 JP-86
decoder/handler，剧情、循环、普通三类队伍也没有各自的领域规则。

上游只提供可参考的 12 字节存储、创建/编辑形状、队长与容量校验以及 type-1 设置广播，并未解释三类
模式的完整业务语义。客户端静态证据指出设置块中的类别与目标字段会随模式改变解释，但这些语义仍需
按“先上游、再客户端、最后真实运行时”逐类闭合，不能从上游的原样复制行为直接推定。

## Goal

建立一个对未知信息保持保守、对已确认规则表达精确的队伍模式规则边界；在不破坏现有城镇组队生命周期
的前提下，依次完成普通、剧情、循环三类队伍的 A21 协议、领域行为和客户端可观察闭环，并在全部模式
证据汇总后重新审视模型，必要时完成有证据支持的聚焦重构。

## Scope

### In

- 建立三类队伍共享的类型化设置模型、规则服务和相关业务边界；默认行为必须兼容当前普通队伍。
- 重建 C2S `0x000C` 的 A21 创建/编辑输入、校验、状态变更与对应队伍设置通知，并保持畸形或越权输入
  不污染现有队伍状态。
- 按 `普通（Normal）→ 剧情（Story）→ 循环（Cycle）` 的顺序，分别研究上游与客户端，补齐每类模式
  真正不同的字段含义、有效目标、编辑约束、进入/返回/离队等与队伍模式直接相关的行为。
- 为每类模式同步协议资料、来源、置信度和运行时证据边界，并提供自动化回归与当前 A21 客户端可观察验收。
- 全部三类完成后执行一次整体建模审计；通常允许局部兼容收敛，若中途出现会导致错误所有权、错误状态
  转移或无法表达后续模式的强证据，则先做最小充分重构再继续。
- 保持现有组队邀请、接受、名册、实时状态、角色详情、主动离队与会话清理行为不回退。

### Out

- 与队伍模式无直接证据关系的副本战斗模拟、掉落、奖励、P2P/UDP 中继实现。
- 仅凭名称或上游原样字节推测并实现未被 A21 客户端或运行时证据支持的玩法语义。
- 把协议实现状态升级为 `ClientVerified` 而没有能归因到对应消息和行为的当前客户端证据。
- 本任务结果的 merge、push、PR、发布或任务 worktree 清理。

## Constraints

- 研究顺序固定为上游行为基线在先、A21 客户端解析/构包在后；发生冲突时，以当前 A21 客户端与真实
  抓包/运行时证据为准，并保留冲突记录。
- Package handler 只负责调用 Command 实施业务、调用 Event/Notification 实施通知；Command 通过领域
  实例和领域服务完成行为；队伍模式规则由规则服务提供，Application 不得引用 Infrastructure。
- 初始规则服务只能表达已确认的共享不变量和默认普通模式，不用占位规则假装剧情/循环已经实现。
- 每个模式允许采用局部适配来保留稳定模型；只有强证据证明当前抽象产生错误所有权、错误原子边界、
  无法表达已确认差异或迫使多个路径复制互相矛盾的规则时，才在中途触发聚焦重构。
- 未完成真实抓包或客户端可归因验收的结论必须标注为 `Implemented`、`High` 或 `Hypothesis`，不得混同
  `ClientVerified`。

| SC-1 | 初始模型能类型化表示三类队伍、共享设置与未知/无效输入，默认普通队伍行为与当前主分支一致。 | 模型/规则服务测试覆盖默认值、类别边界、无效组合和现有普通组队回归；Release build 通过。 |
| SC-2 | `0x000C` 的已确认 A21 创建与编辑形状被严格解析；截断、尾随、非法类别、非队长、旧会话和容量冲突均被拒绝且不改变状态。 | 字节级 codec 测试、handler/Command/领域状态前后对照测试，以及真实 C2S 样本或等价当前客户端构包证据。 |

| SC-7 | 三类模式与现有邀请、接受、名册、实时状态、详情、离队和会话清理组合后没有回归。 | 全量适用测试逐条为 Passed；至少覆盖每类设置下的建队、成员变化和清理路径；Release build 0 warning/error。 |

| SC-9 | 最终建模审计能解释哪些差异由共享模型吸收、哪些由模式规则隔离，并对是否重构给出证据化结论。 | 完整结果审查记录：若模型仍合适，说明已检验的反例与不重构理由；若强信号成立，提交聚焦重构及等价回归证据。 |

## Assumptions

- 当前客户端静态结论 `0=剧情、1=循环、2=普通` 与 12 字节设置块是高置信起点，但在获得可归因的
  当前 A21 运行时样本前不视为全部 `ClientVerified`。
- 需要 UI 操作的实机验收由用户配合完成；等待用户操作时不把纯等待动作作为执行任务循环。
