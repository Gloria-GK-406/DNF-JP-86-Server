# spec-003 完整变更评审

两轮，都由独立的评审子代理执行，均为只读。

## 第一轮

**一条影响效力的程序问题：审阅期间工作树在被改动。** 评审取快照之后我又落了两处大改
（子类型 0 的 64 字节定长尾、子类型 1 的固定 dimension 卷），所以那一轮的「完整变更」判定
本身不成立。这是我的排程错误，不是评审的问题：完整变更评审要在实现停下之后才有意义。
第二轮是在冻结的树上做的。

阻断级三条，全部处理：

| # | 发现 | 处置 |
|---|---|---|
| 1 | 重写金值基线时写了一句可证伪的断言：「帧字节变化**只因**条目 84→101」。实际 `PopulatedCount` 还把条目偏移 26 与 58 的两个计数字节从 2/3 变成了 0 | 注释改写为两个原因都点名，并说明下面那处 span 比较证明的是「增量与快照仍以同一方式编码条目」，不是「前面的字段没变」 |
| 2 | `CharacterRosterService.cs` 有一个游离 CR，导致 git 把 12 行改动记成 389 行整文件重写，且提交后换行会翻成 CRLF | 已归一化，diff 回到 19 行 |
| 3 | `catalog.md` 的 `0x000E` 行仍写「只发空表」，且整份 catalog 没有反映本轮结论 | 三行状态更新，并在「阶段与 A21」下新增一节记录两条被推翻的旧归类及其原因 |

证据与可追溯性四条，全部处理：判据字节已归档为
[a21-reference-entry-bytes-20260825](../../../../protocol/patterns/data/traces/a21-reference-entry-bytes-20260825.md)（仅第 56..200 帧，
不含登录握手，无凭据）；仓内已有的 `a21-world-entry-20260823.log` `[S]` 节被引用；
实机记录被 `world-entry.md` 链接；`NOTI-0x0002.md` 那份过期的残差分析整节替换。

范围一条：`GAME_OPTION` 在契约里是 Out，例外条件是「有证据表明其布局也变了」。
客户端自己回写的 `CMD 0x00C5` body 是 154 = 4 + 150——它那张表就是 75 项，例外成立。
原因记进 catalog。

## 第二轮（冻结态）

十一条，其中一条高、一条中高：

| # | 发现 | 处置 |
|---|---|---|
| F1 | **实机证据取自改动前的构建**：记录里子类型 0 是 184、子类型 1 是 173，而冻结态只能产出 167 / 330。字节量最大的两处改动从未被真实客户端跑过 | 在最终构建上重跑实机，见验证记录 |
| F2 | `a21-entry-batch-diff-20260825.md` 同样过期（172/173，并写着「尾部仍未对齐」），而引用它的页面与测试引的是它没有的数字 | 在最终构建上重新采样并整页刷新 |
| F3 | 子类型 `0x02` 被判成纯数据差异，但 `Docs/ProtocolScaffoldDissonances.md` 第七节已记录一处非数据分歧，且明写它属于本成果范围 | 入场路径改为与角色列表界面写同样的实测字面量；两处共用常量；补一条测试把两者钉在一起 |

| F9 | `NoCreatureLabel` 上叠了两组文档注释，其中一组描述的是方法 | 已拆回各自的成员 |
