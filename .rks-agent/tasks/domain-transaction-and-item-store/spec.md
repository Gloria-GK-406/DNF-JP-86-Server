# Specification: 领域事务与物品存储抽象

## Why and Outcome

今天在这套代码上写一段物品业务，必须同时知道两件本不该知道的事：数据落在哪里，以及自己要不要为一致性负责。持久化没有真正被抽象——领域用的是存储的坐标系（物品以数据库行号寻址，以致一个永不落库的内存容器必须自行发号伪造主键），而存储反过来承载着业务规则（今天是否已领取、加到现有堆还是新开一格、道具属于哪一段槽位）。一致性也没有归属：每个仓储各开各的连接与事务，一次用例跨两处改动就没有共同的边界，"要么全做要么全不做"无处表达。

这次改完之后，写业务的人写下"从这里拿走、放到那里"，得到的就是"要么都成、要么都不成"，而不需要知道这两处各自落在内存还是数据库。对玩家而言什么都没有发生：道具移动与道具使用的帧字节与时序一字不变。

## Task Perspective

- Core outcome: 在这套接缝上写业务的人不再感知持久化——一次用例内的多处物品改动全部生效或全部不生效，该保证由用例边界统一提供；业务代码中不出现事务操作，也不因数据落在内存还是数据库而分支。
- Necessary support: 保证的边界必须是明示的而非巧合成立的——一次事务中提交阶段仍可能失败的参与者最多一个，出现第二个时以失败暴露；在事务之外改动持久物品状态同样以失败暴露。授权来自实测确认的同类缺陷：现用的数据库客户端在环境事务下既不参与也不报错，静默的非原子写入不可检测。
- Peripheral assurance: 帧字节比对、全套自动化测试、实机走查，以及一份可逐条核对的既有耦合构造消失清单。

## Scope and Non-Goals

### In Scope

- 一次用例内物品改动的原子性，及其在用例边界上的归属。
- 物品持久化机制的归拢：机制集中于单一抽象之后，业务规则不再夹带其中。
- 领域词汇中数据库行标识的消除。
- 道具移动与道具使用两条协议在该保证之下运行。
- 每日刷新与教学奖励中业务规则的归属改变，其对外可观察行为不变。

### Non-Goals

- 背包坐标系统的重构：协议槽位映射、按类型划分背包、快捷栏成为独立容器。
- 数据库结构定义的集中化与既有补列逻辑的清理。因此本次新增的持久化机制不建立任何新的数据表，只使用既有已建立的表。
- 角色归属校验的上提与其多份实现语义不一致的修正。
- 物品之外的其他持久化路径与其余命令的执行方式。
- 入场时一次性下发的背包快照改由容器供给。
- 跨两个及以上持久存储的原子性。

## Constraints

- 对外可观察行为一字不变：道具移动与道具使用的帧字节与时序保持原样；每日刷新与教学奖励对客户端的可观察结果保持原样。
- 既有测试语义不得修改，只允许因类型或依赖变化做机械调整。
- 事务提交失败不向客户端回任何提示。业务拒绝不是失败，仍按既有的类型化拒绝原因回帧。
- 本次新增的持久化机制不建立任何新的数据表。

## Definitions

| Term | Meaning |
|---|---|
| 用例边界 | 一次外部请求所触发的、有始有终的业务处理单元。物品原子性的保证以它为单位成立 |
| 参与者 | 在一次用例中被改动、并需要与其他被改动者共同成败的状态持有者 |
| 持久参与者 | 其改动在进程结束后仍然存在的参与者，且其最终写入本身仍可能失败 |
| 仅存内存的参与者 | 其改动不跨越进程存活的参与者。它的最终写入不具备失败的可能 |
| 消失清单 | 一组具名的既有构造。它们在结果中不复存在，是本 Spec 结构目标的可核对形式 |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 一次用例内对物品的多处改动是全有或全无：用例正常结束时全部可见，用例在改动之后失败时一处也不可见，无论这些改动落在持久存储还是仅在内存 |
| RQ-002 | 业务代码不表达事务：道具移动与道具使用在不书写任何开启、提交、回滚或事务对象的前提下获得 RQ-001 的保证 |
| RQ-003 | 业务代码不因载体分支：同一段物品操作逻辑作用于持久容器与仅存内存的容器时走同一条路径，除持久性本身外可观察结果相同 |
| RQ-004 | 一次用例中提交阶段仍可能失败的参与者最多一个；出现第二个此类参与者时以失败暴露，不降级为非原子 |
| RQ-005 | 在用例边界之外改动持久物品状态以失败暴露，不静默完成 |
| RQ-006 | 物品的持久化机制中不含业务规则：今天是否已领取、加到现有堆还是新开一格、道具属于哪一段槽位，均不由持久化机制决定，且可在不涉及数据库的情况下被检验 |
| RQ-007 | 领域词汇中不出现数据库行标识：领域侧的物品寻址与效果描述均不携带存储行号，仅存内存的容器无需发号任何伪造标识 |
| RQ-008 | 持久化机制不理解复合的物品操作：移动、交换、合并、拆堆由领域以基本读写组合表达，持久化机制不接受任何描述「移动」的输入 |
| RQ-009 | 道具移动与道具使用的帧字节与时序、以及每日刷新与教学奖励对客户端的可观察结果，与改动前逐字一致 |
| RQ-010 | 本范围内的每一种物品操作——移动、交换、合并、拆堆、消耗——均以「容器与槽」寻址表达；若某一种无法如此表达，该事实被记录，且不引入替代的实例身份 |
| RQ-011 | 移动的对外拒绝原因集合只在一种情形下发生变化：`SlotsChanged` 在被证明不可达时不再出现。其余拒绝原因、其触发条件与所选提示码均保持不变；若 `SlotsChanged` 仍可达，则该拒绝路径保留 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 一次用例要在两处改动物品，其中一处持久、一处仅存内存 | 用例正常结束 | 两处改动都可见 |
| AC-002 | RQ-001 | 同 AC-001 的起点 | 用例在两处改动之后、结束之前失败 | 两处都不可见，持久侧与内存侧皆然 |
| AC-003 | RQ-002 | 道具移动与道具使用的业务逻辑 | 检查其表述 | 其中不出现开启、提交、回滚或事务对象，而 AC-001 与 AC-002 仍然成立 |
| AC-004 | RQ-003 | 同一段物品移动逻辑 | 分别作用于持久容器与仅存内存的容器 | 两次执行走同一条路径，可观察结果相同 |
| AC-005 | RQ-004 | 一次用例中已有一个提交阶段可能失败的参与者 | 第二个同类参与者加入同一次用例 | 该次用例失败，且失败可被观察 |
| AC-006 | RQ-005 | 不存在进行中的用例边界 | 改动持久容器中的物品 | 操作失败，且失败可被观察 |
| AC-007 | RQ-006 | 每日刷新与教学奖励的既有可观察行为 | 判定规则不再由持久化机制决定 | 这些行为不变，且这些判定可在不涉及数据库的情况下被检验 |
| AC-008 | RQ-007 | 一个仅存内存的容器 | 放入物品并对其执行本范围内的各种操作 | 全程不需要任何存储行标识，且领域侧的效果描述中不携带行标识 |
| AC-009 | RQ-008 | 一次交换、一次合并、一次拆堆 | 由领域以基本读写组合表达 | 结果与改动前一致，且持久化机制不接受描述「移动」的输入 |
| AC-010 | RQ-009 | 一组既有的道具移动与道具使用请求 | 在改动前后分别处理 | 两次产生的帧字节逐字一致 |
| AC-011 | RQ-009 | 每日刷新与教学奖励的既有覆盖 | 在改动后重新执行 | 结果与改动前一致 |
| AC-012 | RQ-010 | 移动、交换、合并、拆堆、消耗五种操作 | 逐一以「容器与槽」寻址表达 | 五种均可如此表达；若有一种不可，该事实被记录且未引入替代的实例身份 |
| AC-013 | RQ-011 | 读与写进入同一用例边界、且用例被串行化 | 检查 `SlotsChanged` 是否仍可触发 | 不可触发时该拒绝原因不再对外出现，其余拒绝原因不变；仍可触发时该路径保留并记录 |

## Assumptions

- 「容器与槽」足以表达本范围内的全部物品操作，附魔与随机属性随物品核心一同移动而不需要额外的实例身份。该前提已按现有五种操作核对，但未被穷尽证明；RQ-010 是它的可观察处置。
- 每日刷新与教学奖励的现有覆盖足以证明规则归属改变前后行为等价。若覆盖不足，须先补齐覆盖再改变归属。
- 本范围内只存在一个持久参与者，因此跨持久存储的情形不会被触发。
- `SlotsChanged` 在读与写进入同一用例边界、且用例被串行化之后不可达。该判断是消失清单收录它的依据；RQ-011 是它的可观察处置。
