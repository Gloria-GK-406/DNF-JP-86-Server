# Spec Result — 翻牌奖励按线上真实结构重做

## 结局

`completed`。独立评审 `approved`，验证 `pass`（七条成功条件全部有当前证据）。

## 交付了什么

翻牌的**协议编码层**按线上真实结构重写。规则层一个值没动。

- **结算通知 `NOTI 0x0023`** 的卡尾按三行 × 八列写：组 0 是普通牌行、组 1 是黄金牌行、
  组 2 是黑砖牌行。本局奖励落在普通行第 0 列，该列声明两条条目 —— 第 0 条是这张牌的金币
  （其物品标识客户端不读），第 1 条是装备。黄金行与黑砖行声明为空。帧长不再是常数：
  空牌面 274，带一件装备 282。
- **翻牌应答 `CMD 0x0047`** 改成整块面板的状态快照：八条记录，每条说这一列的普通牌与黄金牌
  各被哪个座位翻开，**一件东西都不带**（33 字节）。牌面内容全部由结算通知提供。
  `SelectCardResponse` 因此从 `(Kind, Slots)` 变成 `(Kind, TurnedColumn)`。
- **只发牌面的第 0 位**。客户端从不上报点了哪张牌，认领也永远取第 0 位，所以把四个牌位铺到
  四列上等于声明三份没有任何玩家能拿到的奖励。

## 这一轮真正的成果不是那两个编码器

上一个 Spec 交付的翻牌在真实客户端上一律显示 NONE，而它的 1964 条判据全绿、评审通过、验证通过。
原因是**判据断言的是「编码器写了哪些字节」** —— 在那个层次上判据和实现是同一枚硬币的两面。

本次新增 `CardPanelFrameReader`：按客户端的读法把帧走一遍（消费五个计数、由计数决定后续位置、
走不到帧尾就拒绝），所有牌面语义的断言建立在它的输出上。代码里不再有一个指向卡尾的字节偏移常量。

**八个变异全部报红**，包含上一轮那两个真实缺陷（装备写进金币条目、奖励写进黄金行）。
独立评审者另行复核四个，其中一个刻意「同步改长度函数使编码器内部自洽」，仍由纯解码断言抓到 ——
那正是上一轮失守的那族错误。

## 沉淀到协议记载

三页人工区按十四轮实机与客户端反汇编重写，删掉全部被推翻的说法：

- `protocol/game/server-to-client/NOTI-0x0023.md` —— 三组 = 三行、slot = 列、条目 0 金币 /
  条目 1 装备 / 第 2 条起不上屏、帧长公式 `210 + 8N + 8E`（五个不同长度的帧同时闭合）
- `protocol/game/client-to-server/0x0047.md` —— 记录序号 = 列、`a`/`b` 是座位号不是布尔、
  `0x21EF990` 的逐条伪代码、开牌有本地与同步两条路、本帧可由服务端主动推
- `protocol/game/server-to-client/NOTI-0x0043.md` —— `CARD_SELECT_COMPLETE_STATE` 在本客户端
  是 104 个 type 共用的占位实现；顺带给普查表加了「有 handler ≠ 实现了」的通用提醒

## 未查明与具名假设

- **座位号在组队时是否等于自己的队伍座位号未验**。单人实测那个运行时值为 0；写死 `0x00`
  只对单人正确，组队会把每个人的翻牌都算到收件人头上。这一格集中在
  `CardRewardPayloadCodec.OwnSeat` 一处，日后改一个地方即可。
- 每张牌 1 金币仍是本服务器自定的占位值。
- `kind 3 / kind 4`（应答落地的两个 kind）由哪条路径绘制没有追到 —— 本服务器不再往那里写东西。

## 已知的后续事项（不在本 Spec）

1. **翻牌金币应当是「底薪」**：一定给，且随副本等级、击杀数、难度浮动。档案里有料 ——
   `[gold drop ref table]` 每级的基数与第三列的 ±13% 波动、
   `[dungeon difficulty gold drop bonusrate]` 的五个难度倍率。这会推翻上一个 Spec 记的
   「档案说翻牌不出金币」。**本仓目前完全没有按局的击杀计数**，该 Spec 需先新增这项运行时状态。
2. 规则服务一次摇四个位置而只有第 0 位能送达，三次投掷是白摇的 —— 规则层清理。
3. 免费行七个未用列写 `c = 1`（照抄参照服务端），使客户端的「翻完」判定永远不成立；
   参照服务端同性质，实机未暴露。
4. 付费（黄金）牌与黑砖牌的送达路径未实现，帧上写空。
5. 仓库根目录三个 0 字节垃圾文件（`上游源码**。` / `档案` / `社区文档`），早于本课题。
