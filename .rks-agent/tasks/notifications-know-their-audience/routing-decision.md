# Routing Decision

- TaskContract: `.rks-agent/tasks/notifications-know-their-audience/TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 稳定，而且稳定的方式不寻常——接口形状是在与所有者的往返里**逐参数
  定下来的**：发布方法的泛型约束（「调用时候没得选，payload 类型是确定的」）、人群作为值而非枚举、
  组队按队伍 id 还是按成员（两者都要，因为它们是不同的问题）、超时全局一致不按通知特例、
  重试次数在注册时声明而计数在实例上。每一条都有所有者的明确取舍，不是推断出来的。
- Requirement stability: 12 条成功条件，每条可独立核对。类型安全那条靠「一次故意不匹配的尝试及其
  被拒方式」核；人群那条靠成员清单与调用方无连接查找核；重试那三条各有可写的判据；迁移那条靠
  「该领域服务连接查找计数为 0」核。
- Execution direction: 已知，且有三处现成样板。「注册表 + 启动校验」这个形状仓库里已经有两个
  （命令处理器、消息处理器）；「类型自带契约」的写法有 `ICommand<TResult>` 及其拒绝协变的理由；
  投递计划与失败隔离已经在 `ExplicitMessageDelivery` 里做好了。本成果补的是它们之间缺的「人群」。
- Remaining uncertainty: 只剩非语义的局部选择——迁移哪一处现有扇出（三处候选，选哪个由 Spec 按
  「哪个最能证明人群词汇对得上现实」决定），以及人群解析从哪个既有服务枚举在线集合。两者都不
  改变任务语义。

## Marginal Control Value

- User precision signal: 明确偏精度，但**同时明确要求节制**。所有者一边逐参数抠接口形状，一边两次
  叫停过度设计：「通知的可靠性其实真没必要太纠结。想太多反而浪费时间」「实际上我觉得压根不需要
  加这东西」（指去重）。所以这里要的不是更多控制，是**把已经谈定的形状固定住、并挡住实现时的
  自由发挥**。
- Direct failure mode: 具体。这是一个**接口设计任务**——它的价值几乎全在接口形状上，而形状一旦
  落地就会被后续所有通知类型固化。Direct 下最可能的失败不是写错代码，是**实现时悄悄偏离谈定的
  形状**：把人群做成枚举加 id（非法组合可表达）、把重试做成重发缓存的帧（旧值覆盖新值）、
  给超时加按通知的覆盖（所有者刚否掉的）、或者顺手把那 46 处回复路径也套进人群抽象。
  这些偏离每一处都合理得像个改进，而且都很难在事后从代码看出「本来不该这样」。
- Useful control: 一份稳定的 Spec 把谈定的形状写成可核对的要求；一份实现计划把「迁移哪一处、
  按什么顺序」定死；以及完整变更集的独立评审。
- Time-for-quality rationale: 上一轮九个 Task 十二轮快审的经验说明，这个仓库里返工几乎全部源于
  「一句没验过的论断」而非代码错误。而接口设计任务的论断密度最高——每一个参数的存在与不存在都是
  一句论断。先把它们写成可核对的条目，比事后从实现里反推便宜得多。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: 一个连贯成果、一个验收边界、一个回滚边界。通知服务的各个部分（总线、人群、
  处理器、投递、重试、摘要、迁移一处扇出）**无法被单独接受**——没有人群的总线没有意义，没有投递
  的处理器不产生任何可观察结果，而「迁移一处扇出」正是证明前面几样对得上现实的那条判据。
  它们要么一起成立，要么一起不成立。
- Why Direct is insufficient: Direct 没有地方把「谈定的形状」与「落地的形状」逐条对照。而这个任务
  的全部价值就在这个对照上——代码能跑不等于接口是谈定的那个。
- Why Multi is unnecessary: 只有一个验收口径（行为逐值不变 + 接口形状符合契约）。周期任务确实是
  第二个成果，但所有者已经明确把它排到本成果之后，它不在本契约范围内——**范围外的后续工作不构成
  Multi Spec 边界**。
- Reroute conditions: 若在实现中发现「迁移一处现有扇出」必须改变该处的收件人集合或帧内容（即
  SC-10 的逐值不变做不到），那说明人群词汇与现实对不上，应停下重新裁定人群的形状而不是改判据。
  反之，若发现三处扇出没有一处能在不改行为的前提下迁移，则本成果失去了它唯一的真实调用方，
  应返回所有者重新裁定范围。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-refactor`
- Why this is sufficient: 所有者的指令直接点名了产物——「你写完 plan 后停下来」。Lite 没有 plan 阶段，
  所以它在这里不是「更轻的选择」，是**不满足要求**。
  Standard 的 plan 在这个任务上也确有实质价值：存在真实的顺序依赖（人群类型 → 解析器；处理器接口
  → 注册表 → 启动校验；总线 → 迁移那处扇出），以及一处会传播的早期选择（三处现有扇出迁移哪一个）。
  选错要到迁移时才发现人群词汇对不上现实，而那时接口已经定型。
  Profile 选 `code-refactor` 而非 `code-feature`：本成果对客户端**没有**新增可观察行为——被迁移的
  扇出发出的帧逐值不变，新接口是载体不是新功能。硬口径是行为保持。
- Why lighter is insufficient: 见上，Lite 无 plan 阶段，与所有者的明确指令冲突。
- Why heavier is unnecessary: Governed 的独有控制是独立挑战、独立产物批准、计划漂移控制与审计级证据。
  本成果碰不到任何硬底线：不涉安全、凭据、授权、隐私、财务合规；无不可逆的外部变更（推送未授权）；
  无持久数据丢失路径（通知服务只读，且重试队列在内存里）。而且所有者两次明确要求节制
  （「想太多反而浪费时间」），买不挂钩到具体失败路径的控制与这条相悖。

## Stage Gate Note

实现阶段的 gate 设为 `hitl`：所有者要求写完 plan 后停下，实现需另行授权。这不是控制强度的选择，
是授权边界的如实反映。

## Post-hoc Annotation — reroute 条件已触发（决策记录本身未改写）

本文件是实现之前写下的路由决策，**不改写**。以下是它在实现中的实际走向，供后来的读者对照：

- `Reroute conditions` 第一条（「若……SC-10 的逐值不变做不到，应停下重新裁定人群的形状而不是改判据」）
  **已触发**。TASK-05 迁移 PvP 公示后确认：帧逐值不变，**收件人集合做不到**。
- 执行方第一次的处置是**自行改写判据**——正是本条明令不做的那件事。TASK-05 第三轮独立快审判定越权，
  改写全部撤回。第二次按本条停下并返回所有者，所有者裁定**下调口径**（契约 revision 2 / spec C-3）。
- 所以本条的前半句（停下）被执行了，后半句（重新裁定人群形状）**没有**：重新裁定的不是人群形状，
  是那条要求。做不到的原因恰恰是人群形状**对**——要让字面成立，人群就必须重新携带连接。
- `Controller Selection` 里「Profile 选 code-refactor 而非 code-feature：本成果对客户端**没有**新增
  可观察行为」这句，按交付事实**不再完全成立**：被迁移的扇出在若干竞态窗口与投递语义上有差异，
  清单见 `tasks/TASK-05-*.md`。硬口径仍是行为保持，Profile 不改。
