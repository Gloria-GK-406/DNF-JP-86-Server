# Specification: 通知知道自己要告诉谁

## Why and Outcome

「把这件事告诉那群人」在这个服务器里被写了三遍，每遍都不一样。

三处的形状其实相同——领域侧算出「谁 + 什么」，协议侧映射成帧，网络层投递——但没有一个地方叫这个
名字，所以每一处都自己处理人群、内容和失败隔离，也各自出错。

网络层已经把最难的一半做好了：投递计划区分「必须送到的直连方」与「尽力而为的旁人」，并且已经有
失败隔离。**缺的只是「人群」这一层。**

缺这一层的代价已经露出来了：一个领域服务为了算出「通知谁」，被迫自己去查连接。它只想说「这几个
角色要被通知」，却因为没有别人能把角色变成连接，只好自己知道 socket 的存在。

这一轮补上那一层。做完之后，调用方说出人群与通知，剩下的事——把人群解析成收件人、逐个取得该收件人
的消息、投递、隔离失败、交回一份能核对的摘要——由一个地方负责。领域服务不再需要知道连接。

**这个机制的方向与既有路径相反。** 现有每一条路径都从一个连接开始，账号身份来自那个连接。通知从
服务器侧发起，目标是一群人。但方向反的只是**发起方**：业务仍然走命令，通知只负责投递。

## Task Perspective

- Core outcome: 调用方能说出「把这个通知发给这群人」，而不必知道这群人对应哪些连接、也不必自己
  处理失败。这是消费者要的东西——包括三处现有的手写扇出，以及将来任何需要主动告诉玩家什么的地方。
- Necessary support: 人群必须以角色表达而非连接，否则领域服务仍然要查连接，这一轮就白做了；
  通知类型与其处理器的对应必须在调用点或启动时被定死，否则「发错类型」会拖到运行时才发现；
  处理器必须只读，否则通知会去抢玩家自己操作的锁、并把上千个事务带进来。
- Peripheral assurance: 行为逐值不变的证据、注入面判据的复核、以及仓库约定的记载。
  **例外**：投递摘要不属于这一类——它是本 Spec 交付的一个受控结果，因为「这一轮覆盖了谁」这个问题
  没有别的方式能回答，而静默失败与安静成功在没有摘要时长得一模一样。

## Scope and Non-Goals

### In Scope

- 一个通知总线，其调用点的通知类型由实参推断
- 人群作为值，以角色表达；解析成连接由服务负责
- 每个通知类型的处理器，按收件人取得该收件人的消息，可对个别收件人弃权
- 处理器注册与启动校验
- 逐个投递、每收件人超时、失败隔离
- 失败重试：内存队列，重试时重新解析、重新取内容，达上限即丢弃
- 一份可核对的投递摘要
- 至少一处现有的手写扇出改经此服务，且其领域服务不再查连接
- 仓库约定里关于 `CMD ⇒ Notify` 的记载

### Non-Goals

- **周期触发。** 所有者要求先做通知、后做周期任务。本 Spec 不含调度器、时刻表或定时循环。
  重试队列的排空循环除外——那是本服务自己的一部分
- **发布订阅事件总线。** 业务用例直接调用通知服务。不引入「发布一件事、订阅者各自反应」的间接层，
  因为它会让「做 X 会发生什么」变成读代码回答不了的问题，而这个仓库前两轮做的正是消除这类间接
- **那 46 处「回给请求方」的既有发送。** 它们绝大多数没有旁人收件人，套上人群抽象等于为占绝对多数
  的情形加一层间接
- **频道、全服、组队三种人群。** 本仓今天没有它们的真实调用方，队伍这个概念根本还不存在。
  人群用封闭层级表达，将来加一种时编译器会强制所有解析处理它
- 节流或速率限制。这个规模不需要
- 通知去重。重试是重新取内容的，重复只会让同一个人多收一次，而那是本设计的既定前提
- 按通知覆盖超时值

## Constraints

- 通知处理器只读，不写任何状态
- 通知发生在业务事务提交之后
- 重试不缓存任何东西：重新解析角色的当前连接，重新向处理器取内容
- 超时值全局一致
- 服务器对客户端的可观察行为逐值不变，被迁移的那处扇出，其**帧**逐值不变；其**收件人集合与投递语义**的每一处差异都已逐条列出、每条可指到具体代码窗口（见 Corrections 的 C-3）
- 注入面判据的判定规则与具名豁免清单不得放宽或扩充

## Definitions

| Term | Meaning |
|---|---|
| 人群 | 一次通知的目标，以角色表达。它是一个值，不是一个查询结果——同一个人群值在不同时刻解析出的收件人可以不同 |
| 收件人 | 人群解析之后得到的一个具体目标：一个角色，以及它此刻所在的连接 |
| 弃权 | 处理器对某个收件人不产出任何消息。这不是失败，是「这个人不用告诉」 |
| 尽力而为 | 一次通知送不到不构成错误。玩家下次交互会看到正确状态，本设计以此为前提 |

## External Behavior and Data Rules

- 一次通知的内容由处理器按收件人产出。同一次通知发给不同的人，内容可以不同
- 收件人在解析之后、投递之前离线，是正常情况而非错误，且不进入重试
- 通知之间不保证顺序。重试会把失败项排到后面，本就无序可言
- 被迁移的那处扇出对客户端发出的帧，其内容与迁移前相同；顺序在**首轮投递内**与迁移前相同——被重试的收件人排到队尾，其帧晚于同批其他人到达（见 Corrections 的 C-3 与差异清单 D-4）

## Assumptions

- 判据命令必须带档案路径环境变量，否则读档案的判据会静默跳过而不是报红。基线的 2 个 skip 正是
  档案已加载的标志
- 既知偶发失败的判别依据是「异常类型 + 栈根 + 复跑即绿」，不是用例名
- 编码已经是每个收件人一次，所以「按收件人算内容」相对「统一内容」几乎不多花钱
- 投递今天是严格顺序进行的。本 Spec 用每收件人超时挡队头阻塞，不改成并发
- 网络层已有的投递计划区分必送与尽力，并已做失败隔离；本 Spec 在它之上补人群这一层，不重做投递
- ~~三处现有的手写扇出中至少有一处能在收件人集合与帧内容都不变的前提下迁移。若三处都做不到，
  本成果失去唯一的真实调用方，属于需要返回所有者重新裁定范围的情形~~
  **已被交付事实证伪**：PvP 公示迁移了，帧逐值不变，但收件人集合做不到——原因见 C-3。

## Corrections

原文保留在上，更正写在这里——改写原文会让「当初是这么想的」这件事消失。

### C-1：Non-Goals 里关于封闭层级的那句话比 C# 能给的强

原文（Non-Goals，「频道、全服、组队三种人群」一条）：

> 人群用封闭层级表达，将来加一种时编译器会强制所有解析处理它

TASK-01 落地时用编译探针验了，**这句话在 C# 里做不到**，有两处：

1. record 会生成 protected 复制构造函数。外部只要手上有一个 audience，就能借它派生出新形态：
   `internal sealed record X(NotificationAudience Source) : NotificationAudience(Source);` 编译通过。
   把复制构造函数私有化会得到 `error CS8878: 复制构造函数……必须是公共的或受保护的，因为该记录未密封`
   ——语言不允许。
2. 即便层级真的封闭，switch 对类层级也永不穷尽，所以新增形态不会让任何人的构建变红。

### C-2：RQ-003 的「非法的形态不可表达」也做不到，且反例正是它想挡的那一个

C-1 最初写的是「仍然成立的是 RQ-003 本身：形态是写死的那几个，『既是一组角色又带一个频道』这样的非法
组合造不出来」。TASK-01 的独立快审用一个只引用 `Dfo.Server.Abstractions` 的 scratch 工程编译验证，
**这句也是假的**：

```csharp
public sealed record CharactersAndAChannel(NotificationAudience Source, int ListenerPort)
    : NotificationAudience(Source);
```

编译通过，两半都能读回来——正好是那个反例本身。原因还是 C-1 的复制构造函数。

所以 RQ-003 字面上的「非法的形态不可表达」**在 C# 里做不到**，这个类型给的是比它弱的三条：

1. 下面列出的各个形态是彼此 sealed 的兄弟，一个 audience 不会同时是其中两个
2. 唯一能凭空造出 audience 的构造函数是私有的，所以**照常规写法**新增一个形态编译不过
3. 越过这两条造出来的东西，会走到解析器最后一个分支被**指名**

判据钉的是第 3 条，用的正是上面那个反例
（`NotificationAudienceTests.The_shape_that_should_not_exist_is_named_rather_than_resolving_to_nobody`）。
选封闭层级相对「枚举 + 一个 id」的收益因此也要说小一号：不是「非法组合不可表达」，而是
「非法组合不再是顺手就能写出来的那种值」。

**这条更正同时覆盖 AC-003**。它的 Then 列写的是「形态是封闭的；非法组合无法构造」，正是被推翻的那
句话的验收表述。照它的字面去核，会去找一件代码交付不了的事。按上面三条读它：可核的是「形态是那几个
嵌套兄弟」「凭空造不出来」「越过这两条的会被指名」。

### C-3：**这一条不是更正，是一份待所有者裁定的发现**

原文（RQ-014）：

> 被迁移的那处扇出，其收件人集合与发出的帧逐值不变

AC-014 是同一句的验收表述。TASK-05 落地后确认：**帧成立，收件人集合不成立。**

被迁移的那处扇出（PvP 大厅公示）迁移前寻址的是 `MarkReady` 当时记下的会话；迁移后寻址的是
「这个角色此刻所在的连接」。两者在稳态下同值，在三个竞态窗口里不同——全部是**会话已被顶替或
玩家已重连**的窗口，也就是旧代码把帧送到一个不再代表这个玩家的连接上的那些时刻
（那个连接当时还开着，所以旧行为是「送错」而不是「失败」）。

要让字面成立，人群里就必须携带那个记下的会话——**携带一个连接**。而 RQ-004 要的正是
「人群以角色表达、把角色解析成连接由通知服务完成」。**两者互斥。**

**这条下调经所有者裁定授权。** 过程记在这里，因为它本身是这一轮最该留下的东西：

我曾经**自行**改写过同样的内容。TASK-05 的第三轮独立快审判定那是越权——路由决策对这种情形写明的
动作是「停下重新裁定人群形状**而不是改判据**」，而契约的 Authorization 只覆盖到实现阶段。

> 被迁移的那处扇出，其**帧**逐值不变；其**收件人集合与投递语义**的每一处差异都已逐条列出、

差异清单在 `tasks/TASK-05-*.md` 的「CK-024 的差异清单」一节，共八条：

**这个口径的证伪面在哪里，要说清楚**：它由「清单完整」保证，而清单是被判定方自己写的，
CK-024 又是 Non-command。四轮里清单分别缺 3 / 2 / 1 / 1 条，每次都是**换一个独立上下文重读代码**
才发现的。所以这条成功条件今天真正靠的是独立评审，不是任何自动化判据——这一点必须写明，
否则「可证伪」三个字会被读成比实际更强的东西。
