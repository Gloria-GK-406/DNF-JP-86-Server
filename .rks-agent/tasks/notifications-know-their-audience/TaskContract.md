# TaskContract: 通知知道自己要告诉谁

## Context

### Source Request

所有者原话：「那个spec要先不做了。重新起一个新的任务契约和spec来做这次的任务。」——「这次的任务」
指的是在这一轮对话里与所有者逐项谈定的**通知服务**。

这个设计不是凭空来的。它是从「疲劳每日重置怎么触发」一路推出来的：先发现大多数周期状态用惰性期号
就够、不需要定时器；再发现真正需要的是「告诉此刻在线的人状态变了」；再发现这件事和周期触发是两个
机制；最后由所有者定下三者解耦的形状。所有者的原话：

> 「周期事件调用 cmd，然后委托通知发通知包。发包都归并到通知上。形成 cmd=>notify 的标准模式。」

以及关于范围的：「先做通知，再做周期任务。」

### Current Situation

基线 `b05d47e4`（`character-state-finds-its-owner` 已合并）。全量判据 2069 通过 / 2 跳过 / 0 失败。

**「给一群人发东西」这件事，仓库里已经手写了三遍，但没有名字。**

- 选人后的 PvP 大厅公示：`ISelectCharacterLifecycleServices.PlanPvpPublication` 返回
  `IReadOnlyList<PvpParticipantPublicationTarget>`（连接 + 内容），handler 映射成帧发出去
- 会话清理通告：`SelectedSessionCleanupNotificationPlan` 分「必送给本人」与「尽力送给旁人」
- 城镇在场：`ISessionPresenceDomainService.InArea(townId, areaId, excluding, listenerPort?)` 查人群

三处都是同一个形状：**领域侧产出「谁 + 什么」的计划 → handler 映射成帧 → 发送器投递**。每一处各自
处理人群、内容、失败隔离，各错各的。

网络层已经有一半基础设施：`ExplicitMessageDelivery` 不是一条消息而是**一份投递计划**，区分「必须
送到的直连方」与「尽力而为的旁人」，并且已经做了失败隔离。它被用了 46 处。

**缺的是「人群」这一层。** handler 之所以要手写目标，正是因为没有地方能回答「这个频道里有谁」。

而缺这一层的代价已经露出来了：领域服务为了算「通知谁」，被迫自己去查连接——
`PlanPvpPublication` 里有一句 `sessions.FindByCharacter(value.CharacterId)`，一个领域服务在做
连接查找。它只想说「这几个角色要被通知」，却被迫知道了 socket 的存在。

### 这个机制与 socket 路径的方向相反

现有的每一条路径都从 `NetworkDispatchContext(connection)` 开始：账号身份来自连接，命令管道上的
两个执行闸门正是靠它挑锁。**通知是反向的**——它从服务器侧发起，目标是一群人，而不是一个请求方。

方向反的是**发起方**，不该反的是**执行通路**：业务仍然走命令，通知只负责投递。

### 所有者定下的三样东西各自的边界

| | 做什么 | 何时 |
|---|---|---|
| **CMD** | 业务行为 | 本轮已有 |
| **通知服务** | 把帧送给一群人 | **本轮做这个** |
| **周期事件** | 到点了叫醒，调 CMD，再委托通知 | 下一个成果 |

## Goal

服务器有一个统一的方式回答「把这件事告诉这群人」：调用方说出人群与通知，服务负责把人群解析成
收件人、逐个取得该收件人的消息、投递、隔离失败、并交回一份可核对的摘要。领域服务不再需要知道
连接的存在。

## Scope

### In

- 一个通知总线，其调用点的通知类型由实参推断，无从选错
- 人群作为一个**值**，且以角色而非连接表达；由服务负责解析成连接
- 每个通知类型有自己的处理器，按收件人取得该收件人的消息；处理器可对个别收件人弃权
- 处理器注册与启动校验
- 逐个投递、每收件人超时、失败隔离
- 失败重试：内存队列，重试时重新解析、重新取内容，达上限即丢弃
- 一份可核对的投递摘要
- 至少一处现有的手写扇出改为经此服务，并且它所在的领域服务不再做连接查找
- 仓库约定里关于 `CMD ⇒ Notify` 这个模式的记载

### Out

- **周期触发**。所有者明确要求先做通知、后做周期任务。本成果不含任何调度器、时刻表或定时循环
  （重试队列的排空循环除外——那是本服务自己的一部分）
- **发布订阅事件总线**。业务用例直接调用通知服务；不引入「发布一件事、由订阅者各自决定反应」的
  间接层。若将来出现一件事确有多个独立反应方，那是另起的决定
- **那 46 处「回给请求方」的 `SendExplicitAsync`**。它们绝大多数 `BestEffortTargets` 为空，套上人群
  抽象等于为占绝对多数的情形加一层间接。本成果只统一有扇出的那几处
- **频道、全服、组队三种人群**。它们在本仓今天没有真实调用方（队伍这个概念在本仓根本还不存在）。
  人群用封闭层级表达，将来加一种时编译器会强制所有解析处理它
- 通知内容的节流或速率限制。所有者判定这个规模不需要，控制者同意：千人级下一次全服扇出约数十毫秒
- 通知去重。所有者判定「这情况能不能出现都不好说」，且重试是重新取内容的，重复只会让同一个人
  多收一次——而「多通知一次没关系」是本设计的既定前提

## Constraints

- **通知处理器只读**。写属于 CMD 阶段。这一条同时管住三件事：不吃账号闸门、不进事务、成本可预测
- **通知在事务提交之后**。`CMD ⇒ Notify` 是两次顺序调用，命令的工作单元只包住命令自己——这条
  因此是结构性的而非靠人记住
- **重试不缓存任何东西**：重新把角色解析成当前连接，重新向处理器取内容。缓存编码好的帧会让一个
  旧值覆盖新值
- 超时值全局一致，不按通知特例
- 服务器对客户端的可观察行为逐值不变，被迁移的那处扇出，其**帧**逐值不变；其**收件人集合与投递语义**的每一处差异都已逐条列出、每条可指到具体代码窗口（revision 2 下调，原文见下方 Amendments）
- 命令处理器注入面判据仍须通过，其判定谓词与具名豁免清单不得放宽或扩充

## Assumptions

- 判据命令必须带 `PVF_ARCHIVE_PATH`，否则读档案的判据会静默跳过而不是报红。基线里那 2 个 skip
  正是档案已加载的标志
- 既知偶发失败的判别依据是「异常类型 + 栈根 + 复跑即绿」而**不是用例名**：
  `ObjectDisposedException: 'SQLitePCL.sqlite3'`，栈根
  `CharacterDatabaseSchema.KeepWritersAndReadersApart → SqliteCommand.ExecuteScalar`，
  已在两条不同用例上出现过。另有 `Dfo.Server.Networking.Tests` 的一次未记名并行偶发
- 编码已经是每个收件人一次（`DeliverExplicitAsync` 逐目标调 `SendAsync`，其中 `Encoder.Encode`
  每次都跑）。所以「按收件人算内容」相对「统一内容」几乎不多花钱，多出的只有一次 record 分配
- 投递今天是严格顺序 `await` 的。现有扇出规模都很小（同区、大厅），队头阻塞尚未暴露；本成果用
  每收件人超时来挡它，而不是改成并发
- 一次千人扇出约数十毫秒（读代码估算，非压测）。这个量级下不需要节流
