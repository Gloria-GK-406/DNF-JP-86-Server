# Specification: Typed Command Dispatch

## Why and Outcome

命令派发目前用一个枚举把命令连到 handler，用 `object` 把结果传过管线，再在末尾把类型换回来。这套机制是从消息派发照搬的，而消息侧的枚举来自协议、无可避免，命令侧没有这一跳。代价是同一个对应关系被声明三遍且无人校验，配错要等派发时才发现。

改完之后，命令、结果与 handler 的对应关系在注册点由编译器保证，结果类型全程静态携带；因动态连接而存在的运行时弥合检查随之消失。**派发的可观察执行语义必须一字不变**——这是本 Spec 的主要风险面，因为失效方式是静默的。

## Task Perspective

- Core outcome: 注册点三者配错无法通过编译；派发链路全程携带静态结果类型。
- Necessary support: 枚举与所有弥合检查移除后，派发的执行语义与改动前完全一致——四个管线行为仍全部进链且顺序不变，两种 access mode 闸门仍按注册的模式获取与释放，嵌套派发仍被拒绝，每次派发仍开新作用域。
- Peripheral assurance: 未注册命令显式失败并指明命令；编译探针证明三类错配确实被编译器拦下。

## Scope and Non-Goals

### In Scope

- 命令与结果、handler 与命令三组对应关系在注册点的编译期约束。
- 派发链路（终端 handler、管线行为、`SendAsync` 返回值）的静态结果类型。
- 枚举连接键改为命令类型，及随之而来的注册表语义调整。
- 移除仅服务于旧动态连接的检查。
- 执行上下文中命令标识的表示形式，及日志对它的使用。

### Non-Goals

- 消息派发侧的任何改动。
- 命令的业务语义、执行种类、access mode 取值。
- 命令或 handler 的增删、拆分、重命名。

## Constraints

- 不得以放宽类型、抑制诊断或降低警告等级换取编译通过。
- 既有测试须继续通过；仅当某断言所验证的行为本身被本 Spec 有意移除时方可修改，且须在结果中列明。

## Definitions

| Term | Meaning |
|---|---|
| 派发链路 | 自 `SendAsync` 被调用起，经管线行为，至终端 handler 返回结果并回到调用方的完整路径 |
| 弥合检查 | 仅因连接关系在编译期缺失而存在的运行时判定，如 handler 能否处理该命令、结果类型是否为期望类型 |
| 执行语义 | 派发过程中调用方可观察到的行为：行为的组成与顺序、闸门的获取释放、拒绝条件、作用域边界 |

## External Behavior and Data Rules

- `SendAsync` 的调用形态不变：传入一个命令，结果类型由命令的静态类型决定，调用方无需显式给出类型实参。
- 派发一个未注册的命令时失败，且失败信息指明是哪个命令。
- 注册同一个命令两次时失败。
- 不再要求「每个已知命令标识都必须有注册的 handler」；未注册的命令只在被派发时才成为问题。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 注册点把命令、结果、handler 三者绑定；其中任一与其余不匹配时编译失败。 |
| RQ-002 | 结果自终端 handler 返回后，全程以静态结果类型传递至调用方，不经由 `object` 承载。 |
| RQ-003 | 解决方案中不再存在命令枚举，命令不再声明自身的枚举标识。 |
| RQ-004 | 判定 handler 能否处理某命令、以及判定结果是否为期望类型的运行时检查不再存在。 |
| RQ-005 | 派发未注册的命令时显式失败，信息中包含该命令的标识。 |
| RQ-006 | 重复注册同一命令时失败。 |
| RQ-007 | 每次派发依序经过全部已注册的管线行为，顺序与改动前一致。 |
| RQ-008 | 按 online-user 或 account access mode 注册的命令，其闸门仍在派发时获取，并在成功、抛错、取消三种情况下释放。 |
| RQ-009 | 嵌套派发仍被拒绝。 |
| RQ-010 | 每次派发仍在独立的服务作用域中执行。 |
| RQ-011 | 命令执行日志仍能标明是哪个命令、哪个 handler、哪种执行种类。 |

| AC-003 | RQ-003 | 完成后的解决方案 | 检索命令枚举 | 无匹配 |

## Assumptions

- 命令均为 `sealed record`，因此按精确命令类型建立的注册表在派发时解析到的 handler 必定匹配。
- 所有 handler 注册均在同一程序集内完成。
- 本 Spec 建立在同分支上一次提交所加的结果类型非空约束之上。
