# TaskContract: 物品有自己的身份，槽只说它在哪

## Context

### Source Request

所有者原话：

> 「先写设计文档然后写任务契约直接开始重构任务？看起来已经足够清晰了。是包括整个装备系统的架构级重构。」

建模本身也由所有者定：

> 「只有装备，时装，宠物这种是需要独立表的。也就是一张表记录了游戏里都有什么这种可变的东西。
> 另一张表也就是 store 记录了哪个 slot 有啥。而消耗品，材料这里就又不一样了。材料 slot 里记录的是
> 哪个 slot 有多少个什么东西。这个东西是没有实例的，是在 pvf 里定死的不变的。」

> 「我有个世界级的仓库表，里面记录了全世界都有什么装备。然后我个人不再是自己写，而是直接引用
> 世界仓库的东西。」

孤儿的处置也由所有者定：

> 「孤儿问题，用定时清理器来做世界仓库里的孤儿装备。……进地下城，扔下装备，这时候这个装备是在
> 世界仓库里的。然后退出地下城。地下城中生成的所有世界装备都要直接清理掉。这可能是后面要做的。」

随后经提问确认两件：验收口径 = **逐值不变 + 顺带修已知缺陷**；流程 = 完整 SDD。

### Current Situation

完整设计见 `Docs/ItemWorldModel.md`，本契约引用它而不复述。要点：

今天 `items` 一行同时承载「这是什么东西」（`item_core` 82 字节）与「它在哪」
（`owner_scope` / `owner_id` / `list_type` / `slot_index`），唯一键是后四列。结算的做法是
**先 `DELETE` 掉那个槽再 `INSERT`**（`SqliteItemDomainStore.cs:270` / `:292`），因为谓词必须与
唯一键同名才不会撞上残留。三个后果：

1. **`item_uid` 每写一次就换一个。** 它是 `PRIMARY KEY AUTOINCREMENT`，但行被销毁重建，
   所以它不是身份；领域层也看不见它——`ContainerSlotItem` 是 `(SlotIndex, Core)`。
2. **物品无法「存在但不在任何槽里」。** 地上掉落、交易托管、信里的附件、拍卖挂单，
   四件事今天都没有地方表达；`Table Ownership Ruling` 的 D-1 正卡在这里。
3. **`Core.Value` 一字三义**：堆叠数量 / `creature_key` / 头像 UID，靠 `ItemKind` 分辨，
   没有任何东西强制。宠物那边已经在咬人。

四条已核实的证据，实现不必重新发现：

- **82 字节 blob 只是存储格式。** `InventoryItemCore.Encode/Decode` 全仓 7 处命中**全部在
  Persistence 层**；线上那 101 字节条目是**逐字段写的**（`GameInventoryDelivery.cs:53-108`）。
  所以按类型拆存储，客户端一个字节都不会变。
- **线上已经按类型分支，且比存储更严。** `GameInventoryDelivery.cs:47-58`：`ItemKind == 8`
  走 `AvatarDetail`，并强制「时装必须有、非时装必须没有」；`InventoryItemState` 上已经挂着
  `AvatarDetail` 侧记录。
- **拆堆已经在造全新的堆。** `ItemContainers.cs:113-117`，拆出去那一堆是
  `StackableItemCore.Create(kind, itemId, moveCount)`，不继承源堆任何东西——
  **堆叠在今天的代码里本来就没有身份。**
- **「这个 id 在档案里存在吗」这道检查已经有了**，且由规则服务回答：
  `MainSlotAdmission.ItemUnknown`。

## Goal

一件物品有自己的身份，槽只说它在哪。

有身份的物品（装备、时装、契约兽）住在按类型分开的世界表里，一行一件；槽只记
「这个槽放的是什么类型的什么东西、几个」。没有身份的东西（消耗品、材料）只在槽里记模板与数量，
不进世界表。移动一件物品不改变它是哪一件。

客户端看到的字节不变，例外只有下面明确授权的两条缺陷修复。

## Scope

### In

- 有身份的物品与它的位置分开存放；世界侧按类型划分，槽侧对两类东西是同一种形状。
- 现有物品数据迁移到新形状，且迁移的分类依据是显式的、可核的。
- 结算不再以销毁并重建承载物品的那一行的方式改变位置。
- 入场与增量的物品投影仍能产出今天的线上字节。
- 孤儿世界行**可被识别与查询**。
- 顺带修两条已知缺陷：单向丢宠、`ItemKind` 与档案解释不一致。
- 契约兽作为「有身份的一类物品」随之搬进世界侧。
- 仓库约定记下这套建模、被授权的行为变化、以及本轮没做的部分。

### Out

- **定时清理器本身不做。** 孤儿由将来的周期任务成果清扫；本轮只保证孤儿可识别。
  副本内生成的物品在退本时全清，同属那个后续成果。
- **旧数据库的自动升级不做。** 所有者裁定：现有测试库**作废重建**，新形状只对新建的库生效。
  今天的 schema 调和只会 `ALTER TABLE … ADD COLUMN`（`CharacterDatabaseSchema.cs:159`），
  做不到拆表、搬数据、删列或改唯一键；本轮不为此新建迁移机制。
  **注意这不减轻分类风险，只是把它从「一次性搬运」移到「每一次写入」**——见 SC-4。
- **地上掉落、交易托管、拍卖挂单、邮件附件不启用。** 模型允许「存在但不在任何槽里」，
  本轮只把模型腾出来，不接通这些用法。
- **宠物领域本身不做**：实例、动词、喂食、经验、等级、饱食度记账，全部留给后续成果
  （见 `Docs/CreatureDomainDesign.md`）。
- **宠物槽是 24 还是 25 不裁**，**`Pet = 7` 容器装什么不裁**——两者都要线上抓包证据，
  读代码得不出。本轮沿用今天的 24。
- 宠物技能是否进服务端不裁。
- `character_condition` 的五列（`creature_field1..4`、`creature_buffer`）不动——含义未查清。
- 快捷栏、称号书、骑士盾等其它容器的用途不变更。

## Constraints

- **线上行为逐值不变**，例外只有本契约授权的两条缺陷修复；每一处行为变化必须逐条列出
  变了什么、为什么。
- 不新增协议帧，不改任何帧的字节布局。
- 既有判据的期望值与断言不得为迁就实现而改写；类型改名的符号更新、以及正对应被授权行为变化的
  改写除外。
- `CommandHandlerArchitectureTests` 与 `NotificationHandlerArchitectureTests` 必须继续通过，
  其判定谓词与具名豁免清单不得放宽或扩充。
- 领域层中 `store` 一词仍只有一种读法：事务结算的真源，名字以 `DomainStore` 结尾。
- **不得引入「从槽取凭证 → 换实例 → 操作 → 换回新凭证 → 写回槽」的来回。**
  它让实例持有状态，是 lost-update 形状；本仓正是靠「实例不持有状态」才消掉了移动用例的
  竞态失败返回码。
- 分层由项目引用强制：Data → Abstractions → Application → {Infrastructure, Persistence,
  Networking} → Protocol → Host。
- 切片架构（`AGENTS.md`）：`Protocol/<Endpoint>/<Protocol>/` 一个目录，切片内不跨协议引用；
  新协议只改 `ProtocolModule` 一处接线；命令处理器禁止嵌套 dispatch；凡能触达持久写的命令
  一律 Transactional。
- `TreatWarningsAsErrors` 开启，CS9113（未读的主构造器参数）是错误。
- 判据命令必须带 `PVF_ARCHIVE_PATH`。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 一件有身份的物品在槽间移动、穿脱、跨容器移动之后，仍是同一件——它的身份值不变，它的实例状态（强化、洗出的属性、附魔等）随之不变 | 判据：对同一件装备做移动/穿脱后读回，身份值与实例状态逐字段相同 |
| SC-2 | 槽对「有身份的物品」与「消耗品」是同一种形状：都只说类型、是什么、几个 | 判据读得出这一种形状；评审确认没有第二种槽表达 |
| SC-3 | 消耗品没有身份，且没有任何生产代码把它的标识当作身份使用 | 机检判据挡住这种用法；拆堆后两堆各自可用，且不依赖任何继承自源堆的标识 |
| SC-4 | 「一件物品该落到世界侧还是只落在槽里」这个分类依据是显式的、可指认的，且不把库里 `ItemKind` 这一个值当作唯一依据 | 分类规则在代码中可指认，且是**每次写入都会走的那一条**，不是一次性的搬运；判据覆盖至少一处「库里的 `ItemKind` 与档案对同一件物品的解释不一致」的情形，证明分类仍正确 |
| SC-5 | 没有被任何槽引用的世界行可以被查询出来 | 判据：造出一个无引用的世界行，查询能列出它 |
| SC-6 | 玩家把契约兽从装备槽取下之后，能再装回去 | 判据：取下再装回，成功且宠物身份不变。**这是被授权的行为变化之一** |
| SC-7 | 契约兽物品的种类判定与档案对同一件物品的解释一致 | 判据钉住两者一致。**这是被授权的行为变化之二** |
| SC-8 | 除 SC-6、SC-7 之外，服务器对客户端的行为逐值不变 | 全量判据不低于基线计数；入场物品帧与增量物品帧的字节与迁移前逐值相同；`Server/tests` 的 diff 不改任何断言、期望值或用例（类型改名的符号更新除外） |
| SC-9 | 被授权的行为变化被逐条列出，每条能指到具体代码位置 | 成果记录含一份差异清单，评审逐条回到声称位置核过 |
| SC-10 | 命令处理器与通知处理器的注入面判据仍然通过，判定谓词与具名豁免清单未被放宽或扩充 | 两个机检判据全绿；其判定谓词与豁免清单的 diff 为空 |
| SC-11 | 领域层中 `store` 一词仍只有一种读法 | 全仓以 `DomainStore` 结尾的类型逐个核过，无一是非事务结算的真源 |
| SC-12 | 后来的读者能在仓库约定里找到这套建模、被授权的行为变化、以及本轮没做的部分 | `AGENTS.md` 的相应小节与代码一致，且明说孤儿清理器、掉落/交易/拍卖/邮件附件、宠物领域本身都不在本轮 |

## Assumptions

- **W-1 世界标识的宽度未定。** 装备的世界标识不上线，可以宽；但 `0x0069` 把 `PetKey` 用
  `checked((int))` 写出去，**契约兽的对外标识必须塞进 i32，超了当场抛**。宽度与是否分成两个
  标识由 Spec 裁定。
- **W-2 已由所有者裁定为「定时清理器扫孤儿」**，因此本轮不需要任何孤儿防漏纪律；
  但清理器本身不在本轮（见 Scope Out）。若 Spec 阶段发现「不清扫」在本轮就会造成可观察问题，
  这条假设被推翻，须返回所有者。
- **W-3 时装的六列刚按 `Table Ownership Ruling` 的 M-2 并进 `items`，本轮要再搬一次。**
  所有者已认可这个代价。M-2 的理由是「细节的键是物品已经持有的一个值」，而本建模给了物品
  一个真正的键，那个前提被取代。
- **W-4 命名由 Spec 裁定。** 世界侧是事务结算的真源，可能该以 `DomainStore` 结尾，
  但必须与「容器」分清：容器管槽，世界侧管东西。
- **`Core.Value` 的三义必须摊牌**：堆叠取数量，契约兽与时装取实例标识。
  **分错了不会报错，会静默错**——这是本任务最大的单点风险，SC-4 与 SC-8 共同覆盖它。
  旧库作废之后这个风险并没有消失：它从「一次性搬运可能分错」变成
  **「每一次写入都在做这个分类」**，所以判据必须钉住那条活的规则，而不是一次迁移的结果。
- 本轮沿用今天「契约兽在装备槽 24」的假设。若线上证据后来证明是 25，
  受影响的是槽位常数与其副本，不是本建模。
