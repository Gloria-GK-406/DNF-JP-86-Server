# Routing Decision

- TaskContract: `.rks-agent/tasks/items-own-their-identity/TaskContract.md`
- Contract revision: `2`

> revision 1 → 2 发生在路由之后、Spec 之前：所有者裁定现有测试库**作废重建**，
> 于是「旧库自动升级」进入 Scope Out，SC-4 的措辞从「迁移的分类依据」改为
> 「每次写入都会走的那条分类规则」。**这缩小了范围但没有改变风险的性质**，
> 就绪性、边际价值与结构选择均不受影响，本决策不需要重做。

## SDD Readiness

- Intent and outcome stability: 成果可观察且已定死——**线上字节逐值不变，例外只有两条被授权的
  缺陷修复且必须逐条列出**。建模本身由所有者作者化（世界表按类型分、槽记 type/id/count），
  不是执行方推断出来的，所以不存在「做着做着发现要的不是这个」。
- Requirement stability: 十二条成功条件全部可枚举且各有观察面。四条支撑性事实已在动手前核实
  （blob 只是存储格式、线上已按类型分支、拆堆已造新 core、档案存在性检查已有规则服务），
  所以要求不建立在待验证的前提上。
- Execution direction: 中心方向已定——有身份的物品与其位置分开存放，槽对两类东西同一种形状。
  剩下的是 W-1..W-4 四个**机制级**选择（标识宽度、时装六列的搬法、命名，以及孤儿——
  孤儿已由所有者裁定为定时清理器、且清理器不在本轮），它们不改变任务语义，交由 Spec 裁。
- Remaining uncertainty: 只剩非语义的局部选择。两处真正未知（宠物槽 24 还是 25、
  `Pet = 7` 容器装什么）**已划出范围**，因为它们要线上抓包证据，读代码得不出。

## Marginal Control Value

- User precision signal: 所有者明确要求完整 SDD，并把这件事定性为「包括整个装备系统的
  架构级重构」。此前多轮的一贯偏好是精确优先于速度：对判据、变异验证、独立评审都主动加码，
  并多次要求把「没做到的部分」如实记下。
- Direct failure mode: **迁移分类错了不会报错，会静默错。** `ItemKind` 今天不可靠
  （24 槽契约兽入库记 5，档案对同一件物品给 1），`Core.Value` 一字三义（数量 / `creature_key` /
  头像 UID）。分错的行会安静地进错的世界表或丢掉实例状态，而**全量判据仍然全绿**——
  因为投影照样拼得出线上字节。这是一次**数据迁移**，做错了不是回滚一个文件。
- Useful control: Spec 把迁移分类依据钉成显式的成功条件（SC-4），Plan 把它落成可执行的检查，
  完整变更评审由独立上下文对着规则逐条核（SC-9 的差异清单）。这类缺陷靠「跑一遍看绿不绿」
  抓不住，必须有人回到声称位置核对。上一轮成果里，同类清单在五轮独立评审中分别缺
  3 / 2 / 1 / 1 / 0 条，每次都是换一个新上下文重读代码才发现的。
- Time-for-quality rationale: 代价是若干轮评审与验证的时间；收益是把一次不可逆的数据迁移的
  静默错误概率压下来。碰的是**全仓唯一的物品真源**，跨五层，且时装的六列刚落地就要再搬一次——
  返工成本远高于流程成本。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: **只有一个验收口径**——逐值不变，加两条被授权的例外。而且这件事**无法半迁**：
  「世界表存在」不能脱离「投影仍产出同样的字节」被接受，两者要么一起成立要么一起不成立，
  没有一个中间状态可以独立接受或独立回滚。宠物领域、掉落/交易/拍卖/邮件、定时清理器
  都已划出范围，它们才是各自独立的后续成果。
- Why Direct is insufficient: Direct 给不了「独立上下文对着迁移规则逐条复核」这一样，
  而那正是唯一能抓住静默分类错误的控制。判据全绿在这个失败模式下不构成证据。
- Why Multi is unnecessary: 本轮没有第二个独立的验收边界。文件多、跨层、工作量大都不构成
  Multi 边界——上一轮根图已经立过这条规矩：**同一个口径下的几段工作量属于一个成果。**
- Reroute conditions:
  - 若 Spec 阶段发现「本轮不清扫孤儿」在本轮就会造成可观察问题，则 W-2 那条假设被推翻，
    停下返回所有者，而不是把清理器塞进本轮。
  - 若迁移分类被证明无法在不引入行为变化的前提下做对（例如某类物品的归属只能靠线上证据裁定），
    则「逐值不变」这个口径不再成立，须重新裁定口径而不是自行放宽。
  - 若契约兽那部分在执行中发展出自己的验收边界（例如世界侧的搬迁牵动了宠物的实例状态语义，
    使它必须能被独立接受或回滚），则本 Spec 的边界不再成立，应停下重新切分。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-refactor`
- Why this is sufficient: 三样控制各自对着一个具体风险——**Spec** 把迁移分类与「逐值不变的例外」
  钉成可核的成功条件；**Plan** 把跨五层的改动切成有序、各带检查的边界，避免实现期临时决定
  归属；**完整变更评审 + 新鲜验证**由独立上下文复核，是唯一能抓住静默分类错误的控制。
  性质是行为保持的结构重构，`code-refactor` 的方法绑定（test-driven-development、
  reviewing-code）正对。
- Why lighter is insufficient: Lite 没有 Plan 阶段。本轮要动**全仓唯一的物品真源**并做一次
  数据迁移，跨 Data / Abstractions / Application / Persistence / Protocol 五层；
  没有事先定好的边界与顺序，实现期会一边做一边决定归属，而归属正是这次最容易静默错的地方。
- Why heavier is unnecessary: Governed 要求控制器只做编排与裁决、全部生产工作外派。
  本轮只有一个验收口径、一条线性的依赖链，不存在需要控制器居中裁决的相互冲突的边界；
  外派的收益抵不上把上下文在控制器与执行方之间来回搬的成本。上一轮同等规模的结构重构
  用 Standard 走完，未出现需要 Governed 的情形。
