# TaskContract: A21 城镇组队生命周期

## Context

### Source Request

用户先要求检查其刚刚进行的组队相关交互是否已被服务端记录、是否可以实现，并强调所有实现都要同步更新协议文档。在服务端日志、协议库、当前领域结构和旧服行为边界核实后，双方将本任务收敛为城镇组队闭环；用户随后授权：“可以，直接开始实现吧”。Round 5 实机发现组队头像 HP 初始为空，且点击“查看角色详情”产生的 `GET_USERINFO mode=3` 被现有只支持角色列表的解码路径拒绝；用户进一步授权：“可以，按HP修复，完成角色详情查询的顺序完成任务把”。

### Current Situation

初版实现后，当前 A21 双客户端已显示邀请框，但接受时双方同时异常退出。服务端日志表明形成序列完整发出，只有一端曾上报 UDP，另一端在 `NOTI 0x000B` 中收到 `0.0.0.0:0`；两端故障记录在同一秒落到相同客户端地址。旧服同版本组队构造器对缺失上报使用 `127.0.0.1:10000` 与 MTU 1500，而非零端点。同期实测还暴露：两个角色进入 PVF 标为 `[gate]` 的赛丽亚房间后被错误当成同屏用户互相广播；上游明确把该 gate 区域当作每角色私有房间。65 字节名册修正后客户端已能存活并形成队伍，但形成阶段的实时摘要早于名册，双方头像 HP 初始为空；仅邀请者随后主动请求一次 `0x00A6`。同轮“查看角色详情”按钮连续发出两条 3 字节 `0x0008`，现有 decoder 因 mode 不是账号名单模式而拒绝，详情窗口没有服务端响应。

## Goal

让同一 Game 频道、同一城镇区域内的两个当前 A21 会话能够完成组队邀请、接受、双方队伍状态（含初始 HP）显示、主动离队与掉线清理；并让当前角色能够通过原生“查看角色详情”入口读取同频道目标角色的详情。实现、测试、抓包证据和协议资料库保持一致。

## Scope

### In

- 接收并校验城镇组队邀请与邀请响应。
- 维护进程内队伍、成员、邀请和当前会话代际一致性。
- 向相关客户端投影邀请、接受、成员实时信息、P2P 端点和完整队伍名册。
- 在客户端名册状态建立后向全体成员投影当前 HP 摘要，使双方头像无需依赖各自是否主动发送实时查询即可填充。
- 接收客户端已上报的 UDP 端点前缀，为队伍端点投影提供数据。
- 缺少 UDP 上报时使用同版本旧服的安全回落端点，避免客户端在形成 P2P 成员状态时消费零端点。
- 按 PVF town area 的 `[gate]` 类型把赛丽亚到达房间建模为每角色私有区域，不向相同 town/area 数值的其他会话投影同屏用户或位置更新。
- 支持主动离队与连接结束后的队伍清理和剩余成员刷新。
- 支持当前会话发起的角色详情查询，并仅对同一 Game 频道内仍为当前在线会话的指定目标返回 A21 可消费的详情投影。
- 覆盖协议解码、领域行为、通知编码、跨会话投递和生命周期的自动化回归。
- 为本次捕获和实际实现涉及的协议页、样本、游戏协议索引与总清单补充当前 A21 证据和实现映射。

### Out

- `0x01A3` 聊天组/会话功能、`0x0122` 跨服好友功能和 `0x000A type=1` 交易流程。
- PvP 邀请、踢人、转移队长、队伍设置、队伍列表和快速组队。
- 多人副本入场、房间同步、战斗 P2P、掉线重连与 UDP 中继。
- 队伍持久化；队伍只在服务端进程与在线会话生命周期内存在。
- 客户端二进制或 ClientHack 修改。

## Constraints

- 遵守当前分层：协议包 handler 调用 Command 实施业务、通过 Event/Notification 实施通知；Application 不引用 Infrastructure。
- 任何旧服实现只能作为行为与字节布局证据，必须按当前领域与通知边界重建，不整体移植旧会话对象模型。
- 服务端不得把聊天组、好友、交易或 PvP 请求误当作组队状态变更。
- 角色详情查询不得泄露跨频道、离线、过期会话或歧义目标的数据；目标在投影期间被替代或离线时不得继续向请求者发送旧代际详情。
- 未经当前 A21 实机确认的布局或行为必须保留相应置信度，不得标记为 `ClientVerified`。
- 协议文档与 catalog 必须随代码和验证状态同步更新。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 同频道、同城镇区域的当前会话发出 `0x000A type=0` 后，目标客户端收到并显示正确邀请者的组队邀请。 | 编解码与 handler 测试；当前 A21 双客户端入站/出站抓包和可见 UI 结果。 |
| SC-2 | 目标接受有效邀请后，双方都显示同一支两人队伍，队长与成员顺序稳定，且形成通知按客户端可接受的顺序发送。 | 领域/通知/端到端测试；当前 A21 双端抓包与双方 UI 结果。 |
| SC-3 | 成员主动离队或当前连接结束后，离队者恢复无队显示，剩余成员收到刷新；最后一人离开后队伍销毁。 | 生命周期与通知测试；至少一次当前 A21 主动离队实测。 |
| SC-4 | 自邀、跨频道、跨区域、满员、过期邀请、重复响应和被新会话替代的旧邀请不能错误改变队伍。 | 针对各拒绝与竞态路径的自动化测试。 |
| SC-5 | `SET_UDP_IP_PORT` 的已知 A21 前缀被严格解码并供端点投影使用，畸形上报不会污染现有状态；缺失上报不会向组队客户端发送 `0.0.0.0:0`。 | 解码器、状态更新和端点编码测试，覆盖本次两个 31 字节样本与旧服回落形态。 |
| SC-6 | 本次观察及实际实现涉及的协议页、样本、索引与总清单准确反映字段、方向、实现位置、证据来源和当前验证等级。 | 文档差异审查；协议样本与测试/实机记录可追溯。 |
| SC-7 | 全部仓库测试通过，分层约束未被破坏，任务范围外的现有行为无回归。 | 全量构建与逐测试结果验证；独立完整结果审查。 |
| SC-8 | PVF 标为 `[gate]` 的赛丽亚房间不产生跨角色同屏名册、进入/离开或位置广播；走到 `[normal]` 区域后同屏行为恢复。 | PVF 原文、区域规则与投影回归测试；当前 A21 双客户端从赛丽亚房间走到银色村庄主街的 UI 观察。 |
| SC-9 | 队伍名册建立后，双方头像立即显示服务端当前 HP 百分比，不依赖每个客户端是否主动补发 `0x00A6`。 | 形成阶段通知顺序与逐字节测试；当前 A21 双客户端初始头像 UI 观察和对应服务端发送记录。 |
| SC-10 | 当前会话点击同频道在线角色的“查看角色详情”后能打开并显示目标详情；离线、跨频道、过期或歧义目标不返回旧角色数据。 | mode 分流、当前会话授权、目标代际和详情编码测试；当前 A21 双客户端按钮实测与对应帧记录。 |

| Capability | Evidence | Authorized scope |
|---|---|---|

## Requires Confirmation

- 合并、推送、发布、删除任务分支或清理独立 worktree。

## Assumptions

- 当前 A21 对非空队伍的接受响应与名册行为可先依据静态分析和旧服同版本证据实现，再以本任务内的双客户端实机步骤校准；校准前只声明实现就绪，不声明客户端验证完成。
- 城镇组队端点交换优先投影客户端已上报的直接端点；上报缺失时按同版本旧服使用回环/10000/MTU 1500 的结构安全回落。UDP 中继和副本内 P2P 属于后续任务。
- 当前实机的 3 字节 `GET_USERINFO` 是静态记录中的 `mode=3` 指定目标查询；A21 详情响应可先依据同版本客户端解析证据和参照实现重建，再由本任务双客户端实机校准，校准前保持 `Implemented`。
