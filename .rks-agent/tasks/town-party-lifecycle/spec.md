# Specification: A21 城镇组队闭环

## Why and Outcome

当前 A21 客户端已经能在城镇中看到并右键交互，但组队邀请请求原先被服务端当作未处理帧丢弃。初版闭环实机校准后，客户端已能形成队伍，但名册建立前到达的实时摘要没有填充初始 HP；同一菜单中的“查看角色详情”又会发送现有解码器不支持的 `GET_USERINFO mode=3`。交付后，两个处于同一 Game 频道和城镇区域的当前会话应能用原生客户端 UI 发起并接受邀请、立即看到含 HP 的一致两人队伍、查询当前在线目标详情、主动离队，并在任一连接结束时得到一致清理。服务端必须把队伍与聊天组、好友、交易和 PvP 行为严格隔离。

## Scope

本规格覆盖 `SET_UDP_IP_PORT`、`REQUEST_PEER(type=party)`、`RESPONSE_PEER(type=party)`、`LEAVE_PARTY`、`GET_USERINFO(mode=3)` 及形成/刷新队伍和角色详情所需的服务端通知，并覆盖当前会话、城镇位置和连接结束的生命周期。队伍为进程内临时状态；角色详情只从当前服务端状态投影，不新增持久化写入。

聊天组、好友、交易、PvP、踢人、改队伍配置、队伍列表、快速组队、多人副本、战斗同步、UDP 中继和持久化均不在本规格内。范围外请求可以继续被现有未处理路径记录，但绝不能产生队伍变更。

## Definitions and Invariants

- **当前会话**：角色、账号、连接和选择代际仍与在线表及已选择会话目录一致的会话。
- **同域邀请**：邀请者与目标都是当前会话、监听同一 Game 端口、均站在城镇中，且 town/area 相同。
- **队伍身份**：一个角色最多属于一个队伍；一个队伍最多四人；slot 0 是队长，其余槽按成功加入顺序占用。
- **邀请身份**：邀请绑定邀请者和目标双方的精确会话代际及邀请时的队伍代际；只能成功消费一次，并会在有限时间后失效。
- **队伍寿命**：队伍不持久化。普通成员离开时其余成员继续；队长离开或掉线时队伍解散；最后一个成员离开后队伍一定不存在。
- **可信度**：自动化测试可以证明服务端行为和编码，但不能替代当前 A21 实机结果。只有实机抓包与 UI 观察成功的协议才能标记 `ClientVerified`。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 服务端应严格解码 A21 `CMD 0x0002 SET_UDP_IP_PORT` 的 15 字节固定前缀：NAT 类型、内网 IPv4、外网 IPv4、LE UDP 端口和 LE MTU；允许并原样忽略其后的身份尾部。无效长度、非 IPv4 可用地址、零端口或越界 MTU 不得覆盖最近一次有效端点。 |
| RQ-002 | 服务端应识别 `CMD 0x000A REQUEST_PEER` 的目标 uid、请求类型、peer 值和允许的尾部；只有 `type=0` 进入组队用例，其他类型不得读写队伍或邀请状态。 |
| RQ-003 | 组队邀请只允许同域、非自身的当前会话。已有队伍的邀请者必须是队长且队伍未满；已在其他队伍中的目标不得被加入。失败应保持双方与既有队伍不变，不向错误目标发送邀请。 |
| RQ-004 | 有效邀请应记录双方精确会话和队伍代际，并向目标发送 `NOTI 0x0007 REQUEST_PEER` 的组队形态，携带正确邀请者 uid、请求类型和请求关联值。 |
| RQ-005 | `CMD 0x000B RESPONSE_PEER` 只有在请求类型为组队且能够原子消费一条尚未过期、双方仍为当前会话、位置仍同域、邀请者队伍代际未变化的邀请时才可建立或扩展队伍。重复、过期、换线、换角色或队伍已变化的响应必须无副作用。 |
| RQ-006 | 首次接受时创建以邀请者为 slot 0 队长、接受者为 slot 1 的两人队伍；已有未满队伍接受新成员时保留队长和既有 slot，并为新成员分配最小空 slot。 |
| RQ-007 | 成功接受后，双方应从同一不可变队伍快照收到一致形成投影：成员实时信息、邀请接受通知、成员 P2P 端点表和完整队伍名册。发送阶段顺序必须与客户端已知形成顺序一致，任何一个接收方的个性化投影不得混用不同队伍代际。 |
| RQ-008 | P2P 端点表应使用每个当前成员最近一次有效 `SET_UDP_IP_PORT` 值，并保持协议要求的 IP 字节和端口字节序。端点缺失时不得发送会使 A21 客户端形成路径崩溃的 `0.0.0.0:0`；应按同版本旧服写 `127.0.0.1` 内外网地址、BE 端口 10000、NAT 0、MTU 1500，同时不得改变队伍成员关系。 |
| RQ-009 | `CMD 0x000D LEAVE_PARTY` 仅接受空 body。普通成员离队后本人收到清队投影，其余成员收到同一新快照的刷新；队长离队则解散并清理全部成员。无队角色重复离队应幂等。 |
| RQ-010 | 当前连接结束、返回选人或被同账号新会话替代时，必须按精确会话代际撤销相关邀请、端点和成员资格，并把由此产生的队伍刷新/解散事件投递给仍在线的成员。旧连接的迟到清理不得移除新连接或新队伍状态。 |
| RQ-011 | 协议 handler 只负责解码、调用 Command 和发布 Command 产生的 Event/Notification；队伍规则与原子状态变更位于 Application/Abstractions 的领域边界，Application 不引用 Infrastructure。 |
| RQ-012 | 协议资料库必须记录本次四个观察请求的准确归属；对本规格实现的每个 C2S/S2C 协议记录字段、样本、实现映射、证据来源和实际验证等级，并同步索引与 catalog。 |
| RQ-013 | 服务端应以 PVF town area 的 `[gate]`（`TownAreaKind.Gate`）识别每角色私有的赛丽亚到达房间；此区域中的相同 town/area 数值不得产生跨角色同屏名册、进入/离开或位置通知。`[normal]` 与 `[dungeon gate]` 仍按共享城镇区域处理。 |
| RQ-014 | 首次形成或新增成员的完整队伍名册发送完毕后，服务端必须从同一不可变队伍快照再次向所有当前成员投影 `NOTI 0x0099` 实时摘要，使客户端在 slot 已存在时消费当前 HP；该补发不得改变邀请、队伍或端点状态。 |
| RQ-015 | `GET_USERINFO` 必须严格区分账号角色列表的既有 `target=0xFFFF, mode=2` 与指定角色详情的 `mode=3`。详情查询只允许由当前请求会话读取同一 Game listener 上唯一且仍为当前在线会话的目标，并在发送前重新验证请求者和目标的精确会话代际；离线、跨频道、歧义或已替代目标不返回旧详情。 |

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001 | 给定本次两个 31 字节真实样本，解码结果分别保留 NAT=`5`、`172.17.208.1` 内外网地址、UDP 端口 `30976`/`63752` 和 MTU=`1472`；给定任何无效固定前缀，已有有效端点保持不变。 |
| AC-002 | RQ-002,RQ-003,RQ-004 | Given 两个当前角色站在相同 listener/town/area，When 邀请者发送捕获到的 `0x000A type=0` 形态，Then 只向 uid 指定的目标投递一帧可解码的组队 `NOTI 0x0007`；自邀、跨频道、跨区域、离开城镇、非队长和满员场景均不投递且状态不变。 |
| AC-003 | RQ-005,RQ-006 | Given 一条有效邀请，When 目标用 `0x000B type=0` 响应，Then 邀请只消费一次并形成正确队长、成员与 slot；再次响应、超时后响应、任一方重连后响应或邀请者队伍已换代后响应均不改变状态。 |
| AC-004 | RQ-007,RQ-008,RQ-014 | 成功接受产生的跨会话发送按 `0x0099 -> 0x0008(仅邀请者) -> 0x000B -> 0x0009 -> 0x0099(名册后补发)` 分阶段完成；两个接收方从相同成员快照得到一致 uid/slot，端点记录优先来自各自最近一次有效上报、缺失时逐字段等于安全回落，编码器按文档长度和字节序输出。 |
| AC-005 | RQ-009 | 普通成员发送空 body `0x000D` 后本人无队、其余成员保留队伍并刷新；队长发送时全队清理；非空 body 被拒绝；无队重复请求无额外状态变化。 |
| AC-006 | RQ-010 | 对连接结束、返回选人和同账号替代分别执行生命周期测试：只有匹配的旧会话代际被撤销，所有尚存成员最终收到与当前领域状态一致的刷新或清队投影。 |
| AC-007 | RQ-011 | 架构测试证明 Application 不引用 Infrastructure；协议 handler 的业务状态变更仅经 Command，跨会话发送仅由 Event/Notification 投影产生。 |
| AC-008 | RQ-012 | 文档审查能从 catalog/index 导航到 `0x0002/000A/000B/000D` 与 `NOTI 0x0007/0008/0009/000B/0099` 的当前记录；`0x01A3`、`0x0122` 和 `0x000A type=1` 明确标为本次已观察但不属于本任务实现。 |
| AC-009 | RQ-001..RQ-015 | 当前 A21 双客户端实测显示：赛丽亚房间内互不可见；走到共享区域后目标出现正确邀请框，接受后两端显示同一两人队伍且头像立即显示 HP；查看同频道在线队友详情能够打开并显示目标信息；普通成员主动离队后两端 UI 恢复一致；服务端顺序与文档记录一致。实测前相关状态最多为 `Implemented`/待实机验证，不得写成 `ClientVerified`。 |
| AC-010 | RQ-001..RQ-015 | 全量解决方案构建成功，所有测试结果逐项通过，无跳过或仅凭进程退出码推断通过。 |
| AC-011 | RQ-013 | 给定两个已发布会话拥有相同 `[gate]` town/area，进入、移动和离开均不建立对方 audience；给定 `[normal]` 区域则仍建立双方 audience。真实 `town/SilverCrown.twn` 的 area 0 被解析为 `Gate`。 |
| AC-012 | RQ-014 | 投递顺序测试证明两个成员都先收到完整 `NOTI 0x0009` 名册，再收到第二次 `NOTI 0x0099`；补发帧逐字段包含相同快照的 uid、slot 和服务端当前 HP 百分比，且不依赖任一客户端先发送 `0x00A6`。 |
| AC-013 | RQ-015 | 三字节 `GET_USERINFO mode=3` 被独立解码和路由；同 listener 唯一当前目标产生 A21 详情响应，账号名单模式保持原行为；离线、跨 listener、重复 uid、请求者或目标代际在投影前变化时均不发送目标详情。 |

## Success Evidence

- **EV-001（AC-001..AC-008,AC-012,AC-013）**：新增领域、协议、详情投影与生命周期测试的逐项结果，以及完整代码审查结论。
- **EV-002（AC-009）**：双方的 C2S/S2C 观测、服务端对应日志和用户可见 UI 观察；可获取的样本归档到协议页相邻 `samples/`，无法由当前 ClientHack 逐帧落盘的部分明确以服务端接收/发送日志与 UI 结果标注证据边界。
- **EV-003（AC-010,AC-011）**：全量 `dotnet build`、生成的 TRX 中每个 `UnitTestResult` 的通过状态，以及 `PvfProbe` 对 `town/SilverCrown.twn` area 0 `[gate]` 的原文输出。

> 2026-09-11 证据算术更正：两条当前 A21 样本的端口字节分别为 `00 79`、`08 F9`（LE：30976、63752），MTU 字节均为 `C0 05 00 00`（LE：1472）。本更正只修复 AC-001 的样本期望，不改变范围或需求。
