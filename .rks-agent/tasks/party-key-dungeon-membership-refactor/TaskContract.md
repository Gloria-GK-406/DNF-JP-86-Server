# TaskContract: 以稳定 PartyKey 统一副本组队成员真源

## Context

### Source Request

用户要求：“地下城本身绑定一个partyid（这个id不是真实id，而是真实+虚拟队伍都可以用）”；“实例保持住，但是让client认为换了新的队伍”；“id是给client看的，key才是我们内部看的。id不再出现在领域范围内”；新 Cell 应“按partykey找char，然后遍历完成cell创建”。对于成员离开，用户明确排除队伍版本复核与整次 Cell 重算：“如果人退出了，直接查到没这个人跳过就好。”最终授权：“对，范围就是这样。我们用任务契约来重构吧。”

### Current Situation

当前真实队伍在领域服务中以客户端可见的 `ushort PartyId` 标识，虚拟队伍共享 `PartyId=0`。副本有独立 `RunId`，但同时保留入场成员和活跃成员集合；通知又查询实时队伍成员并与副本成员取交集。新 Cell 使用入场时冻结的成员、队长和人数。城镇内队长离队虽在服务端留下新队长，客户端却因同 ID 名册换位而丢失队伍；上游以更换客户端队伍 ID 的投影解决该问题。上述状态使队伍成员资格存在两个裁决来源，且客户端标识变化会牵连副本设计。

## Goal

真实与虚拟队伍均有稳定、可由组队服务解析的内部 `PartyKey`；组队成员关系只有组队服务一个领域真源。地下城实例在生命周期内绑定 `PartyKey` 和自己的 `RunId`，以当前队伍成员裁决操作、新 Cell 的成员相关内容及通知；客户端队伍 ID 的换代仅影响协议投影，不使原地下城实例重建或中断。

## Scope

### In

- 重构真实/虚拟队伍的内部身份与查询，使领域业务以 `PartyKey` 定位队伍，客户端队伍 ID 不再承担领域身份。
- 调整队长离队后的队伍与客户端投影：留下的成员承接队长，客户端收到可正确识别的新队伍代际，队伍设置及业务连续性保留。
- 调整地下城入场、成员操作、过图、Cell 创建、成员相关掉落与通知，使副本绑定稳定 `PartyKey`，成员资格取自当前组队服务；保留必要的每角色副本进度、准备状态和连接安全校验，但不让它们成为第二份成员真源。
- 使离队/退图/连接清理后的副本与队伍关系一致：离开者不再参与后续操作、通知或专属发放，留下的人继续原 `RunId`；图外角色不能仅凭加入队伍进入运行中的副本。
- 覆盖真实多人队、虚拟单人队、队长离队及副本成员变化的自动化回归，并给出实机验证方式。

### Out

- 不修改与该重构无关的怪物、掉落概率、剧情任务规则、结算和 P2P 协议语义。
- 不以队伍成员变化为由取消、重试或整体重算已在创建中的 Cell；成员专属结果在实际落地或发放时确认归属人仍属当前队伍，离开者的结果跳过。
- 不将会话或连接代际作为队伍成员领域身份；它们只保护消息不被发给旧连接。
- 不包含合并、推送、清理工作区或部署运行中的 Host；这些收尾动作分别取得授权。

## Constraints

- `PartyKey` 在一支队伍的业务生命周期内稳定；客户端队伍 ID 换代不得改变运行中副本所绑定的内部队伍身份或 `RunId`。
- 真实与虚拟队伍均须能按内部身份得到当前队伍内容；虚拟队伍不能共用一个无法区分角色的内部身份。
- 入场、离队及退图的已提交状态不得允许图外成员取得当前副本操作或通知资格。
- 已生成的 Cell 内容属于该 Cell；队伍成员变化不应使整个 Cell 回滚或重算。成员专属结果对已离队者跳过，不转赠其他成员。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 真实和虚拟队伍分别有可解析且互不混淆的稳定内部身份；客户端队伍 ID 不参与领域身份判定。 | 领域/API 使用点检查及真实、虚拟、客户端 ID 换代回归测试。 |
| SC-2 | 两人队长离队后，服务端留下的新队长及队伍设置正确；客户端收到旧队伍退役与新队伍建立后，仍能显示单人队及保留队伍提示。 | 服务端状态和通知顺序测试；A21 双客户端实机观察。 |
| SC-3 | 运行中的副本在队长离队及客户端队伍 ID 换代后保持原 `RunId` 和既有 Cell；新队长、剩余成员能继续操作，离开者和图外成员不能操作或接收副本通知。 | 副本领域与协议回归测试，以及双客户端离队后继续过图的实机观察。 |
| SC-4 | 新 Cell 以 `PartyKey` 查询当前成员生成成员相关内容，不再沿用入场时冻结的队长/人数作为当前队伍；离开者的专属结果跳过，现有共享内容不因离队整体重算。 | Cell 创建、成员退出、专属掉落及共享内容回归测试。 |
| SC-5 | 单人虚拟队伍仍可完成选图、入场、过图、掉落和退出；多人队伍原有流程不因身份分离而退化。 | 有针对性的单人/多人集成测试及构建结果。 |

## Authorization

| Capability | Evidence | Authorized scope |
|---|---|---|
| task | 用户先明确“id是给client看的，key才是我们内部看的”“按partykey找char”，排除版本复核与 Cell 重算，随后说“对，范围就是这样。我们用任务契约来重构吧”。 | 创建任务契约并执行该组队/地下城身份与成员真源重构及其验证；不含合并、推送、工作区清理和运行中 Host 部署。 |

## Assumptions

- “退出后跳过”适用于成员专属的尚未实际落地或发放的结果；已经提交给 Cell 的共享内容保留。若某条现有奖励规则无法区分这两者，在规格阶段基于代码证据限定处理，而不自行改变掉落概率。
- 连接断开可能暂时导致成员尚未就绪；准备状态与连接可达性不是第二份成员关系。已提交的离队/清理才改变组队成员资格。
