# Implementation Plan: 以 PartyKey 统一副本组队身份

## Planning Choice

内部身份、客户端投影、副本资格和 Cell 输入有真实的依赖顺序。先落地身份接口后才能迁移消费者；旧客户端换代的运行证据又会影响投影实现细节。采用渐进 Task Units，各单元把自身代码与回归放在一起，跨会话仍可从清晰的接口和检查点继续。这里不预写远端细节。

## Approach and Shared Decisions

- 领域内统一使用一个可区分真实/虚拟的 `PartyKey`，真实队伍在队长换届时仍持有原 Key，虚拟队伍按角色可反查。`PartyService` 保存并查询当前成员与队长；区域目录索引也使用内部身份。
- 客户端 `ushort` 队伍 ID 移到协议投影，由 `PartyKey` 对应当前客户端代际。队长离队发布不可变的旧/新代际通知；旧 ID 清除、新 ID 完整建立必须对同一收件人的发送保持顺序，不能把客户端 ID 反传回组队/副本领域。
- 地下城聚合保留 `RunId`、Cell 和每角色运行进度，仅绑定 `PartyKey`。成员资格查询 PartyService；个人准备、归属、进度不是独立 roster。客户端连接代际只在发包边界防旧连接，不入领域成员判定。入场、离队/退图的应用编排保证提交后的队伍与运行关系一致，并禁止图外成员通过加入运行中队伍获得副本资格。
- 新 Cell 在创建当下按绑定 Key 取得队伍快照作为规则输入，不再复用入场快照；该输入不持久化为副本成员真源。Cell 既有内容保持原状；成员专属结果在真正落地或发放时按当前 Key 查归属人，不在队则跳过，不进行整格版本复核/重算。共享结果依现有规则只生成一次。
- 保持“package handler 调 CMD 执行业务、调 Event 发通知；CMD 经领域服务/实例执行行为；规则由规则服务获取”的项目边界。跨域协调留在应用流程，不建立 PartyService 与 DungeonRunService 的循环依赖。

## Verification

每个单元先用失败回归明确其行为边界，再实施并运行相关项目测试。完成时进行协议、应用、主机相关测试和全解决方案构建，审视领域内客户端 ID 残留、旧连接收件人、离队与新 Cell 边界。最终将 A21 双开测试作为客户端效果证据：城镇队长退出后单人队与提示、地下城原 `RunId` 连续过图、虚拟单人流程。未获部署授权前不更改运行中的 Host；实机未执行时明确标为待验，不冒充完成。

## Next Planning Boundary

先细化并执行 T-001，检查真实 `PartyState`、虚拟 `PartySnapshot.Virtual`、PartyService 查询/目录的所有身份使用点及现有测试。得到稳定身份接口后再细化 T-002；副本/Cell 的具体迁移 Task 以该接口和客户端投影的实际结果为输入。
