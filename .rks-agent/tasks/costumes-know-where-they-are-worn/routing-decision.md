# Routing Decision

任务：`costumes-know-where-they-are-worn`
契约：`./TaskContract.md`（revision 1, state ready, SC-1..SC-8）

## SDD Readiness

**就绪，而且本件的证据是这一系列里最硬的一次。**

- **映射有三个独立来源且逐行吻合**：实机量得的 11 个槽号、档案读出的 11 个
  `[equipment type]` 字符串、上游 `EquipmentType` 枚举的 11 个名字与序号。
  三列没有一处冲突，上衣那一格另有两次更早的独立观测。
- **要改的位置只有一处**：`PvfEquipmentSlots.ByName` 的字典字面量，加 11 行。
- **槽 11 的空缺不是未知，是已查明**：全档案 118479 条 equipment 索引穷尽扫过，
  以 `avatar]` 结尾的类型恰好 11 种，**没有第 12 种**。
- **有可执行判据**：全量套件在 `80bdb144` 实测 2335/2/0。

**一处不是「未就绪」但必须在执行时做掉的事**：上一件在 `PutOnAsync` 留了一处点名，
要求「给装扮槽补上名字的那个人」回来重新判断「被顶下来那件能否回到源格」。
本件正是那一天，契约把它写成了 SC-5。

## Marginal Control Value

值得上 SDD，但保护的东西与前两件都不同：**这次改动本身几乎不可能写错，
风险全在它引爆的下游。**

- **加 11 行字典项，写错了判据当场会红**——三个来源互证，连「值填错」都很难。
- **真正的风险是它让一整条路第一次真的通电**：时装能穿上之后，
  NOTI `0x0002` 子类型 1 与 ITEM_LIST 装备栏路径会**第一次带着真时装的外观块上线**。
  那两条路的编码在 `ec2ef1b6` 与更早的成果里写好了、有判据钉着，**但从来没有真时装走过**。
  本件不负责验证它们（那是所有者说的「做完以后一起测试」），
  **但必须在成果里把这件事说清楚**，否则下一个人不知道该测什么。
- **第二条是 `PutOnAsync` 那个点名**。上一件在同一个方法里因为「问错了问题」
  加过一次判定又回退，**这次要在同一处做一个正着的判断**。
  做错的方式有两种：漏做（留下一个前提已消失的注释），
  或者做过头（再加一次越出授权面的判定）。**契约 Requires Confirmation 明写要先报告再做。**
- **第三条是记账**。上一件在搜索集上栽了两次——范围写对了没执行、承认之后只补跑一条。
  SC-8 因此要求「声明的每一条命令都要真的敲下去，并把命中数写进清单」。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Rationale: 三件事——补键、做掉 `PutOnAsync` 的点名、更正两处记载——共享同一个验收口径：
  「时装能穿上，且非时装的穿戴行为逐值不变」。按本仓规矩，同一口径下的多段工作量属于一个成果。
  issue #13（耳环/契约兽/快捷栏）有独立的验收口径且已单独立项，写进了 Scope Out。
- Reroute conditions:
  - 若 `PutOnAsync` 的判断结论是「需要加一次判定」，那是一处**新的授权外行为变化**，
    回到路由与所有者重议；
  - 若补键之后非时装的穿戴行为发生任何变化，说明「只加字典项」这个结构性假设不成立；
  - 若档案里出现第 12 种 `avatar]` 类型，穷尽扫描的结论被推翻，回到路由重议范围。

## Controller Selection

- Controller: `sdd-lite`
- Profile source: `code-bugfix`
- Rationale:

**要挡的两条失败路径都不在「加 11 行」上**：一是 `PutOnAsync` 那个点名做漏或做过头，
二是记账——本件会推翻若干条现存记载（量具说明书的用途、`AuraSkinAvatar` 的位置），
而上一件正是在记账上耗掉了七条阻塞里的六条。
挡住这两条需要且只需要：一份把验收边界与「哪些行为必须不变」钉死的持久 Spec，
加一次对**完整**结果的独立评审。`sdd-lite` 的
spec → implementation → review → verification 恰好是这两样。

**为什么更重的 `sdd-standard` 不对**：Standard 的独有控制是 `plan.md`。
本件没有可挂的实施决策——改动点是一个字典字面量，映射三源互证已定，
`PutOnAsync` 那处是一次判断而非一串有序步骤。写成 plan 只是把 spec 抄一遍。

**为什么更轻的一档不对**：更轻是不留持久 Spec、靠一次确定性检查收口。
这里不行：**判据全绿证明不了 `PutOnAsync` 那个点名被做掉了**——
漏做它不会让任何判据变红，只会留下一段前提已消失的注释，
而那正是上一件被独立评审抓住三次的形态。它需要写下来的验收条款才能被对着核。

**为什么不是 `sdd-governed`**：硬性门槛一条都不沾——不涉及安全、凭据、隐私、
财务法务、不可逆外部变更、或无恢复手段的数据丢失。最坏后果是时装穿到错误的槽，
可逆，改动全在本地未推送的任务分支上。
