# Specification: 时装知道自己穿在哪一格

## Why and Outcome

玩家把时装拖到装扮槽，服务器答 `NotWearable`：档案说不出它该进哪一格。
根因是 `PvfEquipmentSlots.ByName` **一个以 `avatar]` 结尾的键都没有**，
而那张表自己的注释早就写着「0..11 是装扮槽，穿戴件从 12 开始」——知道有这些格，只是从没填。

要交付的结果是：**那 11 个键在表里**，于是时装能穿上、拖错槽被拒。

映射不是猜的，是**三个独立来源逐行吻合**：实机量到的槽号、档案自己声明的
`[equipment type]` 字符串、上游 `EquipmentType` 枚举。三列的对照表在契约的 Context 里，
本 Spec 不重复。

**本件不做实机验证。** 所有者说「做完以后我们再一起测试」——那是交付之后的事。

## Scope

**做**：补 11 个键；做掉上一件留在 `PutOnAsync` 的那处点名；判据；更正两处记载与量具说明书。

**不做**：issue #13（耳环/契约兽/快捷栏）；槽 11 的键（档案里没有模板声明它）；
`listParam16`（#12）；任何协议帧的字节布局。

### RQ-005：另一个读者

`ByName` **有两个读者**，本 Spec 关心的只有一个是显然的：

1. `PvfEquipmentSlotDefinitionSource` —— 一件装备问「我穿在哪」。**这是本件要修的那条。**
2. `PvfInitialEquipmentDefinitionSource` —— **建号起始装备**：档案的创建表里
   「槽名 + 物品号」成对出现，槽名查不到就把 `pendingSlot` 置空、**那一项被丢弃**。

**第 2 条是本件的反向面。** 补键之前，创建表里任何以 `avatar]` 结尾的槽名都查不到、被丢弃；
补键之后，**同一行会变成一次真的发放**，新角色身上多出一件时装。

**必须查清**：档案的建号表里到底有没有出现过装扮槽名？

- 若**没有**：建号行为逐值不变，如实写明「查过，零命中」并给出查法；
- 若**有**：那是一处**本件带出来的行为变化**，**停下报告**（契约 Requires Confirmation 第一条），
  不得当作「顺带修好了」。

**这一条不能靠判据全绿来回答**：今天没有任何用例走建号表里的装扮槽名，
所以无论有没有，判据都不会变色。**必须真的去档案里查。**

### RQ-006：`PutOnAsync` 的点名

上一件（`80bdb144`）在 `PutOnAsync` 里不判断「被顶下来那件能否回到源格」，理由是
**今天装扮槽上站不了任何东西**（`ByName` 最低到 12），并明写：

> **That stops being true the day those slots get names** -- which is exactly what giving
> costumes a slot map amounts to. Whoever does that has to come back here and decide whether
> what comes off a costume slot can go back where the arriving costume came from.

**本件正是那一天。** 必须给出结论，并把「今天站不了任何东西所以无从发生」这段理由替换掉。

**结论的候选与它们的后果**：

- **不需要判定** → 只改注释，无行为变化。**理由必须是可证伪的**，不能是「大概不会出事」。
- **需要判定** → 那是一处**新的、授权外的行为变化**。上一件正是在同一个方法里
  因为加了一次这样的判定而被判越界并回退。**先报告再做。**

**Spec 不预设答案。** 但它要求答案必须能被下面这样检验：给出「被顶下来那件」的
**可达取值范围**，以及「源格」对它的准入判定，两者放在一起看。

### RQ-007 的一处已知波及

补键之后，`WornSlotForAsync` 对时装第一次返回非空。这使**两条早已写好、但从未有真时装走过的路**
第一次通电：NOTI `0x0002` 子类型 1 的穿戴条目、以及 ITEM_LIST 装备栏容器里的时装条目
（两者都会写外观块）。

**它们的编码与判据在更早的成果里就有**，本件不改一个字节。
但**成果里必须写明这件事**，因为它正是所有者说「做完以后一起测试」要测的东西。
**不写明就等于让下一个人不知道该看哪里。**

### AC-003 场景

```gherkin
Given 角色的装扮栏槽 0 有一件 [coat avatar] 时装
  And 装备栏槽 3 是空的
When 请求把它从装扮栏移到装备栏槽 3
Then 移动成功，装备栏槽 3 有它、装扮栏槽 0 空
  And 结果带着该时装的模板号
```

同一件事从**主背包**出发也要有一条——这两条源列表在 `PutOnAsync` 里走的是同一段代码，
但一条判据只证明一条路。

### AC-006

结论必须被判据钉住，不能只写在注释里。若结论是「不需要判定」，
判据形态是：**一次真的交换走通**——装扮栏槽 0 有 `[coat avatar]` A，
装备栏槽 3 已经穿着另一件 `[coat avatar]` B，把 A 拖到槽 3：
A 穿上、**B 回到装扮栏槽 0**、两端都对。

这条判据同时证明两件事：交换在有了槽名之后**真的可达**（不再是空真），
以及被顶下来那件**确实落回了源格**。

|---|---|
