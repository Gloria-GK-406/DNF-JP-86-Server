# Specification: 一条命令量出本仓的方法级变更风险

## Why and Outcome

维护者要动 `Server/src` 里那 59506 行的任何一块时，眼下没有任何依据判断「这块的
控制流有多绕、有没有测试网兜着」。本 Spec 交付的东西让他跑一条命令，拿到一份
**按方法排的变更风险清单**，并且下次、下个月、换台机器再跑，拿到的是同样口径的
另一份快照，而不是重新发明一套测法。

「可信」在这里有具体含义：报告里每一个 CRAP 数字都能追回到同一份代码快照的
复杂度与覆盖率输入；报告里没有数字的方法，能说清是「实测没被覆盖」还是
「我们没能把它和覆盖率对上」——这两件事对后续决策的含义完全相反。

## Scope

**在内**：`Server/86JP.Server.slnx` 中 `/src/` 目录下 10 个生产项目的 C# 源码。

**在外**：`Server/tests/**`（测试代码本身）、`Tool/**`、`ClientHack/**`、
`Docs/**`、`protocol/**`、任何 `bin/`、`obj/` 下的产物。采集工具自身的代码也在外，
即使它落在本仓内。

## Definitions

### D-1 函数宇宙（canonical function universe）

被测单位是**源码中声明的成员**：方法、构造函数、终结器、属性/索引器/事件的
访问器、运算符、显式接口实现。一个成员在源码里出现一次，就在宇宙里出现一次。

编译器生成的方法（lambda 闭包、局部函数、`async`/迭代器状态机的 `MoveNext`、
主构造函数与 record 合成成员）**不是独立单位**，按显式规则归并回其声明处的源码成员；
其覆盖单位并入该成员。归并不掉的生成方法进入单独的 `generated-unmapped` 分区计数，
**不得静默丢弃**，也不得混进源码成员的分布里。

局部函数与 lambda 的判定点计入其所在的源码成员——这与覆盖率的归并方向一致，
两端口径必须相同。

### D-2 CRAP

对每个函数 `f`：`CRAP(f) = C(f)² · (1 − Cov(f))³ + C(f)`

`C(f)` 为该成员的圈复杂度，`Cov(f)` 为同一成员、同一快照的覆盖率，归一到 `[0,1]`。
输入与结果按未舍入值保存，只在展示时舍入。

CRAP 只在这一粒度存在。类、文件、目录、项目、全域**只有分布**，没有分数：
不得把复杂度或覆盖率先聚合再套公式，不得把和值或均值叫作某个类/文件/项目的 CRAP。

### D-3 证据状态

每个在范围内的成员必须落在且只落在一个状态：

| 状态 | 含义 |
|---|---|
| `computed` | 复杂度与覆盖率都取到并成功对接，CRAP 已算 |
| `measured-zero` | 覆盖率报告**证明**该成员存在可执行单位且一个都没被覆盖（`Cov = 0`，算入 `computed` 口径的分布） |
| `missing` | 该成员对不上任何覆盖率证据 |
| `ambiguous` | 存在多个互相竞争的映射，无法安全裁定 |
| `excluded` | 清单里明确排除 |

`missing` 与 `ambiguous` **不得**被当作 `Cov = 0` 进入实测分布。报告可以另给一个
明确标注的悲观情景（把它们按 0 算），但必须与实测分布分开呈现。

### D-4 运行目录时间戳

`YYYY-MM-DD_HH-mm-ss`，取本地时间。字典序即时间序；不含冒号（Windows 拒绝）、
不含空格（省得每条命令都要加引号）。同秒冲突以确定性后缀区分。
ISO 8601 瞬时、偏移量与时区记在清单里。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 采集系统的实现与钉住的配置留在仓库内稳定路径上；临时目录只放缓存与中间产物，不得是系统的唯一副本 |
| RQ-002 | 有且只有一条记录在案的入口命令，从新 shell、在仓库根即可发起完整的「构建 → 带覆盖率跑测试 → 采集 → 计算 → 出报告」 |
| RQ-003 | 每次调用在仓库根 `.crap/` 下新建一个按 D-4 命名的运行目录；既有目录不被覆盖、不被复用、不被删除 |
| RQ-004 | `.crap` 不进入 git 追踪，且该排除随仓库分发（不是只在本机生效的本地排除） |
| RQ-005 | 运行目录在采集开始前就建好，并携带状态：`running` → `complete` / `partial` / `failed`；失败的运行保留其证据 |
| RQ-006 | 运行目录自描述：一份清单指名本次的仓库快照、范围、包含/排除规则、函数种类政策、复杂度定义、覆盖率口径、工具版本、构建配置、执行命令，以及每件产物的路径与格式；解读该次运行不依赖其他运行目录 |
| RQ-007 | 生产函数清册独立于覆盖率报告建立，其完整性不取决于覆盖率工具报了哪些行 |
| RQ-008 | 复杂度与覆盖率按路径 + 容器 + 限定符号/签名 + 源码区间对接；不得只按短名对接；重载、分部类、嵌套类型、泛型、显式接口实现、状态机、重复行必须被识别 |
| RQ-009 | 每个在范围内的成员有且只有一个 D-3 状态；各状态计数与函数明细总数对账一致，无静默丢行 |
| RQ-010 | CRAP 按 D-2 计算，只对复杂度与覆盖率同属一次快照的记录计算 |
| RQ-011 | 函数明细以机器可读格式落盘，每条保留：项目、规范化源码路径、容器、限定符号与签名、源码区间、成员种类、生成/映射状态、复杂度值、已覆盖与总单位数、覆盖率与其口径、证据状态、CRAP（可算时）、排除或歧义理由，以及回指原始证据的引用 |
| RQ-012 | 生成类 / 文件 / 项目 / 全域四层分布视图，每层给出在范围内、已算、缺失、歧义、排除的计数，以及已算集合的最小值、中位数、P75、P90、P95、最大值，风险分档计数与占比（含 `CRAP > 30` 警戒线之上），Top N 及其源码位置，复杂度×覆盖率四象限 |
| RQ-013 | 均值与和值若出现，须标明是「函数分数的均值/总和」并说明其对规模敏感，不得替代分布与尾部集中度 |
| RQ-014 | 测试以真实入口执行并采集覆盖率；测试的通过/跳过/失败数与退出码如实记录；部分执行、缺失依赖、未测量的范围必须在得出全局结论之前先被呈现 |
| RQ-015 | 出一份人可读报告，顺序为：证据有效性 → 分布形态与风险集中 → 排序后的发现 → 改进选项 → 局限 |
| RQ-016 | 每条排序后的发现指名具体方法与聚合范围，给出复杂度、覆盖率、CRAP、分位/分档、证据状态，并把实测事实与推断分开写 |
| RQ-017 | 每条改进选项绑定到观察到的风险来源（复杂度主导 / 覆盖主导 / 叠加 / 集中 / 证据缺口 / 上下文放大），反事实的「补测后 CRAP 会变成多少」须标注为反事实计算而非承诺 |
| RQ-018 | 用该系统跑出一次真实基线运行，其产物完整留在 `.crap/` 下 |
| RQ-019 | `Document/` 下有一份说明，让维护者不读工具源码也能复跑并解读结果 |
| RQ-020 | 交付不改变 `Server/src` 与 `Server/tests` 下既有代码的行为；新增 .NET 工程服从 net10.0、Nullable、TreatWarningsAsErrors、中央包管理 |
| RQ-021 | 若任何可信的方法级覆盖率映射都取不到，不得编造 CRAP：降级为明确标注的复杂度诊断或采集阻塞报告 |
