# Specification: 婚姻单一实体与阶段记录

## Why and Outcome

「这一对现在到了哪一步」目前要从求婚、预约、婚礼三张表推导，而且有六处各自推导、口径不一。每加一个婚姻功能，就会多一处推导，也多一个出错的机会。

本次交付后：
- 婚姻业务只有一个领域实体；
- 一对角色的当前阶段由一条关系记录直接表达，其余功能都读这个阶段；
- 玩家可见的协议行为、金钱和物品结算保持不变，刻意修正单独列出。

设计依据见 `Document/MarriageAggregateDesign-20261017.md`（下称「设计稿」）。本 Spec 只写交付物和判定标准；设计稿里的实现细节（表名、组件名、签名）可以在 Plan 中依据代码调整，但必须满足下面的要求。

## Scope

**包含**
- 现有婚姻行为的表征测试；
- 关系记录与阶段迁移；
- 已有数据回填；
- 8 个服务合并为一个实体，内部组件化，对外 4 个接口，切换全部调用方并删除旧接口；
- 两项刻意修正；
- 文档更新与实机回归清单。

**不包含**：协议字节和业务规则的改变、离婚等新玩法、客户端改动、可空注入清理，以及对运行库执行迁移。

## Definitions

- **关系**：一对角色从求婚开始的婚姻关系，以现有 relation id（即 `marriage_proposals.id`）为身份。一个角色同时至多有一条活跃关系。
- **阶段**：直接存储在关系记录上的整数，取值只追加、不重排。

| 值 | 阶段 | 03D0 state |
|---:|---|---:|
| 0 | Proposed | 0 |
| 1 | Engaged | 1 |
| 2 | Requested | 1 |
| 3 | Preparing | 2 |
| 4 | Married | 4 |
| 5 | Closed | 0 |

  值域预留到 15，供离婚阶段使用，不需要重建表。没有关系时 03D0 state 也是 0。
- **有效阶段**：读路径看到的阶段。它把已经到期、但还没落库的 Proposed 或 Requested 按到期后的结果来呈现，不写库。
- **一对的判定**：一组会话属于某关系，当且仅当每个会话的「账号 + 角色」都和该关系的参与者一致，并且关系没有关闭。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 婚姻业务由一个领域实体实现，对外暴露 4 个按调用方划分的接口：只读视图、新人操作、婚礼现场、婚前任务，由同一个实例实现。原 8 个婚姻领域服务的实现类被删除；婚前任务接口保留签名，作为 4 个接口之一，其余 7 个旧接口被删除。每个调用方只注入它用到的接口。 |
| RQ-002 | 每条关系的当前阶段直接存储在关系记录上。所有「是否订婚、已预约、筹备中、已婚」的判断都读阶段；03D0 state 由阶段按 Definitions 的表投影得出。 |
| RQ-003 | 阶段只按迁移表变化（见下文），迁移只能在同一事务里伴随它的副作用一起发生。不在表里的迁移被拒绝。 |
| RQ-004 | 不变量 I1–I5 始终成立（见下文）。 |
| RQ-005 | 求婚和预约的到期语义不变：超时，或任一方会话不再有效，即视为到期。写路径在加载关系时把到期迁移落库；读路径只计算有效阶段，不写库。 |
| RQ-006 | 实体内部由职责组件构成：组件之间互不依赖；只有关系账本写阶段、写心意点；实体本身不直接依赖任何存储；阶段写入带 revision 并发检测，冲突时以现有的 `Stale` 失败返回。 |
| RQ-007 | 启动时幂等回填：每条已有关系按回填表得到阶段和关联字段；旧表结构与数据不变；无法判定的情况计数写日志，不编造阶段或时间。 |
| RQ-008 | 心意点的读写以关系记录为准。过渡期内同时写入旧婚礼行的心意点列，回退到旧二进制时点数不丢失。 |
| RQ-009 | 除 RQ-010 外，行为目录 B-01…B-16（见下文）在重构前后一致。 |
| RQ-010 | 刻意修正：(a) 原先六处「是否为一对」统一按 Definitions 判定；(b) 心意点归属于关系（与 RQ-008 一起）。 |
| RQ-011 | 遵守 `AGENTS.md` 分层：Application 不引用 Protocol；命令处理器只注入 `*DomainService` 和 `*DomainStore`；组件按三层约定向规则服务取规则。 |
| RQ-012 | 设计稿开头补上落地状态和与实现的偏差；受影响的仓库文档同步更新；交付双端实机回归清单。 |

### 迁移表（RQ-003）

| # | 从 | 触发 | 守卫（全部满足才迁移） | 到 |
|---|---|---|---|---|
| T1 | 无活跃关系 | 求婚 | 双方会话有效、账号和角色都不同、同城同区、等级与异性配对符合规则、双方都没有活跃关系 | Proposed |
| T2 | Proposed | 接受 | 未到期、同城、资格复核 | Engaged |
| T3 | Proposed | 拒绝 | — | Closed |
| T4 | Proposed | 到期 | — | Closed |
| T5 | Engaged | 申请预约 | tier 与 waitIndex 合法、双方会话有效、同城、是一对、两人的试炼和材料任务都已完成并绑定本关系、申请人金币足够 | Requested |
| T6 | Requested | 接受预约 | 未到期，T5 守卫全部复核；两人教堂准备成功，扣费成功 | Preparing |
| T7 | Requested | 拒绝、到期，或接受时复核失败 | — | Engaged |
| T8 | Preparing | 到点，两人都在场且都已入场 | — | Married |
| T9 | Preparing | 到点，有人不满足 T8 | — | Engaged |

T6 中任一步失败：整个事务回滚，然后照旧由 Protocol 侧再派一次 response=2 的命令，走 T7。

已有的重复请求幂等行为保持不变：相同的待答求婚或预约再次提交时返回原记录；已答复后再次提交相同答复时返回成功。

### 不变量（RQ-004）

- **I1** 一个角色至多一条活跃关系。
- **I2** 阶段为 Requested、Preparing 或 Married ⇔ 关系记录引用一条预约。
- **I3** 阶段为 Preparing ⇔ 该关系恰好有一条进行中（phase=0）的婚礼。
- **I4** 阶段为 Married ⇔ 该关系恰好有一条已完成（phase=1）的婚礼。
- **I5** 阶段只由关系账本写入，每次写入都检查 revision。

### 回填（RQ-007）

| 已有数据 | 阶段 | 引用的预约 | 其它字段 |
|---|---|---|---|
| 求婚 Rejected / Expired | Closed | 无 | — |
| 求婚 Pending | Proposed | 无 | — |
| Engaged，且有已完成的婚礼 | Married | 该婚礼的预约 | 完成时刻（0 视为未知，记为空）；心意点取自该婚礼行 |
| Engaged，且有进行中的婚礼 | Preparing | 该婚礼的预约 | — |
| Engaged，且有 Pending 预约 | Requested | 该预约 | — |
| Engaged，有 Reserved 预约但没有婚礼行 | Engaged | 无 | 计为异常并写日志 |
| 其它 Engaged | Engaged | 无 | — |

所有回填行的阶段起始时间都写迁移时刻，revision 从 1 开始；重复启动不会改变已有的关系记录。

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001 | `Server/src` 中旧 8 个实现类名、以及除 `IMarriageQuestDomainService` 外 7 个旧接口名的搜索结果为零；4 个新接口由同一个类实现，DI 解析出的实例相同；按设计稿 §4.2 列出调用方和注入点，没有调用方注入它不用的写接口。 |
| AC-002 | RQ-002 | `Server/src` 中不再存在从婚礼 phase 或预约 state 推导「已婚」「已预约」的业务判断（仅允许组件维护自己的明细状态）；03D0 投影测试覆盖 0–5 每个阶段以及无关系的情况。 |
| AC-003 | RQ-003 | 阶段规则的穷举测试：6 个阶段 × 全部触发，每个组合要么得到迁移表规定的结果，要么被拒绝；T1–T9 各有一条经实体走通的用例，断言阶段和同事务副作用。 |
| AC-004 | RQ-004 | I1–I5 各有判据：I3、I4 在 T6、T8、T9 后以及回填后核对婚礼行数量；I5 由架构判据加并发冲突用例证明（同一 revision 的第二次迁移得到 `Stale`，阶段不变）。 |
| AC-005 | RQ-005 | 读路径在 Proposed / Requested 到期后返回到期后的有效阶段，且数据库不变；写路径在同样条件下落库到期迁移。 |
| AC-006 | RQ-006 | 架构判据（反射遍历构造器）：组件互不依赖；只有账本接受关系 store；实体不接受任何 `*DomainStore` 或 `*Persistence`。另有一条反例用例证明判据会拒绝违规。 |

| AC-009 | RQ-009 | 表征测试覆盖 B-01…B-16，**在重构前写成并通过（基线记录 EV-001）**，重构后不改断言照样通过（只允许改类型名和接线）；现有婚姻应用测试和协议 codec 测试全部通过。 |
