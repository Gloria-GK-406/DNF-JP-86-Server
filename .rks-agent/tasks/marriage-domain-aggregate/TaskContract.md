# TaskContract: 婚姻业务收为单一实体，阶段由记录直接表达

## Context

### Source Request

用户希望把婚姻业务的 8 个领域服务（Proposal、Engagement、Quest、Ceremony、Church、Wedding、LovePoint、Guestbook）合并成一个聚合服务。理由是它们都要检查角色的情侣关系和进度，而且每个都小而散。

讨论后用户确定了以下几点：
- 对外实体只有一个；实体内部按职责拆成小组件，由同一个实例实现多个接口。原话：“对外实体只有一个，内部有你说的实现是可以的”。
- 阶段要直接记录，不靠推理。原话：“每个阶段是一个准确的，不是靠推理。而是当两人开始婚姻状态后，那个婚姻状态记录就直接表达当前状态……其余的功能靠这个来决定如何处理”。

用户审阅了设计稿 `Document/MarriageAggregateDesign-20261017.md` 和关系图，同意按「表征测试 → 关系表与账本 → 合并实体 → 行为修正」的进度执行。设计稿 §11 的四项按 Agent 的建议决定：
1. 阶段值域预留离婚阶段，不需要日后重建表；
2. 祝词簿归入婚礼现场接口；
3. 保留「预约待答」阶段；
4. 任务服务对婚姻服务的可空注入不在本次范围内。

### Current Situation

基准：`task/next-round-20261013` @ `5a0cbed0`。婚姻业务现在由 8 个领域服务实现，合计约 1000 行。服务之间直接读写彼此的存储。

- 情侣关系是「求婚」记录（`MarriageProposalState` 只有 Pending、Engaged、Rejected、Expired 四种状态）。
- 「已婚」从婚礼表推导，「已预约」从预约表推导，03D0 线上状态再由这两个布尔值拼出来。
- 结婚后预约记录一直停在 Reserved。
- 「是否为一对」的判定散落在六处，口径不一：有的核对账号，有的不核；有的排除已婚，有的不排除。
- 心意点存在婚礼行上。
- 婚姻有应用层用例（Proposal、Ceremony、Church、Engagement 共 41 条），覆盖了大部分主流程：婚礼准备、开场、请柬与礼金、取消、心意点、最后一分钟锁、婚前任务。但多个失败码分支、清理重试、祝词簿访问矩阵等还没有逐条覆盖。

## Goal

婚姻业务由一个领域实体承载，对外按调用方暴露少数几个接口。一对角色当前处于哪个阶段，只由一条关系记录直接表达，其余婚姻功能都依据这个阶段决定如何处理。

重构完成后，玩家可见的协议行为与金钱、物品结算保持不变。刻意的行为修正单独列出，并有测试覆盖。

## Scope

### In

- 先用测试固定现有婚姻行为，尤其是当前没有应用层用例的部分，再开始重构。
- 为每对情侣引入直接记录阶段的关系记录：
  - 覆盖求婚、订婚、预约待答、教堂筹备、已婚、关闭；
  - 为离婚阶段预留值域；
  - 写清阶段迁移规则和不变量；
  - 由唯一的写入者负责阶段迁移，并检测并发冲突。
- 启动时对已有数据库做幂等回填，旧表和旧数据保留。心意点在过渡期保持可回退。
- 把 8 个服务合并为一个实现类：
  - 内部拆成职责组件，组件之间不互相依赖，实体不直接接触存储；
  - 对外发布按调用方划分的接口（只读视图、新人操作、婚礼现场、婚前任务）；
  - 切换全部调用方，删除旧接口和旧实现。
- 刻意的行为修正：
  - 「是否为一对」统一由关系记录判定，双方都核对账号和角色，并拒绝已关闭的关系；
  - 心意点改为归属于关系。
- 更新设计稿的落地状态和受影响的仓库文档；交付双端实机回归清单。

### Out

- 离婚、婚戒升级等新玩法，以及任何客户端改动。
- 修改线上协议字节或婚礼业务规则（金额、次数、时限、状态码、离场 03CF 语义）。
- 任务服务中可空注入的清理；与婚姻无关的重构。
- 推送、PR、合并到其它分支、清理工作区、部署运行中的 Host、对运行库执行迁移。
- 实机回归的执行由用户完成；Agent 只交付清单，不宣称客户端已实机验证。

## Constraints

- 遵守仓库 `AGENTS.md` 的分层与注入约定：Application 不引用 Protocol；命令处理器只注入领域服务和领域 store；规则输入只经规则服务进入。
- 回填不得破坏或删除既有婚姻数据。数据无法判定时如实计数并报告，不编造阶段或时间。
- 重构过程中，测试固定的现有行为只允许以「刻意修正」的形式改变，并且每项修正都要在结果说明中单独列出。

| SC-2 | 每对关系的当前阶段由一条记录直接存储；所有阶段判断都读取它，不再从求婚、预约、婚礼表推导「已婚」「已预约」；03D0 状态由阶段投影得出 | 阶段迁移规则的穷举测试；03D0 投影测试；全仓搜索旧推导路径为零；不变量测试 |
| SC-3 | 实体内部组件之间不互相依赖；只有关系账本写阶段；实体不直接依赖任何存储；阶段写入能检测并发冲突 | 架构判据测试，附一条会被拒绝的反例；并发冲突测试 |
| SC-4 | 已有数据库升级后，每条现存关系得到正确阶段，包括没有完成时刻的旧已婚记录，以及计数报告的异常记录；重复启动幂等；旧表结构与数据完好；心意点回退后不丢失 | 每种回填情形一个迁移测试；完整性检查；对一份近期真实运行库的**副本**执行迁移的结果记录 |

| SC-6 | 刻意修正生效：「是否为一对」口径统一；心意点归属于关系 | 修正前后行为对照测试；结果说明中的修正清单 |
| SC-7 | 解决方案构建无警告；全量测试通过（已知偶发项按 `AGENTS.md` 的判别规则认定）；设计稿落地状态和受影响文档已更新；交付双端实机回归清单 | 构建与全量测试输出；文档 diff；回归清单文件 |

- 执行期间没有其它 Agent 修改 next-round 上的婚姻代码（用户已暂停 GPT）。如果基准分支前进并触及婚姻代码，在合并前另行处理，不在本任务内回填。
- 本结果随 next-round 的 PR 一起发布，不单独递增版本号。
- 设计稿是执行依据，不是硬性实现规格。组件划分、表名、方法签名可以在 Spec 或 Plan 中依据代码证据调整，但不得违背上述 Goal 和 Success Conditions，偏离之处需要在 Spec 中说明。
