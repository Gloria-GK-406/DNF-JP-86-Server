# Implementation Plan: 婚姻单一实体与阶段记录

## Planning Choice

四个阶段之间是真实的产出依赖：
1. 表征测试是后续重构的安全网；
2. 关系记录和账本是合并实体的前提；
3. 统一判定点只有合并之后才存在，行为修正依赖它。

后面单元的细节取决于前面单元的实际结果。比如表征测试暴露出的现状怪癖会影响账本的守卫写法，回填的真实数据分布会影响组件边界。另外，这项工作必然要跨越多次上下文压缩，执行配置要求 on-drift 注意力控制。所以选渐进式 Task Units：本 Plan 只定路线和共享决策，每个单元临近执行时再细化。

## Approach and Shared Decisions

- **关系记录**
  - 新表与现有 relation id 同主键，阶段、revision、引用的预约、结婚时刻、心意点都放在这张表上。
  - 求婚时由账本在同一事务里创建；已有数据由启动时的幂等回填补齐。
  - 旧的求婚、预约、婚礼表继续保存明细和历史，不再作为阶段的来源。
- **存储接缝**
  - 关系 store 接口放在 `Dfo.Server.Abstractions/Marriage`，由 Persistence 实现，DI 只注入给账本。
  - 「只有账本能拿到它」由架构判据守住，不靠命名约定。
- **账本与规则**
  - 账本是 Application 内的具体 internal 类型，负责加载关系、判定是否为一对、处理惰性到期、CAS 提交，以及心意点写入。
  - 阶段规则是 static 纯函数类，提供迁移表和 03D0 投影。
  - 迁移表、阶段值和回填表以 Spec 为准。
- **过渡顺序**
  - T-002 期间，旧的 8 个服务保留原接口，只把阶段的读写改为经过账本。这样关系记录先在不动上层的情况下落地，表征测试照常把关。
  - T-003 再把服务拆成组件并合并成实体。
- **测试构造集中在一个 fixture**
  - 表征测试通过 `Application.Tests/Marriage` 下一个共享的构造入口取得被测服务。
  - T-003 切换接口时只改这个入口，以及调用方法的名字，不改断言（AC-009）。
- **失败语义沿用**
  - CAS 冲突映射到现有的 `Stale`；T6 失败沿用「整笔回滚，再由 Protocol 派 response=2」。
  - 不新增状态码，不改协议层。
- **接口落点**
  - 4 个新接口和 `MarriageView` 等新契约放在 `Dfo.Server.Abstractions/Marriage`，阶段枚举放在 `Dfo.Server.Data/Marriage`。
  - 组件和实体放在 `Dfo.Server.Application/Marriage`。
  - 命名以设计稿为起点，可以按代码现实调整，偏差在 T-005 中记入设计稿。

## Verification

- 每个单元先写失败测试或表征测试，再实施，结束时跑 Application、Persistence、Protocol 三个测试项目的相关用例和全解决方案构建。
- T-003 之后用旧接口名和旧推导路径的搜索结果证明 AC-001、AC-002。
- 最终的完整结果审查对照 TaskContract 和 Spec；验证阶段用新鲜的全量测试和副本迁移记录证明 SC-1…SC-7。
- 实机回归由用户执行，结果不由 Agent 宣称。
