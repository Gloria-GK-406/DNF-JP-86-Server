# Routing Decision

- TaskContract: `.rks-agent/tasks/marriage-domain-aggregate/TaskContract.md`
- Contract revision: `3`

## SDD Readiness

用户已经确定以下几点：
- 对外单一实体，内部分为小组件，多个接口由同一实例实现；
- 阶段由关系记录直接表达；
- 执行进度为四步；
- 设计稿 §11 的四项按 Agent 建议决定。

设计稿和现状代码已经给出 8 个服务的全部方法、调用方、表和推导路径，成功条件都可以用测试、代码检查和迁移结果来观察。剩下的组件边界、表名和签名属于设计稿已授权的实现裁量，不改变任务语义。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Rationale: 用户明确要求用任务契约和单 Spec 多 Task 来约束这次重构，并且看重「行为不变」的精确度。如果直接改，最可能出现三类问题：
  1. 漏掉某个没有测试的结算或宾客路径，导致金额或次数悄悄改变；
  2. 某个调用方仍从婚礼表或预约表推导阶段，形成第二个真源；
  3. 合并后组件之间互相调用，退回到「大杂烩」。

  这三类问题局部测试都可能看不出来。一份 Spec 先写明成功条件和不变量，表征测试先于改动落地，最后对完整结果做审查，就能以可接受的时间成本控制住这些风险。四步之间依次依赖：表征测试是重构的安全网，账本是合并的前提，行为修正依赖合并后的单一判定点。最终它们作为一个整体验收、一次提交，没有可以独立验收和回滚的子目标，所以用一个 Spec。
- Reroute conditions: 出现以下任一情况时，暂停并重评契约或拆分边界：
  - 回填发现无法在不破坏既有数据的前提下表达的关系状态；
  - 某条线上协议行为只能靠改变字节才能保持；
  - 用户要求每一步单独提交。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `long-running`
- Rationale: 关系表和账本的形状一旦定错，返工会扩散到全部组件和调用方。Lite 没有计划阶段，控制不住这种前期决策的传播。整个工作约涉及 1000 行，加上迁移和 4 个依赖单元，几乎必然跨越多次上下文压缩。长任务 Profile 的逐单元计划、目标检查和漂移复盘，正好对应「合并后组件互相调用」这类渐进偏离。

  不选 Governed 的理由：迁移只新增表，旧表和数据保留，心意点双写可以回退，因此不存在缺少恢复手段的数据丢失路径；本任务也不涉及凭据、权限或外部不可逆操作。普通的完整结果审查加新鲜验证已经足够。
