# TaskContract: A21 Story/Cycle 队伍模式续作与建模审计

## Context

### Source Request

既有 `party-mode-rules` 任务已接受队伍设置基础、Normal 模式以及可组合广播作用域/附近角色频道隔离，
但因公共队伍目录缺少真实非空 `0x023C` 业务样本而终止。用户现已把该问题转为后续事项，并明确授权：

> “任务已经派发了,我们继续推进功能开发.对于这个队伍列表这个问题在github提个issue吧.后面再处理”

公共队伍目录由 GitHub Issue #20 独立跟踪。本任务从接受基线继续 Story、Cycle 与最终建模审计，不重开
或改写旧任务的终态。

### Current Situation

接受基线 `9a3a0b492da11f48525d1225d02513e0dd1cd458` 已包含：类型化三类队伍设置、保守规则服务、严格
C2S `0x000C`、Normal 创建/编辑/离队闭环、设置通知顺序保护，以及按实际 Game listener 频道隔离的
附近角色投影。Story 和 Cycle 的模式特有目标、有效组合、编辑约束及相关生命周期尚未实现，最终模型
也尚未用三类完整证据复核。

## Goal

在不依赖公共队伍目录的前提下，依次完成 Story、Cycle 两类队伍的 A21 客户端可消费协议与领域行为，
保持既有 Normal/组队生命周期/频道隔离不回退；随后基于三类已接受证据审计共享模型，只在强证据表明
现有所有权、原子边界或规则表达错误时实施最小充分重构。

## Scope

### In

- 先 Story、后 Cycle，分别重建模式特有目标字段、有效值、创建/编辑约束，以及与该模式直接相关的
  进入、返回、成员变化、离队和会话清理行为。
- 补齐相应 C2S/S2C codec、Application handler/Command、领域实例与规则服务行为；继续遵守
  “handler 调 Command 实施业务，调用 Event/Notification 实施通知；Command 调领域实例/领域服务；
  规则服务提供模式规则”的分层边界。
- 对畸形、尾随、非法类别/目标、非队长、旧会话、容量或状态冲突进行确定性拒绝，且不得污染现有队伍。
- 同步协议记录、静态来源、运行时样本和置信度；当前 A21 客户端可归因验证前不标记 `ClientVerified`。
- 对 Story、Cycle 分别完成自动化回归和可观察客户端闭环；等待用户执行 UI 动作时主动提出一个明确问题，
  不把纯等待作为执行循环。
- 两类模式完成后进行整体建模审计；若出现强重构信号，完成有证据支持的聚焦重构及等价回归。

### Out

- GitHub Issue #20 跟踪的公共队伍目录、`0x023C` 多队编码及目录初始/差分投影。
- “快速组队”匹配队列，除非后续静态证据证明它是 Story/Cycle 基本创建或进入流程不可分割的组成；若会
  扩大本任务语义，先停止并重新对齐。
- 与队伍模式无直接证据关系的副本战斗模拟、掉落、奖励或 P2P/UDP 中继。
- merge、push、PR、发布、旧任务终态改写，或现有 worktree/分支清理。

## Constraints

- 调查顺序为上游行为基线、当前 A21 静态解析/构包、真实运行时证据；冲突时以当前 A21 与可归因实测为准。
- 初始共享模型中尚未确认的 Story/Cycle 字段必须保持未知，不得从 Normal 或字段名称直接类推实现。
- Application 不得引用 Infrastructure；协议 DTO、codec、业务 handler、领域规则和通知职责保持现有分层。
- 用户可见行为必须有客户端或等强度消费者证据；自动化测试通过不能单独证明 UI/游戏行为正确。
- 公共目录 Issue #20 是显式延期项，不得为了补齐目录而阻塞 Story/Cycle，也不得在本任务中暗中实现它。
- 只有证据证明现有抽象导致错误所有权、错误原子边界、无法表达已确认差异或重复矛盾规则时才重构。

## Requires Confirmation

- merge、push、PR、发布、已接受结果回滚，以及任务 worktree/分支清理需要新的明确授权。
- 若静态证据证明“快速组队”是 Story/Cycle 不可分割的前置能力，需要先说明新增范围和影响，再取得确认。

## Assumptions

- 已接受的 `9a3a0b49` 及其前序提交是本任务的有效功能基线；旧 blocked 任务的未提交证据不属于本任务代码基线。
- 已派发的异步静态探索可作为增量证据，但本任务不依赖其按时完成；若它推翻当前模式边界，则在下一安全
  边界重新评估，而不是并发修改相同代码。
