# Specification: 服务器对「一件时装是什么」只有一个说法

## Why and Outcome

服务器今天对时装有两种互不相容的说法，因此**一件时装无法经任何发放通路活着进入游戏**。

发放侧把每一件非契约兽的穿戴品都记成「普通装备」那个种类；而存盘侧只接受被档案判定为时装、
且行上确实记着「时装」那个种类的物品，否则抛出并回滚。两者相遇的结果是：
**一件时装模板一旦经发放通路入库，下一次存盘必被服务器自己的守卫拒绝。**

这个矛盾今天在生产上到不了，依据不是代码而是档案数据——66,328 个时装模板里声明
`[creation rate]` 的是 0 个，而装备掉落池的唯一闸门正是它。
**而下一步的实机验证要用 GM 直接发放时装，那会绕过这个闸门。**
所以本 Spec 修的不是一个理论缺陷，是下一步必然踩响的那颗雷。

把种类对齐并不足以修好它。存盘侧对时装的行还要求它带着自己的时装身份与一份合法的时装细节，
而发放通路只会造「一堆同样的东西」那种形状——它写的是种类、模板号与数量，
数量还被写进了时装用来存身份的那个位置。**只对齐种类，只是把拒绝从一道守卫挪到另一道。**
代码级的逐条追踪见 `findings-kind-chain.md`。

**必须成为真的**：一件档案判定为时装的物品能被发放给角色，并在服务器上完整活下来——
入库、重新装载、再次存盘、再装载，始终是同一件带着自己身份与细节的时装。

本 Spec 不让时装能被穿到身上。服务器说不出任何一件时装该穿在哪一格，
而那个映射在本仓穷尽查证之后确认**只能由实机量得**（`findings-slot-provenance.md`、
`findings-archive-measurement.md`）。因此本 Spec 交付的第二样东西是**量具**：
当服务器因说不出该穿哪一格而拒绝一次穿戴请求时，它把请求点名的那一格记下来。
客户端自己知道映射，一次实机拖动就能把它交出来。

## Task Perspective

- Core outcome: 一件档案判定为时装的物品能被发放给角色并在服务器上完整存活，
  使所有者可以开始对时装做实机验证。消费者是做实机验证的所有者，
  他需要的是「东西发得出去、存得住、重登还在」，不是任何内部结构。
- Necessary support: 服务器内部对时装的种类只有一个说法；一件新入库的时装带着与他人不同的
  时装身份；因种类对齐而改变或不变的既有判定被逐条查明。
- Peripheral assurance: 全量判据、入场帧的整表字节比对、行为变化清单的双向核对、
  以及仓库约定中对「槽号为何未补」的如实记载。
  **量具不属于此类**：TaskContract 把它列为本轮的交付物之一，因此它是一条要求而不是证据。

## Scope and Non-Goals

### In Scope

- 一件档案判定为时装的物品经发放通路入库之后是完整的：种类、身份、细节三者齐备且互相自洽。
- 这样一件时装能被重新装载、再次存盘，不被服务器自己的守卫拒绝。
- 两件分别发放的时装不共用同一个时装身份。
- 量具：服务器因说不出一件时装该穿在哪一格而拒绝穿戴请求时，留下模板号与请求点名的那一格。
- 因种类对齐而产生的可观察行为变化，逐条列出并各自给出位置、生产可达性与判据有无。
- 槽号出处的穷尽结论与未补的类型名，记进仓库约定。

### Non-Goals

- **让时装能被穿到身上。** 服务器说不出任何时装的槽号，而该映射只能由实机量得。
- **给装备类型名到槽号的对照补任何一条。** 出处已穷尽，本 Spec 不靠推断补键。
- 实机验证本身。它由所有者操作客户端，本 Spec 交付的是让它能开始的前提。
- 裁定契约兽穿在第 24 格还是第 25 格。
- 契约兽领域本身；契约兽的类型专属数据在世界行被重建时不被抢救这条已知缺陷。
- 无人引用的世界行的清理。
- 「东西存在但不在任何格子里」的用法：地上掉落、交易托管、拍卖挂单、邮件附件。
- 徽章栏与晶体区分界的裁定，它同样需要实机。

## Constraints

- 本 Spec **有意改变可观察行为**。每一处变化都必须被列出并归因；
  未被列出的可观察变化即为缺陷。
- 行为变化清单的完整性必须从两个方向得出：既从改动的起因往下游追，
  也从新增或改变的拒绝与放行路径往回找。**只做前者加一次全量判据不足以支撑完整性主张**——
  全量判据全绿恰恰意味着没有既有用例走到那些新路径上。
- 覆盖主张必须由变异实测支撑。按消息文本或标识符搜索得出的覆盖读数不作数。
- 记载中不得出现读者无法证伪的基数：给出数目时必须同时列出构成它的各项与计数口径，
  并按成员名而非行号索引。
- 不新增协议帧，不改任何帧的字节布局。
- 命令处理器与通知处理器的注入面机检判据必须继续通过，其判定谓词与具名豁免清单不得放宽或扩充。
- 领域层「store」一词只指事务结算的真源。
- 既有断言的期望值不得为迁就实现而改写；仅当一处改写正对应本 Spec 列出的某条行为变化时才允许，
  且须逐条归因。

## Definitions

| Term | Meaning |
|---|---|
| 时装 | 档案通过该模板自报的装备类型名判定为时装的物品。判定权在档案，不在库里那个种类字节。 |
| 时装身份 | 一件时装用来把自己与同类其它件区分开的那个值，世界要求它在同时存在的时装之间互不相同。 |
| 时装细节 | 一件时装除通用物品数据之外必须携带的那份数据，其中珠宝槽恰为 30 字节。 |
| 发放通路 | 服务器把一件事先不在角色身上的物品交给角色的那条路，卡片奖励、地面拾取、任务给予与奖励、教程奖励都走它。 |
| 快捷栏 | 主背包前部那六格，玩家可把可用物品拖上去以便快速取用。 |
| 穿戴容器 | 角色身上那个容器，时装带与普通装备带都在其中。 |
| 量具 | 服务器在拒绝一次穿戴请求时留下的那条记录，其用途是让实机操作者读出客户端点名的格子号。 |

## External Behavior and Data Rules

- 一件时装在服务器上的完整形态由三部分构成，缺一不可：档案判定它是时装、
  行上的种类与该判定一致、行上带着可用的时装身份与合法的时装细节。
  三者中任意一项不成立时，服务器拒绝并回滚，而不是静默写入。
- 时装的种类判定权归档案。库里那个种类字节是被校验的对象，不是判定的依据。
- 同时存在于世界的两件时装，其时装身份互不相同。
- 时装不得占据快捷栏。该规则今天已经写下，但因发放侧标错种类而对时装不起作用。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 一件档案判定为时装的模板经发放通路入库时，行上记录的种类与服务器各处判定时装所用的那一个相同。 |
| RQ-002 | 一件档案判定为时装的模板经发放通路入库之后，该行携带一个可用的时装身份，以及一份珠宝槽恰为 30 字节的时装细节。 |
| RQ-003 | 一件经发放通路入库的时装可以被重新装载、再次存盘、再次装载，全过程不被服务器自己的守卫拒绝，且物品始终存在。 |
| RQ-004 | 两件分别经发放通路入库的时装，其时装身份互不相同，世界对时装身份唯一性的守卫不拒绝其中任何一件。 |
| RQ-005 | 时装不再被允许占据快捷栏的格子。 |

| RQ-008 | 本轮全部可观察行为变化被逐条列出，每条给出它在何处发生、在生产上是否可达、以及有无判据覆盖；该清单的完整性由双向核对得出而非由一次全量判据推断。 |
| RQ-009 | 仓库约定记下时装槽号出处的穷尽结论、装备类型对照今天认不出的全部类型名、以及其中在档案里从未被任何模板使用过的键。 |
| RQ-010 | 除本 Spec 列出的行为变化之外，服务器发给客户端的入场字节不变。 |

## Assumptions

- 客户端在请求穿戴一件时装时会自己算出目标格子并把它写进请求。依据是一次逐字节抓包，
  以及服务器侧对该请求的既有处理确实持有该格子号。
  **若实机表明客户端在服务器认不出该类型时根本不发出这个请求**，量具将量不到东西；
  那是只有实机能发现的事，届时如实报出，不在本 Spec 内补救。
- 时装槽号今天无法从档案、既有实测转写或上游转写中取得。这不是一条待查的假设，
  而是本轮穷尽查证的结论；本 Spec 据此把补键排除在外。
- 判据基线为全量 2216 通过、2 跳过、0 失败，退出码 0，已在本工作区实测确认。
  那 2 个跳过是内容档案已加载的标志，不是缺陷。
