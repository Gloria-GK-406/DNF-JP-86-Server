# Specification: Game 协议初期文档骨架

## Why and Outcome

后续协议开发按"走一步游戏、实现当下真正触发的协议"推进。每遇到一条未见过的报文，
开发者当前必须从零开始：判断它属于哪个协议族、找构包点或 handler、逐条反汇编推布局。
这一段成本对每条协议重复支付，而其中绝大部分是机械劳动，且所需的原始材料（内存 dump、
两份普查数据、上游枚举与实现）已经全部就位。

本 Spec 完成后，Game 端点两个方向上静态可见的每一条协议都有一篇属于自己的文档：
打开它就能知道该协议属于 CMD 还是 NOTI、type 是多少、官方名称叫什么、body 如何切分、
每个字段可能是什么意思，以及——同等重要地——**哪些部分静态分析回答不了、为什么回答不了**。

## Task Perspective

- Core outcome: 开发者在游戏中遇到任意一条 Game 报文时，能通过其族与 type 直接定位到一篇
  文档，并从中获得该报文的名称、body 切分方式与字段含义线索；当文档给不出答案时，
  能立即看出这是"静态分析的已知边界"而非"尚未有人看过"，从而知道下一步该用什么手段去取证。
- Necessary support: 文档中的每一条断言都必须可追溯到证据来源；未经证据支持的语义推测
  必须以显式未知呈现，否则文档会把猜测洗成事实，使消费者据以做出错误实现，
  其危害大于没有文档。
- Peripheral assurance: 提取逻辑在已知正确的协议上的复现能力、身份集合与文档集合的
  闭合比对、以及重新生成对人工内容的保全能力。

## Scope and Non-Goals

### In Scope

- Game 端点 C→S 方向：客户端静态可见的全部 CMD 请求协议，每条一篇文档。
- Game 端点 S→C 方向：客户端静态可见的全部 NOTI 推送协议，每条一篇文档。
- 每篇文档的身份段：command 族、type、方向、名称及名称来源。
- 每篇文档的 body 段：字段布局（偏移、宽度、编码）与每个字段的可能含义，
  或在无法提取时给出显式的未知分类与不可知原因。
- 每篇文档的定位段：支撑上述结论的构包点或 handler 入口位置。
- 未知的分类体系：区分含义未知与结构未知，后者进一步区分其成因。
- 文档树按方向分层，文件名可无歧义表达协议身份。
- 覆盖全部文档的索引，支持由族与 type 定位到文档。
- 既有手写文档中因本 Spec 取得新证据而可升级之处的增补。

### Non-Goals

- 服务端协议实现：解码器、编码器、消息类型、handler 均不在本 Spec 内。
- 响应流程与回包规则的确认。
- 字段真实语义的确认——本 Spec 只产出"可能含义"与"未知"。
- Channel 端点的协议文档。
- 客户端的任何改动、部署或重建。
- 推翻既有手写文档中的已有结论。

## Constraints

- 未经证据支持的语义推测不得以事实形式出现。不确定必须显式呈现为未知。
- 协议身份为 endpoint、direction、command 族与 type 的四元组。同一 type 在不同族或方向
  是不同协议，必须各自成篇，任一篇不得覆盖另一篇的含义。
- 每条结论须标注其证据来源与置信度，沿用资料库既有的证据分级。
- 既有手写文档的证据、样本与逆向工作日志不得被删除、覆盖或降级。
- 文档中人工补充的内容，在文档被重新生成后必须依然存在。

## Definitions

| Term | Meaning |
|---|---|
| CMD 族 | 帧头 command 字节为 `0x01` 的协议族。客户端的唯一发送通道，请求与响应共用同一套 type 编号。 |
| NOTI 族 | 帧头 command 字节为 `0x00` 的协议族。仅服务端向客户端推送，客户端从不发送。 |
| 协议身份 | endpoint、direction、command 族、type 四者构成的唯一标识。 |
| 含义未知 | body 的字段边界已确定，但该字段代表什么量没有证据支持。 |
| 结构未知 | body 的字段边界本身无法由静态分析确定，因而不存在可填含义的字段表。 |
| 机器区 | 文档中由静态分析与既有数据机械产出的部分，可随基准变化重新生成。 |
| 人工区 | 文档中由人补充的部分，包括证据、样本、实机结论与工作日志。 |

## External Behavior and Data Rules

- 文档树以方向分层：C→S 与 S→C 各占一个目录，位于 Game 端点目录之下。
- C→S 方向只含 CMD 族协议，因为客户端的出站帧构造点将 command 恒定写为 `0x01`。
- S→C 方向同时存在 CMD 响应与 NOTI 推送两个族，二者共享 type 数字空间且互不相干，
  因此该方向的文件名必须携带族标识以避免同号协议相互覆盖。
- 一条 CMD 的请求与其响应属于同一次交换、共用同一个 type，记入该 type 的 C→S 文档；
  已单独成篇的既有例外保留原有归属，并与对应 C→S 文档相互链接。
- 文档的机器区与人工区在同一文件内可被无歧义区分，使重新生成只作用于机器区。
- 索引可由族与 type 两个键定位到唯一文档。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 客户端静态可见的每一条 C→S CMD 协议身份，在 C→S 目录下有且仅有一篇对应文档。 |
| RQ-002 | 客户端静态可见的每一条 S→C NOTI 协议身份，在 S→C 目录下有且仅有一篇对应文档。 |
| RQ-003 | 每篇文档记录其 command 族、type、方向三项身份要素。 |
| RQ-004 | 每篇文档记录该协议的名称及该名称的来源；名称来源不可得时，该事实本身被记录。 |
| RQ-005 | 每篇文档的 body 段处于且仅处于两种状态之一：给出字段布局表，或标记为结构未知并说明其成因。 |
| RQ-006 | 字段布局表中的每个字段给出其偏移、宽度、编码，以及可能含义或含义未知标记。 |
| RQ-007 | 文档中不存在缺少证据来源标注的语义断言。 |
| RQ-008 | 每篇文档记录支撑其结论的定位信息：C→S 为构包点位置，S→C 为 handler 入口位置。 |
| RQ-009 | 机械提取所得的字段布局，在既有已双向验证的协议上与既有手写结论一致。 |
| RQ-010 | 既有手写文档的证据、样本与逆向工作日志在本 Spec 完成后依然完整。 |
| RQ-011 | 文档中的人工区内容在文档被重新生成后依然存在且未被改动。 |
| RQ-012 | 存在覆盖全部文档的索引，可由族与 type 定位到对应文档。 |
| RQ-013 | 同一 type 在不同族或不同方向下的协议，其文档互不覆盖且可各自定位。 |
| RQ-014 | 结构未知的文档说明其不可知成因所属的类别。 |
| RQ-015 | 资料库中因本 Spec 取得新证据而可升级之处已完成增补，且增补标注了新证据来源。 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001, RQ-002 | 客户端静态普查得出的协议身份集合与文档树 | 将两者按身份逐条比对 | 双向差集为空，且无一个身份对应多于一篇文档 |
| AC-002 | RQ-003, RQ-004 | 全部文档 | 检查每篇的身份段字段完整性 | 族、type、方向、名称、名称来源五项均非空 |
| AC-003 | RQ-004 | 全部文档记录的名称与上游枚举 | 按族与 type 比对名称 | 凡名称来源标注为上游枚举者，与枚举内容一致 |
| AC-004 | RQ-005, RQ-014 | 全部文档的 body 段 | 按状态分类统计 | 每篇归入"有布局"或"结构未知"之一，无第三态；结构未知者均带成因类别 |
| AC-005 | RQ-006 | 给出布局表的文档 | 检查每个字段行 | 偏移、宽度、编码非空，含义列为具体推测或未知标记 |
| AC-006 | RQ-007 | 全部文档中的语义断言 | 独立复核抽样核对断言与其证据来源 | 未发现缺少证据来源的语义断言 |
| AC-007 | RQ-008 | 全部文档 | 检查定位段 | C→S 文档含构包点位置或"未找到"的显式记录；S→C 文档含 handler 入口位置 |
| AC-008 | RQ-009 | 既有已双向验证协议的手写布局结论 | 将机械提取结果与之比对 | 字段序列、宽度与总长一致；不一致处已被识别并给出原因 |
| AC-009 | RQ-010 | 本 Spec 执行前后的既有手写文档 | 比对其证据、样本与工作日志内容 | 无删除、无覆盖、无降级 |
| AC-010 | RQ-011 | 一篇已含人工区内容的文档 | 对其重新执行生成 | 人工区内容逐字不变，仅机器区被更新 |
| AC-011 | RQ-012 | 索引与文档集合 | 按族与 type 双向比对 | 索引条目与文档一一对应，无悬空条目与未索引文档 |
| AC-012 | RQ-013 | 同时存在于两族或两方向的 type | 按身份定位其文档 | 各自解析到不同文档，内容互不覆盖 |
| AC-013 | RQ-015 | 资料库中标注为待补证据的既有结论 | 检查其当前状态 | 已取得新证据者完成增补并标注来源；未取得者保持原状 |

## Assumptions

- 上游服务端源码树中的协议枚举，其枚举值即 wire type。该假设已由既有已双向验证协议
  交叉核对，含同号异义样例，未发现错位。
- 现有内存 dump 与当前客户端二进制同源，既有普查数据与本 Spec 的新增分析共用同一基准。
- 静态分析无法覆盖全部协议：被混淆的代码区、经虚函数写出的多态载荷、
  以及不读 body 的接收 handler 均无法从指令推出布局。这部分记为结构未知是预期结果，
  不构成本 Spec 的失败。
- 上游实现与当前客户端同源但非同一份代码，其字段语义为参考证据而非直接证据。
