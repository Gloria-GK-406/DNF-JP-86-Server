## SC-5 提取器在已知正确的协议上可复现

`check-controls.py` **14/14 通过**，取材于本库已双向验证的 14 条协议：

| 协议 | 规则 | 实测 body | 结论 |
|---|---|---:|---|
| `0x00AB` | `3 + n×9` | 39 | 前缀与重复组逐项匹配手写文档，`n=4` 闭合 |
| `0x01DD` | `16` | 16 | 字段序列逐项匹配 |
| `0x00C2` | `30 + n1×10 + n2×3` | 361 | 闭合于 `n=1,107` |
| `0x00FA` | `8 + n1×6 + n2×9 + n3×11` | 50 | 闭合于 `n=0,1,3` |
| `0x008F` | `5` | 5 | 闭合；14 个构包点形状一致 |
| `0x0008` | `3` | 3 | 闭合；5 个构包点形状一致 |
| `0x0003` | `1` | 1 | 字段序列逐项匹配 |
| `0x02A8` | `2` | 2 | 字段序列逐项匹配；3 个构包点一致 |
| `0x0286` | `0` | 0 | 空 body，闭合 |
| `0x01BA` | `0` | 0 | 空 body（构包点在混淆区，未发明字段） |
| `0x0005` | 变长 | — | 形状匹配 `u8 + dstring + u8×4` ↔ 文档 `1 + 4 + nameLength + 4` |
| `0x0006` | 变长 | — | 形状匹配 `u16 + dstring` ↔ 文档 `2 + 4 + nameLength` |
| `0x02B5` | 变长 | — | 形状匹配 `dstring` ↔ 文档 `4 + nameLength` |
| `0x0117` | — | 12 | **反向对照**：多态载荷，正确地**未**被误判为闭合 |

反向对照是这套证据里最关键的一条：一个把 `0x0117` 自信地闭合到 2 字节的提取器，
恰恰错在最要命的地方。

扩充对照集的过程本身产出了两条回写权威文档的结论：
后三条协议一致证明了 `patterns/game-frame.md` 中此前标为"未确认、不得据此解析"的原语
`0x1C90710` **就是** `WriteDString`（`i32 长度 + 字节`）；`0x0286` / `0x01BA` 则暴露出
"空 body 被误判为结构未知"——空 body 是**确定的**布局，修正后 89 条协议由未知转为已闭合。

## 已知边界（不是缺陷）

- **75.9% 的字段含义为 `unknown`**。这是被明确接受的结果。上游实现只覆盖 313 条协议
  （22%），其余无参照物；且上游对相当一部分 CMD 根本不解析 body。
- **22.3% 的协议结构未知**。成因分四类并逐篇标注：多态载荷、构包器在被混淆的第二代码区、
  handler 不读 body、取字段调用进入打包区。这几类静态分析无法解决，需运行时手段。
- **重复组之后的偏移是名义值**（文档中带 `*` 并附说明）。真实位置随运行时计数变化。
- 客户端提取与上游实现存在多处布局分歧，逐条记于
  [`Docs/ProtocolScaffoldDissonances.md`](../../../../Docs/ProtocolScaffoldDissonances.md)，
  **只记录不弥合**——判定它们需要实机样本。
