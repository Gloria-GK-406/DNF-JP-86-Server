### Current Situation

`protocol/` 资料库当前只有 16 篇手写协议文档，均为"走到哪写到哪"的产物。而两个方向的
静态普查早已完成并入库：C→S 以 `MakeHeader` 为锚点得到 604 个 type，S→C 以 `Register`
为锚点得到 CMD 表 538 + NOTI 表 728 个 type。普查数据存在，但从未被用来批量建档。

三项使批量建档成为可能的前置条件现已同时具备：

1. 两个方向的取字段原语均已识别（C→S 的 `WriteU8/U16/U32/Bytes`，S→C 的
   `ReadU8/U16/U32/Bytes/DString`），资料库明确记载 body 布局"可以从指令机械读出"；
2. 上游服务端源码树已进入工作区（`D:\project\86JP`），其 `PacketTypes.cs` 含
   `CmdPacketType` 1086 条与 `NotiPacketType` 1036 条，数量与客户端自报的
   `CommandPacketCount` / `NotificationPacketCount` 完全一致；经 16 个已双向验证协议
   交叉核对，枚举值即 wire type，零错位；
3. 上游同时含约 150 条具名 CMD handler 与大量 NOTI builder 实现，可作为字段语义来源。

后续协议开发按"走一步游戏、实现当下真正触发的协议"推进。缺的是一份可查的地图：
遇到一条包时能立刻知道它属于哪个族、叫什么、body 怎么切。本任务建设的就是这份地图的初稿。

## Goal

Game 端点两个方向上、静态普查可见的每一条协议，都有一篇属于自己的文档，记录其族与
type 身份、官方名称、body 字段布局及每个字段的可能含义；凡静态分析不能确定的部分，
文档显式标记为未知并说明其不可知的原因，而不是给出未经证据支持的猜测。

这些文档是供后续实机开发消费的初稿：响应流程与字段真实含义由那一阶段回填，本任务不产出。

## Scope

### In

- Game 端点 C→S 与 S→C 两个方向、静态普查可见的全部协议的文档建设。
- 每篇文档记录：command 族（CMD `0x01` / NOTI `0x00`）、type、名称及其来源、
  body 字段布局（偏移/宽度/编码）、每个字段的可能含义或显式未知标记、
  以及支撑上述结论的定位信息（构包点或 handler 入口）。
- 未知的分类与说明：区分"结构已提取但含义不明"与"结构本身无法从静态分析得出"，
  后者需记录其不可知的原因。
- 文档在 `protocol/` 下按方向分层组织，并提供可检索的全量索引。
- 既有 16 篇手写文档中因本任务取得新证据而可以升级的部分（如描述性命名可替换为官方名）。
- 支撑上述产出所需的静态分析工具与普查数据的补全。

### Out

- 服务端协议实现（decoder / encoder / handler / 消息类型）。
- 响应流程、回包规则、字段真实语义的确认——留待实机开发阶段回填。
- Channel 端点的协议文档（本任务不涉及，其普查数据不存在）。
- 客户端侧任何部署、改动或重建。
- 对既有手写文档中已有结论的推翻或重写；本任务只做证据支持的增补与升级。

## Constraints

- 不确定的内容必须显式记为未知，不得以推测填充为事实。这是用户明确要求，
  且是本资料库既有规则（`Hypothesis` 不得直接变成生产领域语义）的延续。
- 协议身份为 endpoint + direction + command + type 四元组；同一 type 在不同族或方向
  必须各自成篇，不得相互覆盖。这是客户端使用两张互不相干注册表的机制事实。
- 结论必须标注证据来源与置信度，与资料库既有的证据分级约定一致。
- 人工后续在这些文档上补充的内容，不得因文档的重新生成而丢失。用户已明确本批文档
  将"在这个文件基础上继续演化成完整的确定文件"，破坏人工成果会使该演化路径失效。
- 既有 16 篇手写文档的证据、样本与逆向工作日志不得被降级或覆盖。
