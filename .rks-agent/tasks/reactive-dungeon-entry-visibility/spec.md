# Specification: 响应式地下城入口可见性

## Why and Outcome

队伍进入地下城后，客户端能否创建并绑定远端角色，取决于成员/avatar 信息、端点与用户状态、共享房间描述以及接收者自己的 `participantSlot` 是否来自同一个地下城实例，并按客户端可消费的顺序到达。当前入口 handler 同时承担领域编排、接收者选择、wire 映射与发送，容易让某个成员缺少前置状态或收到旧实例视图。

交付后的入口只有一个状态真源：角色行为提交到共享地下城实例；实例原子更新参与者入口状态、递增修订并给出语义接收者；统一投影边界读取最新实例视图，把稳定角色身份映射为当前有效传输身份和接收者专属入口帧。协议 handler 不再自行维护一套成员扇出规则。

## Scope

本 Spec 覆盖队伍/单人地下城的实例创建、参与者附着、首房间入口投影、`FINISH_LOADING` 就绪提交、入口修订防旧写、当前 session 解析和客户端人物可见所需的入口 wire 映射。剧情入口的既有任务选图规则和城镇离开顺序必须保留。

换房、位置/HP、怪物死亡、掉落、开门、Boss、任务结算、翻牌和返回城镇的响应式迁移不属于本 Spec；它们后续只能复用本次建立的实例变化与投影边界，不能作为本次验收的替代证明。

## Definitions and Invariants

- **地下城实例**：一个 `DungeonRunId` 对应的共享运行聚合；队伍中每个角色索引到同一实例，但读取的是接收者专属视图。
- **语义接收者**：实例根据当前参与者状态决定应观察某项变化的 `CharacterId` 集合；集合不包含 connection、session 或协议类型。
- **传输接收者**：投影边界将语义接收者解析为仍然拥有该角色的当前 selected-session generation；解析失败者不接收旧实例流量。
- **入口修订**：每次会改变入口投影视图的有效提交都产生单调递增修订；重复或过期提交不能倒退状态。
- **入口准备**：共享实例、固定参与者和首房间内容已经成功建立，但客户端尚未全部报告地图加载完成。
- **参与者就绪**：当前有效 session 对该实例的当前入口修订提交了 `FINISH_LOADING`；重复提交幂等。
- 地下城领域不引用 session、connection、网络消息或 encoder；协议投影不成为第二个成员状态真源。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 创建队伍地下城时，所有有效参与者必须在一次原子领域操作中附着到同一个实例，并得到同一个房间、布局和入口修订；单人入口使用同一模型。 |
| RQ-002 | 实例必须接受带调用角色、预期实例和预期入口/房间修订的入口状态提交，并以幂等方式记录参与者就绪；无成员资格、实例不匹配或修订过期的提交不得改变实例。 |
| RQ-003 | 每项已提交的入口变化必须给出不可变的最新实例视图、修订和语义接收者，使后续入口功能可以通过新增变化类型接入同一投影边界。 |
| RQ-004 | 统一入口投影边界必须在发送前重新读取最新实例状态，并只解析仍属于该实例且仍为当前 generation 的传输接收者；较旧修订不得在较新修订之后重画客户端。 |
| RQ-005 | 每名接收者必须获得接收者专属入口映射：成员顺序和队伍槽位稳定，身份使用正确 `WireUserId`，队伍入口的 `START_MAP participantSlot` 等于该接收者槽位，单人入口使用单人哨兵值；所有接收者共享相同房间与 actor/drop 描述。 |
| RQ-006 | 客户端创建远端成员/avatar 所需的成员资料、端点/用户状态前置投影必须先于该接收者的首个 `START_MAP`；`FINISH_LOADING` 只释放提交该就绪变化的当前客户端，同时使实例可响应参与者就绪变化。 |
| RQ-007 | 入口 handler 只负责解码、当前调用者识别、调用 CMD/应用入口协调器与交付直接结果；它不得枚举成员并自行决定通知对象或建立另一套入口生命周期。 |
| RQ-008 | 若实例准备、映射或入口投影失败，不能留下部分成员处于新实例、部分成员仍在城镇的可观察成功状态；城镇成员移除只能发生在入口投影提交成功之后。 |
| RQ-009 | replacement connection、离开成员和已被新实例替换的旧 run 不得收到入口或就绪通知；仍有效成员的投影不受旧连接提交影响。 |
| RQ-010 | 现有剧情选图、普通选图、单人入口和首房间内容编码必须保持兼容，且本次不得改变换房、战斗、掉落、Boss 或翻牌行为。 |

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001, RQ-003 | Given 两名有稳定槽位的队伍成员，When 队长选择有效地下城，Then 两个角色索引指向同一 `DungeonRunId`、同一首房间和同一入口修订，变化结果的语义接收者恰为这两名成员。 |
| AC-002 | RQ-002, RQ-003 | Given 一个已准备实例，When 两名成员按任意顺序提交当前 `FINISH_LOADING`，Then 各自只从未就绪变为就绪一次并产生单调修订；重复、旧修订、错误 run 或非成员提交均不改变状态。 |
| AC-003 | RQ-004, RQ-009 | Given 入口变化排队后某成员 session 被替换、离开或加入新 run，When 旧变化开始投影，Then 旧 generation 不接收帧且新 generation 不继承旧 run 流量；其他仍有效成员只收到最新修订视图。 |
| AC-004 | RQ-005, RQ-006 | Given 槽位 0 的队长和槽位 1 的成员，When 生成两份入口投影，Then 两份前置成员集合相同且顺序稳定，队长的 `participantSlot=0`、成员的 `participantSlot=1`，首房间/actor/drop 数据相同，并且每份成员/avatar 前置帧都排在 `START_MAP` 之前。 |
| AC-005 | RQ-006 | Given 两名客户端先后完成加载，When 各自提交当前就绪变化，Then 只向提交者发送其加载完成直接响应；实例最新快照同时准确反映当前已就绪成员，并可驱动需要观察就绪变化的当前参与者投影。 |
| AC-006 | RQ-007 | Given 完成后的入口代码，Then `SelectDungeonHandler` 和 `FinishLoadingHandler` 不包含按队伍成员选择传输接收者的循环，入口成员扇出只有统一投影边界一个实现。 |
| AC-007 | RQ-008 | Given 任一成员映射失效或投影准备失败，When 入口不能完整提交，Then 新实例被精确回滚或不对外成为成功入口，且城镇区域真源不会提前移除该队伍。 |
| AC-008 | RQ-010 | Given 单人、普通队伍和剧情队伍入口测试，When 构造入口响应，Then 现有有效选图规则、房间编码和单人哨兵保持通过；不属于本任务的相关测试没有回归。 |

## Success Evidence

- **EV-001（AC-001～AC-003）**：地下城领域测试覆盖共享创建、任意就绪顺序、幂等、错误实例/修订、成员离开和新 run 替换。
- **EV-002（AC-003～AC-006）**：协议投影测试分别捕获两名接收者的有序帧列表，断言 session generation、成员顺序、WireUserId、槽位、前置帧和 `participantSlot`。
- **EV-003（AC-007～AC-008）**：入口集成/handler 测试覆盖投影失败边界、城镇离开顺序、单人、普通队伍及剧情入口。
- **EV-004（全部）**：完整代码审查确认领域/协议依赖方向和唯一投影路径，随后进行新鲜解决方案构建与相关测试执行。
- 双客户端互相可见属于部署后的最终实机确认；自动化通过时只能声明“达到实机验收条件”，不得提前声明 `ClientVerified`。
