# TaskContract: 响应式地下城入口可见性

## Context

### Source Request

用户先明确第一步应“做进入可见然后重构成响应式地下城。从地下城拿实例然后提交修改。地下城服务自己来实现给哪些人通知”，随后授权：“可以，启动任务契约实施吧”。

### Current Situation

主干已经有共享 `DungeonRunAggregate`、固定参与者、`RunId`、`RoomVersion` 和旧连接隔离，但进入地下城时仍由协议 handler 逐成员解析运行态、构造封包并手工扇出。双客户端对照已证明上游的客户端、UDP/P2P 和远端角色显示链路能够工作，因此当前入口不可见问题集中在服务端的成员映射、封包内容、发送顺序和加载阶段投影。继续在各 handler 增加通知会产生多个状态与通知真源，并妨碍后续移动、HP、战斗、Boss 和翻牌统一接入地下城实例。

## Goal

建立以共享地下城实例为唯一入口状态真源的响应式投影边界，使队伍进入地下城时，每个当前有效参与者都获得顺序正确、身份映射正确的自身与队友入口视图，为双客户端互相可见提供可实机验收的服务端实现。

## Scope

### In

- 让队伍入口、成员附着和加载就绪变化提交到共享地下城实例，并产生带实例身份与修订信息的不可变变化结果。
- 由地下城实例状态决定变化的语义接收角色集合。
- 建立统一地下城入口投影边界，将语义角色映射到当前有效 session、WireUserId、队伍槽位、人物资料和入口封包。
- 将进入地下城的逐成员通知职责从协议 handler 收拢到统一投影路径。
- 对齐已验证上游入口链路所需的成员资料、端点、角色状态、START_MAP participantSlot 与发送顺序。
- 保留单人地下城、剧情地下城入口选择、城镇离开和 replacement connection 隔离行为。
- 增加覆盖双成员不同加载顺序、重复提交、旧连接和单人入口的自动化回归证据。

### Out

- 地下城内移动与换房的响应式迁移。
- 战斗 HP/MP 的权威上报与顶部血量同步。
- 怪物死亡、掉落、拾取、开门和普通房间清理的响应式迁移。
- Boss 完成、任务结算、翻牌、奖励和返回城镇的响应式迁移。
- 数据库结构或持久化模型调整。
- 合并到 `main`、工作区清理、部署服务或启动客户端。

## Constraints

- 地下城领域只能持有稳定角色与地下城身份并决定语义接收者，不得依赖连接、session 或网络协议类型；传输代际校验和 wire 映射必须位于应用/协议投影边界。
- 同一入口变化只能有一个共享地下城实例真源；延迟投影不得用旧修订覆盖较新的实例状态。
- 旧连接或已被 replacement connection 取代的 session 不得收到旧地下城实例通知。
- 本任务不得通过恢复 handler 内的特供扇出函数来满足可见性。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 两人队伍进入一个共享地下城实例后，每个当前参与者的入口投影都包含顺序正确的自身与队友身份、队伍槽位、端点/成员状态和对应 participantSlot。 | 双成员协议/集成测试分别断言两名接收者的完整入口帧序、成员映射和 participantSlot。 |
| SC-2 | 参与者附着或加载就绪由实例变化驱动，先后加载顺序、重复提交或延迟旧变化不会产生缺员视图或旧状态回写。 | 覆盖两种加载顺序、幂等重复和修订竞争的领域及投影测试。 |
| SC-3 | 入口 handler 不再拥有逐成员通知策略；语义接收者由实例状态给出，传输接收者只通过统一地下城投影边界解析。 | 代码审查与架构测试证明入口通知只有统一投影路径，领域层不引用 session/网络协议。 |
| SC-4 | replacement connection、掉线成员和不再属于该实例的角色不会收到入口通知，仍有效成员不会被旧连接影响。 | 会话代际与成员离开/替换回归测试。 |
| SC-5 | 单人及现有剧情地下城入口仍能生成有效 START_MAP，城镇离开只在入口投影提交成功后发生。 | 现有相关测试和新增单人回归测试通过。 |
| SC-6 | 代码可构建且相关自动化测试全部通过，结果达到双客户端实机验收条件。 | `dotnet build` 与选定测试集的独立验证记录。 |

## Authorization

| Capability | Evidence | Authorized scope |
|---|---|---|
| task | “可以，启动任务契约实施吧”承接前一轮已明确的响应式地下城入口可见性范围。 | 创建并执行本契约；允许任务工件、隔离工作区、实现、测试、审查和一个已验证本地结果提交。 |

## Requires Confirmation

- 将结果合并到 `main`、清理任务工作区、部署服务或启动客户端需要用户另行授权。

## Assumptions

- 上游双客户端成功互联与角色可见的运行结果可作为入口 wire 顺序与映射的对照证据，但上游每角色私有地下城状态模型不作为迁移目标。
- 自动化证据能证明实现达到实机验收条件；“客户端最终互相可见”仍需合并部署后的双客户端测试确认。
