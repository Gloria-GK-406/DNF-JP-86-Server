# TaskContract: 副本归属命令先定位、再单次路由，陈旧帧在入口统一丢弃

## Context

### Source Request

处理 issue #203「幻影塔陈旧序号判定吞掉普通地下城的拾取与 Eplp」。Agent 说明三种副本的拾取并非同一逻辑后，用户提出：“先有个独立的函数返回当前地下城种类之类的。然后再让拾取逻辑变成路由结构。内部直接多个不同的通道解决各自的逻辑……也就是查当前状态和处理拾取分开。就算是在同一个组件内部，内部也要给分离开。”Agent 报告同类写法遍布 13 个文件、31 处并给出“只改 4 个命令 / 全部一起改”两个选项后，用户决定：“直接一次性搞定，正好是一类问题就别分几轮了。你先做一次背景信息收集，然后写任务契约完成吧。提交pr时候在issue里说明修正的扩张范围。别让issue和修正范围不一致了。”

背景收集发现 3 个命令在普通副本与城镇中会处理陈旧帧。Agent 询问“保留现状”还是“一并统一”，用户选择“一并统一”：这些命令在任何位置都丢弃陈旧帧。

### Current Situation

代码基准 `7adec858`（main），路径相对 `Server/src/Dfo.Server.Protocol/Game/`。完整清单与证据见 `evidence/background-7adec858.md`。

- 13 个客户端命令按“依次尝试 Boss 塔分支 → 幻影塔分支 → 普通路径”分发，分布在 7 个处理器类：0x002B 拾取、0x0028 角色死亡、0x0027 怪物死亡、0x0025 加载完成、0x002D 过图、0x0048 Eplp、0x002A 放弃、0x000D/0x000E/0x0079 组队变更、0x000F 进入选图、0x0084 回城、0x0029 复活币。
- 用户决策时看到的“31 处”命中中，约 13 处不是命令分发，不在本次范围：两塔投影内部查成员、入场后的精确性校验、计时器驱动的塔内回城、会话生命周期清理。
- 每个塔分支自己查归属（`bossTowers.Find(session)` / `illusionTowers.Find(session)`），自己调用 `TowerProtocol.IsStale`，先后顺序不一。普通路径从不判陈旧，大多数命令靠前面的塔分支“顺带”丢弃陈旧帧。
- 陈旧帧现行处理不一致的地方：
  - 0x000F 进入选图：在普通副本、幻影塔、城镇照常处理，只在 Boss 塔丢弃；
  - 0x0029 复活币：从不判陈旧，在 Boss 塔回拒绝帧，在其他位置照常处理；
  - 0x0027 物件破坏帧：在普通副本照常处理，在幻影塔与城镇回空通知；
  - 无会话时，0x0048、0x0084 不判陈旧，其他命令判陈旧；日志标签与级别也各不相同。
- 已在入口统一判陈旧的只有 0x002A、组队变更（0x000D/0x000E/0x0079）与 0x0010。
- 组队类命令按整队归属分发：调用者、目标或任一在线队员在塔即进塔分支。0x000F 的 Boss 分支释放副本后，同一命令继续走城镇选图。
- 0x0010 进入地下城按目标地下城分发到 Boss 塔、幻影塔或普通入场，不按当前所在位置分发。
- 领域层已有排他的副本占用登记 `IDungeonParticipationDomainService`（`Find(character)` → 普通 / 幻影塔 / Boss 塔 + RunId），三种副本入场时登记，生产环境必然注册。`Document/LordTower-Design-20261019.md` 将它定为三种玩法共用的参与占用，并要求“按当前玩法分流”。
- 已知的登记与现行查询不一致窗口：
  - 旧会话代次的塔成员资格未清理、新会话已发布时，登记为塔，但塔 `Find(新会话)` 为空，现行代码交给普通路径；
  - 角色已离队、尚未结束本局时，登记仍为普通，但 `runs.Find` 为空，现行代码按不在副本处理。
- 陈旧帧测试现状：0x002A、0x0010、Boss 塔下的 0x000F 有处理器层用例；组队变更只有消息 handler 层用例，CMD 层未覆盖；其余命令在三种副本下均无陈旧帧测试，塔测试多用永不陈旧的 `GameMessageMetadata.Empty`。没有架构或源码测试约束这类分发写法。
- issue #187 第 2 条“塔路由链以可选参数散在 10 多个普通 handler”覆盖本次 13 个命令中的大部分，也点到 0x0010 入场。

## Goal

上述 13 个命令都按同一结构处理：
1. 入口判一次陈旧，陈旧帧在任何位置一律丢弃；
2. 由一个独立的定位能力回答“请求者（组队类命令为相关队伍）当前在哪种副本、是哪个副本”；
3. 只路由到一个通道：Boss 塔、幻影塔、普通或不在副本。

各通道只处理自己那种副本的逻辑，不再判陈旧，也不再为路由自己查归属。唯一的具名例外是 0x000F：Boss 塔通道只负责释放副本，随后直接进入城镇选图，不重新定位、不再判陈旧。陈旧判定只有一个与“塔”无关的定义。除用户授权的陈旧帧统一外，游戏可观察行为保持不变。

## Scope

### In

- 13 个命令（拾取、角色死亡、怪物死亡、加载完成、过图、Eplp、放弃、组队变更三条、进入选图、回城、复活币）的分发改为“入口判陈旧 → 定位 → 单次路由 → 独立通道”，同一组件内的定位与各通道也分开。
- 统一定位能力，以副本占用登记为依据，给出副本种类与该副本快照；另有供组队类命令使用的整队归属定位。
- 陈旧判定改为单一的中性定义，取代 `TowerProtocol.IsStale`。0x009F、0x0010 只改用新定义，分发不变。
- 用户授权的行为变化：13 个命令的陈旧帧在普通副本、Boss 塔、幻影塔、城镇与无会话时一律丢弃，不产生领域写入与回包。
- 结构改动前先提交表征测试，钉住新鲜帧的现有行为；补齐陈旧帧在各位置的测试；以能拒绝反例的结构守护（类型、编译期或源码扫描均可）守住新结构。
- 受影响的测试替身与驱动按新结构调整，补上副本占用登记。
- 在所属专项文档中记录分发结构与陈旧帧规则（唯一归属），其他位置只引用。
- 推送分支、创建 PR。
- 在 #203 评论列出扩张后的范围（13 个命令、排除的非分发命中）与陈旧帧行为变化；在 #187 评论说明本次覆盖的条目与未覆盖的部分。

### Out

- 0x009F（只有幻影塔一个通道）、0x0010（按目标地下城分发，且已在入口判陈旧）的分发结构。
- 不属于命令分发的读取：两塔投影内部查成员、入场后的精确性校验、计时器驱动的塔内回城、会话生命周期清理。
- `EffectOperationLedger` 用 `SequenceIsFresh` 做的效果重放判定，与命令陈旧帧不是同一概念。
- 各通道内部的领域逻辑与协议帧内容；普通拾取业务逻辑位于协议层的问题。
- issue #187 的其余条目：
  - 特殊地下城的可空布局字段及其分散识别；
  - 南部溪谷与 SAO 清场的硬编码调用；
  - 三套运行时各自的成员字典与“是否在副本中”的拼凑调用方；
  - 特殊地下城入场骨架与活动入口事件服务的重复；
  - 次数族的三份枚举；
  - 两塔投影与协调器的复制、塔快照中的队长副本；
  - `DungeonRunDomainService` 拆分与接口默认方法；
  - 0x0010 入场按目标分发的可选塔参数。
- issue #188 魔数 ID。
- 数据库结构、客户端补丁、版本号。

## Constraints

- 除 RI-4 授权的陈旧帧统一外，可观察行为不变：每个命令由哪个通道处理、协议帧、收件人、领域结果均保持现状。日志文本与级别不在保护范围内。具体包括：
  - 定位结果只有在对应副本服务认可这个请求者（塔认可这个会话、普通副本能由该角色找到）时才指向该副本；否则按现行代码的去向处理。上述两个已知不一致窗口都属于这种情况；
  - 组队类命令保持整队归属语义；
  - 0x000F 按 Goal 中的具名例外处理。
- 结构调整与陈旧帧行为变化分开说明和验证：表征测试在结构改动前提交，结构改动后断言不变。
- 版本号不改。
