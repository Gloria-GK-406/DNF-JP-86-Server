# Specification: 角色状态各自找到主人

## Why and Outcome

会话运行态聚合是一个九字段的 record，被一个会话目录长期持有。上一轮已经证明了这种形状会出什么
问题：剩余技能点住在它里面，没有任何东西负责在等级变化时重算，于是玩家升级之后看到的还是登录
那一刻的值。那一处已经修好了，修法是给那个数找到主人——角色实例现读现算。

**这一轮不是修同一类缺陷。** 逐项查过：身份与设置只在入场序列里被读，那是入场投影的正当用法；
任务状态与等级经验都被各自改变它们的路径写回，不会变陈；坐标是运行态本身住在会话里，会话就是
它的权威源。**没有第二个陈值。**

要修的是**没有主人**这件事本身。一个数没有主人，今天可能碰巧是对的，明天多一条改它的路径就会
再出一次上一轮那样的事。四样角色状态今天都处在这个位置：

- **身份**——槽位、名字、职业、成长类型。今天没有任何东西能改它，因为转职与解锁槽位还没做。
  但它们做进来的那天，写入要落到哪里？如果答案仍然是「往会话目录持有的那个九字段 record 里
  `with` 回去」，那就是上一轮那个 bug 的形状。而且职业这个数今天已经有多种可读形状：角色名单
  摘要带一份，身份带一份，技能态带一份——三份都从同一个库列来。
- **坐标**——它的落库时机挂在会话生命周期上：会话结束时要挂进当时正在跑的用例里落库，否则第二个
  连接写不进第一个持有的视图。这是运行态该有的样子，但它现在的持有者是一个大 record 的一个字段，
  改它要整体写回。
- **设置**——热键与选项。表读得出来，**写不回去**：玩家改键根本没有落地的通路。
- **暗帝连招页**——库里按页号分行，入场投影里是按页号寻址的列表，但角色活动态上还挂着一个恒为
  `null` 的单数字段，从来没有被填过。

**任务状态是个反例，值得记下来**：它的目标形状已经建好且完整——领域服务按角色交出任务簿实例，
实例有可改的行为与快照式的读，背后是三段式的领域 store。所以这一样不需要新建任何东西，只有一处
入场之后的读点还在读入场投影，把它重指即可。这条通路就是本 Spec 其余几样要长成的样子。

**疲劳是另一回事**：它没有主人，因为它整个没有实现——值写死、已用量恒为零、拒绝码定义了零引用、
档案标签读出来零消费、库里没有对应的列。本 Spec 只给它一个接缝并让进本处真的调用，**不记账**；
真的记账是下一个成果的事，因为那必须改变可观察行为，而本 Spec 必须逐值不变。

做完之后，四样状态各有主人，任务那一处读点归位，疲劳有了一个被真实调用的接缝；服务器对客户端
说的每一个字节都和现在一样。

## Task Perspective

- Core outcome: 角色的身份、坐标、设置、连招页各自有一个能回答它的主人，且那个主人的类别说得出
  它是什么——领域服务、领域 store 加实例、还是角色实例本身。这是消费者要的东西：转职、解锁槽位、
  改键、疲劳记账这些将来要改这些状态的功能，届时有地方落笔。
- Necessary support: 疲劳的接缝。它在本 Spec 里不产出任何价值（不记账、不改任何值），但它必须
  存在且被进本处真的调用——否则下一个成果落地时，调用面对不对没有任何东西证明过。
- Peripheral assurance: 逐值不变的证据、注入面判据的复核、`store` 一词仍只有一种读法的核对、
  仓库约定的记载。**例外**：疲劳调用点的变异验证不属于这一类——契约把它列为成功条件 C-7，
  它是本 Spec 交付的一个受控结果，因为「允许生产实现空转」这件事的成立完全依赖于它。

## Scope and Non-Goals

### In Scope

- 角色实例能回答自己的身份，每次询问现读
- 一个专门的领域服务持有并回答角色坐标
- 一个领域服务回答角色的按键与选项设置
- 一个领域 store 与其实例持有暗帝连招页
- 角色活动态上那个恒为 null 的单数连招字段退役
- 入场之后读任务状态的那一处改问已有的任务簿实例
- 疲劳的接缝、其不记账的实现、进本处的真实调用，以及证明该调用点会红的判据
- 仓库约定里关于这几样状态各自归谁的记载

### Non-Goals

- **疲劳的真实现**：存储、上限规则、每日重置、真的扣减、耗尽拒绝。那必须改变可观察行为，与本
  Spec 的逐值不变口径互斥
- **疲劳的持久化接缝**：本 Spec 不建 store 也不建表。一个什么都不存的 store 会让读代码的人以为
  持久化通路已经存在
- **会话运行态聚合本身不退役。** 入场投影里的公开态、进度、特性三块内容未查清，所有者要求本轮
  做完再定。聚合与持有它的会话目录在本 Spec 结束时仍然存在
- **收敛职业那几种可读形状。** 「同一个数有多处可读」是身份需要主人的动机，但契约只要求角色实例
  能回答身份、且入场序列之外不从会话聚合读它。把角色名单摘要与技能态各自那份职业也收敛掉，
  超出契约范围
- 账号侧状态、账号背包、角色背包、世界内容四个子面
- 转职与解锁槽位本身
- 为任务新建任何东西

## Constraints

- 服务器对客户端的可观察行为逐值不变
- 不新增任何协议帧，不改任何帧的字节布局
- 既有测试的期望值与断言不得为迁就实现而改写；类型改名带来的符号更新除外
- 本 Spec 新增一个领域 store。`store` 在领域层仍须只有一种读法：事务结算的真源
- 注入面判据的判定规则与具名豁免清单不得放宽或扩充

## Definitions

| Term | Meaning |
|---|---|
| 入场序列 | 选择角色之后，服务器为把这个角色送进游戏而下发的那一串状态帧的产生过程。它消费的是入场那一刻算出的投影 |
| 入场投影 | 入场那一刻从库里算出的一份快照。它按定义就是那一刻的样子，入场序列读它是正当的；入场**之后**再拿它当答案则不是 |
| 主人 | 一个数的单一现读来源，且是将来改这个数时写入要落到的地方 |

## External Behavior and Data Rules

- 身份的四个部分（槽位、名字、职业、成长类型）在本 Spec 里没有任何写入通路，因为改它们的功能
  尚未存在。本 Spec 只要求它们可以从角色实例问出来
- 入场编解码器是一组同步的纯字节写入函数，它们接收入场那一刻的角色快照作为参数。本 Spec 不改变
  这一点：让同步编码器去问一个会读世界的实例，会把编码变成异步的世界查询，那比现状差

## Assumptions

- 判据命令必须带档案路径环境变量，否则读档案的判据会静默跳过而不是报红。基线里那 2 个 skip
  正是档案已加载的标志
- 基线自带两个偶发失败：某个跨事务读取用例会抛已释放的 SQLite 句柄异常（单独复跑其所在项目即
  全绿）；网络项目在全量并行下出现过一次未记名的失败，两次复跑都没有重现
- 暗帝连招页在库里已有独立的行网关，按页号寻址。新增的领域 store 建在它之上，不新建表
- 热键与设置今天没有写回通路，所以设置那一项是纯新建接缝，不存在「搬移现有写入逻辑」的工作
- 疲劳今天在协议上报的是一个固定的总量与一个恒为零的已用量。本 Spec 的接缝要继续报出同样的两个
  值，因为逐值不变

## 一处前提写错，由完整变更评审查出（订正，原文保留）

**Why and Outcome 一节里这句话是错的**：

> 任务状态与等级经验都被各自改变它们的路径写回，不会变陈。

等级经验那半是对的。**任务状态那半是错的**，独立评审查出、控制器复核确认：

- `QuestOfferRefreshDomainService` 对 `CharacterEntry` **零引用**（`grep -c` = 0），它只改 `World.Subject`
  与 `World.Content`——刷新的是世界里的任务可接列表，不是角色的任务投影
- `AcceptQuestHandler` 根本不碰 `CharacterEntry`
- `FinishQuestHandler` 确实改 `CharacterEntry`，但改的是
  `Public.Extras.CharacterExperience`（经验），不是 `Quests`

**所以 `CharacterEntry.Quests` 自入场起就是陈的。**

**错误是怎么产生的**：控制器在写 Spec 前看到接/交任务的 handler 里 `offers.RefreshAsync(...)` 后面
紧跟 `runtimeSessions.ReplaceExact(...)`，据此推断任务投影被刷新了。没有去读 `RefreshAsync` 的实现。
这正是本 Spec 通篇在治的那类错——从方法名与位置推断它做了什么。

**对交付的影响**：RQ-008 与 AC-008 不受影响，它们说的是「那一处改问已有的任务簿实例」，仍然成立且
已达成。变的是这件事的**性质**：它不只是把读取点搬了个位置，**实质上修掉了一个潜在缺陷**——
入场之后接了或交了任务，那份投影不会跟着变。今天之所以仍然逐值不变，只是因为
`DungeonLayoutRuleService.SelectMaze` 刻意不读 facts（该服务自己的 remarks 写明 maze 筛选规则尚未
逆向出来）。等那条规则做出来，读陈值就会给出错的迷宫。

**原文保留不删。** 一份用来支撑验收判断的记载里出现过一句比代码强的论断，本身就是这个 Spec 要禁的
那类错误；删掉它比留着更容易让人再犯一次。这也是上一轮 multi-spec 任务处理同类情形的做法。
