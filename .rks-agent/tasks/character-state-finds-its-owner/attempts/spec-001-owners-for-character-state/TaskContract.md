# TaskContract: 角色状态各自找到主人

## Context

### Source Request

来自根任务 `character-state-finds-its-owner` 的第一个有界成果。根契约要求角色的身份、坐标、
设置、连招页各自有一个能回答它的主人，任务状态的入场后读点改问已有的任务簿，并为疲劳先立一个
占位接缝。本成果做这一整块，**不做疲劳的真实现**——那是第二个成果，它的验收口径与本成果互斥。

### Current Situation

基线 `427331bc`（上一轮任务 `commands-reach-only-domain-shapes` 三批已合并）。全量判据
2024 通过 / 2 跳过 / 0 失败。

会话运行态聚合 `SelectCharacterResult` 是一个九字段 record，被一个会话目录长期持有，协议层
12 个文件持有它，7 处整体写回，118 处子面读取。**本成果不退役它**（理由见 Scope Out），
只把角色侧的其中几样状态搬到各自的主人手里。

六件事各自的现状：

**身份**（槽位、名字、职业、成长类型）。5 处读全在入场消息工厂里——判断职业是不是暗帝、
是不是另一个特定职业，以及往几条消息里填角色 id。今天职业与槽位在全仓**零写入点**，但所有者
指出游戏里它们会变（转职改职业、解锁槽位任务改槽位），所以这是缺主人而不是不会变。承载它的
那个 record 同时被入场编解码器直接当参数消费，这一点见 Assumptions。

**坐标**（城镇、区域、X、Y、朝向）。6 处读（选副本切片一处、城镇投影切片四处、回城投影一处），
2 处整体写回（城镇投影切片里换地图与走动各一次）。落库时机挂在会话生命周期上：会话结束时
坐标要挂进当时正在跑的用例里落库，否则第二个连接写不进第一个持有的视图。所以坐标是运行态本身
住在会话里，会话就是它的权威源——它不是陈值，但它需要一个比「大 record 的一个字段」更像主人
的持有者。

**设置**（热键槽、选项位图、可见位）。2 处读都在入场序列。热键表与设置表今天只被入场装配器
读一次，**没有任何写回通路**——玩家改键根本没有落地。所以这一项是纯新建接缝，不搬任何现有的
写入逻辑。

**暗帝连招页**。入场投影里是按页号寻址的分页列表，库里的行也是分页的，已有独立的行网关。
1 处读在入场消息工厂。另有一个恒为 `null` 的单数残留字段挂在角色活动态上——角色名单服务显式
写 `null`，真正在用的是入场投影里的分页列表。

**任务状态**。目标形状**已经建好且完整**：任务簿领域服务按角色交出任务簿实例，实例有可改的
行为与快照式的读，背后是三段式的任务领域 store。入场投影里的任务字段有 3 处读，2 处在入场
序列（快照的正当用法），只有进本切片那一处在入场之后。

**疲劳**。整个是死的：值写死在角色名单服务里且已用量恒为 0，只被读两次往同一个帧里填两个数，
「疲劳不足」拒绝码定义了全仓零引用，档案里的「本副本不耗疲劳」标签读出来生产零消费，库里
没有当前疲劳与上限的列。本成果只给它一个接缝与一个不记账的占位实现。

### 为什么占位实现必须有会红的判据

空转接缝有一个已被实证的失败模式：没人证明调用点接对了。上一轮的独立评审把一个协议处理器
整段回退到读陈值，**全量判据仍然全绿**，因为那条路径零判据。疲劳占位正是同一种形状——如果
调用点漏了或数错了，空转实现不会报错，全量判据也不会红，要等到第二个成果把空转换成真账时
才会发现调用面是错的。所以本成果里，允许生产实现空转的前提是调用点本身有会红的判据。

## Goal

角色的身份、坐标、设置、连招页各自有一个能回答它的主人；入场之后读任务状态的那一处改问已有的
任务簿实例；疲劳有一个接缝并被进本处真的调用，其调用点有会红的判据。服务器对客户端的行为
逐值不变。

## Scope

### In

- 角色实例能回答自己的身份；入场序列之外不从会话运行态聚合读它
- 一个专门的领域服务持有并回答角色坐标
- 一个领域服务回答角色的按键与选项设置
- 一个领域 store 与其实例持有暗帝连招页；恒为 null 的单数残留字段退役
- 入场之后读任务状态的那一处改问已有的任务簿实例
- 疲劳的接缝、其不记账的占位实现、进本处的真实调用，以及证明该调用点会红的判据
- 仓库约定里关于这几样状态各自归谁的记载

### Out

- **疲劳的真实现**：存储、上限规则、每日重置边界、真的扣减、耗尽拒绝。那是第二个成果，它必须
  改变可观察行为，与本成果的逐值不变口径互斥
- **疲劳的持久化接缝**：本成果不建 store 也不建表。一个什么都不存的 store 比没有 store 更糟，
  它会让读代码的人以为持久化通路已经存在
- **会话运行态聚合本身不退役。** 入场投影里的公开态（15 处读）、进度（11 处读）、特性（8 处读）
  三块内容未查清，所有者要求本轮做完再定。聚合与持有它的会话目录在本成果结束时仍然存在
- 账号侧状态、账号背包、角色背包、世界内容四个子面
- 转职与解锁槽位本身。身份需要主人的理由是它们将来会改它，实现它们不在本成果
- 为任务新建任何东西。那条通路已完整，本成果只重指一处读点

## Constraints

- 服务器对客户端的可观察行为逐值不变
- 不新增任何协议帧，不改任何帧的字节布局
- 既有测试的期望值与断言不得为迁就实现而改写；类型改名带来的符号更新除外
- 本成果新增一个领域 store。`store` 在领域层仍须只有一种读法：事务结算的真源
- 注入面机检判据的判定谓词与具名豁免清单不得放宽或扩充

## Assumptions

- 判据命令必须带 `PVF_ARCHIVE_PATH`，否则读档案的判据会静默跳过而不是报红。基线里那 2 个
  skip 正是档案已加载的标志
- 基线自带两个偶发失败，见到不要当成自己引入的回归：某个跨事务读取用例会抛已释放的 SQLite
  句柄异常（单独复跑其所在项目即全绿）；网络项目在全量并行下出现过一次未记名的失败，两次复跑
  都没有重现。详见根图的 `baseline_evidence`
- **承载角色身份的那个 record 同时是入场投影的快照类型，入场编解码器直接把它当参数消费。**
  「身份归实例」要走多远——只在实例上暴露成员，还是把字段从那个 record 上摘掉——是一处边界
  决定，两种做法都满足「身份有主人」。本成果的 Spec 要明写它选了哪一种及理由，交由评审裁决；
  不得默默选一种
- 暗帝连招页在库里已有独立的行网关，按页号寻址；新增的领域 store 建在它之上，不新建表
- 热键与设置今天没有写回通路，所以设置那一项是纯新建接缝，不存在「搬移现有写入逻辑」的工作
