# Routing Decision

- TaskContract: `./TaskContract.md`
- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 稳定。六样状态各自的归宿由所有者逐项裁决，且每一条都给了理由
  ——身份归实例（转职与解锁槽位将来会改它）、坐标归专门的领域服务（落库时机挂在会话生命周期上）、
  设置归领域服务而不是 store（够不上事务结算的门槛）、连招归 store 与实例（按页号寻址、一角色
  多页）、任务那一层不新建（目标形状已存在）。可观察结果也定了：逐值不变。
- Requirement stability: 11 条成功条件，每条可独立核对。搬家类靠「读取点全部枚举，逐个说明
  去向」；连招那条另加残留字段的全仓计数；疲劳占位那条靠变异验证指名哪一条判据会红；护栏类靠
  既有机检判据的 diff。
- Execution direction: 已知。目标形状在仓库里有完整样板——任务那条通路（领域服务交出实例、
  实例背后是三段式 store）就是这套词汇的现成实例，连招要建的是同一形状；坐标那个持有活状态的
  领域服务也有先例，上一轮已把四个持字典的容器转成过同一形状。
- Remaining uncertainty: 一处，且已写进契约 Assumptions 要求 Spec 明写选择并交评审裁决——承载
  身份的那个 record 同时是入场编解码器直接消费的快照类型，「归实例」是只暴露成员还是把字段摘掉，
  两种做法都满足所有者的意思。这是实现边界，不改变任务语义。

## Marginal Control Value

- User precision signal: 明确偏精度。所有者亲自指定 multi-spec，在本轮对话里逐项推翻了执行方的
  几个判断并要求把理由记下（身份是否会变、任务那一层该叫什么）。同时他有一个具体的速度诉求
  ——疲劳先占位好让他继续实机测试——那是范围决定，不是精度让步。
- Direct failure mode: 具体且已被实证。其一，本成果六件事分散在五个层，逐值不变是唯一能自动
  发现夹带的东西；Direct 没有地方把「哪一处期望值改动对应哪一次类型改名」逐条归因，改坏一个
  帧字段不会被任何东西挡住。其二，疲劳占位是空转实现，上一轮评审实证过同形状的漏洞：一个协议
  处理器整段回退到读陈值，全量判据仍然全绿，因为那条路径零判据。
- Useful control: 稳定的 Spec 固定「逐值不变」这条口径与六样状态各自的归宿；实现计划把六件事
  排成有依赖顺序的任务并给每件定可执行的检查；完整变更集的独立评审；以及对占位调用点的变异
  验证（C-7 直接把它写成成功条件）。
- Time-for-quality rationale: 六件事里有一件要新增领域 store（跨 Abstractions 与 Persistence
  两层并接进事务参与者），有一件是纯新建接缝，其余四件是读取点搬家。先把归宿与顺序定死再动手，
  比边做边改便宜——共享同一个入场投影的几处读点若不先定归属，会成批返工。变异验证的成本只有
  一次改坏与还原，却是「到第二个成果才发现调用面是错的」的唯一拦截点。

## Structural Selection

- Selected workflow: `single-spec-workflow`
- Boundary evidence: 一个验收边界（服务器对客户端逐值不变），一个回滚边界（本成果的全部改动
  可整体接受或整体回退到 427331bc）。六件事共享同一个口径，不构成互相独立的验收边界——它们是
  同一个口径下的几段工作量，而 Multi Spec 的边界要求的是口径互斥。
- Why Direct is insufficient: Direct 拿不到「逐值不变」的逐条归因，也没有地方存放变异验证的
  记录；而这两样正是本成果唯一的两道护栏。
- Why Multi is unnecessary: 六件事无法被单独接受——它们要么一起满足逐值不变，要么一起不满足；
  拆开会让每一份都要独立跑一次全量判据并各自归因，成本翻倍而不增加保护。真正的口径互斥在本
  成果与疲劳真实现之间，那已经由根控制器切成了两个 Spec。
- Reroute conditions: 若连招那个领域 store 的事务参与者接线牵动了别的 store 的结算顺序，使得
  它必须能被独立接受或回滚，则本成果出现了第二个验收边界，应停下返回根控制器重新切分。反之，
  若身份那处边界决定在实现中被发现会带出可观察行为变化（例如入场帧的取数时机改变），那是本
  成果内部的边界收紧，按 Spec 的评审流程处理，不改变本次结构选择。

## Controller Selection

- Controller: `sdd-standard`
- Profile source: `code-refactor`
- Why this is sufficient: Standard 相对 Lite 多出来的那个控制是**持久的实现计划**，而本成果恰好
  有它要挡的那类失败：**真实的顺序依赖**与**会传播的早期选择**。
  顺序依赖有三条：连招的领域 store 必须先定形（Abstractions 接口 + session + Persistence 实现 +
  事务参与者接线）才谈得上它的实例与读点重指；坐标领域服务必须先存在，6 处读与 2 处整体写回才有
  去处；疲劳接缝必须先存在，调用点与那条会红的判据才立得起来。
  会传播的早期选择有两处：其一是身份那处边界决定（只在实例上暴露成员，还是把字段从那个 record
  上摘掉）——后者会涟漪到入场编解码器的 3 个调用点与另外 2 个 record 字段，选错要到评审才发现，
  那时六件事已经全做完了；其二是**六件事里有四件动同一个文件**（入场消息工厂：身份 5 处、设置
  2 处、连招 1 处、任务 2 处不动），归属不先定就会在同一个文件上反复返工。
  Profile 选 code-refactor，因为本成果的验收口径就是行为逐值不变——疲劳接缝虽是新增，但它不改
  任何值。
- Why lighter is insufficient: Lite 没有 `plan.md`。上面那三条顺序依赖与两处早期选择，Lite 只能
  靠执行时的内联判断，而它们的代价正是在最终评审之前就已传播开——这是 Lite 的完整结果评审无法
  廉价纠正的那一类。
- Why heavier is unnecessary: Governed 的独有控制是独立挑战、独立产物批准、计划漂移控制与审计级
  证据。本成果碰不到任何一条硬底线：不涉安全、凭据、授权、隐私、财务合规；没有不可逆的外部变更
  （推送未授权，全部改动可整体回退到 427331bc）；也没有无恢复通路的持久数据丢失风险——连招 store
  建在一个已存在的只读行网关之上，不做迁移也不做破坏性写入。既然那些控制挂不到具体的失败路径上，
  就不买。
