# TaskContract: 角色的每样状态各自找到主人

## Context

### Source Request

所有者原话：「你需要一次性完成批次A和B，起一个multi-spec的任务契约执行吧。然后具体怎么分配spec你来决定。」

这句话之前，所有者与我在同一轮对话里逐项定下了两批的内容。相关的原话按项列在下面的
「所有者的裁决」一节，因为其中几条与我先前的判断相反，理由只有所有者知道。

### Current Situation

基线 `427331bc`（上一轮 multi-spec 任务 `commands-reach-only-domain-shapes` 的三批已合并）。
全量判据 2024 通过 / 2 跳过 / 0 失败。

上一轮做完之后清点全仓，命令处理器的注入面已由机检守住、静态规则类与档案内容源已全部收归
规则服务、聚合命令的专用性成立。剩下最大的一块是会话运行态聚合 `SelectCharacterResult`：
九个字段的 record，被一个会话目录长期持有，协议层 12 个文件持有它，7 处整体写回，118 处
子面读取。

**逐项查过之后，没有第二个「升级后剩余 SP 不动」那样的缺陷等着修。** 这一点必须先说清楚，
因为它决定了这一轮的性质：

- 身份与设置只在入场序列里被读——那是入场投影的正当用法，与上一轮定下的先例一致
- 任务状态与等级经验都被各自改变它们的路径写回，不会变陈
- 坐标是运行态本身住在会话里，会话就是它的权威源，也不是陈值
- **唯一真正没有主人的是疲劳，而它整个是死的**

所以这一轮是结构工作，不是修缺陷。它要做的是让这几样角色状态各自有一个能回答它、将来也能
改它的主人；以及把疲劳从一个假装成状态的常量，变成一个真的子系统。

#### 疲劳今天的样子

五条互相独立的证据说明它没有实现：

| 事实 | 位置 |
|---|---|
| 值是写死的，已用量恒为 0 | 角色名单服务里 `new CharacterFatigueState(188, 0)` |
| 只被读两次，都是往同一个帧里填两个数 | 状态同步的背包段编解码器 |
| 「疲劳不足」拒绝码定义了，全仓零引用 | 进本切片的拒绝码常量 |
| 档案里的「本副本不耗疲劳」标签读出来了，生产零消费 | 副本定义内容源，只有一条测试断言它 |
| 库里没有当前疲劳与上限的列 | `character_condition` 有体力、疲劳惩罚、疲劳加速三个**别的**东西 |

写死的 188 恰好等于所有者给出的「基础 156 + 黑钻 32」，也就是现状等于「假设人人有黑钻」。

### 所有者的裁决

以下几条是所有者做出的结构判断，其中三条与我先前的判断相反。理由原样保留，因为后续任何一个
成果都不得凭自己的推断改动它们。

**身份要挪到角色实例下。** 所有者原话：「identity要挪到char下，这里槽和职业会在游戏里可能
变化。比如转职，完成解锁槽任务。」——我先前从代码推断「除改名外不会变」，那是反的：今天职业
与槽位全仓零写入点，只说明功能没做，不说明游戏里不变。

**坐标不放在角色实例下，用一个专门的领域服务处理。** 所有者原话：「最后就是position，这不要
在char下，用positiondomainservice来处理。」

**设置用领域服务，不用 store。** 所有者原话：「setting的话说实话用store是有点奇怪，还是用
domainservice吧。」

**暗帝连招用 store。** 所有者原话：「darknightcombo是一个特殊的setting，用Store来存。因为一个
角色可以有多个combo，这些combo合一起组成一个instance。」

**疲劳记用了多少，不记剩多少。** 所有者原话：「所以疲劳我觉得应该记用了多少，而不是剩多少。
然后按使用者写入表。」上限是从「基础值 + 账号权益」派生的，存剩余量会在权益开通或到期时变陈
——与上一轮修的剩余 SP 是同一个模子。

**第一批里疲劳只做占位。** 所有者原话：「先实现占位就好了，正常调用sub和add。sub和add先不做
内部处理。这样能减出来疲劳系统，也不会因为疲劳系统让我测试时候归0没法测了。然后执行上先完成
我确定的其他项，然后单开一个spec来跑疲劳系统的构建吧。」——理由是所有者要能实机测试，真的
疲劳系统会让他归零之后进不了本。

**任务那一层不新建。** 所有者原本设想「questContainerStore 用 charid 获取 queststore」。我指出
下面那层按他自己的词汇是 instance 而不是 store——上一轮花了整个成果把 `store` 收敛成一种读法
（事务结算的真源），若按 charId 取出来的可改东西也叫 store，这个词立刻回到两种读法。所有者
接受。而这条通路在仓库里已经建好且完整：任务簿领域服务按角色交出任务簿实例，实例背后是三段式
的任务领域 store。所以这一项只剩一处入场之后的读点要重指。

### 为什么这是两个成果而不是一个

第一批的验收口径是**行为逐值不变**（疲劳占位不改任何值）。第二批**必须**改变可观察行为
（疲劳真的会扣、扣光会被拒）。放进同一个成果，会让第一批的逐值不变判据失去意义——任何差异都
能被归给「那是第二批该改的」。这与上一轮把三批分开的理由同构。

两者各自单独完成都是可交付成果，且可以在不牵动另一个的前提下被接受或回滚。

## Goal

角色的身份、坐标、设置、连招页各自有一个能回答它的主人，任务状态的入场后读点改问已有的任务簿；
疲劳从一个假装成状态的常量，变成一个按「用了多少」记账、上限由基础值与账号权益现算、跨过每日
重置时刻自动归零的子系统，耗尽时进本被既有的拒绝码拒绝。

## Scope

### In

- 角色实例能回答自己的身份；入场序列之外不再从会话运行态聚合读它
- 角色坐标由一个专门的领域服务持有并回答
- 角色的按键与选项设置由一个领域服务回答
- 暗帝连招页由领域 store 与其实例持有；恒为 null 的单数残留字段退役
- 入场之后读任务状态的那一处改问已有的任务簿实例
- 疲劳的接缝与其调用点（第一批占位，第二批记真账）
- 疲劳的存储、上限规则、每日重置边界、进本扣减与耗尽拒绝
- 仓库约定里关于这几样状态各自归谁的记载

### Out

- **会话运行态聚合本身不退役。** 入场投影里的公开态、进度、特性三块（合计 34 处读）内容
  未查清，所有者明确要求本轮做完再定。因此聚合与持有它的会话目录在本轮结束时仍然存在，
  本轮只做到「角色侧的其中几样状态找到主人」
- 账号侧状态、账号背包、角色背包、世界内容四个子面
- 第一批不建疲劳的持久化。一个什么都不存的 store 比没有 store 更糟——它会让读代码的人以为
  持久化通路已经存在
- 转职与解锁槽位本身。身份需要主人的理由是它们将来会改它，但实现它们不在本轮
- HP/MP 等派生属性随等级成长
- 升级之后补发角色面板帧；地面金币堆没有服务端日志。两件旧事，所有者说后面再说
- 入场背包租约那个带版本与脏标记的写回缓存

## Constraints

- 只有第二个成果可以改变可观察行为，且只限于疲劳的记账与耗尽后的进本拒绝。第一个成果对
  客户端逐值不变
- 不新增任何协议帧，不改任何帧的字节布局。疲劳耗尽用的是既有的那个拒绝码
- 既有测试的期望值与断言不得为迁就实现而改写。类型改名带来的符号更新，以及正对应上面那一处
  被授权行为变化的改写，是例外

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 角色实例能回答自己的身份（槽位、名字、职业、成长类型），每次询问现读，不持有跨询问的缓存；入场序列之外，生产代码不从会话运行态聚合读身份 | 实例的成员与实现；身份读取点的全部枚举，逐个说明去向 |
| SC-2 | 角色坐标由一个专门的领域服务持有并回答，不由角色实例回答；会话运行态聚合不再是坐标的取数与写回位置 | 该领域服务的成员；坐标全部读取点与写回点的去向枚举 |
| SC-3 | 角色的按键与选项设置由一个领域服务回答 | 该领域服务的成员；设置读取点的去向 |
| SC-4 | 暗帝连招页由领域 store 与其实例持有；那个恒为 null 的单数残留字段在全仓不再存在 | store 与实例的成员；残留字段的全仓计数为 0 |
| SC-5 | 入场之后读任务状态的那一处改为向已有的任务簿实例提问，且没有为任务新建第二条通路 | 该读取点的去向；本成果新增的任务相关类型清单为空 |
| SC-6 | 疲劳有一个接缝，进本处真的向它报告本次消耗；第一批里它不记账，且这一点可从代码本身读出 | 接缝的成员与其占位实现；进本处的调用 |
| SC-7 | 第一批里疲劳的调用点在被改坏时判据会红 | 变异验证记录：移除或改错进本处的调用，判据失败；还原后恢复通过 |
| SC-8 | 第一个成果做完时，服务器对客户端的行为逐值不变 | 全量判据通过；测试改动中凡改动期望值者都能逐条归因到类型改名，无一处是行为差异 |
| SC-9 | 疲劳按「用了多少」记账；上限由基础值与账号权益现算，服务器里不存在存放剩余量的位置 | 存储的形状；上限两个输入各自的来源；剩余量存储位置的全仓计数为 0 |
| SC-10 | 跨过每日重置时刻之后疲劳消耗归零，且这不依赖任何定时任务或后台触发器 | 一条跨重置时刻的判据；重置不由触发器完成的证据 |
| SC-11 | 疲劳耗尽时进本被拒，用的是既有的那个拒绝码 | 一条耗尽后进本的判据；该拒绝码由零引用变为有引用 |
| SC-12 | 每日补货的行为不变，其日边界不因疲劳而改动 | 每日补货相关判据通过；其边界规则的 diff 为空 |
| SC-13 | 命令处理器注入面判据仍然通过，且其判定谓词与具名豁免清单未被放宽或扩充 | 判据结果；判定谓词与豁免清单的 diff |
| SC-14 | 领域层中 `store` 一词仍只有一种读法：事务结算的真源 | 本轮新增类型的命名与分类逐个对照 |
| SC-15 | 仓库约定记下这几样状态各自归谁，且如实写下会话运行态聚合仍然存在 | 被改动的记载与对应代码事实的逐条核对 |

## Requires Confirmation

- 合并到主干、推送、创建 PR、清理任务 worktree 与分支。所有者未授权，逐项都要单独取得

## Assumptions

- 判据命令必须带 `PVF_ARCHIVE_PATH`，否则读档案的判据会静默跳过而不是报红。基线里那 2 个
  skip 正是档案已加载的标志
- 基线自带一个偶发失败：某个跨事务读取用例会抛已释放的 SQLite 句柄异常，单独复跑它所在的
  项目即恢复全绿。**不要把它当成自己引入的回归**
- 承载角色身份的那个 record 同时是入场投影的快照类型，入场编解码器直接消费它。本轮继续把它
  当快照用，与上一轮「入场序列的帧读入场投影是正当用法」的先例一致
- 疲劳的游戏事实由所有者给出：基础 156 点、黑钻额外 32 点、抗疲劳药剂可恢复、每日 6 点重置。
  写死的 188 = 156 + 32 是对前两条的印证
- 黑钻加成经账号权益表可达，且该表的行带到期时间
- 仓库已有一套惰性期号机制（按日折算 + 记录的期号与当前期号比较），每日补货在用它。疲劳的
  重置时刻与它不同，需要自己的边界而不是改动它
