# Specification: 任务日志成为自己的领域

## Why and Outcome

任务现在不是一个领域概念，只是挂在人物存储上的一批行，规则散在协议层的命令 handler 里。
这已经带来两个可见后果：同一张任务表有两个互不知情的读法；受理规则（查重、占槽）写在
只该做编排的地方。再加上任务完成、放弃、追踪三条协议还没实现，规则会继续按现在的方式复制。

改完之后：任何要问「这个角色在做什么任务、完成过什么任务」或要改动它们的代码，都通过**一个
按角色取得的任务桶**；任务状态由自己的存储承载，不再是人物的一部分；协议层只负责解码、编排
与回包。玩家侧不应察觉任何变化——线上字节与落库结果与改动前完全一致。

## Task Perspective

- Core outcome: 一个按角色取得的任务桶，同时持有在做的与已通关的任务，并且**它自己判定**
  一次领取该成还是该拒、该占哪个槽；调用方拿到的是结果，不是自己算出来的结论。
- Necessary support: 任务状态迁出人物存储、已通关任务可被记录与读回、现有两个写入方改经桶、
  同一份状态的读取路径关系被理清——没有这些，桶只是又一个入口而不是唯一入口。
- Peripheral assurance: 线级重放与落库比对、全量测试、文档更新——它们证明结果，不是结果本身。

## Scope and Non-Goals

### In Scope

- 按角色取得任务桶；桶作答在做的任务与已通关的任务。
- 桶上的动作：领取、推进进度、放弃、完成、追踪与取消追踪。
- 领取的判定（同一任务是否已在做、是否还有空槽、槽位如何选定）由桶给出，并给出可区分的拒绝理由。
- 任务状态由自有存储承载，且与既有存储处在同一个事务参与者之下。
- 已通关任务的记录与读回。
- 现有两处任务写入改为经由桶。
- 同一份任务状态的读取路径关系理清。
- 受本次改动影响的文档更新。

### Non-Goals

- 任务完成、放弃、追踪各自的**协议**实现——本 Spec 只要求领域能表达这些动作。
- 完成任务时的奖励发放流程。
- 「已通关且不可重复」与「前置未满足」两条受理判据的补齐。
- 在任务实例中保存目标与奖励的内容快照。
- 服务架构调整。

## Constraints

- 玩家可见行为不变：领取任务的应答、其后的可接任务表、入场批次中与任务相关的帧，
  改动前后逐字节一致。
- 落库结果不变：同一次领取写出的槽位与进度值与改动前相同。
- 不改变分层依赖方向、命令总线与管线、事务参与者规则。
- 开发阶段的库结构变更采取重建而非迁移。

## Definitions

| Term | Meaning |
|---|---|
| 任务桶 | 一个角色的全部任务状态所对应的领域对象：在做的任务、已通关的任务，以及作用于它们的动作 |
| 在做的任务 | 该角色已领取尚未完成的任务，占据一个槽位，带有一个进度值 |
| 已通关的任务 | 该角色完成过的任务的记录 |
| 进度值 | 一次任务的完成度，由若干独立计数通道打包而成 |
| 领取结果 | 一次领取的结论：成功并给出槽位与初始进度，或失败并给出可区分的理由 |

## External Behavior and Data Rules

- 任务桶不缓存状态：任何一次询问的答案都反映询问那一刻的存储，包括同一用例内此前已经写入
  但尚未落定的改动；一次用例回滚之后再问，答案回到回滚前。
- 一个角色的在做的任务占据互不相同的槽位；槽位的选取在相同的既有状态下是确定的。
- 领取一个该角色已经在做的任务不改变任何状态，并以可与其他失败区分的理由被拒绝。
- 在做的任务与已通关的任务改动可以与同一用例内的物品改动一同成立或一同不成立。
- 任务状态不再出现在人物领域的读写词汇里。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 给定一个角色，可以取得该角色的任务桶；同一角色重复取得所指的是同一份状态。 |
| RQ-002 | 任务桶可作答该角色在做的任务，每一条带有任务标识、槽位与进度值。 |
| RQ-003 | 任务桶可作答该角色已通关的任务。 |
| RQ-004 | 任务桶接受一次领取请求，并给出领取结果：成功时含槽位与初始进度，失败时含可区分的理由。 |
| RQ-005 | 领取一个该角色已在做的任务被拒绝，且不改变任何状态。 |
| RQ-006 | 在没有空槽时领取被拒绝，其理由与「已在做」可区分，且不改变任何状态。 |
| RQ-007 | 领取成功时占用的槽位在相同既有状态下是确定的，与改动前对同一输入给出相同槽位。 |
| RQ-008 | 任务桶可推进一条在做的任务的进度值。 |
| RQ-009 | 任务桶可将一条在做的任务转为已通关，此后它不再出现在在做的任务中，且出现在已通关的任务中。 |
| RQ-010 | 任务桶可放弃一条在做的任务，此后它不再出现在在做的任务中，也不出现在已通关的任务中。 |
| RQ-011 | 任务桶可作答并改变该角色的任务追踪选择。 |
| RQ-012 | 任务桶的作答反映询问那一刻的状态，包含同一用例内已写入尚未落定的改动。 |
| RQ-013 | 一次用例回滚后，任务桶的作答回到该用例开始前的状态。 |
| RQ-014 | 同一用例内对任务状态与物品状态的改动一同成立或一同不成立。 |
| RQ-015 | 人物领域的读写词汇中不再包含任务状态。 |
| RQ-016 | 入场后修正任务进度这一既有行为，其可观察结果与改动前一致。 |
| RQ-017 | 领取任务的线上应答与其后的可接任务表，改动前后逐字节一致。 |
| RQ-018 | 一次领取写入的槽位与进度值，改动前后一致。 |
| RQ-019 | 入场批次中与任务相关的帧，改动前后逐字节一致。 |
| RQ-020 | 同一份任务状态的读取路径或者只剩一条，或者其为何仍是多条、以及多条之间如何保持一致有明确结论可查。 |
| RQ-021 | 领取的判定不再由协议层的编排代码作出。 |
| RQ-022 | 受本次改动影响的文档反映改动后的形状。 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 一个存在的角色 | 两次取得它的任务桶并各写入一条不同的在做的任务 | 任一次取得的桶都能作答两条 |
| AC-002 | RQ-002 | 一个角色已领取两个任务 | 询问在做的任务 | 得到两条，各带任务标识、槽位与进度值 |
| AC-003 | RQ-003 | 一个角色有一条已通关记录 | 询问已通关的任务 | 该任务在其中 |
| AC-004 | RQ-004, RQ-007 | 一个尚未领取任何任务的角色 | 领取一个存在的任务 | 结果为成功，槽位为最小可用槽位，初始进度为该任务内容声明的值 |
| AC-005 | RQ-005 | 一个角色已在做某任务 | 再次领取同一任务 | 结果为失败且理由为「已在做」；在做的任务条数不变 |
| AC-006 | RQ-006 | 一个角色的槽位已全部占满 | 领取又一个任务 | 结果为失败且理由与「已在做」不同；在做的任务条数不变 |
| AC-007 | RQ-008 | 一个角色有一条在做的任务 | 把它的进度值推进到另一个值 | 再次询问时该条的进度值为新值 |
| AC-008 | RQ-009 | 一个角色有一条在做的任务 | 将其转为已通关 | 在做的任务中不再有它，已通关的任务中有它 |
| AC-009 | RQ-010 | 一个角色有一条在做的任务 | 放弃它 | 在做的任务与已通关的任务中都没有它 |
| AC-010 | RQ-011 | 一个角色 | 设置其任务追踪选择后再询问 | 得到刚设置的选择 |
| AC-011 | RQ-012 | 一个用例内已向任务桶写入一条在做的任务且尚未落定 | 在同一用例内询问在做的任务 | 该条在其中 |
| AC-012 | RQ-013 | 一个用例内向任务桶写入后该用例回滚 | 回滚之后询问在做的任务 | 该条不在其中 |
| AC-013 | RQ-014 | 一个用例内既改任务状态又改物品状态 | 该用例失败回滚 | 两侧改动都不存在；该用例成功时两侧改动都存在 |
| AC-014 | RQ-015, RQ-021 | 改动后的实现 | 查看人物领域的读写词汇与协议层的领取编排 | 前者不含任务状态；后者不含领取判定 |
| AC-015 | RQ-016 | 一个入场后需要修正任务进度的角色 | 完成一次入场 | 修正后的进度值与改动前相同 |
| AC-016 | RQ-017, RQ-018 | 与改动前相同的角色与任务 | 在线上发起一次领取 | 应答与其后的可接任务表与改动前逐字节相同；写入的槽位与进度值相同 |
| AC-017 | RQ-019 | 与改动前相同的角色 | 完成一次入场 | 入场批次中与任务相关的帧与改动前逐字节相同 |
| AC-018 | RQ-020 | 改动后的实现 | 追查任务状态的读取路径 | 只存在一条，或存在一份说明其为何多条及如何保持一致的结论 |
| AC-019 | RQ-022 | 改动后的实现 | 查阅受影响的文档 | 其描述与改动后的形状一致 |

## Assumptions

- 领取任务当前的线上行为已被验证为与参照会话逐字节一致，可作为「改动前」的基准。
- 任务状态与物品状态同库，因而处在同一个事务参与者之下；这是 RQ-014 可以成立的前提。
- 客户端与服务端读取同一份任务内容声明，因此不为在做的任务保存内容快照不会造成两侧不一致。
