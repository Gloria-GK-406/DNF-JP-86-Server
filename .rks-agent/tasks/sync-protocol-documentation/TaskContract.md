# TaskContract: 同步服务端协议实现与 A21 协议资料库

## Context

### Source Request

用户要求“迁出一个新分支把这部分补全”，并明确指出服务端代码不一定准确，写协议文档时必须结合逆向结果与 DNF 客户端实际行为共同判别；当协议已经完全探明时，允许直接修正机器生成区域。用户同时要求记住这项长期约定，并授权“放手去做”。

### Current Situation

当前 `main` 的协议实现面明显领先于 `protocol/catalog.md`：源码注册表包含但进度清单未登记的 C→S decoder 与 S→C encoder-backed wire identity 数量较多；部分单协议页仍写着“未实现”或只有生成骨架，另有静态普查盲区导致 `CMD 0x0084` 没有独立页面。代码、旧上游实现、A21 逆向结果和真实客户端行为之间也存在冲突，不能以任一单一来源直接定案。

## Goal

在独立 Git 分支中恢复 A21 协议资料库的权威性：让进度清单、单协议记录、流程记录和可重复检查准确反映现有证据，显式区分服务端实现、逆向结论、线级观察与真实客户端验证，并消除已知遗漏和矛盾。

## Scope

### In

- 盘点 Game C→S decoder、S→C CMD/NOTI encoder 与实际调用路径，并与 `protocol/catalog.md`、单协议页及流程页交叉核对。
- 对照 A21 客户端静态逆向、已有抓包/日志/实机记录、上游参考实现和当前服务端代码，逐条确定可支持的阶段、方向、响应关系、布局与置信度。
- 补齐 `CMD 0x0084` 等缺失记录，修复 `0x0003`、`0x002D`、`0x0048`、`0x0117` 及同类陈旧或矛盾内容。
- 在证据足以闭合时修正机器生成输入、生成逻辑或机器区；无法完全闭合时保留未知并明确证据边界。
- 更新 `protocol/catalog.md` 及必要的 `protocol/game/**`、`protocol/patterns/**`、`Document/**` 文档。
- 增加可重复的资料库同步检查，至少能发现“代码已注册但 catalog 未登记”与缺失协议页。
- 写入一条用户要求的记忆更新备注，记录本任务的长期证据原则。

### Out

- 不修改协议业务实现、网络运行时、客户端二进制或 ClientHack 行为；若审计发现代码疑似错误，只记录证据与风险，不顺手修代码。
- 不把服务端注册、单元测试或参考服行为自动升级为 A21 `ClientVerified`。
- 不补造不存在的实机样本，不在证据不足时猜测字段语义。
- 不执行 merge、push、PR、发布或工作树清理。

## Constraints

- 每个重要协议主张必须标明证据来源和置信度；当前服务端代码只能证明“当前实现是什么”，不能单独证明线协议正确。
- A21 客户端自身的构包/解包路径与真实客户端行为优先于旧 A12 脚手架；上游服务端仅作为参考证据。
- 机器生成区域并非不可修改的真相。完全探明的内容可以直接修正，但应优先修正可重复生成的输入或生成逻辑，并保留证据来源。
- 文档使用 Markdown，项目文档放在 `Document/`；协议资料继续遵循现有 `protocol/` 四层组织。
- 保留用户现有工作；所有仓库改动都在新分支的隔离工作树中完成。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 当前所有已注册 C→S Game decoder 都能在 catalog 或明确排除清单中找到，且存在对应协议页 | 自动差集检查为零；注册表、catalog 与文件存在性报告 |
| SC-2 | 当前所有 encoder-backed S→C Game wire identity 都能在 catalog 或明确排除清单中找到 | 自动差集检查为零；encoder inventory 与 catalog 对账报告 |
| SC-3 | `CMD 0x0084` 有独立 A21 协议记录，方向、名称、请求/响应与静态普查盲区均有证据 | 新协议页引用 A21 实机记录、当前注册与客户端/上游路由证据 |
| SC-4 | 已知陈旧矛盾被修复，且不再把代码存在等同于协议正确或实机验证 | 对 `0x0003`、`0x002D`、`0x0048`、`0x0117` 及发现的同类页面执行精确搜索和人工核对 |
| SC-5 | catalog 的阶段、角色和链接与每条协议当前证据边界一致 | catalog 对账、链接检查、阶段抽样与协议页交叉核对 |
| SC-6 | 机器区的修正可解释、可再生或明确记录为受证据支持的人工修正 | 生成安全检查、相关输入/脚本 diff、证据引用 |
| SC-7 | 协议资料生成/检查脚本和相关测试通过，仓库无无关改动 | 项目既有 protocol 检查、Markdown/链接检查及针对新增同步检查的验证结果 |
| SC-8 | 完整成果在独立分支形成一个经过审查与新鲜验证的本地提交 | 审查结论、验证记录、提交哈希与干净工作树 |
| SC-9 | 长期证据原则已提交到 Codex 记忆更新入口 | `extensions/ad_hoc/notes/` 下新增的单一备注文件 |

## Authorization

| Capability | Evidence | Authorized scope |
|---|---|---|
| task | 用户：“你看看迁出一个新分支把这部分补全一下……这部分记忆一下。放手去做吧” | 创建独立任务分支/工作树，更新上述协议文档、生成输入与同步检查，执行验证，写记忆更新备注，并创建一个验收后的本地结果提交 |

## Requires Confirmation

- merge、push、PR、发布、删除分支或清理工作树。

## Assumptions

- 现有仓库中的 A21 抓包、逆向记录、运行日志和测试足以完成本轮“已实现协议文档同步”；缺少闭合证据的协议允许保持未知或较低阶段，而不是阻塞整个任务。
- “补全”指恢复资料库对当前证据的覆盖与一致性，不要求在本任务中重新逆向全部 1410 条协议。
