# Routing Decision

任务：`the-container-decides-the-entry-shape`
契约：`./TaskContract.md`（revision 1, state ready, SC-1..SC-9）

## SDD Readiness

**就绪，而且这次的证据比上一件强。**

- **规则来自客户端自己的原生代码**：`0x01637740` 未被虚拟化，三行分支
  （选择子 1 / 3 / 其余）逐条可读、可复核。不是推断。
- **形状经实机两轮验证**：装扮栏放 1 件、放 11 件都正常进入游戏、零异常。11 条连续记录
  全部对齐，这是「形状对」而非「碰巧没崩」的证据。
- **有可执行判据**：全量套件在 `f5c00fb8` 实测 2268/2/0；入场序列另有逐字节的字节锚。
- **实机回路可用**：改完能真连客户端验，本轮已往返多次。

边界也清楚：移动路径（`ListNotServed`）与槽位映射各自有独立的验收口径，已写进 Scope Out。

## Marginal Control Value

值得上 SDD，而且理由与上一件**不同**：

- **上一件的教训直接适用**：`f5c00fb8` 修好主背包的同时把装扮栏掐死了，因为它把一条
  **按容器**的规则当成了**按物品种类**的规则。这一类「规则的定义域搞错」的缺陷，
  判据全绿是发现不了的——本仓当时全量 2268 全绿。本轮 SC-3 要求对**其余容器**
  逐个钉住「永不带」，正是为了让定义域本身被判据看住。
- **本轮要改的记载里，有一句是上一件刚写下的修正案**（「那个追加块是旧客户端布局／是错的」）。
  它半对半错：内容对、条件错。**改一条修正案本身，是最容易把话说过头或说不足的地方**，
  需要独立评审看着。本仓已有两次先例：一次变化清单漏了 13 条新增拒绝；一次「零覆盖」的
  理由写成假话、整改时又换成另一句假话，都由独立评审拦下。
- **字节变化这次是有意的且分容器**：装扮栏变长 30（初版这里写的是 42，那是 A12 的形状，
  由契约修正案 C-1 更正）、主背包必须逐值不变。这两件必须**同时**
  成立，而字节锚只覆盖入场序列里出现的容器。需要一次完整变更评审去核「有没有别的容器
  被顺带改了」。

## Structural Selection

**Single Spec。** 三件事——按容器三分、字节锚重锚、记载更正——共享同一个验收口径：
「除装扮栏（与装备栏里的时装）之外逐值不变」。按本仓规矩，同一口径下的多段工作量属于一个成果。

不是 Multi Spec：没有第二个互斥的验收口径。移动路径与槽位映射确实各有独立口径
（前者必须改变可观察行为、后者需要先实机量全 0..11），但**都不在本轮范围**，
且槽位映射还被外部输入阻塞（要逐件拖拽量），不能现在建成子成果。

## Controller Selection

**选定：`sdd-lite` / Profile `code-bugfix`。**

### 真正在保护什么

两条可信失败路径，都不是「写错代码」而是「边界搞错」：

1. **规则的定义域**：上一件正是把按容器的规则当成按物品种类，判据全绿。本轮反过来做，
   同样的错法会以「某个容器被顺带带上了那 30 字节」的形式出现，而字节锚只覆盖入场序列
   出现的五个容器，覆盖不到增量帧可能携带的装备栏。
2. **改一条修正案**：`f5c00fb8` 那句已被证伪的话，改的时候既可能改得不够（读者仍以为
   追加块是错的），也可能改过头（说成「A12 一直是对的」，而 A12 在主背包确实是错的）。

挡住这两条的是**一份把验收边界钉死的持久 Spec**加**一次对完整结果的独立评审**——
Lite 恰好就是这两样：spec → implementation → review → verification。

### 为什么更重的 Standard 不对

Standard 的独有控制是 `plan.md`。本轮没有能挂上去的东西：规则三行已由客户端代码给定，
不存在需要提前解决的实施决策；生产改动集中在一个方法加两个调用点，没有跨层顺序依赖；
「文件多、条目多」按选择规则明确不构成理由。

### 为什么更轻的一档不对

比 Lite 更轻是不留持久 Spec、靠一次确定性检查收口。这里不行：本轮**没有**便宜的确定性
检查能替代验收边界——判据全绿正是上一件出事时的样子。能证伪的只有「拿掉规则就会红」的
变异验证与一次从代码出发的反向扫描，两者都要先有写下来的验收条款才能对着做。

### 为什么不是 Governed

Governed 的硬性门槛一条都不沾：不涉及安全、凭据、隐私、财务法务、不可逆外部变更、
或无恢复手段的数据丢失。最坏后果仍是客户端崩溃，可逆，改动全在本地未推送的任务分支上。
而「独立挑战」这一档控制在本仓已被证明对同一失败模式不是必需的——前两次遗漏都是被
**普通的完整变更评审**抓住的。
