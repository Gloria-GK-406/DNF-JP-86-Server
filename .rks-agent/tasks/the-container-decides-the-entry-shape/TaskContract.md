# TaskContract: 条目的形状由容器决定，不由物品种类决定

## Context

### Source Request

所有者原话（两句，隔了一次实机验证）：

> 别别别，我们先把时装栏问题解决掉。在装备栏能装备了，但是本身的业务场景和现实不符啊。
> 就算做出来又能咋办。还不如老老实实一点点啃时装栏崩溃的问题

> 恩，那我们继续推进好了。

前一句否掉了「让时装走装备栏」的绕行方案，理由是**业务模型不对**：真实模型是独立的装扮栏
加装扮槽。后一句是在装扮栏崩溃的根因被实机判定之后说的，指把那次实验落成正式修改。

### Current Situation

仓库 `E:/Project/DNF/DNF-JP-86-Server`，分支 `main`，HEAD `f5c00fb8`（上一个成果已合并）。
判据命令：`PVF_ARCHIVE_PATH=E:/Project/DNF/DNFClient-A21-protocol/Script.pvf dotnet test Server/86JP.Server.slnx --nologo`
基线（在 `f5c00fb8` 实测）：**2268 通过 / 2 跳过 / 0 失败**，退出码 0。
那 2 个跳过是 `A_missing_archive_*`，只在没有档案可达时才跑，跳过正是「档案确实加载了」的标志。
**跑判据前必须确认没有 `Dfo.Server.Host` 进程在跑**（它锁 `Dfo.Server.Protocol.dll`，构建以 MSB3027 失败）。

#### 上一个成果修对了一半，另一半修坏了

`f5c00fb8` 删掉了 `GameInventoryItemEntry.Write` 末尾那 42 字节追加块。那个块的**条件**是
`core.ItemKind == 8`——按**物品种类**判断。删掉它治好了主背包的
`STATUS_STACK_BUFFER_OVERRUN (0xC0000409)`（主背包按定长 101 跨步，多出的 42 字节会把
其后每条推到错误偏移），**但同时把装扮栏这条路彻底掐死**。

#### 客户端的真实规则（读自客户端原生代码，非虚拟化部分）

`0x01637740`（崩溃链上由 `0x0117D028` 调用）：

```
F(buf /*ebp+8*/, itemId /*ebp+0Ch*/, 选择子 /*ebp+10h*/):
    if (选择子 == 1) { 0x274FBE0(buf); return; }              // 装扮栏：每条都读
    if (选择子 == 3) { if (0x166EBC0(itemId)) 0x274FBE0(buf); return; }  // 装备栏：按物品判定
    return;                                                    // 其余容器：一概不读
```

`0x0274FBE0` 从流里读一个 u32 长度，再 `read_bytes(buf, len)`。
`read_bytes` 在 `0x027C5380`，**未被虚拟化**，逐条可读：

```
027c5383  mov eax,[ebp+8]      ; dst
027c5387  mov esi,[ebp+0Ch]    ; len ← 调用方传入
027c538b  mov edi,[03BAAE38]   ; src = 全局包读游标
027c5394  call 02c61c00        ; memcpy(dst, src, len)
027c5399  add edi,esi          ; 游标 += len
```

**所以正确规则是**：

| 容器 | 每条条目 |
|---|---|
| 装扮栏（`Avatar` = 1） | 101 字节 + 长度前缀数据，**每条都带** |
| 装备栏（`Equipment` = 3） | 101 字节，**只有时装那条带** |
| 其余（主背包 0、个人货柜 2、宠物 7、账号金库 12…） | 定长 101，**永不带** |

**A12 那 42 字节块的条件写错了地方**——它是「装备栏」那一格的规则，被当成了全局规则。
（初版这里还写着「内容一直是对的」。**那句已由 C-1 推翻并收回**：内容也不对，
A12 发 30 字节珠宝而 A21 只发 18，多出的 12 字节落在客户端相邻局部上而不报错。）

#### 判定它的实机证据

`dnf-gs-avatarbag.dmp` 里逐字节对上：装扮栏帧体在客户端工作缓冲的 `0b351022` 起，
`101` 字节记录结束于 `0b35108C`，而接收缓冲的 `'0'` 填充**起点正是** `0b35108C`；
全局包读游标 `[0x03BAAE38]` 停在 `0b351090` = 记录末尾 **+4**。即客户端在记录之后
又从流里读了一个 u32，读到 `0x30303030`（ASCII `"0000"`），随即以此为长度做 memcpy。

随后做了临时实验 **E1**（只对装扮栏追加那 42 字节），实机验证两轮：

| 装扮栏内容 | 结果 |
|---|---|
| 1 件时装 | 正常进入游戏，零异常 |
| **11 件时装（整套骑士时装，槽 0..10）** | **正常进入游戏，零异常** |

11 条连续记录全部对齐，是「形状正确」而不是「碰巧没崩」的证据：任一条的长度前缀块
形状有误，第 2 条起就会错位。

细节记在 `Document/avatar-container-entry-shape.md`。

#### 顺带查清、本轮要一并处置的两处记载

- **上游服务器侧把装扮栏的 `listParam16` 当作恒 0，并忽略它。** 上游参考服务器
  `ServerS4A21` 的 `InventoryService.InitDefaultListParams()` 写
  `_listParams[Avatar] = 0`；`ItemSlotBoundService.GetAvatarOpenRange(int avatarListParam16)`
  **收下参数直接丢掉**，恒返回 `ItemSlotRange(0, 209)`——上游服务器侧固定认 **210 格**，
  上游全仓没有任何装扮栏扩容概念。本仓 `GetDefaultParameter` 返回 0，**与上游一致**。
  （**这只说的是上游服务器侧。客户端侧不同**：实机对照已把「客户端不读这个字段」**排除**
  ——见 C-2。初版这里的加粗领起句写的是「恒为 0，**且客户端忽略它**」，后半已被推翻并收回。）
- **`protocol/game/server-to-client/NOTI-0x000D.md` 里「`listParam16` 是容量」不准。**
  上游对主背包写的 24 是 `ItemSlotBoundService.MainExpandStageFull`，是**扩容阶段键**
  （0/8/16/24），真正槽位区间是 9..64 / 65..120 / 121..176 / 177..232 / 233..288。
  该字段含义逐容器不同：个人货柜=容量、账号金库=SelectionKey、宠物=条目数、装扮栏=恒 0。

## Goal

让条目的形状由**容器**决定而不是由**物品种类**决定，使装扮栏重新可用，同时不让主背包
退回到 `0xC0000409`；并把上一个成果留下的、现在已知说过头的那几处记载改到与证据一致。

## Scope

### In

- `GameInventoryItemEntry.Write` 按**容器**决定是否追加长度前缀数据，规则同上表三行。
- 追加内容为 A21 的形状：`u32(18) + 18 字节珠宝槽（存储 30 字节里的前 18）`、
  `u32(4) + u16 Color1 + u16 Color2`，共 30 字节。见 C-1。
- 两个调用方把容器类型传进来：`InventoryDeltaMessage`（自带 `ContainerType`）与
  `StateSynchronizationPayloadCodec.Inventory`（自带 `containerType`）。
- 判据：三行规则各有判据；「拿掉规则就会红」的变异验证；装扮栏多条条目连续对齐的判据。
- 字节锚：装扮栏那一帧会变长，按规矩**逐帧指名、解释、给出新值**。
- 记载：`GameInventoryItemEntry` 的注释、`EntryWriterAvatarShapeTests` 的说明、
  `protocol/game/server-to-client/NOTI-0x000D.md`，改到与本轮证据一致。
  **其中 `f5c00fb8` 写下的「那个追加块是旧客户端布局／是错的」本身已被证伪，
  必须补记修正案而不是悄悄改掉。**
- `NOTI-0x000D.md` 里 `listParam16` 的含义按上游更正，写明上游服务器侧固定认 210 格；
  客户端侧的实际表现按实测如实记，不得替客户端下断言。见 C-2。

### Out

- **装扮栏的移动路径**：从装扮栏拖出目前被拒为 `ListNotServed`，实机已观测。是真缺口，
  但它属于 `MoveItemSpace` 而不是条目编码，单独一件。
- **时装槽位映射**：客户端认为上衣 `413500000` 该进 3 号槽（主背包拖拽日志
  `item 413500000 6->3 refused as NotWearable`，装扮栏拖拽 `0->3`）。补
  `PvfEquipmentSlots.ByName` 的时装键需要先把 0..11 量全，单独一件。
- **`0x0274FBE0` 去虚拟化**：它是 VMProtect 虚拟化的，但本轮不需要——字节流已经把它的
  行为说清楚了。若日后要知道「到底几段长度前缀块、长度有没有上界」，那是另一件。
- **上游那套槽位区间（9..64 等）搬进本仓**：本轮只更正记载，不改本仓的槽位判定。

## Constraints

- 唯一被授权的字节变化是：**装扮栏容器的条目重新带上那 30 字节外观块**，以及装备栏容器里
  时装条目带上同样的 30 字节。**主背包与其余容器的字节必须逐值不变。**
- 字节锚 `SelectCharacterAcceptedTranscriptTests`：不含装扮栏的帧必须与 `f5c00fb8` 逐字节相同；
  会变的帧要指名是哪一帧、为什么变、变成什么，并证明变化量恰好等于被授权的那 30 字节。
- 既有判据的期望值与断言**不得为迁就实现而改写**；正对应上述授权变化者除外，
  且每处改写要单独说明它对应哪一条。
- 不新增协议帧。
- `CommandHandlerArchitectureTests` / `NotificationHandlerArchitectureTests` 必须继续通过，
  判定谓词与具名豁免清单不得放宽或扩充。
- `TreatWarningsAsErrors` 开启，CS9113 是错误。
- 分层：Data → Abstractions → Application → {Infrastructure, Persistence, Networking} → Protocol → Host。
- 切片架构（`AGENTS.md`）：`Protocol/<Endpoint>/<Protocol>/` 一个目录，切片内不跨协议引用。
- 每个任务单元结束时判据必须全绿，不允许攒红。
- **不得触碰主检出的 `ClientHack/` 与 `.worktrees/client-debug-lab`**（另一个 agent 在做）。
- **禁止任何 git 还原类命令**（`git checkout --` / `git restore` / `git stash`）。
  变异核实用文件级备份 + `sha256sum`，每次用完立刻还原并核散列。
- 记载不得写成比证据强：「静态反汇编」「上游源码读出」「实机观测」要分别标明。

## Success Conditions

- **SC-1** 装扮栏容器的每一条条目都带那 30 字节外观块；判据钉住，拿掉会红。
- **SC-2** 装备栏容器只有 `ItemKind == 8` 的条目带；判据钉住两侧（带与不带）。
- **SC-3** 其余容器（至少覆盖主背包 0、个人货柜 2、宠物 7、账号金库 12）**永不带**，
  条目恒 101 字节；判据钉住，拿掉会红。
- **SC-4** 装扮栏里多条条目（至少 3 条）在一个帧内连续排布，且第 2 条起的起点等于
  前一条的起点加上「101 + 该条实际追加长度」——即证明形状对齐，而不是只证明总长。
- **SC-5** 字节锚：不含装扮栏的帧与 `f5c00fb8` 逐字节相同；会变的帧被逐帧指名，
  且变化量被证明恰好等于被授权的 30 字节。
- **SC-6** 全量判据不低于基线 2268，退出码 0。
- **SC-7** 三处记载与本轮证据一致；`f5c00fb8` 里「那个追加块是旧客户端布局／是错的」
  这句有指名它的修正案，说明它错在哪、正确规则是什么、证据是什么。
- **SC-8** `NOTI-0x000D.md` 里 `listParam16` 的含义按上游更正，写明上游服务器侧固定认 210 格、
  上游发 0；**客户端侧是否读该字段，按实测记，不得照抄上游的行为替客户端下结论**。见 C-2。
- **SC-9** 交回一份变化清单，**正向与反向都报**。本仓已有两次教训：一次漏了 13 条新增拒绝；
  一次把「零覆盖」的理由写成假话又在整改时换成另一句假话。**凡计数、长度、索引类字段，
  除核偏移外必须核上游能写进多大、下游能吃下多大。**

## Assumptions

- 客户端规则读自 `0x01637740` 的原生反汇编（**非虚拟化**，可逐条复核）；
  `0x0274FBE0` 是虚拟化的，其行为由字节流与两次实机实验判定，**不是**从指令读出的。
- 追加内容的形状（`u32(18)+18`、`u32(4)+4`）读自上游 A21 的 `A21AvatarJewelBytes = 18`。
  **实机验证的是形状机制而不是这个长度**：块自带长度，发 30 也对齐、也不崩，
  而实机那 11 件时装珠宝槽全为零，18 个零与 30 个零无从分辨。
  「客户端是否正确解释了这些字节的语义」（珠宝、颜色是否真的渲染出来）同样**未验证**。
- 上游 `ServerS4A21` 是参考实现，不是本仓的规范；引用它的地方要标明是「上游读出」。

## Contract Amendment C-1（implementation 阶段，2026-09-07）

**追加块是 30 字节而不是 42，条目是 131 而不是 143。** revision 1 的 RQ-004、SC-1 与
Scope In 都写的是「`u32(30) + 30 字节 JewelSocket`……共 42 字节」，那是**A12 的形状**。

发现经过：实现时去上游 `ServerS4A21` 核 `GetUpdateEntrySize`，读到

```
Entry84Size         = 84
A21CommonEntryExtra = 17      → 普通条目 101
A21AvatarJewelBytes = 18      ← 不是 30
A21AvatarEntrySize  = 84 + 17 + 4 + 18 + 4 + 4 = 131
```

`ItemListProtocolWriter.WriteAvatarEntry126` 里 `WriteFixedBytes(…, JewelSocket, 18)`
从**存储的 30 字节里截前 18** 发出。存储侧上游与本仓一样是 30
（`jewel_socket BLOB NOT NULL CHECK(length = 30)`）。珠宝槽的结构是
`SocketCount = 5, EntrySize = 6, Size = 30`——**A21 只发前 3 个孔**。
那个函数名里的 `126` 正是 A12 的总长（84 + 4 + 30 + 4 + 4），佐证 30 是旧形状。

**为什么实机没能发现**：块是自描述的（先读 u32 长度再读那么多字节），所以发 30 也对齐、
也不崩；而实机那 11 件时装的珠宝槽全为零，18 个零与 30 个零在屏幕上没有差别。
**所以「11 件全过」证明的是形状机制成立，不是这个长度正确。**

**为什么仍然要改成 18**：另一个 agent 量到客户端接收这段数据的目标缓冲是
`[ebp-0x58]`，只有约 28 字节被清零。多发的 12 字节落在相邻局部上而不会报错——
不崩不等于没踩坏。

受影响的条款按此更正：RQ-004、SC-1、**Scope In 的追加内容那条、Constraints 第一条的两处、
Constraints 中字节锚那条、SC-5、Assumptions 的形状那条**，一律改为 A21 的形状；
字节锚的预期由「变长 42、回到 163」改为「变长 30、成为 151」，**已实测确认**：
62 帧中恰好第 18 帧变化，`121 → 151`。

### C-1 的补充（review 阶段，2026-09-07）

第四次就在第三次的补充文字**上面十行**，而那段补充刚刚诊断过这个错法。
第五次发生在**为第四次写诊断的同一轮**里：那次诊断自称已经「按说法重搜了全部六份产物」，
而那句话对**数字**不成立——搜索集里根本没有 `routing-decision.md`。

**补救物在哪**：本轮实际用的搜索集与搜法，写在 `behavior-change-list.md` 的「扫法」一节。
下一个人要复用或扩充，改那里。

**共同的错法有三层**，前两层答「搜什么」，第三层答「在哪里搜、搜哪些说法」：

1. 改一个数时只顺着「它是从哪条推出来的」往下找，**没有反过来搜这个数还出现在哪些地方**；
2. **搜的是「数字」而不是「被推翻的那个说法」**。同一件事可以写成 `42`、写成 `143`、
   写成 `u32(30) + 30 字节`、也可以写成一句「内容一直是对的」的结论。按 token 搜只抓得到前两种；
3. **搜索集本身没被检查**——两件事各漏一头：
   - **漏了文件**：历轮的扫描口径分别是「契约里现存的 42」与「`Server/` 下的 143/42」，
     两个都不含 `routing-decision.md`，于是它第 31 行「装扮栏变长 42」一路活到第五轮（评审 R-5）。
     **这不是本轮才有的做法**：上一件成果的变化清单用的是一模一样的数字口径，

## Contract Amendment C-2（review 阶段，2026-09-07，经所有者同意）

**「`listParam16` 被客户端忽略」这句被本轮实测否掉了，契约三处照抄它的地方一并更正。**

revision 1 的三处——「上游默认值」那条的加粗领起句、Scope In、SC-8——都写着「装扮栏固定 210 格、`listParam16` 恒 0

**后半不成立**：那是把**上游服务器**的行为当成了**客户端**的行为。

实机对照（所有者观测，控制条件已从库备份复核：两次都是装扮栏 11 件时装、同一服务器构建、
同一客户端，之间只重启服务器并改 `listParam16` 一个值）：

|---:|---|
| `483` | 装扮栏显示为**已全部扩容** |
| `0` | 正常 7 列，**并出现「需要扩容」的标志** |

所以**「客户端不看这个字段」已被观测排除**。交付物（`NOTI-0x000D.md`）是照实测写的，
**有意没照 SC-8 的字面**；本修正案把契约改到与交付物、与证据一致，而不是反过来。

**初版为什么会写错**：证据只来自上游源码，而上游是**服务器**实现；写的时候没有意识到
「上游服务器忽略这个字段」与「客户端忽略这个字段」是两件事，把前者的结论安到了后者头上。
这与 C-1 同属「证据没被检查」这一类，**但要跑的检查不是同一个，不能并成一句口号**：

| | 该问的问题 | 本轮的实例 |

只学会问分辨力的人，照样会把服务器的结论安到客户端头上。
