# Specification: 条目的形状由容器决定，不由物品种类决定

## Why and Outcome

客户端读物品条目时，**先看容器再决定读法**。`GameInventoryItemEntry.Write` 今天不看容器，
于是两种错法各出现过一次：

- `f5c00fb8` 之前：按 `ItemKind == 8` 追加 42 字节 → 主背包里的时装把其后每条推出定长 101
  跨步 → `STATUS_STACK_BUFFER_OVERRUN (0xC0000409)`；
- `f5c00fb8` 之后：一律不追加 → 装扮栏条目短了那一段，客户端读完记录继续读 4 字节当长度，
  读到接收缓冲的 `'0'` 填充 `0x30303030` → 野长度 memcpy → `0xC0000005`。

**两次都是同一个缺陷：规则的定义域搞错了。** 消费者（客户端）需要的结果是：
**同一条物品，放在不同容器里，写出的字节不同；而这个不同由容器决定。**

## Scope

### 覆盖

`GameInventoryItemEntry.Write` 写出的字节、它的两个调用方、相应判据与记载。

### 不覆盖（各有原因）

- 装扮栏的移动路径（`ListNotServed`）——属 `MoveItemSpace`，独立验收口径。
- 时装槽位映射——需先实机量全 0..11。
- `0x0274FBE0` 去虚拟化——本轮不需要，字节流已足够。
- 把上游的槽位区间搬进本仓——本轮只更正记载。

## 权威来源与它们各自的强度

| 事实 | 来源 | 强度 |
|---|---|---|
| 三行分支规则（选择子 1 / 3 / 其余） | `0x01637740` 原生反汇编，**未虚拟化** | 已核实，可逐条复核 |
| `read_bytes(dst,len)` 从全局游标 `[0x03BAAE38]` 拷 len 字节 | `0x027C5380` 原生反汇编 | 已核实 |
| 长度由 `0x0274FBE0` 从流里读一个 u32 得到 | 该函数**是 VMProtect 虚拟化的**；由转储字节流与两次实机实验判定 | **推定，非指令读出** |
| 追加内容的形状 `u32(18)+18`、`u32(4)+4` | 上游 A21 `A21AvatarJewelBytes = 18` | 上游读出。**实机验证的是形状机制，不是这个长度**——块自带长度，30 也对齐；字节语义未验证 |
| 装扮栏固定 210 格、`listParam16` 恒 0 | 上游 `ServerS4A21` 源码读出 | 上游读出，**上游是参考实现不是规范** |

**一处要点明的边界**：上游 `GetAvatarOpenRange` 忽略参数、全仓无装扮栏扩容概念，
这只说明**那个参考实现没做**。实机上客户端 UI **显示了扩容标志**（所有者观测），
所以不得据此写成「装扮栏不能扩容」。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 装扮栏容器（`Avatar`）的**每一条**条目，在定长 101 字节之后追加那段长度前缀数据。 |
| RQ-002 | 装备栏容器（`Equipment`）的条目，**当且仅当** `ItemKind == 8` 时追加同样一段。 |
| RQ-003 | 其余任何容器的条目**一律不追加**，恒 101 字节——包括其中的时装。 |
| RQ-004 | 追加内容为 `u32(18) + 18 字节珠宝槽（存储 30 字节里的前 18）` 加 `u32(4) + u16 Color1 + u16 Color2`，共 30 字节。见下方修正案。 |
| RQ-005 | 容器类型由调用方传入，不由 `Write` 猜；两个调用方各自已经持有它。 |
| RQ-006 | 非时装物品若落在会追加的容器里，仍要写出一段合法的 30 字节（它没有时装数据，写零）。 |
| RQ-007 | 除 RQ-001/RQ-002 命中的条目外，任何物品的任何字节不变。 |
| RQ-008 | 记载与本轮证据一致；`f5c00fb8` 写下的「那个追加块是旧客户端布局／是错的」有指名它的修正案。 |
| RQ-009 | `listParam16` 的含义按上游更正，并写明装扮栏固定 210 格、以及上一节那处边界。 |
| RQ-010 | 交回变化清单，正向与反向都报。 |

### RQ-003 为什么单独立一条，而不是「RQ-001/002 的补集」

因为**上一次的缺陷正是补集写错**。把「不追加」写成一条要被判据钉住的正面要求，
才能让「某个容器被顺带带上了那 30 字节」这件事有用例会红。字节锚只覆盖入场序列里出现的
五个容器，覆盖不到增量帧可能携带的装备栏，所以不能指望它兜底。

### RQ-006 为什么需要

装扮栏里理论上可以出现非时装物品（本轮实机就往里放过一件普通堆叠物）。客户端对
选择子 1 是**无条件**读那段数据的，所以即使物品没有时装明细也必须写满 30 字节。
`AvatarDetail` 为空时写零。

### AC-007 的预判

字节锚 `SelectCharacterAcceptedTranscriptTests` 的 fixture 里有一个装扮栏容器
（`SelectCharacterPayloadTestData.Create()` 建的），含 1 条条目。所以预期**恰好一帧变化**。

#### 修正案（implementation 阶段）：变化量是 30 不是 42，新长度是 151 不是 163

初版这里写「变长 42 字节，本轮应回到 163」。**那是错的**，理由与契约 C-1 同：
上游 A21 的珠宝槽线上长度是 **18** 而非 30，追加块 30 字节，条目 131。

**这条预判错得有教育意义**：初版写它时，我刚看到本轮实测的新哈希**恰好等于
`f5c00fb8` 之前的原值**，于是把「回到原值」当成了「回到正确值」。
原值是 A12 的形状——**能解析、能显示、不崩，但内容不对 A21**。
自描述的长度前缀让错误的长度也能对齐，所以「哈希回到从前」在这里不是正确性的证据。

实测结果：62 帧中恰好第 18 帧变化，`121 → 151`，差 30。

**本修正案初版只改了 RQ-004 与本条，漏了 RQ-006、AC-002、AC-005 三处**——它们仍写着
A12 的 42/143，按字面读会与判据直接冲突。由独立评审发现，已一并更正。
漏改的原因值得记：改一个数时只顺着「它是从哪条推出来的」往下找，
**没有反过来搜这个数还出现在哪些地方**。

## Assumptions

- 「客户端是否正确解释了那 30 字节的语义」（珠宝与颜色是否真的渲染）**未验证**。
  本轮只证明了字节流对齐、客户端不崩、装扮栏能显示条目。
- 装备栏（选择子 3）在本仓是否真有路径走到这个编码器**尚未确认**：入场快照只送
  Main/Avatar/PersonalCargo/Pet/AccountCargo；增量帧的容器类型来自提交结果，可能是装备栏。
  实现按客户端规则做，但若确认无路径可达，要在记载里说明这条规则今天是**空转**的。
