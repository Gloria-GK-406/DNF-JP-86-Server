# Diagnosis: 远端拾取动作与权威地面物投影

## 复现事实

- 双客户端同一地下城内可见、可移动；一端拾取后双方地面物都会消失，且拾取者正常入包。
- 两端 `clienthack-udp-trace.log` 在该会话中持续记录 5063 与 59410 之间的双向 `sendto/recvfrom`，说明 P2P 直连并未因拾取断开。
- 当前 `GetItemHandler` 在 CMD 成功后向拾取者发送 ACK + NOTI 0x0027，并在 Handler 内枚举冻结会话、向其他参与者发送同一 NOTI；观察者能删除地面物，证明该通知已送达且字段足以解析目标地面物。

## A21 客户端证据

- NOTI 0x0027 handler 位于 VA `0x01185970`。它读取地面编号、第一拾取者 ID 和类型旗标，并查找地面对象。
- 本地身份分支从 `0x01185BBC` 开始执行入包/UI 工作；观察者跳到 `0x01185D76`，不执行该本地分支。
- 对物品记录，handler 在 `0x01186002` 用第二个 actor/user ID 调用 `0x019E2EF0` 查队伍成员，然后将地面对象与成员对象传给 `0x0165E4C0`。该函数只是 `0x0165DA20` 的参数包装；现有调用将角色动作参数置零，控制流中没有让远端 avatar 执行拾取动作的调用。
- 因此 0x0027 的观察者职责是“谁拿走了哪个地面物”的场景状态处理，不是角色动作复制。给观察者补发 CMD ACK 没有客户端请求与 reply handler 对应，既无证据也有破坏命令序列的风险。

## 根因

现象不是服务端漏发一条可用于播放动作的 0x0027 变体。权威地面物投影已经工作，而角色动作属于客户端 P2P 表现层；A21 现有服务端协议没有可证实的第二条动作通知。服务端真正的结构性缺陷是拾取成功的共享事实与接收者枚举仍由协议 Handler 直接拼装，和 DungeonRun 实例形成两个真源。

## 修复边界

- 不修改 UDP/P2P，不伪造远端动作，不向观察者发送无请求 CMD ACK。
- 在 DungeonRun 中提交一次带 revision、拾取者、地面编号、结果种类和语义接收者的运行期变更。
- 协议投影组件根据当前有效冻结会话生成：拾取者 ACK/入包或金币状态，观察者只收 0x0027 场景状态。
- Handler 不再自行枚举其他参与者。

## 回归目标

1. 普通地面物、怪物掉落和金币各自只提交一次共享拾取变更。
2. 重复请求、背包拒绝和持久化异常不发布成功变更。
3. 拾取者获得一次奖励；观察者只收到现有 0x0027，且双方地面物状态一致。
4. 已离场、replacement connection、其他 Run 不接收旧变更。
5. 既有 0x0027 编码保持不变，UDP/P2P 代码无改动。
