# Specification: 响应式拾取投影

## Why and Outcome

双客户端已经共享同一个地下城地面状态，但观察者只看到物品消失，没有角色拾取动作。A21 接收端静态控制流证明 0x0027 的观察者分支负责按队伍成员关联地面物，并不触发角色动作；动作属于客户端 P2P 表现层。交付结果是一条由共享 DungeonRun 提交、带拾取者语义和接收者集合的运行期变更；协议投影只输出 A21 所需的权威地面物消息，保持奖励只属于拾取者且不另造动作真源。

## Scope

包含普通房间地面物、怪物掉落和金币拾取的共享变更、逐接收者投影、重复/失败保护与旧会话过滤。角色走动和攻击的 UDP/P2P 流、任务物品、任务进度、Boss 清关、结算和翻牌不在本 Spec 内。

## Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 一次成功拾取必须在共享 DungeonRun 中只提交一个不可重复的运行期变更，包含稳定 RunId、递增 revision、拾取者角色、地面编号、拾取结果种类和当前语义接收者。 |
| RQ-002 | 领域变更不得保存连接、Session 或 wire-only 身份；协议投影必须从当前有效的冻结参与者映射中解析接收连接，并拒绝 replacement connection、已离场参与者和其他 Run。 |
| RQ-003 | 拾取者投影必须保留现有 CMD 应答、入包或金币更新；其他参与者只能收到场景移除与远端拾取表现所需的通知，不能获得物品、金币或背包更新。 |
| RQ-004 | 观察者投影中的拾取者身份和消息形态必须由 A21 客户端接收端证据支持；0x0027 只承担地面物状态，服务端不得通过修改正常 P2P 移动或发送无请求 CMD 应答来伪造角色动作。 |
| RQ-005 | 只有背包/金币结算和共享地面占用都成功后才能发布成功变更；重复、无效或结算失败的请求不得发布成功变更或重复奖励。 |
| RQ-006 | Handler 只负责验证、调用 CMD 和触发变更投影；接收者语义由 DungeonRun 变更表达，旧的 Handler 内多目标目录查询/扇出路径不得继续成为本功能第二真源。 |

## Acceptance Criteria

| ID | Covers | Criterion |
|---|---|---|
| AC-001 | RQ-001, RQ-005 | Given 两名参与者共享一个 Run 和一个可拾取地面编号，When 任一参与者拾取，Then 实例只产生一个 revision 更高的成功变更；再次请求返回拒绝且没有第二个成功变更或奖励。 |
| AC-002 | RQ-002, RQ-003 | Given 拾取时两名参与者仍附着有效连接，When 投影该变更，Then 拾取者收到自身应答和库存/金币结果，观察者只收到场景/表现通知；已替换或已离场连接不在目标内。 |
| AC-003 | RQ-003, RQ-005 | 对普通物品、怪物掉落和金币分别验证：双方地面状态一致，奖励仅落到拾取者一次，其他参与者的持有量不变。 |
| AC-004 | RQ-004 | 诊断证据明确给出 A21 0x0027 观察者分支只关联成员与地面物、没有角色动作调用；对应 codec/消息测试钉住现有字段，且实现未改动 UDP/P2P 移动路径。 |
| AC-005 | RQ-006 | 完整差异中本拾取 Handler 不再自己枚举其他参与者并构造多目标发送；实例变更和投影组件成为唯一成功通知路径。 |
| AC-006 | RQ-001-RQ-006 | 受影响 Application 与 Protocol 定向测试以及 Release 构建通过，无新增警告。 |
