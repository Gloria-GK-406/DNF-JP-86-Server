# TaskContract: 翻牌一定给金币，且金额随副本与难度浮动

## Context

### Source Request

「不是不是，这里的逻辑是金币一定有的，而且是有一定波动。这相当于一个底薪。免费牌一定会给金币。
不过给多少就不太清楚了。」

以及收尾时的授权：「然后合并分支，清理工作区。结束后再出一个工作区把金币这个问题解决一下。」

### Current Situation

前一个 Spec（`one-reward-behind-four-faces`，已封 `completed`，进入 `main` 的 `927e2d0e`）把翻牌的
协议编码层修对了：牌面在真实客户端上显示得出来。但金币那一格仍是两处错的：

1. **只在牌里有装备时才给**（`SelectCardCommand`：`claimed.Item is null ? 0 : ClearRewardCardGold`），
   所以第 0 位摇空的那些局，玩家翻开一张牌**一点反馈都没有**。
2. **金额是本服务器自定的常量 1**（`GameProtocol.ClearRewardCardGold`），没有出处也没有浮动。

使用者明确：**免费牌的金币是「底薪」，一定给，且有波动。**

前一个 Spec 的记录里写着「档案说翻牌不出金币」——**这一条是错的**，本任务要推翻它。档案里有料：

| 出处 | 内容 |
|---|---|
| `etc/itemdropinfo_common.etc` `[gold drop ref table]` | 三个一组：**等级 / 金币基数 / 波动百分比**。等级 1 是 `17 13`，等级 5 是 `44 13`，等级 86 是 `1357 9`；**第三列是分段的**——1–64 为 `13`，65–77 为 `11`，78–200 为 `9` |
| `etc/itemdropinfo_clearreward.etc` `[dungeon difficulty gold drop bonusrate]` | `1.02 1.38 1.6 1.9 2`，五个难度各一个金币倍率，与已在使用的 `[dungeon difficulty drop bonusrate]` 同一组难度 |

本仓现状：前者**已在读但第三列被丢弃**（`PvfDropRateTableSource` 只取前两列）；后者**没读**，
而 `PvfClearRewardRateSource` 里已有常量 `DifficultyGoldBonusRate` 和一段说明，写着「本仓金币是
自定的固定值，所以这个倍率没有可乘的东西」——那段说明随本任务改写。

## Goal

让免费牌**一定**付出一笔金币，金额由档案决定：按副本的基准等级取基数、按本局难度乘倍率、
再按该等级声明的百分比上下浮动。金额在结算时随牌面一并定下，此后不变。

## Scope

### In

- 补读 `[gold drop ref table]` 的第三列（波动百分比）。
- 新读 `[dungeon difficulty gold drop bonusrate]`，并改写那段「无可乘之物」的说明。
- 规则层新增「一张免费牌付多少金币」的规则：吃事实（副本基准等级、难度）与显式种子，产出金额。
- 金额随牌面一并在结算时定下并保持不变（重复询问、断线重来给同一个数）。
- 结算通知的条目 0 写这个金额，取代常量 1。
- 翻牌**一律**入账这笔金币，不再以「牌里有没有装备」为条件。
- 退役 `GameProtocol.ClearRewardCardGold`，或把它降为再也没有人读的历史记录。

### Out

- **不采用参照服务端 `GenerateFreeGoldCard` 的其余因子**：加权击杀数、`(1 + 评级加成)`、
  队伍人数除法、以及那个 `175/1000` 系数。理由见 Constraints。
- 不新增按局的击杀计数（本仓目前完全没有，属另一件事）。
- 不改出货概率、品级带、副本定价、掉落池选取等既有规则层取值。
- 不改协议编码的结构（前一个 Spec 刚定下，条目 0 的**位置**不动，只改它的**值**）。
- 不实现付费（黄金）牌与黑砖牌的金币。

## Constraints

- **每一个进入公式的因子都必须有档案出处。** 参照服务端的 `baseGold = monsterGold * 175 / 1000`
  在它自己的代码里出现两次、没有任何出处注释，档案里也找不到 `175`。本仓已因抄参照服务端的
  无出处常数吃过亏（稀有度分母写死一百万，使两档永远摇不到）。**不抄。**
- 金额必须**恒大于零**：使用者定的「底薪」语义，空牌也要付。
- 金额必须在结算时定下，与牌面同一次决定、同一个种子，不得在翻牌那一刻再摇。
- 判据的断言对象是**规则层产出的数值**与**按客户端读法解码后的帧**，不是编码动作。
  这是上一个 Spec 用血换来的约束，继续生效。
- 分层不变式不变：规则输入只经规则服务进入服务器；规则服务不读世界状态。

## Revision 2 修正的两处（2026-09-03，独立评审查出）

- **第三列不是常数。** revision 1 写的「全档案都是 13」是错的，实际分三段。按一个数读，
  低等级的每一次核对都会通过，而每一个终局等级都是错的。已改正，并由判据钉住三段与两个分界。
- **这笔金币是免费牌的。** revision 1 没说这一条，实现一度让付费（黄金）牌也拿到同一笔 ——
  玩家已经按档案的价钱买过那张牌，再给一次底薪是本服务器凭空多发一份奖励。范围收紧为只给免费牌。

## Assumptions

- **公式的形状是本服务器定的。** 档案给出三个数（基数、难度倍率、波动百分比），但没有任何一处
  说明它们如何相乘。参照服务端把它们乘在一起再叠上四个没有出处的因子；本仓只取有出处的三个。
  这一点在规则所在之处具名，供日后被更好的证据推翻。
- 副本的基准等级沿用前一个 Spec 已确立的读法（`[basis level]`，副本 144 为 5），不重新论证。
- 使用者说的「波动」按档案第三列读作**上下各该百分比**，依据是参照服务端把该列取名
  `variancePercent` 并正是这样用的。这是本任务对该列唯一采信参照服务端的地方，且它有档案位置
  可核对（三列结构与每一段的取值本身都来自档案）。
