# Spec Result — 翻牌一定给金币，且金额随副本与难度浮动

## 结局

`completed`。独立评审四轮，第四轮 `approved`；验证 `pass`（九条成功条件全部有当前证据，
其中实机那条由使用者取得）。

## 交付了什么

免费牌现在**一定**付出一笔金币，金额由档案决定：

```text
金币 = [gold drop ref table] 副本基准等级的基数
     × [dungeon difficulty gold drop bonusrate] 本局难度的倍率
     再按 [gold drop ref table] 该等级那一段声明的百分比上下浮动
```

金额与牌面在同一次结算里定下、用各自的生成器，所以重复询问与断线重来给同一个数，
而加进金币没有挪动任何一张牌面的抽取。

两处行为改了：

- **一律入账**，不再以「牌里有没有装备」为条件。摇空的那些局，玩家翻开一张牌不再一无所获。
- **金额随局变化**，不再是本服务器自定的常量 1。占位常量 `GameProtocol.ClearRewardCardGold`
  已退役，全仓无引用。

**底薪是免费牌的。**付费（黄金）牌不拿它 —— 玩家已经按档案的价钱买过那张牌，再给一次
等于凭空多发一份奖励。这一条是实现过程中发现并收紧的，契约 revision 2 记下了原因。

## 推翻了前一个 Spec 的一条记录

`one-reward-behind-four-faces` 的结果里写着「档案说翻牌不出金币」。**那是错的。**

`PvfClearRewardRateSource` 里原本还有一段说明写着「本仓金币是自定的固定值，所以这个倍率没有
可乘的东西」—— 那段话随本次改写。

## 这一轮真正的成本在判据，不在实现

前三轮评审各裁 `changes_required`，**每一轮都查出真实的空过判据 —— 在变异下照样绿**：

| 轮次 | 查出的 | 根因 |
|---|---|---|
| 一 | 结算金币不进帧；基数按角色等级取；第三列写死 13 | 第一条整段无判据；后两条是 fixture 把两个值写成了同一个 |
| 二 | 难度倍率永远取第 0 档 | fixture 的两档难度同为 `1.5` |
| 三 | 帧写错牌种；付费牌拿免费底薪 | 全仓六张手写牌面一律 `FaceGold = 37` |

**四条是同一个形状**：一个取错下标或取错维度的查表，产出的仍是「随局变化的正数」，
屏幕上、日志里、判据里三处都看不出来。逐个猜嫌疑点抓不完；第四轮把变更集触及的查表维度
列成 21 项清册、逐维度变异，18 条里 15 条必红，才收敛到 `approved`。

**给后来者的一条**：一个 fixture 把两个本该可区分的东西写成同一个值，就等于把那一维的判据
删掉了，而且删得不留痕迹。

## 中途改正的两处事实

- **第三列不是常数。**契约 revision 1 与源码注释都写着「全档案都是 13」。实际是分段的：
  1–64 为 `13`，65–77 为 `11`，78–200 为 `9`。按一个数读，低等级的每一次核对都会通过，
  而每一个终局等级都是错的。已改正并由判据钉住三段与两个分界。
- **付费牌不该拿这笔金币**（见上）。

## 未查明与具名假设

- **三个因子如何相乘是本服务器定的。**档案给出三个数，没有一处说明它们的算法。
  参照服务端把它们相乘后还叠了四个没有出处的因子 —— 加权击杀数、`(1 + 评级加成)`、
  队伍人数除法，以及一个 `175/1000` 的比例。**那个比例在它自己的源码里出现两次、零注释，
  档案里也查不到 `175`。**本仓已因抄它的无出处常数吃过亏（稀有度分母写死一百万，
  使两档永远摇不到），所以一个都没取。这一点在 `ClearRewardRules.CardGoldOf` 处具名。
- 第三列读作「上下各该百分比」，依据是参照服务端把该列取名 `variancePercent` 并正是这样用的。
  这是本任务对该列唯一采信参照服务端的地方，且三列结构与每段取值本身都来自档案、可核对。
