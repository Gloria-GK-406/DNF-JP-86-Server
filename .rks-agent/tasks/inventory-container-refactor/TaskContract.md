# TaskContract: 道具容器抽象与使用效果分离

## Context

### Source Request

用户在一段设计对话后授权：

> 写multispec吧，把第二刀也记录一下。这样省的后面上下文多了，到时候忘了第二刀干啥。这样我们就能用两个subspec来完成这个任务了。

此前已确立采用 SDD 的理由：

> 这个任务还是蛮复杂的，值得我们用sdd来跑。当然只是为了实现别漂移。

### Current Situation

背包目前没有抽象层。`MoveItemSpaceHandler` 与 `UseStackableHandler` 直接调用
`IEntryInventoryMutationRepository`，也就是直接绑死在 SQLite 上。这条路刚建立
（`db22416`、`0af6e0b`），只有两个调用点，改动成本仍然很低。

参考实现走了没有抽象层的那条路，代价是可测量的：背包模块 35,647 行；快捷栏区间
`(3, 8)` 在四个文件里各自声明一次；`lock (SyncRoot)` 有 283 处、散布在 104 个文件里，
而持有可变状态的 `InventoryService` 自身零加锁、`SetItem`/`RemoveItem` 公开；死亡之塔
因为存储层换不掉，另写了一个 857 行、17 个公开方法的 `DeathTowerTransientInventoryService`，
把移动与使用逻辑整份复制了一遍。

道具使用本身也还是半成品。当前实现对主背包里任何非装备物品一律扣减 1，而归档中有
84 个 `[stackable type]` 以 `unlimited` 开头的道具本不应被扣减——对它们而言这是销毁。
归档声明的冷却（6,254 个道具有 `[cool time]`，其中 1,702 个还声明了共享用的
`[cooltime group]`）完全没有实现。

本任务承载两个各自独立可验收的成果：先建立容器抽象且不改变任何外部行为，
再在其上把使用拆成只读判定与状态变更两部分。

## Goal

把道具存储从「协议处理器直接读写持久化仓储」改为「可替换的容器 + 角色对容器的绑定」，
并在其上把道具使用分离为只读的可用性判定与承载全部状态变更的效果两部分，
使副本临时背包、多容器切换等后续需求只需提供新的容器实现，而不必复制既有规则。

## Scope

### In

- 容器抽象：自报身份、容器类型、客户端可见的形状（类型与容量参数）、是否允许移除；
  支持按槽读、写、删，以及枚举已占用的槽
- 持久容器实现与内存容器实现，以及按既有容器的形状创建临时容器的能力
- 角色维度的容器注册与绑定：注册容器、移除容器、按类型列出可用容器、
  按类型取得当前容器、切换当前容器
- 既有的道具移动协议与道具使用协议改为经容器操作
- 背包全量投影与增量投影所需的容器状态可由容器供给
- 只读的道具可用性判定，调用方只需提供角色与道具标识
- 道具使用后的状态变更（效果），按其作用目标区分
- 角色维度的冷却记录

### Out

- 多容器切换所需的持久化结构变更与触发协议
- 副本临时容器是否向客户端展示角色真实物品的策略
- 跨存储的事务机制
- 装备穿戴、丢弃、排序、售卖等其余道具协议
- 经验类道具与仓库扩容的效果实现（其协议入口 `0x001E` / `0x0132` / `0x0198` 尚未实现）
- 参考实现中 `Tool/` 与 `.worktrees/legacy-reference/` 内容的任何改动

## Constraints

- 第一个成果不得改变任何对外可观察行为
- 容器自行决定自身是持久的还是内存的，其使用方不区分二者
- 某类型下第一个被注册的容器成为该类型的当前容器
- 移除当前容器时回落到该类型下第一个不可移除的容器；不存在可回落容器时视为程序错误
- 可用性判定为只读，且不向调用方暴露其所需事实的获取方式
- 协议帧的构造与推送不属于效果，效果只改变状态
- 冷却记录以角色与道具声明的共享标识为键，靠时间比较判定，不依赖定时回调
- 一次道具使用的效果集合作用于同一个存储

| ID | Observable condition | Required evidence |

| SC-2 | 当前容器可作为背包投影内容的来源 | 由容器供给的容器状态，其编码所得帧字节与入场加载路径对同一存储内容所得一致 |

| SC-4 | 移除当前容器后角色仍绑定到一个可用容器；无可回落容器时以异常暴露 | 覆盖这两种情形的自动化测试通过 |
| SC-5 | 第一个成果完成后对外行为一字未变 | 既有测试基线（780 通过 / 2 跳过）保持全绿且测试未被修改语义；实机走通教学关，拖拽物品到快捷栏与饮用药水的表现与改动前一致 |

## Assumptions

- 效果模型需要能表达作用于容器、角色、账号三类目标，但本任务只实现当前已有协议路径
  能够触达的效果；经验与仓库扩容的效果实现随其协议入口一并留待后续
- 冷却记录不持久化，进程重启或重新登录会清空。10 秒级的药水冷却可以接受这一点，
  30 分钟级的召唤冷却会因此被重置；参考实现同样如此
- 一次道具使用的效果是否包裹在单个事务中，留给实现阶段决定；本契约只要求其目标同存储
- 现存的两处背包投影——选角入场的五份初始快照与每日补给的增量——都在本任务范围之外，
  而道具移动与道具使用两条协议只回 CMD 应答、不推送投影。因此 SC-2 交付的是
  「容器可作为投影内容的来源」这一能力并以逐字节一致为证；让生产路径真正改从容器取，
  须与多容器切换的持久化结构和触发协议一并落地，届时另行评估与授权
  （revision 2 据此重述 SC-2，由用户于 2026-08-18 授权）
