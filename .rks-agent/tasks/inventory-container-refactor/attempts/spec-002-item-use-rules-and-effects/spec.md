# Specification: 道具使用的判定、效果与诚实的拒绝

## Why and Outcome

道具使用现在只有一条规则：主背包里任何非装备物品，扣 1。归档为每个可堆叠物写着的限制
——谁能用、多少级能用、多久能用一次、在哪能用、用完是否消耗——一条也没读。84 个声明为
不消耗的道具因此被销毁；6,254 个声明了冷却的道具可以无限连点。

而当服务端确实要拒绝时，它挑的那个码要么客户端一个字都不显示（`0x0013` 的 `0x02` 不在
客户端的分支链里），要么显示一句与真实原因无关的话（`0x04` 说的是「金库空间不足」，
却被用在无会话、无绑定容器、两槽皆空、读写间被改动这四种与空间无关的情形上）。

完成后：一次使用先被问「能不能用」，答案是「可以」或一个具名的原因；可以则按该道具自己的
效果集合改变状态，不消耗的道具数量不减；不可以则回一个客户端确实会显示、且文案与该原因
相符的码——没有相符文案时，不显示任何提示，因为一句假话比沉默更坏。

## Task Perspective

- Core outcome: 玩家使用道具时得到归档所声明的那套规则，且被拒绝时看到的是实话。
  消费者是玩家，其可观察结果只有三样：数量变不变、能不能连点、屏幕上出现哪句话。
- Necessary support: 判定只读且自行取得所需事实；使用引起的状态变更全部归到效果侧且各自
  自述作用目标；冷却记录以共享标识为键；两条协议的失败原因由处理结果承载，而不是由处理器
  在应答处临时推断。
- Peripheral assurance: 拒绝原因到客户端码的对照与已归档的客户端文案逐条对齐；既有测试
  基线保持全绿，因本成果而必须改语义的用例逐条说明。

## Scope and Non-Goals

### In Scope

- 只读的道具可用性判定：入口只接受角色与道具标识，答案为「可用」或一个具名拒绝原因
- 使用引起的状态变更，表达为一组各自自述作用目标（容器 / 角色 / 账号）的效果
- 角色维度的冷却记录，键为角色与道具的共享冷却标识
- `0x002C USE_STACKABLE` 与 `0x0013 MOVE_ITEMSPACE` 的处理结果携带具名的拒绝原因
- 拒绝原因到客户端提示码的对照，依据已归档的客户端文案表

### Non-Goals

- 经验类道具与仓库扩容的效果，其协议入口 `0x001E` / `0x0132` / `0x0198` 尚未实现
- 装备穿戴路径的判定及其专属拒绝码（Equipment 列表尚未被任何容器服务）
- 疲劳值：服务端没有这个模型，客户端的码 `95` 因此无从使用
- 冷却的持久化，以及冷却在进程重启后的恢复
- 客户端字符串表的任何改动，或新增客户端不认识的码
- 把使用后的真实数量推送给客户端
- 选角入场快照与每日补给两条投影路径

## Constraints

- 判定为只读：一次提问不改变存储、冷却记录或任何会话状态
- 判定不向调用方暴露其所需事实的来源，调用方不提供冷却记录、角色等级职业或所在场所
- 应答帧的构造与发送不是效果；效果只改变状态
- 冷却靠时间比较得出，不依赖定时回调
- 一次使用的效果集合作用于同一个存储
- 拒绝原因不得借用文案与之不符的客户端提示码
- 两条协议仍对每一个请求回应答帧；「不显示提示」指客户端收到帧后不弹文案，不是不回帧
- 归档声明了某项限制却读不出可用数值时，按拒绝处理，不猜数值
- 除本 Spec 要求的变更外，其余对外可观察行为不变

## Definitions

| Term | Meaning |
|---|---|
| 不消耗道具 | 归档 `[stackable type]` 以 `unlimited` 开头的道具，全档 84 个 |
| 共享冷却标识 | 归档 `[cooltime group]` 的非零值；该标签缺失或为 0 时，取该道具自己的模板标识 |
| 静默码 | 客户端收到后不显示任何文案的失败码。`0x002C` 的分支链、`0x0013` 的分支链、以及全客户端共用的兜底表，三者都不含该值 |
| 效果 | 一次成功使用所引起的一项状态变更，自述其作用目标为容器、角色或账号 |
| 拒绝原因 | 判定或协议处理给出的具名结果，与客户端提示码是两件事：原因先被确定，码是它的翻译 |

## External Behavior and Data Rules

- 客户端的失败文案表已归档于 `protocol/patterns/data/probes/cmd-reason-messages-20260818.md`，
  含每个码走屏幕提示、聊天行还是仅走日志。选码以该归档为准。
- 失败码的取值空间是全局的：全客户端共用一张兜底表（77 / 105 / 114 / 115 / 122 / 123 /
  134 / 136 / 137 / 208 / 210 / 214 / 228 / 229 / 230 / 237 / 239），落在其中的值无论哪条
  协议回它，都会得到同一句账号安全或交易限制的话。静默码必须同时避开这批值。
- 两条协议的应答帧布局不变：`0x002C` 成功 12 字节、失败 11 字节；`0x0013` 成功 11 字节、
  失败 4 字节。本 Spec 只改变失败体里那个码的取值。
- `0x002C` 的成功应答不带剩余数量，客户端在发出请求时已自行把数量减一。

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 道具能否使用可由「角色 + 道具标识」单独问出；答案是「可用」或一个具名拒绝原因（冷却中 / 等级不足 / 职业不符 / 场所不允许 / 不是可使用的道具） |
| RQ-002 | 判定所需的事实由判定自身取得；调用方不提供冷却记录、角色等级与职业、所在场所 |
| RQ-003 | 归档未声明某项限制时该限制不生效；声明了却读不出可用数值时，该道具判为不可使用 |
| RQ-004 | 一次成功的使用产生一组效果，每个效果自述其作用目标为容器、角色或账号 |
| RQ-005 | 不消耗道具的效果集合中不含减数量：使用后存储中该槽的数量与使用前相同，且应答为成功 |
| RQ-006 | 使用成功后记录冷却，键为角色与该道具的共享冷却标识 |
| RQ-007 | 距上次记录不足该道具 `[cool time]` 毫秒时，同一角色下同一共享冷却标识的任何道具判为冷却中；记录不跨进程存活 |
| RQ-008 | `0x002C` 的处理结果携带具名的使用拒绝原因，`0x0013` 的处理结果携带具名的移动拒绝原因；处理器只把原因翻译成客户端码，不自行推断原因 |
| RQ-009 | 每个拒绝原因所选的客户端码，或是客户端会显示且其文案与该原因相符的一个，或是静默码；两条协议仍对每一个请求回应答帧 |
| RQ-010 | `0x002C` 的原因到码：职业不符→`8`，等级不足→`14`，冷却中→`19`，场所不允许→`19`，槽中不是可使用的道具→`23`，服务端故障或读写间竞态→静默码 |
| RQ-011 | `0x0013` 的原因到码：列表不服务→`23`，物品不能占用目标槽→`23`，交换时被顶出的物品不能占用腾出的槽→`23`，合并会超出堆叠上限→`17`，两槽皆空→静默码，读写间槽位改变→静默码，无会话或无绑定容器→静默码；`4` 只用于目标容器确无空位 |
| RQ-012 | 除本 Spec 要求的变更外，其余对外可观察行为不变 |

## Assumptions

- 客户端在发出使用请求时已自行把数量减一，而成功应答不带剩余数量，服务端无法经由应答
  纠正它。客户端读的是同一份归档，因此推定它对不消耗道具本就不做本地自减。该推定**至今未验证**：
  走查发现当前客户端不肯为任何一个不消耗道具发出使用请求，服务端收不到帧，因此这条既未被证实
  也未被证伪。AC-018 的实机部分据此重述为不含该项（子契约 revision 2，2026-08-19 用户授权）；
  若日后证伪，需要一条把真实数量送回客户端的推送路径，那超出本 Spec 边界
- 冷却记录不跨进程存活。十秒级的药水冷却可以接受这一点，三十分钟级的召唤冷却会因此被重置
- 副本尚未实现，场所判定当前只能在「城镇」一侧取值；声明只允许副本的道具在本服恒被拒绝
- 客户端的失败文案来自其自带的字符串表，服务端只能在既有码里挑选，无法新增文案。
  冷却与场所在客户端没有专属文案，最接近的是 `19`「目前无法使用物品」，两者因此合并为同一句
