# Spec Result: 道具使用的判定、效果与诚实的拒绝

## Outcome

道具使用不再是「主背包里任何非装备物品，扣 1」。归档为每个可堆叠物写着的四条限制——谁能用、
多少级能用、在哪能用、多久能用一次——现在都被读出来并执行；使用引起的状态变更归到效果侧，
不消耗的道具因为效果集合里没有减数量那一项而不再被销毁；两条道具协议的拒绝原因由命令结果承载，
处理器只负责把原因翻译成客户端确实会显示、且文案与原因相符的码，没有相符文案时不显示提示。

84 个 `[stackable type]` 以 `unlimited` 开头的道具从此不会被一次按键销毁一个。
6,254 个声明了 `[cool time]` 的道具的冷却在服务端生效，其中 1,713 个按 `[cooltime group]` 共享。

## What Was Delivered

新增抽象（`Dfo.Server.Abstractions/`）：

- `IItemUseRuleDefinitionSource` 与 `ItemUseRule`：归档为一个道具声明的使用规则。区分「未声明」
  与「声明了却读不出」——后者判为不可读，因而拒绝。这条区分不是洁癖：一个读不出 `[stackable type]`
  的不消耗道具，若把读不出当成未声明，就会被当作消耗品销毁，正是本成果要消除的那个缺陷。
- `IItemUsabilityDomainService`：`CanUseAsync(角色, 道具标识)`，只读，自行取得冷却记录、
  角色等级与职业、所在场所。答案是「可用」或一个具名拒绝原因。
- `IItemUseEffect` 与 `IItemUseEffectDomainService`：一次使用产生一组效果，每个自述其作用目标为
  容器、角色或账号。协议帧的构造与发送不是效果。
- `ICharacterItemCooldownDomainService` 与 `ItemCooldownKey`：角色维度的冷却记录。键是复合的
  ——组号与道具标识是两个不相干的编号空间，用裸整数会让冷却组 70 和道具 70 共用一个计时器。

新增实现：

- `PvfItemUseRuleDefinitionSource` 读六个标签。归档里 `[usable job]` / `[action usable place]` 是
  「标签 + 若干值 + 闭合标签」，值是 QuotedString 而非 Identifier；照标签清单写而不实测的读法，
  会把每个 section 读成空、每条限制读成不存在。
- `ItemUsabilityDomainService` 的判定顺序是「不可读 → 角色状态 → 等级 → 职业 → 场所 → 冷却」。
  永久原因排在会过期的原因前面：冷却是共享的，报一个会过期的理由会让玩家等完再试一次，仍然不行。
- `ItemUseEffectDomainService`：不消耗表达为效果集合中没有减数量，而不是减数量前的一个判断。
  差别在于后者让「使用」永远意味着「扣减，除了有时候」，之后每加一个效果都要重复同一个例外。
- `CharacterItemCooldownDomainService`：一个字典和一个时钟。没有定时器，因为冷却到期不需要触发
  任何事——只是下一次提问得到不同的答案。

迁移与接线：

- `0x002C` 与 `0x0013` 改经 `ICommandBus`，命令结果携带具名的拒绝原因。两个协议处理器只做
  「会话解析 + 原因翻译」，不再对道具下任何判断。
- 两处 `ErrorCodeFor` 与一处 `StatusFor` 逐条列举全部原因，未列举者抛出。兜底会让下一个被加进来的
  拒绝原因悄悄变成静默，而遍历枚举的用例仍然全绿。
- `SelectedSessionCleanupService` 在会话目录条目移除后清理冷却记录，与容器清理同一条件
  ——先确认该角色没有别的活动会话。

顺手拆掉两处既有重复，二者都是本成果需要的：`[usable job]` 的词表原本只在 `PvfQuestDefinitionSource`
里有一份，职业号到职业族的映射原本只在 `WorldContentEntryRuleService` 里有一份。各自抽成一处共享，
而不是抄第二份。

## Evidence

- 自动化：**848 通过 / 2 跳过 / 0 失败**（基线 791/2/0 加新增 57 个用例）。
- 实机：2026-08-19 走通喝药减一与冷却拒绝，日志见 `verification/completion-evidence.md`。
- 评审：三轮独立 subagent 评审，记录见 `reviews/change-review.md`，最终 `approved`。

## What Review Changed

三轮评审共 16 条发现，处置 12 条。其中不是靠测试全绿能发现的：

1. **服务端自己的时序缺口被说成玩家的错**（阻断）。`FindCharacter` 取不到角色运行时状态时答
   `NotAUsableItem`，翻译成 `23`「非消耗品，无法使用」。入场先注册会话、再绑定容器、最后才发布
   运行时状态，中间那段窗口里的请求会撞上它。同一条命令里另外三个同类情形都已正确映到静默，
   唯独这一个没有；该分支在全套用例里从未被执行过。
2. **`_ => Silent` 兜底**让忘记决定码的新拒绝原因悄悄变成静默，而遍历枚举的用例仍绿。改为逐条列举
   加抛出后，那两条用例才成为真检查。
3. **四处「删掉它全套仍绿」**：交换对端放不下的选码、离场清空冷却的接线、命令注册、
   以及三态读取里那两行置位。评审逐一实证，现已各有用例钉住，并经变异验证。
4. **判定顺序**让共享冷却盖住等级不足——玩家被告知一个会过期的原因，等完再试仍然不行。

评审也纠正了我两处自己的判断：把「读不出即拒绝」扩到全部四个标量标签是对的（全档实测误判为 0），
但抛异常的代价比我写的重——异常经不捕获的 dispatcher 到插件，log 后重抛，**该玩家会掉线**，
不只是拿不到应答。这一点已写进注释。

## Boundary Changes Made During Execution

- **根契约升至 revision 3，新增 SC-9**。用户于 2026-08-18 追加要求「command 要承载失败的语义，
  让 handler 能返回正确的错误给 client 显示」，超出 revision 2 的授权范围，取得扩容授权后写入。
- **子契约升至 revision 2，AC-6 的实机要求重述为两项**。「不消耗类道具使用后数量不减」的实机确认
  未能取得：当前客户端不肯为任何一个 `[unlimited *]` 道具发出使用请求。用户于 2026-08-19 授权重述，
  该项记入根 map 的 Deferred Follow-up。

## Known Gaps Left Open

- **177 个道具因声明中混入本服未建模的取值而恒不可用**（职业侧 64、场所侧 113）。这是契约
  「归档里读不出所需事实时按拒绝处理，不猜数值」的直接后果，不是缺陷。要缩小影响面只需向
  `ArchiveJobFamilyTokens` 与 `PlaceTokens` 补入这些取值，但那需要先弄清它们的语义。
  当前 `0x002C` 只服务主背包消耗品，这 177 个里几乎没有可触达的。
- **`[maximum level]`（506 个道具声明）未实现**。客户端没有「等级过高」的诚实文案，
  最接近的 `14` 说的是「Lv过低」；实现它只会多一句假话。
- **疲劳（客户端码 95）未实现**，服务端没有这个模型。
- **装备穿戴路径的诚实拒绝码（`8` / `14` / `7`）用不上**，Equipment 列表尚未被任何容器服务。
- **容器行自带的 `ItemKind == 1` 检查被移除**。新的拒绝集合是旧集合的超集，唯一的理论例外是
  「道具在 stackable 索引内、但存储行上的 kind 被写成 1」——所有写入路径都用同一个推导函数，
  而它对 stackable 标识从不返回 1，正常运行下不可达。
- **冷却不持久化**，进程重启或重新登录会清空。十秒级的药水冷却可以接受，三十分钟级的召唤会被重置；
  参考实现同样如此。

## Facts Learned That Outlive This Spec

- **客户端自己实现了 `[cool time]` 并显示剩余秒数。** 服务端应答帧不含时间字段，倒计时只能是客户端算的。
  这条规则因此有两道，客户端先生效；服务端这道是防改包的权威判定，正常玩家看不到它的拒绝。
- **客户端对 `[unlimited *]` 道具另有有效期检查。** 同样 `ExpireTime=0`，`[waste]` 药剂照用不误，
  三个 `[unlimited waste]` 报「超过使用期限」。提示 `unlimited` 的语义可能是
  「使用不消耗，改由有效期约束」，而不是「永远无限」。
- **客户端在接受按键的那一刻就应用了 `[hp recovery]`，不等服务端应答。** 服务端拒绝时玩家会看到
  「回了血但道具没扣」；这只在客户端冷却被绕过时出现，正常情况下轮不到服务端说话。
