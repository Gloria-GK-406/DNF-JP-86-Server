# TaskContract: 道具使用的判定、效果与诚实的拒绝

## Context

### Source Request

由根任务 `.rks-agent/tasks/inventory-container-refactor/TaskContract.md`（revision 3）
的成果二派生，覆盖其 SC-6 至 SC-9。根授权原话：

> 写multispec吧，把第二刀也记录一下。这样省的后面上下文多了，到时候忘了第二刀干啥。
> 这样我们就能用两个subspec来完成这个任务了。

SC-9 由用户于 2026-08-18 追加授权：

> 并入spec2一起处理。……这里我要说commnd要承载失败的语义，让handler能返回正确的错误给
> client显示。你看如何？

同日就三个设计问题定下：客户端确有提示能力，须先确认其码表；判定与状态变更分开，
状态变更放在效果侧；不消耗的道具表现为「不执行减数量那个效果」。

### Current Situation

成果一（`cf010d5`）之后，`UseStackableHandler` 与 `MoveItemSpaceHandler` 都经容器读写，
但两者仍各自内联做全部判断，且都不经命令总线——同一代码库里已有七个 Game 切片走
`ICommandBus` 并从类型化结果里读失败原因（`DeleteCharacterCommand` 返回
`CharacterDeletionResult`），这两条是仅剩的例外。

道具使用本身仍是半成品：

- 对主背包里任何非装备物品一律扣减 1。归档中 84 个 `[stackable type]` 以 `unlimited`
  开头的道具因此被销毁——`[unlimited waste]` 64、`[unlimited town and dungeon]` 18、
  `[unlimited etc]` 2。
- 归档声明的冷却完全没有实现：`[cool time]` 6,254 个，其中 `[cooltime group]` 1,713 个。
- `[action usable place]`（792 个）、`[usable job]`（34,533 个）、`[minimum level]`
  （28,673 个）均未参与判断。

拒绝的表达同样是坏的。`0x0013` 现用两个码：`0x02` 根本不在客户端的分支链里，
什么都不显示；`0x04` 显示「金库空间不足，无法放入物品」，却被用在无会话、无绑定容器、
两槽皆空、读写间被改动这四种与空间无关的情形上。客户端的完整码表已探明并归档于
`protocol/patterns/data/probes/cmd-reason-messages-20260818.md`，
归档中记有每个码走屏幕提示还是仅走日志、以及其 CN/JP/KR 文案。

## Goal

把道具使用拆成「只读的可用性判定」与「承载全部状态变更的效果」两部分，使不消耗、冷却、
场所这类规则各自有其归属；并让两条道具协议的失败原因由命令结果承载，
使处理器能选出客户端确实会显示、且文案与实际原因相符的提示——没有相符文案时宁可不提示。

## Scope

### In

- 只读的道具可用性判定：入口参数仅为角色与道具标识，内部自行取得冷却、等级、职业、
  场所所需的事实，不由调用方组装
- 道具使用后的状态变更（效果），按其作用目标区分容器、角色、账号；一次使用产生一组效果
- 「使用后不消耗」表现为该道具的效果集合中没有减数量这一项，而非在减数量处加判断
- 角色维度的冷却记录：以角色与道具声明的共享标识为键，内存持有、靠时间比较、
  无定时回调、不持久化
- `0x002C USE_STACKABLE` 与 `0x0013 MOVE_ITEMSPACE` 改经命令总线，命令结果承载
  类型化的失败原因
- 处理器按失败原因选择客户端提示码，选择依据为已归档的客户端码表

### Out

- 经验类道具与仓库扩容的效果实现，其协议入口 `0x001E` / `0x0132` / `0x0198` 尚未实现
- 装备穿戴路径的判定与其专属拒绝码（Equipment 列表尚未被任何容器服务）
- 疲劳值：服务端没有这个模型
- 冷却的持久化
- 客户端字符串表的任何改动
- 多容器切换的持久化结构变更与触发协议
- 选角入场快照与每日补给两条投影路径的迁移
- `Tool/` 与 `.worktrees/legacy-reference/` 的任何改动

## Constraints

- 可用性判定为只读，且不向调用方暴露其所需事实的获取方式
- 协议帧的构造与推送不属于效果，效果只改变状态
- 冷却靠时间比较判定，不依赖定时回调
- 一次道具使用的效果集合作用于同一个存储
- 拒绝原因不得借用文案与之不符的客户端提示码；没有相符文案时选择客户端不显示提示的码
- 协议仍必须应答每一个请求：不提示指的是不弹文案，不是不回帧
- 归档里读不出所需事实时按拒绝处理，不猜数值
- 除 SC-6 至 SC-9 直接要求的行为变更外，其余对外可观察行为不得改变

## Assumptions

- 冷却记录不持久化，进程重启或重新登录会清空。10 秒级的药水冷却可以接受这一点，
  30 分钟级的召唤冷却会因此被重置；参考实现同样如此
- 客户端在使用后自行把数量减一，而应答帧不带剩余数量，故服务端无法经由应答纠正它。
  客户端读的是同一份归档，因此推定它对 `unlimited*` 道具本就不做本地自减；
  若实机证伪，则 AC-2 的实机部分需要一条把真实数量送回客户端的路径，
  那超出本子任务边界，应停在安全点上报根控制器
- 归档为可堆叠物声明了 `[usable job]`、`[minimum level]`、`[cool time]` 与
  `[action usable place]`，四类拒绝分支都有依据；服务端已持有角色是否站在城镇的事实，
  副本尚未实现，故场所判定当前只能在「城镇」一侧取值
- 一次道具使用的效果是否包裹在单个事务中，留给实现阶段决定；本契约只要求其目标同存储
- 不消耗类道具的实机确认不在 AC-6 之内。走查证实当前客户端不肯为任何一个 `[unlimited *]`
  道具发出使用请求（四个候选各被不同的客户端侧门槛挡住，详见 `verification/completion-evidence.md`），
  服务端收不到帧，实现正确与否观察不到差别。该项存储侧行为由 AC-2 的自动化证据覆盖；
  实机确认记入根 `../../multi-spec-map.md` 的 Deferred Follow-up
  （revision 2 据此重述 AC-6，由用户于 2026-08-19 授权：「按1延后吧。后续再说」）
