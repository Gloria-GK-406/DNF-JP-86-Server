# Routing Decision

- Contract revision: `1`

## SDD Readiness

- Intent and outcome stability: 切分线（按概念而非按协议分段）、合并判据（同键、同生命周期、同写入用例）与红线（不得压成通用键值行）都在本轮对话中由用户逐条确认；用户随后拒绝分块推进并要求一次全改，范围因此闭合。可观察结果明确：同一概念在库里只有一处承载，且对外协议行为一字不变。
- Requirement stability: 十条成功条件可枚举且各自有观察方式——承载处的清点、列归属清单、逐表裁定记录、下发帧字节比对、表征用例的可证伪性。改动前的 53 张表构成一个封闭清单，任何一处遗漏都可被清点发现。
- Execution direction: 中心方向已知。上一轮（fc6467a）已把持久化收敛为一表一类、跨表编排归领域层，并留下三份整记录表征用例；本任务在该形状之上只改表的边界，不改谁编排谁。
- Remaining uncertainty: 只剩不改变任务语义的局部裁定——邮件附件是否算作物品的一种归属；`character_active_quests` 与 `character_quest_notify_selections`、`character_daily_challenge` 三张组级表是否满足三条判据。契约已把它们交给 Spec 裁定并要求留下理由，不构成语义空缺。

## Marginal Control Value

- User precision signal: 用户主动指定「按 multi-spec 来处理」，并在此前一轮否决了「先从物品域开刀」的分步方案。用户既往在同类持久化任务上一律选择 SDD 治理流程，理由是「只是为了实现别漂移」。精度优先，且已接受流程时间成本。
- Direct failure mode: 静默丢列与静默丢行。这是数据形状变更而非行为保持重构：把六张 1:1 表折进角色本体、把十余张物品表并成三处时，漏掉一列或一条读路径不会让测试变红——表还在、查询仍能跑，只是返回默认值——而是在实机选人时下发一个字段为 0 的包。上一轮同规格任务已实际发生两次同类：一张表在集中化时无人声明，导致全新服务器首次选人必抛；一条读路径被误加了原本不读的详情，导致仓库里存有时装即抛。两次都是评审而非测试发现的。
- Useful control: 可观察要求（Spec）把「哪一列必须仍然到达客户端」钉成验收条件；整记录表征用例（改写而非删除，且须证明可证伪）把静默丢列变成红灯；对完整结果的独立评审提供上一轮唯一抓住这两个缺陷的那种视角。
- Time-for-quality rationale: 失效不产生红灯、且只在实机远离改动点处显形，事后定位成本远高于流程成本；改动面覆盖 53 张表、58 个按表接口与两处千余行的组装点，Direct 下的注意力损耗是确定的而非假设的。

## Structural Selection

- Selected workflow: `multi-spec-workflow`
- Boundary evidence: 契约含四个可独立验收的成果，各自作用于互不相交的表集合、各自有独立的表征守卫、各自可独立回滚——物品域（SC-1、SC-2）、角色本体与至多一行状态的折入（SC-3、SC-4）、技能域（SC-5）、账号侧（SC-6）。物品域单独交付即可让物品承载处唯一并退役上一代表，不依赖角色本体是否重切；技能域与账号侧同理。四者之间存在需要排序的耦合而非合并的必要：金币上限今天被物品侧读取，折入角色本体会改动物品侧的读路径，因此角色本体这一块须先于或同步于物品域裁定该列的归属。SC-7 至 SC-10 是贯穿性验收，由父控制器在各子成果之上合成。
- Why Direct is insufficient: Direct 无法在事前把「哪一列必须仍然到达客户端」固定成可复核的验收条件，也没有独立评审这一层；而本任务的失效恰恰不产生红灯，只能靠事前钉死要求与事后独立复核拦住。
- Reroute conditions: 若实施中发现上一代物品表存在写入路径（契约 Assumptions 第一条不成立），物品域的边界须重新裁定，可能需要扩充授权范围；若两处租借的列语义无法一一对应，SC-2 的合并前提失效；若六处「至多一行」中任何一处实际可有多行，该处退出折入范围并保留独立承载；若四块之间出现无法靠排序解决的循环依赖，退回单一 Spec 以一个连贯边界交付。
