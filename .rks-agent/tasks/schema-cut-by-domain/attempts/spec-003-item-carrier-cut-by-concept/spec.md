# Specification: 物品承载按概念重切

## Why and Outcome

一件物品今天分属四张表，取决于谁拿着它、它是不是时装。角色背包一张、账号仓库一张、称号册一张，第四张只装时装才有的那几件事。四张表说的是同一件事——某个容器的某个槽里放着一个东西——却各有各的键、各有各的约束强度、各有各的读取路径。租借同样一件事有两张列语义完全相同的表，领域层已经把它们当作一个列表来读，只有存储还没跟上。还有一张表用 `list_kind` 一列决定 `value` 那一列是什么意思，这是库里最清晰的一处「用一列重新解释另一列」。另有两张上一代的分解式表，没有任何写入，只被一处迁移守卫问「空不空」。

要变成真的是：一件物品由 `items` 一处承载，谁拿着它是这一行的列而不是它在哪张表；一次租借只有一处；没有哪一列的含义要靠另一列来决定；上一代的两张表不再存在。而客户端收到的每一个字节与今天完全相同。

## Task Perspective

- Core outcome: 库里物品这一块的形状，与已封存的裁定给出的目标形状一致——概念一张表，边界说得清。
- Necessary support: 称号册的 `category` 与容器类型之间的双向变换必须正确，否则第一个同时拥有背包与称号册的角色会撞键或载入即抛；九张源表的每一条约束要在其落点上继续成立，两处不能直接存续的要各有结论；三条写不成 `CHECK` 的规则要继续由代码保证。没有这三样，形状对了而行为变了。
- Peripheral assurance: 下发帧的字节比对与表征用例的可证伪性。它们证明行为没变，但它们本身不是成果。

## Scope and Non-Goals

### In Scope

- `character_new_items`、`account_cargo_new_items`、`character_new_titlebook`、`character_avatar_detail` 并为 `items`。
- `character_rental_items` 与 `rental_items` 并为 `character_rentals`。
- `character_item_values` 拆为 `character_item_cooldowns` 与 `character_item_effects`。
- `character_items` 与 `account_cargo_items` 退役，连同只依赖它们的那一处迁移守卫。
- 上述各表的读写路径、按表接口与其行类型、索引与可补列清单随之改写。
- 领域层的跨表组装随形状更新。
- 表征用例改写到新形状。
- 裁定指名交给物品侧回答的五处悬置事项各给一个结论。

### Non-Goals

- 不动 `character_item_locks`、`character_collectbox_slots`、`mailbox_attachments`。
- 不动角色本体、技能与账号侧的表。
- 不为既有数据设计回填、修复或迁移路径。
- 不改变对外协议行为。

## Constraints

- 裁定是设计权威。与它不一致的实施须先更新裁定并说明理由，不得就地偏离。
- 源表的每一条约束在其列的落点上存续，或有明确的结论说明为何不存续。
- 三条写不成 `CHECK` 的规则由代码继续保证。
- 开发阶段擦库不迁移：直接以新形状建库。
- 覆盖不可净减少。

## Definitions

| Term | Meaning |
|---|---|
| 裁定 | `Docs/Refactor/TableOwnershipRuling.md`，本 Spec 的设计权威 |
| 目标形状 | 裁定中「Target shape」一节给出的表与列 |
| 承载 | 目标形状中存放某一概念的那一张表 |
| 时装 UID | 物品核心块第 5..8 字节的那个值（`InventoryItemCore.Value`）；时装靠它找到自己那几列 |
| 三条规则 | 裁定「Three rules `items` carries that are not constraints」一节所列：哪些行有时装列、仓库行永远没有、角色的时装必须带非零 UID |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 库形状在物品这一块上与裁定的目标形状逐列一致：表名、列名、列的归属都相同 |
| RQ-002 | 一件物品无论属于角色背包、账号仓库还是称号册，都是 `items` 的一行；时装才有的那几件事是该行的列 |
| RQ-003 | 称号册的 `category` 存为 `19 + category`，读回时还原为 `category`；同一角色的背包 0 号槽与称号册 0 号槽可以共存 |
| RQ-004 | 角色背包的读取不会取到称号册的行 |
| RQ-005 | 改动前九张源表的每一条键、唯一性、检查与外键，在其落点上仍然成立；两处不能直接存续的（时装详情的主键、仓库的槽位唯一性）各有一个已实现或已记录的结论 |
| RQ-006 | 三条写不成 `CHECK` 的规则由代码继续保证：非时装行没有时装列；仓库里的时装不带时装列而角色的时装缺时装列是错误；角色的时装 UID 为零或负时被拒绝 |
| RQ-007 | 一个角色写不到另一个角色的物品行与其时装列 |
| RQ-008 | 租借由一处承载；跨两张源表的重复检查在合并后仍然拒绝同样的输入 |
| RQ-009 | 没有一张物品表用一列重新解释另一列；冷却与效果各自成表，读出来仍是两个领域列表，顺序与今天相同 |
| RQ-010 | `character_items` 与 `account_cargo_items` 不存在，生产代码中不再有针对它们的读取路径与迁移守卫 |
| RQ-011 | 选人下发的帧与改动前逐字节相同 |
| RQ-012 | 今天由整记录表征用例守住的每一列，在新形状下仍被守住，且该守卫可证伪 |
| RQ-013 | 持久化类仍只指名一张表；跨表组装仍在领域层，且每条记录只有一个定义点 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 一个以新形状建起来的库 | 把物品各表的列与裁定的目标形状比对 | 表名、列名与列的归属逐一相同，无多无缺；四张源表不存在 |
| AC-002 | RQ-002 | 一个角色的背包物品、其账号仓库的物品、其称号册的一条 | 载入这个角色与这个账号 | 三者都来自 `items`，且各自的领域记录与改动前逐字段相同 |
| AC-003 | RQ-003 | 一条 `category` 为 0..4 的称号册记录 | 写入后按容器类型清点，再按 `category` 读回 | 存的是 19..23；读回得到原来的 `category` |
| AC-004 | RQ-003 | 同一个角色，背包 0 号槽有物品，称号册 0 类 0 号槽也有 | 两者同时存在于库中 | 两行共存，唯一性约束不被违反 |
| AC-005 | RQ-004 | 一个既有背包物品又有称号册记录的角色 | 载入这个角色的背包 | 只得到背包的物品；称号册的行不出现，也不引发容器类型解析的拒绝 |
| AC-006 | RQ-005 | 改动前九张源表的约束清单 | 逐条在新形状里查找对应的约束 | 每一条都能找到落点，或能指出结论：时装详情的主键与仓库的槽位唯一性各自或由一个部分唯一索引恢复，或有证据说明为何不恢复 |
| AC-007 | RQ-006 | 一个非时装的物品行 | 载入它 | 不去找时装列，也不因为没有时装列而拒绝 |
| AC-008 | RQ-006 | 账号仓库里的一件时装 | 载入这个账号 | 它被带上来且不带时装列，与改动前一致 |
| AC-009 | RQ-006 | 角色背包里的一件时装，其时装 UID 为零 | 载入这个角色 | 被拒绝，理由与改动前一致 |
| AC-010 | RQ-006 | 角色背包里的一件时装，没有时装列 | 载入这个角色 | 被拒绝，理由与改动前一致 |
| AC-011 | RQ-007 | 角色甲持有的一件时装 | 角色乙尝试写它的物品行或时装列 | 没有行被改动，与改动前一致 |
| AC-012 | RQ-008 | 两张源表各有一条租借、且它们指向同一个 item id | 载入这个角色 | 被拒绝为重复，与改动前一致 |
| AC-013 | RQ-009 | 一批冷却与一批效果 | 载入这个角色 | 得到两个领域列表，内容与顺序与改动前相同；库中不存在 `list_kind` 这一列 |
| AC-014 | RQ-010 | 改动后的库与生产代码 | 查找上一代两张表与那处迁移守卫 | 都不存在；一个旧形状的库载入得到空背包而不是拒绝，这一后果已被记录 |
| AC-015 | RQ-011 | 同一个角色在改动前与改动后 | 走一次选人并录下下发帧 | 两次的字节完全相同 |
| AC-016 | RQ-012 | 改写后的表征用例 | 对每一处承载，构造一次列错位或列缺失 | 用例变红 |
| AC-017 | RQ-013 | 改动后的持久化层与领域层 | 清点每个持久化类指名的表，以及每条记录的定义处 | 每个类只指名一张表；每条记录只有一个定义点，且组装在领域层 |

## Assumptions

- 裁定中标为已核实的事实成立。若实施中发现某条不成立，先更新裁定再继续。
- 目标是本机开发库，现有数据可直接丢弃，因此不需要考虑既有行的可转换性。
- 上一代两张表与四张被并入的表在生产代码中只有 `character_new_items` 与 `character_avatar_detail` 有写入语句（已由写入清点核实：前者三插三删两改，后者一处 upsert 与两处删除）。
