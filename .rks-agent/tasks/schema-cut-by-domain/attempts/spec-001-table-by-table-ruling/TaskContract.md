# TaskContract: 全表归属裁定与目标形状

## Context

### Source Request

根任务的第一个成果，由根控制器在成功者决定时划定：对改动前的全部 53 张表逐一给出归属裁定，并把裁定合成为一份目标形状。

根授权原话：「不，一口气全改了。可以按multi-spec来处理。」

### Current Situation

改动前的库形状有 53 张表、420 列，全部声明在一处。它们的边界来自选人下发的协议包分段，而不是来自角色这个概念。根契约要把它改成按概念切，并已确立合并判据（同一个键、同一个生命周期、同一个写入用例，三条同时成立才合并）与一条红线（不得把不同概念压成通用键值行）。

后续将有四块实施成果分别改动物品、角色本体、技能与账号侧。这四块之间有两处必须在任何代码移动之前定下来的东西：

- 金币上限今天由物品侧读取，把它折入角色本体会改动物品侧的读路径。哪一块先做、这一列归谁，两块都无法各自决定。
- 邮件附件按三条判据不满足并入物品：它按邮件与序号定位、生命周期跟邮件而不是跟容器、由邮件用例写入，且同时携带分解列、定长核心块、详情与来源出处。是否把「邮件」视为一种归属从而并入，是一次影响两块边界的裁定。

若不先定，各实施成果只能各自临时决定，那正是本任务要防的漂移。更要紧的是，本任务被具名的失效是静默丢列——数据形状变更时漏掉一列不会让测试变红，只会在实机下发一个值为 0 的字段。一份逐表逐列的归属记录，能把这种遗漏变成记录里的可见缺口。

## Goal

改动前的每一张表与每一列，在目标形状中的去向都有据可查的确定结论；后续实施只需照此执行，不再需要临场判断边界。

## Scope

### In

- 对 53 张表逐一裁定：并入某处、保持独立、或随其概念退役。
- 对每一处合并，说明三条判据各自如何成立；对每一处「看起来相近却不合并」的表，说明哪一条不成立。
- 对 420 列逐一确定去向：在目标形状中的落点，或随表退役并说明它今天是否仍被生产代码读取。
- 裁定邮件附件是否属于物品，并给出理由。
- 裁定金币上限的归属，并据此确定物品与角色本体两块实施的先后。
- 合成目标形状：每一张目标表的名称与列，以及每一列的来源。
- 记录裁定所依据的事实（定位键、基数、写入者、是否存在写入路径），使每条结论可由当前代码复核。

### Out

- 不改动生产代码、测试或库形状声明。本成果只产出记录。
- 不为既有数据设计回填、修复或迁移路径。
- 不裁定红线所排除的那一类合并：语义不同的表不得压成通用键值行。
- 不预先编写后续实施成果的任务分解或执行次序之外的实施细节。

## Constraints

- 合并判据（根契约继承）：同一个键、同一个生命周期、同一个写入用例，三条同时成立才可合并；仅名字相近不足以合并。
- 红线（根契约继承）：目标形状中不得出现以通用键值行承载多个概念的表。
- 每一条裁定依据的事实必须来自当前代码，且必须写明可复核到哪里；不得以推测代替核实。
- 记录须留在仓库内，与代码同处一次提交，可被后续成果更新。
- 全程不产生任务级提交。

## Success Conditions

| ID | Observable condition | Required evidence |
|---|---|---|
| SC-1 | 53 张表全部有裁定，无遗漏、无重复、无两处相互矛盾的归属 | 记录中的表清单与改动前库形状声明的清点逐一对应 |
| SC-2 | 每一处合并都写明三条判据如何成立；每一处「相近但未合并」都写明哪一条不成立 | 逐条可读的判据说明，且所依据的定位键、基数与写入者可在当前代码中找到 |
| SC-3 | 420 列全部有去向：落在目标形状的某处，或随表退役并注明今天是否仍被生产代码读取 | 列级去向清单与改动前的列清点数目相符，退役列各有读取状况的判断 |
| SC-4 | 邮件附件的归属有明确结论与理由 | 记录中该处的裁定文字，含三条判据的逐条判断 |
| SC-5 | 金币上限的归属有明确结论，且物品与角色本体两块实施的先后由此确定 | 记录中该处的裁定文字与由此得出的次序结论 |
| SC-6 | 目标形状可清点：表数、每张表的列均已给出，且没有一张目标表以通用键值行承载多个概念 | 目标形状清单；逐表检查其列名各自具有独立含义 |
| SC-7 | 记录中的每条事实结论都可被独立复核 | 每条事实注明其在当前代码中的可复核位置 |

## Authorization

| Capability | Evidence | Authorized scope |
|---|---|---|
| task | 根 TaskContract 的 task 授权行；用户原话「不，一口气全改了。可以按multi-spec来处理。」 | 在共享任务工作树中产出上述记录；范围内的验证；经评审与新鲜验证后由根控制器接受为一次已接受结果提交 |

## Assumptions

- 裁定基于当前代码可复核的事实。若后续实施发现某条事实不成立（例如某张被判为无写入路径的表实际存在写入），该处裁定由后续成果在其自身边界内修正并更新本记录，不构成本成果的失败。
- 目标是本机开发库，现有数据可直接丢弃，因此裁定不需要考虑既有行的可转换性。
