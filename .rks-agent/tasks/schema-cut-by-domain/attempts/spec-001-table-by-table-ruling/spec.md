# Specification: 全表归属裁定与目标形状

## Why and Outcome

库形状的边界今天来自选人下发的协议包分段，不来自角色这个概念。要把它改成按概念切，四块实施成果会分别动物品、角色本体、技能与账号侧；但其中两处边界任何一块都无法自己决定——金币上限今天由物品侧读取却属于角色，邮件附件按判据不满足并入物品却又确实是一件件东西。若不先定下来，四块只能各自临场判断，那正是要防的漂移。

更要紧的是本任务被具名的失效：静默丢列。数据形状变更时漏掉一列不会让任何用例变红，只会在实机下发一个值为 0 的字段。

因此要变成真的是：改动前的每一张表、每一列，去向都已有据可查地定下来，且这份结论本身可被清点——遗漏成为记录里数得出来的缺口，而不是运行期一个悄悄归零的字段。

## Task Perspective

- Core outcome: 后续实施的执行者对改动前的任意一张表或任意一列，能直接读出它去哪里、依据是什么，不必再自行判断边界；两处跨块的归属（邮件附件、金币上限）已有结论，且金币上限的结论同时给出了物品与角色本体两块的先后。
- Necessary support: 每一处合并与每一处「相近而不合并」都附三条判据的逐条判断；每一条作为依据的事实都注明可复核位置——没有这两样，结论无法被复核，也就无法被信任。
- Peripheral assurance: 表数与列数的清点、结论之间的交叉一致性检查。它们证明记录完整，但它们本身不是记录的价值。

## Scope and Non-Goals

### In Scope

- 改动前每一张表的归属结论。
- 改动前每一列的去向。
- 每一处合并的判据成立说明，每一处「相近而不合并」的判据不成立说明。
- 邮件附件的归属结论与理由。
- 金币上限的归属结论，以及由它得出的物品与角色本体两块实施先后。
- 目标形状：每一张目标表的名称与列，每一列的来源。
- 每一条依据事实的可复核位置。

### Non-Goals

- 不改动生产代码、测试或库形状声明。本 Spec 只产出记录。
- 不为既有数据设计回填、修复或迁移路径。
- 不产出实施步骤、任务分解或执行计划；除两块之间的先后结论外，不规定实施内部的次序。
- 不裁定红线所排除的那一类合并。

## Constraints

- 合并判据：同一个键、同一个生命周期、同一个写入用例，三条同时成立才可合并；仅名字相近不足以合并。
- 红线：目标形状中不得出现以通用键值行承载多个概念的表。
- 每一条裁定依据必须来自当前代码并注明可复核位置；不得以推测代替核实。
- 一处事实若无法从当前代码判明，则该处归属悬置并登记悬置理由，不得据推测给出结论。

## Definitions

| Term | Meaning |
|---|---|
| 判据 | 三条合并条件的合称：同一个键、同一个生命周期、同一个写入用例 |
| 键 | 一行在其所属概念中的定位方式，即需要哪几个值才能指到唯一一行 |
| 生命周期 | 一行何时产生、何时消失，以及它随谁一起被清空 |
| 写入用例 | 改动这一行的业务动作 |
| 承载 | 目标形状中存放某一概念的那一张表 |
| 通用键值行 | 一行以其中一列的值决定其余列的含义，因而列名本身不携带含义的形态 |
| 悬置 | 依据事实无法从当前代码判明，因而归属留待对应实施成果在其边界内裁定 |

## Observable Requirements

| ID | Requirement |
|---|---|
| RQ-001 | 改动前的每一张表在记录中恰有一条归属结论，取值为「并入某承载」「保持独立」「随其概念退役」「悬置」之一 |
| RQ-002 | 每一处把两张或更多表并入同一承载的结论，都给出三条判据各自如何成立的说明 |
| RQ-003 | 每一处概念相近而未并入同一承载的结论，都指出三条判据中具体哪一条不成立 |
| RQ-004 | 改动前的每一列在记录中恰有一条去向：在目标形状中的落点，或随表退役并注明它今天是否仍被生产代码读取 |
| RQ-005 | 邮件附件的归属有明确结论，并含三条判据的逐条判断 |
| RQ-006 | 金币上限的归属有明确结论，且记录由该结论给出物品与角色本体两块实施的先后 |
| RQ-007 | 记录给出目标形状：每一张目标表的名称与其列；每一列可回溯到改动前的来源，或标为新增并给出理由 |
| RQ-008 | 目标形状中没有一张表以通用键值行承载多个概念 |
| RQ-009 | 记录中每一条作为裁定依据的事实都注明其在当前代码中的可复核位置 |
| RQ-010 | 记录中的结论互不矛盾：同一张表不出现两处不同归属，同一列不出现两个落点 |
| RQ-011 | 每一处悬置都登记其依据事实为何无法从当前代码判明，以及该归属由哪一块实施成果在其边界内裁定 |

## Acceptance Scenarios

| ID | Covers | Given | When | Then |
|---|---|---|---|---|
| AC-001 | RQ-001 | 改动前的库形状声明列出其全部表 | 把记录中的表清单与该声明清点比对 | 两者一一对应，无遗漏、无多余，且每张表恰有一条归属结论 |
| AC-002 | RQ-002 | 记录中某处把多张表并入同一承载 | 读该处的判据说明 | 三条判据各有一句针对该处的成立说明，且所述键、生命周期与写入用例可在当前代码中找到 |
| AC-003 | RQ-003 | 记录中某两张表概念相近却分属不同承载 | 读该处说明 | 明确指出三条判据中哪一条不成立，以及不成立在何处 |
| AC-004 | RQ-004 | 改动前的库形状声明含固定数目的列 | 清点记录中的列去向条目 | 数目与之相符，且每一条随表退役的列都注明今天的读取状况 |
| AC-005 | RQ-005 | 邮件附件同时携带按件的内容与它在邮件中的位置 | 读记录中该处的裁定 | 给出并入或不并入的结论，并逐条说明三条判据的判断 |
| AC-006 | RQ-006 | 金币上限今天由物品侧读取而概念上属于角色 | 读记录中该处的裁定 | 给出归属结论，并据此写明物品与角色本体两块实施的先后及理由 |
| AC-007 | RQ-007 | 记录给出目标形状 | 在目标形状中任取一列 | 能读出它来自改动前的哪张表的哪一列，或读到它被标为新增并附理由 |
| AC-008 | RQ-008 | 目标形状的表清单 | 逐张检查其列名 | 没有一张表出现由某一列的值决定其余列含义的形态 |
| AC-009 | RQ-009 | 记录中任取一条依据事实 | 按其注明的位置到当前代码中查证 | 该位置确实存在且支持所述事实 |
| AC-010 | RQ-010 | 完整记录 | 交叉检查表归属与列落点 | 无一张表有两处归属，无一列有两个落点 |
| AC-011 | RQ-011 | 记录中存在一处悬置 | 读该处登记 | 写明依据事实为何无法从当前代码判明，以及由哪一块实施成果裁定 |

## Success Evidence

| ID | Requirements | Scenarios | Evidence class |
|---|---|---|---|
| EV-001 | RQ-001, RQ-004, RQ-010 | AC-001, AC-004, AC-010 | 清点结果：记录中的表数与列数同改动前的库形状声明相符，且交叉检查未发现重复或矛盾的归属 |
| EV-002 | RQ-002, RQ-003, RQ-005, RQ-006, RQ-011 | AC-002, AC-003, AC-005, AC-006, AC-011 | 判据说明与两处具名裁定的逐条可读性，及其所述事实在当前代码中的可查证性 |
| EV-003 | RQ-007, RQ-008 | AC-007, AC-008 | 目标形状的可清点性，以及逐表的列名独立性检查结果 |
| EV-004 | RQ-009 | AC-009 | 依据事实的可复核位置抽查结果 |

## Assumptions

- 裁定基于当前代码可复核的事实。若后续实施发现某条事实不成立，该处裁定由对应实施成果在其边界内修正并更新记录，不构成本 Spec 的失败。
- 目标是本机开发库，现有数据可直接丢弃，因此裁定不需要考虑既有行的可转换性。
