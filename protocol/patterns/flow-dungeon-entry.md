# 副本入场：一条通用流程，教程是它的第一个实例

从城里点开副本列表到人站进第一个房间，是**一条流程**，不是每种副本各有一条。教程副本走的
也是这一条——它只是被客户端自动触发的那个实例。

本页记录这条流程如何编排协议：谁触发、发多少帧、哪些字段在这条流程里被填成什么值、
以及流程今天断在哪。单条协议的字节结构见各自文档；帧头、CMD 两字节结果信封、CMD/NOTI
两张注册表、入站流与读取原语属于帧层，见 [game-frame](game-frame.md) 与
[game-receive](game-receive.md)，本页不复述。

进城本身在 [进入世界](world-entry.md) 收尾。本页从那一页的终点接手。

## 阶段一：客户端发的是一整个突发

### 五帧一口气发完，不等回应

在归档的 12 次连续会话里，凡是发 `0x000F` 的（8 次），
`0x000F` → `0x00C5` → `0x0010` → `0x008F` → `0x0252` **五帧之间没有任何一帧入站**。

这不是"入站队列刚好空着"：那一刻服务端早先发出的进城尾巴四帧
（`0x0002` / `0x0035` / `0x0111` / `0x0016`）还没被读到，它们在这五帧**之后**才出现在抓包里。
也就是说客户端**手上有未读数据，仍然把五帧全部发了出去**。

由此可以确定两件事：

- `0x0010` 的触发与 `0x000F` 的回应**无关**——它不是"收到 `0x000F` 的答复才发"，
  两条是同一个处理轮次里的产物。所以"补上 `0x000F` 的回帧，客户端才会去选副本"这种想法不成立；
- 中间还夹着一条 `0x00C5 SAVE_GAME_OPTION_1`，**`0x000F` 与 `0x0010` 在线上不是相邻的一对**。

> **观察与推论分开**：以上是抓包顺序的观察。它不能证明客户端"永远不等"——
> 只能证明在这条教程入场路径上不等。玩家手动点副本时是不是同一形状，**未解**：
> 我们至今没有一次玩家手动入场的抓包。

### 突发里只有 `0x0010` 没人接

| 客户端发的 | 我们的处理 |
|---|---|
| `0x000F` | 有 handler，推五条 NOTI（下一节） |
| `0x00C5` | 有 handler（`Game/SaveGameOption/SaveGameOption1Slice.cs`） |
| `0x0010` | **2026-08-17 当时没有 handler，没有 type 常量；后续已实现** |
| `0x008F` | 有 handler，消费后丢弃（`Game/TaggedIdReport/`），不回 ACK |
| `0x0252` | 有 handler（`Game/MapEntryReports/MapEntryReportSlices.cs:107`） |

`0x008F` 我们不回 ACK，客户端照样继续发 `0x0252`——**这条不需要响应**（实测）。
上游在这条路径上会回一个 CMD `0x008F` ACK（`DungeonTutorialHandler.cs:109-118`），
带上教程奖励物品清单；我们不发，因此也没有奖励发放。奖励属于业务设定，不在本页范围。

## 教程是这条流程的一个实例

### 判据一：同一角色，只改等级

归档抓包里有 8 次会话属于**同一个角色**（`0x0002` subtype 0 里 characterId=1、
job=0、growType=0，名字四字节 `00a1`），其中 4 次等级字节为 1，4 次为 10：

| 会话 | 等级 | 阶段一那五帧 | 阶段一之外还发了什么 |
|---:|---:|---|---|
| 2、3、4、9 | 1 | **全发** | — |
| 5、6、7、8 | 10 | **一帧都不发** | `0x01F8`×2、`0x00C2`、`0x00FA`、`0x0117`、CMD `0x0003` EXIT |

等级字节的位置由我们自己的编码器给出：subtype 0 的写入顺序是
`u8 subtype / u16 1 / u16 characterId / dstr 名字 / u8 job / u8 growType / u8 level`
（`StateSynchronizationPayloadCodec.Entry.cs:731-732`），四字节名字后第三个字节就是等级。

10 级那四次自己上报了加载耗时（`0x00FA`）并主动发起 EXIT，**客户端认为进城已经结束**。
1 级那四次没有这些，取而代之的是副本入场突发。

另外 4 次是别的角色（characterId=2 与 13，都是 1 级），同样全发——**等级为 1 就发，
与是哪个角色、哪个槽位无关**。

### 判据二：`0x008F` 的两个调用点

`0x008F CHANGE_TUTORIAL_FLAG` 在两个分支里都出现，但**不是同一处代码发的**。
抓包记录了发送栈（客户端 `F78F0AEA…`，栈值已归一化为 RVA）：

| 分支 | body | 栈（前四层） |
|---|---|---|
| 1 级，阶段一内 | `1E00000001`（flag 30） | `0x01C9007C` `0x01C1EE65` `0x00D8577A` `0x00D89CFC` |
| 10 级，会话末尾 | `1F00000001`（flag 31） | `0x01C9007C` `0x01C2064D` `0x01C20D1D` `0x008C626C` |

只有第一层（打包入口）相同，从第二层起完全分岔。10 级那条的第四层
`0x008C626C` 落在**为 S→C type `0x0003` 注册的 handler 内**（入口 `0x008C6260`，+0xC），
与 [`0x008F`](../game/client-to-server/0x008F.md) 记录的触发机制一致——它是处理 EXIT 响应时发的。

1 级那条的栈里**没有任何一个地址落在那个 handler 里**，而且它发出时
我们的 `0x0003 USER_STATE` 还没到（那一帧在它之后 9 帧才出现在抓包里）。
所以：**教程分支的 `0x008F` 不是 EXIT 触发的，是副本入场突发的一部分。**

> `0x0003` 是同号异义的典型：10 级分支里客户端收到的 1 字节 `0x0003` 是它自己 EXIT 的 CMD 响应，
> 1 级分支里收到的 4 字节 `0x0003` 是 NOTI `USER_STATE`。抓包对 S→C 的族不记录，
> 判族要靠读取跟踪的首读地址，见 [game-receive](game-receive.md#两张注册表--cmd-与-noti)。

### 判据三（较弱）：上游的分组

上游把 `0x000F`/`0x0010` 与 `DIE_MONSTER`/`GET_ITEM`/`MOVE_MAP`/`DROP_ITEM`/`SET_PLAY_RESULT`
注册在同一个 `RegisterDungeonHandlers` 里（`GameProtocolHandler.cs:577-621`），
说明在上游作者眼里它们是通用副本指令。

**但这条不能用来把教程和通用入场分开**：`0x008F CHANGE_TUTORIAL_FLAG`（:594）和
`0x01E4 TUTORIAL_LEVEL_UP`（:599）**也在同一个注册块里**。它们只是分派到另一个类
（`DungeonTutorialHandler`），注册表本身不分组。分开两者靠的是上面两条实测判据。

### 目标副本 id = 10000

`0x000F` 的 4 字节 body 与 `0x0010` 的 9 字节 body 里，副本 id 字段都被填成 **10000**
（样本 `../game/client-to-server/samples/0x000F-2026-08-17-01.hex`、`0x0010-2026-08-17-01.hex`），
在 8 次会话里**逐字节相同**：`10270000` 与 `102700000000000000`。
`0x0010` 的难度与两个深渊标志全为 0，尾部 u32 为 0（字段边界见
[`0x0010`](../game/client-to-server/0x0010.md)）。

**10000 就是 `Tutorial/Tutorial.dgn`**，探查产物已归档：
[pvf-dungeon-list-20260817](data/probes/pvf-dungeon-list-20260817.md)。
`dungeon.lst` 在 `Script.pvf` 内、不在文件系统上，所以该页记了读法、归档源的哈希与相关段落。

同表还显示 `10001`–`10004` 是按职业分化的教程副本（`atslayer` = 女鬼剑、`knight` = 骑士），
这一点尚无实机观察——本次样本的两个角色是职业 0 与职业 3。

不过**结论本来就不依赖这条引用**：等级判据加上同一突发里的 `CHANGE_TUTORIAL_FLAG`，
已经足以认定这是教程在自动送人进副本。

## 阶段二：`0x000F` 的下行五帧

### 五帧都投递到了客户端

[`DungeonSelectionSlice.cs:257-271`](../../Server/src/Dfo.Server.Protocol/Game/DungeonSelection/DungeonSelectionSlice.cs)
一次推五条。归档抓包记下了实现补齐的过程：

| 会话 | 客户端实际收到的 |
|---:|---|
| 0、1、4 | `0x0017` `0x0003` `0x001A` `0x001B`（四帧，还没有 `0x0002`） |
| 2、3 | `0x0017` `0x0003`（会话在这里断掉） |
| 9 | `0x0017` `0x0002` subtype 1 `0x0003`（第五帧加进来了，会话断掉） |
| **10、11** | **`0x0017` `0x0002` subtype 1 `0x0003` `0x001A` `0x001B` 五帧齐全** |

10 级那四次会话里，`0x0017` / `0x0002` subtype 1 / `0x001A` / `0x001B` **一条都没有**
——这五帧确实只由 `0x000F` 触发。那四次里出现的 `0x0003` 是 1 字节的 EXIT CMD 响应，
不是 4 字节的 `USER_STATE` NOTI（见上一节的同号异义提示）。

### 这些字段在这条流程里被填成什么

字段的存在属于协议文档；填成什么值是流程的事，所以记在这里：

| 帧 | 字段 | 这条流程里的值 | 依据 |
|---|---|---|---|
| `0x0017` | area | **`0xFF`**（不是角色真实 area） | 实测 body `020001FF...`；我们 `SelectionScreenAreaId`（:94）；上游 `DungeonEntryHandler.cs:63-65` |
| `0x0017` | town / x / y / dir / areaState | 沿用会话里已发布的出生点，不现编 | `DungeonSelectionSlice.cs:227` 取 `result.World.Channel.Spawn` |
| `0x0002` | subtype | 1（属性块），与进城批次里那一份**逐字节相同** | 抓包会话 10 与 11 各有两份 144 字节 body，两两比对完全相等；我们从已准备好的入场状态重建而不是重查库 |
| `0x0003` | UserState | **`0x01`** | 实测 body `01020001`；我们 :267；上游 `DungeonEntryHandler.cs:61` |
| `0x001A` | UDP 主机 | 单字节 `0x00` = 不可用 | 实测；我们 `EncodeUdpHostUnavailable` |
| `0x001B` | 绝望之塔层数 | **固定 1**（我们没有塔进度） | 我们 `DefaultTowerOfDespairFloor`（:97）；上游读 `TowerOfDespairProgress`，取不到时回落 1（`DungeonEntryHandler.cs:105-116`） |

`0x0002` 必须再发一遍：少了它角色进城后属性全为零。这一条的因果记在
[NOTI-0x0002](../game/server-to-client/NOTI-0x0002.md) 与 [world-entry](world-entry.md) 里。

### 不回 CMD `0x000F`

客户端为 `0x000F` 注册了 CMD 接收 handler（`RVA 0x008CFF30`），但成功路径上**不需要回**：
我们一帧 CMD 都没回，客户端收下五条 NOTI 并继续（实测，会话 10、11）。
上游同样只在错误分支回 CMD——佣兵内容被封禁时回一个错误码
（`DungeonEntryHandler.cs:36-47`、`:463-464`）。

### 上游还做了一件我们没做的事：记返回锚点

上游在 `0x000F` 里就把**出本要回到哪**记下来：town / area / x / y / dir / areaState，
其中 town/area/x/y 可被"副本门返回点"配置覆盖（`DungeonEntryHandler.cs:134-162`，
覆盖发生在 `:144-153`）。教程通关（flag 31）时靠它把人送回城
（`DungeonTutorialHandler.cs:121-151` → `ReturnToVillage`）。

**只有上游依据。** 我们不记锚点，也还没有出本流程，所以这条对我们今天没有可观察后果。

### `0x001B` 在读取跟踪里是空白

会话 11 的[读取跟踪](data/traces/read-trace-20260817-entry-batch.log)与抓包**逐帧对齐 73 帧、
顺序完全一致**，唯一的差别是抓包的第 74 帧 `0x001B`（19 字节）在跟踪里**没有任何记录**。

两种解释现有材料分不开：

1. 客户端的 `0x001B` handler 一个字节都没读——纯触发型 handler 是真实存在的一类
   （见 [game-receive](game-receive.md#入站流与读取原语sc-的取字段方式) 的抽样统计）；
2. `0x001B` 恰好是整次抓包的最后一帧，跟踪器的末条记录没落盘。

判别办法很便宜：**在 `0x001B` 之后再发一帧无关 NOTI**。如果 `0x001B` 的记录随之出现，
是落盘问题；如果仍然没有，那就是 handler 真的不读。

注意这里没有"客户端没收到"这个选项：抓包在 recv 侧记下了完整 19 字节，
且与我们编码器的输出逐字节相符。

| 3 | NOTI `0x001D` `START_MAP` | **真正把人放进第一个房间的那一帧**（:704-709 → `DungeonMapHandler.cs:575-580`，type 见 `PacketTypes.cs:36`） |
| 4 | NOTI `0x019F` | 助战标签；没有助战角色时发空 body（:715-721） |

**以下结论描述 2026-08-17 当时基线：这些当时全部只有上游依据（最低等级证据），一帧都没在
我们这边发过。** 后续 A21 已补齐并实机验证成功路径，见本页顶部状态说明。
客户端侧也给不出形状：`0x0010` 的 CMD 接收 handler（`RVA 0x008C56F0`）只读出 1 个 `u8`
就进跳转表，静态走图到此为止。

### 断点的后果

- **1 级新角色走不完新手教程。** 客户端把人往教程副本送，我们不回，迷宫运行从未开始。
- **`0x001D START_MAP` 从来没被发过**，因此"人怎么被放进房间"这一环在我们这里完全空白。
- 断点**不影响进城**：`0x0010` 未被应答时角色仍站在城里（记录见
  [`0x0010`](../game/client-to-server/0x0010.md)）。客户端此刻屏幕上显示什么——
  是停在选图界面、还是卡在加载——**未解**，没人记过。

### 抬等级是验证手段，不是修法

把角色等级抬过 1 级，客户端就不再触发教程，于是这条断点被绕开。
归档会话 5–8 就是这么做的。**它只让断点不发作，不让断点消失**：正常玩家点开副本一样会走
`0x000F`/`0x0010`。

这条绕法本身还有个副作用：`0x000F` 的五帧下行**也**不会被执行，
所以它和"验证那五帧"是互斥的——见[未解](#未解)第一条。

## 逆向工作日志

**2026-08-17 建页。** 本页的结论多数是从 [world-entry](world-entry.md) 那一页
"副本入场是另一条路"的判断里长出来的。逐条核实时推翻了两条已经写进仓库的判据，
并把第三条的适用范围收窄了：

1. **弯路：把"上游注册在同一组"当成教程与通用入场的分界。** 上一页写
   "`0x000F`/`0x0010` 不在教程那一组"，去核对注册表发现
   `CHANGE_TUTORIAL_FLAG` 与 `TUTORIAL_LEVEL_UP` **就在同一个 `RegisterDungeonHandlers` 块里**
   （只是分派到另一个类）。注册表根本不分组，这条判据不成立。
   真正把两者分开的是实测：等级差分，以及 `0x008F` 两条不同的发送栈。
   *教训*：引用上游的"分组"之前先打开那个块数一遍——分派目标不同不等于注册分组不同。
2. **弯路："客户端注册了 CMD 接收 handler，所以服务端必须回帧"。**
   这句话曾经是 [`0x000F`](../game/client-to-server/0x000F.md) 与
   [`0x0010`](../game/client-to-server/0x0010.md) 两页共同的推理起点，
   `0x000F` 那边已经被"不回 CMD 也进城了"证伪一次；`0x0010` 这边它以另一种形式还在：
   "我们一帧没回，客户端拿不到要加载的地图数据"读起来像是客户端在等。
   抓包证明它不在等——五帧一次发完，中间连一帧入站都没有，而且当时它手上还有没读完的数据。
   *教训*：注册了 handler 只说明"能接"，不说明"在等"。要判断在等什么，
   看它发下一帧之前**读到了**什么，而不是看它发了什么。
3. **`0x008F` 的触发机制此前只记了一条路。** [`0x008F`](../game/client-to-server/0x008F.md)
   写的"收到 S→C `0x0003` 时发出"在 10 级分支上完全正确（栈里那个
   `0x008C626C` 一字不差），但教程分支的同一条协议来自另一个调用点，且发出时
   `0x0003` 还没到。一条协议可以有多个触发点，**"这条协议什么时候发"要按分支分别记**。
   那一页的 `Expected response: None` 也是同理——它在"会话最后一帧"那条路径上成立，
   在教程突发里成立的理由不同（我们不回 ACK，客户端继续发下一帧）。
