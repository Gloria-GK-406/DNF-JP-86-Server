# 角色生命周期协议族

角色列表屏上的五条 CMD：两条查询和三条改动。它们共用一套回复约定、一份证据来源和
一个尚未消除的风险，因此共享部分写在这里，各协议自己的布局写在各自文档里。

| Type | 名称 | 方向 | 文档 |
|---:|---|---|---|
| `0x0286` | `CHARAC_VIEW_HIDDEN_CHARAC_INFO` | C→S + 同 type 响应 | [0x0286.md](../game/client-to-server/0x0286.md) |
| `0x01BA` | `MERCENARY_INFO` | C→S + 同 type 响应 | [0x01BA.md](../game/client-to-server/0x01BA.md) |
| `0x02B5` | `CHECK_DOUBLE_CHARACTER_NAME` | C→S + 同 type 响应 | [0x02B5.md](../game/client-to-server/0x02B5.md) |
| `0x0005` | `CREATE_CHARACTER` | C→S + 同 type 响应 | [0x0005.md](../game/client-to-server/0x0005.md) |
| `0x0006` | `DELETE_CHARACTER` | C→S + 同 type 响应 | [0x0006.md](../game/client-to-server/0x0006.md) |
| `0x0289` | 荣誉等级 | S→C NOTI | [0x0289.md](../game/server-to-client/0x0289.md) |

## 为什么请求和响应写在同一个文档里

[README](../README.md) 要求「同一 type 在另一方向出现时必须建独立文档」。这条规则针对的是
**两个含义无关的消息碰巧共用一个号**——`0x0002` 在两个方向上就是完全不同的东西。

本族五条是 CMD 请求／响应对：同一个 type，同一次交换的两半，语义不可分割。把响应拆到
`server-to-client/` 会让读者为了看懂一次交换必须开两个文件，恰好违反「查一条协议只需要打开
一个文件」。因此这里**请求与响应同页**，并在此说明理由，而不是默默地不一致。

NOTI `0x0289` 不属于这种情况——它没有对应请求，所以按常规单独建档。

## 回复约定，以及它自相矛盾的地方

四条协议的响应首字节是状态：

```text
01              成功
00 <errorCode>  失败，附原因码
<errorCode>     失败，裸码（仅 0x0005 的部分分支）
```

`0x0006` 删除**反过来**：成功是 `00` 后跟被删角色的 `u16` id，失败是**非零裸码**。

这不是转录失误。旧服就是这么写的，而且讲得通：客户端必须读出后面那个 id，`00` 在这里是
「后面有 id」的判别位，不是成功标志。但它确实与同族其他四条冲突，**我们没有实机证据能判定
哪一种是客户端真正的期望**。实现按观察到的旧服行为原样复现；若实机结果推翻它，
推翻的记录应写回本节而不是悄悄改代码。

已知原因码（全部来自旧服，无独立佐证）：

| 码 | 含义 | 出现于 |
|---:|---|---|
| `0x04` | 请求不合法／无空槽 | `0x0005` |
| `0x14` | 名字长度非法 | `0x02B5` |
| `0x18` | 名字已存在 | `0x02B5` `0x0005` |
| `0x15` | 确认名与槽位占用者不符 | `0x0006` |
| `0x02` | 请求不合法／槽位为空 | `0x0006` |
| `0x9F` | 名字含不可用文字 | `0x02B5` `0x0005` |

## 名字字段

三条改动类协议共用同一个字段编码：**LE `i32` 字节数 + 该长度的原始字节**。

长度是**字节数不是字符数**。七个 CJK 字符是 21 字节：能过 `0x02B5` 的 30 字节上限，
过不了 `0x0005` 的 18 字节上限。同一个名字合法地在一条协议上通过、在另一条上被拒，
这是旧服的既有行为，不是缺陷。

服务端**从不信任声明的长度**——先与实际 body 长度比较再切片。比较用减法而非加法：
`start + declaredLength` 在长度接近 `int.MaxValue` 时溢出为负，会让边界检查通过、切片抛异常。
这个溢出是本次实现中由测试抓出来的真实缺陷，修复见
[CharacterNameField.cs](../../Server/src/Dfo.Server.Protocol/Game/CharacterNameField.cs)。

名字在库里以 **blob** 为准（`name_bytes`），文本列 `name` 只供人工查库时辨认。
两串不同字节可以解码成同一段文本，用文本比较会让其中一串冒充另一串。

## 证据来源与其分量

本族**没有任何一条有实机抓包样本**。布局全部来自重构前最后一版旧服
（`d51e74b`，其后 `d98cec6` 建立清洁架构基线时整体删除）：

- `Server/DfoServer/Network/Handlers/CharacterSelectHandler.cs` — `0x0005` / `0x0006` / `0x02B5`
- `Server/DfoServer/Network/Handlers/MercenaryExpeditionHandler.cs` — `0x01BA`
- `Server/DfoServer/Network/Protocol/GameProtocolHandler.cs:404-418, 787-789` — 分发注册

**旧服只是参考，不是真理。** 能为它背书的只有一条经验事实：那个服务端当年确实能建角色。
凡是能独立佐证的地方都做了佐证，佐证不了的地方在下面「未解问题」里列明。

独立佐证（客户端普查表
[server-to-client-handlers.tsv](data/server-to-client-handlers.tsv)）：五条 CMD
在客户端**都注册了接收 handler**，说明客户端确实等这些响应。

| Type | client handler | 注册点 | 是否读 body |
|---:|---|---|---|
| `0x0286` | `0x008CBBB0` | `0x008D08C1` | 读 `ReadU8` |
| `0x0286` | `0x0091ABE0` | `0x0093107F`（另一注册表） | 读 `ReadU32` |
| `0x01BA` | `0x008C6240` | `0x008D055B` | 读 `ReadU8` |
| `0x0005` | `0x008CB460` | `0x008D04DC` | **测不出**（见下） |
| `0x02B5` | `0x008C5E30` | `0x008D04EF` | **测不出**（见下） |

`0x0005` 与 `0x02B5` 的可达性扫描（[readreach.py](data/readreach.py)，深度 6）**结论不可用**：
分别走了 499 和 222 个函数，各有 26 / 15 个调用进入打包区。同批次的正对照
（LOGIN `0x008C7E20`）正常命中 `ReadU8`，所以扫描器本身没坏，是这两棵子树太深太黑。
**这两条的响应格式没有指令级证据，只有旧服行为。**

客户端绑定：SHA-256 `F78F0AEA5137DF06B63ED0F7470B66F3A24D061B69D4DA13758E65574A7FC04C`。

## 最大的风险：非空角色列表

建角色一旦成功，服务端补发 NOTI `0x0002` 整份角色列表——而**至今抓到的每一份角色列表都是
空名单**。[AccountCharacterRosterPayloadCodec](../../Server/src/Dfo.Server.Protocol/Game/AccountRoster/AccountCharacterRosterPayloadCodec.cs)
里的 per-character 编码路径，尤其 `WriteRosterTail` 末尾硬编码的
`03 00 00 04 00 00 00 00`，是从旧服搬来的字面量，**从未被客户端解析过一次**。

这是本批改动里唯一无法靠静态分析降低的风险：第一次成功建角色就会走这条路径。
若客户端在建成后显示异常或崩溃，**先怀疑这里**，而不是怀疑 `0x0005` 本身。

## 顺带解决的旧悬案：seq 4 与 seq 6

[catalog](../catalog.md) 长期记录着一条无法解释的现象：五次会话的发送 seq 恒为
`0…3, 5, 7, 8`，**seq 4 和 seq 6 从来没被抓到过**。当时只能归因于抓包引擎挂在
`Cipher::Encrypt` 上、不走加密路径的发送必然漏掉，并明确写下「**不能**断言客户端只发了这些帧」。

2026-08-16 给服务端补上「未识别入站帧」日志后，这两帧当场现形：

```text
seq=4  type=0x0286  body(0B)
seq=6  type=0x01BA  body(0B)
seq=7  type=0x0002  body(31B)
```

客户端侧仍只记到 `0,1,2,3,5`，两边拼起来正好连续 `0–7`。

**方法上的结论比结论本身更值钱**：客户端抓包和服务端入站日志的盲区不重叠。抓包漏掉不走加密
路径的发送，服务端日志则记录一切实际到达的字节。只有两者合起来，「客户端什么都没发」才是可以
下的判断；单靠任何一个都不行。

## 逆向工作日志

**1. 同一个数字在两个枚举里含义不同，先分表再谈语义。**
`0x01BA` 在 `NotiPacketType` 里是 `GROWTH_WEAPON_EVENT_INFO`，在 `CmdPacketType` 里是
`MERCENARY_INFO`；`0x0286` 分别是 `DAILY_CHALLENGE` 和 `CHARAC_VIEW_HIDDEN_CHARAC_INFO`。
最初据此推测这两条是建角色的前置，**推错了**——`0x01BA` 是佣兵远征，跟建角色无关。
先确认 selector 落在哪张表，再谈这个号是什么意思。

**2. 「点了没反应」不等于「客户端没发」，除非两个仪器都看过。**
抓包为空只能说明没走加密路径。是服务端日志证明了 seq 7 之后一个字节都没到，
这个否证才成立。

**3. 真正的门闩不在已逆完的协议里。**
之前完整逆向的七条设置类协议一条都不是路障；卡住建角色的是两个此前完全没留意的空请求。
从普查表里挑协议永远挑不到它们——只有顺着游戏进程走才会撞上。
