# 角色生命周期协议族

角色列表屏上的五条 CMD：两条查询和三条改动。它们共用一套回复约定、一份证据来源和
一个尚未消除的风险，因此共享部分写在这里，各协议自己的布局写在各自文档里。

| Type | 名称 | 方向 | 文档 |
|---:|---|---|---|
| `0x0286` | `CHARAC_VIEW_HIDDEN_CHARAC_INFO` | C→S + 同 type 响应 | [0x0286.md](../game/client-to-server/0x0286.md) |
| `0x01BA` | `MERCENARY_INFO` | C→S + 同 type 响应 | [0x01BA.md](../game/client-to-server/0x01BA.md) |
| `0x02B5` | `CHECK_DOUBLE_CHARACTER_NAME` | C→S + 同 type 响应 | [0x02B5.md](../game/client-to-server/0x02B5.md) |
| `0x0005` | `CREATE_CHARACTER` | C→S + 同 type 响应 | [0x0005.md](../game/client-to-server/0x0005.md) |
| `0x0006` | `DELETE_CHARACTER` | C→S + 同 type 响应 | [0x0006.md](../game/client-to-server/0x0006.md) |
| `0x0289` | 荣誉等级 | S→C NOTI | [0x0289.md](../game/server-to-client/0x0289.md) |

## 为什么请求和响应写在同一个文档里

[README](../README.md) 要求「同一 type 在另一方向出现时必须建独立文档」。这条规则针对的是
**两个含义无关的消息碰巧共用一个号**——`0x0002` 在两个方向上就是完全不同的东西。

本族五条是 CMD 请求／响应对：同一个 type，同一次交换的两半，语义不可分割。把响应拆到
`server-to-client/` 会让读者为了看懂一次交换必须开两个文件，恰好违反「查一条协议只需要打开
一个文件」。因此这里**请求与响应同页**，并在此说明理由，而不是默默地不一致。

NOTI `0x0289` 不属于这种情况——它没有对应请求，所以按常规单独建档。

## 两字节结果信封

本族的响应**没有各自的状态字节**。首字节属于全体 CMD 共有的结果信封，由客户端接收函数在
分发之前读掉，handler 根本看不到它——机制、指令与来源见
[game-receive 的两字节结果信封](game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)。

```text
CMD body = u8 ok                ; 非 0 = 成功
         + u8 reason            ; 仅当 ok == 0 才存在
         + <该 type 自己的载荷>  ; 只有成功路径读得到
```

于是本族四条的完整形状是：

| 协议 | 成功 | 拒绝 |
|---|---|---|
| `0x02B5` 查名 | `01` | `00 <reason>` |
| `0x0005` 创建 | `01` | `00 <reason>` |
| `0x0006` 删除 | `01` + `u8` 标志 + `u16` **请求下标回显** | `00 <reason>` |
| `0x0004` 选人 | `01` + 载荷 | `00 <reason>` |

### 这条误读造成的四个缺陷（2026-08-16 定位并修复）

此前把首字节当成"每条消息各自的状态"，旧服也是这么写的。四处后果，严重程度递减：

| 位置 | 原样 | 客户端实际读到 | 症状 |
|---|---|---|---|
| `0x0006` 成功 | `00` + `u16` id | ok=0 → **失败**，id 低字节当 reason | 无提示、不移除，而服务端已删——[实测三次复现](../game/client-to-server/0x0006.md) |
| `0x0006` 成功（同上修复后） | `01 00` + `u16` **角色 id** | id 被当**列表下标**用 | 删掉了下一个角色；重登才看出删对了人 |
| `0x0006` 拒绝 | `<code>` + `0000` | 非 0 → **成功**，去读没发的载荷 | 行为未定义 |
| `0x0005` 无空槽 | `04` 裸码 | 非 0 → **成功** | 客户端为不存在的角色跑完创建后流程 |
| `0x0003` 退出失败 | `00` 裸码 | 第二个 `ReadU8` **吃掉下一帧首字节** | 此后每帧错位 |

`0x02B5` 查名是唯一原本就正确的一条，纯属旧服的状态约定与信封巧合一致。

### 原因码

reason 由**各 type 的 handler** 逐个 `cmp` 匹配，表外的值静默丢弃。下表的"客户端已确认"
列指该码在对应 handler 的比较链里确有分支：

| 码 | 含义 | 出现于 | 客户端已确认 |
|---:|---|---|---|
| `0x02` | 请求不合法／槽位为空 | `0x0006` `0x0005` | 是 |
| `0x04` | 请求不合法／无空槽 | `0x0005` | 是（提示串 `0x2AA`） |
| `0x14` | 名字长度非法 | `0x02B5` | 未查 |
| `0x15` | 确认名与槽位占用者不符 | `0x0006` | 是 |
| `0x18` | 名字已存在 | `0x02B5` `0x0005` | 是 |
| `0x9F` | 名字含不可用文字 | `0x02B5` `0x0005` | 是 |

`0x0006` handler 另有 `0x13` `0x16` `0x24` `0x28` `0x76` `0x9C` 六个分支，
`0x0005` 另有 `0x12` `0x13` `0x16` `0x17`；服务端目前都不会发出。

## 名字字段

三条改动类协议共用同一个字段编码：**LE `i32` 字节数 + 该长度的原始字节**。

长度是**字节数不是字符数**。七个 CJK 字符是 21 字节：能过 `0x02B5` 的 30 字节上限，
过不了 `0x0005` 的 18 字节上限。同一个名字合法地在一条协议上通过、在另一条上被拒，
这是旧服的既有行为，不是缺陷。

服务端**从不信任声明的长度**——先与实际 body 长度比较再切片。比较用减法而非加法：
`start + declaredLength` 在长度接近 `int.MaxValue` 时溢出为负，会让边界检查通过、切片抛异常。
这个溢出是本次实现中由测试抓出来的真实缺陷，修复见
[CharacterNameField.cs](../../Server/src/Dfo.Server.Protocol/Game/CharacterNameField.cs)。

名字在库里以 **blob** 为准（`name_bytes`），文本列 `name` 只供人工查库时辨认。
两串不同字节可以解码成同一段文本，用文本比较会让其中一串冒充另一串。

## 证据来源与其分量

本族**没有任何一条有实机抓包样本**。布局全部来自重构前最后一版旧服
（`d51e74b`，其后 `d98cec6` 建立清洁架构基线时整体删除）：

- `Server/DfoServer/Network/Handlers/CharacterSelectHandler.cs` — `0x0005` / `0x0006` / `0x02B5`
- `Server/DfoServer/Network/Handlers/MercenaryExpeditionHandler.cs` — `0x01BA`
- `Server/DfoServer/Network/Protocol/GameProtocolHandler.cs:404-418, 787-789` — 分发注册

**旧服只是参考，不是真理。** 能为它背书的只有一条经验事实：那个服务端当年确实能建角色。
凡是能独立佐证的地方都做了佐证，佐证不了的地方在下面「未解问题」里列明。

独立佐证（客户端普查表
[server-to-client-handlers.tsv](data/server-to-client-handlers.tsv)）：五条 CMD
在客户端**都注册了接收 handler**，说明客户端确实等这些响应。

| Type | client handler | 注册点 | 是否读 body |
|---:|---|---|---|
| `0x0286` | `0x008CBBB0` | `0x008D08C1` | 读 `ReadU8` |
| `0x0286` | `0x0091ABE0` | `0x0093107F`（另一注册表） | 读 `ReadU32` |
| `0x01BA` | `0x008C6240` | `0x008D055B` | 读 `ReadU8` |
| `0x0005` | `0x008CB460` | `0x008D04DC` | **测不出**（见下） |
| `0x02B5` | `0x008C5E30` | `0x008D04EF` | **测不出**（见下） |

`0x0005` 与 `0x02B5` 的可达性扫描（[readreach.py](data/readreach.py)，深度 6）**结论不可用**：
分别走了 499 和 222 个函数，各有 26 / 15 个调用进入打包区。同批次的正对照
（LOGIN `0x008C7E20`）正常命中 `ReadU8`，所以扫描器本身没坏，是这两棵子树太深太黑。
**这两条的响应格式没有指令级证据，只有旧服行为。**

客户端绑定：SHA-256 `F78F0AEA5137DF06B63ED0F7470B66F3A24D061B69D4DA13758E65574A7FC04C`。

## 曾经的最大风险：非空角色列表（**已大幅降低**）

建角色一旦成功，服务端补发 NOTI `0x0002` 整份角色列表——而在 2026-08-16 之前，
**抓到的每一份角色列表都是空名单**，per-character 编码路径从未被客户端解析过一次。

2026-08-16 把上游服务端跑起来，实机建出了三个角色（job 11 / 1 / 2），客户端**正常显示了它们**。
随后把两边的编码逐字段对了一遍，结论是 **byte-for-byte 相同**：

| 偏移 | 我们 | 上游 `AccountCharacterListBodyBuilder` |
|---|---|---|
| per-character 头 13 字节 | `u16 slot` + dstr 名字 + `00 00` + job + growType + level | 同 |
| 荣誉三项 | `u32 0` `u32 0` `u16 0` | `WriteHonorRosterFields` 同序同宽 |
| 外观 | `u8 0`（无条目） | `u8 count` + 条目 |
| 尾部 32 字节 | `WriteRosterTail` | `UserInfoType2RosterTailBuilder.Write` |

那串曾被记为"来历不明的字面量"`00 00 00 03 00 00 04 00 00 00 00`，在上游是有名字的字段：

```text
00 00 00   tail_flag21 / tail_flag22 / tail_byte23
03         display_state_bits   ← 上游注释：客户端按 bit0/bit1/bit3 消费
00 00      tail_flag25 / tail_byte26
04         tail_byte27          ← 上游注释：保留样本中的非零值
00 00 00 00 tail_flag28..31
```

所以它不再是"抄来的魔法数"，而是**与一份实机验证过的参照实现完全一致**的编码。

**2026-08-16 已闭合**：本服务端建出了 job 11 的 `aa03`，客户端正常显示。
仍保留一处余量：我们的外观条目恒为 0 条，上游会写真实条目；有外观数据的角色走的是没走过的分支。

## 顺带解决的旧悬案：seq 4 与 seq 6

[catalog](../catalog.md) 长期记录着一条无法解释的现象：五次会话的发送 seq 恒为
`0…3, 5, 7, 8`，**seq 4 和 seq 6 从来没被抓到过**。当时只能归因于抓包引擎挂在
`Cipher::Encrypt` 上、不走加密路径的发送必然漏掉，并明确写下「**不能**断言客户端只发了这些帧」。

2026-08-16 给服务端补上「未识别入站帧」日志后，这两帧当场现形：

```text
seq=4  type=0x0286  body(0B)
seq=6  type=0x01BA  body(0B)
seq=7  type=0x0002  body(31B)
```

客户端侧仍只记到 `0,1,2,3,5`，两边拼起来正好连续 `0–7`。

**方法上的结论比结论本身更值钱**：客户端抓包和服务端入站日志的盲区不重叠。抓包漏掉不走加密
路径的发送，服务端日志则记录一切实际到达的字节。只有两者合起来，「客户端什么都没发」才是可以
下的判断；单靠任何一个都不行。

## 曾以为是「部分职业无法创建」——实为客户端光标 bug

2026-08-16 一度记录：job **11 / 1 / 2** 能建出来，job **0 / 7** 点击后客户端一个字节都不发。
当时的结论是「客户端对部分职业拒绝构包，原因未知」。

**那个结论是错的。**真正的原因是确认对话框上**客户端光标焦点与渲染不同步**：焦点已经移到
「创建角色」，画面却仍把光标画在「是」上，点击因此落空。稍等一下、或把鼠标挪回去，
任何职业都能建出来。

写入追踪（`ISocket::Write`，加密之前）证实了这一点：`0x0005` 全程**只被构建过 4 次，
4 次全部成功**，不存在「构建了却没发」的帧。失败的尝试连构包器都没进——因为点击根本没生效。

同一个 bug 也解释了此前记的「有时能有时不能」和「每次会话只成功一次」。

**方法上的教训**：服务端往返实测 0.4–0.9 ms，这个数一条命令就能量，却是最后才量的。
把单次采样的形状当成规律、再据此改协议（帧头路由字节那一轮），是本次最大的弯路。
**症状归因到协议之前，先量一次延迟、先确认现象可复现。**

## 逆向工作日志

**1. 同一个数字在两个枚举里含义不同，先分表再谈语义。**
`0x01BA` 在 `NotiPacketType` 里是 `GROWTH_WEAPON_EVENT_INFO`，在 `CmdPacketType` 里是
`MERCENARY_INFO`；`0x0286` 分别是 `DAILY_CHALLENGE` 和 `CHARAC_VIEW_HIDDEN_CHARAC_INFO`。
最初据此推测这两条是建角色的前置，**推错了**——`0x01BA` 是佣兵远征，跟建角色无关。
先确认 selector 落在哪张表，再谈这个号是什么意思。

**2. 「点了没反应」不等于「客户端没发」，除非两个仪器都看过。**
抓包为空只能说明没走加密路径。是服务端日志证明了 seq 7 之后一个字节都没到，
这个否证才成立。

**3. 真正的门闩不在已逆完的协议里，也不在本族里。**
之前完整逆向的七条设置类协议一条都不是路障；本族这五条答上之后，建角色 UI **依然打不开**。

真正的门闩是**登录阶段少发了两个包**：`NOTI 0x00AD`（游戏选项）和 `NOTI 0x01C7`（热键）。
旧服在 LOGIN 响应之后立刻下发，我们只在选角色批次里发——而角色列表屏根本走不到选角色。
详见 [设置类协议族的下发时机](game-settings.md#下发时机分歧已判定旧服是对的)。

讽刺的是，这条分歧早就记在文档里了，当时的结论是「证据不足，只记录不改」。那个决定是对的：
硬猜的话，猜中也是运气。

**4. 一份能跑的参照实现，抵得上一堆静态推断。**
卡了两轮的问题——先怀疑服务端、再怀疑客户端补丁、还查了脱壳重建——都没定论。
真正解决它的是**把已知能工作的上游服务端跑起来**，用同一个客户端连过去做对照：
UI 打开了，差异立刻收敛到登录阶段那两个包。

排除法本身也有价值：上游 `Patch/86JP.cpp` 里**一个建角色钩子都没有**（S4A12 分叉才加的），
这直接排掉了"需要客户端补丁"这条线，把注意力逼回服务端。
