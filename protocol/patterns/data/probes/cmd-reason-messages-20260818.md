## 结论：失败码是有文案的，且分两层

[game-receive](../../game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有) 已经记下
「每条 type 的 handler 拿 reason 跟一张固定表逐个 `cmp`，表外的值静默返回」。
本次把那张表的**另一半**读了出来：每个 `cmp` 分支后面跟的立即数是**文案 id**，
经 `GetString`（RVA `0x01DF5AE0`）取出一句话，再交给 UI 显示。

所以 reason **不是**「客户端只知道成功/失败」，它逐码对应一句给玩家看的话。
而且是两层叠加：

```text
失败分发 = 本 type 自己的 cmp 链（各 type 各一份，可能什么都不显示）
         + 共用兜底表 0x01B897C0（无条件调用，全客户端 80 个调用点共享）
```

两层的码集合在 `0x002C` / `0x0013` 上**不相交**，所以不会一次弹两句。

## `dstr.dat` 是个纯资源 DLL，解密只有三行

`dstr.dat` 是一个只有 `.rdata` + `.rsrc` 的 PE。资源类型 `256` 下有三个条目：

| 资源 id | 语言 | 条目数 |
|---:|---|---:|
| 102 | 简体中文 | 13,640 |
| 104 | 日文 | 14,038 |
| 106 | 韩文 | 12,583 |

加载器 `RVA 0x01DF5940`：`GetModuleFileName` → 取目录 → 拼 `dstr.dat` →
`LoadLibraryEx(..., LOAD_LIBRARY_AS_DATAFILE)` → 按标志 `[VA 0x0442B714]`
选 `0x66`(102) 或 `0x6A`(106)。标志默认 0（dump 里该页为 BSS，取不到运行时值），
**本次未确定实机显示哪一份**；三份的 id 语义一致，不影响下面的结论。

每个条目是 `"SC01" + u32 明文长度 + 密文`。解密在 `RVA 0x0215DBE5`，按 dword 链式异或：

```text
key = 0x5819AF17
for each dword c:  p = c ^ key;  key ^= p     // 等价于 key_i = c_{i-1}
```

明文是 **UTF-8 文本**，每行 `<id>>正文`。复现脚本三十行即可，不需要客户端在跑。

「系统提示」= `call 0x0189CFB0` 模板 `0x1BB`；「日志」= `call 0x01CF9800`，只落文件不上屏。

| 码 | 文案 id | 通道 | 简体中文文案 |
|---:|---:|---|---|

**19 和 23 是同一句话**，区别只是 19 多写一行日志。要一句"这东西不能这么搬"时用 23 更干净。

**两条与既有记录冲突，以客户端为准**：

- `0x02` **不在表内**，客户端一个字都不显示。
  [`0x0013`](../../../game/client-to-server/0x0013.md#应答同-type-的-cmd-ack) 记的
  "`0x02` = 操作不允许"是上游的命名，客户端侧无对应文案。
- `0x04` 客户端说的是**槽位/空间不足**，不是"服务端拒绝"。拿它兜"无租约、源不存在"，
  玩家会看到一句与真实原因无关的"金库空间不足"。

### 按拒绝原因选码

只有下面三个码在移动语义上说的是真话，其余十二个各有各的专属场景（装备、交易、地区），
挪作他用就是给玩家一句假话。**没有诚实文案时，静默优于错话**——静默的表现是拖了没反应，
和丢包一样，但至少没有误导。

| 服务端的拒绝原因 | 建议码 | 理由 |
|---|---|---|
| 请求指名一个本服不提供的 list（时装/仓库/装备/宠物/骑士盾） | `23` | 「无法移动该物品」，JP 明写"不可移动类型"——操作不可用，说法成立 |
| 物品不能占用目标槽（kind 的区间不对） | `23` | 同上，这正是该句的本义 |
| 合并会撑破堆叠上限 | `17` **或静默** | 「物品栏已有同类物品」JP 是"存在相同堆叠上限的物品"，方向对但说得拐弯；不接受这层拐弯就静默 |
| 交换时被顶出的物品不能占用腾出的槽 | `23` | 同上 |
| 两个槽都是空的 | **静默** | 表里没有对应文案。这是客户端与服务端认知不一致，不是玩家能理解的事 |
| 读与写之间槽位变了 | **静默** | 表里没有"请重试"这类文案。硬套 `4` 会说成"空间不足" |
| 无会话 / 角色没有绑定容器（服务端自身故障） | **静默** | 玩家没有做错任何事，任何一句现成文案都是甩锅 |

`4` 留给真正的**目标容器没有空位**：那句话本来就是这个意思，别的地方不要用。
`8`（职业不符）/`14`（等级不够）/`7`（补正等级）是**穿戴**路径的诚实文案——
等本服开始服务 Equipment list 时它们才有用武之地，现在用不上。

## 共用兜底表 `RVA 0x01B897C0`

两个 handler 在各自的 `cmp` 链走完后都会**无条件**调一次它，参数是同一个 reason。
全 `.text` 有 **80 个调用点**，几乎全部落在 CMD handler 区（`0x008C…`–`0x008E…`），
所以这张表是**跨 type 共享**的：

| 码 | 简体中文文案（截断） |
|---:|---|
| 77 | 无法与加入黑名单的角色进行聊天。 |
| 105 | 为了保护您的帐号安全，登录 %u 秒后才可以交易。 |
| 114 | 正处于限制交易状态， 系统将取消相关请求。 |
| 115 | 对方正处于限制交易状态， 无法进行物品交易 |
| 122 / 136 | 固定模板 `0x117`（不取文案库） |
| 123 / 228 | 另走分支，不显示文案库文本 |
| 134 / 137 | 因需要二级密码认证， 此次操作被取消， 请重新操作 |
| 208 | 休眠帐号限制交易与技能学习…… |
| 210 | 您的帐户现在处于安全模式中，不能进行任何的交易、丢弃等敏感操作。 |
| 214 | 在物品已锁定状态下， 您无法进行当前操作。 |
| 229 | 固定模板 `0x158` |
| 230 | 您目前处于限制交易状态， 无法使用该功能。 |
| 237 / 239 | 密保卡相关（CN 文案本身是未完成的占位文本） |

**含义：reason 的取值空间是全局的，不是每条 type 自己的枚举。** 这批码全部是账号安全/
交易限制类，任何 type 回这些值都会得到同一句话——所以服务端给某条协议自定义错误码时，
不能占用这张表里的值。

## 对服务端的直接指导

1. **"能不能用"这类查询值得回带原因的类型，而不是布尔。** `0x002C` 上客户端能把
   职业不符（8）、等级不够（14）、当前不能用（19）、非消耗品（23）、疲劳值不足（95）
   分别说清楚，回一个笼统的 23 等于把这些信息全丢掉。
2. **冷却与场所没有专属码。** `[cool time]` / `[action usable place]`
   （见 [pvf-item-use-taxonomy](pvf-item-use-taxonomy-20260818.md)）在客户端失败表里
   没有对应文案，最接近的是 19「目前无法使用物品」。所以四类拒绝理由里，
   **冷却和场所会合并成同一句**，不必为它们各设一个码。
3. **表外的码 = 静默。** 玩家看到的和丢包一样：数量不减、无提示。
   调试时这会被误判成"服务端没回"。

## 边界

- 未做实机验证：本条全部来自静态反汇编 + 文案库解密，没有真的让服务端回一个错误码去看屏幕。
  要提高置信度，最省的做法是在实机上对同一次喝药分别回 8 / 14 / 19 / 23 / 17，各截一次图。
- 未确定客户端实际选 102（中文）还是 106（韩文）文案表；上表用的是 102。
- `0x0013` 的码 1 在中文表里是占位符 `dnf_31628`、日文表是空串，等于**显示一句空话**。
- 显示函数 `0x0189CFB0` 落在加壳区，只读到入口跳转，未展开其内部；把它归为"玩家可见"
  依据的是调用形态（模板 id + 文案指针）与颜色/种类参数，不是它的函数体。
