## `0x000C` direct 实帧

body（12 字节）：

```text
01 01 02 00 00 00 00 05 00 02 00 00
```

规范解释：

| Offset | 值 | 解释 |
|---:|---:|---|
| 0 | `01` | 信息/标题控制字节；本次非零。 |
| 1 | `01` | 后续由 S2C parser 保存到队伍对象 `+0x52` 的控制标志。 |
| 2 | `02` | 容量 2。 |
| 3..6 | `00 00 00 00` | 未解释，原样保存。 |
| 7 | `05` | 未解释，原样保存。 |
| 8 | `00` | 未解释，原样保存。 |
| 9 | `02` | Normal。 |
| 10..11 | `00 00` | `ModeTargetRaw=0`。 |

此帧来自**已有两人队伍的设置编辑**，证明 12 字节 direct 是 wire 形状而不是“仅 create”场景标签。
本次 body 不含 raw-dstr 长度或 UTF-8 标题字节；用户所见名字若变化，只能来自控制/预设索引的本地解析，
不能声称服务端收到了自定义标题文本。`16+n` inline-title 形状仍只有当前客户端静态构包证据与上游样本，
本次不升级为 `ClientVerified`。

定向中转没有观察到同 type 的 S2C CMD response。客户端成功结果由随后主动推送的 NOTI `0x0009`
表达；这只确认本次路径“没有回包”，不能排除拒绝分支在其他条件下使用 CMD response。

## `NOTI 0x0009 type=1` 实帧

两端收到相同 body（18 字节）：

```text
01 00 01 00 01 01 01 02 00 00 00 00 05 00 02 00 00 00
```

```text
u16 blockCount = 1
u16 partyId    = 1
u8  type       = 1
u8  info0      = 1
u8  info1      = 1
u8  capacity   = 2
u32 unknown    = 0
u8  unknown7   = 5
u8  unknown8   = 0
u8  category   = 2 (Normal)
u16 target     = 0
u8  hasExtra   = 0
```

信息块逐字节回显了 C2S 规范设置；`info0!=0`，所以没有条件 raw-dstr。两端各一份、同 party id、同
snapshot，且 type 1 没有名册块，确认当前 encoder/audience/长度边界可被 A21 消费。

## “赛丽亚 Bonus”图标差分

邀请接受时 type-0 refresh 的初始规范设置为：

```text
00 00 04 00 00 00 00 05 00 02 FF FF
```

编辑后规范设置为：

```text
01 01 02 00 00 00 00 05 00 02 00 00
```

用户报告修改后立即出现“赛丽亚 Bonus”标志，修改前没有。当前 parser 在
`VA 0x01172177..0x0117225E` 读取 `info1` 并写到队伍对象 `+0x52`；队伍 UI 在
`VA 0x0240DE79`、`0x0240DFE7`、`0x0240E03E` 等位置直接比较该字段是否为 0。结合旧符号来源对该字段
的 `IsReturnUserParty` 命名与 dstr `429>受赛丽亚祝福的队伍`，**High** 判断本次从 0 变 1 的
`info1` 是图标开关；运行时“该帧后出现图标”本身为 Confirmed。

此图标只证明客户端队伍 UI 的标志投影。当次服务端没有因它计算或发放额外经验，因此不得把本次结果
描述为“赛丽亚祝福奖励已实现”。初始值 0 是服务端自动建队时的保守合成默认；客户端设置 UI 随后提交
真实值 1，当时服务端无损保存并回显，解释了前后差异。

### 后续产品决策（同日）

用户在看到该差分后明确要求暂不实现回归玩家相关玩法，所有队伍一律视为非回归玩家。现行实现因此把
C2S `[1]` 作为兼容输入，在领域写入前由 `IPartyModeRuleService` 强制规范化为 `0`，后续 type-0/type-1
也只发送 `0`；其余 11 字节保持不变。本节原始请求、通知与 UI 观察是决策前的历史事实，样本不改写。

## 同会话范围外观察

用户随后依次尝试委任队长与强制踢出，Host 记录 C2S `0x0079 body=01`、`0x000E body=01`，两条均为
`Unhandled`。操作顺序只能给出“`0x0079` 高度对应委任、`0x000E` 高度对应踢出”的运行时关联，尚未
完成各自静态布局确认；服务端没有执行这两个动作，也没有产生新的设置 revision。

这段是 2026-09-12 当时的历史状态。两条命令的成功路径已于 2026-09-19 闭环，见
[`a21-party-leadership-removal-live-20260919.md`](a21-party-leadership-removal-live-20260919.md)。

## 状态与剩余缺口

- `0x000C` direct 12 字节已有当前 A21 `ClientVerified` 编辑样本；inline-title `16+n` 仍为 High。
- `NOTI 0x0009 type=1` 的 18 字节非零 `info0` 分支已有当前 A21 双端 `ClientVerified`。
- type-0 65 字节创建投影与 `0x0099 → 0x000B → 0x0009` 顺序已被两端消费，但本次队伍由邀请接受时
  服务端自动创建，没有“无队状态 C2S `0x000C` 建队”实帧。
- 非队长设置 UI 是否可达、拒绝时是否存在 CMD response，以及 type-1 `info0==0` 的 22 字节分支仍未
  实机归因；自动化拒绝/字节测试不能冒充这些手工结论。
