# A21 新手副本清房与过图

**2026-08-26。** 判据有三层，和起始装备那次一样：

1. **对照会话。** 同一台机器、同一个脱壳客户端，先跑本仓、再跑上游 `ServerS4A21`，两边都建
   **职业 0 鬼剑士**进副本 **10000**。上游能打、能放技能；本仓不能。所以不是客户端。
   上游那次的抓包在 `ServerS4A21/Server/DfoServer/bin/Debug/packet_log.txt`，
   8/22 那份魔枪士的参照已改名为 `packet_log.reference-20260823.txt`。
2. **上游源码。** `DungeonNotificationBuilder`、`DieMonsterRequest`、`ExpNotificationBuilder`、
   `DungeonActorTemplateProjector`。
3. **档案。** 房间的 `.map` 与 AI 角色的 `.aic`。

---

## 一、`START_MAP` 的 actor 表（这次的主因）

上游同一间房 61000 发 65 字节、`actorCount = 2`；本仓发 23 字节、`actorCount = 0`。
除计数和随机种子外其余每个字节相同。

**客户端只跟服务端登记过的 actor 交互。** 计数为 0 时它照样从自己那份地图数据把怪画出来，
但那是布景：玩家穿得过去、刀砍得过去，对方也不还手。用户实测症状即"能走能挥刀，攻击不和
怪物交互，怪物也不和角色交互，技能全灰"。

布局与来源见 [NOTI-0x001D](../../../game/server-to-client/NOTI-0x001D.md) 的 A21 节。

### 为什么 66 帧对账没发现

`EncodeStartMap` 的注释写着这是有意留空的，等"帧的形状被证明是对的"再填。形状确实被证明了，
然后这条就一直留着——因为**用来证明的那次会话根本没有怪**。参照角色是魔枪士，副本 10005，
`Tutorial_Demonic/tutorial(0,1)_start.map` 整张图没有 `[monster]` 段。空表与它逐字节相同。

## 二、`DIE_MONSTER` 回路

客户端自己判定战斗。它发 `CMD 0x0026 USE_SKILL`（服务端**不回**），然后发
`CMD 0x0027 DIE_MONSTER`，服务端回两帧：

```
C->S CMD  0x0027  (66~76B)  u16 actor序号, u16 击杀者, ...
S->C NOTI 0x0025  (83B)     EXP
S->C NOTI 0x0026  (7B)      u16 actor序号, u8 掉落条数=0, 00 00 FF 00
```

上游实测：`4B 00 00 00 02 00 ...` → 回 `4B 00 00 00 00 FF 00`。

`NOTI 0x0025 EXP` 是定长 83 字节，偏移取自上游构包器。上游那次实际只有四个字段非零：
等级 1、总经验 1、荣誉等级 1，其余（组队、疲劳、赛丽亚祝福、成长契约、网吧、精英击杀、
成长胶囊、频道、公会）都是 0——每一条都是客户端经验弹窗里的一行，也都是一条本仓没有的奖励规则。

**本仓这一击不给经验。** 发的是角色当前的等级与总经验，这一帧因此是"报告"而不是"发放"。
发放需要经验表、升级路径和落库，是另一件事；先把交互闭合、把数字留诚实。

## 三、过图

`CMD 0x002D MOVE_MAP` 的前两字节就是目标格。参照的两次是 `01 01` 和 `02 01`，
对应 (1,1) 和 (2,1)。本仓的解码器读的正是这两字节，原本就对。

服务端回下一间房的 `NOTI 0x001D START_MAP`，客户端随即 `FINISH_LOADING`。

## 四、actor 运行序号必须分段

**这是本次自查出来的一个真缺陷。** 序号是客户端事后指认 actor 的名字（`DIE_MONSTER` 回的
就是它）。A21 每房从 1..60000 随机取起点，沿用旧服 `get_rand_int(60000)`，注释写明目的是
避免快速退本重进时与客户端手里残留的 identity 撞号。

本仓改为从本局种子推导以省掉计数器。**第一版推导是错的**：

```
first = 1 + ((seed * 397) ^ mapId) % 60000
```

副本的房间地图号是连续的，于是相邻房间落在相邻起点——实测第一间房拿到 30946/30947，
第二间房从 30945 起，两段重叠。客户端手里还留着上一间已死的 30946，新房间又把 30946 当成
活怪发过来。

改为两轮乘加移位混合之后：

| 地图 | 序号段 |
|---:|---|
| 61000 | 58209, 58210 |
| 61001 | 31793 … 31796 |
| 61002 | 9933 … 9937 |
| 61005 | 12244 … 12247 |

## 五、整条路的线级验证

`clearprobe.py` 按 (0,1) → (1,1) → (2,1) → (2,0) 走完，每间房把服务端声明的怪全部上报死亡：

```
room 61000  2 actors   怪 61670 + 阿甘左 461(APC, 等级 80, 类型 5)
room 61001  4 actors   61670, 61359, 61670, 61359
room 61002  5 actors   61356 ×5
room 61005  4 actors   62527(Boss), 61357, 61360, 61361
序号段无重叠；连接始终存活；服务端日志零 warn 零 fail
```

每只怪的 `DIE_MONSTER` 都收到 `EXP` + 确认，每次 `MOVE_MAP` 都收到下一间房的 `START_MAP`，
每次 `FINISH_LOADING` 都收到 `NOTI 0x001E`。

**这证明的是服务端答了什么，不是客户端接受什么。** 后者要一次真实会话。

## 六、卡在第二间房：预生成掉落块

**同日实机。** 用户在第二间房 61001 清空 4 只怪之后卡住：客户端连发两次
`CMD 0x00BF 00 02`（剧情暂停开始），**再没发过 `01 02`（结束）**，此后只剩心跳，连接不断。

`START_MAP` 里 actor 表之后那个 `u8` 不是填充，是**房间可破坏物所含物品的条数**，本仓发 0。

61001 的地图声明着一个装道具的箱子：

```
[special passive object]
37183 736 219 0 1 [item] 0 1 -1 -1 -1
```

教学在"打破箱子拿道具"这一步等一件永远不会出现的物品。

**反证很干净：** 魔枪士副本 10005 的前两间房**不声明**可破坏物，上游那两帧就是 23 字节零掉落，
客户端照样走过去了；它的第三间房 61032 声明了，上游那帧就带 1 条
（`objIndex=0 ground=1 item=14400 耐久=25`），而该角色此后确实把护肩 14400 穿在了 15 号槽上。

内容由两处声明合成：房间 `.map` 的 `[special passive object]` 给出组号，副本 `.dgn` 的
`[special passive object item]` 按组给出物品。**组可以声明 0 条**（新手副本第三组写作 `2 -1 0`），
所以那一串必须按计数读而不是按固定步长切。布局见
[NOTI-0x001D](../../../game/server-to-client/NOTI-0x001D.md) 的第二则 A21 补记。

改完之后本仓 61001 发 126 字节、1 条掉落、`item=14400 耐久=25`——与参照在另一个副本经各自的表
取到的是同一件物品。

## 七、捡起来

**同日实机，第二堵墙。** 箱子破了、护肩落地了，人物站在上面按拾取键：客户端发
`CMD 0x002B GET_ITEM` 18 字节，服务端此前没有这一 type，什么也没回，物品原地不动。

```text
#212  C->S CMD 0x002B (18B)  01 00 00 00 e0 02 d5 00 c6 7a f4 02 c8 00 57 24 15 50
（此后只剩心跳）
```

请求里只有前两字节被读：`01 00` 就是服务端自己在 `START_MAP` 里给这件物品编的号。回答是两帧，
`CMD 0x002B` 的 `01` 加 `NOTI 0x0027`，布局见
[0x002B](../../../game/client-to-server/0x002B.md) 与
[NOTI-0x0027](../../../game/server-to-client/NOTI-0x0027.md) 的 A21 节。

### 地上的东西记在哪

房间地上有什么是每次描述房间时重新从档案里读出来的——这是本仓与上游的一处结构差异，上游把掉落
登记在 `run.Drops` 字典里、按一个整局递增的 `SceneSlot` 编号。本仓的号改为**房间内按声明顺序从
1 数**，因此是可推导的：同一间房被重新描述时，同一件东西还叫同一个名字。

代价是必须记住哪一号已经被拿走，否则走出房间再走回来就能把箱子再捡一遍。运行状态里因此多了一
个 `(格子, 号)` 的集合。**剔除发生在编号之后**：拿走第二件不会让第三件改名。

### 线级验证

`pickprobe.py` 走到 (1,1)、清掉 4 只怪、按房间自己报的号拾取：

```text
C->S CMD  0x002B (18B)  ground=1
S->C CMD  0x002B (1B)   01
S->C NOTI 0x0027 (18B)  01 00 01 00 01 00000000 00000000 01 00 09 00 00
再发一次同一号  -> 无回应，连接存活
发一个不存在的号 -> 无回应，连接存活
```

库里那行：`list_type=0 slot=9 kind=1 itemId=14400 value=512242377 durability=25`。
`value` 与 `START_MAP` 掉落记录 +7 处发出去的实例值是同一个数，`durability` 与 +11 处一致。
