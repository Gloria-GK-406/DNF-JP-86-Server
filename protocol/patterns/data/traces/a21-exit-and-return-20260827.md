# A21 退出游戏卡住:退出协议是对的,连接早就没了(2026-08-27)

**症状(玩家报告)。** 鬼剑士教学全程通过——第二间房上路有怪、装备打完才爆、通关回城都正常——
**最后按退出游戏,卡住。** 玩家的判断是"这个协议还没做"。

**结论:退出协议做了,而且和上游逐字节一致。真正断的地方在回城之后、退出之前。**

## 一、上游怎么处理退出的

`CMD 0x0003` 在 A21 的表里叫 `EXIT`。上游 `GameProtocolHandler.RegisterMiscHandlers` 里就一行:

```csharp
d[0x0003] = (s, h, b) =>
    s.SendPacketAsync(GamePacketEnvelopeBuilder.Build(0x01, 0x0003, CommonPacketBodyBuilder.BuildSuccessAck()));
```

**回一个字节的成功,别的什么都不做。** 不落库、不断连接、不推任何投影。上游抓包对得上:

```text
RECV cmd=0x01 type=0x0003 len=15 body=(1B) [00]
SEND cmd=0x01 type=0x0003 len=16 body=(1B) [01]
RECV cmd=0x01 type=0x02B3 STATICS_RUNTIME_TING     ← 之后客户端自己收尾
```

本仓的 `GameExitHandler` 走的是同一条:`GameProtocol.ExitType` 已注册解码器、处理器与编码器,
答 `GameCmdEnvelope.Accept()`,也就是 `[01]`。**这一段本来就是通的。**

## 二、连接是在哪一帧上断的

把两边回城之后的那一段并排看:

| | 上游 2026-08-27 | 本仓同日 |
|---|---|---|
| `CMD 0x02EF` FPS_PERFORMANCE_STATISTIC (424B) | 收下,不回 | 收下,记 `Unhandled`,不回 |
| `CMD 0x00C2` CLIENT_SPEC_PROFILE (**362B**) | 收下,不回 | **解码器抛异常** |
| `CMD 0x045C` FRAMELAG_PER_DUNGEON | 收到 | — |
| `CMD 0x00FA` LODING_TIME_REPORT | 收到 | — |
| `CMD 0x0117` LAG_STATISTICS | 收到 | — |
| `CMD 0x0003` EXIT | 收到,回 `[01]` | — |
| `CMD 0x02B3` STATICS_RUNTIME_TING | 收到 | — |

**本仓的日志在 `0x00C2` 那一行之后再没有任何一帧。** 不是客户端不发——上游同一位置收到了后面
五帧——是连接已经在 `0x00C2` 上被拆掉了。玩家此后做的每一件事,包括按退出,都是在对一个已经关掉
的 socket 说话。

## 三、`0x00C2` 为什么抛

A21 的包头是 **25 字节**,A12 是 24。多出来的一字节在偏移 15,把它后面的每个字段都推后一位。
本仓按 A12 的算法算出体长 361,收到 362,判长度不符抛异常。

判据、字节表和"那一字节是什么不知道"的记录,写在
[`CMD 0x00C2`](../../../game/client-to-server/0x00C2.md) 的 A21 节。核心一句:同一台机器的两份样本
里,偏移 15 之后按 A12 位置读全是噪声,往后挪一字节 DirectX 变回 9.0.0、两个计时变回 -1、
336 字节的表从跨字段变成规整的「计数 + 时长」对。

## 四、这是同一个坑的第二次

第一次是 2026-08-25 的 `CHANGE_TUTORIAL_FLAG`:A21 六字节、本仓要五字节,于是每次进教学都以
"客户端报连接丢失、服务端什么也没记"收场。那次改的是**把抛异常的解码器也记进日志**。

这次日志确实记下来了——定位只花了几分钟,而不是一周。**但掉线那一半没动**:
`NetworkPlugins.Decode` 捕获异常、记 Error、然后 `throw;`,连接随之断开。

于是一帧**上游都不回的纯遥测上报**,把整局玩崩了。分帧是信封层做的,能走到 `Decode` 说明帧本身
已经读对;`Decode` 里抛出的一定是"体内布局与我们的模型不符",而不是"流失步"。这两件事的严重
程度不一样,现在按一件处理。取舍与三个可选项记在
`Docs/ProtocolScaffoldDissonances.md` 二十一,**没有在本次改动里动它**。

## 五、改了什么

- `ClientSpecProfilePayloadCodec` 包头 24 → 25,偏移 15 起的字段整体后移一位;新增的那一字节
  按原样读出并记进日志(`off15=`),而不是跳过。
- 回归样本换成 A21 那帧**完整 362 字节(含表)**,不再是只填包头的构造体。表是钉住偏移的关键:
  读错一字节,行就会跨在自己的字段上。

## 五之二、线级验证

单测证的是编解码读得对，证不了管线：派发登记、不回包、以及**连接是否还在**——最后这条正是
出事的那一半。所以补了两条对照，都打在跑着的服务端上（`127.0.0.1:10011`，直连裸 socket）：

| 送什么 | 观察 |
|---|---|
| 捕获的那帧**原样 362 字节** | 被接受，**0 帧回应**（与上游一致）；随后 `CMD 0x04DD` 得到 1 字节回应——**连接存活** |
| 同一帧截成 **361 字节**（A12 长度） | **连接当场中止** |

**一处要说明的：游戏端口在连上的瞬间会主动推一帧**（`NOTI 0x0001`，68 字节），两次都收到。
它不是这一帧的回应——探针先把它收干净再发 `0x00C2`，上表的"0 帧回应"才是干净的。第一版探针
没分开，把这一帧误算成了回应。

第二行是**有意保留**的行为：2026-08-27 决定暂时维持全敏度，等协议覆盖度上来再按类型分级
（见 `Docs/ProtocolScaffoldDissonances.md` 二十一）。所以"读得懂的放行、读不懂的照断"就是
现在期望的行为，这两行把它钉住了。

### 整串重放（这才是对得上玩家症状的那一条）

单帧对照证明不了"退出这条路通了"——路上有七帧。把上游捕获的**七个 body 原样、按原顺序**打进
跑着的服务端：

```text
greeting on connect: ['0x0001']

0x02EF FPS_PERFORMANCE_STATISTIC   424B -> no answer            [alive]
0x00C2 CLIENT_SPEC_PROFILE         362B -> no answer            [alive]
0x045C FRAMELAG_PER_DUNGEON         21B -> no answer            [alive]
0x00FA LODING_TIME_REPORT           56B -> no answer            [alive]
0x0117 LAG_STATISTICS               61B -> no answer            [alive]
0x0003 EXIT                          1B -> [('0x0003', '01')]   [alive]
0x02B3 STATICS_RUNTIME_TING          1B -> no answer            [alive]

follow-up 0x04DD -> [('0x04DD', '01')]  [ALIVE]
```

**七帧全部被接受，只有 `EXIT` 有回应，且回的正是上游那一个字节 `01`；结束时连接仍然活着。**
与上游同段抓包逐帧同形。玩家那次卡在第二帧上，现在七帧都过得去。

探针是一次性工具，没有入库；重跑只要把这七个 body 各包进一个 14 字节 A21 入站 header
（校验和字段本服务端不校验，填零即可）送到游戏端口，最后补一帧 `CMD 0x04DD` 看回不回。
body 取自 `ServerS4A21/Server/DfoServer/bin/Debug/packet_log.upstream-tutorial-20260827.txt`。

## 五之三、同一段里还有第二颗雷：`CMD 0x00FA`

把捕获的整串按顺序重放，**`0x00C2` 修好之后连接仍然会断，只是晚一帧**：

```text
0x02EF FPS_PERFORMANCE_STATISTIC    alive
0x00C2 CLIENT_SPEC_PROFILE          alive        ← 本次修好的
0x045C FRAMELAG_PER_DUNGEON         alive
0x00FA LODING_TIME_REPORT           *** 断连
```

`0x00FA` 有结构化解码器且校验长度，而它**从来没被真实的 A21 体检验过**——上一次实机在
`0x00C2` 就已经死了，这一帧根本没走到。

原因和 `0x00C2` 同类：**A21 比 A12 多一段**。均值段是 `{u16 tag, u32 mean}`，A12 写七段
（tag 0..6），A21 写八段，第八段的 tag 是**立即数 9**，并且排在两个计数段之前：

```text
00 00 | 00000000     01 00 | 00000000     02 00 | 00000000     03 00 | 00000000
04 00 | 6E010000     05 00 | 00000000     06 00 | 00000000     09 00 | 16EE0000
07 00 | 0000         08 00 | 0000                     8×6 + 4 + 4 = 56
```

本仓读到偏移 42 期望 tag 7、实得 tag 9，抛异常。改成八段之后整串走通：

```text
0x02EF alive   0x00C2 alive   0x045C alive   0x00FA alive   0x0117 alive
EXIT  ->  cls=0x01 type=0x0003 body=01        ← 与上游逐字节相同
after EXIT: alive
```

探针是 `scratchpad/exitprobe.py`，体全部取自参照抓包而不是构造——构造的体只能证明我们的解码器
同意我们自己的猜测。

**这颗雷是"保持全敏度"这个决定直接换来的**：真机上它会表现成"退出又卡住了"，再花掉一次实机
会话才定位。用捕获的字节离线重放，几分钟就找到了。

## 六、还没做的

| type | 上游 | 本仓（改完之后） |
|---|---|---|
| `CMD 0x001F` ACCEPT_QUEST | **回 `01 F8 03 01 00 00 00 00`** | **未实现，仍记 `Unhandled`** |
| `CMD 0x02EF` FPS_PERFORMANCE_STATISTIC | 不注册、不回 | 已登记为有意不回 |
| `CMD 0x045C` FRAMELAG_PER_DUNGEON | 不注册、不回 | 已登记为有意不回 |
| `CMD 0x00FA` LODING_TIME_REPORT | 不注册、不回 | 早已不回；这次把读法从 A12 的 50 字节改成 A21 的 56 |
| `CMD 0x0117` LAG_STATISTICS | 不注册、不回 | 已登记为有意不回 |
| `CMD 0x02B3` STATICS_RUNTIME_TING | 不注册、不回 | 早已不回；1 字节，A21 上没变 |

**这一串里只剩 `0x001F` 是真缺口**，需要任务写入路径。其余六条上游一个都不回，本仓现在也都是
"有意不回"而不是躺在 `Unhandled` 里——一个没实现的洞和一个照着上游不回的决定，在线上长得一模
一样，混在同一条告警里会把真洞埋掉。

## 七、这条路上的下一颗雷:`CMD 0x00FA` 也是错的

`0x00FA` 本仓早就答成"不回"了,所以看起来没问题——**但它的读法是 A12 的**:七个均值、体长 50。
A21 是**八个均值、体长 56**,多出来的一段 tag 是立即数 9,而且排在两个计数段之前。按 A12 读会
在第 7 段抛"tag 9 出现在应为 tag 7 的位置",于是又是一次拆连接。

**它这次没炸,只是因为 `0x00C2` 在它前面先炸了,它压根没到达。** 字节表见
[`CMD 0x00FA`](../../../game/client-to-server/0x00FA.md) 的 A21 节。

*教训*:一个类型"已经登记、已经答成不回"不等于它读得对。这一串退出上报里,已登记的两条
(`0x00FA`/`0x02B3`)当时都没有拿 A21 的真实字节复核过。
