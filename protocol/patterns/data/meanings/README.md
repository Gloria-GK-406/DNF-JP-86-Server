# 字段含义分片

本目录存放**字段可能含义**的数据分片。生成器在产出协议文档时把它们合并进机器区。

含义写在这里而不是直接写进协议文档，有两个原因：文档的机器区每次重新生成都会整体覆盖，
写在文档里会丢；而分片是生成器的**输入**，因此重新生成反而会把它带上。同时每个工作包
独占一个分片文件，多个富化任务可以并行写入而不冲突。

## 格式

TSV，六列，首行为表头：

```text
family	type	offset	meaning	confidence	source
```

| 列 | 含义 |
|---|---|
| `family` | `CMD` 或 `NOTI` |
| `type` | `0x00AB` 形式，四位大写十六进制 |
| `offset` | 顶层字段写十进制字节偏移（`12`）；**重复组内字段写 `gN:偏移`**（`g1:0` = 第 1 个重复组内偏移 0）。组内偏移从 0 重新计数，不加 `gN:` 前缀会与同号的顶层字段撞成同一个键，一条含义会被同时贴到两个不相干的字段上 |
| `meaning` | 该字段可能是什么。**只写有依据的**；没有依据就不要写这一行 |
| `confidence` | `Confirmed` / `High` / `Hypothesis` 三者之一 |
| `source` | 依据出处，精确到文件与行，例如 `上游 PartyHandler.cs:88 读 body[0] 作 slotIndex` |

不写的行等于保留 `unknown`。**留空比猜错便宜得多**——这批文档的用途是让后续实机开发
少猜，一个错误的含义会把人引向错误的实现，比一个诚实的 `unknown` 有害。

## 证据等级怎么定

| 等级 | 什么情况下用 |
|---|---|
| `Confirmed` | 上游代码在**同一 offset、同一宽度**上直接读写该字段，且字段名自解释 |
| `High` | 上游语义明确，但 offset 或宽度需要一步推导（例如上游按结构体读，顺序可逐一对上） |
| `Hypothesis` | 只有名称、注释或上下文暗示，没有逐字段的解析代码 |

**上游代码给"叫什么"，不给"为什么"。** 它的注释里关于客户端行为的断言（"客户端会……"）
一律不能当作证据——本资料库已经有过一次教训：注释声称客户端消费某个包的 body，实测证明
那个 handler 根本不读 body。只有**解析代码本身**才是字段含义的证据。

## 边界

- 提取状态为 `结构未知` 的协议**没有字段表**，不要为它们编造 offset。
- 不要修改协议文档、索引、提取器或其他分片；每个工作包只写自己那一个 `.tsv`。
- offset 必须落在该协议已提取的字段边界上。校验器会拒绝对不上的行。
