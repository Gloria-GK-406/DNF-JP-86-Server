# A21 装备分解流程

状态：**系统分解与便携分解的客户端可见成功流程已通过 A21 实机验收**。请求字段、便携工具槽和
providerId 有客户端静态/实帧证据；成功 S2C body 未归档，逐字段布局仍按各协议页的证据等级。

## 协议编排

```text
C2S CMD 0x001A DISJOINT_ITEM
  -> 解码目标槽、物品空间、分解工具槽、providerId
  -> 服务端验证当前会话、目标装备、NPC 或便携工具与 PVF 规则
  -> 同一事务结算装备、工具、角色材料与账号材料
  -> 仅最后一台便携机耗尽时：先发工具槽 NOTI 0x000E 清空
  -> S2C CMD 0x001A success：本次分解结果
  -> S2C NOTI 0x000E：其余变化槽位与虚拟材料的最终绝对状态

换角色重新入场
  -> S2C NOTI 0x000D：从账号材料真源投影 354..364
```

请求体与模式分流见 [`CMD 0x001A`](../game/client-to-server/0x001A.md)。便携模式由工具槽中的
服务端真实物品决定，providerId 为 0；NPC 模式的 providerId 是服务提供者 NPC index。批量 UI
不发送批量协议，而是逐件重复 `0x001A`，每帧独立结算。

## 权威状态与事务

服务端从 PVF 读取分解资格和产物规则；客户端不决定奖励种类或数量。结算先完成全部校验和落点
规划，再在一次事务中提交：

1. 删除目标装备；
2. 便携模式扣除一台分解机；
3. 普通材料与宇宙灵魂写入角色材料栏；
4. 六种晶体与五种品级灵魂写入账号材料袋。

任何一步失败都不发送成功结果，且上述状态整体回滚。账号材料的领域所有权与固定槽映射见
[账号材料袋模型](../../Document/AccountMaterialBag.md)。

## 回复与刷新职责

- `CMD 0x001A` 成功应答描述**本次产量**，供原生分解结果 UI 使用。
- [`NOTI 0x000E`](../game/server-to-client/NOTI-0x000E.md) 描述事务提交后的**最终绝对状态**：
  源装备槽、便携工具槽、角色材料槽以及账号虚拟材料槽。
- 换角色时，[`NOTI 0x000D`](../game/server-to-client/NOTI-0x000D.md) 从同一账号记录重建
  `354..359` 六种晶体与 `360..364` 五种品级灵魂。

ACK 不是背包最终状态的替代品：首次实机测试已经证明只发 ACK 时，服务器落库成功但客户端仍
保留旧显示；补齐绝对状态通知后问题消失。

2026-10-01 的耗尽工具修复有一个顺序例外：A21 在成功 ACK 末尾检查便携模式的工具引用与数量，
无工具时关闭窗口。因此仅耗尽工具的清空通知提前到 ACK 之前，不重复发送；源装备与产物仍在
ACK 之后刷新，避免干扰 ACK 自己的目标删除与材料增量。该分支为 ClientStatic，修改后的立即关窗
仍是 HumanPending，定位与检查见 [H13记录](../../Document/Verification/H13-portable-disjoint-20261001.md)。

## A21 实机证据边界

2026-09-20，用户在合并后的主干 Release 上完成修复后测试：分解结果符合预期，当前角色的材料
显示正确；切换同一账号的另一个角色后，晶体与五种品级灵魂余额保持一致。这证明成功流程、
运行时刷新和重新入场投影在客户端可见结果上闭合。

本次没有归档修复后的 S2C 抓包或运行时读取跟踪。因此：

- 不能把 `0x001A` 成功 ACK 或这一次 `0x000E` 的具体 body 标为 `WireCaptured`；
- 未观察的拒绝码、特殊装备、玩家分解师 `0x00EB` 与勇者装备分解机 `0x0455` 不随本次验收升级。
