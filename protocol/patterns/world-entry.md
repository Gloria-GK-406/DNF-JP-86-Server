# 进入世界：阶段、闸点与"不能多"

选角色到站在城里，是一条由**若干阶段**串起来的流程。每个阶段有一组**确定的**下行帧，
阶段之间由信号隔开。搞错这个结构，客户端不会报错，它会**崩溃**——而且崩在离原因很远的地方。

本页记录该结构本身。单条协议的字段与样本见各自文档。

## 阶段一：选角色 → 进入世界

```text
C→S  CMD  0x0004  SELECT_CHARACTER
S→C  CMD  0x0004  响应（带两字节结果信封）
S→C  NOTI ×N      角色的全部状态：装备、技能、任务、称号、收集箱、日程……
S→C  NOTI 0x007C  ENTER_GAMEWORLD_COMPLETE   ← 阶段闸点，body 长度 0
S→C  NOTI ×4      0x0002 / 0x0035 / 0x0111 / 0x0016
```

### 闸点是 NOTI，不是 CMD

`0x007C` = `ENTER_GAMEWORLD_COMPLETE`，**body 长度为零**，客户端 handler 在 `RVA 0x0093B150`。

它零长度这一点是关键：**它不是数据，是纯信号**。下面会说到 NOTI 可以缺，而缺了数据帧客户端有
默认值兜底；缺了这一条，客户端的状态机就永远不跳。

> **两个观测陷阱。**
>
> 一、`0x007C` 在客户端抓包里**永远看不见**——`clienthack-frame-capture.log` 不记录零长度
> body 的帧（`0x003F CERA` 处首次发现）。在只有抓包的情况下找这个闸点是找不到的。
> 服务端侧的逐帧日志才能看见它。
>
> 二、闸点**不是最后一帧**。服务端在它之后还接着发四条。
>
> 但"这四条属于阶段一集合"是错的说法（2026-08-17 修正）。抓包证明客户端**一读到 `0x007C`
> 就立刻转状态并发出下一批 CMD**，那四条是它**已经进入下一阶段之后**才从缓冲区里读到的。
> 服务端的发送顺序和客户端的处理顺序在这里分岔了。

### 为什么"多发"致命——机制不是位置，是状态

上一条那个分岔正是"多发会崩"的原因：闸点之后到达的任何东西，落在一个**已经换了状态**的客户端上。

那四条（`0x0002`/`0x0035`/`0x0111`/`0x0016`）能活下来，不是因为它们"属于阶段一集合"，
而是因为它们**在新状态下恰好也合法**。被抑制的那七组不合法，于是杀掉了客户端。

所以判断一帧能不能放在闸点后面，问的不是"它在序列里的位置"，而是"客户端在新状态下接不接受它"。

### 集合"可以少，不能多"

| 方向 | 后果 | 证据 |
|---|---|---|
| **少发** | 无害 | 角色无宠物，序列末尾的 `0x0077 PET_WELCOME` 整条跳过，客户端照常进城 |
| **多发** | **崩溃** | 在闸点之后追加 7 组帧，客户端读完就死；移除后当场进城 |

多发的那 7 组是：pre-publication 五条（含一份**账号角色名单** `0x0002` subtype 2）、库存增量、
PvP、装备锁快照、任务进度、宠物复活、副本重入。它们在参照实现的进场序列里**一条都没有**。

那份角色名单尤其典型——它在选人界面完全合法，在客户端已经进城时到达就不是了。

## 闸点之后：进城已经完成了

**2026-08-17 重写。此前这一节叫"阶段二：进入房间"，把 `0x000F`/`0x0010` 当成进城的必经握手。
错的。** 那两条是**通用的副本入场指令对**，普通角色进城根本不发。

判据来自两次实机对比，同一个角色只改等级：

| 角色等级 | 闸点之后客户端发的 |
|---|---|
| 1 级 | `0x000F` → `0x00C5` → `0x0010` → `0x008F CHANGE_TUTORIAL_FLAG` → `0x0252` |
| 10 级 | `0x01F8`、`0x0252`、`0x00C2`/`0x0117` 卡顿统计、`0x00FA LODING_TIME_REPORT` |

10 级那次**一条 `0x000F` 都没有**，而且它自己上报了"加载耗时"——客户端认为进城已经结束。
1 级那次之所以发，是因为**新手教程把角色自动送进教程副本**，走的正是副本入场那条路。
逐帧证据与更严格的等级差分见 [flow-dungeon-entry](flow-dungeon-entry.md)。

> **零长度帧只有服务端看得见。** 同一次会话里客户端还发了 `0x004F CALL_MEMER_LIST` 与
> `0x0078 REQUEST_BLACKLIST`，两者 **body 都是 0 字节**，因此在客户端抓包里完全不存在
> （同 `0x007C` 隐形的原因，见上文观测陷阱一）。它们只出现在服务端逐帧日志的
> `Unhandled Game frame` 行里，而且 `Game:01`/`02`/`03` 三次会话都有——**没有做过等级差分，
> 所以不能说它们是 10 级特有的**，只能说进城后会发。

所以：**进城的终点就是闸点加那四条**。`0x000F` 之后的东西属于
[副本入场](flow-dungeon-entry.md)，是另一条路。

### 名字的读法

`ENTER_SELECT_DUNGEON` 不是"进入(游戏) + 选副本"，是 `ENTER` + `SELECT_DUNGEON`——
**进入"选副本"这个状态**。城镇本身就是选图界面，所以打开副本列表时才发它。
配对的 `0x0010 SELECT_DUNGEON` 才是"选定并开跑"。顺序没有反。

## 副本入场：`0x000F` + `0x0010`

只在真要进副本时走这条路（1 级角色被教程自动触发也算）。上游的形状：

```text
C→S  CMD  0x000F  ENTER_SELECT_DUNGEON   body = u32 目标副本 id
S→C  NOTI 0x0017  USER_AREA（area 改写为 0xFF）
S→C  NOTI 0x0002  subtype 1 —— 属性块，再发一遍
S→C  NOTI 0x0003  USER_STATE（先置 UserState = 0x01）
S→C  NOTI 0x001A  UDP 主机（不可用）
S→C  NOTI 0x001B  ENTER_SELECT_DUNGEON 状态（带绝望之塔层数）
                  + 账号经验进度
C→S  CMD  0x0010  SELECT_DUNGEON         body 9B，布局已闭合 ← 我们完全没处理
```

`0x000F` **没有 CMD 响应**——客户端为它注册了 CMD 接收 handler，但参照实现在成功路径上
只推 NOTI，CMD 仅用于错误分支（佣兵被拦）。

我们的实现补齐了那五条 NOTI，但**至今没有被实机执行过**：验证时用的是 10 级角色，
它不发 `0x000F`。所以这五条的形状仍然只有参照实现作依据。

`0x0010` 的实现面比看起来大得多。上游成功路径：解析（副本 id / 难度 / 深渊标志）→ 绝望之塔入口
改写 → 载入进行中与已通关任务 → 入场资格评估 → `BeginRun` → 选迷宫、随机 boss 位置、随机出生点、
解析起始房间 map id → 然后才发 `0x001C DungeonInfo`、选择态、**`SendStartMapAsync` 把人放进第一个
房间**、`0x019F` 助战标签。另外 `0x000F` 里还要记一个**返回锚点**（town/area/x/y）供出本时用。

## 顺序：段内无序，段间有序

参照实现把整条进场序列写成一张**有序模板表**（`NewCharacterInitSequence`，53 条），
每条带 `Command` 字段。其中只有两条 CMD：

| 位置 | 帧 |
|---:|---|
| 0 | `cmd=01 type=0x0004` |
| 1–34 | 连续 34 条 NOTI，中间没有任何 CMD |
| 35 | `cmd=01 type=0x0312` |
| 36–52 | 连续 17 条 NOTI，以 `0x0077` 收尾 |

所以 **NOTI 之间不需要被 CMD 分隔**，一口气连发几十条是正常的。CMD 在这里不是分隔符，
而是"这一条本身需要结果信封"的协议（见
[CMD body 的两字节结果信封](game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)）。

## 服务端实现

[`SelectCharacterHandler`](../../Server/src/Dfo.Server.Protocol/Game/SelectCharacter/SelectCharacterHandler.cs)
按 `SelectCharacterDeliveryOptions` 控制闸点之后是否继续发帧：

- `ReferenceSequence`（生产）——闸点之后不再发任何帧，与参照实现的序列一致；
- `Everything`——历史行为，仅测试使用，用来保留那些帧的投递契约覆盖。

**命令与帧是分开的**：被抑制的只是发送，`PublishSelectedCharacterSessionCommand` 等仍然执行，
否则会话不会发布，阶段二的 handler 就读不到它。

## 未解

- 那 7 组被抑制的帧**本该在什么时候发**。它们承载真实数据（装备锁、任务进度、宠物），
  参照实现在别的路径上发它们。逐组挪到闸点**之前**再实机验证，是把它们找回来的办法。
- `0x0010 SELECT_DUNGEON` 整条未实现，因此**新角色走不完新手教程**：1 级角色一进城就请求
  教程副本，我们一个字都不回。绕开的办法是把等级抬过 1 级（客户端就不再触发教程），
  这只是验证手段，不是修法。
- 我们给 `0x000F` 补的那五条 NOTI **至今没有被实机执行过**，形状只有参照实现作依据。
  要验证它，需要一个 1 级角色，而 1 级角色会立刻撞上上一条。
- **槽位 0 的角色进城后必崩**，成因未定。同一角色挪到槽位 5 就正常；char 13（槽位 2）、
  char 2（槽位 1）都正常。两次崩溃与三次成功的帧流**逐字节相同**，261 字节的 `0x0004` 响应里
  只有偏移 9（角色 id）和偏移 218（槽位）不同，而崩溃时偏移 218 恰好是 `00`，成功的三次是
  `02`/`01`/`05`——**包括越界的 `05`**。所以不是"客户端拿它当列表下标"。已排除：属性值
  （清零照崩）、user id = 1（挪槽后 id 未变而正常）、响应整体错位（与上游逐字段对齐）。
- 是否还有进入副本后的第三阶段以及它自己的闸点。

## 逆向工作日志

**2026-08-17**：本页记录的结构花了三轮才定下来，走过的两条弯路值得写下来：

1. **先怀疑"缺回帧"**。客户端发 `0x000F`/`0x0010` 得不到应答，看起来像在等。补上四条 NOTI 后
   仍然崩——因为那四帧**发出去了但客户端没读到就死了**，死因在更早的地方。
   *教训*：服务端日志说"已发送"不等于客户端读到了。
2. **断言"没有闸点 CMD"就停下**。参照序列里确实没有收尾 CMD，于是我认为不存在闸点。
   这个结论逻辑上不成立——客户端容忍 NOTI 缺失，就不可能靠"收齐"判断阶段结束，**必然**存在
   某种信号。是这个反问把 `0x007C` 找出来的。
   *教训*：找不到某个机制时，先确认它是否**必须存在**；必须存在而没找到，说明找的地方不对。

**2026-08-17 第二轮**：查"进城了但 HP/MP 显示 0"。真正的原因是 `0x0002` subtype 1 偏移 95
那一个字节（当前血量百分比，我们写 0），见
[NOTI-0x0002.md](../game/server-to-client/NOTI-0x0002.md#偏移-95当前血量百分比)。
到那之前先撞了三件事，全都值得记：

3. **"多发致命"的机制我一开始记成了位置**。以为闸点后的四条"属于阶段一集合"。抓包证明客户端
   一读到闸点就立刻转状态并发出下一批 CMD，那四条是它**转完状态之后**才读到的。
   *教训*：服务端的发送顺序不等于客户端的处理顺序。判据是"新状态接不接受这一帧"，不是位置。
4. **把 `0x000F` 当成进城的必经握手**。它是通用副本入场指令，1 级角色发它只因为教程把人往
   `Tutorial/Tutorial.dgn` 送。10 级角色一条都不发。查证方式很便宜：**同一角色只改等级**，
   对比闸点之后客户端发了什么。
   *教训*：一条协议在某个场景下出现，不等于那个场景是它的语义。要看它注册在哪一组、
   同组还有谁——上游把它和 `DIE_MONSTER`/`GET_ITEM`/`MOVE_MAP` 注册在一起，这比名字可靠。
5. **改完没确认改动被执行**。补了 `0x000F` 的第五帧，实机回报"还是 0"，我差点当成"补了没用"。
   实际是 10 级角色不发 `0x000F`，handler 一次都没跑——服务端日志里 `notifications handed`
   计数为 0 就能看出来。
   *教训*：解读实机结果之前，先确认代码路径真的被走到了。这一条差点让我否掉一个正确的改动。
