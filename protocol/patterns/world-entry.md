# 进入世界：阶段、闸点与"不能多"

选角色到站在城里，是一条由**若干阶段**串起来的流程。每个阶段有一组**确定的**下行帧，
阶段之间由信号隔开。搞错这个结构，客户端不会报错，它会**崩溃**——而且崩在离原因很远的地方。

本页记录该结构本身。单条协议的字段与样本见各自文档。

> ## A21 与 A12 在这条流程上分道扬镳
>
> **2026-08-24 增补。** 本页此前的全部结论来自 A12 客户端与其参照实现。A21 在同一条流程上
> 有若干**方向相反**的行为，下面各节已就地标注。最重要的三条：
>
> 1. **闸点 `0x007C` 的 body 在 A21 是 8 字节**，不是 0。「零长度所以是纯信号」这条推理
>    对 A21 不成立。
> 2. **闸点之后 A21 还有 12 帧，而且必须发。** A12 时代记录的「多发致命、要把闸点后的帧
>    全部抑制」在 A21 下是**反的**：抑制它们正是客户端进不了城的原因。详见
>    [闸点之后：A21 必须继续发](#闸点之后a21-必须继续发)。
> 3. **客户端"崩溃"不等于解析崩溃。** A21 客户端在进城失败时执行的是一个**故意的自杀桩**
>    （`RVA 0x01147BB0`：`mov dword ptr [0], 0; ret`，前后 `int3` 填充，全镜像仅一个调用点），
>    条件是 `InitGraphicSystem` 返回 `0x8000005B`。也就是说它先弹「图形系统初始化失败」再
>    自行终止。**据崩溃地址反推协议字段会把人带偏**——该地址在连续五轮协议修改下一个字节
>    都不会动。定位这类死亡必须先反汇编崩溃点，确认它是不是解析路径。

## 阶段一：选角色 → 进入世界

```text
C→S  CMD  0x0004  SELECT_CHARACTER
S→C  CMD  0x0004  响应（带两字节结果信封）
S→C  NOTI ×N      角色的全部状态：装备、技能、任务、称号、收集箱、日程……
S→C  NOTI 0x007C  ENTER_GAMEWORLD_COMPLETE   ← 阶段闸点，body 长度 0
S→C  NOTI ×4      0x0002 / 0x0035 / 0x0111 / 0x0016
```

### 闸点是 NOTI，不是 CMD

`0x007C` = `ENTER_GAMEWORLD_COMPLETE`，客户端 handler 在 `RVA 0x0093B150`。

**A12 的 body 长度为零；A21 是 8 字节**（`01 00 00 00 01 00 00 00`）。下面「零长度是关键」的
那段推理只适用于 A12。

它零长度这一点是关键：**它不是数据，是纯信号**。下面会说到 NOTI 可以缺，而缺了数据帧客户端有
默认值兜底；缺了这一条，客户端的状态机就永远不跳。

> **两个观测陷阱。**
>
> 一、`0x007C` 在客户端抓包里**永远看不见**——`clienthack-frame-capture.log` 不记录零长度
> body 的帧（`0x003F CERA` 处首次发现）。在只有抓包的情况下找这个闸点是找不到的。
> 服务端侧的逐帧日志才能看见它。
>
> 二、闸点**不是最后一帧**。服务端在它之后还接着发四条。
>
> 但"这四条属于阶段一集合"是错的说法（2026-08-17 修正）。抓包证明客户端**一读到 `0x007C`
> 就立刻转状态并发出下一批 CMD**，那四条是它**已经进入下一阶段之后**才从缓冲区里读到的。
> 服务端的发送顺序和客户端的处理顺序在这里分岔了。

### 为什么"多发"致命——机制不是位置，是状态

上一条那个分岔正是"多发会崩"的原因：闸点之后到达的任何东西，落在一个**已经换了状态**的客户端上。

那四条（`0x0002`/`0x0035`/`0x0111`/`0x0016`）能活下来，不是因为它们"属于阶段一集合"，
而是因为它们**在新状态下恰好也合法**。被抑制的那七组不合法，于是杀掉了客户端。

所以判断一帧能不能放在闸点后面，问的不是"它在序列里的位置"，而是"客户端在新状态下接不接受它"。

### 集合"可以少，不能多"（**仅 A12**）

| 方向 | 后果 | 证据 |
|---|---|---|
| **少发** | 无害 | 角色无宠物，序列末尾的 `0x0077 PET_WELCOME` 整条跳过，客户端照常进城 |
| **多发** | **崩溃** | 在闸点之后追加 7 组帧，客户端读完就死；移除后当场进城 |

多发的那 7 组是：pre-publication 五条（含一份**账号角色名单** `0x0002` subtype 2）、库存增量、
PvP、装备锁快照、任务进度、宠物复活、副本重入。它们在 A12 参照实现的进场序列里一条都没有。

> **A21 推翻了这一节的一半。** A21 的参照会话在闸点之后发 12 帧，其中就包括上面被列为"致命"的
> pre-publication 四条与装备锁快照。而且不是可发可不发：**抑制它们，客户端就进不去城**——
> 因为其中那份 `0x0002` subtype 2 记录正是客户端用来建自己城镇形象的东西。
>
> 「那份角色名单在客户端已经进城时到达就不合法」这句话对 A21 是错的，而且错得刚好相反。
>
> 「可以少」在 A21 下也要打折扣：少发**数据**帧多半无害，但少发客户端建模型要用的记录，
> 结果不是画得难看，是 `InitGraphicSystem` 失败后自杀。

## 闸点之后：进城已经完成了

**2026-08-17 重写。此前这一节叫"阶段二：进入房间"，把 `0x000F`/`0x0010` 当成进城的必经握手。
错的。** 那两条是**通用的副本入场指令对**，普通角色进城根本不发。

判据来自两次实机对比，同一个角色只改等级：

| 角色等级 | 闸点之后客户端发的 |
|---|---|
| 1 级 | `0x000F` → `0x00C5` → `0x0010` → `0x008F CHANGE_TUTORIAL_FLAG` → `0x0252` |
| 10 级 | `0x01F8`、`0x0252`、`0x00C2`/`0x0117` 卡顿统计、`0x00FA LODING_TIME_REPORT` |

10 级那次**一条 `0x000F` 都没有**，而且它自己上报了"加载耗时"——客户端认为进城已经结束。
1 级那次之所以发，是因为**新手教程把角色自动送进教程副本**，走的正是副本入场那条路。
逐帧证据与更严格的等级差分见 [flow-dungeon-entry](flow-dungeon-entry.md)。

> **零长度帧只有服务端看得见。** 同一次会话里客户端还发了 `0x004F CALL_MEMER_LIST` 与
> `0x0078 REQUEST_BLACKLIST`，两者 **body 都是 0 字节**，因此在客户端抓包里完全不存在
> （同 `0x007C` 隐形的原因，见上文观测陷阱一）。它们只出现在服务端逐帧日志的
> `Unhandled Game frame` 行里，而且 `Game:01`/`02`/`03` 三次会话都有——**没有做过等级差分，
> 所以不能说它们是 10 级特有的**，只能说进城后会发。

所以：**进城的终点就是闸点加那四条**。`0x000F` 之后的东西属于
[副本入场](flow-dungeon-entry.md)，是另一条路。

### 名字的读法

`ENTER_SELECT_DUNGEON` 不是"进入(游戏) + 选副本"，是 `ENTER` + `SELECT_DUNGEON`——
**进入"选副本"这个状态**。城镇本身就是选图界面，所以打开副本列表时才发它。
配对的 `0x0010 SELECT_DUNGEON` 才是"选定并开跑"。顺序没有反。

## 副本入场：`0x000F` + `0x0010`

只在真要进副本时走这条路（1 级角色被教程自动触发也算）。上游的形状：

```text
C→S  CMD  0x000F  ENTER_SELECT_DUNGEON   body = u32 目标副本 id
S→C  NOTI 0x0017  USER_AREA（area 改写为 0xFF）
S→C  NOTI 0x0002  subtype 1 —— 属性块，再发一遍
S→C  NOTI 0x0003  USER_STATE（先置 UserState = 0x01）
S→C  NOTI 0x001A  UDP 主机（不可用）
S→C  NOTI 0x001B  ENTER_SELECT_DUNGEON 状态（带绝望之塔层数）
                  + 账号经验进度
C→S  CMD  0x0010  SELECT_DUNGEON         body 9B，布局已闭合 ← 我们完全没处理
```

`0x000F` **没有 CMD 响应**——客户端为它注册了 CMD 接收 handler，但参照实现在成功路径上
只推 NOTI，CMD 仅用于错误分支（佣兵被拦）。

我们的实现补齐了那五条 NOTI，但**至今没有被实机执行过**：验证时用的是 10 级角色，
它不发 `0x000F`。所以这五条的形状仍然只有参照实现作依据。

`0x0010` 的实现面比看起来大得多。上游成功路径：解析（副本 id / 难度 / 深渊标志）→ 绝望之塔入口
改写 → 载入进行中与已通关任务 → 入场资格评估 → `BeginRun` → 选迷宫、随机 boss 位置、随机出生点、
解析起始房间 map id → 然后才发 `0x001C DungeonInfo`、选择态、**`SendStartMapAsync` 把人放进第一个
房间**、`0x019F` 助战标签。另外 `0x000F` 里还要记一个**返回锚点**（town/area/x/y）供出本时用。

## 顺序：段内无序，段间有序

参照实现把整条进场序列写成一张**有序模板表**（`NewCharacterInitSequence`，53 条），
每条带 `Command` 字段。其中只有两条 CMD：

| 位置 | 帧 |
|---:|---|
| 0 | `cmd=01 type=0x0004` |
| 1–34 | 连续 34 条 NOTI，中间没有任何 CMD |
| 35 | `cmd=01 type=0x0312` |
| 36–52 | 连续 17 条 NOTI，以 `0x0077` 收尾 |

所以 **NOTI 之间不需要被 CMD 分隔**，一口气连发几十条是正常的。CMD 在这里不是分隔符，
而是"这一条本身需要结果信封"的协议（见
[CMD body 的两字节结果信封](game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)）。

## 服务端实现

[`SelectCharacterHandler`](../../Server/src/Dfo.Server.Protocol/Game/SelectCharacter/SelectCharacterHandler.cs)
按 `SelectCharacterDeliveryOptions` 控制闸点之后是否继续发帧：

- `ReferenceSequence`——闸点之后不再发任何帧，与 **A12** 参照序列一致；
- `Everything`（**A21 生产值**）——闸点之后继续发，这正是 A21 参照会话的行为。

生产注册在 2026-08-24 由 `ReferenceSequence` 改为 `Everything`。改之前该成员上的注释写着
「客户端就是在读这段尾巴时死的」，A21 抓包证明相反：**withhold 才是死因**。

**命令与帧是分开的**：被抑制的只是发送，`PublishSelectedCharacterSessionCommand` 等仍然执行，
否则会话不会发布，阶段二的 handler 就读不到它。

## 城镇的持久化

登录要落在"上次离开的那个镇"，这条链有四环：

| 环 | 载体 | 状态 |
|---|---|---|
| 客户端换区 | CMD [`0x0024`](../game/client-to-server/0x0024.md) `SET_USER_AREA` | 已实现，**换区已实机走通**（2026-08-17，四次） |
| 客户端换镇 | 同上 | 实现同一条，但**换镇至今没有实机样本**，见下 |
| 客户端上报镇内移动 | CMD [`0x0023`](../game/client-to-server/0x0023.md) `SET_USER_POSITION` | 已实现，坐标与朝向已确认随移动改变 |
| 写库 | 会话清理时写 `characters.town_id/area_id/pos_*` | 已实现 |
| 登录读回 | `EntryPlacementRuleService`：`persistedTownId > 0 ? persistedTownId : DefaultTownId` | 已实现 |

**换区答两条 NOTI，缺一条就卡住**：`0x0017` 定位 + [`0x0018`](../game/server-to-client/NOTI-0x0018.md)
区域名册。只答 `0x0017` 时客户端把同一帧 `0x0024` 重发八次，角色停在原地。

**只恢复镇，不恢复镇内位置。** 读回的只有镇号，落点一律重算为该镇 `[gate]` 区域——
参照实现同构（`GameChannelSpawnPolicy.Resolve` 拿 `GetCeraRoomInfo(townId)` 覆盖 area 与坐标，
并把找不到 `[gate]` 的镇当错误抛出，异常信息里就叫它 *Seria-room*）。所以库里存的
area/pos 至今只被写、不被读；它们服务的是同屏与断线重连，不是登录落点。

**写库只在会话结束时发生一次**，写的是运行时会话当时的位置。参照实现额外做了按步节流的
写穿（`set_user_position` 节流、`set_user_area` 强制、teleport / 断线 / 返回选人各一次），
差别只在"客户端被硬杀、socket 没关"时会丢掉最后一次移动。等真的观察到丢失再补。

### 换镇这一环走不通，原因在内容而不在代码

四次实机跨区的镇号**全是 1**。要跨镇就得走到一个通往别的镇的区域，而
[镇间通路探针](data/probes/pvf-town-links-20260817.md)显示：25 个镇里只有暗黑城有这种区域，
且全部要 17 级以上；银色村庄的三个区域（到达点、主街、决斗场入口）**一个都不是**。

所以"走出城镇"和"换镇"是两件事——前者成功了四次，后者一次都没发生过。
要验证最后一环，需要一个能站在暗黑城的角色，或者走传送那条路。

### 这条链曾经是空转的

2026-08-17 之前，第三、四环都齐了，前两环却都没有输入：`0x0024` 完全未实现，`0x0023` 被
当成[进图上报族](../game/client-to-server/0x0023.md)整段收下丢弃。于是运行时位置永远是入场
spawn，清理时把同一个值写回去——**"回到上次离开的城镇"既不会失败，也不会生效**。

这类缺陷不会报错：每一环单独看都是对的，只有把链走通才看得出中间断了。

而"走通"本身也分层：现在链上跑的是**区域**，不是**镇**。写库那一环存的两个值里，
只有 area/pos 被真的改过，`town_id` 至今只被写成入场时算出来的那个值。

## 未解

- 那 7 组被抑制的帧**本该在什么时候发**。它们承载真实数据（装备锁、任务进度、宠物），
  参照实现在别的路径上发它们。逐组挪到闸点**之前**再实机验证，是把它们找回来的办法。
- `0x0010 SELECT_DUNGEON` 整条未实现，因此**新角色走不完新手教程**：1 级角色一进城就请求
  教程副本，我们一个字都不回。绕开的办法是把等级抬过 1 级（客户端就不再触发教程），
  这只是验证手段，不是修法。
- 我们给 `0x000F` 补的那五条 NOTI **已发出但未被证实被正确消费**。服务端逐帧日志有三次
  「5 notifications handed to the sender」，三次都是 1 级角色，所以 handler 确实跑过；
  但客户端紧接着就发 `0x0010` 并停在那里，没有任何证据说明它对这五条做了什么。
  形状仍只有参照实现作依据。
- 是否还有进入副本后的第三阶段以及它自己的闸点。

## 逆向工作日志

**2026-08-17**：本页记录的结构花了三轮才定下来，走过的两条弯路值得写下来：

1. **先怀疑"缺回帧"**。客户端发 `0x000F`/`0x0010` 得不到应答，看起来像在等。补上四条 NOTI 后
   仍然崩——因为那四帧**发出去了但客户端没读到就死了**，死因在更早的地方。
   *教训*：服务端日志说"已发送"不等于客户端读到了。
2. **断言"没有闸点 CMD"就停下**。参照序列里确实没有收尾 CMD，于是我认为不存在闸点。
   这个结论逻辑上不成立——客户端容忍 NOTI 缺失，就不可能靠"收齐"判断阶段结束，**必然**存在
   某种信号。是这个反问把 `0x007C` 找出来的。
   *教训*：找不到某个机制时，先确认它是否**必须存在**；必须存在而没找到，说明找的地方不对。

**2026-08-17 第二轮**：查"进城了但 HP/MP 显示 0"。真正的原因是 `0x0002` subtype 1 偏移 95
那一个字节（当前血量百分比，我们写 0），见
[NOTI-0x0002.md](../game/server-to-client/NOTI-0x0002.md#偏移-95当前血量百分比)。
到那之前先撞了三件事，全都值得记：

3. **"多发致命"的机制我一开始记成了位置**。以为闸点后的四条"属于阶段一集合"。抓包证明客户端
   一读到闸点就立刻转状态并发出下一批 CMD，那四条是它**转完状态之后**才读到的。
   *教训*：服务端的发送顺序不等于客户端的处理顺序。判据是"新状态接不接受这一帧"，不是位置。
4. **把 `0x000F` 当成进城的必经握手**。它是通用副本入场指令，1 级角色发它只因为教程把人往
   `Tutorial/Tutorial.dgn` 送。10 级角色一条都不发。查证方式很便宜：**同一角色只改等级**，
   对比闸点之后客户端发了什么。
   *教训*：一条协议在某个场景下出现，不等于那个场景是它的语义。要看它注册在哪一组、
   同组还有谁——上游把它和 `DIE_MONSTER`/`GET_ITEM`/`MOVE_MAP` 注册在一起，这比名字可靠。
5. **改完没确认改动被执行**。补了 `0x000F` 的第五帧，实机回报"还是 0"，我差点当成"补了没用"。
   实际是 10 级角色不发 `0x000F`，handler 一次都没跑——服务端日志里 `notifications handed`
   计数为 0 就能看出来。
   *教训*：解读实机结果之前，先确认代码路径真的被走到了。这一条差点让我否掉一个正确的改动。

**2026-08-17 第四轮**：把城镇持久化那条链走通。

8. **我判"单人不需要区域名册"，判错了。** 实现换区时只答 `0x0017`，跳过

9. **"走出城镇"被我当成了"换镇"。** 实机成功之后我差点记成持久化验证通过。四次跨区的镇号
   全是 1，而银色村庄根本没有跨镇通路——测的一直是换区。
   *教训*：验证一条链时，先确认这次操作真的经过了要验的那一环，而不是经过了它的邻居。

**2026-08-17 第三轮**：查"槽位 0 的角色进城必崩"。成因是 `0x0004` 响应偏移 218 我们写了槽位，
而客户端把这一字节当**镇 id** 查表，取回的对象不查空就解引用——槽位 0 送出一个不存在的镇 id。
判据与反汇编见 [`0x0004.md`](../game/client-to-server/0x0004.md#偏移-218-是入场镇-id不是槽位写-0-必崩)。

6. **"崩溃与成功的帧流逐字节相同，只有槽位那一字节不同"这句话本身就是答案，我却读成了谜题。**
   那一字节确实是唯一变量，我却因为它"名字叫槽位"而去排查槽位以外的一切（属性值、user id、
   整体错位），把差分结果当成了背景噪声。
   *教训*：差分把变量缩到一个字节时，**先怀疑那个字节的含义标注是错的**，再怀疑别的。
7. **`05` 越界却正常，这条反常我看见了但没用。** 当时的结论是"所以客户端不拿它当列表下标"——
   只否掉了一种读法就停下了。其实它同时**指向**了正确读法：作为槽位越界、作为镇 id 合法的数，
   本身就在说这个字段的值域不是槽位的值域。
   *教训*：一个反常样本否掉旧假设之后，还要问它**支持**什么。否证只用掉了它一半的信息。


## 闸点之后：A21 必须继续发

**2026-08-24 新增，只讲 A21。**

A12 的闸点后只有四条（`0x0002`/`0x0035`/`0x0111`/`0x0016`）。A21 的参照会话有 **12 条**：

```text
S→C  NOTI 0x007C  ENTER_GAMEWORLD_COMPLETE   ← 闸点，body 8 字节
S→C  NOTI 0x0002  subtype 6，25 字节
S→C  CMD  0x01BA  MERCENARY_INFO
S→C  NOTI 0x0035  CERA
S→C  NOTI 0x0111  UNITED_SERVER_FRIEND_INFO
S→C  NOTI 0x0016  USER_POSITION
S→C  NOTI 0x000E  UPDATE_ITEM_LIST
S→C  NOTI 0x0165  CHARAC_INVISIBLE_FALGS
S→C  CMD  0x0239  SET_CLONE_TITLE
S→C  NOTI 0x0002  subtype 2，103 字节   ← 客户端用它建自己的城镇形象
S→C  NOTI 0x0289  HONOR_LEVEL_INFO
S→C  NOTI 0x00FB  ITEM_LOCK_LIST（第二次）
S→C  CMD  0x01BA  MERCENARY_INFO（第二次）
```

### `0x0002` subtype 2 就是花名册载荷

把参照的 103 字节按下标摊开，`[0:18]` 与账号花名册的头部逐字段一致
（`0x02`、SlotLimit 两遍、`00`、i32 0、u16 0、i32 0、u16 条数），之后是一条标准角色条目：

```text
u16 槽位 / u32 名字长度 + 名字 / 00 00 / Job / GrowType / Level / 0x0B / 0x01
u32 0 / u32 0 / u8 外观件数 / 外观件 ×23 / 尾部 36（结尾 00*6 FF 00*8）
```

`18 + 2 + 4 + 4 + 2 + 3 + 8 + 1 + 23 + 36 = 103`，严丝合缝。**进城时客户端从这条记录建人物模型**，
所以它复用花名册的编码不是巧合。

### 角色没有外观就进不去城

外观 blob 为空的角色会让 `InitGraphicSystem` 返回 `0x8000005B`，客户端弹错误后自杀——
**看起来像协议崩溃，其实是缺数据**。

判据分两步，第二步把结论收窄了：

1. 同一份服务端代码，在库里补上参照角色的三件装备（槽位 12/14/16）与对应的三件外观，
   客户端当场进城，子类型 1 从 173 字节涨到 395 字节，崩溃地址彻底改变。
2. **再把三件装备删掉、只留外观，客户端照样进城**——所以要的是外观，不是穿戴的装备。

客户端在这里要的是"有东西可以建模型"，不是"有一套自洽的库存"。装备缺失只让子类型 1 变短
（395 → 更短），不影响进城。

建号因此必须写外观。档案里没有按职业的建号装备表——这个游戏里起始装备是服务端数据而不是
内容数据（`character/<job>.chr` 的 `[initial value]` 只有属性和 `[skill]`），所以服务端侧
只能给一份默认外观，见 `CharacterRosterService.CreatedAppearance`。

### 进城之后客户端才会做的第一件事

```text
C→S  CMD  0x0023  SET_USER_POSITION   body 7B
S→C  NOTI 0x0016  USER_POSITION       body 9B ← A21 会答，A12 不答
```

`0x0016` 的九字节 = `u16 线上用户 id` + 客户端刚上报的 x、y、方向和尾部 `u16`。尾部是客户端
说了算：参照里上报 `68 00`、回包也是 `68 00`，而入场帧里是 `64 00`。

客户端发出这一条，本身就是**城镇已经建成**的判据——在此之前它还在 `InitGraphicSystem` 里。

## A21 入场批次的顺序

A12 的模板表是 53 条；A21 的参照会话是 **67 帧**，而且顺序不同。最要紧的一处：

**A21 先发角色记录（`0x0002` subtype 0），再发物品表。** 本仓原本反过来——五个 `0x000D`
在前、角色记录在后，等于把物品挂在一个还没建立的角色上。

开头十二帧的参照顺序：

```text
CMD  0x0004 (261) → NOTI 0x0002 subtype 0 (188) → 0x0166 ×5 → 0x0167 → 0x0015
→ 0x0164 → 0x0013 → 0x0069 → 0x0002 subtype 1 (519) → 0x0003 → 0x00CA → 0x0005
→ 0x000D ×6 ...
```

### A21 在入场序列里**不发**的三条

`NOTI 0x0025`、`NOTI 0x019F`、`NOTI 0x019D`。其中 `0x019F` 参照是在客户端请求之后才答。

`0x0025` 尤其要注意：本仓曾在闸点后主动下发一个 95 字节的 body，客户端读它时把
**66 万个元素**拷到自己栈外（`ecx=0x000A252E`）。这说明该协议的 A21 布局与我们写的不是一回事，
在拿到真正含它的抓包之前不应主动下发。
