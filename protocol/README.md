# DNF 86JP 协议资料库

本目录保存协议的原始样本、客户端构包/解包证据、服务器行为证据和当前实现结论。它回答的不只是“代码现在怎么写”，还要回答“为什么相信它是对的”。

这里记录的协议均以当前 86JP 客户端为对象，默认仍是代码反推结论，不等同于官方协议说明。客户端版本发生变化时，不得直接假定地址、字段或行为仍然成立。

## 如何查找

- [协议目录](catalog.md)：按端点、方向、command 和 type 查找已有记录及成熟度。
- [逆向与验证方法](methodology.md)：从未知报文到实现完成的固定工作流。
- [记录模板](templates/message.md)：新增协议时复制使用。
- [Game 帧组织](patterns/game-frame.md)：跨协议共享的帧级结构与组织规律。

协议记录按以下路径组织：

```text
protocol/<endpoint>/<direction>/<command-type-name>/
  README.md       协议结论、布局、期望行为和实现映射
  samples/        去敏后的原始 body/frame 样本
```

例如：

```text
protocol/game/client-to-server/0x00AB-client-spec-statistic/
```

目录名中的十六进制编号是 `type`。协议身份必须同时阅读记录中的 endpoint、direction 和 command；不能仅凭 type 判断含义，因为相同数字可能在不同方向代表不同消息。

## 证据等级

每项结论使用下列等级之一：

- **Confirmed**：由客户端构包/解包指令、服务器消费代码或可重复实机行为直接证明。
- **High**：多条独立证据一致，尚缺一条直接指令级证据。
- **Hypothesis**：有合理迹象，但仍需要反汇编、动态 trace 或对照样本确认。

`Hypothesis` 不得直接变成生产领域语义。可以先按 offset 和原始宽度建模，并保留未知名称。

## 完成标准

一条协议只有同时满足下列条件，才可在目录中标记为 `ClientVerified`：

1. 已确认方向、触发阶段和是否需要响应。
2. 客户端构包或解包路径已有指令级证据。
3. 字段顺序、宽度、条件分支和编码方式已记录。
4. 至少一个真实样本可由记录的布局无损解释。
5. 服务端 parser/codec 与 typed message 有回归测试。
6. 实机客户端验证通过，并记录可观察结果。

## 安全边界

- 登录凭证、账号令牌、聊天隐私和可识别个人的数据不得提交到本目录。
- 硬件遥测样本只保留协议研究所需字段；不关联真实用户身份。
- 大型二进制、完整客户端和数据库不进入本目录，只记录哈希与可定位的 RVA。
- 证据修订应保留旧结论为何被推翻，避免相同误判再次发生。
