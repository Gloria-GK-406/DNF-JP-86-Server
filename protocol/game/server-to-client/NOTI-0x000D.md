#### `+0x2F` 是一个崩溃向量，服务器侧已夹紧

客户端读这条记录的两个处理器都用 `+0x2F` 驱动一条**没有上界**的 `rep movsd`，拷进固定的栈
缓冲：`0x0117C670`（本帧）目标距 /GS cookie 40 字节，`0x0117D720`（NOTI `0x000E`）距 196 字节。
两处都只用 `jle` 挡 `<= 0`，`1..127` 都能打崩（`vmp1-9.md` 第五节，**静态反汇编，未实机**）。

本仓此前把 `item_core[45]`（`byte`，0..255）原样写进 `+0x2F`。已改为夹到 **2**——即本编码器
在 `+0x30` 之后**实际写出**的选项 dword 条数（`EmblemId1`、`EmblemId2`）。选这个界而不选
上面任何一个客户端数值，是因为它能在本仓里被核对；它同时远低于两个客户端上界。装备那条路
（`StateSynchronizationPayloadCodec.Entry.cs`）一直是这么夹的，背包这条是唯一没夹的。

### 补记（2026-09-07，同日第二次）：条目形状由**容器**决定，前一条补记里两句话要收回

#### 客户端按容器选读法（读自客户端原生代码，未虚拟化）

`0x01637740`，由 `0x0117D028` 每条记录调用一次：

```
F(buf /*ebp+8*/, itemId /*ebp+0Ch*/, 选择子 /*ebp+10h*/):
    if (选择子 == 1) { 0x274FBE0(buf); return; }                        // 装扮栏：每条都读
    if (选择子 == 3) { if (0x166EBC0(itemId)) 0x274FBE0(buf); return; } // 装备栏：按物品判定
    return;                                                             // 其余容器：一概不读
```

选择子就是帧首那个 listType（`0x0117C6C2` 用 `read_byte` 从 NOTI 体读入）。
`0x0274FBE0` 是 VMProtect 虚拟化的，但它的行为由下面这段明文与实机字节流定死：

```
read_bytes(dst, len) @ 0x027C5380        ← 未虚拟化
  027c5383  mov eax,[ebp+8]      ; dst
  027c5387  mov esi,[ebp+0Ch]    ; len ← 调用方传入
  027c538b  mov edi,[03BAAE38]   ; src = 全局包读游标
  027c5394  call 02c61c00        ; memcpy(dst, src, len)
  027c5399  add edi,esi          ; 游标 += len
  027c539c  mov [03BAAE38],edi
```

**所以条目形状是三分的：**

| 容器（listType） | 每条条目 | 长度 |
|---|---|---:|
| 装扮栏 `1` | 101 字节记录 + 长度前缀外观块，**每条都带** | **131** |
| 装备栏 `3` | 101 字节记录，**只有时装那条带** | 131 / 101 |
| 其余（主背包 0、个人货柜 2、宠物 7、账号金库 12、公会勋章 38…） | 定长 101，**永不带** | 101 |

#### 外观块的形状（上游 A21 读出 + 实机验证）

```
u32  18            ← A21AvatarJewelBytes；存储 30 字节里的前 18
     18 字节珠宝槽  ← 珠宝槽结构 SocketCount=5 × EntrySize=6 = 30，A21 只发前 3 个孔
u32  4
u16  Color1
u16  Color2
                   合计 30 字节
```

上游 `ItemListProtocolWriter`：`Entry84Size=84`、`A21CommonEntryExtra=17`、
`A21CommonEntrySize=101`、`A21AvatarJewelBytes=18`、
`A21AvatarEntrySize = 84+17+4+18+4+4 = 131`；写法在 `WriteAvatarEntry126`，
用 `WriteFixedBytes(…, JewelSocket, 18)` 从 30 字节列里截前 18。
**那个函数名里的 `126` 是 A12 的总长**（`84+4+30+4+4`）——A12 发 30 字节珠宝，A21 发 18。

#### 两种错法各崩一次，方向相反（均实机观测）

| 规则写法 | 后果 |
|---|---|
| 按**物品种类**（`ItemKind == 8`）追加 | 主背包里的时装也带块 → 打乱 listType 0 的定长 101 跨步 → `STATUS_STACK_BUFFER_OVERRUN (0xC0000409)` |
| **一概不追加** | 装扮栏条目短了 → 客户端读完记录再从流里取 4 字节当长度，取到接收缓冲的 `'0'` 填充 `0x30303030` → 野长度 memcpy → `STATUS_ACCESS_VIOLATION` |
| 按**容器**三分（现行） | 主背包与装扮栏同时正常；实机放 11 件时装于装扮栏，11 条连续对齐、零异常 |

**自描述长度的陷阱**：块是「先读 u32 长度再读那么多字节」，所以发 30 字节珠宝也能对齐、
也不崩，实机也看不出区别（珠宝槽全零时 18 个零与 30 个零同样）。
**「实机不崩」不能用来判定这个长度。** 它只能判定形状机制。

**2026-09-07 追记：合并后的正式实现已实机跑通**（提交 `308ac02c` 之后，装扮栏 11 件时装、
`listParam16 = 0`、主背包另有一件 `EmblemSocketCount = 200` 的物品）：入场序列走完、
服务器零异常、11 件时装在装扮栏正常显示、容量呈未扩容、主背包物品正常。

**这一次同样不能用来判定 18 与 30 谁对**——理由与上一段相同，那些时装的珠宝槽全是零。
它新增的是另一件事：**在此之前上过真客户端的是临时实验（42 字节形状），
正式实现从未上过**；现在正式实现本身有了端到端的实机证据。
`WireJewelBytes = 18` 的依据仍然只有上游 A21 源码这一条。

#### `listParam16` 的含义逐容器不同，本节此前写成「容量」不准

上游 `InventoryService.InitDefaultListParams()` 与 `ItemSlotBoundService`：

| 容器 | `listParam16` 写什么 | 说明 |
|---|---|---|
| 主背包 `0` | **扩容阶段键**，取值 `0 / 8 / 16 / 24` | `MainExpandStageFull = 24`；槽位区间随之为 9..64 / 65..120 / 121..176 / 177..232 / 233..288 |
| 装扮栏 `1` | **恒 0** | `GetAvatarOpenRange(int avatarListParam16)` **收下参数直接丢掉**，恒返回 `0..209`——装扮栏固定 **210 格** |

**一处边界不得越过**：上游全仓没有装扮栏扩容概念，但这只说明**那个参考实现没做**。
所以**不得**据此写成「装扮栏不能扩容」。

##### 客户端**确实**看这个字段：实机对照

两次观测（所有者，2026-09-07）。**控制条件**：同一份存档（装扮栏同样 11 件时装，
主背包同样内容）、同一个服务器构建、同一个客户端，两次之间**只重启服务器并改了
`listParam16` 一个值**，背靠背进行：

| 发出的 `listParam16` | 客户端表现 |
|---:|---|
| `483` | 装扮栏显示为**已全部扩容** |
| `0` | 正常 7 列，**并出现「需要扩容」的标志** |

**所以「客户端不看这个字段」这个可能已被观测排除**——不是「多半不是」，是这两次对照直接否掉的。

**残余风险**：这是一次 n=1 的 A/B，**没有做回摆**。它足以排除「客户端不读这个字段」，
**没有**排除「重启服务器时还有别的东西跟着一起变了」。读者可据此自行称量。

**注意 483 不是任何权威来源的值**：它是本仓调试期手工写进 `character_container_state`
的一个凑数（按 `7×7×10−7` 猜的）。有价值的不是 483 本身，是这个对照。

**一处指针要说清，免得读者对不上**：主检出的 `Document/avatar-container-entry-shape.md`
里也有 483，但那是**另一次、更早的会话**——那段转储的装扮栏 `count = 1`（一件普通堆叠物），
不是上表控制条件里的 11 件时装，且发生在外观块被补回之前。**那份文档引 483 是为了
逐字节的游标证据，与本节的扩容对照不是同一次观测。** 该文档尚未注明 483 是凑数，应当补；
本轮的工作区碰不到主检出，故只记不改。

**这与上游 `GetAvatarOpenRange` 收下参数直接丢掉并不矛盾**——那是上游**服务器侧**
「哪些槽位收得下东西」的判定，客户端画不画扩容标志是**客户端侧**的渲染，两件事不冲突。
上游为什么不实现，**没有证据，属推测**，不写。

**尚未查清**：这个字段在装扮栏的确切语义（是格子数？是扩容阶段键，像主背包那样取

## 补记（2026-09-07，第三次）：「那条路本轮未改动」这句到此为止

上面「一处仍然存在的功能缺口」一节里写着，穿戴中的时装那条路
（`StateSynchronizationPayloadCodec.Entry.cs`）**本轮未改动**。

**那句话在写下时是对的，从今天起不再成立。** 原句原地留着，这里说明它何时、被什么取代。

### 它当时说的是什么

`308ac02c` 那一轮只动了背包家族（本帧与 NOTI `0x000E`）的条目编码，把珠宝槽从 A12 的
30 字节改成 A21 的 18 字节。穿戴那条路没有跟着改，所以那句「未改动」是如实记录。

### 今天改了什么

珠宝槽在本仓共有**三条**上线路径，而不是两条：

| 路径 | 帧 | `308ac02c` 之后 | 今天 |
|---|---|---|---|
| 背包家族 | 本帧、NOTI `0x000E` | 18 | 18 |
| 穿戴条目 | NOTI `0x0002` 子类型 1；消息 `0x019F` | **30** | **18** |
| 邮件附件 | 消息 `0x0061` | **30** | **18** |

第三条（邮件附件，`WriteMailboxAvatarDetail`）**上一轮完全没有被发现**——上一轮的搜索口径是
「背包家族改成 18 之后还有谁没跟上」，从被改动的那一处往外找，找到了共享 "NOTI-2" 这个名字的
穿戴条目，没有找到名字不同的邮件路径。它是本轮开工前按「搜数字而不是搜说法」重扫时撞见的。

三处现在读同一个常量、走同一段写法：`Dfo.Server.Protocol.Game.AvatarJewelSocketOnTheWire`。

### 依据仍然只有一条，且仍然不是实机

18 来自**上游源码读出**：参照服务器的三个写入方共用一个 `A21AvatarJewelBytes = 18`
（`ItemListProtocolWriter.cs` 第 89、193 行与 `MailboxHandler.cs` 第 1127 行）。

**本轮同样没有、也不可能有实机证据**，理由与本文档上面「自描述长度的陷阱」一节相同：
块自带长度，任何长度都对齐；测过的珠宝槽全是零，两个长度看起来一样。
判据里因此有一条**不指名任何长度**的收敛判据，只断言四个发送方彼此相等
（`JewelSocketHasOneWireLengthTests.EveryFrameDeclaresTheSameJewelLength`）——
它挡的是「只改了其中一条」，而那正是这次真的发生过的事。
