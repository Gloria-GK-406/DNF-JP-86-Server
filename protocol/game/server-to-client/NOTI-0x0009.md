### town-visible 非成员投影（2026-09-13）

**状态：ClientVerified（A21 原生 ID `0x11` 同区非成员 add/update/delete）。**

A21 当前主目录不需要新的目录 wire：客户端先由 `NOTI 0x0002` subtype 0 建立远端 CNUser，再用本条
type-0 refresh 把该角色关联到 party。服务端因此把既有成员投影与 town-visible 非成员投影分区：

- create、settings update、accept、普通成员 leave、disband 及 lifecycle cleanup 在领域 mutation 的
  lock 内冻结 `VisibleTownArea` exact-session observer；跨 channel/town/area、未站在城镇、未共享 presence、
  stale/replacement session 均排除；
- observer 只复用本条既有 type-0 refresh 或 type-3 clear，不接收 member-only 的 realtime、endpoint、
  acceptance 序列；普通成员离队时，离队者先收到旧 party clear，随后作为同区非成员收到幸存 party refresh；
- 首次选角和换区以 town publication 的实际 `Delivered` recipients 为边界：对应远端角色的 `0x0002`
  成功后才 read-repair 当前 `0x0009`；任一 exact recipient 的瞬时发送失败由因果链所有者原位重试一次，
  town 的通用 detached retry 已禁用，因而成功补发 `0x0002` 后仍会继续 `0x0009`；
- mutation 与 read-repair 共用每个 party generation 的串行 gate，并额外按所涉 CharacterId 稳定持有
  participant gate，使旧 generation 的 read-repair 不能落到新 generation mutation 之后；gate 内重新查询
  当前 snapshot。已提交的同 revision 仍允许投给新 observer；真正旧 revision 被抑制，read-repair 和
  requester-only realtime 本身都不推进完整 mutation revision。

服务端行为证据位于 `PartyDomainServiceTests`、`PartyNotificationTests`、
`PartyTownProjectionDeliveryTests`、`TownProjectionHandlerTests`、`SelectCharacterLifecycleTests` 与
`CleanupNotificationDeliveryTests`。这些测试证明 exact audience、顺序、去重、单次顶层调用的瞬时失败重试、
持久失败后的同 revision 重入，以及同/跨 generation 竞态收敛，
这些自动化结果现由 2026-09-13 的双客户端 exact-session 补齐客户端层：observer 先收到远端 leader 的
`0x0002 subtype 0`，再收到同 party 的 `0x0009 type 0`；原生主目录出现 A/B 两行。A 切换为预设标题
“强强联合”时 observer 收到同 partyId refresh 且同一行更新；A 解散后 observer 收到 5-byte type-3 clear，
界面先标记“已取消组队”，原生刷新后该行删除，只剩 B。截图时客户端只读回读也只保留 B 的 CParty 与
CNUser 关联。完整证据与边界见
[`a21-party-directory-live-20260913.md`](../../patterns/data/traces/a21-party-directory-live-20260913.md)。
