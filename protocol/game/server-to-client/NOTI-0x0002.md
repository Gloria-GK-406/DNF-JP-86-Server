## 证据与样本

<!-- 人工区：重新生成不会触碰本节及其之后的一切内容。 -->

本 type 的 body 按首字节分 **subtype**，不同 subtype 是形状完全不同的载荷。机器区那张字段表
走出来的是 **subtype 0**（外观/公开信息），下面记的是 **subtype 1**（属性），两者不要混读。

2026-08-17 实机观察到三个 subtype：

| subtype | body 长度 | 出现位置 |
|---|---|---|
| 2 | **随名单长度变化**（`18 + 58 × 角色数`；上方读取跟踪那次是 2 个角色 = 134） | 登录后的账号角色名单 |
| 0 | 132 | 入场批次 + 闸点后各一次 |
| 1 | 144 | 入场批次，承载属性 |

subtype 2 不要记成一个固定长度：测试账号的角色数会随建号/删号探针变动，
同一条协议在不同会话里长度不同是正常的。

### subtype 1 的属性块：`83` 是长度前缀，块就是 83 字节

**2026-08-17 用运行时读取跟踪确证**（做法见
[game-receive.md](../../patterns/game-receive.md#四个原语是唯一出口)）。客户端读这一帧的
方式不是逐字段，而是：

```text
off  9  w4   v=83                        ← 长度
off 13  w83  bytes B0040000D0070000…     ← 一次 ReadBytes(83) 吞掉整块
off 96  w1   …                           ← 13 + 83 = 96，下一个字段
```

`B0040000` = 1200、`D0070000` = 2000，正是样本角色（职业 3 魔法师）的 HP/MP 上限。

这解开了一个长期的困惑：偏移 9 那个常量 `83` 曾被记为"恒 83、语义不明"，而按字段逐个相加
只得到 82。**它是块长度，块含 83 字节**——差的那一个字节就是块尾的血量百分比。所以下表里
偏移 13–95 对客户端而言是**一个整体**，逐字段的划分来自服务端的写入顺序，客户端不做这个划分。

body 被**完整消费**：144 字节，`unread tail = 0`。

`0x0002` subtype 1 的 body 前 97 字节偏移固定（装备列表在其后，才随数量变长）：

### 偏移 95：当前血量百分比

这个字节**不进机器区**——机器区的字段表是 subtype 0 的，静态走不到这里，
`check-meanings.py` 因此正确地拒绝了把它写成字段含义的尝试。

实机三点差分，同一角色只改这一个字节：

| 值 | 血条 | HP 上限 | 状态栏 |
|---|---|---|---|
| 0 | 空 | 1800 | 无 |
| 50 | **半格** | 1800 | 无 |
| 100 | 满 | 1800 | 无 |

**上限恒定、当前值线性跟随**，所以它是"当前血量占上限的百分比"，不是上限的缩放。

> **虚弱状态不止这一个出口。** 值为 50 时血条半格，但状态栏**没有**出现 `虚弱 xx%` 的 buff
> 图标。所以完整的虚弱状态至少是这个字节加上 [`0x01E8 CHARACTER_ADD_BUFF`](NOTI-0x01E8.md)
> 两处联合作用，解除时还要 [`0x01E9`](NOTI-0x01E9.md)，运行中改血量另有
> [`0x0088 CHANGE_HP`](NOTI-0x0088.md)。

**名字的教训。** 上游把这个字节存在名为 `stat_level` 的列里，而它自己的注释就写着
"该字段非角色等级锚点"——**上游知道名字不对，但没查出是什么，就固定填 100 了事**。
我们照抄了列名，我又把那个 100 判成"语义未知的魔数"选择不抄（见
[0x0004.md](../client-to-server/0x0004.md) 的 2026-08-17 日志），于是这个字节成了
"属性上限全部正确却显示为 0" 的直接原因。

*教训*：一个来源可疑的**常量**和一个来源可疑的**字段名**，风险完全不同。名字可以先照抄再改，
常量不抄就等于替对方做了一个自己没有依据的决定。

## A21 子类型 `0x02`（角色列表）：逐角色条目（2026-08-23）

一个角色带一条外观时，本子类型的 body 为 103 字节。**本仓产出与参考会话逐字节相同**
（实测比对，见下）。

### 外观条目（23 字节）

```text
u8   槽位
i32  显示部件标识
i32  常量 4          <- 其后那个四字节字段的长度
4B   扩展数据
u8   状态
i32  关联部件标识
u32  强化值
u8   标志
```

**条目开头的 9 字节由样本确证**：索引 44 是槽位、45..48 是显示部件标识、49..52 是那个
字面量 `4`。其中非零的只有 44..49（`4` 的高三字节本就是零），但字段边界由这 9 字节
本身给出。索引 50..93 共 44 字节全为零。

**23 这个长度本身没有被样本约束。** 外观条目与尾部合计 59 字节；由于中间全零，凡满足
「外观 + 尾部 = 59」的任何切分——23+36、27+32、19+40——都产生**完全相同的线上字节**，
实机渲染也完全相同。因此本记录此前写的「两重印证」是循环的：那条差值以「尾部 36」为前提，
而「尾部 36」的唯一来源就是参考实现。

该区间唯一的锚点是索引 94 的 `0xFF`，而它只在接受参考实现的尾部内部布局时才把切分钉住。
单凭这一条，结论的支撑只是一条上游转录。

**判定它的是另一个构造：一个零外观的条目，后面还跟着条目。** 零外观条目里没有任何外观
字节，它的长度就等于 `26 + 尾部`，于是尾部长度直接决定其后条目的起点：

| 切分 | 三角色（槽位 1 零外观）的 body 总长 |
|---|---:|
| 外观 23 / 尾部 36 | 250 |
| 外观 27 / 尾部 32 | 246 |

本仓按 23/36 发出 250 字节，A21 客户端把三个角色**全部正确渲染**（名字、职业、等级皆对）。
若客户端的读法是 27/32，它读完第二条后会停在偏移 161，而第三条实际始于 165——第三条的
槽位与名字长度会从第二条尾部的零字节里读出来，渲染不可能正确。

**关键在于"零外观的那条后面还得有条目"**：单角色的花名册、或零外观排在最后的花名册，
客户端读满 `count` 就停，多写的字节被忽略，两种切分产生的可观察行为完全相同。
本记录此前只有单角色样本，因此当时确实判不了。

归档：[`patterns/data/traces/a21-world-entry-20260823.log`](../../patterns/data/traces/a21-world-entry-20260823.log)
的 `[J]` 节。


**本记录此前记的尾部是 32 字节**，末 11 字节为 `00 00 00 03 00 00 04 00 00 00 00`。
那是 A12 的形状，对该客户端成立。

长度错的代价不是某个字段显示错：**它让其后每一条角色条目整体错位**，所以一个角色的账号
看不出问题，两个角色的账号会丢掉第二个。

尾部的 36 字节因此与外观条目的 23 字节同为 `High`：两者是同一次判定的两面。

**该判定只覆盖到"一条外观"**。观察过的角色最多带一条，所以"n 条就是 23×n"是按定长条目
外推的，与本仓存储 blob 的步长一致但没有独立样本。带两条外观的角色会顺带把它确定下来。
**仍未确定的是尾部内部的字段划分**——`0xFF` 落在第 27 字节这一点只有参考实现支撑，
样本里那一带除它以外全为零。若将来需要在尾部里放非零值，先补这条证据。

### 这两个字节是什么：一个样本判不了

等级之后的 `0x0B` `0x01` 在唯一的观察样本里就是这两个值。本仓的入场路径把这一带建模为
两个 32 位进度值加一个 16 位保留字段，按那种读法同一批字节意味着首个进度值为 267。

倾向"常量"的迹象有两条：这两个字节在同一角色的其余入场报文（子类型 `0x00`/`0x01`）里
一次都没有出现；参考实现也把它们写成字面量。但两条都不足以定论。

**判定它最便宜的证据**：第二个进度值不同的角色。在那之前本仓按观察到的字节实现，
而一个猜错的代价至多是一个说不出名字的字段显示错。

### 2026-08-25：子类型 0 的无生物三元组

判据是本仓入场批次与 A21 参照会话的逐帧对账，归档于
[a21-entry-batch-diff-20260825](../../patterns/data/traces/a21-entry-batch-diff-20260825.md)。

**A21 不用零来表示「没有生物」。** 参照那个角色没有生物，它在这三个字段上写的是：

```text
FF FF FF FF                        物品 id
0C 00 00 00  E6 B2 A1 E6 9C 89 E5 AE A0 E7 89 A9   dstr("没有宠物")
FF                                 状态
```

共 21 字节。A12 写的是「物品 id 0 + 空串 + 状态 0」，共 9 字节。那句 `没有宠物` 是客户端自己的
「无宠物」文案，所以这个字段是**服务端要填的显示名**，不是客户端在空串时自行替换的。

有生物的情形在 A21 上未被观察到——参照全程没有装备过生物，所以那一支保持 A12 的写法未动。

### 2026-08-25：子类型 0 的尾部是一个 64 字节定长块

**这一节替换了先前那份「尾部仍未对齐」的分析。** 那份分析算出「本仓比参照多 17 字节」并
列了几个锚点，方向是对的，但它是在**改动之前**的构建上量的：当时子类型 0 还没写 A21 的
无生物三元组，所以文里的偏移与那个 172 字节的长度都已经不成立。锚点法本身也只是从一份几乎
全零的样本上推的，得不出字段。

真正把它定死的是**产出那份参照的服务端自己**：A21 在存活字节之后写的不是几十个字段，而是
一个**固定的 64 字节块**，只有三个补丁点——副职业类型在 `+23`、其经验在 `+24`、它称作
channel id 的 `u16` 在 `+59`。把那个常量与参照抓到的 64 字节逐字节比，**只差一处**：偏移 59
上是 2，正是第三个补丁点。

改完之后：

| | 参照 | 本仓 |
|---|---:|---:|
| body | 188 | 167 |
| 扣掉名字（`dstr`）与外观件后的基数 | **157** | **157** |
| 最后 64 字节 | — | **与参照逐字节相同** |

本仓角色名 6 字节、外观 0 件，参照名 4 字节、外观 1 件，`157 + 10 + 0 = 167`、
`157 + 8 + 23 = 188`，两边都闭合。剩下的差异只有角色数据。

**这一块是转抄，不是建模。** 除三个补丁点外那 61 个字节代表什么没有确证。被它取代的那些字段
（公会等级、混沌值、变身、硬核计数、疲劳、频道、表情、PvP 名次）**没有从领域里消失**，只是
在 A21 的线上没有已知的位置——按旧客户端的偏移写出去不是「部分正确」而是错的：块短了 17 字节，
其后每个字段都落在 A21 不用的偏移上。上游那条注释值得照抄一遍：这个块的形状是特意选的，
为的是**不让客户端把一个陈旧的进度值当成字符串长度读**。

### 2026-08-25：子类型 1 的 dimension 卷同样是固定的

A21 的 dimension 列表不是「角色存了什么就发什么」，而是**固定 26 个键**，每次都发，存储里
有该键时才用存储的一对值覆盖。其后是一段 9 字节常量、`ManageLevel`、一个 `u32`（上游称
manage point，参照为 0），再一段 16 字节常量。

本仓原本发存储列表——新角色为空，于是声明 0 而参照声明 26，其后一切早了 156 字节。改完之后
本仓 330 字节，与参照 519 扣掉 3 件装备（3×60）和 3 条技能（3×3）后的 330 相等，
**最后 187 字节与参照逐字节相同**。

### 一处未解释的重复

技能树索引现在有两个来源：子类型 0 的定长块里 `+61` 是常量 `0xFF`，子类型 1 仍写
`SkillTreeIndexOnTheWire(SkillTreeIndex)`。参照那个角色第二技能页未购买（存储 -1 → 线上
`0xFF`），所以两种读法在参照上不可区分——**`+61` 是不是技能树索引，没有证据**。
上游把它当常量，本仓照此处理；真实值仍由子类型 1 送达。

### 2026-09-07：时装槽的条目在放大值之后多一段外观块

上面那张 60 字节表是**普通穿戴槽**的。**时装槽（0..11）不是 60 字节**——它在
`22 amplifyValue` 之后、`24 编年史条数` 之前插一段外观块，其后的一切顺延：

```
偏移  长度  字段
 24     4   珠宝槽长度 L                ← 时装为 18，非时装为 0
 28     L   珠宝槽前 L 字节             ← 非时装时这一段不存在
 28+L   4   颜色长度，恒 4
 32+L   2   Color1                     ← 非时装为 0
 34+L   2   Color2                     ← 非时装为 0
```

所以时装槽的条目比普通槽长 **30 字节**（`4+18+4+2+2`），
时装槽里放着非时装时长 **12 字节**（`4+0+4+2+2`）。

**珠宝槽发 18 而不是存储的 30。** 存储是 `SocketCount 5 × EntrySize 6 = 30`，A21 只发前 3 个孔。
依据是**上游源码读出**：参照服务器三个写入方共用一个 `A21AvatarJewelBytes = 18`
（`ItemListProtocolWriter.cs` 第 89、193 行与 `MailboxHandler.cs` 第 1127 行）。

**这个长度实机验不了，也没有验过。** 块自带长度，客户端按给的长度读，发 30 一样对齐一样不崩；
而至今测过的时装珠宝槽全是零，18 个零与 30 个零在屏幕上没有差别。上一个成果
「11 件时装实机全过」证明的是**外观块的形状机制**成立，不是这个长度正确。

参照会话里没有人穿时装，所以这一段**没有线级样本**，形状来自本仓写入方与上游写入方的对照。

**本仓 2026-09-07 之前在这里发 30**，与同期已改成 18 的背包家族（NOTI `0x000D` / `0x000E`）
不一致。三条路径现已共用同一处常量，见 `Dfo.Server.Protocol.Game.AvatarJewelSocketOnTheWire`。
