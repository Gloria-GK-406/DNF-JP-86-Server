## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Server → Client |
| Command | `0x00` NOTI |
| Type | `0x0289` |
| Role | Notification |
| 阶段 | 实现服务端功能 |

**触发时机与响应顺序不记在本页**，它们属于流程层：见 [flow-login](../../patterns/flow-login.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

客户端**从不请求**本帧。旧服把它放在应答角色列表的同一批里推出，本实现照做。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。body 固定 **8 字节**：

```c
struct Body0289 {
    u32 honorLevel;   // 本服务端恒 0
    u32 honorExp;     // 本服务端恒 0
};
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 4 | LE `u32` | 荣誉等级 | Hypothesis | `E-001` |
| 4 | 4 | LE `u32` | 荣誉经验 | Hypothesis | `E-001` |

旧服在此处留有注释，称客户端直接把第一个字段显示为 Lv、不能写成经验。该说法**未经独立验证**。

## Client reversing evidence

| Evidence | Kind | Location | Supports |
|---|---|---|---|
| `E-001` | static | 旧服 `HonorLevelPacketBuilder.BuildInfoBody`（`d51e74b`） | 8 字节双 `u32` 布局 |

**客户端普查表里 `0x0289` 没有任何注册记录。** 普查表只含静态注册、缺 439 条运行时注册，
所以这不能证明客户端不处理它。字段**含义**仍然只有旧服 builder 作依据——
它被实现进去，是因为旧服在同一批里发过它，而不是因为我们知道客户端需要它。

> **本页与文末的读取跟踪互相矛盾，尚未裁决。** 跟踪记录客户端读了两个 `u32`
> 并完整消费到偏移 8（这与"客户端可能根本不处理它"冲突），但它测到偏移 0 的值是 **1**，
> 而本实现声称恒发 `AccountHonorLevel.None`（两个 0）。此外那两个读取者 RVA
> （`0x001703EF` / `0x001703F8`）远低于本二进制其余读取者的地址区间，归属本身可疑。
> 在裁决之前，不要据这条跟踪断言"客户端确实消费本帧"，也不要据本页断言"服务端恒发 0"。
> 最便宜的裁决：发一个非零 `honorLevel` 再抓一次跟踪，看读到的值是否跟着变。

发送是安全的：客户端没注册的 type 会被它自己的注册表查找丢弃，机制与本服务端丢弃未注册入站键
完全相同。

## 实测字段表（运行时读取跟踪）

客户端**实际**读取这条协议的方式，由运行时读取跟踪测得（做法见 [game-receive](../../patterns/game-receive.md#四个原语是唯一出口)）。

**本节优先于机器区的 Body 表。** 机器区那张表由静态走图产出，在 S→C 上普遍止步于打包区，给出的是下界；载荷多形时它只描述其中一形，却读起来像描述了整条协议。本节是实测，但**只给边界，不给含义**——`含义` 一列留给人填，偏移已确证之后用实机改值做差分是最便宜的填法。
