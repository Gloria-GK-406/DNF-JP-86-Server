# NOTI `0x0381` `USER_BUY_RESTRICT_UPDATE_ITEM_LIST`

<!-- rks:origin:a21 -->

**手写页，A21 原生。** 生成器不会为这个号产出页面：普查在 A21 客户端里**找不到它的接收
handler**，而生成器的文档集是按「注册了 handler 的 type」建的。它仍然值得有一页，因为
A21 参照服务器**确实在入场批次里发它**，本仓也发。

## 身份

| 项 | 值 | 来源 |
|---|---|---|
| Endpoint | Game | 帧协议基线 |
| Direction | Server → Client | 参照会话 |
| Command 族 | `0x00`（NOTI） | 参照会话帧头 |
| Type | `0x0381` | 同上 |
| 名称（A21） | `USER_BUY_RESTRICT_UPDATE_ITEM_LIST` | `PacketTypesA21.cs` |
| 名称（A12） | `COLLECT_BOX` | A12 的 `PacketTypes.cs`；A21 把 `COLLECT_BOX` 移到了 `0x03EB` |

## 客户端不收它

A21 的接收注册表普查里，`0x0381` 上**没有任何 handler**——两张表（CMD/NOTI）都没有。
客户端自己的注册表查不到就丢弃，与本仓丢弃未注册的入站键是同一形状。

**这不是「不该发」的理由。** 参照服务器照发不误，而参照那一局是跑通的。

## 参照发的两帧

入场批次里两帧，各 8 字节：

```text
01 01 FF FF FF FF 00 00
02 01 FF FF FF FF 00 00
```

首字节递增（1、2），其余相同。本仓在同一位置发的两帧与之**逐字节相同**——因为这两帧的字节
当初就是从这份抓包抄下来的。

## 一次把判据用反了的记录

本仓一度把这条协议改发到 `0x03EB`，理由是「A21 的 `COLLECT_BOX` 是 `0x03EB`，而客户端在
`0x0381` 上没有 handler，所以发过去等于没发」。两个前提都成立，结论却是反的：

- 号一直是对的——参照就在 `0x0381` 上发这个载荷；
- `0x03EB` 在 A21 上**有** handler（RVA `0x008A7490`），而参照全程不发它。

于是那次改动把一条协议的 body 从「一个不存在的 handler」挪到了「一个活着的、期待别种格式的
handler」，严格更糟。已改回。教训与 [world-entry](../../patterns/world-entry.md) 里记的那条
相同：**表能给假设，抓包才能定论；两者冲突时以抓包为准。**

## 服务端实现映射

`Server/src/Dfo.Server.Protocol/Game/StateSynchronization/StateSynchronizationMessages.cs`
的 `CollectionBoxStateMessage`。名字仍沿用 A12 的语义（它读的是
`character_collectbox_slots`），因为**这个 body 表示什么并没有确证**——只知道参照在这个号上
发这些字节。等到有证据说明它是收集箱还是购买限制表，再改名字。
