## A21

**2026-08-24。** 上面的机器区由 **A12** 客户端（SHA-256 `F78F0AEA…`）的静态普查生成。
本节记录 **A21** 客户端（SHA-256 `1F8244D3…`）上不同的部分。判据除另有注明外，都是一份
A21 参照会话，归档于
[a21-world-entry-20260823.log](../../patterns/data/traces/a21-world-entry-20260823.log)
（section L 是入场序列的逐帧顺序）。

A21 在 `0x0016 USER_POSITION` 之后发这一帧（section L 第 60 帧）。

参照 body 508 字节，结构由步长解出：

```text
[0]      标志/子类型（参照为 0）
[1..2]   u16 条目数（参照为 5）
之后     每条 101 字节，条目内偏移 69 处是 0xFF
```

`3 + 5×101 = 508`，闭合。参照的五条 id 是 `0xB1`..`0xB5`，与该角色 `items` 表里
`list_type=0` 的五行一一对应；每条的 `[2:]` 与库里的 `item_core` **前 81 字节相同**，
其后还有 18 字节未解释。

服务端目前**发空表**（`00 00 00`，条目数 0），因为条目内容尚未建模。

### 2026-08-25：入场批次逐帧对账

判据是本仓入场批次与 A21 参照会话的逐帧对账，归档于
[a21-entry-batch-diff-20260825](../../patterns/data/traces/a21-entry-batch-diff-20260825.md)。

**入场窗口里参照只发一帧，而且不是空信封。** 那一帧就是当日补给的实际结果（5 条，
id `0xB1`..`0xB5`），位置紧接 `0x0016 USER_POSITION` 之后、`0x0165` 之前。

本仓此前在批次里发一帧空表（`00 00 00`），补给的真结果在四帧之后另发一帧——于是参照有一帧
的地方本仓有两帧，且两帧都不在参照的位置上。现在补给命令与它的增量都提到闸点之后的尾帧
**之前**执行，空信封撤掉。

上文「服务端目前发空表」那句到此为止：它描述的是那次改动之前的状态。

### 补记：同一天第二次进场没有这一帧

当日补给每角色每天只发一次。撤掉空信封之后，`CommittedUpdates` 为空时这一帧一帧都不发——
所以「与参照多重集一致」只在当天首次进入该角色时成立。

参照那一局是不是首次进场无从判断，因此**无法区分「A21 总是发一帧 `0x000E`」与「因为补给
发生了才发」**。两种读法在现有证据下等价；如果后者为真，现在的行为是对的，如果前者为真，
非补给日就少一帧。取得一份「同一角色当天第二次进场」的参照即可判定。

### 2026-09-01：第二个调用方——通关翻牌

在此之前本帧只有一个调用方，就是上面那条入场补给。现在有第二个：**通关结算的翻牌**
（`CMD 0x0047 SELECT_CARD`）。玩家翻开一个牌位，牌位上的装备进背包，本帧说明背包哪一格
变成了什么。

**参照服务端确实在翻牌之后发本帧，而且紧接应答。** 判据是参照服务端自己的报文日志
`ServerS4A21/_reference-backup-20260826/packet_log.txt`（本仓之外），822–825 行连续两帧：

```text
SEND cmd=0x01 type=0x0047 len=48  body=(33B)  [01 00 FF 00 00 FF FF 00 00 FF FF …]
SEND cmd=0x00 type=0x000E len=119 body=(104B) [00 01 00 00 00 00 00 00 00 91 00 …]
```

先应答后通知，中间没有别的帧。同一份日志 236 行是入场那一帧（508 字节，5 条，
`0xB1`..`0xB5`），与本页 A21 一节记的完全一致，所以这份日志与那一节是同一类证据。

**这一帧的 body 闭合于 `3 + 1×101 = 104`。** 列表类型 `0x00`（主背包），条目数 1，
条目按已记的布局读出：槽位 `0`、物品 id `0`、数量 `145`。

**但这条参照样本装的不是一件装备。** 同一份日志 148 行是参照自己的主背包全量快照
（`NOTI 0x000D`，14 条），它的头三条就是 `槽 0 / id 0`、`槽 1 / id 1`、`槽 2 / id 2`，
数量都是 0——这三个是虚拟槽，id 等于槽号。所以参照那一次翻牌用本帧告知的，是虚拟槽 0
的数量变成了 145，而不是某一格里多了一件东西。**因此「参照如何用本帧描述一件装备的到货」
并无样本**——本仓翻牌到货写的是普通条目，依据是本帧条目区的布局本身（已闭合），不是对
这条参照样本的模仿。

同样**无从判断的**还有：参照是不是每次翻牌都发这一帧，还是只在有东西可说时才发。只有一份
样本，而那一次恰好有变化。

**顺序在本仓的实现。** 应答与本帧在同一次发送里发出，应答在前；这既是上面那段参照的顺序，
也与地面拾取（`CMD 0x002B` 的应答后跟 `NOTI 0x0027`）一致。

**实现映射变了一处。** 该帧此前是 `Game/StateSynchronization/` 切片内的类型；
`AGENTS.md` 的「切片内不跨协议引用」不许翻牌切片伸手进去拿，所以它连同它与入场全量快照
共用的条目写法一起，被上提到端点层
`Server/src/Dfo.Server.Protocol/Game/GameInventoryDelivery.cs`。上提只是搬家：入场路径的
整帧 SHA-256 判据（`InventoryDeltaLiftTests`）用的是上提之前就记录在案的那个值，仍然通过。

## 槽 0 承载随身金币，且是赋值而非累加

**2026-09-03。** 本仓实现角色随身金币时给这一帧添了第三个发送方，并确立了一条此前未取证的语义。

**第三个发送方。**此前只有世界进入的每日补给与通关翻牌的落袋在发它；现在**翻牌的金币收付**与
**地面拾取金币**也各发一帧，容器都是主背包（listType=0），条目是槽 0、itemId 0，条目的第三个
字段（`Value`）承载金额。形状与登录全量帧 NOTI 0x000D 为槽 0 写出的 101 字节逐字段一致。

**赋值而非累加 —— 这是新确立的事实。**同一个金额有两种语言在传：

| 帧 | 语义 | 用在哪 |
|---|---|---|
| NOTI `0x0027` `GET_ITEM`（金币形态） | **累加**，body 偏移 +6 是本次拾取的增量 | 地面拾取 |
| NOTI `0x000E` 槽 0 | **赋值**，条目里是变更后的总额 | 翻牌收付；拾取时随增量帧一并发出以校正 |

判据是实机的：角色持有 200000，付费翻牌扣 580、免费翻牌给 47，客户端显示正常且与服务端所存的
199467 一致。**若 0x000E 是累加**，同一次交换后客户端会显示约 399467，玩家会立刻看见。
（参照实现侧的旁证：`DropItemBuilder.cs:90` 写进 GET_ITEM 的是本次增量而非余额，而落库另走
`DropService.cs:251` → `TryGrantGold` → `SetMainVirtualCount(0, 0, target)`；若客户端对 GET_ITEM
是赋值，参照实现自己的显示在第二次拾取后就会崩。）

**两种语言不能对同一次变动各说一遍而不校正。**地面拾取现在两帧都发：增量帧让玩家立刻看到
「捡到多少」，紧随的赋值帧把总额钉死。二者在寻常拾取上一致；**只有携带上限截断时才不一致**，
而那正是单发增量帧会让客户端与服务端错开、直到下次登录才对齐的情形。

## 补记（2026-09-07）：单条长度随容器而变，原文那个 `0x7E` 是旧客户端的数

上面字段表里「时装为 `0x7E` 字节」应作 **131**。`0x7E` = 126 是 **A12** 的装扮条目总长
（`84 + 4 + 30 + 4 + 4`）；A21 的普通条目由 84 涨到 101，装扮条目由 126 涨到 131。

上游 `ItemListUpdateBuilder.GetUpdateEntrySize` 把这件事说得很直白：

```
Avatar                                        → AvatarEntrySize  = 131
Equipment / Main / PersonalCargo /
AccountCargo / QuickSlot / Pet / GuildMedal   → CommonEntrySize  = 101
default                                       → CommonEntrySize  = 101
```

**但这张表只管空条目，不能用来证明填充条目的规则——上一版这里写错了。**
`GetUpdateEntrySize` 在上游只有 **1 个调用点**（`ItemListUpdateBuilder.cs:106`，在
`BuildEmptyUpdates` 里）。上游写**填充**条目走 `ItemListPacketBuilder.TryWriteOnlineEntry`，
它**收下 `itemSpace` 却只看 `core.ItemKind == ItemCore.KindAvatar`**（`:196`）来决定调
`WriteAvatarEntry126`——也就是**按物品种类**，正是本仓这一轮否掉的规则。

上游这样写不会崩，是因为它把时装**锁死在装扮栏**：`ItemSlotBoundService.TryGetSlotRange`
的 `case ItemCore.KindAvatar:` 直接 `listType = InventoryListType.Avatar`，
时装进不了主背包，于是「按种类」与「按容器」在上游恰好重合。

**本仓没有这个约束**——实机把时装放进主背包能正常显示。所以对本仓两条规则真的不同，
本仓**有意选了按容器**，依据是客户端自己的 `0x01637740`（未虚拟化，三行分支），
不是上游。两帧的详细规则、外观块字节形状、两种错法各自造成的崩溃，
统一记在 [NOTI-0x000D.md](NOTI-0x000D.md) 的「补记（2026-09-07，同日第二次）」一节。

> **一条待办，附带一个必须同时满足的条件**：两条规则要重新重合，上游靠的是**两道门**，
> 缺一不可：
>
> 1. 时装**出不去**装扮栏——`ItemSlotBoundService.TryGetSlotRange` 的
>    `case ItemCore.KindAvatar:` 直接把 `listType` 定为 `Avatar`；
> 2. 非时装**进不来**装扮栏——同文件 `TryGetItemKindBySlot` 的
>    `case InventoryListType.Avatar: itemKind = ItemCore.KindAvatar;`。
>
> **只做第 1 道会重新把客户端打崩。** 本仓明确允许装扮栏放非时装（这正是 RQ-006 的理由，
> 实机也真放过一件普通堆叠物 8474），而客户端对选择子 1 是**无条件**读外观块的；
> 若那时改成按种类，装扮栏里的非时装条目就短 30 字节，
> 直接回到本轮刚修掉的 `STATUS_ACCESS_VIOLATION`。
>

> **2026-09-07 更正**：第 2 道门的**移动侧**已经立起来了——装扮栏被接进 `MoveItemSpace`，
> 一次移动只放时装进装扮栏（`IItemSlotRuleService.CanOccupySlot`，`0..209` 且
> `WorldClass == Avatar`）。**但上面那段论证不受影响，两个理由：**
> 其一，**门只管移动，不管既有的行**——存储侧从未禁止装扮栏里放非时装，
> 实机放过的那件 8474 至今还能存在，编码器仍然必须为它写外观块；

## 2026-09-20：账号级虚拟材料的绝对值更新

分解结算新增了本帧的账号虚拟材料调用方。六种晶体使用主背包虚拟槽 `354..359`，五种
品级灵魂使用 `360..364`；每个条目的 `Value` 都是**事务提交后的账号总量**，不是本次增加量。
同一次 `CMD 0x001A DISJOINT_ITEM` 成功响应中的材料条目仍携带本次增加量，因此两者职责为：

1. `CMD 0x001A` 应答说明本次分解产出了什么；
2. `NOTI 0x000E` 把客户端的账号虚拟槽校正到最终绝对值。

这沿用本页已经实机确认的“虚拟槽更新是赋值”语义。新增发送路径先由编码与应用层测试闭合，
随后在 2026-09-20 的主干 Release 上完成 A21 实机验收：分解后的客户端材料状态即时恢复正确，
切换同账号角色后晶体与五种品级灵魂余额保持一致。该观察确认了账号虚拟材料绝对值投影的
**客户端效果**，因此这一调用场景可标为 `ClientVerified`。

本次验收没有归档修复后的 S2C body；不能由 UI 结果反推这一次实际发送的条目数、顺序或逐字节
内容，也不能把它标为 `WireCaptured`。换角色后的相同余额还同时经过入场 `NOTI 0x000D`，所以
它证明的是 `0x000E` 运行时更新与 `0x000D` 重载最终收敛到同一账号状态，而不是仅凭换角色现象
单独证明某一帧。跨协议顺序见[装备分解流程](../../patterns/flow-equipment-disjoint.md)。
