# `0x0001` LOGIN response（CMD）

> 名称沿用请求侧的 `LOGIN`。本记录只描述 **CMD**（`command = 0x01`）方向的响应。
> 同一 type 在 **NOTI**（`command = 0x00`）下是另一条完全不同的消息（初始连接通知），
> 必须另建记录——见[命名与身份](../../catalog.md#命名与身份)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Server → Client |
| Command | `0x01`（CMD） |
| Type | `0x0001` |
| Role | Response——对 C→S CMD `0x0001` LOGIN 的回应 |
| Trigger | 服务端接受登录后立即发出 |
| Expected response | 无需回帧，但客户端在**处理本帧的过程中**发出 C→S `0x0008` GET_USERINFO |
| 阶段 | 确定语义 |

尚未进入 `双向验证结束`：body 尾部 24 字节还不能被记录的布局无损解释（见
[Unknowns](#unknowns-and-next-evidence)）。

### 客户端 handler 与因果链

本帧由 **CMD 表**（`command = 0x01`）的 handler `RVA 0x008C7E20` 处理。该 handler 内部
`+0x799` 与 `+0x886` 两处是 C→S `0x0008` 的构包点，因此抓包里的
`recv 0x0001 → send 0x0008` 是**因果**而非顺序——机制同
[`0x008F`](../client-to-server/0x008F.md) 的 Trigger 证据。

### 主机名 + 两个端口构成一个端点（`E-004`）

三者读完后一起交给 `RVA 0x01DCBEA0`，本记录称之为 `SetEndpoint(host, portA, portB)`：

```asm
mov  byte  [esi+0xB78], 1        ; 置「已配置」标志
… wcslen(host)，上限 259 字符 …
call 0x211FAAA                    ; host → this+0x94C（宽字符串）
mov  dword [esi+0xB58], edx       ; portB
mov  dword [esi+0xB54], edi       ; portA
mov  dword [esi+0xD80], edi       ; portA 再存一份
… host 再拷一份到 this+0xB80 …
```

**这一组配的是客户端的公告/消息端点**——见 [Verification](#verification) 的实机结果。

## Server and historical evidence

服务端实现自旧服移植，body 布局此前**从未经抓包确认**——协议清单曾明确标注
「`EncodeSuccess` 内多个字段是旧服移植的魔数」。移植版本在 offset 4 多写了一个 `0x00`
（见[逆向工作日志](#逆向工作日志)），2026-08-16 已修正。

`UnknownPort` 这个配置名来自移植：它其实是**一对**端点端口，目前两个槽被同一个配置值填充。

## Verification

- Parser/codec vectors：`GameLoginCodecTests.EncodeSuccess_PreservesLegacyLoginBody` 逐字段断言
  offset 0..3 / 4 / 8 / 12 / 12+len / 16+len 与 body 总长
- Boundary cases：`GameLoginOptions` 校验两个端口在 `1..65535`；`ServerIp` 上限 256 ASCII 字节
  （注意客户端 `ReadDString` 的 `maxLen = 0x10`，主机名超过 15 字符会被客户端放弃，
  服务端校验比客户端宽——见 Unknowns）
- 条件分支/重复项：本 body 无分支
- Response count/order：不需要回帧；客户端在 handler 内发出 `0x0008`
- Integration：`GameLoginIntegrationTests` 用真实 TCP + SQLite 断言逐字节帧
- **Real-client result（`E-005`）**：2026-08-16 实机会话，body 53 字节，逐字段解出
  `10128` / `"127.0.0.1"` / `17200` / `17200`。修复前后的**行为差异**是本记录最强的证据：
  修复前客户端从不弹出公告窗口，修复后登录到角色列表即弹出韩文「던파 소식」（DNF 消息）
  窗口。两次会话之间只有这一处字节差异，因此 offset 12/12+len/16+len 三个字段确实驱动
  公告端点的配置。

## 逆向工作日志

### 1. 多写一个字节，症状却只出现在很远的地方

移植版 body 在 offset 4 多写了一个 `0x00`（原来是 `0x01,18,0x00,Environment,0x00` **五个** u8
再接端口），而客户端只读**四个** u8 就开始读 4 字节端口。错位一字节后：

| 客户端字段 | 实际读到 | 后果 |
|---|---|---|
| offset 4 端口 | `00 90 27 00` = `0x279000` | 垃圾端口 |
| 长度前缀 | `00 09 00 00` = 2304 | ≥ `maxLen 0x10` → `ReadDString` 放弃，主机名为空 |
| 两个端点端口 | `"\0127"`、`".0.0"` | 端口变成地址文本的 ASCII |

**登录照常成功**，因为客户端据以推进的是 offset 1 和 3 两个布尔，都在错位点之前；
错位只让公告端点配不出来，而那是登录之后才用的功能。这是一个典型的
「协议错了但主流程不报错」——只能靠逐字段对齐发现，抓包看长度是看不出来的。

判定多余的是 offset 4 而不是 offset 2：删 offset 4 时 offset 0..3 的现有含义全部不变
（`Environment` 仍落在 offset 3 的布尔上）；删 offset 2 会把 `Environment` 挤到 offset 3
之前、并让那个布尔变成 `0x00`。

### 2. 「不是端口，是时间戳」这个死胡同

追 offset 12+len / 16+len 两个 u32 时，先在同一个 handler 里找到一处连续两个 `ReadU32`，
随后被 `/3600`、`/86400`、`/31536000` 除、并把两值之和送进 `localtime`（`tm_year + 1900`
的 `add esi, 0x76C` 是铁证），于是判定「这两个是时间戳 + 剩余秒数」。

**那是同一个 handler 另一条分支上的另一个记录**（形状为 `{u16 kind, u32 时间戳, u32 秒数}`，
`kind` 取 3/4/5 选不同的到期提示文案）。真正的端口对在更靠前的位置，中间隔着一次
`ReadDString`——而当时还没识别出 `0x01C920A0` 会消费入站流，误判它不读流，导致偏移对不上。

**教训**：在同一个大 handler 里按"找到形状匹配的指令"定位字段是不可靠的；必须**按读取顺序
逐个原语走下来**，并且先把所有会消费流的辅助函数识别全（尤其是包了一层的字符串读取器）。

### 3. 行为差异比字节更能定性

字节对齐只能证明"服务端发的和客户端读的一致"，证明不了字段**是什么**。修复前后的行为差异
（公告窗口从不出现 → 出现）把 `(host, portA, portB)` 的用途一次性钉到了公告/消息端点上，
而这是任何静态分析都给不出的结论。做协议时值得刻意制造这种 A/B 对照。
