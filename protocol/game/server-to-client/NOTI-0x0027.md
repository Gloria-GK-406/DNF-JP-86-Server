## A21

**2026-08-26。** 判据是上游构包器 `DropItemBuilder.BuildPickupItem` 与本仓实机对照。归档见
[a21-room-clear-20260826](../../patterns/data/traces/a21-room-clear-20260826.md)。

**这一帧是 `CMD 0x002B GET_ITEM` 的第二帧回答**，跟在 1 字节的 CMD `01` 之后——客户端先消费那一
字节，再解析这一帧。定长 18 字节：

```text
u16  srcSlot            ← 请求里那个号，原样送回
u16  拾取者 actorId
u8   1
i32  0
i32  0
u16  拾取者 actorId     ← 再写一次
u16  目标背包槽位
u8   0
```

**拾取者写了两遍。** 前一对是「谁捡的」，后一对是「现在谁持有」；单人拾取时两者相同，组队分配
物品时才会分开。中间两个 dword 上游在本仓走得到的每条路径上都写 0。

本仓实测（教学第二间房，护肩 14400 落到背包 9 号槽）：

```text
01 00 01 00 01 00 00 00 00 00 00 00 00 01 00 09 00 00
```

**入库的那一件带着它落地时的那两个值。** 耐久取物品自身 `[durability]`（14400 是 25），
实例值取 `START_MAP` 掉落记录 +7 处发出去的那个数——上游参照会话里落地的护肩与穿在身上的那件
带着同一个值，所以这里是兑现已经宣告过的数，而不是另造一个。库里那行为
`kind=1 itemId=14400 value=512242377 durability=25`，与帧里发出去的一致。

**已拿走的不会再出现。** 房间地上有什么是每次描述房间时重新从档案里读的，所以运行状态里记的是
「哪一号已经被拿走」——否则走出房间再走回来就能再拿一次。编号在剔除之前完成，拿走第二件不会让
第三件改名。

## 组队观察者与动作边界（2026-09-16）

**Confirmed（A21 接收端静态控制流）。** handler `0x01185970` 在观察者路径上用后一份 actorId
调用 `0x019E2EF0` 查队伍成员，并把成员与地面对象交给 `0x0165E4C0`；该调用负责地面物的远端归属/
移除。它不会走 `0x01185BBC` 开始的本地入包/UI 分支，也没有让远端 avatar 执行拾取动作的调用。

因此本协议的服务端职责是权威表达“谁拿走了哪个地面物”。角色弯腰等拾取动作属于客户端 P2P 表现
层，不能通过向观察者重复 CMD 应答或猜测 0x0027 字段来补造。双客户端实测也与此一致：UDP 直连与
移动持续正常，观察者收到本帧后地面物正确消失，但不播放角色拾取动作。

服务端运行期以 `DungeonPickupChange` 作为共享事实：DungeonRun 在耐久化入包/金币成功后原子提交
一次变更，记录 RunId、单调 revision、拾取者、地面编号、种类和仍在场的语义接收者；协议投影层再
把角色身份解析为当前连接代次。领域状态不保存 connection 或 Session。
