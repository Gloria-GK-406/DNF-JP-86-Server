## 偏移 14 是地图 id，不是迷宫序号——用错会崩

上游那个字段在类型里叫 `MazeSumInfo.Index`，名字读起来像"迷宫序号"，**它不是**。两条旁证：

- 血色祭坛分支往同一个位置传的是 `(ushort)sentMapId`（`DungeonMapHandler.cs:568`）
- 深渊那段日志把它和另一个 map id 并列打印：`hellMap={maze.Index} normalMap={hellRoomInfo.NormalMapId}`

迷宫序号另有其位——它是 [`0x001C`](NOTI-0x001C.md) 里的 `modeFlag`，而且是 `u8`。

**实机判别（2026-08-18）**：这里误写迷宫序号 `0` 时，客户端进度条正常走满，
随后**切换时黑屏、等待数秒、进程崩溃**——即"加载一个不存在的地图"的表现。
改成房间地图 id（教程起点房间 `61000`）后角色正常站入。

*教训*：上游的字段名是转录来的线索，不是定义。一个叫 `Index` 的字段可以是 id。

**23 字节，不是 21。**

两处不同：

1. **房间地图号是 `i32`，不是 `u16`。** 值没变，宽度错了——这是两个字节里的两个。
2. **偏移 7 那个字节默认是 2，不是 0。** 本仓把它当深渊模式标志写 0；A21 的构包器把它
   默认成 2（普通副本标记），参照会话的两帧 `START_MAP` 也都是 2。

顺带纠正一个曾经的猜测：`[0]` 就是当前格的 X。参照第二帧 `01 01 00 …` 是 X=1、Y=1，
不是「是否换图」。

### 2026-08-26（二）：预生成掉落块，房间可破坏物的内容

`actor` 表之后那个 `u8` 不是恒零的填充，是**房间里可破坏物所含物品的条数**，每条 19 字节：

```text
u8   对象序号（房间内声明顺序，从 0）
u16  地面物件号（从 1 起）
u32  itemTemplateId
u32  实例值
u16  耐久
u8   强化类型
u16  强化值
u16  扩展
u8   扩展
```

**注意与 `NOTI 0x0026 DIE_MONSTER` 的掉落记录不是同一形状**：那边每条 48 字节，多一个掉落组 id
和两段留白。同一件事，两帧写法不同。

**内容由两处声明合成，缺一不可：**

- 房间的 `.map` 的 `[special passive object]`，每条 `code x y z ? [item] 组号 数量 -1 -1 -1`
  （5 个整数 + 一个引号词 + 5 个整数）。只有引号词是 `[item]` 的才产出东西。
- 副本的 `.dgn` 的 `[special passive object item]`，是一串组：`组号 ? 条数`，其后 `条数` 对

耐久取自物品自己的 `[durability]`，与角色创建时穿上的那几件同源。

**判据。** 参照会话（魔枪士，副本 10005）第三间房 61032 发 63 字节：1 个 actor + **1 条掉落**，
`objIndex=0 ground=1 item=14400 耐久=25`。14400 是残破的牛皮护肩，其耐久正是 25，而该角色
此后确实把它穿在了 15 号槽上。本仓在鬼剑士副本 10000 的第二间房 61001 发 126 字节、同样 1 条、

### 2026-08-26（三）：地面物件号是客户端后来指认这件东西的名字

上一节把「地面物件号」记作「从 1 起」，那时它只是照抄参照帧的一个数。同日实机之后它有了意义：
玩家拾取时发的 [`CMD 0x002B GET_ITEM`](../client-to-server/0x002B.md) **只读两字节，就是这个号**。

于是它有两条约束：

- **同一间房内互不相同**——否则拾取请求指认不出是哪一件；
- **同一间房被重新描述时不变**——玩家走出去再走回来，客户端手里那个号还得对得上。

本仓因此把它定为**房间内按声明顺序数，从 1 起**，而不是像上游那样从一个整局递增计数器取。
上游 `PassiveObjectDropProjectionService` 把掉落登记进 `run.Drops` 字典、按 `SceneSlot` 分配，
本仓则每次重新从档案读房间、只在运行状态里记「哪一号已被拿走」。两种做法都满足上面两条；本仓
这一种不需要为一间房存一份掉落表。

**剔除在编号之后。** 已被拿走的那一条从表里去掉，但不重排剩下的号——先按房间的完整声明编号，
再滤掉拿走的。否则玩家拿了第二件之后，第三件就会改叫「2」。
### 2026-08-26(四):重访的房间是空的

**同日实机。** 玩家从 Boss 房走回上一间房,本仓把**整屋怪原样重发了** —— 而且序号和第一次进来时
完全相同(61002 两次都从 22670 起,Boss 房两次都从 4087 起)。客户端手里那批号刚被标记成死的,
现在又被当成活怪发过来。

上游有一个单独的重访构包器 `BuildStartMapRevisit`,写的是 **actorCount = 0、extraCount = 0** ——
固定 23 字节的空房间。这是对的:副本的门在房间清空前不开,所以能被重访的房间一定是已经清空的。

本仓改为重访时 actor 表与掉落块都发空。线级实测:第一次进 (1,1) 是 126 字节 / 4 个 actor / 1 条
掉落,走回 (0,1) 是 **23 字节 / firstEntry=0 / 0 个 actor**,再回 (1,1) 同样 23 字节。

**代价是:重访时地上没捡走的东西够不着了。** 上游也是这样。运行状态里"哪一号已被拿走"仍然记着,
所以不会重复发放。归档见 [a21-room-rules-and-leaving-20260826](../../patterns/data/traces/a21-room-rules-and-leaving-20260826.md)。

### 2026-08-27(五):包内索引是 actor 在**同类里**的位次,不是填充

**上游读法。** `DungeonNotificationBuilder.BuildStartMap` 的 actor 循环里,这个 `i32` 是
`monster.PacketIndex ?? (isApc ? apcIndex++ : normalIndex++)` —— **两个独立计数器**,以
`Type >= 5` 分界:怪物一路数,AI 角色另起一路数。本仓此前每条都写 0。

**为什么一直没暴露。** 新手副本第一间房 61000 正好是「一只怪 + 一个 AI 角色」,两者各是**自己
那类的第 0 个**,写 0 恰好是对的。第二间房 61001 有四条,才第一次分得出真假。

**实机症状(2026-08-27,玩家对照上游后报告)。** 第二间房的**上半场没有怪** —— 按地图声明那里
本该站两只 61359 —— 而箱子里的牛皮护肩已经躺在地上了。地图 `[monster]` 段的坐标解释了「上下
半场」:

```text
61670 1 0 517 426 ...   ← 下半场
61359 1 0 518 222 ...   ← 上半场
61670 1 0 608 426 ...   ← 下半场
61359 1 0 654 229 ...   ← 上半场
[special passive object] 37183 736 219 ...   ← 箱子也在上半场
```

四条 actor 都声称自己是第 0 个,客户端只留下了其中一条;教学里「打完这两只再开箱」那一步于是
没有可等的东西,直接推进到了发物品。

**逐字节对账。** 同一客户端、同一档案,上游 2026-08-27 那次跑完整教学发的 61001 房 `START_MAP`
是 126 字节;本仓按同样的 actor 表与掉落表构包,**只差三个字节** —— 偏移 42 / 63 / 84,正是第
1、2、3 条 actor 的包内索引低位:

| offset | 上游 | 本仓(修前) |
|---:|---|---|
| 42 | `01` | `00` |
| 63 | `02` | `00` |
| 84 | `03` | `00` |

这一帧现在有回归测试逐字节钉住（`DungeonEntryCodecTests`）。

**实机验证（2026-08-27）：** 改完之后玩家把鬼剑士教学（副本 10000）从头跑到尾——第二间房上路
那两只 61359 正常出现，牛皮护肩在打完之后才落地，四间房与通关全程没有卡点。**本节到此闭合。**

**顺带:种子是**房间**的,不是本局的。** 上游对每个新房取一次
`ServerRandom.Next() & ~0x40000`,四间房四个不同的值;本仓此前整局只发一个。改为由本局种子与
房间格子推导——重访重发同一间房仍得同一个值,这是上游靠缓存房间实例得到的性质——并照抄那个掩码。
**`0x40000` 这一位对客户端意味着什么没有读出来**,能说的只是上游从不把它置位。

归档见 [a21-start-map-actor-index-20260827](../../patterns/data/traces/a21-start-map-actor-index-20260827.md)。

### 2026-09-18：actor 等级投影的当前来源

今天修正了副本/房间 PVF 对怪物等级的解释：新 Cell 创建时结合副本基准等级、
房间的绝对/相对等级声明确定 actor 等级；`START_MAP` 再投影已解析的值，
不把“房间写零”直接当成 0 级怪物。此次变更有 PVF 解析、房间规则和编码器
回归测试；此前玩家观察到组队时低级角色收到 2、9 点经验，只是发现错误的症状，
**还没有修复后的 A21 成对 `START_MAP` / 击杀经验帧与客户端等级显示记录**。
因此本节是当前服务端投影来源，不提升为 `ClientVerified`。

### 2026-10-07：地图资源与 cell 身份分离（CurrentImplementation）

`START_MAP` 的 mapId 来自本局 cell 已选资源，不再取自布局的固定坐标/mapId 字典。
同一 MAP 被不同 cell 使用时，actor 序列基数加入 cell 坐标；回访仍使用原 cell 和既有空重访投影。
字节布局未改；详见 [结构规则](../../../Document/DungeonStructureRules.md)。本次变更的客户端验收待补。
