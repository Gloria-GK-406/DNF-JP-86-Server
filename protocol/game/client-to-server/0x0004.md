## 那个 `u16` 是**列表位置**，不是槽位

这是本条最重要的结论，它同时改写了 [`0x0006` DELETE_CHARACTER](0x0006.md) 的读法。

机器区把它标成「角色槽位索引 slot」，证据是上游
`CharacterSessionLifecycleCoordinator.cs:523-525` 拿它当 `ListByAccount` 结果的下标。
**注意那正是"列表下标"而不是"槽位"**——只是在无洞名单上两者相等，所以描述被写成了 slot。

2026-08-16 的实机样本把两者分开了：

| 名单位置 | 服务端下发的 slot | 名字 |
|---:|---:|---|
| 第 1 个 | 0 | `aa03` |
| 第 2 个 | **2** | `0000` |
| 第 3 个 | **3** | `1111` |

名单（NOTI `0x0002`，见 `../server-to-client/samples/NOTI-0x0002-2026-08-16-01.hex`）
里每条记录前的 `u16` 是**真实槽位**，hex 上逐条可查：偏移 `0x12` = `00 00`、
`0x4C` = `02 00`、`0x86` = `03 00`，与编码器
[`AccountCharacterRosterPayloadCodec`](../../../Server/src/Dfo.Server.Protocol/Game/AccountRoster/AccountCharacterRosterPayloadCodec.cs)
的 `WriteUInt16(body, character.SlotIndex)` 一致。

玩家点的是**第二个**角色，客户端发的是 **`1`**。槽位 1 上没有活角色，客户端也无从知道这个数——
唯一自洽的解释是它发的是自己列表里的下标。

**推广到 `0x0006`**：删除请求索引的是同一个 936 字节角色 vector（构包点把 `[esi+0x138]`
推给 `0x020332A0`，`0x0203ECC0` 又拿同一个值当 vector 下标做边界检查），
而该 vector 由名单按顺序填充。所以删除的那个下标也是列表位置。

**为什么一直没暴露**：位置与槽位只在名单有洞时才不同，而在此之前的每一次抓包名单都是连续的。

### 偏移 218 是**入场镇 id**，不是槽位——写 0 必崩

三条独立证据同向：

1. **上游把它当镇 id 用，只是名字起错了。** `Network/Builders/Init/SelectCharacterPacketBuilder.cs:64`
   写的是 `snapshot.InitializationSnapshot.AckCharSlotIndex = snapshot.CharacterRecord.TownId`
   ——字段名叫 `AckCharSlotIndex`，赋进去的是 `TownId`。名字是上游自己的误称。
2. **客户端拿它查表，且取回的对象不查空。** 由客户端 `F78F0AEA…` 的
   `0x008C9E9A`–`0x008C9F5A` 反汇编：

   ```text
   0x008C9E9A  call  0x1D00420                  ; ReadU8 -> [ebp-0xE]，即偏移 218
   0x008C9E9F  movzx edx, byte ptr [ebp-0xE]
   0x008C9EA3  mov   ecx, dword ptr [0x3091EF4] ; 全局管理器
   0x008C9EAC  push  1
   0x008C9EAE  push  edx                        ; 这个字节作为键
   0x008C9EAF  call  0x1C94C10                  ; 按键查找
   0x008C9EB4  cmp   eax, ebx                   ; 查不到就跳过（这一处是安全的）
   ...
   0x008C9F4C  call  0x8BC420                   ; 再次以该字节取对象
   0x008C9F51  mov   ecx, eax
   0x008C9F53  call  0xBA70B0                   ; mov eax,[ecx+0xA8]; ret —— 不查空
   ```

   `0x00BA70B0` 只有两条指令，取 `[ecx+0xA8]` 后返回。ecx 为 NULL 时它读地址 `0x000000A8`。
3. **实机差分**：同一角色，只有这一字节不同。`00` → 进城即崩；`01`/`02`/`05` → 正常，
   **`05` 包含在内**。`05` 作为槽位下标越界，作为镇 id 合法——这一条单独就否掉了"槽位"读法。
4. **归档内容侧对得上，而且对出了一处越权。** `town/town.lst` 的 25 个镇里
   **没有 id 0**（见[探针产物](../../patterns/data/probes/pvf-town-list-20260817.md)），
   所以槽位 0 送出的是一个内容里不存在的镇。更有力的是槽位 2 那次：id 2 = 暗黑城，
   而暗黑城**每个区域都要求 17 级**——那次是个 1 级角色。一个 1 级角色站在 17 级门槛的镇里，
   只能说明这一字节选的是镇。

合法值也不是一段连续区间（`16`、`18`、`24`–`98` 缺号），所以"范围检查"不是判据，
存在性才是。

**该送哪个值**：这次入场实际落地的那个镇，也就是 NOTI [`0x0017`](../server-to-client/NOTI-0x0017.md)
携带的同一个值，而不是角色行里存的 `town_id`——新建角色那一列是 0。

**落点不由本字段决定。** 客户端拿到镇 id 之后自己把角色放到该镇的赛丽亚旅馆，那是游戏里
登录后的出生点；`town.lst` 与各 `.twn` 的 `[name]` 里都没有这个地名，它不是协议字段。
1 级新角色因此落在 id 1 银色村庄（`[need level] 1`），随后由教程把人送进
`dungeon.lst` 10000 —— 两件事各走各的协议，见
[flow-dungeon-entry](../../patterns/flow-dungeon-entry.md)。

### 一个由此暴露的缺陷

偏移 5 应该是建号时间戳，实机送的是 **0**——我们没有这个数据可送，
`SqliteCharacterRepository.FindByAccountAndSlotAsync` 硬写 `DateTimeOffset.UnixEpoch`。
这是实现缺口，不是协议未知；补法属于领域设计，见仓库根 `Docs/`。

同一次会话还首次观察到 [`0x02C1`](0x02C1.md) 与 [`0x00C5`](0x00C5.md)。

**2026-08-16 第二轮**：下标改按列表位置后解析正确（点第二个 → `character 13`，slot 2），
但撞上服务端自己的一个缺口：入口 profile 查询对 `character_subtype0_fields`、
`character_subtype1_fields`、`character_init_flags` 做 INNER JOIN，而建角色只写了
`characters` 一行——**我们建出来的角色进不去游戏**。这不是协议未知，是实现不完整。
已改为在同一个事务里连同这三行一起写出，并回填了此前建的角色。

新角色的属性因此全是 schema 默认值（零属性）。这次只让行**完整**，不代表它**正确**——
真实初始属性属于 PVF 职业表，留到了下一轮。**2026-08-17 已补**，见下。

**2026-08-16 第三～五轮**：连续撞上三堵墙，都不在协议层，逐条记下以免重走：

| 轮次 | 失败 | 性质 |
|---|---|---|
| 三 | `Script.pvf was not found` | **环境**：`PVF_ARCHIVE_PATH` 是 [HostStartup](../../../Docs/HostStartup.md) 里写着的启动参数，我漏了。归档是懒打开的，所以登录与角色列表全程正常，走到要读职业表才炸 |
| 四 | `PC-room compatibility state is unavailable` | **我第二轮改动的缺陷**：`character_init_flags.pc_room_state` 可空且无默认，裸插入留下 NULL，而账号入口加载器拒绝 NULL。顺带发现该列归**账号**侧 schema 所有，全新库里建角色会因缺列直接失败 |
| 五 | `Collection-box definition 3 was not resolved` | **实现与内容不符**：代码在两处硬编码收集箱为 `{3, 4}`，而本客户端归档 `localization/collectbox/collectboxinfo.etc` 只声明 **box 1 和 2** |

第五条的修法参照上游：`CollectionBoxBodyBuilder` 用 `CollectBoxDataService.GetAllIndexes()`，
**由内容表决定有哪些箱子**，角色存储只提供箱内进度。我们原来是反的——入口状态凭空造出一对
下标，投影再要求每个下标都能解析到定义，于是任何不声明这两个下标的归档都进不去游戏。

**共同的教训**：这三堵墙没有一堵是协议未知，全是"服务端把某个环境/内容事实写死或漏配"。
进游戏这条路径上，协议之外的依赖比协议本身多。

**2026-08-17**：角色进城了但是具空壳（HP/MP 上限 0），补上建号时的初始属性。数据来自归档的
`character/character.lst` → `character/<职业>/<职业>.chr`，段 `[initial value]`，
**每个数乘十**送上线（鬼剑士 `[HP MAX] 180` → 1800）。职业不声明的属性就是零，不是解析失败：
鬼剑士不声明火/水抗，圣骑士四抗齐全。

同一文件里 `[growtype N]` / `[awakening M]` 是每级成长量，**本轮没读**——没有任何路径会升级角色。
读的时候必须在第一个 `[growtype 1]` 处停下，否则拿到的是"每级 +45"而不是"出生 180"。

两处与上游的分歧，都是有意的：

| 项 | 上游 | 我们 | 理由 | 结果 |
|---|---|---|---|---|
| `PremiumHpBonus` +9800 / MP +10500 | 种子里直接加 | **不加** | 不是归档里的数，是上游自己塞的。先送真实值，实机看面板 | 站得住：不加也满血，客户端没有任何地方要求它 |
| `stat_level` | 固定写 100 | 保持默认 0 | 语义未知。上游注释说它不是等级锚点，但没说是什么 | **错了**，见下 |

上游还有个 `RecomputeAllCombatStats()`，注释写着"修复历史**升级未重算属性**的存量数据"——
存储副本陈旧的现成教训。我们不做重算：角色永远建在 1 级，等实现升级时**同一份成长表就在同一个文件里**。

**同日续**：`stat_level` 那个决定是错的，而且它就是"属性上限全部正确却显示为 0"的直接原因。
实机三点差分（0=空条 / 50=半条 / 100=满条，上限恒为 1800）定下它是**入场时当前 HP/MP 占上限的
百分比**，与角色等级无关。完整结论、字段表与虚弱状态的其余出口见
[NOTI-0x0002.md](../server-to-client/NOTI-0x0002.md#偏移-95当前血量百分比)。

当时我在这张表里写下"面板要是不对，这是第一个该翻的牌"，事后确实是这张牌。但**代价是绕了两轮**——
先怀疑帧没送到（送到了，逐字节正确），再怀疑少发一帧（补了，而那次实机根本没触发）。

*教训*：一个来源可疑的**常量**和一个来源可疑的**字段名**风险不对等。名字照抄再改没有代价；
常量不抄，等于替对方做了一个自己没有依据的决定，而且这个决定会以"数据明明正确却不生效"的形式回来。
