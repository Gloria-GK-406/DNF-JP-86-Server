## 响应形状：客户端注册了 CMD handler，但布局取不到

客户端为本 type 注册了 CMD 接收 handler（`RVA 0x008C56F0`）。

### 客户端侧给不出响应布局

按读取原语表走两个 handler，各自只读到 **1 个 `u8`** 就进入间接跳转与打包区：

| type | handler | 读出的字段 | 之后 |
|---|---|---|---|
| `0x000F` | `0x008CFF30` | `u8` | 大量间接调用，opaque `0x04D41803` / `0x04E6558B` |
| `0x0010` | `0x008C56F0` | `u8`（深度 1，在 `0x008C4350` 内） | `jmp dword ptr [ecx*4 + 0xCC557C]` 跳转表 |

所以客户端能提供的只有"信封之后至少 1 字节"这一个约束，不足以构造响应。

上游 `HandleSelectDungeonCore` 的成功路径不产出本 type 的 CMD 响应，而是一路委派到
副本运行（`DungeonRunLifecycle.BeginRun` / `BeginTowerRun`），随后才推 `0x001C DungeonInfo`
等下行。也就是说本条的"响应"是一批 NOTI 而不是一帧 CMD，具体集合尚无证据。

## 应答：三条 NOTI，没有 CMD 回帧

实机 2026-08-18 确认。客户端虽为本 type 注册了 CMD 接收 handler，成功路径上**不需要回 CMD**：
我们一帧 CMD 都没回，客户端收下三条 NOTI 并进入副本。

| 序 | 帧 | 内容 |
|---:|---|---|
| 1 | NOTI [`0x001C`](../server-to-client/NOTI-0x001C.md) | 副本 id / 难度 / 迷宫序号 / boss 格 / 深渊格（非深渊 `0xFF`），30 字节 |
| 2 | NOTI [`0x001D`](../server-to-client/NOTI-0x001D.md) | START_MAP —— 真正把人放进房间的那一帧 |
| 3 | NOTI [`0x019F`](../server-to-client/NOTI-0x019F.md) | 助战标签，无助战时 `0000` |

上游在 1 与 2 之间还有一步"选择态"（`SendSelectionStateAsync` → boss 入口小地图图标），
普通副本什么都不发，我们未实现且无可观察后果。

**三帧不是终点。** 客户端随后发
[`0x0025 FINISH_LOADING`](0x0025.md)，必须应答，否则卡在进度条最后并超时断线。
完整链路见[副本入场流程](../../patterns/flow-dungeon-entry.md)。
