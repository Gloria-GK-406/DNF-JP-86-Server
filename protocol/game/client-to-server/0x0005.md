# `0x0005` `CREATE_CHARACTER`

<!-- rks:a12:begin -->

> **本区结论得出于 A12 客户端**（SHA-256 `F78F0AEA…`），**A21 上尚未复核**。
> 按迁移规则，本协议在 A21 上重做完成后整区删除；在那之前它是脚手架，不是 A21 的记录。
> 迁移状态见[协议清单](../../catalog.md#a12-内容的退场)。

> 名称取自旧服 `CmdPacketType` 枚举。共享证据、原因码表与名字字段编码见
> [角色生命周期协议族](../../patterns/character-lifecycle.md)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server（响应同 type 反向） |
| Command | `0x01` |
| Type | `0x0005` |
| Role | Mutation / 有响应 |
| 阶段 | 实现服务端功能 |

**触发时机与响应顺序不记在本页**，它们属于流程层：见 [character-lifecycle](../../patterns/character-lifecycle.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

**已有实机样本**（2026-08-16，四份，见下）。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。

**请求**：

```text
BodyLength = 1 + 4 + nameLength + 4        // 四份实机样本逐份闭合
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | 职业，来自 UI 对象 `+0x134`；旧服限 0..12 | **Confirmed** | `E-003` |
| 1 | 4 | LE `i32` | 名字字节数，旧服限 2..18 | **Confirmed** | `E-003` `E-004` |
| 5 | `nameLength` | 原始字节 | 名字，来自 `+0x148` | **Confirmed** | `E-003` `E-004` |
| 5+len | 1 | `u8` | **常量 `0`** | **Confirmed** | `E-003` `E-009` |
| 6+len | 1 | `u8` | 全局对象 `[0x3074DF0]+4 != 0` 的布尔值 | High | `E-003` |
| 7+len | 2 | `u8` × 2 | 续写 `+0x138`、`+0x13C`；四份样本均为 `0` | 宽度与数量 Confirmed；含义未定 | `E-003` `E-009` |

2026-08-16 直接反汇编了客户端构包器（`E-003`），前四项因此从 Hypothesis 升为 **Confirmed**：

```asm
0x0195E99F  push 5                              ; type
0x0195E9A1  call 0x1C8F5B0                      ; GetWriter
0x0195E9A8  call 0x1C90460                      ; MakeHeader
0x0195E9AD  movzx edx, byte ptr [esi+0x134]     ; ← 职业
0x0195E9BC  call 0x1C90550                      ;   WriteU8
0x0195E9C1  lea eax, [esi+0x148]                ; ← 名字
0x0195E9CF  call 0x1C90710                      ;   WriteDString
0x0195E9D4  push 0
0x0195E9DD  call 0x1C90550                      ; ← 常量 0：那个"未知尾部"
```

尾部是**四个**独立的 `u8`（见下方 Samples 的写入追踪），四份样本全为 0。
**它们之后没有别的字节**：`1 + 4 + nameLength + 4` 与实测长度精确闭合。

**响应**恰好就是[两字节结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)，
没有自己的载荷：

| 情况 | body |
|---|---|
| 成功 | `01` |
| 名字已占用 | `00 18` |
| 名字非法 | `00 9F` |
| 请求不合法 / 无空槽 | `00 04` |

`0x04` 是 **reason**，必须带前导 `00`：首字节是族级信封的 ok，**非 0 一律是成功**，
所以裸发 `04` 会让客户端认为角色建好了，接着去跑一个不存在的角色的创建后流程。
handler `RVA 0x008CB460` 对 `0x04` 有分支，提示串 `0x2AA`。

handler 的 reason 比较表：`0x02` `0x04` `0x12` `0x13` `0x16` `0x17` `0x18` `0x9F`。

成功后**必须补发角色列表**：ack 里不含任何角色信息，客户端只能从 NOTI `0x0002` 得知
建出来的角色和它落在哪个槽。顺序为先 ack 后列表。

## Samples

2026-08-16 从 `clienthack-write-trace.log`（钩在 `ISocket::Write`，在加密之前）取得四份真实请求。
该钩子记录每一次暂存写入，因此能看到构包器逐字段写下的内容：

| job | 名字 | body（拼接后） |
|---:|---|---|
| `0x0B` | `2222` | `0B 04000000 32323232 00 00 00 00` |
| `0x01` | `22221` | `01 05000000 3232323231 00 00 00 00` |
| `0x02` | `121` | `02 03000000 313231 00 00 00 00` |
| `0x0B` | `aa03` | `0B 04000000 61613033 00 00 00 00` |

四份的形状完全一致，**长度闭合**：`1 + 4 + nameLength + 4`。

**尾部是 4 个独立的 `u8`，不是 1 个。**追踪里它们是四次各 1 字节的写入，与构包器反汇编吻合
（`WriteU8(0)`、`WriteU8(全局标志)`、`WriteU8(+0x138)`、`WriteU8(+0x13C)`）。
四份样本里这四个字节**全部为 0**，所以它们各自的含义仍未分辨——只知道宽度和数量。

这四份也是仅有的四次：整段追踪里 `0x0005` **只被构建过 4 次，且 4 次全部成功**。
失败的尝试连构包器都没进。

### 那些「失败」不是协议问题

2026-08-16 查明：确认对话框上**客户端的光标焦点与渲染不同步**——焦点已经移到「创建角色」，
画面却还把光标画在「是」上，于是点击落空。稍微动一下鼠标、或直接在原位点，都能成功。

这解释了此前记录的全部异常现象，**它们全是同一个客户端 bug 的不同侧面**：

| 当时的记录 | 实际 |
|---|---|
| 「job 0 / 7 建不出来」 | 那两次点空了，与职业无关 |
| 「有时能有时不能」 | 取决于点击是否落在真实焦点上 |
| 「每次会话只成功一次」 | 一次成功的采样被当成了规律 |

**教训**：服务端往返实测 0.4–0.9 ms，这个数一开始就该量。把一次采样的形状当规律、
再据此去改协议，是这轮走的最大弯路——先量，再改。

## Client reversing evidence

| Evidence | Kind | Location | Supports |
|---|---|---|---|
| `E-001` | static | 旧服 `CharacterSelectHandler.Handle_ENUM_CMDPACKET_CREATE_CHARACTER`（`d51e74b`） | 请求布局、职业与长度上限、全部原因码、成功后补发列表 |
| `E-002` | static | client handler `0x008CB460`，注册于 `0x008D04DC` | 客户端等响应 |
| `E-003` | static | 客户端构包器 `0x0195E99F`（RVA） | **请求布局**：职业、名字、常量 `0`、后续字段 |
| `E-004` | static | 写原语 `0x01C90710` → `0x01C90680` | 名字为 `i32 长度 + 字节`（dstring） |
| `E-009` | dynamic | `clienthack-write-trace.log`（`ISocket::Write` 钩子），2026-08-16 四份真实请求 | **body 完整长度闭合**：`1 + 4 + len + 4`；尾部确为 4 个独立 `u8` |
| `E-010` | static | 接收函数 `RVA 0x00D89B16` + handler `0x008CB460` 失败路径的比较链 | **响应即两字节信封**；`0x04` 是 reason 而非状态，裸发会被读成成功 |

**`E-002` 只证明 handler 存在**，`E-010` 才给出响应格式的指令级证据。可达性扫描走了
499 个函数、26 个调用进入打包区，未命中读取原语；同批正对照（LOGIN）正常命中，
故是子树过深而非扫描器故障——但那条路本来也找错了方向：**信封在分发之前就被接收层读掉了，
不在 handler 的子树里**，所以从 handler 往下扫永远看不到它。

`E-004` 的链路值得单独记：`0x01C90710` 先把字符串过一遍 `0x01CF51B0`（TLS 相关的编码转换），
再交给 `0x01C90680`；后者内联 `strlen`，先写 4 字节长度再写字节。所以名字字段是
`i32 长度 + 原始字节`，与旧服一致，**但这一条现在有客户端侧的独立证据，不再依赖旧服**。

**构包器无法回溯到调用方**：`0x0195E99F` 在整个 dump 里既没有直接 `call`/`jmp` 引用，
也没有任何 vtable 槽存着它的 VA（`0x01D5E99F`）。它只能是从打包区（RVA ≥ `0x02300000`）
被间接调用的。因此**"建角色按钮在什么条件下才会构包"这个门闩，静态分析追不下去**——
这是一条明确的死胡同，别再重复尝试。

## Server and historical evidence

旧服建号时另外写入位置与初始化数据（`TownId` / `PosX` / `PosY` / `Direction` / `AreaState`），
并调用 `_selectCharacterDataSource.InitializeNewCharacter`。这些是**游戏设定值与我们的存储设计**，
不是本 body 的字段——建号该落哪些列、初始属性从哪来，见 [`0x0004`](0x0004.md) 与仓库根 `Docs/`。

### 槽位与协议的关系

协议侧只有两条事实：

- 角色列表头自己声明 `SlotLimit = 32`，所以任何分配策略都不得产出 `>= 32` 的槽位号；
- 客户端每次收到角色列表都**重建自己的 vector**，跨刷新不保留编号——所以槽位号不是稳定标识，
  删掉任何一个角色，其后的列表位置本来就会改号（这也是
  [`0x0006`](0x0006.md) 的下标是列表位置而不是槽位的原因）。

分配策略本身（填最低空位）属于领域设计，见仓库根 `Docs/`。

**一次未解释的崩溃**：2026-08-16 名单为 `slot 0 / 2 / 4 / 5`（4 个角色、三处空洞）时，
客户端**建角色后崩溃**（`minidump.dmp`，发出建角色请求后再无任何帧）。

> **因果未证实，且已有的反例范围很窄。** 用来反驳"有空洞就崩"的那次正常登录是
> **2 个角色、`slot 0 / 2`、且只走了登录**；崩溃那次是 **4 个角色、`slot 0/2/4/5`、走的是建号**。
> 角色数、空洞数、路径三项全不同，所以那次正常登录**不足以**排除空洞。

此前这里挂着一条线索，说"槽位 0 的角色进城后必崩"可能是同一个缺陷。**那条崩溃已定因，
且与本条无关**：它的成因是 `0x0004` 响应偏移 218 送出了槽位而客户端要的是镇 id，
见 [`0x0004`](0x0004.md#偏移-218-是入场镇-id不是槽位写-0-必崩)。本条崩溃发生在建号之后、
入场之前，那一帧根本还没发出，所以两者不共享成因。本条仍未解释。

## Implementation mapping

| Layer | Type/path | Responsibility |
|---|---|---|
| Data | `NewCharacterSpec` / `CharacterCreationStatus` / `CharacterCreationResult` | 领域契约 |
| Networking | `GameMessageDecoderRegistry` 键 `0x01/0x0005` | 分发 |
| Protocol | `Game/CreateCharacter/` | 解码、command、handler、编码器 |
| Application | `CharacterDomainService.CreateCharacterAsync` | 职业校验、名字规则、槽位上限与分配、重名 |
| Infrastructure | `SqliteCharacterRepository.CreateAsync` | 落库，`name` 与 `name_bytes` 同写 |

命令为 `Direct` + 账号 `Exclusive`：先读名单算槽位再写，共享访问会让并发建角色算出同一个槽。

## Verification

- Parser/codec vectors：`CharacterLifecyclePayloadCodecTests` 覆盖职业+名字解析、无尾字节可通过、
  全部状态编码。
- Boundary cases：超长/负数声明长度被拒（含整数溢出用例）。
- 领域规则：`CharacterLifecycleServiceTests` 覆盖 job>12、字节长度上限、槽位分配、名单已满。
- 持久化：`SqliteCharacterLifecycleTests` 覆盖落库回读、非法 UTF-8 名字原样往返、槽位排序。
- Real-client result：**建角色成功**（2026-08-16，job 11 名字 `aa03`），服务端落库、补发角色列表；
  客户端随后正常显示该角色。名字检查往返实测 0.4–0.9 ms，服务端侧无可感知延迟。

## Unknowns and next evidence

| 问题 | 影响 | 最便宜的证据 |
|---|---|---|
| 建角色后客户端崩溃的机制 | **高**：已实测发生一次，名单为 `slot 0/2/4/5`（4 个角色） | 在有空洞的名单上重现一次；崩了就说明与槽位形状有关，不崩则要回头查建角色 ack 之后的那两次 UI 调用 |
| 尾部四个 `u8` 各自的含义 | 中：四份样本全为 0，分辨不出 | 在会触发非零值的界面状态下再抓一次 |
| 连续创建是否稳定 | 低：此前的「只成功一次」已查明是客户端光标问题 | 一次会话内连建两个 |
| 无空槽分支改为 `00 04` 后的实机表现 | 低：需要先把 32 个槽（`SlotLimit`）填满才触发 | 建满一个账号再建一个 |
| job 上限确为 12 | 低 | 实机试 13 |
| 新角色是否还需要位置/初始化数据 | 中（影响后续进游戏） | 建完后尝试选择该角色 |
