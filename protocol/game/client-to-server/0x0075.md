## 客户端不为它注册应答 handler（Confirmed）

客户端有两张分发表，CMD 一张、NOTI 一张。对 CMD 表的普查列出 **671 个 type**，客户端为它们
各自登记了一个「服务端回同 type 时走哪个函数」的 handler。**`0x0075` 不在其中**——表从
`0x0071` 直接跳到 `0x0076`：

```
… 0x006B 0x006D 0x006F 0x0071 0x0076 0x0077 0x0078 0x0079 0x007D …
```

来源：`protocol/patterns/data/protocol-identity.tsv`，筛 `direction=S2C, family=CMD`。

**结论：服务端对本帧回任何东西都是发给一个没有收件人的地址。** 因此本仓不应答，且
`BossDieCheckHandler` 干脆不依赖 `IGameMessageSender`——要加一个应答，先得加那个依赖，
`ResultScreenTests` 盯着这一点。

## 普查为什么看不见它

普查的出站表靠在 `.text` 里找构包点。**用「立即数 `push <len>; push <type>; call GetWriter`」
这一种模式去扫，`0x0075` 扫不到**——但那只说明这一种模式扫不到它，不说明普查整体看不见它：
同样扫不到的 `0x002E SET_PLAY_RESULT`，`protocol-identity.tsv` 里**是有**构包点的
（`0x01541EBF`），普查用的手段比这一种模式更宽。

`0x0075` 在 `protocol-identity.tsv` 的 C2S 表里确实缺席（表从 `0x0071` 跳到 `0x0076`），
**成因未查明**。它不是「客户端不发这一帧」的证据——实机日志里它就在那儿。

## 它在链路里是什么

**顺序是：服务端先判定清关，客户端再发这一帧。** 不是反过来。

上游把本帧当作**清关的触发器**：`DungeonCombatHandler.HandleBossDieCheck` 解析出 boss 序号，
交给 `DungeonMechanismCoordinator.OnBossDieCheck` 判断本局该不该清，然后自己去
`SubmitClearIntentAsync`。它对本帧也不回应答。

本仓不采用这个顺序，是有意的：

* 本仓的清关判定是「boss 房声明的敌对 actor 全部被上报死亡」，**服务端自己能核**。实机顺序
  证实它先发生——`ENABLE_CLEAR_DUNGEON` 已经发出去了，客户端才发来本帧。
* 改用客户端的触发意味着**客户端说清关了就清关**，把一条服务端可核的规则换成一条不可核的。
* 本帧可以重放。作为触发器它就是第二次结算；作为报告它什么也不是。

所以本仓读它、核对它说的 actor 是不是本房间已登记死亡的那个、把结论写进日志，然后**什么都不
改**。分歧只有那一行日志会说出来，而那一行是唯一会说出来的地方。

## 与结算界面无关（推论，非实测）

本帧一度被怀疑是「打死 boss 后修理商与回城 UI 不出现」的成因。**证据指向不是。** 实机日志里它未被应答，
而客户端此后照样发出了 `SET_PLAY_RESULT`、收下了结算帧、并画完了结算卷轴——卡住的是再往后的
[`0x0045 SCORE_SCROLL_STATE`](0x0045.md)。

这是从「未被应答仍然走到了下一步」推出来的，不是把本帧应答了再看差别——要那样才算实测。
