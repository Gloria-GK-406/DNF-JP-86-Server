## A21：已实现（2026-08-27）

**这一帧是任务推进，不是任务完成。** 玩家做了任务要求的那件事——点了 `[meet npc]` 任务指名的
NPC、用了 `[use item]` 任务指名的道具——客户端就发它。把任务交掉是 `FINISH_QUEST` 的事。

**判据只有两层，没有第三层。** 请求字节来自本仓 2026-08-27 的实机日志；应答形状与推进规则来自
上游 `QuestService.HandleSetTrigger` / `QuestClientTriggerAuthority` / `QuestTrigger` /
`QuestAckBuilder.BuildSetTrigger`。**参照抓包里没有这一帧**——存档的几次参照会话都没把任务带到
NPC 面前，两个方向都没有样本。所以应答是照上游源码写的，不是照字节写的。

### 请求：6 字节，前两字节是包类型回显

```text
21 00 F8 03 00 00      任务 1016，triggerType 0，increment 0     ← 本仓实机，连发 5 次
```

样本存于 [`samples/0x0021-2026-08-27-01.hex`](samples/0x0021-2026-08-27-01.hex)。产生它的动作：
一级鬼剑士在城里点赛丽亚，任务 1016「与赛丽亚的初次见面」（`[type] [meet npc]`、
`[int data] 2`，2 就是赛丽亚的 npc index）。**连发 5 次**是因为本仓当时不认这一帧，只记
`Unhandled`——不应答，客户端就重发。

上游 `HandleSetTriggerAsync` 在解析前调 `StripEcho(body)` 丢掉前两字节，与 `0x001F` 同一套路。
本仓照读，但**校验**这两字节：不带回显的体是没读懂的体，跳过它会把之后两字节当成任务号。

| Offset | Size | Enc | 含义 |
|---:|---:|---|---|
| 0 | 2 | `u16` | 包类型回显，恒 `0x0021` |
| 2 | 2 | `u16` | 任务号 |
| 4 | 1 | `u8` | 通道选择 triggerType |
| 5 | 1 | `u8` | 方向，非 0 为「多一个」，缺这一字节按「少一个」读 |

**第 5 字节可以缺。** 上游读的是 `body.Length >= 4 && body[3] != 0`（去回显后的下标），所以
5 字节的体它也收。本仓照收，没有收紧到实测的 6 字节——收紧就是凭空造一处与上游的差异。

### 应答：`01` + 任务号 + 一个 trigger 字

上游 `QuestAckBuilder.BuildSetTrigger`：

```text
成功  01 | u16 任务号 | u32 trigger
拒绝  00 | u8 原因
```

本例点完赛丽亚之后应答 `01 F8 03 00 00 00 00`：任务 1016，trigger 落到 0。

**拒绝只有一个号：22。** 上游这一帧的每一条拒绝路径都是 `QuestSetTriggerResult.Fail(22)`——体
读不动、任务档案里没有、会话没选角色，线上长得一模一样。

### trigger 字：三个九位通道

低位在前，`0` 是**目标达成**而不是「没有进度」。要一件东西的任务从 1 开、到 0 结束；要三件的
从 3 开。三个通道是上游打包法给的位置，实测的两个任务都只用最低那个。

推进算法（上游 `QuestTrigger.ApplyClientMutation`）：

| triggerType | 作用 |
|---|---|
| `1` | 整字 +1，只加不减 |
| `0` | 整字 ±1，方向看第 5 字节 |
| `0x10` / `0x20` / `0x40` | 分别是第 0/1/2 个通道 ±1，可以按位或起来一次动多个 |
| 其余 | **不是能读的报告**，拒绝 |

两级都饱和：整字不会从 0 减到 `0xFFFFFFFF`，单通道也不会向上借位。这一条是必需的而不是保险
——客户端没被应答就重发，一个已经在 0 上的任务必须把重发吸收掉，否则它会把自己退回未完成。

### 谁有权推进：按任务的 `[type]` 分

上游 `QuestClientTriggerAuthority.Resolve` 是一张四十来个词的表，本仓照抄成
`QuestObjectives`：

| 归属 | 词 | 本帧的效果 |
|---|---|---|
| 客户端计数 | `meet npc`、`use item`、`level up` 等三十七个 | 按上表推进并落库 |
| 服务端计数 | `hunt monster`、`clear map`、`clear quest`、`quest clear` | 答库里的值，不动 |
| 由背包推算 | `seeking`；`seek n meet npc` 的非 `0x20` 通道 | 不接受客户端借本 CMD 自行增加；由服务端持有量变化事实重算并另发活动任务快照 |
| 不接受 | `question` 的通道选择；不可读的 triggerType | 拒绝 22 |

**表里没有的词一律算服务端计数**，这也是上游的默认。方向是刻意的：把服务端计数的任务错当成
客户端计数，等于让客户端靠发包把任务做完；反过来只是任务不推进。

**`hunt enemy` 不能只按任务词决定。** 2026-09-14 A21 实机在 quest 1776 的剧情 maze 1 boss 房
发送 `quest=1776, triggerType=0x10, increment=0`；PVF 目标
`144/-1/13099/type3/count1` 中 type 3 是 Passive Object，而 map 55607 也把 13099 声明在
`[passive object]`。因此 type 1/2（Monster/AI Character）继续由服务器 actor 事实计数，type 3
由客户端地图脚本报告。为避免任意发包完成任务，本仓仅在当前运行冻结为同任务、同 dungeon、匹配
difficulty 的 Active QuestLinked 时接受 type 3 的声明通道；普通运行或错配上下文拒绝。

**2026-09-18 实现边界更新。** `seeking` 的持有量重算已经接入拾取、怪物直发任务物品、接受
任务起始物品、NPC 购买、主背包丢弃、交任务奖励及角色进入校准。它不是客户端发本 CMD
后按 `trigger +1` 推进，而是服务端按当前持有量计算剩余需求；变化通过
[`NOTI 0x023F`](../server-to-client/NOTI-0x023F.md) 投影。交任务前也会重新核对，避免旧的
完成状态在物品已丢弃时仍能领取奖励。其他物品/金币变化入口（如未来邮件领取）尚未逐条接入。
上述为当前代码及回归测试结论，**并非这些场景在 A21 客户端逐帧确认的结果**。

### 不在这一帧里的东西

上游这条路上只发这一帧，**不重发任务列表**。trigger 到 0 只是目标达成，任务还在活动列表里；
交任务、发奖励、刷新两张列表都是 `FINISH_QUEST` 的事。
