**触发时机与响应顺序不记在本页**，它们属于流程层：见 [flow-dungeon-entry](../../patterns/flow-dungeon-entry.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

### Trigger 是机制性证据，不是位置推断（`E-004`）

本帧出现在 `0x0003` EXIT **交换之后**，早期只能记成"EXIT 之后仍发出"这类位置描述。
抓包栈 + [接收 handler 普查](../../patterns/game-receive.md) 给出了机制：

```text
0x008F 的发送栈 stack[3] = RVA 0x008C626C
     ↓ 落在
为 S→C type 0x0003 注册的 handler（入口 RVA 0x008C6260，注册点 RVA 0x008D057B）内 +0xC
```

也就是说客户端是在**处理 EXIT 响应**时发出本帧的。因此：

- 服务端**不回** `0x0003` 响应时，本帧不会出现；
- 它不属于退出 flush（`0x00C2`/`0x00FA`/`0x0117` 那三条是主动 flush），
  而是对服务端响应的回应。

这同时是接收 handler 普查的第二个独立校验点（第一个是
[`0x0008`](0x0008.md) 落在 type `0x0001` 的 handler 内）。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。body 固定 **5 字节**，
`4 + 1 = 5`，与实测精确闭合：

```c
struct Body008F {
    u32 id;      // 实测 0x0000001F = 31
    u8  flag;    // 实测 1
};
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 4 | LE `u32` | 某个 id。14 个构包点中 12 个写运行时值，2 个写立即数（`0x4D` = 77、`0x26` = 38）。实测 `0x1F` = 31 | 位置与宽度 Confirmed；语义未定 | `E-002` |
| 4 | 1 | `u8` | 标志。14 个构包点中 **12 个写立即数 `1`**，2 个写运行时值。实测 1 | 位置与宽度 Confirmed；语义未定（多数路径恒 1，疑似"成功/启用"） | `E-002` |

### 全部构包点（`E-002`）

`MakeHeader` 普查在 `.text` 内找到本 type 的 **14 个**构包点，形状**完全一致**
（`WriteU32` → `WriteU8` → `Finalize`，无分支、无循环、无可变尾部）：

| 构包点 | offset 0 | offset 4 |
|---|---|---|
| `0x01C1EE40` | `esi` | `1` |
| `0x01C1F3A9` | `esi` | `1` |
| `0x01C1F4C7` | `edi` | `1` |
| `0x01C20628` | `esi` | `1` |
| `0x01C20CB5` | `esi` | `1` |
| `0x01C21740` | `esi` | **`ebx`** |
| `0x01C22773` | `esi` | `1` |
| `0x01C227D1` | `esi` | `1` |
| `0x01C22969` | `esi` | `1` |
| `0x01C24638` | **`0x4D`** | `1` |
| `0x01C246E7` | **`0x26`** | `1` |
| `0x01C24900` | `esi` | `1` |
| `0x01C24A88` | `esi` | `1` |
| `0x01C27EC9` | `esi` | **`esi`** |

14 个点全在 `0x01C1E000`–`0x01C28000` 这一段内，说明它们属于同一个子系统。
两个写立即数 id 的点（77、38）说明 offset 0 是**取自某个枚举的 id**，而不是句柄或指针。

> 本记录之所以能给出"offset 4 多数路径恒 1"这种结论，靠的是普查列出**全部**构包点。
> 只看抓到的那一帧，`1` 和 `0x1F` 都只能记成"实测值"，无从判断哪个是常量、哪个是变量。
> 参见 [game-frame 的构包点普查](../../patterns/game-frame.md#构包点普查先枚举再挑协议)。

## Server and historical evidence

前四次会话服务端尚未注册本 type、帧被 `GameNetworkPlugin` 静默丢弃，客户端仍在发出本帧后
正常结束连接。服务端在第五次会话已注册（见下方 Implementation mapping），但仍是只记录日志、
不回响应。旧服是否有对应 handler 未核对（旧服源码树当前不在工作区）。

> **这四次会话证明的是"客户端容忍"，不是"客户端不需要"**——四次的服务端都是我们自己这台，
> 而它从不回包；观察自己的沉默再断言对端想要沉默是循环论证（该谬误的完整案例见
> [`0x02A8`](0x02A8.md)，那条协议正是因此被判错过一次）。
> 本条的额外底气不来自这四次会话，而来自 `E-004`：它由 EXIT **响应**的 handler 发出，
> 且是连接关闭前的最后一帧，之后没有任何客户端行为需要被这一帧的回包解锁。

注意本帧在服务端已经回了 `0x0003` 响应**之后**才到，此时连接可能正在关闭——
服务端若将来要处理它，必须容忍"在关闭流程中收到最后一帧"。

## Verification

- Parser/codec vectors：`1F000000 01` → `id=31, flag=1`；`78563412 FF` → `id=0x12345678, flag=0xFF`
- Boundary cases：长度 0 / 4 / 6 → 抛 `InvalidDataException`
- 值域：两个硬编码枚举 id（77、38）均可无损解码；`flag` 不做值校验（两个构包点的取值范围未知）
- 条件分支/重复项：无
- Response count/order：无响应
- Real-client result：2026-08-15 第五次实机会话通过——`TaggedIdReportHandler` 输出
  `Tagged id report Game:01-00-00-00 account=1 onlineUser=…: id=31 flag=1`，且该行**出现在
  `AcknowledgeGameExitCommand` 之后**，与 `E-004` 推出的"它是 EXIT 响应的反应"一致
- 归属：本次连接在收到本帧时在线用户尚未清理（日志有 `account=1`），
  但 handler 的容忍逻辑仍属必要——清理时机不受协议保证

## 回执里的槽位会引出一帧 `0x0013`

2026-08-18 实机：服务端答 `01 01 4100 1A210000 01000000`
（物品 8474 ×1 落在槽 65）之后，客户端**紧接着自己发了一帧**
[`0x0013 MOVE_ITEMSPACE`](0x0013.md)，要求把它搬到槽 3——快捷栏的第一格。

所以本条的回执不只是"告知"，它给出的槽位会被客户端拿去做下一步决策。
上游发放消耗品时优先塞快捷栏，那一帧就不会出现；我们发在消耗品区间的第一格，
于是客户端自己来纠正。两种都对，但**回执里报的槽位必须是物品真实所在的槽位**，
否则客户端会拿一个不存在的位置去发移动请求。

## 逆向工作日志

### 1. 「EXIT 之后仍发出」这个描述掩盖了机制

协议清单里原来记的是"`1F000000 01`，EXIT 交换之后仍发出"。那是纯位置描述，
带着一层隐含假设：它是退出序列的第 6 步。接收 handler 普查一查栈就否掉了这个假设——
它是 **EXIT 响应的 handler 发出来的**，因果方向和"序列第 6 步"完全不同：
服务端不回响应，它就不出现。

**教训**：C→S 帧的 Trigger 不要只写"在什么之后"。发送栈往下第 3~4 层通常落在某个接收
handler 里，查一下普查表就能把"顺序"升级成"因果"。

### 2. 14 个构包点让常量和变量分开了

只看抓到的一帧，`id=31` 和 `flag=1` 是同等地位的两个"实测值"。列出全部 14 个点后
才看出 `flag` 在 12 个点是硬编码 `1`、`id` 在 2 个点是硬编码枚举值——
这两条都是单样本无法得出的结论，也直接指出了下一步最便宜的证据在哪
（去读那两个写立即数 id 的点）。

## A21

**2026-08-26。** 上面的机器区由 **A12** 客户端（SHA-256 `F78F0AEA…`）的静态普查生成。
本节记录 **A21** 客户端（SHA-256 `1F8244D3…`）上不同的部分。判据是 A21 参照会话的字节
（[原始字节](../../patterns/data/traces/a21-reference-entry-bytes-20260825.md)）与本仓的线级重放
（[副本段对照](../../patterns/data/traces/a21-dungeon-wire-20260826.md)），以及产出那份参照的
服务端自己的构包器。

**body 是六字节，不是五字节，而且字段错位一格。**

A21 的布局是 `u8 模式`、`u32 flagIndex`、`u8 rewardFlag`；客户端也可能在后面再补九个保留字节
（十五字节形态），两种形态的前六字节相同。

本仓此前按旧客户端读成 `u32 id` + `u8 flag`，并且**要求长度恰好为五**。两处后果：

1. **长度校验必然失败**，而解码器抛出的异常当时没有报告路径——`GameNetworkPlugin.OnTcpReceived`
   的 `try/catch` 只包住派发、不包解码——于是异常逃出接收回调，连接被拆，日志里一个字都没有。
   客户端弹「网络连接中断」，服务端什么都不说。这一条在 2026-08-25 用线级重放证实：
   **连接就断在这一帧上，别的帧都不断**。
2. 即使放宽长度，字段也是错的：抓到的 `00 1E 00 00 00 01` 按旧读法是 id=7680、flag=0，
   按 A21 的读法是 flagIndex=**30**、reward=1。教程奖励要按 flagIndex 查表，读错就查不到。

**应答是两字节 `01 00`**（成功 + 授予件数 0）。参照与本仓现在逐字节相同。

上游把 flagIndex 的两个特殊值记在案：**31** 结束教程副本回城，**77** 一次置位全部 0–77 号旗标。
## A21(二):奖励落在哪一格

**2026-08-26 实机。** 教学第三间房清空后客户端发 flag 38,本仓照 A21 档案
`etc/serverparameter.etc` 的 `[escalade tutorial reward]`(整张表只有一条:`38 8474 1`)

```text
参照 :  01 01 03 00 1A 21 00 00 01 00 00 00   → 槽位 0x0003 = 3
```

**差别不在这一帧,在放东西的规则。** 上游

```csharp
var emptyFirst = canUseQuickSlot && item.ItemKind == KindConsumable ? QuickSlotRange : range;
```

`QuickSlotRange = (3, 8)` —— **消耗品先给快捷栏,栏满了才退回自己的 65–120 段**;其余可上栏的
种类反过来,先自己的段、快捷栏兜底;生物及其装备/饲料一概不上栏。药水落进背包,快捷栏就是空的,

回包形状本身两边一致:`01 | u8 条数 | 条数 ×(u16 槽位, u32 物品, u32 数量)`。
归档见 [a21-tutorial-ending-20260826](../../patterns/data/traces/a21-tutorial-ending-20260826.md)。
