## A21：已实现，且是入站最频繁的一帧

**副本里每一段剧情演出的开始与结束。** 客户端走到一个脚本点就发一次「暂停开始」，演完再发一次
「暂停结束」，服务端各回一帧确认，脚本才继续。参照的教学本一局里它出现 **38 次**——所有入站
type 里最多的一个。

### 请求：2 字节，一开一合

参照抓包 `packet_log.upstream-tutorial-20260827.txt`，38 帧只有四种体，且**严格配对**：

| body | 次数 | 含义 |
|---|---:|---|
| `00 01` | 1 | requestType 1 暂停开始 |
| `01 01` | 1 | requestType 1 暂停结束 |
| `00 02` | 18 | requestType 2 暂停开始 |
| `01 02` | 18 | requestType 2 暂停结束 |

样本存于 [`samples/0x00BF-2026-08-27-01.hex`](samples/0x00BF-2026-08-27-01.hex)（开始）与
[`samples/0x00BF-2026-08-27-02.hex`](samples/0x00BF-2026-08-27-02.hex)（结束）。

「18 对」与教学本的房间数对得上：每进一间房演一段、演完收一段。requestType 那一对 1 是开场的
单独一段。**两个字节的含义在机器区已是 Confirmed**，来自上游 `DungeonTutorialHandler` 读
`body[0]`/`body[1]` 再原样写回。

### 应答：换了个 type 回来

```text
C->S  CMD  0x00BF  00 02
S->C  NOTI 0x00AA  03 00 00 02      u16 用户号 + 原样回显请求那两字节
```

上游把两个字节**原样送回**，不作判断——服务端是在确认客户端的状态转换，不是替它选一个。本仓
照做，逐字节相同，见
[a21-dungeon-wire-20260826](../../patterns/data/traces/a21-dungeon-wire-20260826.md)。开头那
`03 00` 是发起者的用户号，随会话变（该次参照是 3，本仓一局是 1），不是常量。

### 机器区把它标成 request-only，那一栏在这里是错的

上面「身份说明」写着 `request-only (no client response handler)`，理由是客户端没有为
**同一个 type** 注册接收 handler。这是真的，也不相干：**应答走的是另一个 type**（NOTI
`0x00AA`）。只看同 type 注册表的普查，看不见换号回来的应答。

这不是这一条独有的毛病，是普查判据本身的边界。凡是「请求一个 type、应答另一个 type」的协议，
`request-only` 这一栏都会这么说。

### 不答会怎样

**脚本停在它要求停的地方，再也不动。** `a21-room-clear-20260826` 记了一次：客户端发了
`00 02`（暂停开始），此后**再没发过 `01 02`**，只剩心跳——连接没断，游戏也没法继续。这一帧
的漏答不会炸连接，只会静静地卡住演出，是最难从日志上看出来的那一类。
