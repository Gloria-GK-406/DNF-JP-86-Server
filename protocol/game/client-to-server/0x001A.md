## 当前实现边界（2026-09-20）

机器区仍是早期普查结果；之后对普通系统分解构包函数 `0x016F7B80` 的逐指令复核表明，
`0x016F7F30` 开始写入的 body **恰好为 9 字节**，`0x016F7FDE` 随即发送：

```text
i16 targetSlotIndex
u8  itemSpace
i16 disjointToolSlotIndex
i32 disjointProviderId
```

offset 3 是便携式分解机道具在主背包中的槽位，`-1` 表示没有便携工具。Handler 将两种合法
形状直接分流：`toolSlot == -1` 进入 NPC 分解命令；`toolSlot >= 0 && providerId == 0` 进入
便携分解命令。两个命令不再用可空工具槽表达模式。

offset 5 命名为 `disjointProviderId`：NPC 模式下静态数据流与 A21 PVF 三方闭合为服务提供者的
NPC index（例如 `1000=德利拉`、`20064=勇者装备分解机`）。2026-09-20 A21 实机采样确认，
便携模式下该字段恒为 `0`：普通、坚固、优质三档单件请求分别携带工具槽 89、90、91，随后
普通档批量分解的三条逐件请求均重复携带工具槽 89，六帧的 providerId 全部为 0。因此便携
分解机身份只由 offset 3 指向的服务端背包物品决定；providerId 仍只保留在协议 DTO 和诊断日志，
不作为便携资格或产物计算权威。

玩家分解师商店不走本协议：分解窗口状态 `0xF` 使用独立 tick `0x0235EA20`，逐件发送
`0x00EB {u16 StoreOwnerUserId, i16 TargetSlotIndex, u8 ItemSpace}`；它不会再嵌套发送 `0x001A`。
详细证据、撤回记录和动态验证矩阵见
[A21 分解供应商字段调查](../../../Document/Verification/2026-09-19-A21-disjoint-provider-client-investigation.md)。

批量分解 UI（`0x0235E480`）没有批量协议；它遍历选择项并在 `0x0235E7E2`
反复调用同一个单件发送函数。实机样本也确认同一次便携批量分解会为每件装备重复发送同一工具槽。
因此服务端把每一帧作为独立事务处理并各消耗一个便携分解机，前一件成功不要求后一件也成功。

便携工具资格由服务端读取 offset 3 槽位中的真实物品，并从 PVF 的 `[portable disjoint]` 档位和
`character/expertjob/disjointer.exj [portable disjoint info]` 得到可分解等级上限 30/50/70/90。
工具扣除、目标装备删除和产物写入处于同一事务，失败不会只消耗工具或只删除装备。

成功响应采用上游可执行实现的布局；成功流程已获 A21 客户端行为验证，但响应 body 仍无归档
实帧，因此下列逐字段布局保持上游/服务端实现证据，不能仅凭 UI 成功升级为线级 Confirmed：

```text
u8  success = 1
i16 targetSlotIndex
u8  itemSpace
u8  materialCount
repeat materialCount:
  i16 materialSlotIndex
  i32 materialItemId
  i32 materialCount
```

失败响应为 `00 + errorCode`；当前实现使用上游的 `0x04`（材料栏无空间）和
`0x13`（目标/请求无效）。分解产物不是客户端权威：服务端读取
`etc/disjoint.etc` 与装备定义，以系统分解规则生成结果。以上请求构包为客户端静态证据，
响应字段布局与产出规则分别属于上游/服务端实现证据；客户端成功行为不能反推未归档的响应字节。

2026-09-20 的首次便携分解实机验收发现：两条请求后数据库中源装备已删除、工具数量已从
20 降至 18，晶体/灵魂产物也已落库，但 A21 客户端没有把这些变化反映到背包界面。这证明
本仓此前仅发送上述 `0x001A` 成功响应不足以完成客户端背包同步；它是否因响应布局仍有差异，
或原本就只负责结果 UI，尚未由客户端静态链路最终裁决。

当前服务端在成功响应后另发 `NOTI 0x000E UPDATE_ITEM_LIST`，投影事务提交后的绝对状态：

- 源装备槽为空；
- 便携分解机槽为扣除后的最终数量（耗尽时为空）；
- 晶体、宇宙灵魂等全部产物槽为合并/新建后的最终数量。

`0x001A` 中的产物 count 仍是本次分解结果，用于结果展示；`0x000E` 使用最终绝对数量校正背包，
两者职责不再混用。

## 2026-09-20：修复后 A21 实机验收

用户在合并后的主干 Release 上重新执行分解并检查背包，确认此前“事务已落库但客户端仍显示旧
数量”的问题不再出现；随后切换同一账号的另一个角色，晶体与五种品级灵魂仍显示相同余额，
符合账号级材料袋的验收结果。该一次性观察证明以下**客户端可见流程**闭合：

1. `0x001A` 成功流程能够完成原生分解结果展示；
2. 随后的背包绝对状态刷新能够让当前角色看到分解后的材料状态；
3. 换角色重新入场后，账号虚拟材料从同一持久化状态恢复，而不是从角色材料槽恢复。

本次没有归档修复后 S2C 帧抓包或读取跟踪，因此它不证明 `0x001A` 成功响应的每个字段，也不把
`NOTI 0x000E` 的具体 body 提升为 `WireCaptured`。分解流程的跨协议编排见
[装备分解流程](../../patterns/flow-equipment-disjoint.md)。
