## 当前实现边界（2026-09-19）

机器区仍是早期普查结果；之后对普通系统分解构包函数 `0x016F7B80` 的逐指令复核表明，
`0x016F7F30` 开始写入的 body **恰好为 9 字节**，`0x016F7FDE` 随即发送：

```text
i16 targetSlotIndex
u8  itemSpace
i16 disjointItemSlotIndex
i32 contextValue
```

系统 NPC 路径当前只接受 `itemSpace=Main`、`disjointItemSlotIndex=-1`。末尾
`contextValue` 是客户端/UI 透传的非权威上下文值：批量分解调用点从窗口对象读取它，
上游解析后也不参与装备资格或产物判定，因此服务端不得要求它恒为 `0`。便携式分解道具
会进入另一条客户端路径，本次不归入普通系统分解。

批量分解 UI（`0x0235E480`）没有批量协议；它遍历选择项并在 `0x0235E7E2`
反复调用同一个单件发送函数。因此服务端把每一帧作为独立事务处理，前一件成功不要求后一件也成功。

成功响应采用上游可执行实现的布局，尚待 A21 实帧确认：

```text
u8  success = 1
i16 targetSlotIndex
u8  itemSpace
u8  materialCount
repeat materialCount:
  i16 materialSlotIndex
  i32 materialItemId
  i32 materialCount
```

失败响应为 `00 + errorCode`；当前实现使用上游的 `0x04`（材料栏无空间）和
`0x13`（目标/请求无效）。分解产物不是客户端权威：服务端读取
`etc/disjoint.etc` 与装备定义，以系统分解规则生成结果。以上请求构包为客户端静态证据，
响应与产出规则为上游/服务端实现证据，均不能标为 `ClientVerified`，直至实机 UI 与持久化结果通过。
