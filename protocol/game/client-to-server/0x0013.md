## 快捷栏不是独立容器，是主背包的第 3~8 格

这是本条最重要的结论，而且它推翻了 `InventoryListType.QuickSlot = 29` 给人的第一印象。

实机这帧**两端都是 list 0**。上游三处独立命名同一个区间：

| 位置 | 常量 |
|---|---|
| `InventoryMoveService.cs:72` | `MainQuickSlotRange = new ItemSlotRange(3, 8)` |
| `InventoryInsertService.cs:73` | `QuickSlotRange = new ItemSlotRange(3, 8)` |
| `ItemSlotBoundService.cs:31-32` | `MainQuickSlotStart = 3` / `MainQuickSlotEnd = 8` |

所以主背包 list 0 的槽位空间是：

```
0..2     ——（无 kind 归属）
3..8     快捷栏，数字键那一排，几乎任何 kind 都能放
9..64    装备
65..120  消耗品
121..176 材料
177..232 任务
233..288 专家职业材料
289..344 时装徽章
345..359 立方碎片
```

「物品栏是快速访问入口、背包才是真源」这个直觉在**建模上不成立**——它们共用一份
`item_core`、一个槽位空间，不存在两份数据，也就没有复制/同步问题。真正的差别只是
UI：客户端把 3~8 这六格另画了一排。与仓库（`PersonalCargo=2` / `AccountCargo=12`）
完全不是一回事，那些才是独立容器。

`QuickSlot = 29` 这个枚举值在本条路径上从未出现，它指的是别的东西，尚未查明。

## 请求可能是反着发的

实机这帧里 `srcSlot=3` 是**空格**，`dstSlot=65` 才有药（`dstIV=8474` 就是药的 itemId）。
按字面读是"把空的搬到有东西的格子上"，讲不通。

正确读法是：**客户端在指名它想要被填上的格子**。上游对此有专门分支
（`InventoryMoveService.cs:96-137`）：源槽取不到物品时，回头把 `Destination*` 当作
物品来源，反向搬一次。两种读法在实现上等价（空↔满的交换 = 单向搬运），
所以上游用一个 `reverseSource` 兜底就够了。

**ACK 无论走哪个分支都原样回请求自己的 src/dst**，因为客户端是拿回执和自己发的对账。

## 不回它会怎样：背包锁死

实机这帧是**整份抓包的最后一帧**。客户端发完就静默等 ACK，期间背包进入挂起状态，
后续任何拖动都不再产生报文——表现为"拖了没反应"，很容易误判成客户端不支持拖动。

和 [`0x0025`](0x0025.md) 一样属于必答，但症状不同：那个卡进度条并超时断线，
这个不断线，只是背包不再响应。

## 应答：同 type 的 CMD ACK

上游 `MoveItemSpaceAckBuilder`：

| 结果 | 长度 | body |
|---|---:|---|
| 成功 | 11 | `01` + `u8 srcList` + `i16 srcSlot` + `i32 moveValue` + `u8 dstList` + `i16 dstSlot` |
| 失败 | 4 | `00` + `u8 错误码` + `u8 srcList` + `u8 dstList` |

错误码：`0x02` = 操作不允许（目标槽非法、不能堆叠、不能交换），
`0x04` = 服务端拒绝（无租约、源不存在）。

`moveValue` 是**实际搬走的数量**，不是请求里的 `moveCount`。
`moveCount = 0` 表示整堆（`NormalizeMoveCount`：`<=0` 或超过堆叠数都取整堆），
只有拆分对话框才会填真数字。

## 触发点：教学奖励会自动跟一帧

实机顺序：

```
send 0x008F  26000000 01                    教学 flag 38
recv 0x008F  01 01 4100 1A210000 01000000   服务端答：物品 8474 ×1 落在槽 65
send 0x0013  src=(0,3) dst=(0,65,IV=8474)   客户端立刻要求搬到快捷栏
```

也就是说 [`0x008F`](0x008F.md) 的回执里报哪个槽，客户端就会据此决定要不要再搬一次。
上游发放消耗品时**优先塞快捷栏**（`InventoryInsertService.cs:104-106`：
`canUseQuickSlot && ItemKind == KindConsumable` 时先试 3~8 再试本命区间），
所以参考实现下这一帧本来不会出现——它出现恰恰是因为我们把药发在了 65。
两种做法都对，实现 `0x0013` 更忠实：让客户端自己决定物品该在哪。

喝掉它是另一条：[`0x002C USE_STACKABLE`](0x002C.md)。
