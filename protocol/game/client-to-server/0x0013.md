## 快捷栏不是独立容器，是主背包的第 3~8 格

这是本条最重要的结论，而且它推翻了 `InventoryListType.QuickSlot = 29` 给人的第一印象。

实机这帧**两端都是 list 0**。上游三处独立命名同一个区间：

| 位置 | 常量 |
|---|---|
| `InventoryMoveService.cs:72` | `MainQuickSlotRange = new ItemSlotRange(3, 8)` |
| `InventoryInsertService.cs:73` | `QuickSlotRange = new ItemSlotRange(3, 8)` |
| `ItemSlotBoundService.cs:31-32` | `MainQuickSlotStart = 3` / `MainQuickSlotEnd = 8` |

所以主背包 list 0 的槽位空间是：

```
0..2     ——（无 kind 归属）
3..8     快捷栏，数字键那一排，几乎任何 kind 都能放
9..64    装备
65..120  消耗品
121..176 材料
177..232 任务
233..288 专家职业材料
289..344 时装徽章
345..359 立方碎片
```

「物品栏是快速访问入口、背包才是真源」这个直觉在**建模上不成立**——它们共用一份
`item_core`、一个槽位空间，不存在两份数据，也就没有复制/同步问题。真正的差别只是
UI：客户端把 3~8 这六格另画了一排。与仓库（`PersonalCargo=2` / `AccountCargo=12`）
完全不是一回事，那些才是独立容器。

`QuickSlot = 29` 这个枚举值在本条路径上从未出现，它指的是别的东西，尚未查明。

## 请求可能是反着发的

实机这帧里 `srcSlot=3` 是**空格**，`dstSlot=65` 才有药（`dstIV=8474` 就是药的 itemId）。
按字面读是"把空的搬到有东西的格子上"，讲不通。

正确读法是：**客户端在指名它想要被填上的格子**。上游对此有专门分支
（`InventoryMoveService.cs:96-137`）：源槽取不到物品时，回头把 `Destination*` 当作
物品来源，反向搬一次。两种读法在实现上等价（空↔满的交换 = 单向搬运），
所以上游用一个 `reverseSource` 兜底就够了。

**ACK 无论走哪个分支都原样回请求自己的 src/dst**，因为客户端是拿回执和自己发的对账。

## 不回它会怎样：背包锁死

实机这帧是**整份抓包的最后一帧**。客户端发完就静默等 ACK，期间背包进入挂起状态，
后续任何拖动都不再产生报文——表现为"拖了没反应"，很容易误判成客户端不支持拖动。

和 [`0x0025`](0x0025.md) 一样属于必答，但症状不同：那个卡进度条并超时断线，
这个不断线，只是背包不再响应。

## 应答：同 type 的 CMD ACK

上游 `MoveItemSpaceAckBuilder`：

| 结果 | 长度 | body |
|---|---:|---|
| 成功 | 11 | `01` + `u8 srcList` + `i16 srcSlot` + `i32 moveValue` + `u8 dstList` + `i16 dstSlot` |
| 失败 | 4 | `00` + `u8 错误码` + `u8 srcList` + `u8 dstList` |

错误码：`0x02` = 操作不允许（目标槽非法、不能堆叠、不能交换），
`0x04` = 服务端拒绝（无租约、源不存在）。

`moveValue` 是**实际搬走的数量**，不是请求里的 `moveCount`。
`moveCount = 0` 表示整堆（`NormalizeMoveCount`：`<=0` 或超过堆叠数都取整堆），
只有拆分对话框才会填真数字。

## 触发点：教学奖励会自动跟一帧

实机顺序：

```
send 0x008F  26000000 01                    教学 flag 38
recv 0x008F  01 01 4100 1A210000 01000000   服务端答：物品 8474 ×1 落在槽 65
send 0x0013  src=(0,3) dst=(0,65,IV=8474)   客户端立刻要求搬到快捷栏
```

也就是说 [`0x008F`](0x008F.md) 的回执里报哪个槽，客户端就会据此决定要不要再搬一次。
上游发放消耗品时**优先塞快捷栏**（`InventoryInsertService.cs:104-106`：
`canUseQuickSlot && ItemKind == KindConsumable` 时先试 3~8 再试本命区间），
所以参考实现下这一帧本来不会出现——它出现恰恰是因为我们把药发在了 65。
两种做法都对，实现 `0x0013` 更忠实：让客户端自己决定物品该在哪。

喝掉它是另一条：[`0x002C USE_STACKABLE`](0x002C.md)。

**这一句对它自己那一帧成立,不要当通则读(2026-09-08 补注)。** 那件护肩去的是装备槽 15,而
NOTI `0x0002` 子类型 0 画外观只读 `0..12` 与 `23`(生物三元组另读 `24`),**15 不在里面**,所以
它后面确实什么都不跟。上游按同一个形状判——`ShouldSendSubtype0AppearanceUpdate` 看的正是「变的

`TheCharacterChangesAsYouDressItTests`。

**目标槽由服务端自己算,不采信请求。** 物品在 `equipment/*.equ` 里声明 `[equipment type]`,
值是一个引号词:14400 是 `[shoulder]`、27600 是 `[weapon]`、10400 是 `[coat]`、12400 是
`[pants]`。名字到槽号的表与角色创建时读的 `[create equipment list]` 是同一张。客户端本地就会
算这个,不会提交它认为非法的拖放 —— 正因如此服务端不能拿请求当答案。

**脱下来是同一 type 两个列表对调**,本仓已实现。

**2026-09-08 实机,有样本了,而且它推翻了上面那半句「已实现」。** 玩家把穿在装备槽 1
（发型装扮）的时装拖回装扮页第 0 格,客户端发的是:

```text
源列表 1(装扮页) 源槽 0 | srcIV 0 | 数量 1 | 目标列表 3(装备) 目标槽 1 | dstIV 413560000
```

**东西在目标端,身份也在目标端**,源端是玩家松手的那个空格 —— 正是本页上面
「请求可能是反着发的」记着的那一种。本仓当时三条跨列表的路
（`PutOnAsync` / `TakeOffAsync` / `CarryAcrossAsync`）都只读自己的源端,读到空就回
`BothSlotsEmpty`,所以**每一次脱下都被拒**,日志读作 `item 0`。列表内的移动
（`StoreBackedItemContainer.MoveToAsync`）一直是对的,那条规则没被带到跨列表的三条路上。

也就是说:**「本仓已实现」当时只对正着发的那一半成立**,而客户端脱下来时发的是反着的那一半。
**抓到的是一帧**（上面那条）;**「所以一次也没成功过」是从它推的**——所有者当天报告 11 件时装
一件也脱不下来,而正着发的脱下当时是能成的,所以那 11 次发的应当都是反着的那一半。
推论没有第二帧佐证。三条路现在都按「哪一端有东西就动哪一端」办,两端都空才是
`BothSlotsEmpty`；判据见 `EitherEndMayBeHoldingItTests`。

**一条复述守卫**。上游有它的一半（`InventoryMoveService.IsEquipmentClientEchoWhenSourceMissing`,
只读参照）:源端为空、目标端是装备栏、且请求在**源端**写了一个等于该装备 itemId 的实例值时,那是
客户端在复述一次已经被应答过的移动,不能按反向搬运办 —— 否则刚穿上的会被当场脱下。
本仓最初照抄了这一半,记作 `MoveAlreadyMade`,客户端码同 `BothSlotsEmpty`(`0x02`,不画字)。

**照抄的那一半只认一个方向,而脱下被复述走的是另一个方向**,于是刚脱下来的会被当场穿回去。
本仓现在按对称的说法办,不再限定哪一端是装备栏:

> 请求把身份写在那件东西**来的那一端**。如果它指名的那一端是空的、而库里那件东西在另一端,
> 这次移动已经做过了。

`MOVE_ITEMSPACE` 分派到**四**条路——穿上、脱下、跨列表搬运,以及同列表内的移动（它交给
`StoreBackedItemContainer.MoveToAsync`,而那里正是这条「哪一端有东西就动哪一端」规则的出处）。
四条路各按上面那句话判两次,一次读源端的实例值、一次读目的端的,共八处。

它的安全性在于这是一个**矛盾**而不是一种相似。判据见 `EitherEndMayBeHoldingItTests`（变异 N3
实测:去掉身份相等那一条,一次合法移动就会被误伤）。

**但那是证据,不是证明。** 有一种形状会击穿它:客户端若把**正在移动那件东西**的身份写在一个
**空的目的端**上,四个子句会全中,一次合法的穿上会被拒。已观测的 11 次穿上目的端那一栏都是零,
所以证据范围内够不到——但「没见过」不等于「不会有」。本文早先一版把这句写成了「一次真实的拖拽
永远不会……」,那是把证据说成了证明。

两端实例值到底是什么语义,本身也没有定论:可以读作「每一端指名从它那里出发的东西」,也可以读作
「每一端指名自己的占用者、空则为零」。**两种读法吻合全部 12 次观测**,而后一种会让上述误伤形状
根本不存在。定它需要在跑着的客户端上抓一帧。

**未实机观测**:至今没有人抓到过一次复述。整条修复建立在「复述发的是原样的字节」这个假设上;
若客户端是按新状态重新组帧,复述与真实拖拽逐字节相同,这条守卫就永远不触发。
