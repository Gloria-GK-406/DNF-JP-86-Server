# `0x04DD` `CHECK_USER_CONNECTION`

> 本记录为手写，不是静态普查生成的：普查跑在 A12 客户端上，那份枚举里没有这个 type。
> 名称取自 A21 客户端字符串表中的 `ENUM_CMDPACKET_CHECK_USER_CONNECTION`。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server |
| Command | `0x01`（CMD） |
| Type | `0x04DD` |
| Role | Query / 有响应 |
| 阶段 | 实现服务端功能 |

## Wire layout

帧结构见 [game-frame.md](../../patterns/game-frame.md)；A21 入站 header 为 14 字节。

### 请求

```text
BodyLength = 0
```

没有字段。整帧就是 14 字节 header。

### 响应

同一 command 族、同一 type，body 为 CMD 接受包封的单字节：

```text
BodyLength = 1
Body       = 01
```

即 [`GameCmdEnvelope`](../../patterns/game-receive.md) 的接受字节本身，其后没有载荷。

## Samples

请求（实测，取自本仓服务端与 A21 客户端的一次会话）：

```text
01 DD 04 0E 00 00 00 8A D6 51 F4 00 0D 00
   ^type       ^len=14  ^checksum  ^保留 ^seq=13
```

响应（实测，同一会话）：

```text
01 DD 04 10 00 00 00 00 00 00 00 00 00 00 00 | 01
   ^type       ^len=16  ^出站 15 字节 header  ^body
```

一次已知良好会话里出现三十次请求、三十次响应，横跨整局（探测帧的 seq 为 13,15,16,…,179,181,182）。

归档摘录：[`patterns/data/traces/a21-world-entry-20260823.log`](../../patterns/data/traces/a21-world-entry-20260823.log)
的 `[C]`（全部探测的 seq）与 `[E]`（请求/响应原始字节）两节。

**间隔"约十秒"不由该会话支撑**——它的日志不记时间戳。该数值来自本仓服务端一侧的中转记录
（归档件 `[G]` 节的相对时刻），只作参考。

## Client reversing evidence

| Evidence | Kind | Location | Supports |
|---|---|---|---|
| `E-001` | dynamic | [归档件](../../patterns/data/traces/a21-world-entry-20260823.log) `[E]` 节（源：`ServerS4A21` 一整局 458 帧会话） | 请求恒为 14 字节且 body 为空；响应同 type、body 恒为单字节 `01` |
| `E-002` | dynamic | 同上 `[C]` 节 | 三十次请求全部得到应答，探测仍持续到会话结束——是周期性保活，不是"未应答才重试" |
| `E-003` | dynamic | 同上 `[B]` 节 | 客户端在首条探测（seq 13）之前就发出了 LOGIN（seq 0）：探测不门控登录 |

**没有指令级证据**：本记录尚未定位客户端发出该探测的构包点或接收应答的 handler，
因此按 [catalog.md](../../catalog.md) 的准入条件不能进入 `双向验证结束`。

支持客户端 SHA-256：`1F8244D3F7309BBE2FDE4299E1863A894F6B28D5707BF01732980585B20B00DD`
（A21，`DNFClient-A21-protocol/DNF.exe`）。

## Server and historical evidence

上游参考实现把它接在登录处理器上并回一个固定 6 字节零 body 的另一条协议之外，
对本 type 回的是 `GamePacketEnvelopeBuilder.Build(0x01, SECURITY_STATUS, ...)` 之类的常量应答；
本记录不采用其字节，采用实测的单字节 `01`。

**不接它的后果，比一开始以为的小。** 本仓在接上它之前，传输层按线级键查不到解包器，
帧被静默丢弃；客户端照常继续发，服务端日志里只留一条重复的未处理帧告警，看着像噪声。

本记录此前把它写成"客户端拿不到应答就不会发登录命令"，**那是错的，并且被本记录自己引的
会话直接推翻**：该会话第一条入站帧就是 LOGIN（seq 0），首条探测在 seq 13。当时之所以只看到
探测在重复而没看到 LOGIN，真实原因是 `NOTI 0x0001` 初始连接通知那 8 个字节还没修对
（见 [NOTI-0x0001.md](../server-to-client/NOTI-0x0001.md)），与本协议无关。

## Verification

- Parser/codec vectors：空 body 解码通过；带 body 的请求被拒（那意味着入站 header 边界又错了）。
- Boundary cases：body 非空即抛，不容忍。
- Response count/order：一问一答，不批量。
- Real-client result：A21 客户端在本仓服务端上收到应答（归档件 `[G]` 节可见成对的
  `CMD/04DD` 往返）。**"被应答后停止重发"不成立**，见 `E-002`。

## Unknowns and next evidence

| 未知 | 最便宜的证据 |
|---|---|
| 应答 body 的单字节是否必须为 `01`，还是任何非零值均可 | 改成别的非零值再跑一次会话，看客户端是否仍继续 |
| 客户端在多长时间收不到应答会放弃（若会） | 注册解包器但不回包，观察它重试多少次后的行为 |
| 探测的构包点与应答的接收 handler（进入 `双向验证结束` 所缺的指令级证据） | 在 A21 客户端上重跑构包点普查，或对该 type 的收发路径下断点 |
