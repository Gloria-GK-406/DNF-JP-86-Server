## 地址口径：本页地址都是 RVA，不是 VA

换算 **VA = RVA + 0x400000**。本帧的应答 handler `0x00D05250` 处是 `55 8B EC` 的函数首字节；
按 VA 读同一数值会落在指令中间。**注册表里存的却是 VA**：`0x00D0C3E6` 处
`push 0; push 0x01105250; push 0x47; call 0x0123C4A0` —— `0x01105250` 就是 `0x00D05250 + 0x400000`。

读写原语：`0x0234CA50` 取写入器、`0x0234D1E0` `Begin(type, x)`、`0x0234D2E0` `WriteU8`、
`0x0234D340` `WriteU32`、`0x0234E6D0` 发送；读侧 `0x023C5230` 读 1 字节 / `0x023C5310` 读 4 字节。

## 请求 C→S：2 字节

| 偏移 | 宽 | 含义 | 取值 |
|---:|---:|---|---|
| 0 | 1 | 牌型 | `0x00` 免费 / `0x01` 付费 |
| 1 | 1 | 牌位序号 | `0x00`–`0x03` |

**第二字节恒为 `00`。** 上游 9 份收包日志里 `RECV 0x0047` 共 14 帧，去重只有 `[00 00]` ×10 与
`[01 00]` ×4；实机也复现。**客户端不在这一帧里说翻的是哪一张** —— 它自己记在 `[panel+0x6FC]`
（普通行）/ `[panel+0x65C]`（黄金行）里，从不上线。

全镜像 1411 个 `Begin` 调用点扫过一遍，以 `0x47` 起包的**只有两处**：

| 构包点 | 写法 | 走哪条 |
|---|---|---|
| `0x00704460` / `0x0070446E` | `WriteU8(0)`（`0x0070447C`）+ `WriteU8(arg2)`（`0x0070448C`） | 点牌面那条，首字节写死 0，**永远发免费牌** |
| `0x00D10C30` 里的 `0x00D10DFF` | 只写**一个**字节，值是 `[[0x03B3DFB8]]` 虚表槽 `+0xB68` 的返回值（`0x00D10E17`） | 门槛 `[obj+0x558] != 0` 才走 |

第二个构包点发的那个字节，和应答里 `a`、`b` 被拿去比较的**是同一个值**。

上游语料里首字节 `01` 的那 4 帧，A21 客户端两个构包点都发不出来 —— **这条冲突未查明**，
语料是上游服务端自己的收包日志，产生它的客户端版本没钉死。

## 应答 S→C：信封 + 8 条记录

```text
byte 0      0x01        CMD 成功信封（接收路径在分发前读掉，handler 看不到）
byte 1..    8 条记录
```

循环从 `0x00D05270` 到 `0x00D0538B`（`inc esi; cmp esi,8; jl`），`esi` = 记录序号 0..7。

### 一条记录

| 字段 | 宽 | 含义 | 读取点 |
|---|---:|---|---|
| `a` | 1 | 这一列的**普通牌**被谁翻了 | `0xD05276` |
| `b` | 1 | 这一列的**黄金牌**被谁翻了 | `0xD0529B` |
| `c` | 1 | 其后 `(u32,u32)` 条目的条数 | `0xD052A6` |
| 条目 | 8×`c` | `u32 itemId` + `u32 amount`；`itemId == -1` 是金币 | `0xD052DB` / `0xD052E4` |
| 尾 | 1 | 标志 → `panel+0x789[记录序号]` | `0xD05365` |

**记录序号 = 第几列。**

`a` / `b` 的取值是**座位号**，不是布尔：

| 值 | 含义 |
|---|---|
| `0xFF` | 这一格没人翻 |
| 等于自己的身份值（单人实测 = `0`） | **我**翻的 |
| 其他 | **别人**翻的 |

实机：四条记录写 `a = 0x00 / 0x01 / 0x02 / 0x03`，**只有 `0x00` 那一条生效**，其余三条什么都没发生。
若 `a` 是布尔（`0xFF` 假、其余真），四条该全生效。

条目落地：`AddCard(itemId, amount, b, kind)`，`kind=3` 物品 / `kind=4` 金币，存进
`panel + 0x1E8 + 100*b + 20*kind` —— 注意 slot 取的是 **`b`**，不是记录序号。

### 三条门槛只挡落地，不挡读取

`(u32,u32)` 对在 `0xD052DB` 就已经从流里读走了，`b > 7`（`0xD052EC`）与「已翻过」（`0xD052F2`）
两道判断在**读之后**。所以被跳过的记录照样吃掉 `8*c` 字节，帧不会错位。同理 `a == 0xFF`
也不会让这条记录不被解析。

### 长度

```text
BodyLength = 33 + 8·Σcᵢ
```

八条全不带条目 = **33 字节**，与抓到的空脸应答一致。

## `a` / `b` 落到面板的哪里

`a` 交给 `0x21EF990(记录序号, a)`，`__thiscall`，this = 面板：

```c
if (a == 0xFF) return;                          // 0x21EF999

int me = g_main->vtbl[0xB68]();                 // 0x21EF9AD / 0x21EF9B6
if (me != a) {                                  // 0x21EF9B8 / 0x21EF9BA
    panel[0x694 + 4*a] = a;                     // 0x21EFA70   记到「别人」那张表
    PlayResource(0x3062D20);                    // 0x21EFA81   别人翻牌的表现
    return;
}

for (k = 0; k < 8; k++)                         // 0x21EF9D0 … 0x21EF9E2
    controls[0x550 + 8*k]->vf_0x88(0x7D);

int col = (panel[0x6FC] != -1)                  // 0x21EF9E4 / 0x21EF9ED
        ? panel[0x6FC]                          //   我刚点的那一列
        : recordIndex;                          //   还没点过 → 记录序号
panel[0x530 + 4*col] = a;                       // 0x21EF9F9 / 0x21EFA2B
panel[0x590]         = col;
controls[0x550 + 8*col]->vf_8();                // 翻牌动画
panel[0x594 + 4*col] = ...;                     // 0x21EFA1F
PlayResource(0x3067ADC);                        // 0x21EFA58   自己翻牌的表现
```

**下标是列，写进去的值是 `a` 本身**（座位号），不是记录序号。

`b` 是同一份代码的镜像 `0x21EFAA0`：同一个全局、同一个 `+0xB68`、同样的相等判断，写
`panel+0x5B8[列] = b`，「刚点的列」取 `[panel+0x65C]`。两行各记各的，所以重发一条已翻的
`a` 不会被新点的黄金牌列带跑。

`panel+0x530[]`（普通行）与 `panel+0x5B8[]`（黄金行）各 8 项，复位时都置 `-1`
（`0x21F7E3C` / `0x21F7E46`）；`0x21EEE70` 数这两排里非 `-1` 的项数，都等于 `[panel+0x1E4]`
才算这一局翻完，而 `[panel+0x1E4]` 由结算帧组 0 的非空 slot 数累加（`0x21EF2C0`）。

**两条分支播的是两个不同的资源** —— 自己翻牌和别人翻牌，客户端本来就打算表现得不一样。

## 开牌有两条路，本帧只是其中一条

| 路径 | 触发 | 作用 |
|---|---|---|
| 本地点击 | 玩家点牌 | 立刻翻开自己点的那一张，**不等服务端** |
| 本帧里 `a == 我` | 收到帧 | 也翻开，并记下「这一列算谁的」 |

实机证据：把应答改成八条全填充（`a`、`b` 全 `0xFF`），**牌照样翻开**。所以本帧不是翻牌的必要条件。

但它不是冗余：丢掉它，重连后面板是空的、组队时看不到队友翻了哪张、`panel+0x694[]` 永远是空的。

## 本帧可以主动推，不需要客户端先问

**实机证实。** 在面板刚摆出来、玩家一张都没点的时候，服务端主动推一帧应答，记录 0/1/2 写
`a = 0x00`，客户端立刻把三列翻开（此时 `[panel+0x6FC]` 还是 `-1`，所以记录 k 落在第 k 列）。

线上没有「这是回复」这回事：`0x01` 只是族，`0x0047` 是 type，客户端按 type 查分发表，
登记的 handler 处理**任何**到达的该 type 帧。

配套的一条约束：**推过去的帧是即时生效的，没有动画缓冲**。所以不能在玩家自己那一格预推
已翻状态 —— 会直接吞掉他的操作。

## 参照服务端怎么写

`CardRewardNotificationSender.BuildCardInfoAck`：

```csharp
writer.WriteByte(0x01);                       // 信封
for (index = 0; index < 8; index++) {
    if (index >= 4) { FF FF FF FF; continue; }        // 记录 4-7
    if (index != 0) { FF FF 00 00; continue; }        // 记录 1-3
    a = freeSelected ? 0x00 : 0xFF;
    b = paidSelected ? 0x00 : 0xFF;
    if (paidSelected) { c = 2; (0, 付费金币); (付费物品, 数量); }
    else              { c = 0; }
    tail = 0x00;
}
```

两点要紧：

1. **免费翻牌 `c = 0`，一件东西都不带。** 免费牌的内容全部由结算帧
   [`NOTI 0x0023`](../server-to-client/NOTI-0x0023.md) 的组 0 提供，本帧只说「这一列算谁的」。
2. **它是从状态数组重建整帧的**（逐条读 `FreeCardSlots[i]` / `PaidCardSlots[i]`，两者都是 `byte[4]`），
   所以是**幂等的状态快照**，不是事件回执。这也正是它能拿来广播的原因。

记录 1–3 上游用 `FF FF 00 00`（`c = 0`，**合法**），只有记录 4–7 才用 `FF FF FF FF`
（`c = 0xFF` 声明有 255 对条目，不合法）。七条全用后者是本仓自己引入的，比上游差一档。

## 组队（推论，未实测）

单人已实测出那个身份值 `= 0`，`a`/`b` 与它做相等比较。据此推出的组队形状是：

```text
队员 X → S      0x0047 (牌型, 0)
S → 队伍每个人   同一帧应答，8 条记录 = 当前整块面板状态
                 记录 k：a = 第 k 列普通牌被哪个座位翻了，没人写 0xFF
                         b = 第 k 列黄金牌同理
                         c = 0
```

每人收到同一份快照，各自客户端拿 `a` 和自己的身份值比：相等画到自己面板，不等落进
`panel+0x694[a]` 并播另一个资源。**不需要第四种帧。**

**没验的是「身份值 = 我的队伍座位号」这个语义本身** —— 单人时它是 `0` 已实测，
「我在 2 号位时它变成 2」要真的组队才知道。当前服务端按队伍槽位写 `a`/`b`；这是
上游建模与双开画面共同支持的实现假设，尚未由双人原始帧确认。

## 请求被丢弃的三种情形

牌型不是 `0x00` / `0x01`、牌位序号 > `3`、体长不足 2 字节 —— 解包时返回 null，丢帧，连接不受影响。
与上游 `cardType > 1 return` / `cardIndex > 3 return` 同界。`0x00D10DFF` 那条 1 字节的付费请求
因此不被接受：它的语义未查明，不猜。
