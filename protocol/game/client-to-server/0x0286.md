# `0x0286` `CHARAC_VIEW_HIDDEN_CHARAC_INFO`

> 名称取自旧服 `CmdPacketType` 枚举。**注意同号异义**：`NotiPacketType` 里的 `0x0286` 是
> `DAILY_CHALLENGE`，与本条无关。共享证据见
> [角色生命周期协议族](../../patterns/character-lifecycle.md)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server（响应同 type 反向，见下） |
| Command | `0x01` |
| Type | `0x0286` |
| Role | Query / 有响应 |
| 阶段 | 实现服务端功能 |

**触发时机与响应顺序不记在本页**，它们属于流程层：见 [flow-login](../../patterns/flow-login.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

本帧长期未被抓到——它不走加密路径，客户端抓包看不见。2026-08-16 由服务端的未识别帧日志
首次捕获，同时解释了 [0x02A8](0x02A8.md) 里记录的 seq 4 空缺。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。

**请求** body 长度 **0**。

**响应** body 固定 **2 字节**，就是
[CMD 结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)，
本 type 没有自己的载荷：

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | 信封 `ok`；`0x00` = 拒绝 | **Confirmed** | `E-005` |
| 1 | 1 | `u8` | 信封 `reason`，实发 `0x04` | **Confirmed** | `E-005` |

回的是**拒绝**而不是占位数据：账号没有隐藏角色可展示，这就是正确答案。旧服发的正是这两个
字节，而那时建角色是能用的。

## Samples

请求已实测（服务端日志，2026-08-16）：`selector=0x01 type=0x0286 seq=4 body(0B)`。
响应已有实机观察，见下方「实测字段表」（客户端读到 body 偏移 2，两次会话一致）。

## Client reversing evidence

| Evidence | Kind | Location | Supports |
|---|---|---|---|
| `E-001` | static | 旧服 `CharacterSelectHandler.cs:561`（`d51e74b`） | 响应常量 `00 04` |
| `E-002` | static | client handler `0x008CBBB0`，注册于 `0x008D08C1` | 客户端等响应且读 `ReadU8` |
| `E-003` | static | client handler `0x0091ABE0`，注册于 `0x0093107F` | 另一注册表也有 handler，读 `ReadU32` |
| `E-004` | dynamic | 服务端未识别帧日志，2026-08-16 | 请求存在、body 为空、seq 4 |
| `E-005` | static | 接收函数 `RVA 0x00D89B16`（CMD 分支） | 这 2 字节是族级信封，不是本 type 的载荷 |

`E-003` 那个「同一个号在两张注册表各有一个 handler」不再是悬案：两张表就是 CMD 与 NOTI
两个协议族，同号不同义是常态（见
[game-receive 的两张注册表](../../patterns/game-receive.md#两张注册表--cmd-与-noti)）。
读取宽度不同正是因为它们本来就是两条不同的消息；本文档只覆盖 CMD 那条。

`E-002` 的「读 `ReadU8`」也要重新理解：信封由接收层读掉，handler 那次 `ReadU8` 读的是
信封之后的字节——而本 type 的成功路径服务端从不触发，所以它读什么尚无观察。

## Server and historical evidence

旧服**没有为本 type 注册入站 handler**——它在 `Handle_GET_USERINFO` 里把响应跟角色列表
一起主动推给客户端。本实现改为应答实际观察到的请求，对客户端而言结果相同，且不必假设推送时序。

| Layer | Type/path | Responsibility |
|---|---|---|

## Verification

- Parser/codec vectors：编码器常量由 `HiddenCharacterInfoResponseEncoder` 固定，无分支。
- Real-client result：**已做**。实机读取跟踪确认客户端解析本响应；本地回环另测 `sel=0x01 type=0x0286 body=0004`，两者一致。

## Unknowns and next evidence

| 问题 | 影响 | 最便宜的证据 |
|---|---|---|
| 两张注册表各有 handler 的原因 | 低 | 反汇编 `0x0091ABE0` |
| 客户端是否因这条而解锁建角色 UI | 高 | 实机点一次创建角色 |

## 实测字段表（运行时读取跟踪）

客户端**实际**读取这条协议的方式，由运行时读取跟踪测得（做法见 [game-receive](../../patterns/game-receive.md#四个原语是唯一出口)）。

**本节优先于机器区的 Body 表。** 机器区那张表由静态走图产出，在 S→C 上普遍止步于打包区，给出的是下界；载荷多形时它只描述其中一形，却读起来像描述了整条协议。本节是实测，但**只给边界，不给含义**——`含义` 一列留给人填，偏移已确证之后用实机改值做差分是最便宜的填法。

偏移 0 那次读取属于**接收层**而不是 handler：每条 CMD body 都以两字节结果信封开头，由分发前的接收函数读掉（见 [结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)）。

### 形状 body 2 字节

| Offset | Size | Enc | 读取者 RVA | 实测值 | 含义 |
|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | `0x00D89B25` | 0 | — |
| 1 | 1 | `u8` | `0x00D89B57` | 4 | — |

读取 2 次，消费到偏移 **2**。
