能说的只有：它在选角色前后都会发，帧数与取值都不定。（怎么走到这个结论的见下方工作日志。）

静态普查说的"布局已闭合 = 1 字节"被样本证实。那一字节**是个会变的判别值**，不是常量：
单一构包点却发出不同取值，说明它取自调用方传入的参数。所有观察到的取值服务端都回同样的
全零响应，客户端每次都继续往下走——但这只说明全零对已见取值可接受，不说明它没有语义。

**响应已被客户端接受**：19 字节（信封 `01` + 18 个零）发出后，客户端照常发出下一帧，
没有卡住也没有错位。这同时验证了"按下界发"的做法在本条上成立。

### 响应侧：脚手架没走过，这里补上

索引的 body 状态只描述**请求**。响应的 handler 入口 `0x008C6DD0` 在普查表里，但
[extract-layout.py](../../patterns/data/extract-layout.py) 的 handler walk 只对
`direction == S2C` 的行跑，而 CMD 的请求与响应共用一行 C2S 记录——所以 538 个 CMD
响应 handler 一个都没被走过。本条是手工补的。

按同样的读取原语表走 `0x008C6DD0`：

```text
0x008C6DEA  ReadU8
0x008C6DF5  ReadU8
0x008C6DFE  ReadU32
0x008C6E07  ReadU32
0x008C6E10  ReadU32
0x008C6E19  ReadU32
            → call 0x008C6E58 → ... → 进入打包区（0x049E6650 / 0x0491687D），走不下去
```

即响应 body 在信封之后**至少**是 `u8 + u8 + u32×4 = 18` 字节。**这是下界不是总长**：
走到打包区就停了，后面还有没有字段无法从指令判断。

## 服务端实现映射

[`ContentsPlayInfoSlice.cs`](../../../Server/src/Dfo.Server.Protocol/Game/ContentsPlayInfo/ContentsPlayInfoSlice.cs)

- 请求：`ContentsPlayInfoPayloadCodec` 只接受恰好 1 字节，其余长度抛 `InvalidDataException`；
- 响应：信封 `01` + 18 个零字节，共 19 字节。

**为什么按下界发、且发零**：入站流是逐帧重设的（见
[game-receive](../../patterns/game-receive.md#入站流与读取原语sc-的取字段方式)），
少发会让 handler 把缺口从下一帧里读走，多发则在下一帧重设游标时被丢弃——所以在两个方向上，
**宁可多发**。零值是因为六个字段没有一个有已知含义；填看起来合理的数字只会把猜测固化。
