## 不回它会怎样：药水永远喝不完

实机 2026-08-18：血确实回了，但**数量不减**。回血是客户端自己算的，
服务端不应答就没人去动那一堆。表现上不像卡死，像个无限药水 bug。

和 [`0x0013`](0x0013.md) 不同——那个不回会锁死背包，这个不锁，只是静默地不生效。

## 应答：同 type 的 CMD ACK，成功和失败长度不同

上游 `UseStackableAckBuilder`：

| 结果 | 长度 | body |
|---|---:|---|
| 成功 | 12 | `01` + `i16 slot` + `u8 list` + `i32 instanceValue` + `i32 itemCode` |
| 失败 | 11 | `00` + `u8 错误码` + `u8 list` + `i32 instanceValue` + `i32 itemCode` |

**失败体里没有槽位号**——错误码写在成功体写槽位的位置上，所以两者长度差 1。
默认错误码 `23`（`InvalidItemErrorCode`）。

ACK **不带剩余数量**。客户端在发请求前就自己减了 1，服务端只需要说"这个减法算数"。
所以服务端必须**只消耗 1 个**，消耗别的数目客户端无从得知。

`instanceValue` 原样回传，上游不解释它。
