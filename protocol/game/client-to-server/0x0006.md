# `0x0006` `DELETE_CHARACTER`

> 名称取自旧服 `CmdPacketType` 枚举。共享证据与名字字段编码见
> [角色生命周期协议族](../../patterns/character-lifecycle.md)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server（响应同 type 反向） |
| Command | `0x01` |
| Type | `0x0006` |
| Role | Mutation / 有响应 |
| Trigger | 角色列表屏删除角色并输入名字确认 |
| Expected response | CMD `0x01` / `0x0006`，**成功时其后再补一帧 NOTI `0x00` / `0x0002` 角色列表** |

**已有实机样本**（2026-08-16，见下）。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。

**请求**：

```text
BodyLength = 2 + 4 + nameLength
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 2 | LE `u16` | 槽位序号 | **Confirmed** | `E-002` |
| 2 | 4 | LE `i32` | 名字字节数 | **Confirmed** | `E-002` |
| 6 | `nameLength` | 原始字节 | 确认名，须与该槽位占用者相同 | **Confirmed** | `E-002` |

### 槽位是 `u16`，旧服读错了（`E-002`）

实机请求：`06 00 | 04 00 00 00 | "00a6"`。

旧服（以及照抄它的本实现）把槽位当 `u8` 读、并从 offset 1 取长度——正好压在槽位的高字节上，
读出 `00 04 00 00` = 1024，超过 30 上限，**每一次删除都被判为 malformed**。
所以旧服这条**从来就是坏的**，只是大概没人真正跑过。

确认名不是冗余：它是唯一能阻止**客户端持有过期名单**时误删当前占用该槽角色的东西。
比较用原始字节，不用解码后的文本。

**响应恒为 3 字节：`u8 状态` + LE `u16` 角色 id。**

| 情况 | body |
|---|---|
| 成功 | `00` + 被删角色 id |
| 确认名不符 | `15` + `0000` |
| 请求不合法 / 槽位为空 | `02` + `0000` |

同族其他四条里 `00` 开头代表拒绝，这里却代表成功——**客户端 handler 证实了这个反转**（`E-003`）：

```asm
0x008C5C78  call ReadU8                ; 状态
0x008C5C80  cmp  byte ptr [ebp+0xF], 0
0x008C5C84  je   0x008C5C9B            ; == 0 → 成功，跳过错误分支
0x008C5C96  call 0x01C32F70            ; != 0 → 错误提示
0x008C5C9B:
0x008C5CA6  call ReadU16               ; ★ 两条分支都会走到这里
            → 从角色列表界面移除该 id
```

**那个 `u16` 是无条件读的。**旧服失败时只回 1 字节裸码，本实现照抄了，
结果就是 2026-08-16 实测到的现象：客户端弹出提示、从空流里把 id 读成 0、
「移除角色 0」什么也没移除，**角色留在界面上**。失败分支现在显式补上 `0000`，
让客户端读到它本来就要读的东西。

成功后补发角色列表，理由与 [0x0005](0x0005.md) 相同。

客户端普查表里 `0x0006` 确有接收 handler（`0x008C5C60` 与 `0x009338E0`）——此前记「无静态注册」
是查错了列。`E-003` 因此把响应格式从「只有旧服行为支撑」升级为**指令级证据**。

## Server and historical evidence

旧服为**软删除**（`delete_flag = 1`），不删行；并在删除前检查 `MercenaryRestrictions.CanDelete`，
角色正在佣兵远征时回 `{0x28}`。本实现保留软删除，**不实现远征限制**——没有佣兵子系统，
这条检查没有可判定的输入。相应地 `0x28` 不会被发出。

软删除同时释放名字：`NameExistsAsync` 只看 `delete_flag = 0` 的行。

## Verification

- Parser/codec vectors：`CharacterLifecyclePayloadCodecTests` 覆盖槽位+名字解析、
  成功体含 id、两种裸码。
- 领域规则：`CharacterLifecycleServiceTests` 覆盖确认名不符不删、空槽位、正常删除。
- 持久化：`SqliteCharacterLifecycleTests` 覆盖软删除后从名单消失、名字被释放、重复删除返回 false。
- Real-client result：2026-08-16 实测暴露两个缺陷并已修复——请求槽位宽度、失败响应缺 id。
  **修复后尚未复测**。
