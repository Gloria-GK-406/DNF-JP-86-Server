# `0x0006` `DELETE_CHARACTER`

<!-- rks:a12:begin -->

> **本区结论得出于 A12 客户端**（SHA-256 `F78F0AEA…`），**A21 上尚未复核**。
> 按迁移规则，本协议在 A21 上重做完成后整区删除；在那之前它是脚手架，不是 A21 的记录。
> 迁移状态见[协议清单](../../catalog.md#a12-内容的退场)。

> 名称取自旧服 `CmdPacketType` 枚举。共享证据与名字字段编码见
> [角色生命周期协议族](../../patterns/character-lifecycle.md)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server（响应同 type 反向） |
| Command | `0x01` |
| Type | `0x0006` |
| Role | Mutation / 有响应 |
| 阶段 | 实现服务端功能 |

**触发时机与响应顺序不记在本页**，它们属于流程层：见 [character-lifecycle](../../patterns/character-lifecycle.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

**已有实机样本**（2026-08-16，见下）。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。

**请求**：

```text
BodyLength = 2 + 4 + nameLength
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 2 | LE `u16` | **角色列表下标**（不是槽位，见下） | **Confirmed** | `E-002` `E-006` |
| 2 | 4 | LE `i32` | 名字字节数 | **Confirmed** | `E-002` |
| 6 | `nameLength` | 原始字节 | 玩家键入的确认名 | **Confirmed** | `E-002` |

### 这个 `u16` 是列表下标，不是槽位（`E-006`）

构包器 `RVA 0x01960B31` 把要发的那个值**直接当下标**用来取确认对象：

```asm
0x01960B31  mov  ecx, [esi+0x138]      ; ← 上线的那个 u16
0x01960B3B  push ecx                   ; ← 同一个值，作为下标
0x01960B51  call 0x01C332A0            ; GetEntryAt(i) → begin + i*0x3A8
            ; 取到条目后与玩家键入的字符串比较，相等才发包
0x01960B82  movzx edx, word [esi+0x138]
0x01960B91  call WriteU16              ; 写上线
```

`0x01C332A0` 按 `[+0x8c, +0x90)` 这个 **936 字节元素的 vector** 的元素个数做边界检查。
所以这个数是**客户端自己角色 vector 的下标**，而服务端角色列表正是这个 vector 的来源。

**它等于列表位置，不等于槽位**（`E-008`）。判据来自**另一条协议**：`0x0004` SELECT_CHARACTER
的 `u16` 索引同一个 vector，在一份 slot 为 `0 / 2 / 3` 的名单上玩家点第二个角色、客户端发的是
`1`——槽位 1 上没有活角色，客户端也无从产生这个数。详见
[0x0004](0x0004.md#那个-u16-是列表位置不是槽位)。既然是同一个 vector 的下标，本条随之确定。

> 位置与槽位**只在名单有洞时才不同**，而在此之前的每一份样本都是从末尾往前删、名单始终连续。
> 这是为什么两者被混为一谈能撑那么久：连续名单对这个区分毫无鉴别力。

### 宽度是 `u16`，旧服读错了（`E-002`）

实机请求：`06 00 | 04 00 00 00 | "00a6"`。

旧服（以及照抄它的本实现）把它当 `u8` 读、并从 offset 1 取长度——正好压在高字节上，
读出 `00 04 00 00` = 1024，超过 30 上限，**每一次删除都被判为 malformed**。
所以旧服这条**从来就是坏的**，只是大概没人真正跑过。

**响应**：首字节属于[全体 CMD 共有的两字节结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)，
不是本协议自己的状态字节。

| 情况 | body |
|---|---|
| 成功 | `01` + `u8` 标志 + LE `u16` **请求里那个下标，原样回显** |
| 确认名不符 | `00 15` |
| 请求不合法 / 找不到该名字 | `00 02` |

`E-003` 给出 handler 的完整形状（`RVA 0x008C5C60`）：

```asm
0x008C5C64  cmp byte ptr [ebp+0x0C], 0  ; 信封的 ok，由接收层填入
0x008C5C68  je  0x008C5D25              ; 失败路径：一个字节都不读
; ---- 成功路径 ----
0x008C5C78  call ReadU8                 ; 标志；非 0 时先调一次 UI 场景 0
0x008C5CA6  call ReadU16                ; 下标 → 从角色列表界面移除该条
0x008C5CC7  push 0x2B0                  ; 「删除成功」提示串
0x008C5D05  push 0x286 → GetWriter/MakeHeader/Finalize   ; 回发 CMD 0x0286
; ---- 失败路径 ----
0x008C5D26  mov bl, byte ptr [ebp+0x10] ; 信封的 reason
            cmp bl, 2 / 0x13 / 0x15 / 0x16 / 0x28 / 0x24 / 0x76 / 0x9C
```

失败路径**不读流**，只按 reason 分支；成功路径的两个字段在信封之后。

### 成功体里那个 `u16` 必须是请求里那个数，原样回显

客户端的移除方法（`0x0203ECC0`）拿这个 `u16` 当**下标**用：

```asm
mov  eax,[ecx+0x7c] / sub eax,[ecx+0x78] / sar eax,2   ; 指针 vector 的元素数
cmp  esi, eax / jae bail                               ; 边界检查
mov  ecx,[ebx+8]  / sub ecx,[ebx+4] / (/0x3A8)         ; 936 字节条目 vector 的元素数
cmp  esi, ecx / jae bail                               ; 再一次边界检查
push esi                                               ; 作为下标取条目
```

请求侧索引的是**同一个下标空间**（`E-006`）。所以服务端不需要知道这个数是位置还是槽位，
把它原样送回即可；**角色 id 与这个下标空间无关**（回 id 会删错位置，见工作日志弯路 3）。

成功路径末尾客户端必发 `0x0286`——**这一帧的有无是判断 handler 是否走完的现成探针**：
handler 在第一句 `cmp` 就返回时它不出现。

### 成功后**不能**补发角色列表

[0x0005](0x0005.md) 成功后必须补发角色列表，本条**不能**——两者的 ack 内容不同：

| | ack 是否含角色信息 | 客户端如何更新界面 |
|---|---|---|
| `0x0005` 创建 | **不含** | 只能靠随后的 NOTI `0x0002` |
| `0x0006` 删除 | **含请求里那个下标** | handler 自己就按该下标把条目从列表移除 |

2026-08-16 实测：删除成功后补发一份完整角色列表，**客户端直接崩溃**。
它刚把那一条从自己的列表里删掉，紧接着又收到全量列表，落在一个刚被改动过的结构上。
上游发完 ack 就停，本实现现在也是。

## Server and historical evidence

旧服为**软删除**（`delete_flag = 1`），不删行；并在删除前检查 `MercenaryRestrictions.CanDelete`，
角色正在佣兵远征时回 `{0x28}`。本实现**不实现远征限制**——没有佣兵子系统，
这条检查没有可判定的输入。相应地 `0x28` 不会被发出。

删除采用软删除、以及软删除如何影响名字占用，属于领域设计，见仓库根 `Docs/`。

- Parser/codec vectors：`CharacterLifecyclePayloadCodecTests` 覆盖槽位+名字解析、
  成功体的信封+标志+id、两种拒绝形状。
- 领域规则：`CharacterLifecycleServiceTests` 覆盖确认名不符不删、空槽位、正常删除。
- 持久化：`SqliteCharacterLifecycleTests` 覆盖软删除后从名单消失、名字被释放、重复删除返回 false。
- Wire：2026-08-16 探针跑通建号→错名删除→正确删除→再删空槽，四步收到
  `01`、`00 15`、`01 00 0A 00`、`00 02`。
- Wire（有空洞的名单）：名单为 `pos0/slot0`、`pos1/slot2`、`pos2/slot3`、`pos3/slot4` 时
  按 `下标=2` 删 `gapA`，服务端删对了角色并回 `01 00 02 00`。这是位置与槽位**首次不相等**
  的用例；旧的按槽位定位在这里会去比对 `00a1` 并判名字不符。
- Real-client result：2026-08-16 实测累计暴露**五个**缺陷——请求宽度、成功后多发角色列表
  （导致客户端崩溃）、成功响应缺信封、失败响应缺信封、成功体回角色 id 而非下标。
  前四个已实机复测通过，**第五个尚未复测**。

## 逆向工作日志

本条的字段边界是对的，栽在三次**读法**上。三条弯路都留着，因为它们指向同一类错误。

### 弯路 1：只挑跳转目标看，把失败路径当成了成功路径的续行

`E-003` 曾被写成「响应为 `u8 状态 + u16 id`，且 `u16` 两条分支都读」。两半都错：那个"状态"
是 `E-004` 的族级信封字节；"两条分支都读 `u16`"来自把失败路径的入口（`0x008C5D25`）
误当成成功路径的续行——失败路径一个字节都不读。
*教训*：地址要连着读完整个函数，不能只挑跳转目标看。

### 弯路 2：把信封字节当成载荷字段，于是"发现"删除反转了同族约定

响应曾被写成 `00 <u16 id>`。接收层把 `00` 读成"失败"，再把 id 的低字节当作 reason，
而那个值不在 handler 的 reason 比较表里，于是**静默返回**——无提示、无移除、无回帧，
与丢包完全一致。当时据此得出的"删除反转了同族约定"是这个错误的产物；删除与同族其余四条
遵守同一套规则。
*教训*：症状与丢包相同的时候，先确认自己有没有把族级信封当成自己的字段。

### 弯路 3：回角色 id 而不是下标

补上信封后删除生效了，但客户端删掉的是**下一个**角色：玩家删第二个、界面上消失的是第三个。
当时回的是 `character_id`（2），而被删角色的列表位置是 1。角色 id 与下标空间毫无关系，
只是在 id 恰好等于位置时看起来是对的。
*教训*：客户端拿这个数当 vector 下标（`0x0203ECC0` 的两道边界检查），所以唯一安全的做法
是把请求里那个数原样送回，服务端不需要知道它是位置还是槽位。

### 死胡同：补一帧 NOTI `0x0006`

试过在 CMD ack 之外补一帧 NOTI `0x0006`（该 type 在 NOTI 表里另有 handler `RVA 0x009338E0`，
读一个裸 `u16`）。**实测无效**，已移除：那个 handler 属于世界/生物移除语义，与角色列表屏无关。
同号异义在这里不是理论问题。
