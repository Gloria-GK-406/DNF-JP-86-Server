## 这是翻牌链的第二帧：把牌背面朝上摆出来

请求体 0 字节（上区已闭合）。构包点 `0x00D0E4D1` 落在客户端**处理 `0x0045` 应答的那个
handler**（`0x00D0E410`）内部，所以本帧只在结算卷轴被应答、且该 handler 走上翻牌那一支时才发出
——那一支的五项条件尚未取尽，见 [`0x0045`](0x0045.md#分支条件尚未取尽)。

### 应答 17 字节，且**不含任何物品**

```text
01        成功标志（CMD 结果的第一个字节，接收路径在派发前读掉）
01 00     u16 = 0x0001
FF FF ×7  u16 = 0xFFFF，共七个
```

即 `01 01 00 FF FF FF FF FF FF FF FF FF FF FF FF FF FF`。

八个 u16 一位一个牌位。**它们各自的含义未查明**：客户端对本帧的处理器只取 u16，调用图里没有
任何 32 位读，所以无论这八个字选的是什么，其中都没有物品 id——**牌此刻是背面朝上的**。

证据两条，都属上游转录一级（见 [evidence.md](../../evidence.md)）：

- 上游 `SendLayoutAsync` 的发送日志抄在 [`0x0045.md`](0x0045.md#应答是两帧本仓两帧都发)：
  `SEND cmd=0x01 type=0x0046 len=32 body=(17B) [01 01 00 FF …]`；
- 上游 `Network/Handlers/Dungeon/CardRewardNotificationSender.cs` 的 `BuildCardLayoutAck`
  写的正是「一个 `0x01`，一个 `0x0001`，七个 `0xFFFF`」。

两者逐字节一致。本页未独立复核那份抓包文件本身。

### 上游不收本帧，本仓收

上游的 `GameProtocolHandler` 只登记了 `d[0x0045]`、`d[0x0047]`、`d[0x0048]`，**没有 `d[0x0046]`**
——它在应答 `0x0045` 时就把版式一并推了出去，客户端随后发来的本帧被丢弃。

本仓登记本 type 的解包器，并把它和结算后的自动 layout timer 归到同一个 presentation
coordinator：结算后 2 秒仍未开牌面时主动推版式；客户端先发本帧时立即提交
`CardLayoutOpen`、回同样的 17 字节并取消旧 layout timer。牌面打开后才注册 4 秒自动免费翻牌。
牌面已经打开时不再重发版式：否则定时器先发送、客户端请求后到会让每人看到两遍开牌
效果。重复请求也不取消已经在等待的自动免费翻牌计时器。

状态：Implemented，计时与组队流程待 A21 实机验证。
