# `0x01BA` `MERCENARY_INFO`

<!-- rks:a12:begin -->

> **本区结论得出于 A12 客户端**（SHA-256 `F78F0AEA…`），**A21 上尚未复核**。
> 按迁移规则，本协议在 A21 上重做完成后整区删除；在那之前它是脚手架，不是 A21 的记录。
> 迁移状态见[协议清单](../../catalog.md#a12-内容的退场)。

> 名称取自旧服 `CmdPacketType` 枚举。**注意同号异义**：`NotiPacketType` 里的 `0x01BA` 是
> `GROWTH_WEAPON_EVENT_INFO`，与本条无关。共享证据见
> [角色生命周期协议族](../../patterns/character-lifecycle.md)。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server（响应同 type 反向） |
| Command | `0x01` |
| Type | `0x01BA` |
| Role | Query / 有响应 |
| 阶段 | 实现服务端功能 |

**触发时机与响应顺序不记在本页**，它们属于流程层：见 [flow-login](../../patterns/flow-login.md)。协议文档只回答「这些字节是什么」；本 type 是否会收到同 type 的 CMD 响应，机器区的注册表结论已经给出。

佣兵远征信息，**与建角色无关**。它出现在这批工作里，只是因为它和建角色卡在同一屏，
且同样得不到应答。与 [0x0286](0x0286.md) 一样，本帧长期只以 seq 空缺的形式存在。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。

**请求** body 长度 **0**。旧服显式要求长度为 0，非 0 即回错误。

**响应** 长度随记录数变化：

```text
BodyLength = 7 + Σ(记录)   // 每条记录 = 12 + 名字字段
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | [CMD 结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)的 `ok`，`1` = 成功 | **Confirmed** | `E-005` |
| 1 | 1 | `u8` | 管理等级 | High | `E-001` |
| 2 | 4 | LE `u32` | 管理点数 | High | `E-001` |
| 6 | 1 | `u8` | 记录数 `N` | High | `E-001` |
| 7 | … | `N ×` 记录 | 见下 | High | `E-001` |

单条记录：`i32 characterId`、名字字段（`i32` 长度 + 字节）、`u8 state`、
`i32 remainingSeconds`、`u8 areaIndex`、`u8 periodIndex`、`u8 avatarBonusTier`。

失败为 `00 01`：信封的 `ok = 0` 加 reason `0x01`，此时后面的字段一个都不发。

**本服务端恒发空名单** `01 00 00000000 00`（7 字节）：没有佣兵子系统，而「你没有派出佣兵」
是真话，也是一个新账号在正常服务端上会得到的答案。回错误则是在声称请求失败，那不是事实。

## Samples

请求已实测（服务端日志，2026-08-16）：`selector=0x01 type=0x01BA seq=6 body(0B)`。
响应无实机样本；本地回环实测 `body=01000000000000`。

## Client reversing evidence

| Evidence | Kind | Location | Supports |
|---|---|---|---|
| `E-001` | static | 旧服 `MercenaryExpeditionBodyBuilder.BuildInfoSuccess`（`d51e74b`） | 响应布局 |
| `E-002` | static | 旧服 `GameProtocolHandler.cs:788` | 注册为入站 CMD handler |
| `E-003` | static | client handler `0x008C6240`，注册于 `0x008D055B` | 客户端等响应，经一层后读 `ReadU8` |
| `E-004` | dynamic | 服务端未识别帧日志，2026-08-16 | 请求存在、body 为空、seq 6 |
| `E-005` | static | 接收函数 `RVA 0x00D89B16`（CMD 分支） | offset 0 是族级信封，成功／失败两种形状由它决定 |

此前把 `E-003` 的首读 `ReadU8` 当作"客户端读状态字节"的佐证。**对不上**：信封在分发之前
就被接收层读掉了，handler 的第一次 `ReadU8` 读到的是 offset 1 的管理等级。
wire 布局本身不受影响（`01` 仍在最前），但这条佐证关系作废——offset 0 的证据现在是 `E-005`，
而且比原来更强。

## 实测字段表（运行时读取跟踪）

客户端**实际**读取这条协议的方式，由运行时读取跟踪测得（做法见 [game-receive](../../patterns/game-receive.md#四个原语是唯一出口)）。

**本节优先于机器区的 Body 表。** 机器区那张表由静态走图产出，在 S→C 上普遍止步于打包区，给出的是下界；载荷多形时它只描述其中一形，却读起来像描述了整条协议。本节是实测，但**只给边界，不给含义**——`含义` 一列留给人填，偏移已确证之后用实机改值做差分是最便宜的填法。

偏移 0 那次读取属于**接收层**而不是 handler：每条 CMD body 都以两字节结果信封开头，由分发前的接收函数读掉（见 [结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)）。

### 形状 body 7 字节（2 帧共享）

|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | `0x00D89B25` | 1 | — |
| 1 | 1 | `u8` | `0x00B50019` | 0 | — |

## A21

**2026-08-25。** 上面的机器区由 **A12** 客户端（SHA-256 `F78F0AEA…`）的静态普查生成。
本节记录 **A21** 客户端（SHA-256 `1F8244D3…`）上不同的部分。判据是本仓入场批次与
A21 参照会话的逐帧对账，归档于
[a21-entry-batch-diff-20260825](../../patterns/data/traces/a21-entry-batch-diff-20260825.md)。

**参照在入场批次里主动发一帧，不等客户端问。** 位置在 town-ready（`0x0002` 子类型 6）
与 `0x0035 CERA` 之间，body 七字节 `01 00 00 00 00 00 00`——族信封的接受字节，加
manageLevel、managePoint 与为零的记录数。

客户端进城后**还会**自己问一次，参照再答一次，body 相同。所以这条协议在入场窗口里出现两次，
只实现「答请求」的那一次会漏掉前一帧。
