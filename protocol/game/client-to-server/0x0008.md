# `0x0008` `GET_USERINFO`

> 名称说明：`GET_USERINFO` 来自**旧服实现的反推命名**（见 `Docs/NetworkingFrameProtocol.md`
> 的 Game CMD `0x0008` 段），不是从客户端二进制里取到的枚举名。旧服同时把 body 反推为
> `{ u16 targetUserId, u8 mode }`——本记录用客户端指令**独立确认了这个布局**，见下文。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server |
| Command | `0x01` |
| Type | `0x0008` |
| Role | Query（body 内含 `mode` 判别字段，一个 wire type 承载两种语义不同的查询） |
| Trigger | `mode=2`：登录握手内，紧接 `0x01DD` 之后一次性发送；`mode=3`：未观察到 |
| Expected response | `mode=2` → S→C `0x0002` 角色列表（Confirmed，抓包内紧随其后）；`mode=3` → 未知 |
| 阶段 | 双向验证结束 |

本 type 是**目前已确认的第一条真正的 Query**：`0x00AB`/`0x01DD`/`0x00C2` 都是 fire-and-forget
上报，本条则有确定的响应帧。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。Body **固定 3 字节**，
`2 + 1 = 3`，与实测长度精确闭合：

```c
struct Body0008 {
    u16 target;   // 0xFFFF = 无特定目标（哨兵）
    u8  mode;     // 2 = 账号级查询（角色列表）；3 = 针对 target 的查询
};
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 2 | LE `u16` | 查询目标 id。`mode=2` 的两个构包点都写入立即数 `0xFFFF`；`mode=3` 的三个构包点都写入运行时值 | Confirmed | `E-002` |
| 2 | 1 | `u8` | 模式判别。客户端 `.text` 内**只存在 `2` 和 `3`** 两个立即数 | Confirmed | `E-002` |

### `0xFFFF` 是哨兵而非合法 id（Confirmed，`E-002`）

构包点 `0x01ABC0A1` 在写入之前对目标值设了双向门：

```asm
test eax, eax
js   skip            ; 负值 → 不发送
cmp  eax, 0xffff
jge  skip            ; >= 0xFFFF → 不发送
```

即合法 target 被限制在 `[0, 0xFFFE]`，`0xFFFF` 被显式排除。因此 `mode=2` 写的 `0xFFFF`
是"无目标"哨兵，`mode=2` 下服务端**不应**用它做任何定位——与旧服"该模式下 targetUserId
不参与账号定位"的反推一致，现在有了客户端侧证据。

### 全部构包点（`E-002`）

`MakeHeader` 全量普查（见 [game-frame](../../patterns/game-frame.md) 的"构包点普查"）在
`.text` 内找到本 type 的 **5 个**构包点，每个都是 `WriteU16 + WriteU8` 后立即 `Finalize`：

| 构包点 | offset 0 | offset 2 | 备注 |
|---|---|---|---|
| `0x008C85B9` | `0xFFFF` 立即数 | `2` 立即数 | 与下一行同属一个函数的另一分支，前置条件 `0xE30060() == 1` |
| `0x008C86A6` | `0xFFFF` 立即数 | `2` 立即数 | **抓包中实测的就是这一条** |
| `0x00A86CA2` | `esi` | `3` 立即数 | |
| `0x01ABC0A1` | `[esi+0x108]`（`movzx`） | `3` 立即数 | 带上述 `[0, 0xFFFE]` 范围门 |
| `0x01B17067` | `ebx` | `3` 立即数 | |

**修正旧服反推**：旧服文档称"`mode=0/1/3` 属于查看其他在线角色的流程"。本客户端 `.text`
内不存在写 `0` 或 `1` 的构包点，只有 `2`/`3`。`mode=0/1` 或已在本版本移除，或只存在于
`.text` 之外那个被混淆的第二代码区（见 game-frame 的普查盲区小节）。

### 构包点反汇编（`0x008C85B9`，指令级）

```asm
0x008C85A2  call   0xE30060                 ; 前置判定
0x008C85A7  cmp    eax, 1
0x008C85AA  jne    0x8C8634                 ; 不等于 1 → 不发送
0x008C85B0  push   8                        ; type = 0x0008
0x008C85B2  call   0x1C8F5B0                ; GetWriter
0x008C85B7  mov    ecx, eax
0x008C85B9  call   0x1C90460                ; MakeHeader
0x008C85BE  push   0xFFFF
0x008C85C3  call   0x1C8F5B0                ; GetWriter
0x008C85C8  mov    ecx, eax
0x008C85CA  call   0x1C90580                ; WriteU16(0xFFFF)   body=2
0x008C85CF  push   2
0x008C85D1  call   0x1C8F5B0                ; GetWriter
0x008C85D6  mov    ecx, eax
0x008C85D8  call   0x1C90550                ; WriteU8(2)         body=3
0x008C85DD  call   0x1C8FDD0                ; Finalize
```

五个构包点的指令形状完全相同，只有两个被写入值不同——这就是"一个 type 两种语义"在
客户端侧的全部实现，没有其他分支、没有可变长度尾部。

## Server and historical evidence

- 旧服反推布局 `{ u16 targetUserId, u8 mode }`，与 `E-002` 完全一致；旧服对 mode 值域的
  描述（含 `0`/`1`）与 `E-002` 不一致，已在上文修正。
- 当前实现只处理 `mode=2`，映射为 `GetAccountCharacterRosterRequest`；其余 mode 返回
  `null`，由 `GameNetworkPlugin` 静默忽略。
- `mode=2` 的响应 S→C `0x0002` 的 body 编码仍由旧服移植、**未经客户端侧验证**，
  单独记录在 `0x0002`（S→C）文档中，本条不重复。

### 已修正的实现缺陷

原 `GetUserInfoPayloadCodec` 用 `body.Length < 3` 判定后就把 offset 0 的 u16 用
`_ =` 丢弃。在 `mode=2` 下无害（该字段是哨兵），但：

1. 它同时接受长度 **> 3** 的 body，而客户端已确认恒为 3；超长 body 只可能来自
   非本客户端或解帧错位，按 3 字节布局解释是错的。
2. 丢弃 offset 0 使实现无法区分"哨兵 `0xFFFF`"与"某个真实 id"，一旦将来接入
   `mode=3` 就必须重写解码入口。

现改为三点：长度必须**恰好等于 3**；`0xFFFF` 哨兵与 `mode=2` 写成命名常量；`mode=2` 且
target ≠ `0xFFFF` 也判为非本消息（两个 `mode=2` 构包点都写立即数 `0xFFFF`，本客户端不可能
产生别的组合）。offset 0 仍然不向业务层透传——它在 `mode=2` 下没有语义——但现在是被
**读取并校验**后丢弃，而不是无解释地跳过。

## Implementation mapping

| Layer | Type/path | Responsibility |
|---|---|---|
| Networking | `Framing/GetUserInfoPayloadCodec.cs` | 长度校验、mode 判别、哨兵常量 |
| Networking | `Framing/GameProtocol.cs`（`GetUserInfoType`） | 线路 type 常量 |
| Data | `Networking/NetworkMessages.cs`（`GetAccountCharacterRosterRequest`） | `mode=2` 的强类型消息 |
| Application | `Game/GetAccountCharacterRosterHandler`（既有） | 取角色列表并回发 S→C `0x0002` |

`mode` 不向业务层透传：它是线路层的协议判别字段，不同 mode 应生成不同的强类型消息。

## Verification

- Parser/codec vectors：`FFFF02` → `GetAccountCharacterRosterRequest`
- Boundary cases：长度 2 / 4 → `null`；`mode` ∈ {0,1,3,4,255} → `null`
- 条件分支/重复项：无可变长度部分
- Response count/order：`mode=2` 恰好一个 S→C `0x0002`（`E-004`）
- Real-client result：四次会话稳定进入角色列表界面；第四次是在 codec 收紧**之后**跑的，
  确认长度恒等与哨兵校验没有引入回归（`E-005`）

## 逆向工作日志

### 1. 起点：一条被"顺手"打穿的协议

本条不是计划中的目标。计划是先做 S→C `0x0002`，`0x0008` 只是它的配对请求。
但在为 `0x0002` 做准备时建的**构包点普查**工具直接把 `0x0008` 的全部构包点列了出来，
5 个点的指令形状一致、body 三字节闭合，语义当场就完整了，于是先收掉。

结论：**先做全量普查再挑协议**比"挑一条协议再去找它的代码"效率高得多。

### 2. 调用栈定位在这里失效了一次

抓包的 stack[1] = `0x008C86CF` 落在构包器内部（`call Finalize` 的返回地址），
按既有流程应该用 stack[2] = `0x00D8566E` 反求外层 `call` 的目标来得到构包器入口。
但那条指令是 `call edx`——**虚分发**，直接方法在这里不可用：

```text
return address 0x00D8566E
  call site  0x00D8566C  call edx
  callee     indirect -- resolve via vtable/import
```

padding 扫描回退方法给出的入口 `0x008C867D` 反汇编成垃圾（`cmp edi, 0x3AE8C88B`），
是又一个假阳性。这次没有去追 vtable：`0x0008` 的 body 只有 3 字节，
从 stack[1] 往前二十几条指令就能看到完整的 `MakeHeader → WriteU16 → WriteU8 → Finalize`
序列，函数入口对结论没有贡献。

**教训**：入口地址是手段不是目的。当 body 很小、写入序列在同一基本块内时，
直接从返回地址往回读比死磕入口更快。

### 3. 普查揭示"一个 type 多个构包点"是常态

`0x0008` 有 5 个构包点，其中 2 个写 mode 2、3 个写 mode 3。如果只看抓到的那一个，
就会把 offset 0 记成"常量 `0xFFFF`"、把 offset 2 记成"常量 `2`"——一个看起来
完全闭合、实际上错的结论。

全客户端 1082 个可定 type 的构包点对应 604 个 type，即**平均每个 type 有 1.79 个构包点**。
所以从今以后：确定一条 C→S 协议的布局，必须看它**全部**构包点，不能只看抓到的那一个。
这条已提升到 [game-frame](../../patterns/game-frame.md)。

### 3b. 普查工具本身返工了三次

第一版用"调用点前 32 字节内最后一个 push"取 type，看着能跑，实际在 `0x00E40D75` 读出了
根本不存在的 type `0x2AFF`（真值在 `ebx` 里，那个 `push 0x2AFF` 属于另一条代码路径）。
改成"必须紧贴 `call GetWriter`"后精度对了但漏掉 252 个点。改成反向逐指令解码后又有
168 个点失同步。最终用"前向对齐投票"才做到 1082/1099。三次失败的判据都写进了
[game-frame](../../patterns/game-frame.md)。

值得记的是**发现第一版错了的方式**：拿已确认的三条协议做交叉校验。`0x00AB` 的构包点
必须落在已知序列化器 `0x1CD1120` 内、`0x00C2` 落在 `0x01CD6260` 内、`0x01DD` 落在
`0x00C375B0` 内，`0x0117` 必须出现。任一条不满足就说明工具错了，而不是发现了新东西。

### 4. 未走的路

- 没有去解 `0x00A86CA2` / `0x01B17067` 的 `esi`/`ebx` 来源。三个 mode=3 构包点里
  `0x01ABC0A1` 的 `movzx edx, word ptr [esi+0x108]` 已经给出了字段宽度和范围门这两个
  关键事实，另外两个只会重复同一结论，而它们的对象类型识别需要 RTTI 解析，代价不成比例。
- 没有实机触发 `mode=3`。它要求"查看其他在线角色"，当前账号连一个角色都还没有。
