## A21 服务端结算边界

**2026-09-14，代码/PVF 推导，尚未提升为 ClientVerified。** 请求中的
`rewardSelection` 与 `completionCount` 进入事务命令，不再只记录日志：

- 没有 `[reward selection int data]` 时只接受 `rewardSelection=0xFFFF`；存在可选奖励时，
  索引作用于按角色当前持久化 job/growType 过滤后的候选，并且只发其中一项。
- `[reward int data]` 是固定奖励表；其 `[job] job growType count` 条件必须保留，不能把
  后续整数重新配成 item/count。真实 PVF 任务 1776 对 job=0/growType=0 的结果是
  `101010437 x1`，不是表内所有职业装备。
- itemId=0 的声明是金币语义；金币通过角色领域入口结算，成功响应再以 ItemId=0 投影
  实际增加量，不能当普通物品，也不能占用 completionCount 或末尾哨兵字段。
- 奖励计划在写任务日志前完成校验；任务、物品、金币和经验处于同一事务。可预期的后置
  发放失败以专用拒绝异常越过命令边界触发回滚，再由 Handler 映射为拒绝响应。

**2026-09-18 补充：** 对持有物品目标，当前服务端在事务内再次根据背包计算剩余需求，
然后才允许任务日志完成和发奖。若旧 trigger 为零但物品已经丢掉，回复拒绝并补发
[`NOTI 0x023F`](../server-to-client/NOTI-0x023F.md) 校正任务进度。
这是本仓规则与回归测试；“丢弃 → 交付被拒 → 任务 UI 回退”的 A21 成对帧及画面
仍未归档，不能把拒绝码或通知次序升级为实机确认。

## A21 双构包路径复核（2026-09-18）

机器区的两个构包点虽然均为 10 字节，**末字段值却不一致**：
`RVA 0x00C7ED10` 路径写 `0x0022, arg1, arg2, arg3, 0xFFFF`；
`RVA 0x00B4D307` 路径写 `0x0022, [ebx], 0xFFFF, 1, u16(edi)`，而该路径
先检验 `edi > 0` 才发包。故 offset 8 不是所有 A21 路径都恒写 `0xFFFF`。
指令与边界见[`A21 静态复核`](../../patterns/data/probes/a21-quest-repair-durability-readers-20260918.md)。

当前服务端 decoder 和上游都把 offset 8 强制当 `0xFFFF` 哨兵，因此会拒绝
后一条路径产生的非 `0xFFFF` 值；尚不知它对应何种任务/交付方式，也没有实帧证明本次场景触发。
本页只记录这个协议差异，不据此放宽校验或猜测奖励计算。
