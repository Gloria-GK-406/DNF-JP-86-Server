## 响应形状：客户端注册了 CMD handler，但成功路径不用它

客户端为本 type 注册了 CMD 接收 handler（`RVA 0x008CFF30`）。**注册不等于必须回**——
参照实现在成功路径上只推 NOTI，CMD 仅用于错误分支；实机（2026-08-17）证明只发 NOTI
客户端即继续。

### 客户端侧给不出响应布局

按读取原语表走两个 handler，各自只读到 **1 个 `u8`** 就进入间接跳转与打包区：

| type | handler | 读出的字段 | 之后 |
|---|---|---|---|
| `0x000F` | `0x008CFF30` | `u8` | 大量间接调用，opaque `0x04D41803` / `0x04E6558B` |
| `0x0010` | `0x008C56F0` | `u8`（深度 1，在 `0x008C4350` 内） | `jmp dword ptr [ecx*4 + 0xCC557C]` 跳转表 |

所以客户端能提供的只有"信封之后至少 1 字节"这一个约束，不足以构造响应。这个下界与
"成功路径只推 NOTI"并不矛盾：错误分支要回的那一帧同样要过信封。

### 上游给出的推送集合

`DungeonEntryHandler.HandleEnterSelectDungeon` 不回 CMD `0x000F`，而是推 `0x0017`、
`0x0002` subtype 1、`0x0003`、`0x001A`、`0x001B` 与一条经验进度；CMD `0x01` 只在
"佣兵内容被封禁"的错误分支上回。上游只用来给形状与字段名，判据以客户端为准——
我们实发的四条见下节。

> 用它的缺席去质疑本 handler 是否执行过，会得出相反的结论——那是仪器假象。

## 2026-09-14：作为下一次 `0x0010` 的一次性入口意图

当前 A21 证据表明，普通选图和定向进入最后都会提交同一条
[`0x0010 SELECT_DUNGEON`](0x0010.md)，不能用 opcode 区分普通/剧情：

- 普通交互选图实帧：`0x000F = 00 00 00 00`；
- 已确认的定向教学构包：`0x000F` 偏移 0 写目标 dungeon id，随后 `0x0010` 写同一 id；
- A21 静态路径中，普通队伍分支（RVA `0x00D38860`）写 `0`，通用定向构包函数
  （RVA `0x003434E0`）写传入 dungeon id。

服务端因此将偏移 0 的 `u16` 保存为当前角色精确连接代次的一次性选择上下文：`0` 是交互式普通意图，
非零是定向目标。`0x0010` 必须消费该上下文；缺失、重复消费或目标 id 不一致返回
`InvalidSelectionState`。任务状态只能验证定向入口是否有合格 `[quest connection]`，不能把
普通入口升级为剧情入口。

任务 1776 的实际剧情点击是否也产生 `0x000F=dungeonId` 仍待本次 A21 双路径实机确认；在
确认前不增加“持有任务即剧情”的兜底。
