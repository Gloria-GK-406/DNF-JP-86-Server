# `0x02A8` `LOAD_EXTEND_CHARACS`

> 名称取自上游服务端 `CmdPacketType` 枚举
> （`D:\project\86JP` → `Server/DfoServer/Network/Core/PacketTypes.cs`）。
>
> **2026-08-16 更正**：本记录此前写"尚无可用名称：没有旧服枚举证据"，原因是当时上游源码树
> 不在工作区。官方名与本帧的实测时机吻合——它紧跟角色列表（`0x0002`）之后发出，
> 而 `LOAD_EXTEND_CHARACS` 正是"载入扩展角色栏"。
>
> **body 那个 u16 的语义仍未定**：名称说明了这条协议做什么，没有说明该字段是槽位数、
> 页号还是别的什么。
>
> **注意同号异义**：`NotiPacketType` 里的 `0x02A8` 是 `REJOIN_DUNGEON`，与本协议无关。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server |
| Command | `0x01` |
| Type | `0x02A8` |
| Role | **屏障 / 有响应**（选角屏就绪闸门；响应 body 客户端不读） |
| Trigger | 收到 S→C `0x0002`（角色列表）之后立即发出，seq 恒为 5 |
| Expected response | **CMD `0x01`/`0x02A8`，body `00 00`**（`E-004`–`E-006`，2026-08-16 修正） |
| 阶段 | 双向验证结束 |

`seq` 从 3（`0x0008`）跳到 5：中间的 seq 4 被一次抓不到的发送消耗了，
原因见 [game-frame 的抓包覆盖边界](../../patterns/game-frame.md#抓包的覆盖边界)。

**seq 4 已于 2026-08-16 查明**：是 CMD [`0x0286`](0x0286.md)（空 body）。它不走加密路径，
客户端抓包看不见，由服务端新增的「未识别入站帧」日志捕获。本条记录的时序不受影响——
`0x02A8` 仍紧跟在角色列表之后——只是中间那一帧现在有名字了。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。body 固定 **2 字节**：

```c
struct Body02A8 {
    u16 value;   // 实测 0xFFFF
};
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 2 | LE `u16` | 单个 u16，三个构包点全部写运行时值。实测 `0xFFFF`；**必须 ≥ `0x24`**，否则不发 | 位置与宽度 Confirmed；语义仍未定 | `E-002` `E-007` |

### 全部构包点（`E-002`）

`MakeHeader` 普查在 `.text` 内找到 **3 个**构包点，每个都只调用一次 `WriteU16`：

| 构包点 | offset 0 |
|---|---|
| `0x01C3331C` | `esi` |
| `0x01C349BB` | `esi` |
| `0x01C34A6A` | `ebx` |

三个点都**没有**其他写入原语调用——把每个构包点到下一个 `Finalize` 之间的字节全扫过一遍，
只命中 `MakeHeader` 与 `WriteU16`，没有 `WriteU8`/`WriteU32`/`WriteBytes`。因此
`2 = 2` 长度闭合，且不存在"某条分支多写几个字节"的可能。

`0xFFFF` 与 [`0x0008`](0x0008.md) 的"无目标"哨兵取值相同，但**没有证据**说明二者同义：
`0x0008` 的哨兵有客户端侧的范围门（`[0, 0xFFFE]`）作证，本协议没有。故服务端按原始 u16
建模，只在日志里标注"与已知哨兵取值相同"。

## Server and historical evidence

上游 `GameProtocolHandler.cs:942-943` 注册了本 type，回 `CMD 0x01/0x02A8` body `00 00`，
且**完全不看请求 body**——是个无条件常量应答。

### 语义：选角屏的就绪闸门（`E-007`）

**这是一次请求／响应屏障，不是上报。**客户端在选角屏上维护一个就绪标志
`<选角屏对象> + 0x70`，本协议的往返就是这个标志的生命周期：

```asm
; 三个构包点全部是同一形状（此处为 0x01C3331C）
0x01C33307  cmp  esi, 0x24                 ; 门槛：u16 < 0x24 就不发
0x01C3330A  jb   0x01C33334
0x01C3330C  push 0x2A8
0x01C33311  mov  byte ptr [ecx+0x70], 0    ; ← 发之前把标志清零
0x01C33315  call GetWriter
0x01C3331C  call MakeHeader                ;   type = 0x02A8
0x01C33329  call WriteU16(esi)             ;   body 的那个 u16
0x01C3332F  jmp  Finalize

; 回包 handler 尾调用到的 0x01C3F4F0
0x01C3F52C  mov  byte ptr [esi+0x70], 1    ; ← 回包到达把标志置 1
```

三个构包点的清零指令分别在 `0x01C33311` / `0x01C349B0` / `0x01C34A5F`，
**都紧贴各自的 `MakeHeader` 之前 11 字节**；全区间内把 `+0x70` 置 **1** 的只有回包路径一处。

而 `+0x70` 有 **18 处**读取点，形状统一为：

```asm
0x01C3390C  cmp byte ptr [esi+0x70], 0
0x01C33910  je  <跳过>                      ; 标志为 0 → 什么都不做
```

所以**没有回包 → 标志永远是 0 → 选角屏上十八处交互全部静默跳过**，
表现就是「按钮点了没反应」。2026-08-16 的 A/B 直接复现了这一点：关掉回包，创建角色打不开；
加回去，立刻能打开。

顺带得到一个此前未知的发送前置条件：**u16 必须 ≥ `0x24`**，否则整个构包器直接 `ret` 不发。
实测值 `0xFFFF` 满足。这也说明该 u16 不是纯哨兵——它参与判定。

### 响应 body 的语义：那两个字节就是信封，而且这条的判定是反的（`E-006`）

客户端的接收 handler `0x008C6C60` 只有 8 条指令，**一次读取原语都没调**：

```asm
0x008C6C60  push ebp; mov ebp, esp
            cmp  byte ptr [ebp+0xC], 0     ; ← 信封的 ok
            jne  0x008C6C7D                ; 非零 → 直接返回，什么也不做
            call 0x008BC420                ; 取对象
            call 0x000E1690                ; 取对象
            jmp  0x01C3F4F0                ; 尾调用，置就绪标志
0x008C6C7D  ret
```

从它出发做深度 8 的可达性扫描，走了 1052 个函数**没命中任何读取原语**（29 个调用进打包区，
故记 High 而非 Confirmed；同批正对照 NOTI `0x00C5` 正常命中 `ReadDStringW`）。

它确实不读流，但 `00 00` 并非"没有语义的两个字节"——2026-08-16 查明它是
[全体 CMD 共有的两字节结果信封](../../patterns/game-receive.md#cmd-body-的两字节结果信封每一条-cmd-都有)：
`ok = 0`（失败）、`reason = 0`（未用）。信封由接收层读掉，所以 handler 自然扫不到读取原语。

**本条是全族唯一判定反向的一条**：`jne` 而不是 `je`，干活的是失败分支。发 `01`（成功）
会让 handler 立刻返回、就绪标志永远不置位——和不回帧的效果一样。上游的 `00 00` 因此不是
可照抄的魔数，而是唯一正确的取值；本实现现在按信封显式表达（`GameCmdEnvelope.Refuse(0x00)`），
理由写在编码器上，避免以后有人"顺手统一成 `01`"。

### 本页此前写着「无响应即可兼容」，那是错的

依据是「前四次会话服务端未处理本帧而客户端行为正常」——但**那四次会话都由本服务端提供，
而它从不回包**。观察自己的沉默、再断言客户端想要沉默，是循环论证。它能活这么久，
是因为从来没有任何测试拿一台行为不同的服务端验证过。

2026-08-16 把同一段请求序列分别打到本服务端和上游、逐步 diff 响应，差异当场显形。
补上回包后客户端第一次打开了创建角色界面；随后单独关掉本回包再登一次——**打不开**（`E-008`），
因果就此隔离到这一帧，与同轮的 `0x0286` 去重无关。

## Verification

- Parser/codec vectors：`FFFF` → `value = 0xFFFF`；`3412` → `0x1234`（非哨兵值也接受）

- 条件分支/重复项：无
- Response count/order：一帧 `CMD 0x01/0x02A8`，body `00 00`

## 逆向工作日志

### 0. 「无响应」这个结论是循环论证出来的

见上方 Server and historical evidence。教训比这条协议本身重要：**一条关于对端期望的断言，
不能用「我方不做某事时对端没抱怨」来证明。**那只证明了对端容忍，没证明对端不需要。
要证伪它，必须存在一个行为不同的对照实现——本例中是把同一段请求序列同时打到两台服务端并 diff。

### 1. 「三个点都只写一个 u16」是扫出来的，不是读出来的

前两个构包点（`0x01C3331C` / `0x01C349BB`）的线性反汇编在 200 条指令内都没走到
`Finalize`——它们的收尾在分支之后，线性读甚至会直接走进下一个构包器（读 `0x01C349BB` 时
走进了 `0x01C34A6A`）。这种情况下"我没看到别的写入"是不可靠的。

改用**字节扫描**：把构包点到下一个 `Finalize` 之间的全部字节按 `E8 rel32` 扫一遍，
列出所有命中写入原语的调用。两个点都只有 `MakeHeader` + `WriteU16`，
这才把"长度恒 2"从"看起来是"变成"确实是"。

**教训**：线性反汇编走不到 `Finalize` 时，不要据此断言写入序列完整。改用范围内的
调用点扫描——它不依赖指令流的可达性。

### 2. 相同的字节不等于相同的含义

`0xFFFF` 在 `0x0008` 里已确认是"无目标"哨兵，很容易顺手把本协议的 `0xFFFF` 也这么记。
但 `0x0008` 的结论有客户端范围门（`js` / `cmp 0xFFFF; jge`）作证，本协议一条这样的证据都没有。
所以记录里只写"取值相同"，服务端也不据此做校验——只在日志里标注。
