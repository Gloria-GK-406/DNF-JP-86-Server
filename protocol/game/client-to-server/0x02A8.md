# `0x02A8`（未命名）

> 尚无可用名称：没有旧服枚举证据，body 只有一个 u16 且语义未定，不给描述性命名。

## Identity and behavior

| Property | Value |
|---|---|
| Endpoint | Game |
| Direction | Client → Server |
| Command | `0x01` |
| Type | `0x02A8` |
| Role | Query / 有响应（携带单个 u16；响应 body 客户端不读，见下） |
| Trigger | 收到 S→C `0x0002`（角色列表）之后立即发出，seq 恒为 5 |
| Expected response | **CMD `0x01`/`0x02A8`，body `00 00`**（`E-004`–`E-006`，2026-08-16 修正） |
| 阶段 | 双向验证结束 |

`seq` 从 3（`0x0008`）跳到 5：中间的 seq 4 被一次抓不到的发送消耗了，
原因见 [game-frame 的抓包覆盖边界](../../patterns/game-frame.md#抓包的覆盖边界)。

**seq 4 已于 2026-08-16 查明**：是 CMD [`0x0286`](0x0286.md)（空 body）。它不走加密路径，
客户端抓包看不见，由服务端新增的「未识别入站帧」日志捕获。本条记录的时序不受影响——
`0x02A8` 仍紧跟在角色列表之后——只是中间那一帧现在有名字了。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。body 固定 **2 字节**：

```c
struct Body02A8 {
    u16 value;   // 实测 0xFFFF
};
```

| Offset | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 2 | LE `u16` | 单个 u16，三个构包点全部写运行时值。实测 `0xFFFF` | 位置与宽度 Confirmed；语义未定 | `E-002` |

### 全部构包点（`E-002`）

`MakeHeader` 普查在 `.text` 内找到 **3 个**构包点，每个都只调用一次 `WriteU16`：

| 构包点 | offset 0 |
|---|---|
| `0x01C3331C` | `esi` |
| `0x01C349BB` | `esi` |
| `0x01C34A6A` | `ebx` |

三个点都**没有**其他写入原语调用——把每个构包点到下一个 `Finalize` 之间的字节全扫过一遍，
只命中 `MakeHeader` 与 `WriteU16`，没有 `WriteU8`/`WriteU32`/`WriteBytes`。因此
`2 = 2` 长度闭合，且不存在"某条分支多写几个字节"的可能。

`0xFFFF` 与 [`0x0008`](0x0008.md) 的"无目标"哨兵取值相同，但**没有证据**说明二者同义：
`0x0008` 的哨兵有客户端侧的范围门（`[0, 0xFFFE]`）作证，本协议没有。故服务端按原始 u16
建模，只在日志里标注"与已知哨兵取值相同"。

## Server and historical evidence

上游 `GameProtocolHandler.cs:942-943` 注册了本 type，回 `CMD 0x01/0x02A8` body `00 00`，
且**完全不看请求 body**——是个无条件常量应答。

### 响应 body 的语义：客户端不读它（`E-006`）

客户端的接收 handler `0x008C6C60` 只有 8 条指令，**一次读取原语都没调**：

```asm
0x008C6C60  push ebp; mov ebp, esp
            cmp  byte ptr [ebp+0xC], 0     ; 检查一个入参标志
            jne  0x008C6C7D                ; 非零 → 直接返回
            call 0x008BC420                ; 取对象
            call 0x000E1690                ; 取对象
            jmp  0x01C3F4F0                ; 尾调用，干活
0x008C6C7D  ret
```

从它出发做深度 8 的可达性扫描，走了 1052 个函数**没命中任何读取原语**（29 个调用进打包区，
故记 High 而非 Confirmed；同批正对照 NOTI `0x00C5` 正常命中 `ReadDStringW`）。

所以那两个字节**没有可解释的语义**——`00 00` 不是状态码也不是计数，客户端根本不看。
**有意义的是"这一帧到了"，不是它装了什么。**换句话说这是个纯信号／闸门，
本服务端照抄上游的 `00 00` 只是为了不发明未观察过的字节。

### 本页此前写着「无响应即可兼容」，那是错的

依据是「前四次会话服务端未处理本帧而客户端行为正常」——但**那四次会话都由本服务端提供，
而它从不回包**。观察自己的沉默、再断言客户端想要沉默，是循环论证。它能活这么久，
是因为从来没有任何测试拿一台行为不同的服务端验证过。

2026-08-16 把同一段请求序列分别打到本服务端和上游、逐步 diff 响应，差异当场显形。
补上回包后客户端第一次打开了创建角色界面——但**同一轮还去掉了重复的 `0x0286` 回包，
两者尚未隔离**，见下方未解问题。

## Verification

- Parser/codec vectors：`FFFF` → `value = 0xFFFF`；`3412` → `0x1234`（非哨兵值也接受）
- Boundary cases：长度 0 / 1 / 3 → 抛 `InvalidDataException`
- 条件分支/重复项：无
- Response count/order：一帧 `CMD 0x01/0x02A8`，body `00 00`
- Real-client result：2026-08-15 第五次实机会话通过——`RosterFollowUpHandler` 输出
  `Roster follow-up Game:01-00-00-00 account=1 onlineUser=…: value=0xFFFF (sentinel)`，
  客户端随后正常进入角色列表并完成退出

## 逆向工作日志

### 0. 「无响应」这个结论是循环论证出来的

见上方 Server and historical evidence。教训比这条协议本身重要：**一条关于对端期望的断言，
不能用「我方不做某事时对端没抱怨」来证明。**那只证明了对端容忍，没证明对端不需要。
要证伪它，必须存在一个行为不同的对照实现——本例中是把同一段请求序列同时打到两台服务端并 diff。

### 1. 「三个点都只写一个 u16」是扫出来的，不是读出来的

前两个构包点（`0x01C3331C` / `0x01C349BB`）的线性反汇编在 200 条指令内都没走到
`Finalize`——它们的收尾在分支之后，线性读甚至会直接走进下一个构包器（读 `0x01C349BB` 时
走进了 `0x01C34A6A`）。这种情况下"我没看到别的写入"是不可靠的。

改用**字节扫描**：把构包点到下一个 `Finalize` 之间的全部字节按 `E8 rel32` 扫一遍，
列出所有命中写入原语的调用。两个点都只有 `MakeHeader` + `WriteU16`，
这才把"长度恒 2"从"看起来是"变成"确实是"。

**教训**：线性反汇编走不到 `Finalize` 时，不要据此断言写入序列完整。改用范围内的
调用点扫描——它不依赖指令流的可达性。

### 2. 相同的字节不等于相同的含义

`0xFFFF` 在 `0x0008` 里已确认是"无目标"哨兵，很容易顺手把本协议的 `0xFFFF` 也这么记。
但 `0x0008` 的结论有客户端范围门（`js` / `cmp 0xFFFF; jge`）作证，本协议一条这样的证据都没有。
所以记录里只写"取值相同"，服务端也不据此做校验——只在日志里标注。
