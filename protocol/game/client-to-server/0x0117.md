# `0x0117` `LAG_STATISTICS`

> 名称取自上游服务端 `CmdPacketType` 枚举
> （`D:\project\86JP` → `Server/DfoServer/Network/Core/PacketTypes.cs`）。
>
> **2026-08-16 更正**：本记录此前写"既没有旧服枚举证据，也不适合给描述性命名"，
> 原因是当时上游源码树不在工作区。官方名对本协议的多态结构是一条**实质线索**：
> 内层条目的 kind 很可能是**延迟统计的种类**，而不是任意异构载荷。这缩小了
> "kind → 载荷布局"表的搜索范围。
>
> 与退出 flush 中相邻的 `0x00C2` `FRAME_LAG_STATISTICS` 同属延迟统计一族，
> 两者一起发出与该命名相符。
>
> **仍为多态信封**：名称不改变"外层无法静态展开"这一结论，见下方 Wire layout。

因此无法解析任意 kind 的帧——不满足"任一真实样本可被无损解释"。

## Wire layout

Game header 见 [Game TCP 帧组织](../../patterns/game-frame.md)。构包器 `RVA 0x01CD5300`
是**形状 B**（writer 由参数 `[ebp+8]` 传入，不自取），见
[game-frame 的两种构包形状](../../patterns/game-frame.md#两种构包形状)。

```text
u8   envelope_tag          ← [this+0x10]，四次样本恒为 0x01
repeat 遍历 this+4 起的链表：
    u8   item_kind         ← [item+0xC]，四次样本恒为 0x06
    <载荷>                 ← item 的虚函数 vtable[+0x1C](writer) 写出，长度由该函数决定
终止条件：链表走完，或 [item+0x15] != 0
```

**没有条目计数字段**，也没有总长度字段：接收方只能靠 `item_kind` 推出每个条目的长度。
这意味着服务端解析本协议**必须**先建立完整的 kind → 长度/布局表，缺一个 kind 就会错位。

### `item_kind = 0x06` 的载荷（四次样本一致的切分）

| Offset（body 内） | Size | Encoding | Meaning | Confidence | Evidence |
|---:|---:|---|---|---|---|
| 0 | 1 | `u8` | `envelope_tag`，实测恒 `0x01` | 位置与宽度 Confirmed；语义未定 | `E-002` |
| 1 | 1 | `u8` | `item_kind`，实测恒 `0x06` | Confirmed | `E-002` |
| 2 | 4 | LE `f32` | 随会话时长增长的量（ms 量级） | 宽度 High；语义未定 | `E-001` |
| 6 | 4 | LE `f32` | 同上，另一个量 | 宽度 High；语义未定 | `E-001` |
| 10 | 2 | LE `u16` | 小整数，四次样本 5 / 6 / 3 / 3 | 位置与宽度 High；语义未定 | `E-001` |

`f32` 宽度只是 High 而非 Confirmed：切分来自四个样本的差分（见下表），
不是来自 kind 6 那个虚函数的反汇编——该函数要经 vtable 取，而 vtable 在 dump 里为零。

## Samples

四次会话，`envelope_tag` 与 `item_kind` 恒定、载荷全变：

| 会话 | body（hex） | f32 a | f32 b | b/a | u16 |
|---|---|---:|---:|---:|---:|
| 2026-08-14 s1（最长） | `0106 A1C98A48 E12A0A49 0500` | 284237.03 | 565934.06 | 1.99 | 5 |
| [2026-08-15 s3](samples/0x0117-2026-08-15-01.hex) | `0106 00DE9D46 9C372847 0600` | 20207.00 | 43063.61 | 2.13 | 6 |
| [2026-08-15 s4](samples/0x0117-2026-08-15-02.hex) | `0106 0170A445 673DA145 0300` | 5262.00 | 5159.68 | 0.98 | 3 |
| [2026-08-15 s5](samples/0x0117-2026-08-15-03.hex) | `0106 AC6AC544 41BF9744 0300` | 1579.33 | 1213.98 | 0.77 | 3 |

- s3 body SHA-256：`B4C3FAB8D1C30207811DE77F51D39734C5F78754A1A7C913322A12560A1EC43C`
- s4 body SHA-256：`BEA6BEE5C4E5C603FDA31E21C68D8D096B1911ABC9AC92226779AF29A2577D2B`
- s5 body SHA-256：`65C10B33F3F89ED6F1C91C0DCF4AD496923DE112D822AAA616B81B2138565B8E`

两个 `f32` 单调地随会话规模变小而变小，四个样本跨了三个数量级
（2.8×10⁵ → 2.0×10⁴ → 5.3×10³ → 1.6×10³），与"累计耗时/累计量"相符。

但**不能**据此断言它们是同一时钟的两个刻度：`b/a` 四次分别是
1.99 / 2.13 / 0.98 / 0.77，跨越 1 的两侧——长会话里 b 约为 a 的两倍，
短会话里 b 反而小于 a。这排除了"b 是 a 的固定倍数"和"b 恒为二者中较大"两种解释。

另外它们**不是整个会话的墙上时长**：s5 那次登录到退出明显超过 1.6 秒。
所以更可能是某个子过程的累计量，而不是会话计时。

`u16` 四次为 5 / 6 / 3 / 3，与两个 `f32` 的大小**不单调相关**（s3 最大的 6 出现在中间量级），
因此它不像是从同一量派生的。

### 构包器反汇编要点（`RVA 0x01CD5300`）

```asm
0x01CD5309  mov   esi, ecx                  ; this
0x01CD5310  mov   ebx, [ebp+8]              ; writer 由参数传入（形状 B）
0x01CD5313  push  0x117
0x01CD531A  call  MakeHeader
0x01CD531F  movzx eax, byte [esi+0x10]
0x01CD5326  call  WriteU8                   ; envelope_tag
0x01CD532B  add   esi, 4                    ; 链表头
loop:
0x01CD5346  call  0x010CAD00                ; 取下一个节点
0x01CD5367  cmp   esi, [eax+8]
0x01CD536A  je    finalize                  ; 走完 → 收尾
0x01CD537B  movzx eax, byte [esi+0xC]
0x01CD5382  call  WriteU8                   ; item_kind
0x01CD5392  mov   ecx, [esi+0x10]           ; 条目对象
0x01CD5395  mov   edx, [ecx]                ; vtable
0x01CD5397  mov   eax, [edx+0x1C]
0x01CD539A  push  ebx                       ; writer
0x01CD539B  call  eax                       ; ← 载荷由虚函数写出
0x01CD53A2  cmp   byte [esi+0x15], 0
0x01CD53A6  jne   finalize                  ; 条目自带的提前终止标志
0x01CD53AB  call  0x0014D0A0                ; 迭代器前进
0x01CD53B3  jmp   loop
finalize:
0x01CD53BA  call  Finalize
```

**长度算术在这里不闭合，而且这是正确的**：直线宽度只有 2 字节，其余 10 字节由虚函数写出。
本记录因此是"长度闭合"这条判据的边界情形——闭合失败不一定意味着读漏了分支，
也可能意味着**布局根本不是静态的**。判别方法：看是否存在经 vtable 的间接 `call`。

## 逆向工作日志

### 1. 单样本读法给出的"布局"是错的

本 type 早先在协议清单里记的是
"`01 06 A1C98A48 E12A0A49 0500`，含两个疑似时间戳/浮点的 4 字节量"——把**一个实例**当成了
布局。2026-08-15 陆续拿到第二至第四个样本后才看出前两字节恒定、后十字节全变，
反汇编随即证明后十字节根本不属于本构包器，而是虚函数写的。

**教训**：只有一个样本时，"看起来像浮点的 4 字节"这类判断不能进记录；
差分至少需要两个样本，而结构判断必须来自构包器本身。

### 2. 长度不闭合这次是正确结果

前三条协议（`0x00AB`/`0x01DD`/`0x00C2`）都靠"`WriteXX` 宽度之和 = 实测 body 长度"收尾，
本条第一次遇到闭合失败：直线只有 2 字节，实测 12 字节。
起初怀疑是漏读了分支，实际是遇到了多态载荷。已把这一判别写进
[game-frame](../../patterns/game-frame.md) 与本记录上方。

### 3. 普查是怎么找到它的

本构包器不是靠调用栈找到的。它的 `MakeHeader` 调用点 `0x01CD531A` 在早期版本的普查里
**被漏掉**，因为那版要求 `call GetWriter / mov ecx,eax / call MakeHeader` 这个尾部形状，
而本构包器的 writer 是参数传入的。把锚点改成只认 `MakeHeader` 之后它才出现——
也正是它暴露了"存在第二种构包形状"这件事。
