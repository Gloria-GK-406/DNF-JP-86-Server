### 客户端等的是「有没有回」，不是「回了什么」

构包点 `0x021EE7DE`（RVA）：条件是 `[esi+0x658] == 0`，写完 header 就收尾，**body 0 字节**。

应答 handler `0x00D0E410`（RVA）的整个调用图里**没有任何取字段原语调用**——`ReadU8` /
`ReadU16` / `ReadU32` / `ReadBytes` 一个都没有。它一进来就去查一串与本局有关的条件，然后二选一：

```text
条件全满足 → [0x3A5C9B8]->[0x8FA0] 上一个虚调用(1)，随即构包 CMD 0x0046（0 字节）发出去
否则       → [0x3A5C9B8]->[0x8F68] 上调用(2)
```

`0x0046` 的构包点就在 `0x00D0E4D1`，即本 handler 内部——这是
[`0x0046 CARD_SELECT_RIGHT_STATE`](0x0046.md) 与 [`0x0047 SELECT_CARD`](0x0047.md) 那条翻牌链
的起点。

**所以 handler 不读 body。但首字节仍然是必需的**：CMD 结果的第一个字节是接收路径在派发之前
读掉的成功标志，回 `00` 或回空体不是「一帧 handler 会忽略的应答」，而是一次失败结果——它根本
到不了上面那个 handler，此后每一帧还会静默错开。本仓发一个字节 `0x01`。

### 应答确认与牌面计时由同一结算状态机协调

上游 `HandleCardStartRequest` 收到本帧后调 `SendLayoutAsync`，一次发**两帧**：

```text
SEND cmd=0x01 type=0x0045 len=16 body=(1B)  [01]
SEND cmd=0x01 type=0x0046 len=32 body=(17B) [01 01 00 FF FF FF FF FF FF FF FF FF FF FF FF FF FF]
```

第二帧是[翻牌面板的版式](0x0046.md)。当前实现不再把它硬编码为本请求的第二帧：参与者结算
成功后注册 2 秒 layout timer；若客户端先发来 `0x0046`，同一个 presentation coordinator 会立即
打开牌面并使旧 layout timer 失效。本帧本身始终只回成功 ACK。这样“自动计时”和“客户端主动
进入牌面”不会成为两个真源，二者都提交同一个参与者 `CardLayoutOpen` 状态。

一次完整通关的上游抓包（`packet_log.upstream-killexp-20260827.txt` 第 748 行起）里，这两帧的
位置比本帧更早：服务端的自动翻牌计时器先把版式推了出去，客户端稍后发来的本帧因此落在
`SettlementState != ResultShown` 上、**没有得到应答**。所以「上游不答本帧」这个观察是那次计时器
抢先的结果，不是本帧不需要应答——它的处理器就在 `d[0x0045]` 上。

同一段抓包还给出了本帧之后整条收尾链，包括**离开副本走的是 [`CMD 0x0048 EPLP_COMMAND`](0x0048.md)
而不是 `GIVEUP_GAME`**，随后服务端主动推 `NOTI 0x0003 / 0x0017 / 0x0018 / 0x00CA / 0x0002`。
