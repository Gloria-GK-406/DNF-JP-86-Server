# 协议逆向与双向验证方法

目标是快速得到可运行实现，同时不把猜测伪装成协议事实。

## 0. 先查它已有的文档

Game 端点静态可见的每一条协议**都已经有一篇文档**，见
[全量索引](game/index.md)。开工前先打开它——多半已经能拿到：官方名、族归属、
构包点或 handler 入口、body 字段序列与宽度，有时还有来自上游实现的字段含义。

这改变了下面几步的性质：**不再是"从零逆向"，而是"验证并补全一份初稿"**。
具体地：

- 第 1 步的身份四要素、第 2 步的构包点定位，通常已经在文档里，直接核对即可；
- 真正要做的是把 `unknown` 逐个换成有证据的结论，以及确认响应流程；
- 文档标为「结构未知」的部分，说明静态分析已经走到头了，**不要再往那个方向投入**，
  直接上运行时手段（断点、真实样本）。

改字段含义请改 [`patterns/data/meanings/*.tsv`](patterns/data/) 而不是文档的机器区——
机器区每次重新生成都会覆盖，分片则是生成器的输入，会被带上。机器区之外的一切都是人工领地。

## 1. 建立观察身份

先记录：

- endpoint；
- direction；
- command；
- type；
- body 长度；
- 前后消息和触发场景；
- 客户端是否等待、重试、断开或继续前进。

先据此把消息分为：

- **Report**：客户端上报，通常无响应；
- **Query**：读取服务器状态并期待响应；
- **Mutation**：改变业务状态并返回结果；
- **Session side effect**：修改连接/会话状态，可能无响应；
- **Notification**：服务器主动通知客户端。

分类是工作结论，最终仍需客户端代码或运行行为证明。

## 2. 逆向客户端构包/解包

对客户端发送消息：

1. 在明文 `Cipher::Encrypt` 入口按 command/type 过滤。
2. 捕获完整 header/body、线程和调用栈，并将地址归一化为 DNF RVA。
3. 从 `MakePacket` 调用者和动态调用栈的交集定位业务构包函数。
4. 记录每次 `ISocket::Write` 的 caller RVA、写入长度和字节。
5. 沿写入值向上追踪到游戏对象字段、Windows API、PVF 数据或计算公式。

对服务器发送消息，**不能**照抄上面的方法：调用栈对入站帧不含 per-type 信息，而 body 解析
路径进入了被混淆的保护区。走 handler 注册表普查，见
[patterns/game-receive.md](patterns/game-receive.md)。

**要字段布局就用运行时读取跟踪**。静态走图在 S→C 上普遍止步于打包区，产出的是下界；
读取跟踪直接测客户端自己的每一次入站读取，打包区挡不住它。跑一次游戏就能闭合一批协议的
边界，再用 `patterns/data/trace-to-docs.py` 写进各文档人工区。

**证据的种类、效力顺序、引用怎么写、错了怎么处理，全部在 [evidence.md](evidence.md)。**
那一页是判决规则：冲突时谁赢、什么该删、什么该留。本页只讲工作顺序。

### 先翻客户端自己的日志文件

在动手反汇编之前，**先看客户端往自己目录里写了什么明文日志**。这是最便宜的证据，而且
往往直接给出**客户端自带的字段名**——比我们的描述性命名可靠得多。

`0x00C2` 就是这样定下三个字段的：`LagLog.txt` 在退出时把同一批统计量按 wire 顺序打成明文，
`DIRECTX VERSION` / `START_LOADING` / `RETURN_VILLAGE` 直接对上了原先只能叫 `off15`/`off20`/
`off22` 的三个量，还顺带独立确认了内存归一化（它把 `原始 (归一化)` 两个值一起打出来）。

用法要点：

- **必须对齐会话**。只有和抓包样本来自同一次运行的那条日志才能逐字段对账。
- **位置对应不等于同一个量**。同一次对账里 `TING` 与 `off19` 位置吻合但取值不一致
  （8 对 6），因此 `off19` 至今不命名。名字要靠"位置 + 取值 + 来源"三项一致才能定。
- 日志里可能有 wire 上没有的字段（`CPUVender`），反之亦然（`off19`）。数量对不上是正常的。

反汇编记录的要求（客户端哈希、RVA 而非绝对地址、够支撑结论的指令）见
[evidence.md 的引用怎么写](evidence.md#引用怎么写)。

## 2.5 跨版本换号：表只给假设，抓包才能定论

**2026-08-24 增补，代价是四处改错。**

A21 相对 A12 在两处插入了条目（NOTI 在 `0x0294`、CMD 在 `0x02D4`），插入点之上的编号整体位移。
很自然会想到：把我们已实现的协议按名字在 A21 表里查一遍，位移点之上的全部改号。

**这样推出来的结论有一半是错的。** 实际做了八处，抓包判掉四处：

| 推出来的新号 | 参照会话实际用的号 | 判据 |
|---|---|---|
| `0x033F` | `0x02D5` | 两边都是 3×16 字节 |
| `0x039B` | `0x0331` | 两边都是 1 字节 |
| `0x03EB` | `0x0381` | 两边都是 2×8 字节 |
| `0x0442` | `0x03D8` | 两边都是 **204 个零，逐字节相同** |

204 个零逐字节相同不可能是巧合。真相是：**那些载荷当年就是照同一份抓包在这些号上抄下来的**，
号一直是对的，错的只是我们按 A12 表给它起的名字（A21 管它们叫 `ACCOUNT_TUTORIAL_INFO`、
`LIMIT_IPGNO`、`USER_BUY_RESTRICT_UPDATE_ITEM_LIST`、`COUPLE_ROOM`）。

规矩：

- 换号**必须**有该版本的抓包作证，位移推理只能立假设；
- 两者冲突时**以抓包为准**，不要反过来怀疑抓包；
- 一条协议在我们代码里的**名字**和它在线上的**号**是两件事。名字错了只是可读性问题，
  按错的名字去改号才会把本来正确的线上行为改坏；
- 判定用**载荷形状**（条数、长度、字节内容）比用名字可靠得多。

## 3. 用网络样本验证

客户端逆向给出结构，服务端诊断日志验证最终 wire 结果：

- 同一环境重复运行，确认稳定字段；
- 不同环境或不同业务状态做差分，确认可变字段；
- 检查总长度、checksum、sequence 和 body；
- 验证前后消息顺序及客户端是否等待响应。

抓包差分用于反证和补充分支，不代替构包代码证据。

## 4. 映射到服务端边界

- Networking 只做 frame/body 与 typed message 的转换。
- Application handler 决定消费方式和业务协调。
- 领域服务只接收已确认的业务语义。
- 未确认字段以 offset/width 命名，不扩散成领域概念。
- Report 且无业务用途时可以被 typed handler 消费并丢弃；不要制造 ACK。
- 响应必须有客户端 reader 或旧服务/实机行为证据，不能试探性补零。

## 5. 验证实现

每条协议至少保留：

1. 真实向量 parser/codec 测试；
2. 截断、超长、非法枚举等边界测试；
3. 条件分支或重复项测试；
4. `Encode(Decode(body)) == body`，仅在协议本身双向对称或作为测试辅助时使用；
5. 响应数量和顺序测试；
6. 实机客户端可观察结果。

## 6. 更新资料库

实现不是终点，但**每一层各收各的东西**：

| 内容 | 去处 |
|---|---|
| 这些字节是什么、凭什么这么说 | 该协议的文档（`game/**/*.md` 人工区） |
| 协议怎么被编排成一个有业务语义的流程 | `patterns/flow-*.md` / `patterns/world-entry.md` |
| 跨全部协议的包结构不变量 | `patterns/game-frame.md` / `patterns/game-receive.md` |
| 证据的种类与判决规则 | [evidence.md](evidence.md) |
| 我们服务端的领域设计（建什么表、怎么算） | 仓库根 `Docs/`；协议文档只放链接 |
| 业务设定的数值与规则 | **不记录**——那是游戏设定，不是逆向发现 |

**带着证据改。** 这样证据入库是更新的副作用，而不是一件需要另外记得去做的事；
只改结论不给证据，等于把一个新猜测放进一个看起来已经验证过的位置。

### 6.1 用当前实现发现遗漏，不用当前实现裁决协议

服务端接入面是很有价值的**覆盖探针**：它能暴露“decoder/encoder 已存在，但 catalog 或协议页
没有跟上”的漂移。仓库根可运行：

```powershell
python protocol/patterns/data/check-server-documentation-sync.py --repo-root .
```

检查通过只说明每个当前注册的 C→S decoder 与 encoder-backed S→C identity 都能在资料库中
找到。它不把实现提升为 Confirmed，更不自动授予 ClientVerified。发现代码与文档不一致时，
应分别核对：A21 构包/解包指令、线级帧、真实客户端可观察行为、当前实现与测试。前三者没有
闭合时，页面必须保留 Unknown/High 或“实现服务端功能”的边界。

机器区若已被更强 A21 证据推翻，应优先修正生成输入或生成逻辑再重建；只有静态普查无法表示、
但身份与布局已经有直接证据的例外，才使用生成器明确登记的手写页机制。不要靠人工覆盖一份
仍会持续产出错误结论的生成源。

协议文档**不回答**"什么时候触发""响应顺序如何"——那是流程层的问题。
